# AGENTS.md: how we build Seon

Seon is where agents do real work for their user, each in its own process on its own branch. The good changes merge into one program that gets smaller, faster and more certain as it grows. This file is for every Claude session and every Seon agent alike. It holds the rules; the wiki (`docs/`) holds how the system works. When a rule changes, this file is edited in place: a new rule replaces an old one, and the file does not grow. The owner's rulings, with his words, are in [decisions](docs/decisions.md).

## 0. Start here

You are in `next/`: **Seon on Jolt, built to replace Seon** (`~/src/seon` is the JVM version, read-only). A v1 capability left out has its reason in `BAGGAGE.md`.

**Read before acting, every time:** [principles](docs/principles.md) first and whole (what Seon is for, how designs are chosen, when to raise the alarm), then this file, `docs/plan.md` (what is in flight), `docs/README.md` (the wiki's map), then your task (`resources/seon/tasks/<ns>.edn`) and what its plan cites. **Every helper or subagent you start is told to read [principles](docs/principles.md) first**, and its brief says how its piece fits the whole, so no research or build happens from a fragment of the picture.

**Find a detail** in `docs/README.md`, then through `seon_context` (§6), then with ``git grep -n 'term' -- docs resources/seon/tasks src``. A `bin/` script's header comment is its manual.

**The running system:** `bin/system status` (server port 7888, dashboard http://127.0.0.1:7777/). The standing system and its store (`runs/store`) are for use: agents work and merge there, and sessions reach it through the MCP tools (§6). Once a system is up, its store is the source of truth ([files and the db](docs/source.md#files-and-the-db-two-directions)), and **everything we keep also reaches git**, in the files the system imports from, so a store can be wiped or rebuilt without loss.

**What we keep, and its file:** code and tests (`src/`, `test/`), the wiki (`docs/`), tasks (`resources/seon/tasks/<owning-ns>.edn`), schemas (`resources/seon/schemas/`), config (`resources/seon/config/`), `bin/` scripts. Nothing else is kept: scratch namespaces, `runs/`, `target/` and test data are not, and a test never writes on the standing store's main.

**How it gets there, by where you work:**
| You work as | Your change lives on | It reaches git by |
|---|---|---|
| A Seon agent | your task's branch in the store | its merge into main (`seon_done`), then the write-back of main's changed files |
| A Claude session, today | its one worktree's branch `jolt/<name>` (§3) | `bin/land`, which merges it into main |
| A Claude session, once Stage 1's safety list is on main | its Seon agent's branch (`seon_attach`, then `seon_eval` and `seon.repl/edit!`), as a Seon agent's | the same: `seon_done`, then the write-back |
| Anyone writing on main directly (`seon_create`, `my.task/update!` on main) | main in the store | nothing yet: write the same entry into its file on your branch, in the same session |

**Work from inside the runtime; Claude sessions are not special** (owner, 2026-11-14: "All solutions must be seon centric from now on ... The db is the source of truth and it is to be queried for truth not reading git for a secondary truth ... No more solutions outside of it"; "Claude agents are not special, they need to fit into this system"; 2026-11-15: "The mindset must be that we are transitioning away from claude agents being focused on building infrastructure that only works from the outside. The view of the system from the runtime should be the focus and seon agents working inside the system itself and claude agents using the internal systems via mcp repl and thin wrapper scripts"). Seon agents work inside the system; a Claude session uses the same insides, through the MCP REPL and thin wrappers. How to work:
1. **Look from the runtime first.** A question about the system (what is on main, what a task holds, why a test is red, what a process waits on) is a form evaluated at the standing system (`seon_eval`, at root or your agent), on the store, the program index and the live procs' state. Files, git, logs and `ps` are what the system writes out; read them only for what it cannot show yet, and file that gap as a task in its owner's namespace.
2. **Change code inside.** Evaluate the definition at your agent's REPL (`seon_eval`, `seon.repl/edit!`); a file you edit is imported onto your agent's branch by the hook (`bin/seon-import`, `my.branch/import!`). The runtime tracks main by evaluating each merge in place; a new binary is needed only for a build input (a pin, native code, `deps.edn`). Today that is a stop and start (`bin/system next`) that ends the agents and flights in flight; a switch-over that loses nothing is owed (runtime, deps).
3. **Prove and merge inside:** the test service by reach (`seon_prove`), then `seon_done`, which merges a branch with no conflict and its reached tests green into main with no release; git follows the store through the write-back.
4. **A script is a thin wrapper over an op** (`bin/mcp call OP KEY=VALUE`): it carries no logic, state or decision of its own; the logic lives in a namespace the runtime loads. Nothing new is built outside: no shell loop, watchdog, file format, checker or worktree tooling. When the inside cannot do something, making it do so is the task, never a tool beside it, and a design that starts outside is refused and named to the owner at once.
5. **Until the Stage 1 safety list is on main** (proving as Flow, every wait ending, updates that lose nothing in flight), sessions land through `bin/land` (the table's "today" row). It and `bin/check`, `bin/jolt-gates`, `bin/test` and the worktrees are frozen: nothing more is built on them, and each is deleted as the inside path replaces it. Your work in that time is the inside path, built and proved at the REPL.

**The rule:** a change you mean to keep is on a branch that will merge, with its file, before you end your turn. Until a task created in the store is written to its file by the system (`seon.source/a-task-changed-in-the-db-is-written-back-to-its-file`), that last row is yours to do by hand. The store is erased only while it holds nothing that is not in git; ask root before any erase.

## 1. What Seon is for, and what moving forward means

**Seon does any work its user wants,** improving its own code included. It grows by accretion while resisting growth: agents reuse and improve the core instead of writing one-offs.

**Moving forward means the loop works for real tasks, end to end:**
1. a user's request becomes tasks;
2. an agent works each task from context good enough to finish it in a few turns;
3. its proofs go green, its branch merges to main, and main runs the result.

**The number one metric is the turns it takes an agent to go from a roughly specified task to completed, merged code** (owner, 2026-11-13; [decisions](docs/decisions.md#the-number-one-metric-turns-from-a-roughly-specified-task-to-merged-code)). It is measured on rounds of 2 or 3 backlog tasks drawn at random, worked by agents in parallel on their own branches and iterated on until each is done, learning from what the group shares (randomness keeps us from teaching to the test); Claude sessions curate the backlog as they go, rewriting bad tasks and deleting superseded ones; a good solution merges to disk and to main and its task is done, and Claude sessions review every agent's change until the system's own review is shown trustworthy. A task that never merges is a failure, not a low count. Work is ranked by the turns it removes from that path, with every v1 capability present ([parity](docs/parity.md)); work that removes none, or unblocks no step of THE PLAN (`docs/plan.md`), waits. A count of landings is never a measure of progress. Before building, look at what is built.

Run, then right, then fast. If you can't show it running, it isn't done.

## 2. Who does what

- **The owner (Sean)** sets direction and makes the rulings. He talks to the managing session, root, which manages the others.
- **Area sessions** each own an area and know all of it: context, web, runtime, tests, deps, data and flow (Jolt's Flow, Seon's use of it, and the review of every design that waits), each named once for its title, its branch `jolt/<name>` and its worktree ([sessions](docs/sessions.md#sessions-own-their-areas)). A session never answers for code it has not read.
- **Root** keeps the schedule, reads each landed diff and brings the owner his decisions ([the managing session](docs/sessions.md#the-managing-session)). A session asks root before it asks the owner.
- **No fan-out.** A session starts no other session unless the owner asks. It may use helpers: each gets a well-specified piece in the session's one worktree, on files nobody else is editing, commits there and stops; a helper may rerun the one test it works on (`bin/test ns/name`) in that worktree, and runs no suite, `bin/prove` or `bin/land`; its session proves the whole once for all of them (owner, 2026-11-12: "no separate worktrees and separate test suite runs"; "Agents working on one test can re-run their one test in the same worktree"). The session reviews every line a helper writes. Since 2026-11-12 every session and helper runs on Opus or Sonnet, never Fable without the owner's yes.
- **Work that blocks another area is a task, not a conversation** ([the plan](docs/plan.md#stage-1-claude-sessions-work-through-the-system-the-priority)): file it in the owning area's namespace with its evidence, and name it in your task's `:seon.task/needs`. A message goes to the owning session only to block, unblock or agree an interface, in 6 lines or fewer, with no acknowledgements (owner, 2026-11-13; it replaces "talk to root only"). Its evidence, and any decision, ownership move or interface agreed in it, goes into the task it concerns (its plan, or a task filed in the owner's namespace) when it is made: a message, a note or a memory file is lost at a reset (principles §4), and on the night of 2026-11-14 three ownership moves and four agreed interfaces lived only in messages. Root brings the owner his decisions and keeps the work moving by feedback, not by clock (owner, 2026-11-15: "Remove all of your time estimates it will just slow agents down. I want a much faster velocity and dynamic timing and updates based on feedback and learning"): no item carries a time estimate; root reads what lands, what rounds lose and what each session last did, and a session with no progress to show, or on a repeated wrong turn, has its transcript read and is corrected; past that, it writes its state and a fresh one starts with an audit brief (owner, 2026-11-14). A cost estimate (n, big-O, ticks, bytes: §3a) is design, not schedule, and stays.
- **Write in Clojure's, its libraries', Jolt's and git's words** (§7a), to the owner above all. A name we made up is explained or replaced before it is sent.
- **Seon agents** work tasks through the server (§6). What a session finds missing from their context is a task for Seon.

## 3. How work moves

**Work is tasks** ([tasks](docs/tasks.md)): an entry in `resources/seon/tasks/<owning-ns>.edn` with `:seon.task/plan`, `:seon.task/proofs` (the tests that say it is done) and `:seon.task/needs`. **A plan delivers three things before any code** (owner, 2026-11-15: "What existing mechanism does this has to be delievered as part of the plan along with the ideal algorithmic estimates (which it should cost) and what they measured"):
1. **Prior work, searched, and the existing mechanism that does this job** (owner, 2026-11-15: "All agents must start all work looking for the existing or previous solutions. They must report that they searched and found no prior work if none is quoted"): the plan opens `PRIOR WORK:`, with what was searched (forms over the program index, `my.agent/grep`, `git log --grep`, the wiki section, the tasks) and what was found, quoted with file:line, or "searched <these>; none found". The change extends, fixes or deletes onto the mechanism it names (Seon's, a library's or Jolt's); a plan that builds beside it, outside Seon, or without the search is refused unread. A second miss is an external audit of the session's transcript, the docs that misled it fixed, and a fresh session in its place ("An agent that stops following instructions we need to find out why with an external audit, clean up the documentation and start fresh");
2. **The ideal cost, worked out as arithmetic:** n, big-O, ticks and bytes, the lower bound the design is held to (§3a);
3. **What was measured,** at the REPL on real data: today's cost of the job, and later the new code's, beside the estimate.
The plan also gives the cause, and what the change replaces and deletes. It is written before anything is built, and its owner's lead reads it before the build starts (owner, 2026-11-12: "The broken ones mean we don't have clear research or plans in place. Do more forward planning"). A plan names every path that runs the change: `bin/land`, `bin/prove`, the prove service, agents on the standing system, test children, worktree systems, `bin/update`. A change to shared machinery (the `bin/` scripts, the prove service, a pin, the api or fork server, a key, schema or config entry other areas read) is run end to end through each of those paths before anything relies on it. A cause is named only after both ends of its code path are read. Order: delete first, then foundations, then fixes. Growth is held by finding duplication, first in the data model (two shapes or schemas for one thing), then in processing it (two walks, imports or merges over one shape), and fixing both so each thing is processed once, done well (owner, 2026-11-14: "I am not going to set arbitrary amounts"); a plan names the duplicate it removes. A problem outside your task is filed as a task, never fixed in passing.

**The method:**
1. **Learn.** List what exists before designing. Ask what the ordinary Clojure (or library) way is, and why ours is it or is not. Read good Clojure code: check out any library worth reading into `reference-code/` without asking (owner, 2026-11-14: "I strongly encourage always reading good clojure code as it helps correct mistakes we make in our own code").
2. **Estimate before you build** (§3a), algorithmically, and reject an inefficient design before writing it; then pick the balance of simple to express and to get right: 90% of the efficiency for 10% of the effort, in less and simpler code, beats 100% (owner, 2026-11-14). Work out from what has to be done what the work should cost: n, its big-O, the ticks, bytes and seconds expected. Write the estimate into the plan, and into every new test as its budget. Never take the estimate from the last run: it is the lower bound as arithmetic, and a cost proof carries no waiver (owner, 2026-11-14: "How can they have no idea what the bounds are?"; 2026-11-15: "I do want to remove all the waivers and to either own the limits and tweak them until they work or remove them if we can't reliably measure them"): each `:overrun` goes once ticks are a test's own work; a proof named for what moved declares the growth of what moved. **Measured over 10 times the estimate stops the work:** the gap is the finding, and its cause is found before anything else. An estimate found wrong is corrected, with the reason it was wrong said in the change (the work it missed, not just the number), and the cost behind the gap is filed for its owner when it is waste. A good change is never held back by an estimate (owner, 2026-11-12: "if our estimate is found to be wrong we adjust it and don't hold back good solutions"). A slow test is a bug.
3. **Prove first,** at the REPL as an agent would, on real data and at n ≤ 100. A data shape others will read is tried at a REPL with the forms its readers will write, and its name is settled once before any code. A proof is seen red first.
4. **Act:** the simplest code that passes, at the cause, in the owner of the bad value. **A bug is a class:** find what allowed it, change that so the class cannot recur, and sweep for its siblings. No special case, retry, guard or hand-kept list. **Fences, guards, locks, waits, timers and atoms are likely bugs:** anything stateful that runs is a Flow agent or proc wired into the system (channels, a REPL, errors as data, the topology), its state is that proc's, coordination is channels, and everything else is an immutable value; an atom is a proc not yet made ([flow](docs/flow.md#the-step-fn-contract-every-proc-follows)).
5. **Work it as a Seon agent would,** from inside the runtime (§0, §6). A change to what the owner sees is checked in a browser.

**One branch per session, landed often** ([merging](docs/merging.md#a-branch-lands-with-binland)):
1. **Each session has one worktree and one branch,** `jolt/<session>` (`bin/worktree NAME`), and works all its items there together: build, iterate and test them as one, and merge main in often so nothing waits (owner, 2026-11-12: "they work on multiple things at once ... and it gets merged with main regularly so it isn't a bottleneck"). No other branch or worktree, ever: not per change, per fix, per helper, per experiment, per bisect or per landing (owner, 2026-11-12: "I will not allow us to create hundreds of tiny change branches all queued up to run the same tests over and over again for tiny bullshit. It's the same agent working on the same files it can build and debug several solutions in the same branch"). A second branch needs the owner's yes. The main tree stays on main and clean. Worktrees are temporary: sessions move onto branches of the one system ([plan](docs/plan.md#stage-1-claude-sessions-work-through-the-system-the-priority)).
2. When the branch holds something worth landing, merge main into it and run `nice -n 15 bin/prove`. It runs everything the change reaches and reuses every green stored at its digest; it is never a hand-picked set of namespaces. `bin/prove` and `bin/land` still prove on the local path (`bin/test`'s parallel test processes), outside the effects owner's admission (`bin/prove` header), so nothing caps them: three lands at once took load to 57 on 18 cores [M, 2026-11-14]. Until proving goes through the effects owner ([plan](docs/plan.md#the-order-of-work-now), item 2), no prove or land starts while the 1-minute load is over 18, and that holds the `bin/prove` a session runs before its land as much as the land. The check is each session's own, so it admits a herd: at 06:43 on 2026-11-15 three lands and a prove passed it within 50 s and load reached 62 [M]; only admission by one owner ends that.
3. Green: land it (step 4) with a landing message of 10 lines or fewer. It gives the step of THE PLAN, what the change deletes, the `src` delta, the estimate beside the measured number, and what allowed the bug. A docs-and-tasks change is proved by what it reaches, like any change: every test that reads the changed docs reruns, and none that doesn't ([what a test takes](docs/source.md#tests-run-by-reach)).
4. **A session lands when green, with no release** (owner, 2026-11-14: "No more ... waiting hours with them queued up so nothing is merging. Agents are to figure shit out on their own and ideally self merge"). `bin/land --check -F MSGFILE` (ending `LAND CHECK OK <branch> <tip> on main <sha>`) is optional, the land exactly with main unmoved. Before a landing or a long run, a session brings its resume note up to date. The session lands with `bin/land -F MSGFILE`; `bin/land` merges main, proves what moved, moves main atomically and brings the standing system up to date through `bin/update`. Root reads each landed diff within the hour and files what it finds. Branches of different sessions are never batched into one landing. One hold remains until it is a fact the system reads: while a watched `seon_done` runs, root holds lands that restart root or load code its path uses (pins, config, the reconciler, the merge, the agent) and tells their owners when it lifts ([the managing session](docs/sessions.md#the-managing-session)).
**The fast lane, `bin/land --fast`, is how every session lands until the one queue lands** (owner, 2026-11-15: "pick and implement the best ideas even if it means we are not doing full runs ... I'm willing to suffer short term confusion of not know what agent to blame if shit goes sideways"): a session merges main into its branch, runs `bin/laws` and `bin/check health`, then in the background runs by name only the tests the system's reach names for the vars its change moved, and its last land's reds (`bin/test ns/name ...`), never a full suite; the reach comes from the program, never a grep, which misses most of it (flow, 2026-11-15: 38 by grep against 284 by reach), at root's REPL: `(let [db @(:conn sys) [_ in] (seon.agent/test-inputs db) g (seon.agent/branch-graph db nil in)] (into (sorted-set) (mapcat #(seon.program/tests-reaching g %)) '[ns/changed-var]))` (1.3 s and 1.4 GB for the graph once, then 3 ms a var); green, the session lands itself with `bin/land --fast NAMESFILE -F MSGFILE` (the file holds the test names): `bin/land` merges main, builds, runs health and the laws, runs those tests in place of its full prove, then swaps main atomically, bridges the change into root's main and updates root in place; no one merges by hand. The merge message, 10 lines or fewer, gives for each function it adds or changes on a hot path the estimate worked out before the code (n, big-O, ticks, bytes) beside the measured number, and the lower bound the design was held to; root reads every landed message and sends back one that lacks them or is past 10x, and a plan, before any code, must first name the existing Seon mechanism it extends and run inside Seon (an op or a namespace function, at most a thin `bin/` wrapper over it) (owner, 2026-11-15: "Make sure that agents are designing seon centric designs. I just corrected tests who was rebuilding half the code we've already written in a shell script"; "I'm not seeing algorithmic estimates being done and agents catching bad design decisions early before deployment"). A red on main afterwards is fixed forward by its owner at once. **After each act, check its outcome, not the intent** (owner, 2026-11-15: "What can we do to imrpove our instructions and your ability to catch things"): after a land, read its last lines (`LANDED`; `UPDATE OK: kept running`, never `restart:` but for a pin); before holding or waiting on something, see it exist (`ps`, its log, the session's events); before a commit, check no land of yours proves from that worktree; before sending a number, sha or time, read it (`git`, `date`, the log); before any code, the plan's three parts and its existing Seon mechanism. Steps 2 to 4 above describe `bin/land`'s full prove, which waits for the queue.
5. Never wait on a landing, and never touch the worktree it proves: `bin/land` proves the worktree's files as they stand and fails if the branch moves during its proof, so until it ends nothing there is edited or committed (two of runtime-2's lands went red this way on 2026-11-15, at 02:10 and 06:26). Meanwhile read, review or work at a REPL; never in a new branch.

- **A change lands with what uses it.** A capability comes in the tip of its first caller, or with the deletion it makes possible. A docs change and a pure deletion land alone.
- **A merge that completes a task** removes the task's entry and says `Completes: ns/name`.
- **No regressions:** a number that got worse is refused unless the message names its reason and who follows it up.
- **Never delete or move a red verdict:** the fix is a new digest ([merging](docs/merging.md#verdicts-are-a-cache)). A flaky result is a defect to fix at its cause.
- **A fix deletes the other implementations** (owner, 2026-11-14: "Find fixes and you must delete the other implementations. This is how our code base shrinks and we get better code and faster and more correct code"): every implementation of the same job goes in the same landing, code, tasks and wiki text, and the landing message's `Deletes:` line names each. **No change removes functionality** (owner, 2026-11-14: "You are not to remove any functionality through these changes. The goal is make all of our dependencies clearly defined with data and validated. Not to break the system"): every `Deletes:` line says, for each item, what now does its job. A fix deletes duplicate mechanisms, never a feature or a knob: a knob the owner uses becomes a spec'd config entry the one mechanism reads (owner, 2026-11-14: "I'm not saying delete features. I'm saying make them explicit"), and any key or feature removed is listed to root before it goes. Root reads each landed diff against that line and files what was left.
- **A dependency pin** is proved whole on its own branch before it is handed over ([merging](docs/merging.md#conflicts-and-pins)).
- **Before a compaction,** a session sends its parent a few lines: what it finished, what cost it time, and what change to a script, check or this file would have saved that time. It then makes each fact it learned true where that fact lives (the wiki section, the task, the docstring), and removes the entries it completed.

**The gate, before any new process (a mechanism, proc, script, service or workflow), format, key, layer, namespace or rule** (owner, 2026-11-14, standing for every agent: "Do not create any new processes until you have verified we don't have an existing solution that needs to updated or deleted by this implementation"); its plan names the existing solution it updates or deletes: (1) which existing mechanism does this, whether ours, v1's or a dependency's? (2) what did v1 do? (3) what is the field's best known way? (4) why can't the existing one do it? A new key is fully namespace-qualified and has a schema entry.

## 3a. Design to the lower bound

The owner, 2026-11-12: "We are never to design systems that are so inefficient again." Every slow design found that day broke one of these rules: a suite rerun 52 times a day, a docs edit rerunning 280 tests, a fresh system booted for every test, a store reseeded in every fork, a file re-analyzed whole for one changed form, a schema registry recompiled whole, a pull of every attribute, a 4e9-tick floor. Each is checked before a design is built, and again when its cost is measured.

1. **Work the lower bound out first, as arithmetic.** It is the least work the job can be done in: n, the work per item, and the constants in [cost](docs/cost.md#what-things-cost-here) (a fork, a seek, a test, a boot). The design's estimate is held to it, and 10x over stops the work (§3).
2. **Proportional to what changed, never to the whole.** A change of size d costs O(d), not O(N): tests rerun by what they read, a catch-up analyzes the changed forms, a registry recompiles the changed schemas and their dependents, a diff skips shared structure, a plan touches only the keys whose inputs moved.
3. **Done once, kept with its source.** A derived value is computed once, from immutable inputs, and kept with them or reused by their digest. Nothing is recomputed per call, per fork or per process: not a store seed, a compiled pattern, a config read or a file parse.
4. **Warm, not cold.** Never start a process or boot a system to do what a fork of a running one does in milliseconds; never rebuild what a cache keyed by content holds.
5. **Take exactly what is needed, in the shape it is needed.** A pull names the attributes and joins its reader uses: the pattern is the shape of the data, and every agent's context is made by one, so a pattern is never replaced by `*`. Seek an index, never scan it; read a file once; fetch the part, never the whole. Where a library makes the named read cost more than it should (a Datahike named pull seeks once per attribute), the library is fixed and measured.
6. **Waiting is not working.** Wall time far above CPU time means something waits. Find the waiter: a bound, a lock, a lost reply or a queue. Never raise the bound.
7. **The machine is scheduled by the system.** Work is admitted from the cores and the memory, and the critical path goes first. A person never picks worker counts, caps or holds; work in flight stays near the core count.
8. **Nothing is switched off, sampled or waived** to get around a bug or a cost; the cause is fixed (§9).
9. **Measure the result in work done** (ticks, bytes; calls are no cost dimension, since they count every thread: owner, 2026-11-15) beside the estimate, before and after, and say which mattered. A claim of "faster" without both numbers is not taken.

## 4. The principles: everything is data flowing through the system

- **If nothing has changed, we do nothing, and no clock guesses when something will finish** ([clocks](docs/clocks.md#two-kinds-of-wait)): a wait on our own system blocks on its Flow channel until the producer's value, typed error or death arrives; a wait on the world outside (the web, a model provider, a subprocess) has a declared, spec'd timeout and ends with a typed error.
- **Every need is met by one of six things.** If none fits, stop and say so:
  - a value: immutable Datahike values in one store with many branches ([storage](docs/storage.md));
  - a Flow proc and its channels ([flow](docs/flow.md#the-step-fn-contract-every-proc-follows));
  - a task: desired state on attributes, observed state as facts, one reconciler ([tasks](docs/tasks.md));
  - a process: an agent is a forked OS process with a real REPL, on its own branch ([processes](docs/processes.md#the-agent-process));
  - a render declared on the entity's schema ([render](docs/render.md));
  - an error as data, flowing to whoever can fix it ([errors](docs/errors.md)).
- **Complicated means step back to a pillar, data model first** (owner, 2026-11-15: "We know exactly what has changed and there are efficient solutions to everything in our design. If you see complicated garabge we need to step back and take a fresh approach ... always fix things at the data model first"): a process with state is a Flow proc, or its Flow setup is changed; data is stored in the db in the shape it is read back by; a value derived from the db is a reaction (a page's, a component of the render walk). What changed is always known (a commit's datoms), so a design that rereads history or the whole store to find it is the wrong design.
- **Nothing crashes, nothing hangs, and no command blocks its caller:** every wait ends, with its value or a typed error saying why it never will ([errors](docs/errors.md#nothing-crashes-and-nothing-hangs)); work longer than a few seconds is a message to the Flow owner that runs it, and the asker is told when it ends (owner, 2026-11-15: "No commands should do that period. We should have long running systems be flow systems and sending a message can trigger a long running task that you can get notified for"). Until each such tool is an op, a session runs it in the background.
- **Store what must be stored; derive the rest, cheaply; render the system from itself** (owner, 2026-11-14: "we really should be asking what do we need to store and what can be derived ... it's very important that we render the system from itself. This is a data driven system"): before storing anything (on an agent, a task, anywhere), ask whether a reaction over a pull pattern and its render schema can derive it. If it can, derive it, and if deriving is costly, store only the extra fact that makes it cheap. Data stored with no consumer is a finding: weigh both sides' cost and delete or derive it.
- **Never pass or keep a db value:** a kept db value is a reference, `{:branch :commit :t}` ([storage](docs/storage.md#a-kept-db-value-is-a-reference)).
- **A mechanism is built once and reused everywhere, and that one path is made optimal** (owner, 2026-11-14: "Make all hot paths optimal and make everything that can be into hot paths. No more 4 ways of doing the same thing. 2 ways of doing the same thing even has to justify itself"). Before building anything that waits, retries, spawns, answers a request or reads config, find its one implementation and route through it. A second way to do one job is a problem until its justification is written where it lives, and the one path's cost is held to its lower bound. A cost reading is the canary: a number far past what the work should take (seconds where it should be milliseconds) is not allowed, and its cause is found first. A hot path is made the easiest way to do its job, so agents choose it (owner: "Hot paths should make it so damn easy to do the right thing that agents want to use it").
- **Get out of an agent's way:** it has a real REPL; record what happened, never gate what it may do, and never cut its context ([processes](docs/processes.md#an-agent-is-never-gated)).

## 5. Laws

A check or a test reads each law, and its section says how.

- **Data is entities, refs and indexes;** there are no kinds ([data modeling](docs/data-modeling.md)).
- **Only documented config:** every limit or default is a key read through the one resolver, and reaching a bound is a typed error ([config](docs/config.md#constants)). **Hand-made lists are judged case by case** (owner, 2026-11-14: "all hand made lists need to justify themselves and they need to be config options that are clearly spec'ed"; then "I want a case by case basis for judging if we should keep the hand lists or fix the problem they are trying to solve at their root. max-workers and all of those config dials are there for a reason"): for each list in code, ask what problem it solves. A real choice or dial (max-workers, max-load, which namespaces to ignore) is kept and made explicit: a spec'd config entry with its reason. A list that patches over a missing mechanism (which attributes a merge carries, which tests a change reaches) is fixed at that root, and the list goes with it. One that restates data already held (a schema's enum, the program's forms) is derived. Health's `:hand-written-list` class shows each list in code with its owner, for that judgement; it never deletes a dial.
- **One store, many branches** ([testing](docs/testing.md#testing-in-the-world)).
- **Every write passes the one path,** checked against the entity's schema ([storage](docs/storage.md#the-write-checks-every-entity-it-touches)).
- **Contracts on every function,** and every contract generates ([checks](docs/checks.md#contracts-armed-at-definition)).
- **No guards:** only a named edge catches ([failure points](docs/failure-points.md)).
- **Effects go through their owner** ([flow](docs/flow.md#effects-one-owner-and-its-workers-per-kind)).
- **Every definition happens once, where it is defined** ([resolution](docs/resolution.md)).
- **Results are reused by input digest;** derived data is a cache, never relied on ([data modeling](docs/data-modeling.md#derived-data-is-a-cache-never-relied-on)).
- **Estimates are proofs:** a cost is work done (ticks, bytes), never time measured under load, and it is held to its estimate (§3 step 2; [cost](docs/cost.md#what-is-measured)). Until a test's tick count is its own work, ticks are recorded on every verdict and do not make it red (owner, 2026-11-15; the same section).
- **Good tests only:** real assertions, red under a mutation, on data that looks like production's ([testing](docs/testing.md#a-proof-is-focused)).
- **Procs follow the step-fn contract** ([flow](docs/flow.md#the-step-fn-contract-every-proc-follows)).

## 6. The running system, as a Seon agent sees it

The standing system (the main checkout's root, its store `runs/store`) is the one you work in and look from (§0). Per-checkout systems (`bin/system start | status | stop` on a worktree's ports, `bin/ports`) are temporary, until the [Stage 1](docs/plan.md#stage-1-claude-sessions-work-through-the-system-the-priority) pilot replaces them. Reach a system through the `seon` MCP server (`bin/mcp`): every op of `seon.server/ops` is a tool `seon_<op>` ([server](docs/server.md#ops)). `seon_context` is what the model reads now; `seon_eval` evaluates in an agent's REPL or in the system; `seon_attach` and `seon_done` work a task as a Seon agent; a message to an agent you attached comes at the top of your next `seon_eval` reply, once, as a model reads it in its next request ([messages](docs/users.md#messages)). A helper in a worktree uses its own system: `bin/mcp call OP KEY=VALUE` ([working a task from a worktree](docs/server.md#working-a-task-from-a-worktree)). The system follows main through `bin/update`, never `bin/system stop/start`.

## 7. The wiki is the one home for how the system works

`docs/` is what an agent's context pulls, so a fact that lives anywhere else is a fact no agent reads, and every useless word costs every agent on every turn. Each fact has one home:
- **the wiki:** how the system works now, by topic, briefly; no dated stories, no plans, no history;
- **docstrings and schemas:** what one var or one value is, in a sentence;
- **task entries:** work to do;
- **decisions:** the owner's rulings, with quote, date and where each is stated;
- **the plan:** what is in flight and THE PLAN;
- **git:** history, and every number a merge measured.

Every function, schema entry and deftest cites the wiki section of its mechanism by its address (``docs/<topic>.md#<anchor>``) and never restates it ([references](docs/references.md#the-delimiter-picks-the-depth)). A section links to code and never copies it. A merge updates its section in the same commit, and a section is written once it is true.

## 7a. Words

Name things with Clojure's, its libraries', Jolt's and git's words: entity, attribute, ref, pull, schema, render, html, messages. The words we do not use are in [vocabulary](docs/vocabulary.md#words-we-do-not-use). A stored keyword is renamed by erasing the store, never by a migration.

## 8. The machine

- **Seon's target is a 16 GB MacBook M1** (`bin/check scale-work`). The machine the sessions build on has 18 cores and 128 GB.
- **Heavy runs** (`bin/build`, `bin/prove`) run under `nice -n 15`; until the effects owner admits them, the load rule in §3 holds them (§3).
- **Never flood it:** anything that makes threads or processes starts at n ≤ 100; one experiment at a time; never make load to reproduce something, and no test makes load (owner, 2026-11-12: "No tests that simulate load by loading my machine ... test 95% of what you're testing and have it be the most important 95%"): a claim is proved by a fast test of its one path, and a race is fixed by design, never sought by load ([machine](docs/machine.md#processes)).
- **Kill only verified PIDs:** read the full command and its cwd first; never `pkill`, `killall` or a `pgrep -f` pattern. A system's processes end with it.
- **A hang is evidence:** capture it before killing the process ([machine](docs/machine.md#reading-a-hang)).
- **Clean up after yourself:** remove a finished worktree with `bin/worktree --remove NAME`; delete a merged branch (`git branch -d`, which refuses an unmerged one); delete a branch your work superseded (`git branch -D`) once your mail names what superseded it. Leave nothing running. Clean up garbage when you see it, after checking that nothing live uses it ([machine](docs/machine.md#disk-stays-bounded)).
- **Git:** commit explicit paths; never bare `git stash`; never `checkout`, `restore` or `reset` on paths you didn't change; never `git submodule` in a worktree (`bin/worktree --sync NAME`); never push a branch of this repository: root pushes main to GitHub after a landing. A cause in a dependency is fixed on a `jolt/<topic>` branch of its fork (`seantempesta/<lib>`), pushed with no force and never to the fork's main.
- **Secrets are never printed.** Paid model calls come from the owner's standing $50 budget, for productive work only ([model](docs/model.md#paid-runs)). Install nothing system-wide. Never write in `~/src/seon`.

## 9. Mistakes we do not repeat

- Fanning out, and building infrastructure instead of the product.
- A number accepted without an estimate to hold it against: a test spending 8,000 times what it should, a suite rerun 52 times a day.
- Switching a mechanism off, or routing around it, because it has a bug: a forked test child that died was answered by turning forks off, and every test ran as a cold process after that. A bug is fixed at its cause; nothing is switched off for it.
- Batching different sessions' branches into one landing, or calling a hand-picked set of tests a prove.
- A rule added after every incident, instead of the cause fixed and the old text deleted.
- A parallel system, or a mechanism built twice.
- A swallowed error, a fake default, a clock standing in for a dependency.
- A check that cannot fail, or one that nobody read.
- A claim passed on unchecked, or the owner's sentence turned into a build before the code was read.
- Dropping a store or rewriting history: that is the owner's act. A branch is not: its commits stay in git.
- A merge rule proved only on a synthetic fixture: three rules landed on 2026-11-14 that a real stale branch broke (one retracted 712 facts). A merge change is proved on real-shaped data before it lands ([merging](docs/merging.md#a-merge-change-is-proved-on-a-real-branch)).
- A number, time, cause or commit id stated before it was read (`date`, `git log`, the file at its line) or measured: a guess passed on is a lost turn for every reader.
- Acting on a branch, a process or a store without first checking its content and identity: a branch moved to the wrong commit, a stray waiter that landed a tip.
