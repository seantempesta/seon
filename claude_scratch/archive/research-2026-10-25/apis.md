# Provider API facts for the agent-view design (read 2026-10-24)

## What Seon uses today
Only DeepSeek, through one OpenAI-compatible chat/completions client (config :seon.config.ai/providers "deepseek", base-url https://api.deepseek.com; models deepseek-flash, deepseek-v4-pro; `:seon.config.ai/thinking :disabled`). No Anthropic, OpenAI or OpenRouter entry in default.edn or src/seon/model.clj. seon.model sends no tool_choice today (grep: none). It sends tool_calls with our own ids ("call-<turn>"), and reasoning_content back when present (model.clj ~101-113); reads usage prompt_cache_hit_tokens / prompt_cache_miss_tokens (DeepSeek) or prompt_tokens_details.cached_tokens (OpenAI-style).

## DeepSeek (api-docs.deepseek.com)
1. Ids: tool_call_id is "Tool call that this message is responding to"; no format/length rule is documented (create-chat-completion). Rewriting to "e43" is not forbidden by docs; untested live. (Seon already sends its own "call-N" ids.)
2. User message after tool messages: docs state no ordering rules ("does not address this case"). Works in practice via OpenAI-compat; not documented. Must keep each assistant tool_calls immediately followed by its tool messages (OpenAI-compat convention).
3. tool_choice: values none/auto/required/named. FORBIDDEN in thinking mode: "Thinking mode rejects `required` and named choices with a 400 error, so you must disable thinking mode" (create-chat-completion page). Fine for Seon only while thinking stays :disabled.
4. Reasoning: thinking guide: if request includes `tools`, reasoning_content "from all previous turns must be sent back" (fully, in all subsequent requests); omitted -> 400. Without tools it is ignored. (So the opposite of "must not": it MUST be sent back in tool mode. Matches model.clj comment.) With thinking disabled, no reasoning_content exists.
5. Caching: automatic, on by default. Prefix must "fully match" a cache prefix unit; units saved at end of user input, end of model output, detected common prefixes, and fixed token intervals for long inputs. No minimum length stated; no fixed TTL ("usually within a few hours to a few days"), best-effort, build takes seconds. Usage: prompt_cache_hit_tokens / prompt_cache_miss_tokens. Changing only the tail keeps the prefix hit, but the hit is at cache-unit granularity (prefix up to the last saved unit), so the tail beyond the last unit boundary is re-billed: expect hits slightly short of the true common prefix.
6. Tool message content: "Either a string, or an array of content parts (for image input)" (text/image_url/file parts). JSON objects are not a type: serialize to a string (our printer's output).

## Anthropic Messages API (platform.claude.com/docs)
1. Ids: tool_use id is "a unique identifier ... used to match up the tool results"; docs give no pattern for ids (only tool *names*: ^[a-zA-Z0-9_-]{1,128}$). Client-chosen ids in replayed history are accepted in practice (SDK users do it); keep to [A-Za-z0-9_-]; "e43" fits. Verify with one live call.
2. Text after tool_result in the same user message: ALLOWED and documented ("tool_result blocks must come FIRST ... Any text must come AFTER all tool results"; text before -> 400). Tool results must immediately follow the assistant tool_use message, no message in between. Exception: if a server tool is unresolved, only tool_result blocks.
3. tool_choice any/tool: NOT allowed with manual extended thinking (thinking.type enabled): error; only auto/none. Adaptive thinking itself allows forced tool use but a forced call skips thinking. And for Claude Opus 5.5, Sonnet 5.5, Fable 5.1, Mythos 5.1: any/tool return 400 regardless of thinking. So "required" is unavailable on the newest models (use auto + strict tools). Forced tool use also prefills the assistant turn: no prose before tool_use.
4. Thinking: during a tool loop you "must pass the thinking blocks ... back, complete and unmodified" with signatures; modified/reordered/dropped -> 400. Older models strip prior-turn thinking on non-tool-result user content; Opus 4.5+/Sonnet 4.6+/Haiku 5.5 preserve it by default. A client cannot rewrite thinking.
5. Caching: explicit cache_control on blocks (up to 4) or a top-level automatic cache_control that moves to the last cacheable block. Lookback 20 positions per breakpoint. Prefix hash up to the breakpoint, so changing content AFTER the breakpoint keeps the hit (best practice: breakpoint on the last block identical across requests). Order of invalidation: tools -> system -> messages. tool_choice change invalidates messages; thinking params/effort changes invalidate messages. Min length: 512 (Sonnet 5.5, Opus 5.5, Haiku 5.5, Fable), 1024 (Sonnet 4.x/5, Opus 4/4.1/4.8), 2048 (Opus 4.7), 4096 (Opus/Haiku 4.5/4.6). TTL 5 min default (refreshed on use), 1h optional (2x price; writes 1.25x for 5m). Usage: cache_creation_input_tokens, cache_read_input_tokens, input_tokens (after last breakpoint); total = sum.
6. tool_result content: string, or list of text/image/document/search_result blocks (not raw JSON; serialize to text). is_error flag exists. Parallel tool results all go in ONE user message.

## OpenAI (developers.openai.com/api/docs)
1. Ids: call_id / tool_call_id must reference the model's call; no format documented in pages read. Chat Completions accepts arbitrary strings in practice; not verified. NOTE docs: newest models (GPT-6 Astra / 6.1 Sol) "require the Responses API for tool calling", a different shape (function_call items + call_id).
2. User message after tool outputs: not addressed on pages read; allowed in practice in Chat Completions; in Responses it is just another input item.
3. tool_choice "required" = "Call one or more functions". Interaction with reasoning not stated on the page read (unverified).
4. Reasoning models (GPT-5, o4-mini): "any reasoning items returned in model responses with tool calls must also be passed back with tool call outputs" (Responses API; Chat Completions cannot carry them).
5. Caching: automatic, on by default; minimum 1,024 tokens (GPT-5.6+); "Cache reuse requires the entire rendered prefix to match"; retention typically ~30 min, up to 24 h extended (newer: prompt_cache_options.ttl). Usage: cached_tokens (prompt_tokens_details / input_tokens_details). Tail-only change keeps the prefix hit.
6. Function output: "typically a string, where the format is up to you"; arrays of image/file objects allowed for results that return images/files.

## Flags against the design
- "One tool, tool_choice required" is FORBIDDEN on DeepSeek with thinking enabled (400) and on Anthropic with manual extended thinking (400) and on Claude Opus 5.5 / Sonnet 5.5 / Fable 5.1 / Mythos 5.1 at any thinking setting. OK today only because DeepSeek runs thinking :disabled and no Anthropic provider exists. Design should say: required only where supported; otherwise auto plus a done-must-be-a-call rule (no-call reply is an error fact).
- "Thinking sent back as the provider requires" is right but per provider: DeepSeek-with-tools requires all reasoning_content back; Anthropic requires thinking blocks + signatures back unmodified for the current tool loop. Neither lets a render/rewrite alter them: keep them as opaque stored fields on the record.
- Prefix-caching claim "byte-identical through the last tool result": true for all three if the dynamic section is the LAST content. For Anthropic put the cache breakpoint on the last tool_result block (or automatic top-level cache_control, which moves to the last cacheable block, i.e. it would land on the dynamic text: then a breakpoint must be explicit on the tool_result). Text after the tool_result in the same user message is legal. For OpenAI/DeepSeek the dynamic section must be appended as a separate trailing user message (or text in the last tool message) and re-built each turn, never stored. DeepSeek's hit is at cache-unit granularity, so expect a partial miss of the newest evals.
- Dynamic section as a trailing user message after tool messages: legal on Anthropic only as text after tool_result in the same user message (a separate consecutive user message is merged by the API; fine). On OpenAI-compat undocumented but works.
- Rewriting tool_call ids to "e43": no documented prohibition on any of the three; must be consistent between assistant tool_call and tool message each turn; unique within the request. Do one live check per provider.
- Tool message must be a string (or text parts): the printed result map is a string, fine. Do not send structured JSON objects.
- A new user turn between an assistant tool call and its tool result is illegal on Anthropic ("no messages between") and on OpenAI-compat: user prose arriving while a call is pending must wait until after the tool message (order the record accordingly), or be placed after it.
- "Never a fake assistant tool call" for user forms is the right call: a synthetic tool_use would need a signature/thinking context on Anthropic.
