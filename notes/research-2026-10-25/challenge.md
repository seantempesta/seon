# Challenge: agent view and context as renders of the record

Grounding: render/proc.clj keeps a view only while a tab watches it ("a view no tab watches keeps nothing"); model.clj already sends one `eval` tool with `code` + optional `thinking`, stores `reasoning_content` per message, has no tool_choice; context.clj rebuilds a whole context each turn (found/rrf/tf-idf over the db); render.clj `cite` pulls each citation once, depth by delimiter.

## 1. Questions that break each part

**Dynamic section = "what the user sees"**
- Zero tabs: the render proc drops the view, so the section is empty or undefined. Two tabs: whose scroll/expansion? Three tabs with different expansions: union (unbounded), last-writer (flapping), first (arbitrary). The model prompt becomes a function of browser state, so a headless run (agent working at 3am, the normal case) and a watched run get different prompts. Reproducibility of a run is lost: "turn basis" (context.clj records commit + observations) must now also record the view set, which is not in the db.
- Tab expands an eval mid-turn: the request being built is already in flight. Which one sees it? Either it is racy (clock-like) or you snapshot per request and record the snapshot (the right answer; then it is a recorded fact, not "what the user sees now").
- Dynamic section sits LAST, but tool results from a call that lands after the section was built must come after it. The previous request's dynamic section is "never kept", so the prefix up to the last tool result is identical only if the new tool result is appended after dropping the old dynamic section. OK for Anthropic/OpenAI prefix caching. But the dynamic part is then re-billed uncached every turn; if it is 10k tokens (function cards, plan, proofs) and the run is 50 turns, that is 500k uncached tokens. Today's context.clj does the same, so this is not worse, but the pitch "cache hits" only covers the history, which is the small part early on.
- Thinking blocks: Anthropic requires the thinking blocks (with signature) of the last assistant turn preserved during tool use, and rejects edits to them; with extended thinking, `tool_choice` must be `auto` or `none`. "one tool + tool_choice required" is INCOMPATIBLE with extended thinking on Anthropic (400). OpenAI reasoning models and DeepSeek accept required but DeepSeek needs reasoning_content echoed. So the design needs a per-provider answer; "required" gives guarantee of a call, but then "finish" is `(my.task/done!)` and a model that wants to just answer cannot. What happens to a message with prose and no call? Today model.clj treats empty+reasoning as an error; prose-only would loop forever under required or stall under auto.
- Rewriting tool_call_id to `eN`: Anthropic ids must match `^[a-zA-Z0-9_-]+$` (ok), OpenAI up to 40 chars (ok). But thinking signatures on Anthropic are over the block content, not the id, so probably fine; verify. Real hazard: ids must be unique across the conversation and the id is chosen by the provider at generation time: rewriting in history means the stored message differs from what the provider sent, so you cannot replay byte-identical for cache unless the rewrite is applied at record time and always. Parallel tool calls in one assistant message: `e43`, `e44` per call is fine, but "one tool call per message" is stated; if the provider emits two, who handles it?
- Handles `result/e43`: a value "already in a tool result is written as its handle, not re-printed". After a branch merge, restart, or fork, does `result/e43` still resolve in the REPL? A fresh forked process has an empty REPL; handles must be re-bound from the record (every eval's value is retained? 1000 evals of large values = memory). The REPL binding makes every value immortal (leak) unless it is dereferenced from the store lazily.
- User eval from a form "with `{:from "user" ...}`" as a user message: the model then sees state changes (a def) with no matching call id; fine, but the user's REPL is the agent's REPL? A user eval landing mid-turn mutates the namespace under a running eval. Recorded in tx order, but the model's eval of the same turn may have read the older value. Needs "applies at the next turn boundary" or accept it as real REPL semantics (state it).

**References from all on-screen strings**
- Unbounded: prose, thinking, user messages and task plan all are parsed, and `cite` pulls each citation at depth set by delimiter. One `[ns]` depth cite pulls a whole namespace. Thinking text is the worst source: the model mentions `my.foo` while musing and next turn the whole namespace shows. Positive feedback: pulled content mentions more symbols, but `cite` only parses prose, not pulled values (good; keep that, state it). Bound must be a budget in tokens with a recorded "left N, read with X" (AGENTS.md: no clipping without saying what was left), and the budget is a config key. "Fallback if too big" is a second mechanism (built-in layout + last X evals). That is a guard/ fake path: replace by one rule: render in priority order until the budget, list the rest by name.
- Citation sets are non-monotonic: the reference vanishes when its mentioning message scrolls offscreen, so the dynamic section changes shape turn by turn, and the model loses a function card it was mid-edit on. The sticky set should be a fact on the record (pinned), not a function of scroll position.

**Page / tiles / expand**
- Expand as `/call` -> eval with origin :ui. An eval per click means a click in a 1000-eval timeline writes a tx and wakes everything watching that branch. Expansion is view state, not agent history; recording it in the agent's branch pollutes the transcript the model reads (does the model see "user expanded e12" as a user message? the design says it sees the section, not the message; then why record it as an eval at all?). Existing `/call` for UI actions is recorded, but a purely presentational toggle is not an action on the record. Simplest: expansion state in the render proc (it already keeps per-view rows), and the model prompt does NOT depend on it (see section 2).
- Agent overriding its render on its branch: the branch registry wins "for that agent's page". An agent can then hide errors, red proofs or its own diffs from the user, and root renders agents' summaries via the same lookup unless root uses main's registry. Also contradicts AGENTS "Every view is a render declared on the schema... one printer". Rule needed: pages for users/root always use main's registry; an agent's override affects only its own model context (what it sees), never what is shown about it. Even then, an override changing what the model sees is fine (get out of the agent's way), but it must be a recorded fact so reviewers can see it in the diff.
- Two tabs expanding different evals: if expansion is per tab, units are per (view, tab) and the "unit = digest of f + props" patch fanout (serialize once, fan out) breaks for expansion props. Needs expansion as a client-side Datastar signal (no server state) with the server rendering both collapsed and expanded markup (or lazily fetching expanded on click).

**Render system**
- `[f props & children]` with defaults merged: this is Reagent/hiccup-component semantics; fine, but "function symbols" in data plus `{:seon.render/from some-fn}` providers means a render reads arbitrary queries; dependency tracking is then via `query-attribute-dependencies` in a Datahike fork. Anything not via q/pull falls back to "any commit on the branch": git, file reads, `docs/` are not datoms, so those units re-run on every commit of a busy branch. The fallback is the common case (function card uses callers, git, costs), so the incremental machinery covers little. And "same result digest -> nothing" means the provider is rerun on every commit anyway; the saving is only in re-render + send.
- Digest of "f + explicit props" for the unit id: f must be identified by content or var + program digest, else an override or a code merge leaves stale units. Props may be big values (digest cost O(size) on every pass).
- Parents hold child call vectors, not child output: how is a parent's own output (hiccup with child placeholders) assembled for a fresh tab? Needs a full expansion walk; where is it cached? If not, keyframe cost = whole tree.

## 2. Simpler versions (what is lost)

1. **Dynamic section = a function of the record only, never of tabs.** Show: task plan, red proofs, the agent's pinned/cited references (recorded facts), sidebar-peers summary. No tab state. Lost: "the agent sees exactly what the user sees". Gained: reproducible runs, works with zero tabs, no race, no per-tab union, the turn's basis is the commit as today. The user's expansion is for reading; if the user wants the agent to look at something they say so (a user message citing it, which the reference parser already turns into a card). That is one mechanism (citation) rather than two (citation + view mirroring).
2. **Drop "expand = eval".** Client-side Datastar signal + lazy `/unit/e43` fetch. Lost: record that the user looked. Gained: no tx per click, no wake of the branch.
3. **Keep the tool message as the existing `:seon.agent/item` printed by the one printer**; skip the reshaping to `{:result :value :ms :ticks :bytes}` until a test shows models do worse. Handle `result/eN`: keep, but make it a lazy var resolving from the record, not an eagerly-bound leak.
4. **Skip `tool_choice required`**; use `auto`, and treat a call-less reply as a user-visible message that ends the turn (waiting for user), exactly what chat agents do. `done!` stays an eval. Compatible with extended thinking. Lost: guarantee of a call; but the current code already handles empty replies as an error fact.
5. **Don't rewrite tool_call_id in history; mint ours at record time** (`eN` is the id we hand to the provider where the provider lets us choose; otherwise store the provider's id on the record and use `eN` only for the REPL handle). One id column each, no rewrite. Or accept the provider id as the handle if short enough.
6. **Per-agent render override**: cut it from v1 of this. A schema's render is main's. Agents that want different context print differently in their REPL. Lost: agents tuning their own context. Add later as a recorded branch change if turns-to-green data demands it.
7. **Units/incremental render**: start with per-view re-render on commit where the view's recorded read-attributes intersect tx-data (attribute set only, no per-unit providers), digest of output to suppress. Keep unit granularity only for the one thing that is proven big (eval timeline rows, already per-row).
8. **Sidebar tiles for 1000s of agents**: one materialized summary per agent (status, task, id), written by the agent's own record on change; the sidebar is a paged query over that, not a subscription to every branch.

## 3. Scaling

| Operation | Cost | Fix |
|---|---|---|
| Reference extraction over all on-screen strings per request | O(total on-screen text) parse + `docs/cited` pulls, per turn, per agent | Parse each message once at record time, store its cites on the message (facts); a request unions stored cites with the plan's. Cost O(new text). |
| Dynamic section rebuild per request | O(cards) each with callers (compiler facts), tests reaching, measured cost | cache card by (var digest, program digest), already allowed by "content-keyed reuse for measured-expensive units". Show timings first. |
| Expanded-set per view per tab | O(tabs x expansions) memory in render proc | client signal; nothing server-side. |
| Fork per agent with REPL-bound `result/eN` | O(evals x value size) heap per agent; 1000 evals of a 1 MB value = 1 GB, past the 16 GB target at 16 agents | bind lazily (a var that pulls from the store), or retain only handles + digest; evict, say what was evicted. |
| History in the model request | O(evals) tokens; no compaction story in the design | A 1000-eval run overflows the window; the cached prefix is no help once over. Need an explicit elision rule (older results as `result/eN` + one line), through the printer, saying what was left. This is the real scaling limit and the design is silent. |
| Per-commit unit invalidation | O(units on page x commits) provider re-runs for "any commit" units | attribute-level deps only; "any commit" is a defect fact so it gets fixed (git/file reads get a dependency datom, e.g. the commit sha). |
| Sidebar for thousands of agents | O(agents) tiles pushed per tab | paged by status, only visible rows rendered (already the scroll mechanism); the agent's own dynamic section includes only its peers named in its task/messages, not all. |
| Thinking blocks stored per message | O(tokens), always replayed | already stored; do not render in the model's tool result, only in the chat. |

## 4. Conflicts

- "The agent sees what the user sees" vs AGENTS §4 "no clock/timer decides; value in one store": tab state is not a value in the store; it is ambient input. Either record it (then it is the user acting on the record, i.e. an eval/fact) or don't use it.
- "Fallback if too big: built-in layout + last X evals" vs §9: a fallback instead of a fact; a "last X" is a clipping function. Replace by budget + "left N, read via ...".
- Dynamic section "never kept" vs "turn records its basis" (context.clj docstring: "a turn records its basis ... and `render` makes the text from it, for anyone who reads it later"). If it is not kept, how is it reproduced? Only possible if it is a pure function of recorded inputs, which tab state is not. Strongly favours simplification 1.
- Agent-overridable render vs "get out of an agent's way" (consistent) but vs the owner/root seeing the truth about an agent and vs "one printer / no second mechanism" (a branch registry is a second lookup layer besides schema default).
- "Values in the REPL are never rendered: the printer prints them" vs "tile per eval whose value has a render": the page renders values the model's own result string prints differently. Two views of one value are allowed (§4 "a render"), but the model's tool message and the tile must be derived from the same schema-declared render with a different `:as`, or this is two producers of one view (§9).
- "One tool: eval, required" vs extended thinking on Anthropic (hard conflict), see above.
- Render providers `{:seon.render/from some-fn}` that may do "a query, git" vs §5 "effects go through their owner" and "no guards": a provider that shells out to git during a render pass blocks the render proc (step never blocks). Providers must be pure over the db, git facts should already be datoms.
- Mutable per-view expanded set in the render proc vs "state is plain data under its schema": fine if schema'd; flag it.

## 5. Riskiest assumptions, smallest experiments

1. **Models do as well (turns to green) with a vanilla function-call transcript + a rebuilt-every-turn dynamic tail as with today's context, and the cache still pays.** Experiment: take 5 finished tasks with recorded turns; replay prompts in the new shape (history as tool messages, tail = today's context render) against the real provider with usage logged; compare `cache-hit-tokens` per turn (turn.clj already records them) and run the 5 tasks for turns-to-green. Needs no web UI. Kill criterion: hit rate under ~60% after turn 3, or turns-to-green worse.
2. **Provider constraints: required tool_choice + thinking + rewritten ids + last-message dynamic section.** Experiment: a 30-line script per target provider (Anthropic, OpenAI, DeepSeek, whichever Seon uses): 3-turn conversation with thinking on, tool_choice required (expect Anthropic 400), ids `e1..e3` rewritten after the first response, a trailing user/system message replaced each turn; assert 200, thinking signature accepted, cache read tokens > 0 on turn 3. Smallest and most likely to kill a part of the design today.
3. **"What the user sees" is worth its cost (the premise).** Experiment: ablate it. Run the same 5-task set with the dynamic tail = record-only (plan, red proofs, cited refs) versus a simulated "user view" (last 10 evals expanded + tiles). If turns-to-green are equal, the whole tab-mirroring machinery (per-tab sets, race, non-reproducible turns) is dropped. Cheap because the simulated view is just a different render of the record. Second-order check in the same run: size of the cite closure from thinking text (tokens per turn, max) to see the unbounded-reference risk empirically.

Bonus fourth if time: the render dependency tracking claim. Count, over a recorded 200-eval run's commits, how many units fall to "any commit on the branch" because a provider uses git/docs/non-q reads; if over half, the incremental unit system saves little over per-view re-render.
