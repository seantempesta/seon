# Merging

How a branch is merged into main: what it runs, how batches are proven, and how conflicts are resolved. Who merges and why is [AGENTS.md §3](../AGENTS.md) ("Integrate small and often", "Testing: compute only what is needed"); the machine the proofs run on is [machine](machine.md).

## A worktree session works in a checkout of its own

A worktree session is a separate instance of the whole system: `bin/worktree NAME` (run from the main tree) makes `../next-NAME` on branch ``jolt/NAME`` from main, with its own submodule checkouts at their pins, an APFS clone of `target/` (so `nice -n 15 bin/build seon` is the only build), its own ports (`config/local.edn`, `bin/ports`) and its own stores under its `runs/`. In it:
- `bin/root start | status | stop` runs that worktree's own root, never the standing one (7888); a Claude session started in the worktree reaches it through the committed `.mcp.json` (`./bin/mcp` asks this checkout's root);
- `bin/prove` runs what the change reaches, nothing else ([below](#a-merge-runs-what-the-change-reaches)); `bin/test NS` runs one namespace's selection and `bin/check MODE` one check step; `bin/check` (one mode or a run) works on a store of the checks' own, ``target/check-store``, seeded when missing (`SEON_STORE` names another): `runs/store` is the worktree root's, made without the example program the checks seed, so reusing it fails steps falsely;
- after each merge into main: `git merge main` in the worktree, then `bin/worktree --sync NAME` (it moves only this worktree's submodule checkouts to the pins its branch records; never `git submodule` in a worktree);
- a submodule the session adds (``reference-code/X``) is written as a `.gitmodules` entry and a gitlink, with its checkout cloned from a local copy; root initializes it in the main tree when it merges (`git submodule update --init reference-code/X`), so later worktrees get it.

`bin/worktree-check` (run from the main tree) proves this whole workflow end to end with a throwaway worktree session and removes it; run it after a change to `bin/worktree`, `bin/root`, `bin/mcp` or the build. Leave nothing running: `bin/root stop` before you report. Root removes the worktree after the merge (`bin/worktree --remove NAME`).

## A worktree session's part

A worktree session merges main into its branch, proves the merged result with `bin/prove`, and reports. Branches live hours: merge main into yours after every merge into main. Iterate at the REPL first, then with `bin/prove` (or `bin/test NS`), never a full run per edit. Long runs only when the work is done: the full `bin/test --all` and `bin/check 100` run once per session, when it believes its task is finished and its review findings are fixed. To be merged, report the commits, proofs red → green, numbers against estimates, what you deleted, `bin/prove`'s last lines (and the check's ``target/check/<time>/`` path when steps ran), and that nothing of yours is running.

## Every branch is reviewed before it merges

A reviewer reads the branch's diff against main for AGENTS §9's mistakes (a guard, a fake default, a clock deciding, a second mechanism, a fix at the reader instead of the producer, an old word of §7a, a test that cannot fail, an ignored answer), each finding with its file:line and its right fix. The worktree session fixes them before its branch merges; the proof it reports is the run after the fixes.

## Root merges, and reads the verdict

Root merges the branch, never copying files over newer changes, and reads the merged tree's proof to its last line before main moves.
- Every stage's exit status decides the next: no pipe hides a failure (`setopt pipefail`, output to a log), and a check counts only if the build before it succeeded and the binary was built from the tree it proves (`bin/test` builds `target/seon` whenever anything runs).
- Root rebuilds main as part of every merge, so a worktree made from main never reads config with a stale binary.

## A merge runs what the change reaches

A merge runs what the change reaches, not every check. The merge's proof is `bin/prove` on the merged tree, then `bin/check smoke`; `bin/laws` (every law's sites) runs inside it as a step keyed by the whole tree. One rule selects for everyone: a key runs exactly when no green result is stored at its reach digest (```seon.proofs/plan```), in the one results directory every checkout shares (`:seon.config.source/test-results-dir`), so an unchanged tree runs nothing and a result proven in any checkout is reused in every other.
- **What reaches a process runs when asked.** A run that names nothing (`bin/prove`, `bin/test` with no namespace, the on-change runs) leaves out every test and bin/check step that reaches a process of its own: a root or an agent booted for it, a shell, a fork, the binary (```seon.program/reach-index```'s `:process?`, the one walk, over `:seon.config.source/process-vars`; ```test-runner/automatic```). Owner, 2026-10-23: "Tests shouldn't be running agent turns. Not automatically run tests at least." They run when named (`bin/test NS`, `bin/check MODE`), in the full run (`bin/test --all`, `bin/check 100`), or by root's gate before a merge that reaches them. Measured from the recorded durations of the 2026-10-23 full run: those were 90 of 443 tests and 782 of their 917 s, and every check step that boots a root; a run that names nothing went from about 26 minutes to about 2.
- **The binary is built when a selected key uses it.** `bin/test` builds `target/seon` (about 46 s) only when a selected test uses the binary (```seon.program/reach-index```'s `:binary?`: a reached form references ```seon.test-store/binary-sh```, the one way a test runs it, other than a form that only names it as data or is its own definition) or a selected step runs a `seon.check` mode (```seon.proofs/step-needs-binary?```, from `check-steps`: laws and lmdb-kill run none). The plan writes `out/binary` and `out/steps-binary`; empty, `bin/test` builds nothing and `bin/check --steps` seeds, lists and drops nothing. A step that ran no mode is stored green whatever binary stands. Measured on the shared machine: `bin/prove --checks` selecting only `laws` and `lmdb-kill` ran in 16.8 s (plan 8-15 s, the two steps a few), and 9.4 s when both were reused; the 46 s build and about 6 s of seeding and dropping it used to add are not spent.
- **Tests.** A test's key is its reach digest (```seon.program/reach-digests```: the forms it reaches through refs, macros, quoted names, methods, fixtures and schemas, plus the checkout's inputs with no program facts; [source](source.md#tests-run-by-reach)). The digest is the tree's, never the process's: the same commit gives the same digests in any checkout and any run (`seon.program-test/the-same-tree-gives-the-same-digests-in-any-checkout-and-any-run`). `bin/test [NS ...]` imports src and test once, selects, and deals what runs, a namespace at a time, into `:seon.config.proofs/jobs` shards, each a process of its own started at once and reaped by the shell (```seon.proofs/run-tests!```): a fork of the runner cannot connect to a store, since Datahike's connection state does not survive fork (measured: the child's first `d/connect` never returns). A shard stores its greens once it has run (```seon.proofs/store-greens!```, through ```seon.fx/write-file```, each answer read: a refused write is named, and its test runs again), unless the tree changed since the plan took its digests (an edit during the run: what ran is not what the digests name); a shard that dies midway stores nothing. Only greens are reused, so a red runs again. The shards are dealt by each test's last measured ms (kept per checkout in `target/prove/ms`, one file per test), the longest part first into the lightest shard, a namespace longer than a shard's share split into share-sized parts, so they end together (`test-runner/shards`; measured 2026-10-23, dealt by count, the four shards of a full run ended 437, 397, 110 and 68 s in). A shard stores its greens only if the tree is the plan's both before and after its run.
- **Check steps.** Each `bin/check` step is keyed the same way by the `seon.check` mode functions its body runs: `seon.proofs/check-steps` is the one list of the steps (`bin/check` reads it from ``./seon steps``), and `seon.proofs/step-digests` digests them ([checks](checks.md#modes)). A change to `seon.check/smoke` or what it calls reruns smoke; a change to bin/, native/, resources/ or a pin (the binary's other inputs, `:env`) reruns every step. `bin/prove` runs the steps to run through `bin/check`'s own bodies (`bin/check --steps target/prove`: the names in ``target/prove/steps``, the greens written to ``target/prove/green``) and stores the greens at their digests unless the binary was built from another tree than the plan's. A run's steps run at once, `:seon.config.proofs/jobs` at a time (a FIFO of tokens: a blocking read, no poll), the longest first by the last run's measured wall seconds, each on an APFS clone of the one seeded store (one root per store: two roots branching at once can drop a branch from the store's roster, task `seon.db/two-processes-branch-one-store-at-once`, and root collects only as the store's only writer, [storage](storage.md#collection)), deleted when it is green; `scale` runs alone after them, since it measures the machine's memory. Each step's wall and CPU seconds are kept beside its log (`STEP.time`), and each shard's beside its (`target/prove/tests/shard-<i>.time`).
- **Agents.** A Seon agent's run (the turn's observe, the judge's `:tests`, the merge gate, and `(my.agent/prove)`) uses the same `plan` against the agent's base, main at its merge base (`seon.agent/test-plan`, [source](source.md#tests-run-by-reach)). Its digests' inputs with no program facts are its root's: the `:source` read (```seon.fx/read-source```, on an effect worker) answers the source tree's inputs (```seon.fx/inputs```), and ```seon.root/import-source!``` writes them on that boot's `:seon.root/source` fact only when the running binary is built from that very tree (``target/seon.tree``, which `bin/build` writes; ```seon.fx/tree-id```), with why not otherwise (`:unshared`). An agent uses only its root's current boot's inputs, so a previous root's never key its results. Agents keep their greens in the one results directory bin/test and every checkout share (`:seon.config.source/test-results-dir`), stored through root's `:file` owner (```seon.proofs/store-greens!```): a test that is the same is not run again once green, by an agent or a checkout, "especially when freshly branched" (owner, 2026-10-23); every eval is a recorded form, so the digest covers what ran (`seon.agent-test/an-agents-greens-and-a-checkouts-are-one-store`).
- **What an agent runs** (root's ruling (a), 2026-10-22, from step E's run 7, where a change to `seon.problems/report` put 294 reached tests in every turn's run). A turn runs the task's proofs and the tests the branch itself changed or added, under `:seon.config.agent/turn-test-ticks` (a run its bound ends leaves the rest unknown, never red); root's judge runs, once at the attempt's end, the plan's in-process tests (`(my.agent/prove)` runs the same). A process test (one whose reach references a var of `:seon.config.source/process-vars`: a shell, a fork, a root of its own, the binary; ```seon.program/process-tests``` over ```seon.program/reach-index```, the same walk as the digests) never runs automatically, a proof among them, only when named (owner, 2026-10-23: "Tests shouldn't be running agent turns"): the done rule reads such a proof as deferred, neither red nor unknown. The turn says each: `:tests {:this-turn :at-judge :when-asked}`. The plan's two reach walks (the branch's ```seon.program/reach-index```, the base's ```seon.program/reach-digests```) are each reused while the db value walked is the same (```seon.agent/walk```): the base's once per base (until merge-main replaces it), the branch's once per value, so root's `:tests` after the last observe plans in about 1 ms (measured 2026-10-23: 2.7 s and 4.2 GB a first plan, 1.4 s for a new branch value on the same base). The turn's contract gaps read what changed (```seon.merge/uncontracted-since```, over ```seon.program/divergence```), and its unmerged entries read the program only while one is open.

- **The merge gate** (root's rulings, 2026-10-22/23; owner 2026-10-23: only when asked). A merge whose branch's change reaches process tests (`:seon.attempt/deferred`, recorded by the judge) runs them before it merges only on root's go, ```my.root/gate!``` setting `:seon.task/gate?` on the task before its attempt is judged (root gives it to a change that reaches the turn loop), on a worktree of the root's declared gate checkout (`:seon.config.source/gate-checkout`, the standing root's merges tree) at the merges head with the candidate's changed files over it, through prove's entry (the `:tests` effect, ```seon.fx/run-tests```); their results are `:seon.attempt/deferred-results`, and a red, or a run that could not run them (`:error`), refuses the merge as a red proof does. A changed namespace the gate cannot read from the branch (no `:ns/file`: made at the REPL, never written) is named with why on the attempt (`:seon.attempt/gate-unread`) and on its `:unrun` row, and the run, over another tree than the one that merges, vouches for none of its tests (each `:error`). Unasked, or on a root that declares no gate checkout (a test's root, a check's), it merges with them unrun: recorded on the attempt with no results, never green, an open `:unrun` problem ("merged with N process tests unrun") until a run gives them results; root's git merge of the branch runs them with `bin/prove`, the real gate.

The full runs are explicit: `bin/test --all` and `bin/check 100`. They run once a day in the background, once per worktree session when its work is done, and before a merge that changes boot, the writer, the reconciler or the build; a red there becomes a task, not a blocked merge.

Measured on the shared machine, niced, at about 370 tests and 34 steps: selecting takes the import plus the digests, 7-12 s; an unchanged tree reuses every green (`bin/prove --checks`: 34 of 34 steps reused in 8.5 s, against about 6 minutes for `bin/check 100`); a one-defn change on the agent's turn path ran 71 tests and 33 steps in about 11 minutes; a cold run (nothing green) took about 19 minutes. A digest follows the tree, never what the process analyzed, and a test takes the whole tree as an input only through ```seon.program/env-readers```; a pin bump moves `:env` for every test, honestly.

## Ready branches merge in batches

Root merges ready branches in batches: three branches merged one at a time cost about 40 minutes of serial full checks, plus re-proving after every main move. Branches that are ready, reviewed and file-disjoint (or whose overlaps are both-sides additions) merge onto one integration branch from main and are proven together by one `bin/prove` there (each branch's own greens are reused; only what the combination moved runs); then main moves to it. A conflict stops the batch: it is resolved, or the branch leaves the batch, before anything else merges. Nothing merges into a batch while its proof runs, since the proof would then name a tree that no longer exists.

## Every merge's `src` diff stat is read

Root reads every merge's `src` diff stat before merging, against the goal of about 10k lines of our own code. Every function a merge adds names the existing system it extends, or why none could carry it; a new namespace or mechanism where an existing one could be extended is sent back, not merged; the merge's commit message states its net `src` lines (`bin/laws growth` prints them and the definitions the branch adds), and a merge that grows `src` says what it deletes or plans to delete.

## Conflicts and pins

A conflict is resolved by copying each side's lines, never retyping; the lines after `>>>>>>>` may belong to both sides; each resolved file's forms must balance as its parents' do. Submodule pin bumps happen only in root's merges into main, never in a worktree session's merge of main. Commits in the forks ([forks](forks.md): Jolt, Chez, Datahike, konserve) carry no AI trailers. After a merge, root archives the worktree session first (its `bin/mcp` holds the worktree open), then removes its worktree ([machine](machine.md#disk-stays-bounded)).

## Seon's merge is a three-way merge of the program

Seon's own merges (a branch into main, main into a branch) are git's three-way merge over the program as data, never over files.

```seon.merge/program``` reads a db's program as a map from keys (``[:form id]``, ``[:var sym]``, ``[:schema k]``, a declared datum) to content, and ```seon.merge/three-way``` compares base, ours and theirs: each side's changes, the keys to apply, and the conflicts. The writer's merges use it (`seon.writer/writer-proc`), and it is the one derivation behind the done rule's unmerged entries, the agent's merge of main and the dashboard. A conflict stays on the branch as an unmerged entry (```seon.merge/unmerged```), base, ours and theirs as data, until the branch redefines the key or resolves it (`my.branch/resolve!`, ```seon.merge/resolve-tx```); ```seon.merge/apply-tx``` writes a merged map onto a db. The files a merge touches are written back by [source](source.md); a merge task's turns are [turn](turn.md#a-merge-tasks-loop).

## Not built: a merge queue on root

Root's merges of worktree branches are git merges, batched by hand as above. Seon's own merges are merge tasks judged by the reconciler, one at a time: an octopus merge of several merge attempts is built and off (`:seon.config.merge/max-running` 1, until one combined test run of all its members is proven). No queue on root merges main into each candidate, proves the merged result and batches the disjoint ones, and builds, tests and checks are not tasks on root (task ``seon.reconcile/a-check-step-is-a-task``).
