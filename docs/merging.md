# Merging

How a branch is merged into main: what it runs, how batches are proven, and how conflicts are resolved. Who merges and why is [AGENTS.md §3](../AGENTS.md) ("Integrate small and often", "Testing: compute only what is needed"); the machine the proofs run on is [machine](machine.md).

## A worktree session works in a checkout of its own

A worktree session is a separate instance of the whole system: `bin/worktree NAME` (run from the main tree) makes a worktree on branch ``jolt/NAME`` from main (at `.worktrees/NAME` inside the root; `bin/worktree --path NAME` prints it), with its own submodule checkouts at their pins, an APFS clone of `target/` (so `nice -n 15 bin/build seon` is the only build), its own ports (`config/local.edn`, `bin/ports`) and its own stores under its `runs/`. In it:
- `bin/root start | status | stop` runs that worktree's own root, never the standing one (7888); a Claude session started in the worktree reaches it through the committed `.mcp.json` (`./bin/mcp` asks this checkout's root);
- `bin/prove` runs what the change reaches, nothing else ([below](#a-merge-runs-what-the-change-reaches)); `bin/test NS` runs one namespace's selection and `bin/check MODE` one check step; `bin/check` (one mode or a run) works on a store of the checks' own, ``target/check-store``, seeded when missing (`SEON_STORE` names another): `runs/store` is the worktree root's, made without the example program the checks seed, so reusing it fails steps falsely;
- after each merge into main: `git merge main` in the worktree, then `bin/worktree --sync NAME` (it moves only this worktree's submodule checkouts to the pins its branch records; never `git submodule` in a worktree);
- a submodule the session adds (``reference-code/X``) is written as a `.gitmodules` entry and a gitlink, with its checkout cloned from a local copy; root initializes it in the main tree when it merges (`git submodule update --init reference-code/X`), so later worktrees get it.

`bin/worktree-check` (run from the main tree) proves this whole workflow end to end with a throwaway worktree session and removes it; run it after a change to `bin/worktree`, `bin/root`, `bin/mcp` or the build. Leave nothing running: `bin/root stop` before you report. Root removes the worktree after the merge (`bin/worktree --remove NAME`).

## A worktree session's part

A worktree session merges main into its branch, proves the merged result with `bin/prove`, and reports. Branches live hours: merge main into yours after every merge into main. Iterate at the REPL first, then with `bin/prove` (or `bin/test NS`), never a full run per edit. Long runs only when the work is done: the full `bin/test --all` and `bin/check 100` run once per session, when it believes its task is finished and its review findings are fixed. To be merged, report the commits, proofs red → green, numbers against estimates, what you deleted, `bin/prove`'s last lines (and the check's ``target/check/<time>/`` path when steps ran), and that nothing of yours is running.

## Every branch is reviewed before it merges

A reviewer reads the branch's diff against main for AGENTS §9's mistakes (a guard, a fake default, a clock deciding, a second mechanism, a fix at the reader instead of the producer, an old word of §7a, a test that cannot fail, an ignored answer), each finding with its file:line and its right fix. The worktree session fixes them before its branch merges; the proof it reports is the run after the fixes.

## Root merges, and reads the verdict

Root merges the branch, never copying files over newer changes, and reads the merged tree's proof to its last line before main moves.
- Every stage's exit status decides the next: no pipe hides a failure (`setopt pipefail`, output to a log), and a check counts only if the build before it succeeded and the binary was built from the tree it proves (`bin/test` builds `target/seon` whenever anything runs).
- Root rebuilds main as part of every merge, so a worktree made from main never reads config with a stale binary.

## Main goes first

A merge's verification is one command, `bin/prove --merge`.
- **One command, one verdict.** It runs every test and `bin/check` step with no green at its digest, the ones that reach a process too (the plan's `:merge` mode, `test_runner/plan-of`: nothing is left out and none is named by hand), `bin/check contracts` and `bin/check smoke` among them (steps of that same run, keyed by digest: not run again beside it). It ends on `MERGE OK` or `MERGE FAILED` from that run's exit status alone, and prints its line for the merge commit's message: the sha, the plan's counts, each verdict, the reds, the src delta of HEAD against its first parent, and the keys left out against main's last merge message (git keeps every merge's numbers; no separate log). So a merge line cannot say green over a red exit, and a step cannot go unrun unsaid.
- **No lock.** Nothing waits on main's verification (owner, 2026-10-27: "Remove it"): it runs niced like any run. It rarely runs, since a branch that holds main and proved its tip merges with no run on main, and load is kept down by not running the same work twice, not by ordering runs.
- How many heavy runs go at once is AGENTS' number (§2), not a gate here.

`bin/update ARGS` hands its arguments to the restarted root, so the owner's root restarts with `nice -n 15 bin/update --profile deepseek` (the first after the command-line profile merged must pass it: the old binary's resume arguments carry none; [config](config.md#layers)). A root that is restarting (`bin/update`) refuses connections for the moment, so a plan run that meets it prints `TEST FAILED` for the connection, a rerun and not a red; the verdict to read is the one a run ends on once root is up.

## A merge runs what the change reaches

A merge runs what the change reaches, not every check. The merge's proof is `bin/prove` on the merged tree, then `bin/check smoke`; `bin/laws` (every law's sites) and `health` ([health](health.md)) run inside it as steps keyed by the whole tree. One rule selects for everyone: a key runs exactly when no green result is recorded at its reach digest (```seon.proofs/plan```), in the verdict cache every checkout shares ([verdicts](#verdicts-are-a-cache)), so an unchanged tree runs nothing and a result proven in any checkout is reused in every other.
- **What reaches a process runs when asked.** A run that names nothing (`bin/prove`, `bin/test` with no namespace, the on-change runs) leaves out every test and bin/check step that reaches a process of its own: a root or an agent booted for it, a fork, the binary (a shell call, git or perl, is none: it costs milliseconds; ```seon.program/graph-index```'s `:process?`, the one walk, over `:seon.config.source/process-vars`; ```seon.proofs/left-out```, the one filter bin/test and an agent's run apply). Owner, 2026-10-23: "Tests shouldn't be running agent turns. Not automatically run tests at least." They run when named (`bin/test NS`, `bin/check MODE`), in a merge's verification (`bin/prove --merge`), in the full run (`bin/test --all`, `bin/check 100`), and at the judge before a merge whose change reaches them, nobody asking (owner, 2026-10-27; the reconciler's `:gate`, on the declared `:seon.config.source/gate-checkout`). Measured from the recorded durations of the 2026-10-23 full run: those were 90 of 443 tests and 782 of their 917 s, and every check step that boots a root; a run that names nothing went from about 26 minutes to about 2.
- **The binary is built when a selected key uses it.** `bin/test` builds `target/seon` (about 46 s) only when a selected test uses the binary (```seon.program/graph-index```'s `:binary?`: a reached form references ```seon.test-store/binary-sh```, the one way a test runs it, other than a form that only names it as data or is its own definition) or a selected step runs a `seon.check` mode (```seon.proofs/step-needs-binary?```, from `check-steps`: laws, lmdb-kill, lmdb-sem and forks run none). The plan writes `out/binary` and `out/steps-binary`; empty, `bin/test` builds nothing and `bin/check --steps` seeds, lists and drops nothing. A step that ran no mode is stored green whatever binary stands. Measured on the shared machine: `bin/prove --checks` selecting only `laws` and `lmdb-kill` ran in 16.8 s (plan 8-15 s, the two steps a few), and 9.4 s when both were reused; the 46 s build and about 6 s of seeding and dropping it used to add are not spent. With it, `bin/test`'s plan makes the one store the process tests' roots take a branch of, `target/runs/test-store-<schema digest>` (```seon.test-store/make-process-store!```, named by ```seon.test-store/kept-store!```), once when it is missing and before any shard starts; shards whose roots each made it raced, one opening the store another was still creating. Both kept stores of regenerable output, it and the program store, are named by the schema's digest (```seon.db/schema-digest```): a changed schema makes a new store, and one of another schema is removed, never migrated or refused.
- **A shard's agent tests share one root.** ```seon.agent-test/in-agent``` asks ```seon.test-store/shared-root!``` for the shard process's root for its root arguments (its `:dirs` and `:sets`), started at the first test that asks, on a main of its own of the process store, and stopped with its main dropped when the shard process ends (a shutdown hook; hooks run at once, so no other hook may remove what its stop uses: the starter fifo is reclaimed by the next process instead). Each test loads a task file of a namespace of its own (`t<8 hex>`), attaches its own agent and names both by what the attach answered, never by a counter's value (`a1`, `demo/t`); at its end its agent is killed, its end awaited, its tasks cancelled (a run left `:running` keeps the reconciler from quiet, and a later test's ```seon.await/await-quiet``` would wait on it forever) and their branches deleted. Its task and run facts stay on the shard's main and go with it. A test's scripted model (`:seon.config.ai/script`) or missing one (`:seon.config.ai/provider` `:none`) is its task's own setting (`in-agent`'s `:config`, the task's `:seon.task/config`, read first by ```seon.config/provider-at```: [config](config.md#the-resolver)), never a root argument, so those tests share one root where each distinct `--set` booted one (measured 2026-10-29, `bin/test --all seon.agent-test`, 70 tests in 4 shards: 7 min 42 s and the longest shard 396 s before, 5 min 22 s and 263 s after, at differing load; about 15 roots fewer in the namespace). Left red either way, load- and state-sensitive: `a-failed-call-keeps-what-it-sent`, `an-agent-allocates-little-from-ready-to-its-first-request` (12.3-16.2 MB against its 12 MB bound, on baseline code too) and `an-agents-collect-trip-is-the-configured-one` (flaky at its digest). A root's `:sets` stay for a setting no task can carry (a verdict cache as the test's subject, `an-agents-greens-and-a-checkouts-are-one-store`). A test whose agent merges into main (`:own-root? true`), and every test whose subject is a root's life (boot, stop, kill, a generation: ```seon.test-store/start-root!``` directly), keeps a root of its own. Measured 2026-10-27 on the shared machine (load about 8): a root's boot was 9.5 s of an in-agent test's 15 (4.8 s of it the source import), an attach on a running root 66 ms; ``seon.repl-test``'s nine agent tests went from 13.1-15.7 s each to 2.3-5.5 s after their shard's first. The digest is unchanged: the root imports and runs the checkout's tree (```seon.fx/read-source```), so an agent test's input is the tree (`seon.test-store-test/agent-tests-in-one-process-share-its-root`).
- **Tests.** A test's key is its reach digest (```seon.program/graph-index```: the forms it reaches through refs, macros, quoted names, methods, fixtures and schemas, plus the checkout's inputs with no program facts; [source](source.md#tests-run-by-reach)). The digest is the tree's, never the process's: the same commit gives the same digests in any checkout and any run (`seon.program-test/the-same-tree-gives-the-same-digests-in-any-checkout-and-any-run`). A test takes only what its reach names, never the whole tree and never the whole schema registry (owner, 2026-10-27: "I don't care if it's perfect and if it's possible a test could be doing other work we don't know of … no tests should include all of src"): a schema entry it names as a literal keyword, or that a contract it reaches names, and no more, though `seon.db/schema` derives the store's attributes from every entity schema and a renderer looks properties up by a computed key. A test that reads the checkout's own program from its kept db (a docstring, a form's source: `seon.main-test`'s whole-src checks) takes the text of src/ and test/ as a file class, `:seon.env/src` (`seon.test-store/kept-program-store`, [source](source.md#tests-run-by-reach)), so a docstring edit reruns those tests and no other (2026-10-30: one digest had stood for a red and a green). What a reach cannot show (a file read by a path built at run time, a schema looked up by a computed key) is the daily full run's to catch (`bin/test --all`). `bin/test [NS ...]` reads the program of the checkout's git tree, selects, and deals what runs, a namespace at a time, into `:seon.config.proofs/jobs` shards, each a process of its own started at once and reaped by the shell (```seon.proofs/run-tests!```). The program is a function of the tree, so it is kept per tree (```test-runner/program-db```): a branch per tree id in one LMDB store per checkout (`:seon.config.proofs/program-store`); a tree never seen is branched from the kept tree with the fewest changed program files and brought current by ```seon.source/refresh-tx```, and only an empty store imports the whole program; every text is read from the tree's git objects, one writer at a time per store; a test that reads the checkout's own program takes that branch from this store (```seon.test-store/kept-program-store```: the plan has just kept it) instead of importing the tree again in its shard's process (3.4 G ticks to the first test in each shard that read it), and a test that imports another tree takes ```seon.test-store/program-store```, a store of its process's own (measured 2026-10-23: the selection ~15 s with an empty store, 1.65 s on a kept tree, 1.7 s after a one-file edit; what is left is the reach graph, ~1 s). A shard caches its verdicts, greens and reds, with their failures and its tests' function costs, once it has run (```seon.fx/write-verdicts!```; a file the cache would not take is named, `UNRECORDED`, red, and its tests run again), unless the tree changed since the plan took its digests (an edit during the run: what ran is not what the digests name); a shard that dies midway stores nothing. A green is reused and a red alone runs again; a digest that judged both is flaky, red and never run again ([health](health.md#a-flaky-test)). Each run writes its shard files and logs under a directory of its own, `target/prove/<run-id>` (a timestamp and the pid, named on the run's first line; `bin/prove --out DIR` names one, as the :tests effect does for the plan it reads), so two runs on one checkout never overwrite each other (`seon.prove-test/two-runs-on-one-checkout-each-end-with-their-own-result`); a green run's directory is removed with the run (a red, killed or `--merge` run keeps its logs, the evidence; one `--out` names is its caller's), and a new worktree is cloned none of them (`bin/worktree`). The shards are dealt by each test's typical ms (the median of the ms its cached verdicts measured, ```seon.fx/typical-ms```; the largest let one hung run weigh a 17 s test as 625 s, and a merge's four shards ended 640, 62, 637 and 746 s in, 2026-10-29), the longest part first into the lightest shard, a namespace longer than a shard's share split into share-sized parts, so they end together, measured 2026-10-29 on `seon.agent-test seon.server-test seon.root-test` (`bin/test --all`, one copied verdict history): 657 s dealt by the largest ms (load 12-14), 545 s by the median, 499 s with a namespace over half a shard's share split (load 6-8), 416 s with `:seon.config.proofs/jobs` 6 (```seon.proofs/shards```, the one deal; measured 2026-10-23, dealt by count, the four shards of a full run ended 437, 397, 110 and 68 s in). A shard records its results only if the tree is the plan's after its run. An agent's test run (```seon.agent/run-tests-forked```) deals what it runs with the same function and the same median ms into at most `:seon.config.proofs/jobs` test children, each forked from the agent with its own run directory and heap cap and read on a fiber of its own (one child is the one-child case of the same code); a child that dies costs only the test it was running, as before. It forks no more children than the work needs: its tests' typical ms (a test never measured counts the mean of those measured, else `:seon.config.proofs/unmeasured-ms`) over `:seon.config.proofs/child-min-ms` (a fork, a child's start and exit measured 36-42 ms on 2026-10-29), so a handful of quick tests run in one child. Each child closes every pipe end it holds for a sibling. Measured 2026-10-29 (load 12-16): 262 tests of six namespaces, 91.7 s with jobs 1, 48.9 s with jobs 4. Memory: an idle child is ~10 MB (copy-on-write); each may grow to the agent's heap at its fork plus `:seon.config.agent/heap-extra-bytes` (1 GiB), so the worst case at jobs 4 is four times that on top of the agent.
- **Check steps.** Each `bin/check` step is keyed the same way by the `seon.check` mode functions its body runs: `seon.proofs/check-steps` is the one list of the steps (`bin/check` reads it from ``./seon steps``), and `seon.proofs/step-digests` digests them ([checks](checks.md#modes)). A change to `seon.check/smoke` or what it calls reruns smoke; a change to bin/, native/, resources/ or a pin (the binary's other inputs, `:env`) reruns every step. `bin/prove` runs the steps to run through `bin/check`'s own bodies, started by `bin/test` beside the test shards, not after them (they share no store, port or checkout state with a test's roots, so a merge's run takes the longer of the two, not the sum: 12 min of shards then 11 min of steps in the 2026-10-29 merge run; its output is `check.log` in the run's directory, printed after the shards') (`bin/check --steps target/prove`: the names in ``target/prove/steps``, the greens written to ``target/prove/green``) and stores the greens at their digests unless the binary was built from another tree than the plan's. A run's steps run at once, `:seon.config.proofs/jobs` at a time (a FIFO of tokens: a blocking read, no poll), the longest first by the last run's measured wall seconds, each on an APFS clone of the one seeded store (one root per store: two roots branching at once can drop a branch from the store's roster, task `seon.db/two-processes-branch-one-store-at-once`, and root collects only as the store's only writer, [storage](storage.md#collection)), deleted when it is green; `scale` runs alone after them, since it measures the machine's memory. Each step's wall and CPU seconds are kept beside its log (`STEP.time`); a shard's tests' ms are their results'.
- **Agents.** A Seon agent's run (the turn's observe, the judge's, the merge gate, and `(my.agent/prove)`) uses the same `plan` against the agent's base, main at its merge base (`seon.agent/test-plan`, [source](source.md#tests-run-by-reach)). Its digests' inputs with no program facts are its root's: the `:source` read (```seon.fx/read-source```, on an effect worker) answers the source tree's inputs (```seon.fx/inputs```), and ```seon.root/import-source!``` writes them on that boot's `:seon.root/source` fact only when the running binary is built from that very tree (``target/seon.tree``, which `bin/build` writes; ```seon.fx/tree-id```), with why not otherwise (`:unshared`). An agent uses only its root's current boot's inputs, so a previous root's never key its results. An agent's runs cache their verdicts as every run does ([verdicts](#verdicts-are-a-cache)), and an agent reads them from that one cache: a test that is the same is not run again once green, by an agent or a checkout, "especially when freshly branched" (owner, 2026-10-23); every eval is a recorded form, so the digest covers what ran (`seon.agent-test/an-agents-greens-and-a-checkouts-are-one-store`).
- **What an agent runs** (root's ruling (a), 2026-10-22, from step E's run 7, where a change to `seon.problems/report` put 294 reached tests in every turn's run). A turn runs the task's proofs and the tests the branch itself changed or added, each test under `:seon.config.agent/test-ticks`, the one per-test bound bin/test and the judge use too, so a test has one verdict wherever it runs; root's judge runs, once at the run's end, the plan's tests other than process tests that are not proofs, less every one green at its digest (what the turn ran green it never runs again, and with nothing left it forks nothing) (`(my.agent/prove)` runs the same). The turn whose proofs pass runs that selection itself before it is done or merges (`(agent/prove! :judge)` in ```seon.turn/work!```, its status read again from the branch): a red its change made in a test it reaches is a reason on its own status, and its next turn reads it, never a run that ends green for the judge to refuse after (owner, 2026-10-29: the reached tests run once the proofs are green and before done; md-scan #24 ended green on its proofs and the judge found 18 reds its change had made). The judge's run after it finds every result at its digest. These are the two stages the owner ruled (2026-10-30): light while the agent develops (its proofs and the tests its change reaches, in-process: a median change reaches 31 tests, under a second each), heavy once its proofs are green and it builds toward a merge (the process tests and the full suite, sharded: a process test ~15 s, most of it its shard's test root starting, the full suite 15.5 min on 4 shards (bin/test --all, main d339ca690c, 2026-10-30: shards 508, 512, 750 and 899 s; the longest shard sets the wall), measured 2026-10-30). A process test (one whose reach references a var of `:seon.config.source/process-vars`: an agent, a fork, a root of its own, the binary; ```seon.program/process-tests``` over ```seon.program/graph-index```, the same walk as the digests) never runs automatically unless it is one of the task's proofs (```seon.agent/run-selection```), and otherwise only when named (owner, 2026-10-23: "Tests shouldn't be running agent turns"): a process test left out is listed as deferred. Main's tests judge a branch whether or not it still holds them: a test its base holds that the branch removed is selected by both runs and defined in the test child from the base's source (```seon.agent/test-plan```'s `:removed`), so a red one refuses the run and names main's test (owner, 2026-10-26: "deleting the old test doesn't stop the old test from running"; `seon.agent-test/a-branch-that-deletes-mains-test-it-breaks-is-not-merged`). The plan reads one reach graph, main's: the fork server keeps it (`:graph` in its state, built at the first fork and brought to its db by ```seon.program/reach-update``` at each later one), and every agent forks holding it (```seon.agent/base-graph```), so its base's graph is that graph updated to the base (a resumed branch's older base, each merge-main), never built in the agent, and the branch's is the base's updated by what the branch changed since: measured 2026-10-23 on Seon's program, the base's graph 640 ms and 816 MB once, then a plan's update and index 20-45 ms for a one-form change, where each plan walked the branch whole before (0.5-1.1 s, five plans in a loop turn 4.3 s); with main's graph forked, a loop turn's five plans took 76 ms (measured 2026-10-23, e2e-loop, against 1.1 s with the base built per run). The turn's contract gaps read what changed (```seon.merge/uncontracted``` over ```seon.merge/delta-changes```, about 6 ms on Seon's program), and its unmerged entries read the program at their own keys only (```seon.merge/unmerged```).

- **The merge gate** (root's rulings, 2026-10-22/23; owner 2026-10-27: nobody asking). A merge whose branch's change reaches process tests (`:seon.run/deferred`, recorded by the judge) runs them before it merges, on a worktree of the root's gate checkout (`:seon.config.source/gate-checkout`; undeclared, the root's own source root, the standing root's merges tree, written by ```seon.root/start!```) at the merges head with the candidate's changed files over it, through prove's entry, named by exactly the deferred tests (`bin/prove --tests NS/TEST ...`, never their namespaces: the restart test's gate ran 48 tests, 47 of them nobody's deferral, for one deferred test) (the `:tests` effect, ```seon.fx/run-tests```, which reads each test's verdict at the digest prove's plan wrote in `target/prove/tests.edn`, from the verdict cache its run wrote: ```seon.fx/test-results```); their results are `:seon.run/deferred-results`, and a red, or a run that could not run them (`:error`), refuses the merge as a red proof does. A changed namespace the gate cannot read from the branch (no `:ns/file`: made at the REPL, never written) is named with why on the run (`:seon.run/gate-unread`) and on its `:unrun` row, and the run, over another tree than the one that merges, vouches for none of its tests (each `:error`). A root with no checkout to run them on (a test's root given no source) holds such a merge, its reason naming the tests. A test cannot be its own gate: the test that started a root (```seon.test-store/start-root!``` passes the running test as `--started-by`, the boot's `:seon.root/started-by` fact) is left out of its gate, with no result recorded for it. ```my.root/gate!``` still runs them for a run that merged before, and the `:seon.task/gate?` it sets is no longer read.

The full runs are explicit: `bin/test --all` and `bin/check 100`. They are also the safety net of the reach digests: a test is digested by the forms it reaches, never by the tree (owner, 2026-10-27), so a file it reads or a binary it runs that its reached forms do not name can change without rerunning it, and the full run finds it. The daily run is the cron proc's (`seon.cron`, at `:seon.config.proofs/full-run-at`, UTC; "" by default, set on the standing root of the main tree): it puts a full-run request for main on the test service's queue (`:full` mode, `seon.prove`), whose executor is the `:tests` effect (`bin/test --all` in a worktree of main, an OS child), its shards caching their verdicts as any run does; a root started after the time waits for the next day's. They run once per worktree session when its work is done, and before a merge that changes boot, the writer, the reconciler or the build; a red there becomes a task, not a blocked merge.

Measured on the shared machine, niced, at about 370 tests and 34 steps: selecting takes the import plus the digests, 7-12 s; an unchanged tree reuses every green (`bin/prove --checks`: 34 of 34 steps reused in 8.5 s, against about 6 minutes for `bin/check 100`); a one-defn change on the agent's turn path ran 71 tests and 33 steps in about 11 minutes; a cold run (nothing green) took about 19 minutes. A digest follows the tree, never what the process analyzed, and a test takes the whole tree as an input only through ```seon.program/env-readers```; a pin bump moves `:env` for every test, honestly.

## The test service

One proc, `:prove` (```seon.prove/prove-proc```, declared in `resources/seon/system.edn`), admits every request to run tests, whoever asks: a Claude session (the server's `:prove` op, the MCP tool `seon_prove`, ```seon.root/prove!```) and an agent's turn (```seon.agent/prove!```, which ```seon.turn/observe``` calls) share it, so a change is proved once.
- **The key names what the run reads** (```seon.prove/run-key```: `branch@digest`, with the test namespaces when a request names some, and `!turn` for an agent's turn, whose run is the proofs and what the branch changed; the judge's is the plan's tests; owner's ruling 2026-10-24, DECISIONS). The judge asks the service too: its `:judge` request makes the agent call ```seon.agent/prove!``` in mode `:judge`, so the judge's run caches its verdicts like any other. A branch's tx is not it: any write moves the tx, a run's own result facts, its prove agent's end and the eval that asked among them, so a key at the tx made every repeat ask a second run.
  - **Main's** digest is main's program digest (```seon.program/program-digest```: its live forms, schema entries and namespace tails, one read of their datoms), as an agent's is: its run reads main's program, its tests among it. A write of data never moves it; a moved key that changed nothing a test reaches is a re-plan that reuses every green. It is coarser than the per-test digests (```seon.agent/test-plan```) because it must be known before the run is admitted.
  - **An agent's** digest is its branch's program digest, its tests included; the root's inputs it also reads are fixed for the boot, as the service's state is. Its merge base is not in it: a merge of main that leaves the branch's program as it was keeps the answer, which then covers more tests than the new selection, not fewer. An agent's turn commits, then asks with the digest of its head (```seon.agent/prove!```); a session asks with the digest ```seon.root/prove!``` takes of the same head, so both ask for one key.
- **Admission.** One run at a time per checkout. A request whose key is running, or is the next to run, joins its waiters. A request for another key while a run is in flight replaces the next run of its branch (the latest wins, and the askers it replaced follow the newer run). Branches take turns in name order, so a burst on one branch never starves another. A key whose run ended is answered at once from that answer, until the key moves. Every waiter is answered exactly once (```seon.prove-test```).
- **A run is a chain of requests the proc sends the api.** The agent that holds the branch forks itself and runs the plan (```seon.agent/run-tests-forked```), on root's `:tests` request, which its `:tests` proc serves on its own fiber whatever its REPL runs, a prove of its own that waits for root's answer included (```seon.repl/tests-step```; md-scan #21 hung when a `:tests` waited behind a wait that held the agent's one loop, [processes](processes.md#the-agent-process)); main has no such agent, so a prove agent is forked from the fork server's main onto the `tests` branch, holding main's program and its tests (`:seon.config.source/dirs` takes `test/`), runs them, and is killed.
- **Main is proved at each program commit, nobody asking, when `:seon.config.proofs/prove-main-on-commit` says so (off by default: the run of all of main's tests in one child dies, task seon.agent/a-test-run-streams-its-reports).** The writer's commit notice (`:main`, a sliding buffer of one) is a request when its ops move the program (```seon.program/moves-program?```, what moves the fork server's reach graph too): a run of main keyed by its program digest, with no waiter, which a session asking for the same key joins. A burst of commits is one run, the latest. Its verdicts are cached by digest, so every agent forked after finds main's tests at their digests and runs none of them again (`seon.prove-test/main-is-proved-at-boot-with-the-config-on-nobody-asking`); process tests are left to the merge's `bin/prove --merge`.
- **Verdicts are cached by digest by the agent that ran them** ([verdicts](#verdicts-are-a-cache)), before the waiters are answered; nothing is written to the store. ```seon.agent/test-plan``` finds a verdict by digest (```seon.fx/stored-results```), green or red, so a digest that holds one is not run again. A red is reused as a green is, reported with the failures its run recorded and marked `:reused`, since a test's verdict is a function of its digest (one per-test tick bound everywhere).
- **The writer's commit notice** (`:main`, a sliding buffer of one beside the reconciler's) tells the proc main's latest tx. A process test (```seon.program/process-tests```) is left out of a run that names nothing, unless it is a proof (```seon.agent/run-selection```): the answer lists it as deferred.

## A branch proves its in-process tests, main's batch runs the process tests once

- **A ready branch that already contains current main**, and whose own plain `bin/prove` ran at that tip (with `bin/test` of the process-test namespaces its change reaches, or its `--merge`), is merged `--no-ff` with no run on main: the merge commit's tree is the one it proved, and main's first parent stays main, so `git log --first-parent` lists every merge (an ff hid 22+ commits, audit 2026-10-28). The merge message carries the branch's src delta, what it replaces and its measured number. Prefer this: ask a branch that is one merge behind to merge main and re-prove (every green at its digest is reused) rather than verifying on main.
- **A `bin/prove --merge` on main** runs only when branches are combined into a tree nobody has tested (two or more ready at once, or one that does not contain main). One run covers the batch, after one `bin/build`. A red names its test: revert only the branch whose change reaches it (`(my.agent/tests-reaching ...)`, or its diff against the test), send it back with the log, keep the rest. Then `bin/update`.
- **Fast path** (owner, 2026-10-27: "Don't wait for fixes that should just be merged and tested later"): the dev-speed branches (reuse, the shared test root, tree-id) merge as soon as their own targeted tests (the namespaces they changed plus their proofs) are green. Their first full run is the next one main does anyway; a red the branch caused is fixed forward within the hour, and reverted only if it breaks main for everyone. Each is reported to root in one line.
- **A pin bump** goes in a batch of its own, and the main tree's submodule checkouts must be moved to the new pins before `bin/build` (`git -C reference-code/<lib> checkout --detach <pin>` in the main tree; a merge moves the recorded pin, not the checkout, and a run on the old checkout says nothing about the bump: seen 2026-10-27). A Jolt or Chez bump re-runs every test and every check step once (the non-process set takes about 5 minutes): the runtime's gitlinks (`:seon.config.source/runtime-pins`) are in every digest's `:env` ([source](source.md#tests-run-by-reach); 2026-10-29: a cost proof stayed green across a Jolt bump that moved its numbers). For a datahike, persistent-sorted-set or konserve bump its diff and index tests run too, and every test whose reach names their namespaces. After the merge, `bin/build` syncs the main tree's submodules to the recorded pins (task seon.build/a-build-takes-its-pins), and before `bin/update` the merges worktree's submodules are moved with `bin/worktree --sync merges` (`bin/update` refuses a worktree whose submodule checkouts differ from its pins).
- Heavy runs: no slot lock (owner, 2026-10-27: "I want a lock free system").

## Every merge's `src` diff stat is read

Root reads every merge's `src` diff stat before merging, against the goal of about 10k lines of our own code. Every function a merge adds names the existing system it extends, or why none could carry it; a new namespace or mechanism where an existing one could be extended is sent back, not merged; the merge's commit message states its net `src` lines (`bin/laws growth` prints them and the definitions the branch adds), and a merge that grows `src` says what it deletes or plans to delete.

## Conflicts and pins

A conflict is resolved by copying each side's lines, never retyping; the lines after `>>>>>>>` may belong to both sides; each resolved file's forms must balance as its parents' do. Submodule pin bumps happen only in root's merges into main, never in a worktree session's merge of main. A pin bump reaches everything, so its merge also runs the cost proofs `bin/prove` leaves out (`bin/test seon.program-cost-test seon.record-cost-test`): Jolt 0d39edc3 passed prove and still made reach-update grow n^1.96. Commits in the forks ([forks](forks.md): Jolt, Chez, Datahike, konserve) carry no AI trailers. After a merge, root archives the worktree session first (its `bin/mcp` holds the worktree open), then removes its worktree ([machine](machine.md#disk-stays-bounded)).

A pin bump is verified in a worktree with every Jolt gate, run as `make -o submodules GATE` (plain `make` runs `git submodule update`, which fails in a worktree); a Jolt pin that skipped a gate regressed once, so it counts as ready only with each gate's verdict (the one environmental red is fiberspoll's socket test, red on stock Chez too, because macOS refuses a connect to a full backlog at once). `bin/build` resets every submodule checkout to the pin in HEAD, so a pin bump is committed before building, or a gate run on the checkout tests the old code. Stage explicit paths: `git add -A` staged lagging submodule checkouts as gitlink changes.

## Seon's merge is a three-way merge of the program

Seon's own merges (a branch into main, main into a branch) are git's three-way merge over the program as data, never over files.

A db's program is a map from keys (``[:form id]``, ``[:var sym]``, ``[:schema k]``, a declared datum) to content (```seon.merge/program``` of a db and its declared data attributes, which only tests read whole; a merge reads ```seon.merge/program-of``` at the keys that differ), and ```seon.merge/three-way``` compares base, ours and theirs: each side's changes, the keys to apply, and the conflicts. A merge reads only where the dbs differ (```seon.merge/delta-three-way```: the keys the datoms that differ bear, read on each side by index seeks, never whole programs; [storage](storage.md#merges-read-what-changed)). The writer's merges use it (`seon.writer/writer-proc`), and it is the one derivation behind the done rule's unmerged entries, the agent's merge of main and the dashboard. What merges is carried as it is: the branch's own datoms for those keys, with their entity and transaction ids, after the declarations of the attributes they use that the target lacks (```seon.merge/merge-tx```). A conflict stays on the branch as an unmerged entry (```seon.merge/unmerged```), base, ours and theirs as data, until the branch redefines the key or resolves it (`my.branch/resolve!`, ```seon.merge/resolve-tx```). The files a merge touches are written back by [source](source.md); a merge task's turns are [turn](turn.md#a-merge-tasks-loop).

Main took 301 first-parent merges from 2026-10-20 to 2026-10-27, all by git (worktree merges and `bin/prove --merge`); Seon's own merge (octopus merge, write-back) made 14, all only on `jolt/seon-merges`. The one-merge design is task `seon.merge/one-merge-system`.

## Root repairs a failed merge from its REPL

Root's REPL (`seon_eval` as root, or `printf '{:op :eval :agent "root" :code "..."}\n' | nc -w 30 127.0.0.1 PORT`, newlines in the code escaped as `\n`, one request per line) repairs the four failures with the tools that exist; staged and repaired once on a worktree root (2026-10-27, the staging recipe and each reply in git history).
- **Merge refused (`:hairy`, the run ended `:merge-failed`):** `(my.root/problems sys)` shows `:merge` and `:failed` rows; `(select-keys (get (seon.task/runs @(:conn sys)) RUN) [:seon.run/status :seon.run/outcome :seon.run/conflicts :seon.run/unmerged])` is the best read (each conflict with base, ours and theirs). Repair: `{:op :attach :task "T"}` answers `{:agent A ...}`; in agent A `(mapv (juxt :key :kind) (my.branch/unmerged))`, then `(doseq [e (my.branch/unmerged)] (my.branch/resolve! (second (:key e)) :theirs))` (or redefine the var), then `{:op :done :agent "A"}` answers the verdict. Root has no conflict function of its own: `my.branch` runs in an agent.
- **Green on its branch, red once merged (`:semantic`):** the held reason reads `proof-unknown`, not "merge main first". Attach, `(my.branch/merge-main!)`, rerun the proofs, fix, `:done`. The writer refuses a branch behind main, so a red merged program never reaches main.
- **A held task:** raise the limit that held it (`@(root/transact-main! sys [{:seon.task/id "T" :seon.config.merge/max-conflicts 3}])`, flat keys on the task), then `(my.root/run! sys ["T"])`. A run stuck `:behind` has no repair yet (task `seon.root/a-behind-merge-ends-in-a-fact`); `(my.root/cancel! sys ["T"])` ends it and the branch's work is lost.
- **A write-back that failed (`:seon.run/commit-error`, an `:effect` row for `seon.fx/git-commit`):** remove the cause (a stale `.git/refs/heads/jolt/seon-merges.lock`), then `(my.root/write-back! sys [RUN-ID ...])`. A worktree root writes its own `jolt/seon-merges-<worktree>`, never the main tree's.
- After an attach, the task's model stays "outside" (task `seon.root/an-attached-run-is-taken-back-by-root`): retract `:seon.task/model` before releasing it again.

## Not built: a merge queue on root

Root's merges of worktree branches are git merges, batched by hand as above. Seon's own merges are merge tasks judged by the reconciler, one at a time: an octopus merge of several merge runs is built and off (`:seon.config.merge/max-running` 1, until one combined test run of all its members is proven). No queue on root merges main into each candidate, proves the merged result and batches the disjoint ones, and builds, tests and checks are not tasks on root (task ``seon.reconcile/a-check-step-is-a-task``).

## Main moved is said at every eval

Every `seon_eval` answer an outside agent gets carries one line saying how main differs from its branch, or none when main's head is still its merge base (owner, 2026-10-28: "there are never any surprises"). ```seon.agent/main-line``` makes it from the merge base, the branch and main as the agent last heard it:
- how many names main changed since the base (```seon.merge/readiness```, the three-way a merge of main runs, so it costs what changed on each side);
- those of them the branch changed too;
- those its changed functions call;
- those a merge of main would conflict on;
- and the form that merges main, `(my.branch/merge-main!)`.

Each list is cut by the one printer. ```seon.repl/eval-string``` puts it on the answer as `:main`, live, never recorded: it is a function of the db at t. Its cost is what changed (```seon.agent-test/main-line-costs-what-changed```; measured 2026-10-29 with `seon.cost/measure` on a four-var program with two names moved on main): while main is the base it is O(1) (680 ticks, 3 contracted calls; ```seon.agent/main-difference``` compares commits before it calls); the first eval at a new main pays main's diff since the base (```seon.agent/main-changes```, held keyed by the two points it is a function of, evicted by the next pair and regenerated from the two dbs) and the branch's (```seon.agent/branch-changes```): 9.2 M ticks, 25.8 MB, 172 calls; each later eval at that main pays only the branch's diff when the branch moved and one query over its changed vars: 64.6 k ticks, 376 KB, 4 calls (before: 13.9 M ticks, 38.8 MB and 304 calls on every eval, 13.0 M with main the base, which `seon.merge/readiness` ran each time). A conflict is a name both changed to different content, read from the two diffs. The line is made from main as the agent last heard it (```seon.agent/main-difference``` reads no store: a read of main's head on every eval held the agent's heap past its ceiling in `seon.agent-test/an-agent-finds-no-repository`), so an agent that hears no main is told only what it last heard until root pushes main's commit (task ``seon.writer/main-notices-carry-a-commit-not-a-db``). It reaches the outside agent's `seon_eval` answer (```seon.server/op-answer``` `:eval` passes `:main` on); an in-process model agent's turn reads the recorded eval, which does not hold `:main`, so it is not told on each eval. The agent merges main when it chooses; at `seon_done` the done answer (```seon.server/verdict-line```: one line, each red with its first failure, and the form that reads the whole verdict) names the same difference, so nothing in it is new. Proofs: `seon.agent-test/main-moved-is-said-at-every-eval`, `seon.server-test/the-done-answer-is-a-line-and-a-handle`.

## Verdicts are a cache

A test's or a check step's verdict is derived data, a function of the code it reaches (its reach digest), so it is kept as an evictable cache by digest outside the store, and the store keeps only decisions (owner, 2026-10-28: "derived data may be cached with the understanding that it may be evicted at any time"; AGENTS §5). It replaced the result facts on the standing root's main (2026-10-27 to 2026-10-28: 250,796 datoms, 28% of main's history, and an agent's start heap +35%, the overnight audit's worst finding), which in turn had replaced the uncapped `test-results/` directory (349,131 files, 1.3 GB, which nothing reads now; the owner's to remove).
- **Where.** One directory for every checkout, `:seon.config.proofs/results-dir`, which `bin/env` sets to the main tree's `target/results` (found from git's common dir, as the build caches are), so a digest proved in any worktree, by an agent or by the merge gate's checkout is reused by all. A file a key, digest and status: `<ns>/<test>/<digest>.pass.edn` for a green, `<digest>.red.edn` for a red; a `bin/check` step's under `steps/<step>/`.
- **Keys.** A test's file is under its var's name, a step's under `steps/<step>/`, and each contract of the generative check under `steps/mg/<ns>/<name>/` ([checks](checks.md#the-generative-check-is-per-function)): `mg-check` has no digest of its own, only its functions do.
- **Who writes.** Whoever ran the test, with no round trip to a root: ```seon.fx/write-verdicts!``` stages each file and renames it over (```seon.fx/write-file```), so no reader sees half a file and no lock is needed. `bin/test`'s shards, `bin/prove`'s steps, an agent's test run (```seon.agent/run-tests-forked```, whoever asked: a turn, the judge, the test service) and the merge gate's run all write the same way. A file names its writer (the run's id, tree or branch, the agent): recorded, never judged. A file the cache would not take is named (`UNRECORDED`), the run ends red, and that test runs again; nothing is queued.
- **What is written: only what ran.** A test reused at its digest writes nothing. A test that ran writes its status, failures, cost proof's report, ms, ticks, bytes and what it spent in each contracted function ({var [calls ticks self-ticks bytes self-bytes]}), once a digest: nothing is copied per run. Flaky: green and red are two files, so two writers of one digest never lose either, and the digest is flaky while both exist ([health](health.md#a-flaky-test)).
- **Beside it, facts on the agent's branch.** An agent's run of its tests also records each result on the test's var entity on its branch (```seon.proofs/result-tx```, written by ```seon.agent/run-tests-forked``` when the run ends, in every mode but main's): `:seon.test/digest`, `:seon.test/status` (`:green` `:red` `:flaky`), the failing assertions as data as `:seon.test/failures` while not green (the test child's reports, every one), and the sums `:seon.test/runs` `:ms` `:ticks` `:bytes` over the runs at that digest, each `noHistory` (overwritten in place). A test reused from the cache gets its digest, status and kept failures when the branch's facts differ; a test whose reach digest moved and that the run did not judge loses its facts (a status is the verdict at the digest it has now: absent is unknown); a run that changes nothing writes nothing. The agent's record (@ctx, under the task's `:proved`) holds them and the task part of the one layout renders each proof's status from there (`seon.render.ui/task-data`); the cache stays what reuse reads (also `my.task/status`, for now), and main's prove and `bin/test` write no facts yet (task seon.proofs/test-results-are-a-few-facts).
- **What reads them.** A plan, two file checks a key (```seon.fx/stored-results```): bin/test, bin/prove, an agent's test plan, the merge gate's read-back (```seon.fx/test-results```). A green is its file's existence, never read (its content is nothing a plan uses: 2,280 reads were 76.8 MB and 25.1 M ticks of one turn, 2.1 MB and 0.8 M ticks as file checks, `seon.results-test/a-green-is-found-by-its-file-never-read`); a red's file is read, for its failures. A red's file that cannot be read is an error, never a miss (```seon.fx/read-verdict```, [failure points](failure-points.md)): the plan says so (`TEST FAILED`, `:seon.proofs/unread`). The deal's order reads each test's median measured ms over its files (```seon.fx/typical-ms```).
- **The bound, with no clock.** The whole cache holds at most `:seon.config.proofs/results-max-bytes` (512 MB; 121 MB in 27,079 files on 2026-10-29). A write that takes it past the bound evicts the least recently used verdicts (```seon.fx/evict!```): oldest file mtime first, greens and reds alike, never one just written, until the cache is under; below the bound nothing goes. A read touches the mtime (```seon.fx/stored-results```) and a write sets it, so a verdict a run reuses stays and a key whose test no longer exists ages out with no special case. The size is kept in the cache's `.size` file (other writers' changes make it a guess, corrected by the next count): a write under the bound reads and rewrites that one file and counts nothing (cost `seon.results-test/a-write-under-capacity-costs-nothing-of-the-cache`); past it the verdict files are counted once by metadata and the oldest removed (`seon.results-test/a-write-past-capacity-counts-the-cache-once`). An evicted verdict's test runs again once.
- **The questions** ([cost](cost.md#what-a-test-run-measures)): which tests at a tree's digests exercise f, and how much (```seon.proofs/exercising``` over ```seon.fx/details```), and its cost per call over them (```seon.proofs/per-call```). An agent asks ```my.agent/cost```. The cost trend over time lives in the merges' commit messages and the perf papers, not in the cache.

## A test's tick budget

Every test runs under a budget of engine ticks of its own (work done, never time; owner, 2026-10-29: "I don't want long running tests period and I want to catch the problems sooner"), set in one place, ```seon.proofs/run-tests!``` (bin/test's shards, an agent's test child, the judge): `min(:seon.config.agent/test-ticks, max(:seon.config.agent/test-ticks-floor, :seon.config.agent/test-ticks-factor x the median of its green verdicts' ticks at any digest))`, from ```seon.fx/test-budgets```, which reads the history once a run (about 2.5 ms a test: 1,367 tests in 3.5 s over 45,000 verdicts, from each green file's first 768 bytes). A test with no green gets the floor, a `^{:seon.test/ticks N}` on its deftest raises its own budget to N (never past `test-ticks`; the mark is its source, so it is in its digest), and the budget used is on its result (`:budget`, in the verdict). A test past it is red with the typed `:seon.test/ticks-spent` `{:ticks :budget}` naming the budget, and the run goes on ([failure points](failure-points.md)).

- **Chosen from the cache** (2026-10-29, 45,333 verdicts of 1,194 tests): newest green ticks median 1.7 M, p90 153 M, p99 1.7 G, max 8.3 G. A test's own greens sit at 1.0 to 1.07 x their median through p90 and 3.3 x at p99, because the digest moves with the code a test reaches, and the worst are tests that scan the source (a green at 3 G against a median of 1.8 M). Floor 4 G (1 to 5 s of work) and factor 10 trip no green but one runaway: `seon.db-test/a-create-that-fails-leaves-no-store`, three greens of 81 to 147 G against a median of 264 M. A floor of 1 G tripped 8 greens at factor 20 and 14 at 50.
- **The history is not in the digest** (the choice). A verdict is reused by digest, so a budget that read the history would move every digest with each green written, and no verdict would reuse. The digest takes the three config keys instead (```seon.fx/inputs```' `:env`, as it takes `test-ticks`), so changing a key reruns everything once, as changing the cap does. The cost: a red `:seon.test/ticks-spent` is cached at its digest like any red, and a test that legitimately needs more than the factor allows has no green to raise its median, so the author marks it (`:seon.test/ticks`), which moves its digest.
- **A cap lower than the floor wins** (`test-ticks` is the cap on every test), and a test whose median green is itself large (the heaviest: 8.3 G, so a budget of 83 G under a 200 G cap) is bounded by the factor and the cap alone.
