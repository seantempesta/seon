# Merging

How a branch is merged into main: what it runs, how batches are proven, and how conflicts are resolved. Who merges and why is [AGENTS.md §3](../AGENTS.md) ("Integrate small and often", "Testing: compute only what is needed"); the machine the proofs run on is [machine](machine.md).

## A worktree session works in a checkout of its own

A worktree session is a separate instance of the whole system: `bin/worktree NAME` (run from the main tree) makes `../next-NAME` on branch `jolt/NAME` from main, with its own submodule checkouts at their pins, an APFS clone of `target/` (so `nice -n 15 bin/build seon` is the only build), its own ports (`config/local.edn`, `bin/ports`) and its own stores under its `runs/`. In it:
- `bin/root start | status | stop` runs that worktree's own root, never the standing one (7888); a Claude session started in the worktree reaches it through the committed `.mcp.json` (`./bin/mcp` asks this checkout's root);
- `bin/prove` runs what the change reaches, nothing else ([below](#a-merge-runs-what-the-change-reaches)); `bin/test NS` runs one namespace's selection and `bin/check MODE` one check step; `bin/check` (one mode or a run) works on a store of the checks' own, `target/check-store`, seeded when missing (`SEON_STORE` names another): `runs/store` is the worktree root's, made without the example program the checks seed, so reusing it fails steps falsely;
- after each merge into main: `git merge main` in the worktree, then `bin/worktree --sync NAME` (it moves only this worktree's submodule checkouts to the pins its branch records; never `git submodule` in a worktree);
- a submodule the session adds (`reference-code/X`) is written as a `.gitmodules` entry and a gitlink, with its checkout cloned from a local copy; root initializes it in the main tree when it merges (`git submodule update --init reference-code/X`), so later worktrees get it.

`bin/worktree-check` (run from the main tree) proves this whole workflow end to end with a throwaway worktree session and removes it; run it after a change to `bin/worktree`, `bin/root`, `bin/mcp` or the build. Leave nothing running: `bin/root stop` before you report. Root removes the worktree after the merge (`bin/worktree --remove NAME`).

## A worktree session's part

A worktree session merges main into its branch, proves the merged result with `bin/prove`, and reports. Branches live hours: merge main into yours after every merge into main. Iterate at the REPL first, then with `bin/prove` (or `bin/test NS`), never a full run per edit. Long runs only when the work is done: the full `bin/test --all` and `bin/check 100` run once per session, when it believes its task is finished and its review findings are fixed. To be merged, report the commits, proofs red → green, numbers against estimates, what you deleted, `bin/prove`'s last lines (and the check's `target/check/<time>/` path when steps ran), and that nothing of yours is running.

## Every branch is reviewed before it merges

A reviewer reads the branch's diff against main for AGENTS §9's mistakes (a guard, a fake default, a clock deciding, a second mechanism, a fix at the reader instead of the producer, an old word of §7a, a test that cannot fail, an ignored answer), each finding with its file:line and its right fix (owner, 2026-10-22). The worktree session fixes them before its branch merges; the proof it reports is the run after the fixes.

## Root merges, and reads the verdict

Root merges the branch, never copying files over newer changes, and reads the merged tree's proof to its last line before main moves.
- Every stage's exit status decides the next: no pipe hides a failure (`setopt pipefail`, output to a log), and a check counts only if the build before it succeeded and the binary was built from the tree it proves (`bin/test` builds `target/seon` whenever anything runs).
- Root rebuilds main as part of every merge, so a worktree made from main never reads config with a stale binary.

## A merge runs what the change reaches

A merge runs what the change reaches, not every check (owner, 2026-10-21: "I want faster iteration not a matrix with every run permutation"; 2026-10-22: "why don't we have a comprehensive policy where we are only running tests that have changed?"). The merge's proof is `bin/prove` on the merged tree, then `bin/check smoke`; `bin/laws` (every law's sites) runs inside it as a step keyed by the whole tree. One rule selects for everyone (task `seon.proofs/prove-runs-what-a-change-reaches`): a key runs exactly when no green result is stored at its reach digest (```seon.proofs/plan```), in the one results directory every checkout shares (`:seon.config.source/test-results-dir`), so an unchanged tree runs nothing and a result proven in any checkout is reused in every other.
- **Tests.** A test's key is its reach digest (```seon.program/reach-digests```: the forms it reaches through refs, macros, quoted names, methods, fixtures and schemas, plus the checkout's inputs with no program facts; [source](source.md#tests-run-by-reach)). The digest is the tree's, never the process's: the same commit gives the same digests in any checkout and any run (`seon.proofs-test/the-same-tree-gives-the-same-digests-in-any-checkout-and-any-run`). `bin/test [NS ...]` imports src and test once, selects, and deals what runs, a namespace at a time, into `:seon.config.proofs/jobs` shards (```seon.proofs/shards```), each a process of its own started at once and reaped by the shell (```seon.proofs/run-tests!```): a fork of the runner cannot connect to a store, since Datahike's connection state does not survive fork (measured 2026-10-22: the child's first `d/connect` never returns). Each result is stored as it ends (```seon.proofs/store!```, through ```seon.fx/write-file```, its answer read: a failed write is an `:error` result); only greens are reused, so a red runs again.
- **Check steps.** Each `bin/check` step is keyed the same way by the `seon.check` mode functions its body runs (```seon.proofs/check-steps```, the one list of the steps: bin/check reads it from `./seon steps` and fails a step it does not name; digested with ```seon.proofs/step-digests```, which names a step whose function the program no longer defines as missing, red). A change to `seon.check/smoke` or what it calls reruns smoke; a change to bin/, native/, resources/ or a pin (the binary's other inputs, `:env`) reruns every step. `bin/prove` runs the steps to run through `bin/check`'s own bodies (`bin/check --steps target/prove`: the names in `target/prove/steps`, the greens written to `target/prove/green`) and stores the greens at their digests.
- **Agents.** A Seon agent's run (the turn's observe, the judge's `:tests`, the merge gate, and `(my.agent/prove)`) uses the same `plan` against the agent's base, main at its merge base (```seon.agent/test-plan```): the proofs and the tests whose digest moved, each green one held at its digest reused (```seon.agent/run-tests-forked```).

The full runs are explicit: `bin/test --all` and `bin/check 100`. They run once a day in the background, once per worktree session when its work is done, and before a merge that changes boot, the writer, the reconciler or the build; a red there becomes a task, not a blocked merge.

Measured 2026-10-22 (worktree session PROVE, `jolt/prove` on main `fcac0df`, 369 tests and 34 steps, the shared machine niced): selecting takes the import plus the digests, 7-12 s. An unchanged tree reuses every green: `bin/prove --checks` answers 34 of 34 steps reused in 8.5 s (the full `bin/check 100` takes ~6 min), `bin/prove` ran only the one red test (402 of 403 reused, 1:05 with the build its run needs), and two namespaces' 32 tests were all reused in 14.7 s. A one-defn change on the agent's turn path (`seon.reader/forgive`'s docstring) ran 71 tests and 33 steps, 10:41; a change only seon.proofs reaches reran 6 of `seon.proofs-test`'s 8 tests and reused the others. The cold run (nothing green at its digests: every test in 4 shards and every step) took 18:39, of which the steps 6 min and three shards 10-122 s; the fourth was held by `seon.source-test/a-restart-catches-up-and-a-new-generation-resumes`, red on main and waiting on an `nc` that never times out, until its root was killed. Before, `bin/test --reach` with nothing reusable ran 354 tests serially in 12:41, beside a full `bin/check 100`, since no step was selected; and it reused nothing across checkouts or after any edit, for three causes fixed at the producer: a quoted name counted only when its var existed yet (the digests followed what the process had analyzed: 43 of 387 equal on a second import of the same tree), 327 of 368 tests took the whole tree as an input (```seon.program/env-readers```), and every merge's pin bump moves `:env` for every test (honestly).

## Ready branches merge in batches

Root merges ready branches in batches (owner, 2026-10-21: "this is taking forever"; three branches merged one at a time cost ~40 minutes of serial full checks, each ~10 min, plus re-proving after every main move). Branches that are ready, reviewed and file-disjoint (or whose overlaps are both-sides additions) merge onto one integration branch from main and are proven together by one `bin/prove` there (each branch's own greens are reused; only what the combination moved runs); then main moves to it.

## Every merge's `src` diff stat is read

Root reads every merge's `src` diff stat before merging (owner, 2026-10-21: "If we are building shit we don't need to build and not using the existing systems or extending them for minimal code we are doing the wrong thing"; `src` grew 14.1k -> 15.9k lines in one day against the ~10k goal). Every function a merge adds names the existing system it extends, or why none could carry it; a new namespace or mechanism where an existing one could be extended is sent back, not merged; the merge's commit message states its net `src` lines (`bin/laws growth` prints them and the definitions the branch adds), and a merge that grows `src` says what it deletes or plans to delete.

## Conflicts and pins

A conflict is resolved by copying each side's lines, never retyping; the lines after `>>>>>>>` may belong to both sides; each resolved file's forms must balance as its parents' do. Submodule pin bumps happen only in root's merges into main, never in a worktree session's merge of main. Commits in the forks ([forks](forks.md): Jolt, Chez, Datahike, konserve) carry no AI trailers. After a merge, root removes the session's worktree and prunes checks and generations ([machine](machine.md#disk-stays-bounded)).

## Where this is going

A merge queue on the one root that merges main into each candidate, runs `prove` on the merged result, and batches disjoint candidates. All builds, tests and checks become tasks on that root, run as their workload allows, with results reused by digest (as `prove` does today). Seon's own merges get the same gate, and `:behind` fires only when main's change touches what the branch changes or reaches.
