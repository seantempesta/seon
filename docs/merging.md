# Merging

How a branch is merged into main: what it runs, how batches are proven, and how conflicts are resolved. Whoever proves a branch lands it ([below](#a-branch-lands-with-binland)); why is [AGENTS.md §3](../AGENTS.md) ("Land small and often", "Testing: compute only what is needed"); the machine the proofs run on is [machine](machine.md).

## A worktree session works in a checkout of its own

A worktree session is a separate instance of the whole system: `bin/worktree NAME` (run from the main tree) makes a worktree on branch ``jolt/NAME`` from main (at `.worktrees/NAME` inside the root; `bin/worktree --path NAME` prints it), with its own submodule checkouts at their pins, an APFS clone of `target/` (so `nice -n 15 bin/build seon` is the only build), its own ports (`config/local.edn`, `bin/ports`) and its own stores under its `runs/`. In it:
- `bin/root start | status | stop` runs that worktree's own root, never the standing one (7888); a Claude session started in the worktree reaches it through the committed `.mcp.json` (`./bin/mcp` asks this checkout's root);
- `bin/prove` runs what the change reaches, nothing else ([below](#a-merge-runs-what-the-change-reaches)); `bin/test NS` runs one namespace's selection and `bin/check MODE` one check step; `bin/check` (one mode or a run) works on a store of the checks' own, ``target/check-store``, seeded when missing (`SEON_STORE` names another): `runs/store` is the worktree root's, made without the example program the checks seed, so reusing it fails steps falsely;
- after each merge into main: `git merge main` in the worktree, then `bin/worktree --sync NAME` (it moves only this worktree's submodule checkouts to the pins its branch records; never `git submodule` in a worktree);
- a submodule the session adds (``reference-code/X``) is written as a `.gitmodules` entry and a gitlink, with its checkout cloned from a local copy; root initializes it in the main tree when it merges (`git submodule update --init reference-code/X`), so later worktrees get it.

`bin/worktree-check` (run from the main tree) proves this whole workflow end to end with a throwaway worktree session and removes it; run it after a change to `bin/worktree`, `bin/root`, `bin/mcp` or the build. Leave nothing running: `bin/root stop` before you land. Remove the worktree once its branch has landed and you are done with it (`bin/worktree --remove NAME`).

## A branch lands with bin/land

Every session, Claude's or Seon's, works its branch in a worktree of its own (`bin/worktree NAME`) and lands it itself with `bin/land [-F MSGFILE]` run in that worktree; the main tree (`~/src/seon-next`) stays on main and clean, and nobody works or checks out a branch there (owner, 2026-11-08: a branch checked out there had stopped every other session's merge and `bin/update`). `bin/land`:
1. merges main into the branch (a conflict stops it: resolve, commit, run it again), and refuses, before any proof, a message whose `Completes: ns/name` names a task the tree still holds an entry for ([a merge says what it completes](#a-merge-says-what-it-completes): the test of it reads main's messages, so it went red only after such a landing);
2. runs `bin/prove --merge` on that tip, niced, beside any other run. A bare `bin/prove` and a `--merge` run leave the same nothing out and share one green marker per tree, so a branch that held main when its session proved it is answered at once and merges with nothing run; when main moved, only the tests main's new commits reach run, every other green reused from the one cache all checkouts share (`target/results` of the main tree, [verdicts are a cache](#verdicts-are-a-cache));
3. moves main to a merge commit whose tree is the proved tip's (`git commit-tree`, then `git update-ref` with main's old value): no checkout of main. When another landing moved main during the proof, it merges main in and lands without proving again: what main gained was proved when it landed, and chasing main under load could prove without end (owner, 2026-11-08: "that's fucked"); the message says the merge was unproved, and the daily full run catches the combination. Only a conflict stops it;
4. runs `bin/update`, which first brings the main tree's files to main, then restarts the standing root on it;
5. removes the landed worktree (`bin/worktree --remove`) and its branch (`git branch -d`, which refuses an unmerged one), so nobody cleans up after a landing (owner, 2026-11-08: "Why are we always having to do cleanup?"). It keeps the worktree, and says why, when anything in it is uncommitted or untracked, or a process other than the landing's own (its ancestors, and the members of its prove's process group, whose last processes can still be ending when the wait returns) has its working directory there (a demo root, a helper's shell): a change made while it landed is never lost. The next change starts in a new worktree (`bin/worktree NAME`), branched from main or from the landed branch's tip.

A landing that changes what the store holds (an attribute moves between entities, a schema key is removed or renamed) erases the standing store in that landing, never saved up for a window of several (owner, 2026-11-10): before `bin/land`, the landing session tells the sessions working on the standing root that it is about to be erased and waits for each to say nothing of theirs is mid-run on it; the session that runs the standing root moves `runs/store` aside and runs `bin/update`. While Seon holds no user's data the standing store is test data, erased and never migrated ([machine](machine.md#disk-stays-bounded)).

A stop ends everything a run started: `bin/prove` makes its run a process group of its own (a prove inside a run, a test's nested gate, stays in that run's), and a TERM, INT or HUP to it, or to the `bin/land` waiting on it, ends the whole group, shards, check steps and build included; a test's roots end with their test process besides (`:seon.config.root/end-with`). Before 2026-11-08 a stopped landing left its prove, shards and check steps running, and their roots for a session to find. It ends on `LANDED` or `LAND FAILED`. The message file says what the merge completes and its numbers (AGENTS §3, [a merge says what it completes](#a-merge-says-what-it-completes)); `bin/prove`'s line is added. Branches live hours: land small and often. The recipe (AGENTS §3): iterate with `bin/test NS`, prove once with a bare `bin/prove` when done, then `bin/land`; nothing is run twice.

What a session does around a landing:
- **It checks its change and hands the tip over** (owner, 2026-11-10: "I don't want 100% separated work separately running all the tests for each little change"): the checks of AGENTS.md §3, then a message to the managing session with the branch and its tip. A session lands its own branch only when the managing session asks it to (a pin bump's whole prove is its own: [conflicts and pins](#conflicts-and-pins)).
- **It never waits on a landing** (owner, 2026-11-08: "Agents should assume that shit is going to work and to build on the batched codebase"): the next change starts at once in a new worktree, from main or from its own tip.
- **It never touches a worktree while its `bin/land` runs.** On 2026-11-08 files were edited, the binary rebuilt and a demo root started in `.worktrees/uifix` while its landing proved, and the landing went red on `seon.check-test/a-failed-seed-says-failed`, a test that boots that tree's binary.
- **Root follows main through `bin/update` only,** never `bin/root stop` and `start`: the standing root imports main's program from `.worktrees/merges`, which only `bin/update` moves. On 2026-10-26 root was restarted by stop and start after every merge, and main's program stood still for 262 commits, unnoticed. After a landing, read that a just-merged var's entity is on root's main. `bin/update` refuses a write-back tree whose index or files differ from its HEAD, and says `UPDATE OK` only once that tree's HEAD contains main (`bin/update --merges-only DIR` runs that step alone; `seon.source-test/an-update-never-says-ok-on-a-merge-that-did-nothing`): on 2026-11-11 eight updates said OK while `.worktrees/merges` stayed at batch 24, its index left behind by the write-back's commit (task `seon.fx/a-write-back-moves-the-checked-out-trees-files`).
- **`LANDED, ROOT NOT UPDATED` means git's main moved and the standing root's main did not:** the bridge's write was refused, so `bin/land` ran no `bin/update` (a new binary on main's older program would fork no agent). The session reads the refusal `bin/land` printed, fixes its cause on a new branch if it is the landing's (a task file or page the load refuses), and brings root's main to the tree by one of the acts in [files and the db](source.md#files-and-the-db-two-directions): a re-index at root (```my.root/import!```, ```my.root/load-docs!```, ```my.root/load-tasks!```) then `bin/update`, or, with the other sessions warned as for any erase, `bin/root stop`, `bin/root start --reindex` and `bin/update`. It never runs `bin/update` alone first: that root would start on a binary of another program and its last line would say `UPDATE FAILED: ROOT STALE BINARY`.
- **The main tree is never on a topic branch.** The standing root once advanced the merges branch to the main tree's checked-out branch, so a held branch reached main unreviewed (7dfd1f7b75, 2026-10-29); a branch checked out there also stops every other session's merge.

## The managing session lands a batch

Sessions' ready branches land together, proved once (owner, 2026-11-10: "Can we batch them together?"; before it each session proved and landed its own, and three proves at once took the machine to load 43).

1. **Build it:** a worktree from main (`bin/worktree batch-N`), each ready tip merged in. A conflict is resolved keeping both sides' intent, and when the reason one side differs is a guess, its owner is asked first (2026-11-10: a task entry restored on purpose was dropped as an accident).
2. **Check before proving:** `git status --short` is clean; `bin/laws`, `bin/check health` and `seon.main-test` pass on the merged tree. They take seconds and are what a session's own named runs most often missed. The prove is never chained after a command that can fail.
3. **Prove once:** `nice -n 15 bin/prove`, in the background, with its expected end noted. Green is the prove's own last line and each check step's own log, never a filtered log: a step that dies writes no verdict line.
4. **A red batch is taken apart, not waited on:** the failure is read; the branch at fault is found from it, or by running the one failing test on each merge; that branch is taken out (`git revert -m 1 <its merge>` when it applies cleanly, else the batch is built again without it), the rest is proved and landed, and the owner of the branch gets the evidence. A fix of a line or two that is plainly right (a site's name in the wiki, a date in a docstring) is made in the batch and said in the note.
5. **Land:** `bin/land -F MSGFILE`; the note says what the batch holds, what was taken out and why, and what is open.

What a whole prove caught on 2026-11-10 that a session's own runs had not: a dependency pin (6 reds after runs of parts), a change to root's writer (10 reds behind greens reused from before the change: [what a digest holds](#what-a-digest-holds-and-what-it-does-not-yet)), and a digest change (13 reds after 88 named tests). So a change to selection, to what root runs or to a pin is proved whole by its own session first, and the batch's prove is the second look, not the first.

## A landing message carries its audit

Every branch is audited for hand-wired code before it lands, by the session that lands it, in the landing message; the managing session reads the audit and gives its go before `bin/land` (owner, 2026-11-09: "I want regular audits on all worktrees before merging confirming that we are not building hand wired custom code everywhere"; "The code base should actually get smaller after we remove all the custom parts and focus on reusing and refining"; "If you find yourself needing heroics and writing a shitload of code we are doing the wrong thing and we need to fix the design"). The session reads its whole diff and the message states:
- the step of THE PLAN it moves ([plan](plan.md)), and each task it completes ([below](#a-merge-says-what-it-completes));
- its `src` line delta, and what it replaces or deletes: a branch that grows `src` names what it deletes, and one that needed heroics goes back to the design;
- for each function, key, proc or path it adds, which of the reused pieces it is ([users](users.md#one-system-of-agents-the-design-agreed-2026-11-09): an entity and its schema, a pull, a render, a request over Flow, the one merge, the reconciler);
- every place it recognizes data by keys checked in code rather than by its schema, or treats one entity or role apart: found and removed, or named and owed;
- its algorithmic estimate (what n is, its big-O, the number expected) beside the number measured (turns to green, ticks, bytes, wall time), and main's number before it;
- for a fix: what allowed the bug, why the change makes its class impossible, and which siblings the sweep checked ([a bug is a class](decisions.md#a-bug-is-a-class-remove-what-allowed-it-owner-2026-11-03)).

What the audit holds a branch to:
- **Every change earns its place.** A merge that grows `src` with no measured value, or adds a namespace, a config key, a schema attribute, a proc, a route or a second way to do something, waits for the gate's four questions ([AGENTS.md §3](../AGENTS.md)) with its evidence; "nothing reads it yet" is a reason to wait, not to merge.
- **No regression without a named reason** (owner, 2026-10-26: "don't accept regressions for no reason"): a number that got worse is refused unless the message names its reason and who follows it up. A cost bound moves only with the owner's yes, never in the merge that overran it.
- **Measured before and after.** A perf or cost claim carries numbers from the same input before and after, and every "faster" is checked by an independent measurement; the numbers go in the commit message and the wiki section they concern, and a regression found is a task the same day.
- **What a new design replaces goes with it** (owner, 2026-11-08: "I want this shit gone so it doesn't keep coming back"): its tasks, wiki text, decisions pointers and session notes leave in the same change.
- **Unused is not dead** (owner, 2026-10-27: "Just because things aren't in use doesn't mean I haven't worked hard on the design"): code with no caller is cut only with the owner's go.
- **Parked work is finished** (owner, 2026-11-06: "we are merging things and not just abandoning them halfway"): a parked branch is landed, or retired by the owner.

## A branch that grows src or adds a mechanism is reviewed

When `src` grows or a mechanism is new (AGENTS §3), a reviewer reads the branch's diff against main for the mistakes the laws rule out: a guard ([failure points](failure-points.md)), a fake default or an ignored answer ([errors](errors.md#unknown-is-never-a-default)), a clock deciding ([clocks](clocks.md#if-nothing-has-changed-we-do-nothing)), a second mechanism or a fix at the reader instead of the producer (AGENTS §4, §9), a test that cannot fail ([testing](testing.md#a-proof-is-focused)). Each finding carries its file:line and its right fix. The worktree session fixes them before its branch merges; the proof it reports is the run after the fixes. The review is for value too, not only for mistakes: it rates the branch worth it, questionable or overbuilt, and for the last two says what to cut; overbuilt goes back. Deleting is preferred to adding, and a fix that adds a layer to work around another layer is the wrong fix.

## Main goes first

A merge's verification is one command, `bin/prove --merge`.
- **One command, one verdict.** It runs every test and `bin/check` step with no green at its digest, the ones that reach a process too (the plan's `:merge` mode, `test_runner/plan-of`: nothing is left out and none is named by hand), `bin/check contracts` and `bin/check smoke` among them (steps of that same run, keyed by digest: not run again beside it). It ends on `MERGE OK` or `MERGE FAILED` from that run's exit status alone, and prints its line for the merge commit's message: the sha, the plan's counts, each verdict, the reds, the src delta of HEAD against its first parent, and the keys left out against main's last merge message (git keeps every merge's numbers; no separate log). So a merge line cannot say green over a red exit, and a step cannot go unrun unsaid.
- **No lock.** Nothing waits on main's verification (owner, 2026-10-27: "Remove it"): it runs niced like any run. It rarely runs, since a branch that holds main and proved its tip merges with no run on main, and load is kept down by not running the same work twice, not by ordering runs.
- How many heavy runs go at once is judged by the machine's cores and free memory ([machine](machine.md#builds-and-checks)), not a gate here.

`bin/update ARGS` hands its arguments to the restarted root, so the owner's root restarts with `nice -n 15 bin/update --profile deepseek` (the first after the command-line profile merged must pass it: the old binary's resume arguments carry none; [config](config.md#layers)). A root that is restarting (`bin/update`) refuses connections for the moment, so a plan run that meets it prints `TEST FAILED` for the connection, a rerun and not a red; the verdict to read is the one a run ends on once root is up.

## A merge runs what the change reaches

A merge runs what the change reaches, not every check: every computation must earn its time, and a run that can tell nothing new is waste (owner, 2026-10-22: "I want faster development"; "We should always be trying to minimize extra computations and do smarter testing"). The merge's proof is `bin/prove` on the merged tree, then `bin/check smoke`; `bin/laws` (every law's sites) and `health` ([health](health.md)) run inside it as steps keyed by the whole tree. Those two run beside the rest, and a red in either ends the run's shards and other steps at once, from before the build: they answer in seconds, and no later result can make that tree mergeable (of 57 proves one day, 7 ran a laws or health red for up to 1,074 s; now 11 s with the binary built and 44 s with a build). What it ended it does not report, so a tree red there and in a test shows the test's red in its next run. A run of what a change reaches shards by its measured work (```seon.proofs/worth-shards```, one for each `:seon.config.proofs/shard-min-ms`), so a few seconds stay one process, and a gate of 206 process tests no longer runs on one (751 s). `:tests` keeps one worker: two gates of those at once measured 404 s each and about 22 GB, and the target machine has 16. A candidate that cannot make a plan (a namespace its files do not load) answers from its held failure, keyed by its commit and files, rather than a new worktree and build each time it is asked (17 in a row, about 40 s each, in one real run). A gate holds its greens only: a digest does not see the machine, so a red from outside the program would stand until one moved, and a red runs again when asked, as a test's plan runs it. One rule selects for everyone: a key runs exactly when no green result is recorded at its reach digest (```seon.proofs/plan```), in the verdict cache every checkout shares ([verdicts](#verdicts-are-a-cache)), so an unchanged tree runs nothing and a result proven in any checkout is reused in every other. A check step's digest takes the program's source and the shipped config whole (`:code`, ```seon.fx/inputs```), never only what its reach names, as a step runs the whole binary and calls much of it from strings and procs: about 37 percent of `src`, `my.agent` and `seon.server` among it, lies outside a step's reach. The wiki, the task files and the tests are not in it (nor the `:seon.env/src` class, which holds `test/` too and which every step reaches through ```seon.contract/uncontracted```), so a merge of those skips the steps that run the binary, about one merge in four, and they run at the next merge of code. `laws` and `health` read the whole tree, and `test-inputs` reads `test/`, so they keep it.
- **A green counts only with its plan.** A merge compares the plan's line (keys, tests, left out, to run) with main's before it, and a jump in what is left out is red until explained: on 2026-10-25 a quoted name in a render made 662 of 686 tests look like process tests, and `bin/prove` ran 29 of them while saying OK.
- **What reaches a process runs when asked.** A run that names nothing (`bin/prove`, `bin/test` with no namespace, the on-change runs) leaves out every test and bin/check step that reaches a process of its own: a root or an agent booted for it, a fork, the binary (a shell call, git or perl, is none: it costs milliseconds; ```seon.program/graph-index```'s `:process?`, the one walk, over `:seon.config.source/process-vars`; ```seon.proofs/left-out```, the one filter bin/test and an agent's run apply). Owner, 2026-10-23: "Tests shouldn't be running agent turns. Not automatically run tests at least." They run when named (`bin/test NS`, `bin/check MODE`), in a merge's verification (`bin/prove --merge`), in the full run (`bin/test --all`, `bin/check 100`), and at the judge before a merge whose change reaches them, nobody asking (owner, 2026-10-27; the reconciler's `:gate`, on the declared `:seon.config.source/gate-checkout`). Measured from the recorded durations of the 2026-10-23 full run: those were 90 of 443 tests and 782 of their 917 s, and every check step that boots a root; a run that names nothing went from about 26 minutes to about 2.
- **A gate runs its candidate on its root's runtime.** A gate's checkout (```seon.fx/run-on-checkout```, `bin/worktree --at DIR COMMIT REPO FROM`) clones the built products of the checkout whose root runs it (FROM: the runtime, Chez, the native libraries, by their stamps), never the main tree's, and takes that root's binary; the runner builds `target/seon` again only when ```seon.root/binary-current``` says it is not current for the candidate's tree, which a pin (the runtime's included) or a schema change is. A root on another Jolt pin than the main tree's once judged its candidates on main's runtime: its runner made no plan and the gate answered `:seon.fx/io-error :no-plan` (```seon.source-test/a-gates-checkout-takes-its-roots-built-products```).
- **The binary is built when a selected key uses it.** `bin/test` builds `target/seon` (about 46 s) only when a selected test uses the binary (```seon.program/graph-index```'s `:binary?`: a reached form references ```seon.test-store/binary-sh```, the one way a test runs it, other than a form that only names it as data or is its own definition) or a selected step runs a `seon.check` mode (```seon.proofs/step-needs-binary?```, from `check-steps`: laws, lmdb-kill, lmdb-lock, lmdb-crash and forks run none). The plan writes `out/binary` and `out/steps-binary`; empty, `bin/test` builds nothing and `bin/check --steps` seeds, lists and drops nothing. A step that ran no mode is stored green whatever binary stands. Measured on the shared machine: `bin/prove --checks` selecting only `laws` and `lmdb-kill` ran in 16.8 s (plan 8-15 s, the two steps a few), and 9.4 s when both were reused; the 46 s build and about 6 s of seeding and dropping it used to add are not spent. With it, `bin/test`'s plan makes the one store the process tests' roots take a branch of, `target/runs/test-store-<schema digest>` (```seon.test-store/make-process-store!```, named by ```seon.db/kept-store!```), once when it is missing and before any shard starts; shards whose roots each made it raced, one opening the store another was still creating. Both kept stores of regenerable output, it and the program store, are named by the schema's digest (```seon.db/schema-digest```): a changed schema makes a new store, and one of another schema is removed, never migrated or refused. And only when the binary is not current for the tree (rule (a), ```seon.root/binary-current```: what differs between the tree it was built from and this tree reaches code root runs from its binary, or something the build bakes, [source](source.md#the-binary-records-its-program)); the plan writes what differs to out/build (```test-runner/build-text```), empty for a change that reaches no root code, which builds nothing. The merge gate takes root's running binary and its kept stores into its worktree (```seon.fx/run-on-checkout```), so a gate of a test-only candidate measured 32 s against 130 s (2026-11-10).
- **A shard's agent tests share one root.** ```seon.agent-test/in-agent``` asks ```seon.test-store/shared-root!``` for the shard process's root for its root arguments (its `:dirs` and `:sets`), started at the first test that asks, on a main of its own of the process store, and stopped with its main dropped when the shard process ends (a shutdown hook; hooks run at once, so no other hook may remove what its stop uses: the starter fifo is reclaimed by the next process instead). Each test loads a task file of a namespace of its own (`t<8 hex>`), attaches its own agent and names both by what the attach answered, never by a counter's value (`a1`, `demo/t`); at its end its agent is killed, its end awaited, its tasks cancelled (a task left `:running` keeps the reconciler from quiet, and a later test's ```seon.await/await-quiet``` would wait on it forever) and their branches deleted. Its task and agent facts stay on the shard's main and go with it. A test's scripted model (`:seon.config.ai/script`) or missing one (`:seon.config.ai/provider` `:none`) is its task's own setting (`in-agent`'s `:config`, the task's `:seon.task/config`, read first by ```seon.config/provider-at```: [config](config.md#the-resolver)), never a root argument, so those tests share one root where each distinct `--set` booted one (measured 2026-10-29, `bin/test --all seon.agent-test`, 70 tests in 4 shards: 7 min 42 s and the longest shard 396 s before, 5 min 22 s and 263 s after, at differing load; about 15 roots fewer in the namespace). Left red either way, load- and state-sensitive: `a-failed-call-keeps-what-it-sent` and `an-agents-collect-trip-is-the-configured-one` (flaky at its digest). A root's `:sets` stay for a setting no task can carry (a verdict cache as the test's subject, `an-agents-greens-and-a-checkouts-are-one-store`). A test whose agent merges into main (`:own-root? true`), and every test whose subject is a root's life (boot, stop, kill, a generation: ```seon.test-store/start-root!``` directly), keeps a root of its own. Measured 2026-10-27 on the shared machine (load about 8): a root's boot was 9.5 s of an in-agent test's 15 (4.8 s of it the source import), an attach on a running root 66 ms; ``seon.repl-test``'s nine agent tests went from 13.1-15.7 s each to 2.3-5.5 s after their shard's first. The digest is unchanged: the root imports and runs the checkout's tree (```seon.fx/read-source```), so an agent test's input is the tree (`seon.test-store-test/agent-tests-in-one-process-share-its-root`).
- **Tests.** A test's key is its reach digest (```seon.program/graph-index```: the forms it reaches through refs, macros, quoted names, methods, fixtures and schemas, plus the checkout's inputs with no program facts; [source](source.md#tests-run-by-reach)). The digest is the tree's, never the process's: the same commit gives the same digests in any checkout and any run (`seon.program-test/the-same-tree-gives-the-same-digests-in-any-checkout-and-any-run`). A test takes only what its reach names (and a test that starts a root, what root runs: [source](source.md#tests-run-by-reach)), never the whole tree and never the whole schema registry (owner, 2026-10-27: "I don't care if it's perfect and if it's possible a test could be doing other work we don't know of … no tests should include all of src"): a schema entry it names as a literal keyword, or that a contract it reaches names, and no more, though `seon.db/schema` derives the store's attributes from every entity schema and a renderer looks properties up by a computed key. A test that reads the checkout's own program from its kept db (a docstring, a form's source: `seon.main-test`'s whole-src checks) takes the text of src/ and test/ as a file class, `:seon.env/src` (`seon.test-store/kept-program-store`, [source](source.md#what-a-test-takes-of-a-forms-text)), and so does a test reading a docstring, so a docstring or comment edit reruns those tests and no other (2026-10-30: one digest had stood for a red and a green). What a reach cannot show (a file read by a path built at run time, a schema looked up by a computed key) is the daily full run's to catch (`bin/test --all`). `bin/test [NS ...]` reads the program of the checkout's git tree, selects, and deals what runs, a namespace at a time, into `:seon.config.proofs/jobs` shards, each a process of its own started at once and reaped by the shell (```seon.proofs/run-tests!```). ## The full run is the net

What the full run found is kept beside the verdict cache, where a store erase cannot take it: `bin/test --all`, whoever runs it (the cron's request, `seon.fx/full-run-command`, or a session by hand), writes `full-run.edn` in `:seon.config.proofs/results-dir` when it ends, whole (temp and rename): the commit it ran, `:green` or `:red` with each red test, when it ended and its logs. A run that dies writes nothing, so the file names the last run that ended, and an absent file says none has. Every landing says how far main is past it: `bin/full-run` prints "full run: N landings ago, :green|:red, at <commit>", or "none recorded", and `bin/land` prints it before `LANDED`, `bin/root status` after its own line. A count, not a time: no clock decides anything ([clocks](clocks.md#if-nothing-has-changed-we-do-nothing)), and a landing is what moves the code the net has not seen. Before it, the outcome lived only in root's store as a problem, and an erase took it: on 2026-11-10 nothing could say whether the 03:00 run had run.

## A test child is a fork of a live agent

A test that waits for good is told. Tick budgets count work, and a parked test does none, so what ends such a test is Jolt's own all-asleep check: a wait nothing can end throws its typed deadlock in the test, an `:error` naming every wait. A test child therefore watches for its agent's death without waiting on the signal (```seon.intr/exit-at-eof!```, wake? false), since a signal waited on counts as something that can wake the process and the check never ran (deepseek-run3: one agent's test deref'd a promise nobody delivers, its child parked at 0% CPU, and every other agent's turn queued behind it on the test service's one slot). A test parked on a descriptor it holds itself is still not told, since a descriptor awaited can wake it: task ```seon.proofs/a-test-parked-on-a-descriptor-holds-every-agent```.

A test's verdict is a function of the test alone, but an agent's test child is a fork of a process that has been working, where a `bin/test` shard starts blank. It inherits the agent's walk, its config (profile, ports, source and runs directories), its environment, and a working directory of its own (```seon.fx/run-dir```). So a child disposes the walk as it starts (```seon.agent/run-tests-forked```), and a test reads nothing of its runner: a test of the config resolves the config it names, and a test of a file names it from ```seon.config/checkout```. The check that holds this is `agent-tests` ([checks](checks.md#modes)): it runs a sample of the tests that reach no process through one agent that has drawn its page, on a root whose provider is not the scripted one. It selects as an agent's run selects (```seon.agent/test-plan```), so a test an agent's plan should not take shows there: a stall task's proofs (```seon.template/stall-proofs```) are judged only by a task that names them. The other direction is ```seon.repl/eval-string```'s: an eval that leaves the agent's state empty, as a test's cleanup run at its REPL can, gets it back.

## The test service

One proc, `:prove` (```seon.prove/prove-proc```, declared in `resources/seon/system.edn`), admits every request to run tests, whoever asks: a Claude session (the server's `:prove` op, the MCP tool `seon_prove`, ```seon.root/prove!```) and an agent's turn (```seon.agent/prove!```, which ```seon.turn/observe``` calls) share it, so a change is proved once.
- **The key names what the run reads** (```seon.prove/run-key```: `branch@digest`, with the test namespaces when a request names some, and `!turn` for an agent's turn, whose run is the proofs and what the branch changed; the judge's is the plan's tests; owner's ruling 2026-10-24, DECISIONS). The judge asks the service too: its `:judge` request makes the agent call ```seon.agent/prove!``` in mode `:judge`, so the judge's run caches its verdicts like any other. A branch's tx is not it: any write moves the tx, a run's own result facts, its prove agent's end and the eval that asked among them, so a key at the tx made every repeat ask a second run.
  - **Main's** digest is main's program digest (```seon.program/program-digest```: its live forms, schema entries and namespace tails, one read of their datoms), as an agent's is: its run reads main's program, its tests among it. A write of data never moves it; a moved key that changed nothing a test reaches is a re-plan that reuses every green. It is coarser than the per-test digests (```seon.agent/test-plan```) because it must be known before the run is admitted.
  - **An agent's** digest is its branch's program digest, its tests included; the root's inputs it also reads are fixed for the boot, as the service's state is. Its merge base is not in it: a merge of main that leaves the branch's program as it was keeps the answer, which then covers more tests than the new selection, not fewer. An agent's turn commits, then asks with the digest of its head (```seon.agent/prove!```); a session asks with the digest ```seon.root/prove!``` takes of the same head, so both ask for one key.
- **Items, askers and workers.** The unit is an item: one test at its digest. A request is planned once by the agent that holds its branch (its `:tests` with `:plan?`, ```seon.agent/run-plan```): what it reuses at its digest, what it defers to the gate (process tests), and the items it would run. Its items join the one queue (```seon.prove/ask-items```): an item queued or running gains the asker as a waiter, so ten askers of one program run each test once. As many items run at once as there are workers (`:seon.config.proofs/test-workers`): a free worker takes the most valuable queued item (```seon.prove/grant```: an agent's turn first, then waiters and age, counted in grants passed over, over measured ms), alone, asked of the agent holding it with its digest, which runs it as its plan of the run planned it (```seon.agent/item-selection```), with nothing planned again. An asker is answered at its first red or its last green (```seon.prove/item-ended```), and an item no one waits on any more leaves the queue. Runs of different keys are in flight at once. A key whose run ended green is answered at once from that answer, every verdict in it read as reused, until the key moves. Every waiter is answered exactly once (```seon.prove-test```).
- **The asker's agent writes the run's facts on its branch, once an answer** (```seon.agent/record-answer!```): what ran, what was reused and what was deferred, at the digests of its plan, so a fact whose digest moved is retracted. An item's run writes the verdict cache only.
- **A run is a chain of requests the proc sends the api.** The agent that holds the branch plans it, then forks itself for each item granted (```seon.agent/run-tests-forked```), on root's `:tests` request, which its `:tests` proc serves on its own fiber whatever its REPL runs, a prove of its own that waits for root's answer included (```seon.repl/tests-step```: a `:tests` never waits behind a wait that holds the agent's one loop, [processes](processes.md#the-agent-process)); main has no such agent, so a prove agent is forked from the fork server's main onto the `tests` branch, holding main's program and its tests (`:seon.config.source/dirs` takes `test/`), runs them, and is killed.
- **Main is proved at each program commit, nobody asking, when `:seon.config.proofs/prove-main-on-commit` says so (off by default: the run of all of main's tests in one child dies, task seon.agent/a-test-run-streams-its-reports).** The writer's commit notice (`:main`, a sliding buffer of one) is a request when its ops move the program (```seon.program/moves-program?```, what moves the fork server's reach graph too): a run of main keyed by its program digest, with no waiter, which a session asking for the same key joins. A burst of commits is one run, the latest. Its verdicts are cached by digest, so every agent forked after finds main's tests at their digests and runs none of them again (its boot test (removed 2026-11-08: the config leaves it off)); process tests are left to the merge's `bin/prove --merge`.
- **Verdicts are cached by digest by the agent that ran them** ([verdicts](#verdicts-are-a-cache)), before the waiters are answered; of the store, only the asker's facts on its own branch, once an answer (above). ```seon.agent/test-plan``` finds a verdict by digest (```seon.fx/stored-results```), green or red, so a digest that holds one is not run again. A red is reused as a green is, reported with the failures its run recorded and marked `:reused`, since a test's verdict is a function of its digest (one per-test tick bound everywhere).
- **The writer's commit notice** (`:main`, a sliding buffer of one beside the reconciler's) tells the proc main's latest tx. A process test (```seon.program/process-tests```) is left out of a run that names nothing, unless it is a proof (```seon.agent/run-selection```): the answer lists it as deferred.

- **A ready branch that already contains current main**, and whose own plain `bin/prove` ran at that tip (with `bin/test` of the process-test namespaces its change reaches, or its `--merge`), is merged `--no-ff` with no run on main: the merge commit's tree is the one it proved, and main's first parent stays main, so `git log --first-parent` lists every merge (an ff hid 22+ commits, audit 2026-10-28). The merge message carries the branch's src delta, what it replaces and its measured number. Prefer this: ask a branch that is one merge behind to merge main and re-prove (every green at its digest is reused) rather than verifying on main.
- **A `bin/prove --merge` on main** runs only when branches are combined into a tree nobody has tested (two or more ready at once, or one that does not contain main). One run covers the batch, after one `bin/build`. A red names its test: revert only the branch whose change reaches it (`(my.agent/tests-reaching ...)`, or its diff against the test), send it back with the log, keep the rest. Then `bin/update`.
- **Fast path** (owner, 2026-10-27: "Don't wait for fixes that should just be merged and tested later"): the dev-speed branches (reuse, the shared test root, tree-id) merge as soon as their own targeted tests (the namespaces they changed plus their proofs) are green. Their first full run is the next one main does anyway; a red the branch caused is fixed forward within the hour, and reverted only if it breaks main for everyone. Each is reported to root in one line.
- **A pin bump** goes in a batch of its own, and `bin/update` brings the write-back tree to main before moving its submodules, because a tree behind its pin is not the tree its binary was built from, and a binary built from it is no program of main's (a stale binary, [health](health.md#a-stale-binary)), whose agents share no greens. The main tree's submodule checkouts must be moved to the new pins before `bin/build` (`git -C reference-code/<lib> checkout --detach <pin>` in the main tree; a merge moves the recorded pin, not the checkout, and a run on the old checkout says nothing about the bump: seen 2026-10-27). A Jolt or Chez bump re-runs every test and every check step once (the non-process set takes about 5 minutes): the runtime's gitlinks (`:seon.config.source/runtime-pins`) are in every digest's `:env` ([source](source.md#tests-run-by-reach); 2026-10-29: a cost proof stayed green across a Jolt bump that moved its numbers). For a datahike, persistent-sorted-set or konserve bump its diff and index tests run too, and every test whose reach names their namespaces. After the merge, `bin/build` updates the main tree's submodules (git submodule update) to the recorded pins (task seon.build/a-build-takes-its-pins), and before `bin/update` the merges worktree's submodules are moved with `bin/worktree --sync merges` (`bin/update` refuses a worktree whose submodule checkouts differ from its pins).
- Heavy runs: no slot lock (owner, 2026-10-27: "I want a lock free system").

## Every merge's `src` diff stat is read

Root reads every merge's `src` diff stat before merging, against the goal of about 10k lines of our own code. Every function a merge adds names the existing system it extends, or why none could carry it; a new namespace or mechanism where an existing one could be extended is sent back, not merged; the merge's commit message states its net `src` lines (`bin/laws growth` prints them and the definitions the branch adds), and a merge that grows `src` says what it deletes or plans to delete.

A work task is judged on its branch and never told it is behind main: its merge task merges main into the branch and the gate tests what that writes, so main moving under a green work task is the merge task's, not the work agent's ([turn](turn.md#what-a-turn-merges-from-main), `seon.reconcile-test/a-green-work-task-judged-behind-is-done-and-its-merge-runs`).

## A merge says what it completes

A merge that completes a task's work says so in its message, one line a task, `Completes: ns/name`, and removes that task's entry from `resources/seon/tasks/` in the same commit (git keeps the plan, test/ keeps the proofs). `seon.task-files-test/no-shipped-task-is-merged-work` reads those lines on main's first-parent merges and is red on any that names an entry still in the files. Nothing else in a message counts: a merge that files a task, names one it merged past, or moves one without finishing it completes nothing and needs no exception (on 2026-10-31 two merges that named a filed task read as merged work left behind, under the rule this replaces: a message naming a task, kept open by a list of thirteen exceptions).

## Conflicts and pins

A conflict is resolved by copying each side's lines, never retyping; the lines after `>>>>>>>` may belong to both sides; each resolved file's forms must balance as its parents' do. Submodule pin bumps happen only in root's merges into main, never in a worktree session's merge of main. A pin bump reaches everything, so its merge also runs the cost proofs `bin/prove` leaves out (`bin/test seon.program-cost-test seon.record-cost-test`): Jolt 0d39edc3 passed prove and still made reach-update grow n^1.96. Commits in the forks ([forks](forks.md): Jolt, Chez, Datahike, konserve) carry no AI trailers. After a merge, root archives the worktree session first (its `bin/mcp` holds the worktree open), then removes its worktree ([machine](machine.md#disk-stays-bounded)).

A pin bump proves whole on its own branch before it is handed over: its session runs `bin/prove` there (every test, every check step, every dependency unit: a pin moves every digest) and sends the tip with the prove's last lines. On 2026-11-10 a Jolt pin came as ready on five dependency units, four namespaces, three check steps and all 192 Jolt gates, and its whole prove was red on six things (streaming over a socket, the page's stream to a tab, the declared threads, three unit costs, a render cost proof); a Datahike pin raised a cost proof past its bound through a hashing change. A pin bump is verified with `git ls-tree HEAD reference-code/<lib>` and `gh api repos/seantempesta/<lib>/commits/<sha>` (the pinned commit is the one pushed to the fork), and after it, before any cutover, the full run goes on a clean main checkout. A Jolt pin is ready only with the verdict of every Jolt gate (forkheldlocks, siginfodump, stacklimit, gcpolicy, the fiber and lock gates, and unit): on the night of 2026-10-28 three pins were merged on their new gate alone, and one of them could set a stack limit of 0 at a full heap. A pin skips the day's soak only when it fixes a bug already on main. A pin bump is verified in a worktree with every Jolt gate, run as `make -o submodules GATE` (plain `make` runs `git submodule update`, which fails in a worktree); a Jolt pin that skipped a gate regressed once, so it counts as ready only with each gate's verdict (the one environmental red is fiberspoll's socket test, red on stock Chez too, because macOS refuses a connect to a full backlog at once). `bin/build` resets every submodule checkout to the pin in HEAD, so a pin bump is committed before building, or a gate run on the checkout tests the old code. Stage explicit paths: `git add -A` staged lagging submodule checkouts as gitlink changes.

## Seon's merge is a three-way merge of the program

Seon's own merges (a branch into main, main into a branch) are git's three-way merge over the program as data, never over files.

An agent's own records never merge: a merge carries the program and tasks, main holds what root needs of the agent, and its branch is kept and queried for what happened to it. So a branch can be restored and forked, and the same agent key on two branches stays valid. Reclaiming a record is the owner's act; archiving branches that worked is a later production policy, with no code for it now ([decisions](decisions.md#agent-branches-are-kept-and-queried-owner-2026-11-04)).

A db's program is a map from keys (``[:form id]``, ``[:var sym]``, ``[:schema k]``, ``[:section address]``, ``[:script path]``, a declared datum) to content (```seon.merge/program``` of a db and its declared data attributes, which only tests read whole; a merge reads ```seon.merge/program-of``` at the keys that differ), and ```seon.merge/three-way``` compares base, ours and theirs: each side's changes, the keys to apply, and the conflicts. A merge reads only where the dbs differ (```seon.merge/delta-three-way```: the keys the datoms that differ bear, read on each side by index seeks, never whole programs; [storage](storage.md#merges-read-what-changed)). The writer's merges use it (`seon.writer/writer-proc`), and it is the one derivation behind the done rule's unmerged entries, the agent's merge of main and the dashboard. What merges is written as it is: the branch's own datoms for those keys, with their entity and transaction ids, after the declarations of the attributes they use that the target lacks (```seon.merge/merge-tx```); an entity whose identity the source retracted (a deleted var) is retracted whole on the target, so no fact the target wrote of it (a test's results) stays on a nameless entity, which the next test run would read as a nil test key. The wiki merges as code does: a section is the key ``[:section address]``, its content every `:seon.doc/*` attribute the page states, so a section only main changed overwrites the branch's copy when main merges in, one both changed is an unmerged entry, and main's new and removed pages reach the branch (`seon.merge-test/a-branch-takes-mains-wiki`), so a branch never reads main's code against its fork's older wiki. A branch's own doc change merges as its code does, and its page is written back with the merge, so the next load of `docs/` reads what merged (`seon.merge-test/a-branch-doc-edit-merges-and-its-page-is-written-back`; [source](source.md#write-back-mains-files-byte-for-byte)). A conflict stays on the branch as an unmerged entry (```seon.merge/unmerged```), base, ours and theirs as data, until the branch redefines the key or resolves it (`my.branch/resolve!`, ```seon.merge/resolve-tx```). The files a merge touches are written back by [source](source.md); a merge task's turns are [turn](turn.md#a-merge-tasks-loop).

Main took 301 first-parent merges from 2026-10-20 to 2026-10-27, all by git (worktree merges and `bin/prove --merge`); Seon's own merge (octopus merge, write-back) made 14, all only on `jolt/seon-merges`. The one-merge design is task `seon.merge/one-merge-system`.

## A merge leaves no name unbound

A merge into main is judged against what it merges into: main, with the members of the same octopus merge taken before it (```seon.writer/judged-members```), and a merge that would leave a live form calling a definition it removes is refused, read from the forms' recorded references (```seon.merge/dangling```: the diff of main and the merged value, then one `:form/refs` seek a removed var). Each member alone is judged against main, so two members with disjoint keys, one removing `f` and one calling it, each passed and merged in one commit; now the second is behind and told why, and merges main first. One branch removing `f` that main's unchanged `g` calls is refused as `:seon.merge/dangling`, by the octopus merge and by the gate's candidate alike (``seon.reconcile-test/a-merge-leaves-no-name-unbound``).

It reads facts, never loads code: Jolt compiles a name under an alias with no var (`x/f`) as a lookup at each call, so a process loading the merged program from main's raises nothing for it (tried, 2026-11-08); an unqualified one fails at load. Not covered: a removed namespace another form still requires (`:form/requires` has no index to seek), and a changed macro's callers. The analysis of the candidate's files still runs in root's own image (```seon.writer/unanalyzable```); moving it out is task ``seon.writer/a-merged-tree-is-analyzed-in-a-fork``.

## Root repairs a failed merge from its REPL

Root's REPL (`seon_eval` as root, or `printf '{:op :eval :agent "root" :code "..."}\n' | nc -w 30 127.0.0.1 PORT`, newlines in the code escaped as `\n`, one request per line) repairs the four failures with the tools that exist; staged and repaired once on a worktree root (2026-10-27, the staging recipe and each reply in git history).
- **Merge refused (`:hairy`, the agent ended `:merge-failed`):** `(my.root/problems sys)` shows `:merge` and `:failed` problems; `(d/pull @(:conn sys) [:seon.task/outcome :seon.task/reason :seon.task/conflicts :seon.task/unmerged] [:seon.task/id "T"])` is the best read (each conflict with base, ours and theirs). Repair: `{:op :attach :task "T"}` answers `{:agent A ...}`; in agent A `(mapv (juxt :key :kind) (my.branch/unmerged))`, then `(doseq [e (my.branch/unmerged)] (my.branch/resolve! (second (:key e)) :theirs))` (or redefine the var), then `{:op :done :agent "A"}` answers the verdict. Root has no conflict function of its own: `my.branch` runs in an agent.
- **Green on its branch, red once merged (`:semantic`):** the held reason reads `proof-unknown`, not "merge main first". Attach, `(my.branch/merge-main!)`, rerun the proofs, fix, `:done`. The writer refuses a branch behind main, so a red merged program never reaches main.
- **A held task:** raise the limit that held it (`@(root/transact-main! sys [{:seon.task/id "T" :seon.config.merge/max-conflicts 3}])`, flat keys on the task), then `(my.root/run! sys ["T"])`. A task stuck `:behind` has no repair yet (task `seon.root/a-behind-merge-ends-in-a-fact`); `(my.root/cancel! sys ["T"])` ends it and the branch's work is lost.
- **A write-back that failed (`:seon.task/commit-error`, an `:effect` problem for `seon.fx/git-commit`):** remove the cause (a stale `.git/refs/heads/jolt/seon-merges.lock`), then `(my.root/write-back! sys ["T" ...])`. A worktree root writes its own `jolt/seon-merges-<worktree>`, never the main tree's.
- An attach writes no `:seon.task/model`: attach then done, run on a root 2026-11-06, left the task with none, so there is none to retract before releasing it again. What is left of root taking an attached run back is task `seon.root/an-attached-run-is-taken-back-by-root`.

## Not built: a merge queue on root

A session's branch is landed by the session itself (`bin/land`, [above](#a-branch-lands-with-binland)): a git merge, no queue. Seon's own merges are merge tasks judged by the reconciler, one at a time: an octopus merge of several merge tasks is built and off (`:seon.config.merge/max-running` 1, until one combined test run of all its members is proven). No queue on root merges main into each candidate, proves the merged result and batches the disjoint ones, and builds, tests and checks are not tasks on root (task ``seon.reconcile/a-check-step-is-a-task``).

## Main moved is said at every eval

An outside agent's reply, as a model's turn does, merges main in first when main has moved, so an agent never runs old code (owner, 2026-11-07); a conflict is an unmerged entry on its status. A process forked before a pin keeps its binary until root restarts (`bin/update`), when every agent resumes on the new one. Every `seon_eval` answer an outside agent gets carries one line saying how main differs from its branch, or none when main's head is still its merge base (owner, 2026-10-28: "there are never any surprises"), which is what moved since that merge. ```seon.agent/main-line``` makes it from the merge base, the branch and main as the agent last heard it:
- how many names main changed since the base (```seon.merge/readiness```, the three-way a merge of main runs, so it costs what changed on each side);
- those of them the branch changed too;
- those its changed functions call;
- those a merge of main would conflict on;
- and the form that merges main, `(my.branch/merge-main!)`.

Each list is cut by the one printer. ```seon.repl/eval-string``` puts it on the answer as `:main`, live, never recorded: it is a function of the db at t. Its cost is what changed (```seon.agent-test/main-line-costs-what-changed```; measured 2026-10-29 with `seon.cost/measure` on a four-var program with two names moved on main): while main is the base it is O(1) (680 ticks, 3 contracted calls; ```seon.agent/main-difference``` compares commits before it calls); the first eval at a new main pays main's diff since the base (```seon.agent/main-changes```, held keyed by the two points it is a function of, evicted by the next pair and regenerated from the two dbs) and the branch's (```seon.agent/branch-changes```): 9.2 M ticks, 25.8 MB, 172 calls; each later eval at that main pays only the branch's diff when the branch moved and one query over its changed vars: 64.6 k ticks, 376 KB, 4 calls (before: 13.9 M ticks, 38.8 MB and 304 calls on every eval, 13.0 M with main the base, which `seon.merge/readiness` ran each time). A conflict is a name both changed to different content, read from the two diffs. The line is made from main as the agent last heard it (```seon.agent/main-difference``` reads no store: a read of main's head on every eval held the agent's heap past its ceiling in `seon.agent-test/an-agent-finds-no-repository`), so an agent that hears no main is told only what it last heard until root pushes main's commit. It reaches the outside agent's `seon_eval` answer (```seon.server/op-answer``` `:eval` passes `:main` on); an in-process model agent's turn reads the recorded eval, which does not hold `:main`, so it is not told on each eval. The agent merges main when it chooses; at `seon_done` the done answer (```seon.server/verdict-line```: one line, each red with its first failure, and the form that reads the whole verdict) names the same difference, so nothing in it is new. Proofs: `seon.agent-test/main-moved-is-said-at-every-eval`, `seon.server-test/the-done-answer-is-a-line-and-a-handle`.

## Verdicts are a cache

A test's or a check step's verdict is derived data, a function of the code it reaches (its reach digest), so it is kept as an evictable cache by digest outside the store, and the store keeps only decisions (owner, 2026-10-28: "derived data may be cached with the understanding that it may be evicted at any time"; [derived data](data-modeling.md#derived-data-is-a-cache-never-relied-on)). It replaced the result facts on the standing root's main (2026-10-27 to 2026-10-28: 250,796 datoms, 28% of main's history, and an agent's start heap +35%, the overnight audit's worst finding), which in turn had replaced the uncapped `test-results/` directory (349,131 files, 1.3 GB, which nothing reads now; the owner's to remove).
- **A sample of the reused greens runs again every run** (the owner's plan, 2026-11-10: a writer change reused 226 of 233 process tests' greens, five of them red; whatever input a digest misses next). ```seon.proofs/reuse-audit``` picks `:seon.config.proofs/reuse-audit` (10) reused greens that start a process and 10 that do not, first by the digest of the tree and the key, so a rerun of one tree audits the same ones; never a red, a flaky one, a check step or a slow test; a run that names keys or runs everything audits none. The plan line names them (`prove: reuse audit:`), they run beside what the change selects, and a red among them is `REUSE MISMATCH` (`bin/test`): a red at a green's digest, so flaky, both kept, an input the digest missed (`seon.proofs-test/a-run-runs-a-sample-of-its-reused-greens-again`). One run catches a gap reddening 5 of 233 process tests with about 19% odds, a day of five runs about 66%: a net, not the fix.
- **A red verdict is never deleted or moved** (the owner's ruling, 2026-11-09), even one a fixed tree has made stale: a fixed tree gets a new digest, and the red stays at the old one. A red at a digest that cannot move (flaky: green and red at one digest) is a gap in the digest, raised with the digests as its reproduction. To see a test red first, run it on the unfixed tree and leave its verdict.
- **Who runs it moves no digest.** Each key that says where a process runs or as what is `:seon.config/place`, out of every digest: its ports, store and source, its profile and what that picks, and what `bin/test` sets for itself, because a root's value is not the one its tests run under (```seon.config-test/what-bin-test-sets-for-itself-moves-no-digest```: `:seon.config.vector/texts`, 64 in a root and 0 in a test run, alone split 231 of 1,469 digests). Nearly every test reaches one of those, so before they were place, on one tree 46 of 1,452 of an agent's digests matched a checkout's and no process test's, and neither reused the other's greens. A green is anyone's; an agent reuses a red only if it wrote it (```seon.agent/test-plan```), so its judge need not rerun what its turn recorded and no one else's red, under load, is told to it as its work.
- **A branch's config is its own input.** An agent's digests take its root's boot's values, with the config its branch holds laid over them key by key when that differs from what it loaded with (```seon.agent/branch-inputs```, ```seon.fx/config-input```), so a branch's value for one key moves the tests reading that key, and a place moves nothing (`seon.agent-test/a-branchs-config-key-moves-the-tests-reading-it-and-no-other`).
- **Where.** One directory for every checkout, `:seon.config.proofs/results-dir`, which `bin/env` sets to the main tree's `target/results` (found from git's common dir, as the build caches are), so a digest proved in any worktree, by an agent or by the merge gate's checkout is reused by all. A file a key, digest and status: `<ns>/<test>/<digest>.pass.edn` for a green, `<digest>.red.edn` for a red; a `bin/check` step's under `steps/<step>/`.
- **Keys.** A test's file is under its var's name, a step's under `steps/<step>/`, and each contract of the generative check under `steps/mg/<ns>/<name>/` ([checks](checks.md#the-generative-check-is-per-function)): `mg-check` has no digest of its own, only its functions do.
- **When, and who reads it while a run goes on.** A `bin/test` shard writes a green the moment its test ends, and asks the cache for a test's green just before the test would start (`seon.proofs/run-tests!`'s reused): a green another run stored since this run's plan is reused, never run again, and the shard's line counts it (`reused from another run`). So runs at once share what each finishes: two runs of `seon.proofs-test` 8 s apart on an empty cache ran 34 tests between them, not 64 (2026-11-10). A full run (`bin/test --all`, a rerun by name) and the reuse audit's tests run whatever the cache holds (the shard file's `:rerun`). A shard whose tree changed under it takes back the greens it wrote (```seon.fx/forget-greens!```) and stores nothing else; its reds are written at its end. A step toward the test service owning each (test, digest) item ([plan](plan.md)).
- **Who writes.** Whoever ran the test, with no round trip to a root: ```seon.fx/write-verdicts!``` stages each file and renames it over (```seon.fx/write-file```), so no reader sees half a file and no lock is needed. `bin/test`'s shards, `bin/prove`'s steps, an agent's test run (```seon.agent/run-tests-forked```, whoever asked: a turn, the judge, the test service) and the merge gate's run all write the same way. A file names its writer (the test run's id, tree or branch, the agent): recorded, never judged. A file the cache would not take is named (`UNRECORDED`), the run ends red, and that test runs again; nothing is queued.
- **What is written: only what ran.** A test reused at its digest writes nothing. A test that ran writes its status, failures, cost proof's report, ms, ticks, bytes and what it spent in each contracted function ({var [calls ticks self-ticks bytes self-bytes]}), once a digest: nothing is copied per run. Flaky: green and red are two files, so two writers of one digest never lose either, and the digest is flaky while both exist ([health](health.md#a-flaky-test)).
- **What the asker is answered: its reds.** A run's answer (```seon.proofs/answer```) holds its counts and, of its reports, only what the done rule reads: a pass for each proof that passed, every report of a test that died, each red test's failing assertions, and every error that names no test (the run's own: a line its test process sent that did not read), so a count is never without its report. The run stays whole in the cache by digest.
- **Beside it, facts on the agent's branch.** An agent's run of its tests also records the results worth a fact (```seon.proofs/facts-worth-keeping```: a proof of its task, a test not green, one the branch already holds a fact of; nothing reads another green's, and each would rewrite a leaf among the program's) on the test's var entity on its branch (```seon.proofs/result-tx```, written by ```seon.agent/run-tests-forked``` when the run ends, in every mode but main's): `:seon.test/digest`, `:seon.test/status` (`:green` `:red` `:flaky`), the failing assertions as data as `:seon.test/failures` while not green (the test child's reports, every one), and the sums `:ticks` `:bytes` over the runs at that digest, each `noHistory` (overwritten in place). A test reused from the cache gets its digest, status and kept failures when the branch's facts differ; a test whose reach digest moved and that the run did not judge loses its facts (a status is the verdict at the digest it has now: absent is unknown); a run that changes nothing writes nothing. The agent's record (@ctx, under the task's `:proved`) holds them and the task part of the one layout renders each proof's status from there (`seon.render.ui/status`); the cache stays what reuse reads (also `my.task/status`, for now), and main's prove and `bin/test` write no facts yet (task seon.proofs/test-results-are-a-few-facts).
- **What reads them.** A plan, two file checks a key (```seon.fx/stored-results```): bin/test, bin/prove, an agent's test plan, the merge gate's read-back (```seon.fx/test-results```). A green is its file's existence, never read (its content is nothing a plan uses: 2,280 reads were 76.8 MB and 25.1 M ticks of one turn, 2.1 MB and 0.8 M ticks as file checks, `seon.results-test/a-green-is-found-by-its-file-never-read`); a red's file is read, for its failures. A red's file that cannot be read is an error, never a miss (```seon.fx/read-verdict```, [failure points](failure-points.md)): the plan says so (`TEST FAILED`, `:seon.proofs/unread`). The deal's order reads each test's median measured ms over its files (```seon.fx/typical-ms```).
- **What a run reads of a test's past is one file.** Each green also goes on its key's `.recent`, the newest `:seon.config.proofs/recent-verdicts` as `[ms ticks]` (```seon.fx/history```), which a run's order, a test's tick budget and the slow-test read take, so a test's cost does not grow with the digests it has had: listing and reading those verdicts was 15-19 s of a merge's 22-25 s selection. It is derived: gone, it is made again from the verdict files.
- **A stopped run keeps its greens and nothing false.** `bin/test`, told to stop (a timeout's TERM), sends its shards TERM; each shard's shutdown hook stores the greens of the tests that ended (`test-runner`'s shard, unless the tree changed since its plan), never a red, since a test cut short reads a root the stop ended and its red would turn flaky beside the next run's greens. A shard that dies with no hook (killed, out of memory) stores nothing. `agent-tests` keeps a cache of its own across runs and removes its reds first; its key is what its code reaches and its tests' digests with no tree in them (```seon.proofs/agent-tests-digest```), so an edit that reaches none of them boots nothing.
- **The bound, with no clock.** The whole cache holds at most `:seon.config.proofs/results-max-bytes` (512 MB; 121 MB in 27,079 files on 2026-10-29). A write that takes it past the bound evicts the least recently used verdicts (```seon.fx/evict!```): oldest file mtime first, greens and reds alike, never one just written, until the cache is `:seon.config.proofs/results-evict-percent` under it, so the writes after it count nothing; below the bound nothing goes. A read touches the mtime (```seon.fx/stored-results```) and a write sets it, so a verdict a run reuses stays and a key whose test no longer exists ages out with no special case. The size is kept in the cache's `.size` file (other writers' changes make it a guess, corrected by the next count): a write under the bound reads and rewrites that one file and counts nothing (cost `seon.results-test/a-write-under-capacity-costs-nothing-of-the-cache`); past it the verdict files are counted once by metadata and the oldest removed (`seon.results-test/a-write-past-capacity-counts-the-cache-once`). An evicted verdict's test runs again once.
- **The questions** ([cost](cost.md#what-a-test-run-measures)): which tests at a tree's digests exercise f, and how much (```seon.proofs/exercising``` over ```seon.fx/details```), and its cost per call over them (```seon.proofs/per-call```). An agent asks ```my.agent/cost```. The cost trend over time lives in the merges' commit messages and the perf papers, not in the cache.

## What a digest holds, and what it does not yet

A verdict is reused when its digest matches, so whatever its run read that the digest does not hold can change under a green. The digest holds (```seon.program/graph-index```): the forms the test reaches by refs, macros, quoted names (in a test namespace, also the names its strings read as code), methods and fixtures; its namespaces' plain forms; the values of the config keys those forms read; `:env`; the input classes its reached forms name (```seon.program/env-class-readers```), the tree for a test namespace's form that reads files (`:scans`); and, in an agent, the branch's schema changes, changed files, config and, for a test reading the program as data, its program (```seon.agent/branch-inputs```). What it does not hold yet, each with when it was found, what covers it now, the fix and the session that owns it (a list that shrinks):
- **Schema entries chosen at run time** (found 2026-11-10; Tests). ```seon.db/entity-index``` picks an entity schema by the attributes an entity holds, which no name says; every test reaching it takes the whole schema class, so about 1,160 of 1,614 tests rerun on any entity-schema edit. Sound, coarse. Fix: recorded reads (task `seon.program/a-tests-verdict-holds-the-schema-entries-it-read`).
- **Names in data outside a test namespace** (found 2026-11-10; Tests). A string read as code is an edge only in a test namespace; a var named in src's data (a render named in a schema, a proc in system.edn) is a quoted name, not a reference.
- **Names resolved at run time from computed values** (found 2026-11-10 by the Tests session; Tests). `seon.root/binary-current`'s roots come from the data that names them (system.edn, the schemas' renders, the config's symbols), but two lookups take a computed name: `seon.cost`'s `requiring-resolve` of a cost proof's `:of`, `:input` and `:generator` (test-side), and `seon.model`'s script when a task's `:seon.task/config` names it rather than the config. A change to such a script is not seen as root-side.
- **A docstring read through a var's metadata** (found 2026-11-10; Tests). A form's code leaves its docstring out, and a test reading one takes the src class only when its namespace calls `clojure.repl/doc` or names `:var/doc` or `:ns/doc` ([source](source.md#what-a-test-takes-of-a-forms-text)). `(:doc (meta v))` is not seen: `meta` is in every `deftest`'s expansion and `:doc` is no fact a form holds (`seon.model-test/a-transport-failure-is-answered-to-the-agent` is one). Neither is a src function reading docstrings for a test, a render of a var. Covered by the full run; a form's facts naming the unqualified keywords it looks up would close it.
- **Task files** (found 2026-11-09; Tests). A task file is no input of any digest (`seon.task-files-test/the-trees-task-files-and-pages-load-with-no-refusal` says so): an edit to one is the full run's.
- **What arms a process** (found 2026-11-10 by Context; Tests). Contracts armed or not change a cost proof's count (a health read measured 87 inside an agent against 88 by `bin/test`); the place keys are out of the digest by design, the arming is not yet named.
- **A run that died** (found 2026-11-10 by the managing session; Tests). A test or check step that dies on an unhandled exception writes no verdict, red or green: nothing reuses it, and nothing counts it either, so its run must end red on it (`bin/test`'s exit, the step's log).

## A slow test runs last

A test measured at `:seon.config.proofs/slow-test-ms` or over is left out of an agent's run, so one slow test never slows every turn, and `bin/prove` (bare or `--merge`) runs it last: the slow tests with no green at their digest run once everything else is green (owner, 2026-11-08: "Yes, run them early": a session's own prove runs the process and slow tests its change reaches, so a red shows before landing and `bin/land` reuses the greens; a bare run and a `--merge` run share one marker per tree), so a fast red answers first and no red waits unseen behind merges (owner, 2026-11-07: "The slow ones are just the last ones to run"; 2026-11-08: "Slow tests should be treated as bugs and fixed", so a slow test is fixed at its cause, most often a root it boots that it could share or do without, or cut, never only run last; before it, 2026-11-06: "exclude them by default until they can run fast"; a slow red stayed on main through every merge). The measure is the system's own verdict cache, read by ```seon.fx/slow-tests```: the fastest of its newest greens and its green at its digest, because load only ever slows a run, so a test is slow when it is slow every time, and only for the tests that would run (```seon.proofs/plan-of```), so a test green at its digest costs nothing.

- **What runs it:** a merge's last tier, naming it (`bin/test NS/TEST`), `bin/test --all`, and a task whose proof it is. `bin/prove` prints each with what it measured.
- **It comes back by itself:** make it fast and run it by name; its green at its digest is under the bound.
- **It is work:** ```my.root/file-slow-tests!```, which `bin/update` calls once root is up, files each slow test as a held task from ```seon.template/slow-test```, with its measure, the bound, and itself as its proof. Cost: about 4 s over the whole cache (1,641 tests, 132,798 verdicts).

## A test's tick budget

Every test runs under a budget of engine ticks of its own (work done, never time; owner, 2026-10-29: "I don't want long running tests period and I want to catch the problems sooner"), set in one place, ```seon.proofs/run-tests!``` (bin/test's shards, an agent's test child, the judge): `min(:seon.config.agent/test-ticks, max(:seon.config.agent/test-ticks-floor, :seon.config.agent/test-ticks-factor x the median of its green verdicts' ticks at any digest))`, from ```seon.fx/test-budgets```, which reads the history once a run (about 2.5 ms a test: 1,367 tests in 3.5 s over 45,000 verdicts, from each green file's first 768 bytes). A test with no green gets the floor, a `^{:seon.test/ticks N}` on its deftest raises its own budget to N (never past `test-ticks`; the mark is its source, so it is in its digest), and the budget used is on its result (`:budget`, in the verdict). A test past it is red with the typed `:seon.test/ticks-spent` `{:ticks :budget}` naming the budget, and the run goes on ([failure points](failure-points.md)).

- **Chosen from the cache** (2026-10-29, 45,333 verdicts of 1,194 tests): newest green ticks median 1.7 M, p90 153 M, p99 1.7 G, max 8.3 G. A test's own greens sit at 1.0 to 1.07 x their median through p90 and 3.3 x at p99, because the digest moves with the code a test reaches, and the worst are tests that scan the source (a green at 3 G against a median of 1.8 M). Floor 4 G (1 to 5 s of work) and factor 10 trip no green but one runaway: `seon.db-test/a-create-that-fails-leaves-no-store`, three greens of 81 to 147 G against a median of 264 M. A floor of 1 G tripped 8 greens at factor 20 and 14 at 50.
- **The history is not in the digest** (the choice). A verdict is reused by digest, so a budget that read the history would move every digest with each green written, and no verdict would reuse. The digest takes the three config keys instead (```seon.fx/inputs```' `:env`, as it takes `test-ticks`), so changing a key reruns everything once, as changing the cap does. The cost: a red `:seon.test/ticks-spent` is cached at its digest like any red, and a test that legitimately needs more than the factor allows has no green to raise its median, so the author marks it (`:seon.test/ticks`), which moves its digest.
- **A cap lower than the floor wins** (`test-ticks` is the cap on every test), and a test whose median green is itself large (the heaviest: 8.3 G, so a budget of 83 G under a 200 G cap) is bounded by the factor and the cap alone.
