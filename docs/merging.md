# Merging

How a branch is merged into main: what it runs, how batches are proven, and how conflicts are resolved. Who merges and why is [AGENTS.md §3](../AGENTS.md) ("Integrate small and often", "Testing: compute only what is needed"); the machine the proofs run on is [machine](machine.md).

## A worktree session works in a checkout of its own

A worktree session is a separate instance of the whole system: `bin/worktree NAME` (run from the main tree) makes a worktree on branch ``jolt/NAME`` from main (at `.worktrees/NAME` inside the root; `bin/worktree --path NAME` prints it), with its own submodule checkouts at their pins, an APFS clone of `target/` (so `nice -n 15 bin/build seon` is the only build), its own ports (`config/local.edn`, `bin/ports`) and its own stores under its `runs/`. In it:
- `bin/root start | status | stop` runs that worktree's own root, never the standing one (7888); a Claude session started in the worktree reaches it through the committed `.mcp.json` (`./bin/mcp` asks this checkout's root);
- `bin/prove` runs what the change reaches, nothing else ([below](#a-merge-runs-what-the-change-reaches)); `bin/test NS` runs one namespace's selection and `bin/check MODE` one check step; `bin/check` (one mode or a run) works on a store of the checks' own, ``target/check-store``, seeded when missing (`SEON_STORE` names another): `runs/store` is the worktree root's, made without the example program the checks seed, so reusing it fails steps falsely;
- after each merge into main: `git merge main` in the worktree, then `bin/worktree --sync NAME` (it moves only this worktree's submodule checkouts to the pins its branch records; never `git submodule` in a worktree);
- a submodule the session adds (``reference-code/X``) is written as a `.gitmodules` entry and a gitlink, with its checkout cloned from a local copy; root initializes it in the main tree when it merges (`git submodule update --init reference-code/X`), so later worktrees get it.

`bin/worktree-check` (run from the main tree) proves this whole workflow end to end with a throwaway worktree session and removes it; run it after a change to `bin/worktree`, `bin/root`, `bin/mcp` or the build. Leave nothing running: `bin/root stop` before you report. Root removes the worktree after the merge (`bin/worktree --remove NAME`).

## A worktree session's part

A worktree session merges main into its branch, proves the merged result with `bin/prove`, and reports. Branches live hours: merge main into yours after every merge into main. Iterate at the REPL first, then with `bin/prove` (or `bin/test NS`), never a full run per edit. Long runs only when the work is done: the full `bin/test --all` and `bin/check 100` run once per session, when it believes its task is finished and its review findings are fixed. To be merged, report the commits, proofs red → green, numbers against estimates, what you deleted, `bin/prove`'s last lines (and the check's ``target/check/<time>/`` path when steps ran), and that nothing of yours is running.

## Every branch is reviewed before it merges

A reviewer reads the branch's diff against main for AGENTS §9's mistakes (a guard, a fake default, a clock deciding, a second mechanism, a fix at the reader instead of the producer, an old word of §7a, a test that cannot fail, an ignored answer), each finding with its file:line and its right fix. The worktree session fixes them before its branch merges; the proof it reports is the run after the fixes.

## Root merges, and reads the verdict

Root merges the branch, never copying files over newer changes, and reads the merged tree's proof to its last line before main moves.
- Every stage's exit status decides the next: no pipe hides a failure (`setopt pipefail`, output to a log), and a check counts only if the build before it succeeded and the binary was built from the tree it proves (`bin/test` builds `target/seon` whenever anything runs).
- Root rebuilds main as part of every merge, so a worktree made from main never reads config with a stale binary.

## Main goes first

A merge's verification is one command, `bin/prove --merge`.
- **One command, one verdict.** It runs every test and `bin/check` step with no green at its digest, the ones that reach a process too (the plan's `:merge` mode, `test_runner/plan-of`: nothing is left out and none is named by hand), then `bin/check contracts` and `bin/check smoke`, each whatever the one before answered. It ends on `MERGE OK` or `MERGE FAILED` from those exit statuses alone, and appends its line to `notes/merge-log.md`: the sha, the plan's counts, each verdict, the reds, the src delta of HEAD against its first parent, and the keys left out against main's last merge line. So a merge line cannot say green over a red exit, and a step cannot go unrun unsaid.
- **No lock.** Nothing waits on main's verification (owner, 2026-10-27: "Remove it"): it runs niced like any run. It rarely runs, since a branch that holds main and proved its tip merges with no run on main, and load is kept down by not running the same work twice, not by ordering runs.
- How many heavy runs go at once is AGENTS' number (§2), not a gate here.

## A merge runs what the change reaches

A merge runs what the change reaches, not every check. The merge's proof is `bin/prove` on the merged tree, then `bin/check smoke`; `bin/laws` (every law's sites) and `health` ([health](health.md)) run inside it as steps keyed by the whole tree. One rule selects for everyone: a key runs exactly when no green result is recorded at its reach digest (```seon.proofs/plan```), on the standing root's main, where every checkout's runs record them ([results](#results-are-facts-on-main)), so an unchanged tree runs nothing and a result proven in any checkout is reused in every other.
- **What reaches a process runs when asked.** A run that names nothing (`bin/prove`, `bin/test` with no namespace, the on-change runs) leaves out every test and bin/check step that reaches a process of its own: a root or an agent booted for it, a fork, the binary (a shell call, git or perl, is none: it costs milliseconds; ```seon.program/reach-index```'s `:process?`, the one walk, over `:seon.config.source/process-vars`; ```seon.proofs/left-out```, the one filter bin/test and an agent's run apply). Owner, 2026-10-23: "Tests shouldn't be running agent turns. Not automatically run tests at least." They run when named (`bin/test NS`, `bin/check MODE`), in a merge's verification (`bin/prove --merge`), in the full run (`bin/test --all`, `bin/check 100`), and at the judge before a merge whose change reaches them, nobody asking (owner, 2026-10-27; the reconciler's `:gate`, on the declared `:seon.config.source/gate-checkout`). Measured from the recorded durations of the 2026-10-23 full run: those were 90 of 443 tests and 782 of their 917 s, and every check step that boots a root; a run that names nothing went from about 26 minutes to about 2.
- **The binary is built when a selected key uses it.** `bin/test` builds `target/seon` (about 46 s) only when a selected test uses the binary (```seon.program/reach-index```'s `:binary?`: a reached form references ```seon.test-store/binary-sh```, the one way a test runs it, other than a form that only names it as data or is its own definition) or a selected step runs a `seon.check` mode (```seon.proofs/step-needs-binary?```, from `check-steps`: laws, lmdb-kill, lmdb-sem and forks run none). The plan writes `out/binary` and `out/steps-binary`; empty, `bin/test` builds nothing and `bin/check --steps` seeds, lists and drops nothing. A step that ran no mode is stored green whatever binary stands. Measured on the shared machine: `bin/prove --checks` selecting only `laws` and `lmdb-kill` ran in 16.8 s (plan 8-15 s, the two steps a few), and 9.4 s when both were reused; the 46 s build and about 6 s of seeding and dropping it used to add are not spent. With it, `bin/test`'s plan makes the one store the process tests' roots take a branch of, `target/runs/test-store-<schema digest>` (```seon.test-store/make-process-store!```, named by ```seon.test-store/kept-store!```), once when it is missing and before any shard starts; shards whose roots each made it raced, one opening the store another was still creating. Both kept stores of regenerable output, it and the program store, are named by the schema's digest (```seon.db/schema-digest```): a changed schema makes a new store, and one of another schema is removed, never migrated or refused.
- **A shard's agent tests share one root.** ```seon.agent-test/in-agent``` asks ```seon.test-store/shared-root!``` for the shard process's root for its root arguments (its `:dirs` and `:sets`), started at the first test that asks, on a main of its own of the process store, and stopped with its main dropped when the shard process ends (a shutdown hook; hooks run at once, so no other hook may remove what its stop uses: the starter fifo is reclaimed by the next process instead). Each test loads a task file of a namespace of its own (`t<8 hex>`), attaches its own agent and names both by what the attach answered, never by a counter's value (`a1`, `demo/t`); at its end its agent is killed, its end awaited, its tasks cancelled (a run left `:running` keeps the reconciler from quiet, and a later test's ```seon.await/await-quiet``` would wait on it forever) and their branches deleted. Its task and run facts stay on the shard's main and go with it. A test whose agent merges into main (`:own-root? true`), and every test whose subject is a root's life (boot, stop, kill, a generation: ```seon.test-store/start-root!``` directly), keeps a root of its own. Measured 2026-10-27 on the shared machine (load about 8): a root's boot was 9.5 s of an in-agent test's 15 (4.8 s of it the source import), an attach on a running root 66 ms; ``seon.repl-test``'s nine agent tests went from 13.1-15.7 s each to 2.3-5.5 s after their shard's first. The digest is unchanged: the root imports and runs the checkout's tree (```seon.fx/read-source```), so an agent test's input is the tree (`seon.test-store-test/agent-tests-in-one-process-share-its-root`).
- **Tests.** A test's key is its reach digest (```seon.program/reach-digests```: the forms it reaches through refs, macros, quoted names, methods, fixtures and schemas, plus the checkout's inputs with no program facts; [source](source.md#tests-run-by-reach)). The digest is the tree's, never the process's: the same commit gives the same digests in any checkout and any run (`seon.program-test/the-same-tree-gives-the-same-digests-in-any-checkout-and-any-run`). A test takes only what its reach names, never the whole tree and never the whole schema registry (owner, 2026-10-27: "I don't care if it's perfect and if it's possible a test could be doing other work we don't know of … no tests should include all of src"): a schema entry it names as a literal keyword, or that a contract it reaches names, and no more, though `seon.db/schema` derives the store's attributes from every entity schema and a renderer looks properties up by a computed key. What a reach cannot show (a file read by a path built at run time, a schema looked up by a computed key) is the daily full run's to catch (`bin/test --all`). `bin/test [NS ...]` reads the program of the checkout's git tree, selects, and deals what runs, a namespace at a time, into `:seon.config.proofs/jobs` shards, each a process of its own started at once and reaped by the shell (```seon.proofs/run-tests!```). The program is a function of the tree, so it is kept per tree (```test-runner/program-db```): a branch per tree id in one LMDB store per checkout (`:seon.config.proofs/program-store`); a tree never seen is branched from the kept tree with the fewest changed program files and brought current by ```seon.source/refresh-tx```, and only an empty store imports the whole program; every text is read from the tree's git objects, one writer at a time per store (measured 2026-10-23: the selection ~15 s with an empty store, 1.65 s on a kept tree, 1.7 s after a one-file edit; what is left is the reach graph, ~1 s). A shard sends its results, greens and reds, with their failures and its tests' function costs, to the standing root once it has run, one request (```seon.proofs/record!``` there; a refusal is named, `UNRECORDED`, and its tests run again; no root answering keeps the request to send later), unless the tree changed since the plan took its digests (an edit during the run: what ran is not what the digests name); a shard that dies midway stores nothing. A green is reused and so is a red, with the failures it recorded; a digest that judged both is flaky, red and never run again ([health](health.md#a-flaky-test)). The shards are dealt by each test's last measured ms (kept per checkout in `target/prove/ms`, one file per test), the longest part first into the lightest shard, a namespace longer than a shard's share split into share-sized parts, so they end together (`test-runner/shards`; measured 2026-10-23, dealt by count, the four shards of a full run ended 437, 397, 110 and 68 s in). A shard records its results only if the tree is the plan's both before and after its run.
- **Check steps.** Each `bin/check` step is keyed the same way by the `seon.check` mode functions its body runs: `seon.proofs/check-steps` is the one list of the steps (`bin/check` reads it from ``./seon steps``), and `seon.proofs/step-digests` digests them ([checks](checks.md#modes)). A change to `seon.check/smoke` or what it calls reruns smoke; a change to bin/, native/, resources/ or a pin (the binary's other inputs, `:env`) reruns every step. `bin/prove` runs the steps to run through `bin/check`'s own bodies (`bin/check --steps target/prove`: the names in ``target/prove/steps``, the greens written to ``target/prove/green``) and stores the greens at their digests unless the binary was built from another tree than the plan's. A run's steps run at once, `:seon.config.proofs/jobs` at a time (a FIFO of tokens: a blocking read, no poll), the longest first by the last run's measured wall seconds, each on an APFS clone of the one seeded store (one root per store: two roots branching at once can drop a branch from the store's roster, task `seon.db/two-processes-branch-one-store-at-once`, and root collects only as the store's only writer, [storage](storage.md#collection)), deleted when it is green; `scale` runs alone after them, since it measures the machine's memory. Each step's wall and CPU seconds are kept beside its log (`STEP.time`), and each shard's beside its (`target/prove/tests/shard-<i>.time`).
- **Agents.** A Seon agent's run (the turn's observe, the judge's, the merge gate, and `(my.agent/prove)`) uses the same `plan` against the agent's base, main at its merge base (`seon.agent/test-plan`, [source](source.md#tests-run-by-reach)). Its digests' inputs with no program facts are its root's: the `:source` read (```seon.fx/read-source```, on an effect worker) answers the source tree's inputs (```seon.fx/inputs```), and ```seon.root/import-source!``` writes them on that boot's `:seon.root/source` fact only when the running binary is built from that very tree (``target/seon.tree``, which `bin/build` writes; ```seon.fx/tree-id```), with why not otherwise (`:unshared`). An agent uses only its root's current boot's inputs, so a previous root's never key its results. An agent's runs are the test service's, which records their results on main ([results](#results-are-facts-on-main)), and an agent reads results on its db and main: a test that is the same is not run again once green, by an agent or a checkout, "especially when freshly branched" (owner, 2026-10-23); every eval is a recorded form, so the digest covers what ran (`seon.agent-test/an-agents-greens-and-a-checkouts-are-one-store`).
- **What an agent runs** (root's ruling (a), 2026-10-22, from step E's run 7, where a change to `seon.problems/report` put 294 reached tests in every turn's run). A turn runs the task's proofs and the tests the branch itself changed or added, each test under `:seon.config.agent/test-ticks`, the one per-test bound bin/test and the judge use too, so a test has one verdict wherever it runs; root's judge runs, once at the run's end, the plan's tests other than process tests that are not proofs, less every one green at its digest (what the turn ran green it never runs again, and with nothing left it forks nothing) (`(my.agent/prove)` runs the same). A process test (one whose reach references a var of `:seon.config.source/process-vars`: an agent, a fork, a root of its own, the binary; ```seon.program/process-tests``` over ```seon.program/reach-index```, the same walk as the digests) never runs automatically unless it is one of the task's proofs (```seon.agent/run-selection```), and otherwise only when named (owner, 2026-10-23: "Tests shouldn't be running agent turns"): a process test left out is listed as deferred. Main's tests judge a branch whether or not it still holds them: a test its base holds that the branch removed is selected by both runs and defined in the test child from the base's source (```seon.agent/test-plan```'s `:removed`), so a red one refuses the run and names main's test (owner, 2026-10-26: "deleting the old test doesn't stop the old test from running"; `seon.agent-test/a-branch-that-deletes-mains-test-it-breaks-is-not-merged`). The plan reads one reach graph, main's: the fork server keeps it (`:graph` in its state, built at the first fork and brought to its db by ```seon.program/reach-update``` at each later one), and every agent forks holding it (```seon.agent/base-graph```), so its base's graph is that graph updated to the base (a resumed branch's older base, each merge-main), never built in the agent, and the branch's is the base's updated by what the branch changed since: measured 2026-10-23 on Seon's program, the base's graph 640 ms and 816 MB once, then a plan's update and index 20-45 ms for a one-form change, where each plan walked the branch whole before (0.5-1.1 s, five plans in a loop turn 4.3 s); with main's graph forked, a loop turn's five plans took 76 ms (measured 2026-10-23, e2e-loop, against 1.1 s with the base built per run). The turn's contract gaps read what changed (```seon.merge/uncontracted``` over ```seon.merge/delta-changes```, about 6 ms on Seon's program), and its unmerged entries read the program at their own keys only (```seon.merge/unmerged```).

- **The merge gate** (root's rulings, 2026-10-22/23; owner 2026-10-27: nobody asking). A merge whose branch's change reaches process tests (`:seon.run/deferred`, recorded by the judge) runs them before it merges, on a worktree of the root's gate checkout (`:seon.config.source/gate-checkout`; undeclared, the root's own source root, the standing root's merges tree, written by ```seon.root/start!```) at the merges head with the candidate's changed files over it, through prove's entry (the `:tests` effect, ```seon.fx/run-tests```, which reads each test's result at the digest prove's plan wrote in `target/prove/tests.edn`, on the results root's main, read back by its `:results`: ```seon.fx/test-results```); their results are `:seon.run/deferred-results`, and a red, or a run that could not run them (`:error`), refuses the merge as a red proof does. A changed namespace the gate cannot read from the branch (no `:ns/file`: made at the REPL, never written) is named with why on the run (`:seon.run/gate-unread`) and on its `:unrun` row, and the run, over another tree than the one that merges, vouches for none of its tests (each `:error`). A root with no checkout to run them on (a test's root given no source) holds such a merge, its reason naming the tests. ```my.root/gate!``` still runs them for a run that merged before, and the `:seon.task/gate?` it sets is no longer read.

The full runs are explicit: `bin/test --all` and `bin/check 100`. They are also the safety net of the reach digests: a test is digested by the forms it reaches, never by the tree (owner, 2026-10-27), so a file it reads or a binary it runs that its reached forms do not name can change without rerunning it, and the full run finds it. They run once a day in the background, once per worktree session when its work is done, and before a merge that changes boot, the writer, the reconciler or the build; a red there becomes a task, not a blocked merge.

Measured on the shared machine, niced, at about 370 tests and 34 steps: selecting takes the import plus the digests, 7-12 s; an unchanged tree reuses every green (`bin/prove --checks`: 34 of 34 steps reused in 8.5 s, against about 6 minutes for `bin/check 100`); a one-defn change on the agent's turn path ran 71 tests and 33 steps in about 11 minutes; a cold run (nothing green) took about 19 minutes. A digest follows the tree, never what the process analyzed, and a test takes the whole tree as an input only through ```seon.program/env-readers```; a pin bump moves `:env` for every test, honestly.

## The test service

One proc, `:prove` (```seon.prove/prove-proc```, declared in `resources/seon/system.edn`), admits every request to run tests, whoever asks: a Claude session (the server's `:prove` op, the MCP tool `seon_prove`, ```seon.root/prove!```) and an agent's turn (```seon.agent/prove!```, which ```seon.turn/observe``` calls) share it, so a change is proved once.
- **The key names what the run reads** (```seon.prove/run-key```: `branch@digest`, with the test namespaces when a request names some, and `!turn` for an agent's turn, whose run is the proofs and what the branch changed; the judge's is the plan's tests; owner's ruling 2026-10-24, DECISIONS). The judge asks the service too: its `:judge` request makes the agent call ```seon.agent/prove!``` in mode `:judge`, so the judge's run is recorded on main like any other. A branch's tx is not it: any write moves the tx, a run's own result facts, its prove agent's end and the eval that asked among them, so a key at the tx made every repeat ask a second run.
  - **Main's** digest is main's program digest (```seon.program/program-digest```: its live forms, schema entries and namespace tails, one read of their datoms), as an agent's is: its run reads main's program, its tests among it. A write of data never moves it; a moved key that changed nothing a test reaches is a re-plan that reuses every green. It is coarser than the per-test digests (```seon.agent/test-plan```) because it must be known before the run is admitted.
  - **An agent's** digest is its branch's program digest, its tests included; the root's inputs it also reads are fixed for the boot, as the service's state is. Its merge base is not in it: a merge of main that leaves the branch's program as it was keeps the answer, which then covers more tests than the new selection, not fewer. An agent's turn commits, then asks with the digest of its head (```seon.agent/prove!```); a session asks with the digest ```seon.root/prove!``` takes of the same head, so both ask for one key.
- **Admission.** One run at a time per checkout. A request whose key is running, or is the next to run, joins its waiters. A request for another key while a run is in flight replaces the next run of its branch (the latest wins, and the askers it replaced follow the newer run). Branches take turns in name order, so a burst on one branch never starves another. A key whose run ended is answered at once from that answer, until the key moves. Every waiter is answered exactly once (```seon.prove-test```).
- **A run is a chain of requests the proc sends the api.** The agent that holds the branch forks itself and runs the plan (```seon.agent/run-tests-forked```); main has no such agent, so a prove agent is forked from the fork server's main onto the `tests` branch, holding main's program and its tests (`:seon.config.source/dirs` takes `test/`), runs them, and is killed.
- **Main is proved at each program commit, nobody asking, when `:seon.config.proofs/prove-main-on-commit` says so (off by default: the run of all of main's tests in one child dies, task seon.agent/a-test-run-streams-its-reports).** The writer's commit notice (`:main`, a sliding buffer of one) is a request when its ops move the program (```seon.program/moves-program?```, what moves the fork server's reach graph too): a run of main keyed by its program digest, with no waiter, which a session asking for the same key joins. A burst of commits is one run, the latest. Its results are main's facts, so every agent forked after finds main's tests at their digests and runs none of them again (`seon.prove-test/main-is-proved-at-each-program-commit-and-an-agent-forked-after-reuses-it`); process tests are left to the merge's `bin/prove --merge`.
- **Results are facts on main, one per test digest that ran** (`:seon.proof/digest`, greens and reds, ```seon.prove/result-tx```), written before the waiters are answered, a fact per run (`:seon.proof.run/id`, with its detail) and main's newest result per test (`:seon.proof/latest`, which `:test-red` reads) ([results](#results-are-facts-on-main)). ```seon.agent/test-plan``` finds a result by that digest on its db and main (```seon.proofs/stored-results```), green or red, so a digest that holds a result is not run again. A red is reused as a green is, reported with the failures its run recorded and marked `:reused`, since a test's verdict is a function of its digest (one per-test tick bound everywhere).
- **A red is a class,** `:test-red` ([health](health.md#a-red-test)), read from the newest result per test; a later green at a new digest closes it with nothing written.
- **The writer's commit notice** (`:main`, a sliding buffer of one beside the reconciler's) tells the proc main's latest tx. A process test (```seon.program/process-tests```) is left out of a run that names nothing, unless it is a proof (```seon.agent/run-selection```): the answer lists it as deferred and the run's fact records it as `:seon.proof.run/skipped-process`.

## A branch proves its in-process tests, main's batch runs the process tests once

Owner, 2026-10-27: "Why are we reverifying on main? Don't do unnecessary work if the agent on the worktree can validate the merge." Process tests read the whole tree, so one branch's merge moves every other branch's digest.
- **A ready branch that already contains current main**, and whose own plain `bin/prove` ran at that tip (with `bin/test` of the process-test namespaces its change reaches, or its `--merge`), is merged `--ff-only` with no run on main: its tree is the one it proved. Prefer this: ask a branch that is one merge behind to merge main and re-prove (every green at its digest is reused) rather than verifying on main.
- **A `bin/prove --merge` on main** runs only when branches are combined into a tree nobody has tested (two or more ready at once, or one that does not contain main). One run covers the batch, after one `bin/build`. A red names its test: revert only the branch whose change reaches it (`(my.agent/tests-reaching ...)`, or its diff against the test), send it back with the log, keep the rest. Then `bin/update`.
- **Fast path** (owner, 2026-10-27: "Don't wait for fixes that should just be merged and tested later"): the dev-speed branches (reuse, the shared test root, tree-id) merge as soon as their own targeted tests (the namespaces they changed plus their proofs) are green. Their first full run is the next one main does anyway; a red the branch caused is fixed forward within the hour, and reverted only if it breaks main for everyone. Each is reported to root in one line.
- **A pin bump** goes in a batch of its own, and the main tree's submodule checkouts must be moved to the new pins before `bin/build` (`git -C reference-code/<lib> checkout --detach <pin>` in the main tree; a merge moves the recorded pin, not the checkout, and a run on the old checkout says nothing about the bump: seen 2026-10-27). For a datahike, persistent-sorted-set or konserve bump its diff and index tests run too.
- Heavy runs: no slot lock (owner, 2026-10-27: "I want a lock free system").

## Every merge's `src` diff stat is read

Root reads every merge's `src` diff stat before merging, against the goal of about 10k lines of our own code. Every function a merge adds names the existing system it extends, or why none could carry it; a new namespace or mechanism where an existing one could be extended is sent back, not merged; the merge's commit message states its net `src` lines (`bin/laws growth` prints them and the definitions the branch adds), and a merge that grows `src` says what it deletes or plans to delete.

## Conflicts and pins

A conflict is resolved by copying each side's lines, never retyping; the lines after `>>>>>>>` may belong to both sides; each resolved file's forms must balance as its parents' do. Submodule pin bumps happen only in root's merges into main, never in a worktree session's merge of main. A pin bump reaches everything, so its merge also runs the cost proofs `bin/prove` leaves out (`bin/test seon.program-cost-test seon.record-cost-test`): Jolt 0d39edc3 passed prove and still made reach-update grow n^1.96. Commits in the forks ([forks](forks.md): Jolt, Chez, Datahike, konserve) carry no AI trailers. ## Seon's merge is a three-way merge of the program

Seon's own merges (a branch into main, main into a branch) are git's three-way merge over the program as data, never over files.

A db's program is a map from keys (``[:form id]``, ``[:var sym]``, ``[:schema k]``, a declared datum) to content (```seon.merge/program``` of a db and its declared data attributes, which only tests read whole; a merge reads ```seon.merge/program-of``` at the keys that differ), and ```seon.merge/three-way``` compares base, ours and theirs: each side's changes, the keys to apply, and the conflicts. A merge reads only where the dbs differ (```seon.merge/delta-three-way```: the keys the datoms that differ bear, read on each side by index seeks, never whole programs; [storage](storage.md#merges-read-what-changed)). The writer's merges use it (`seon.writer/writer-proc`), and it is the one derivation behind the done rule's unmerged entries, the agent's merge of main and the dashboard. What merges is carried as it is: the branch's own datoms for those keys, with their entity and transaction ids (```seon.merge/merge-tx```). A conflict stays on the branch as an unmerged entry (```seon.merge/unmerged```), base, ours and theirs as data, until the branch redefines the key or resolves it (`my.branch/resolve!`, ```seon.merge/resolve-tx```). The files a merge touches are written back by [source](source.md); a merge task's turns are [turn](turn.md#a-merge-tasks-loop).

## Not built: a merge queue on root

Root's merges of worktree branches are git merges, batched by hand as above. Seon's own merges are merge tasks judged by the reconciler, one at a time: an octopus merge of several merge runs is built and off (`:seon.config.merge/max-running` 1, until one combined test run of all its members is proven). No queue on root merges main into each candidate, proves the merged result and batches the disjoint ones, and builds, tests and checks are not tasks on root (task ``seon.reconcile/a-check-step-is-a-task``).

## Results are facts on main

Every result is a fact on the standing root's main, written by its one writer like every other fact (owner via root, 2026-10-27: "one writer for sure"; "please tell me it's in the database and not a separate system"). It replaced the `test-results/` directory of one file per digest (349,131 greens and 783 reds, 1.3 GB on disk, 2026-10-27), which nothing reads now; the directory is the owner's to remove.
- **Who writes.** One builder, ```seon.proofs/record-tx```, and one writer, ```seon.proofs/record!``` (root's writer). The test service writes its runs' facts in the transaction that records them (```seon.prove/result-tx```). `bin/test`'s shards and `bin/prove`'s step runs send theirs to the standing root's server, one `:record` request each (```seon.server/ops```; the root is `:seon.config.proofs/results-port`, which `bin/env` sets to the main tree's server port). A root booted by a test has no results port and records only its own test service's runs. When no root answers, a run keeps its request in `:seon.config.proofs/unsent-dir` (`NOT RECORDED`), and the next `bin/test`, or the results root's `bin/root start`, sends it; a root that answers an error refuses it (`UNRECORDED`, red: those tests run again).
- **What is written: only what ran, only what changed.** A test reused at its digest writes nothing. A test that ran writes its result at its digest (`:seon.proof/digest`, test or step, status, run, ms, ticks, bytes, failures; `:seon.proof/green` or `:seon.proof/red` the first time it is judged so: both is flaky, red, never reused as green). A run writes one entity (`:seon.proof.run/id`, its tree or branch, counts) with one value, `:seon.proof.run/detail`, what each of its tests spent in each contracted function ({test {var [calls ticks self-ticks bytes self-bytes]}}, ```seon.proofs/detail```), stored once under its content key ([values out of line](storage.md#values-out-of-line)). A run of main's tree also writes each function whose self ticks or self bytes per call moved past `:seon.config.proofs/fn-noise` (```seon.proofs/fn-tx```, one `:seon.proof.fn/` entity a function). No datom a call, an assertion or a (test, function) pair. Measured 2026-10-27 on a worktree's root: 22 tests that ran wrote 198 result datoms (9 a test) and 4 runs 12 datoms, with 8 KB of detail values; the second run of the same tree wrote nothing.
- **What reads them.** A plan, by one AVET and one EAVT seek a digest (```seon.proofs/stored-results```): bin/test through the server's `:results`, an agent on its db and main. Measured on 700 digests (2026-10-27): 3.5M ticks and 12 MB, where the files read 2.39M ticks and 14.7 MB and spent most of their time in system calls, which ticks do not count.
- **The questions, by query** ([cost](cost.md#what-a-test-run-measures)): the slowest and the heaviest functions per call (```seon.proofs/slowest```, a scan of the function facts); what got slower than main's last measure (```seon.proofs/slower```, a run's or a tree's detail against them); which tests exercise f, and how much (```seon.proofs/exercising```: the results at a tree's digests, the few runs that recorded them, their details); flaky tests (`:seon.proof/red` with `:seon.proof/green`); slow or heavy tests (the results' ms, ticks and bytes). An agent asks ```my.agent/cost```.
