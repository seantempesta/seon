# Render: what a person or a model reads

Every view, the model's context included, is a render: the one value printer (`seon.print`), or a render function declared on the value's schema (``:seon.render/hiccup``). A render answers hiccup, and the page and the model read the same hiccup, exactly as it was returned: there is no second face for the model (owner, 2026-10-26: "don't leave anything out I want the agent to understand problems with the rendering functions"). Nothing else shapes output, and nothing clips.

**It's like React, or Reagent.** A render is a component: a plain function of its props and its children, Reagent's form, `(fn [opts & children] result)` (owner, 2026-10-23: "It's all just functions and results"; 2026-10-26, the call shape: [components](#components)). A render of one value takes it as its one child, `(fn [opts v] result)`. Its props are optional: `:as`, the room it is shown in (`:inline`, one line in a chat stream or a table cell; `:block`, a full panel, the default; `:tile`, compact and live; `:row`, one member of a page's list), `:budget`, its tokens, and `:handle`, the form its cuts read the rest through. A component that does not care about a prop ignores it. Its result is hiccup, which the page shows and the model reads. A schema declares the component of its values (`{:seon.render/hiccup sym}`), and ```seon.render/hiccup``` finds it in O(1) by the value's schema (the producer's `:schema`, the value's metadata, an error map's type when it holds every key an error holds (a map that only picks an error's keys is data), or an identity attribute: `seon.render/schema-of`); a value with none takes the default component, the one printer (```seon.render/print-hiccup```), which takes the same props and auto-renders: wherever a value inside the printed one has a render of its own, the printer shows that render in its place, one line (`seon.print/print-value`'s `:render`: a call of its render in the hiccup, the value in one line in the text), in its one pass (`seon.render-cost-test/the-printer-renders-nested-values-in-one-pass`: 19 contracted calls a nested value, linear). Inside hiccup, a vector headed by a function is a component call, as in Reagent: `[task-summary {:as :inline} task]` is written as what `(task-summary {:as :inline} task)` answers, itself expanded the same way, by the one serializer (`seon.web.html/html`); a keyword head is an HTML element. The render proc is the reconciliation, one level up: a page's parts (its units) render again only when their input value changed, and only the bytes that changed are sent (`seon.render-cost-test/render-calls-are-one-pass-over-their-nodes`: nested calls serialize in one pass, linear in their nodes).

## A render does no work of its own

What a person or the model reads is a render of what already exists: the render declared on each entity's schema, over the pull, and it never computes again what the system already computed (owner, 2026-10-24: "the debug page should be doing basically zero work … in the past I've asked for the debug page and entirely separate machinery that is somehow slower is built"). The debug html shows what was sent, made again from the facts of that turn's commit ([below](#the-debug-page-is-the-wire-request)), never a request rebuilt beside it; a render's cost proof shows it costs what changed. A session whose work changes what an agent is sent or what the owner sees opens it in a browser before it reports ([checks](checks.md#checking-a-page-in-a-browser)).

## No clipping

A cut never drops silently. It says what it omitted and how to read the rest. Storage keeps the exact value (an error's message, a running form, a provider's HTTP body travel whole); renders budget it. There is no `clip`, no `subs` for display, no `take n` without its count, and no stylesheet clip (`text-overflow: ellipsis`, `line-clamp`, `overflow: hidden` on text): the render's budget is the clamp.

## Text, and the one string cutter

Text is cut one way, inside a value or shown as itself: the printer's string cutter (`seon.print.select/break-at`) ends the shown part after a line break in its room's second half, else after a space in its final quarter, else at the room, and the cut says `…+N chars in M more lines` and the form that reads exactly the rest (`seon.print.emit/cut-words`). A string in a printed value reads `"its prefix"…+7279 chars in 88 more lines (subs result/h3 19523)`. A keyword or symbol longer than `:seon.config.render.agent/max-name` cuts the same way, its printed text read as `str`: `:nnn…+44 chars (subs (str result/h1) 257)`. Source text is code, not a string: its producer marks it (```seon.print/code```, plain data `{:seon.print/code text}` that a record stores and reads back as it is, recognized by ```seon.print.select/code?```: a form's `:form/src`, a red proof's `:source`, an assertion as written, a cited var's definition head), and the printer prints it exactly as written wherever it stands, every line where it stands in its file and a string's newlines as newlines (`seon.print.emit/code-text`; the width estimate counts each character once, `seon.print.select/code-width`; a cut's "more lines" counts the text's newlines, as `subs` reads them): any slice of the shown text is the recorded text, so a reader copies it into `seon.repl/edit!` as it stands, and no layout indentation enters a string, so a map holding it still reads as Clojure. A nested definition's later lines start at column 0, not under its key: re-indented under its key, or with its docstring's newlines escaped, no line of it would match the recorded text, and an edit copied from it would not apply (`seon.print-test/code-prints-exactly-as-recorded`, `seon.repl-test/an-edit-copied-from-the-shown-source-applies`). Text (```seon.print/plain```) is still indented to where it stands (`:source (deftest f-test …)`); cut, its cut reads `(subs (:seon.print/code (get-in result/a3f9c1d2 [:source])) 1200)`. The printer never guesses code from a string's text (owner, 2026-10-25: agents should see Clojure as it is in files or the REPL). A cited thing on the page is its cite drawn by its render (```seon.render.ui/cite-hiccup```, [an entity cites](references.md#an-entity-cites)): a section as Markdown, a var its source as code, each with the form that reads it whole (`(my.agent/doc "docs/render.md#one-printer")`, `(clojure.repl/source sym)`). `seon.print/plain` shows text as itself (unquoted) under a token budget, sized as the printer sizes (`:seon.config.ai/chars-per-token-prior` characters a token, `seon.print.select/estimate`, the one sizer: the history budget and the scripted model's usage count with it too): whole when it fits, else that same cut; given a source form that answers the whole text, the cut names `(subs source offset)` (with `:one-line?`, the offset is still the source's). On the page, `seon.render.ui/plain` links the cut to the page that shows the whole, or carries the whole in the cut's title; a printed value's cut names its result handle (`result/h3 at its REPL`).

A cut is read as its text, where it stands: the printer answers no list of its cuts. Decided by blind scoring on production-shaped values (`docs/render.md`): Haiku readers answered every question about a cut value from the inline cut alone (100%, 60 answers), and ranked it first in 30 of 30 three-way comparisons against the same text with a closing "left out" list (repeats every cut, up to 2.9x the tokens) or with footnote markers; text's cut words beat the bare `…+N` in 18 of 22 pairs (the unit and the line count tell a reader how much it is missing), and text's break beat a cut at the last line end, which can spend most of the room on nothing (47 of 256 tokens shown in one case).

## A value on the page is its structure

The page draws a value from its data, the model reads it as text, and both come from one selection: `seon.print.emit`'s hiccup fold reads the same operation stream the layout reads, so the text is unchanged by what the page shows (owner, 2026-10-25: "We can do more complex representations of values there"). A map is a grid of keys and values, folded as any collection is (a map of scalars, or the value printed, not at all). A reference, a map of identity attributes alone (a ref as a pull joins it: a message's sender `{:seon.agent/key "user"}`), prints as its identity value, alone and in the line of the value holding it, never drawn by its schema's render: so what is read of a message's line is its sender's name, as when senders were strings, while the data stays a ref (```seon.render/nested```; `seon.render-test/a-printed-reference-is-its-identity-value`; Point's ruling for the owner, 2026-11-10). Two or more maps in a vector sharing two or more keys are a `<table>`, a column per key and a `<tr>` per map (`seon.print.emit/table`). Text marked as itself is drawn as itself: code, `{:seon.print/code s}` (`seon.print/code`), verbatim in `<pre><code>` and highlighted as Clojure by highlight.js (served at `/highlight.js` from `:seon.config.web/public-dir`): one observer in the page's shell (`seon.render.ui/shell`) highlights each `code.language-clojure` (`seon.print.emit/highlight`) as it arrives and again when a patch morphs an element back to its plain text, so a per-element init, which a morph of unchanged attributes never re-runs, is not used; each mutation batch costs one scan of the page's code elements, and a screen eval opened under its turn carries the same `eval-eN` anchor; text, `{:seon.print/plain s}`, a paragraph; both print verbatim and unquoted, and a cut of either reads its rest through its key, `(subs (:seon.print/plain (get-in result/a3f9c1d2 [:plan])) 1200)`. A page an agent built is the value's own `:seon.render/hiccup` key, a render already made, and renders as that hiccup wherever the value sits (`seon.render/nested`). A handle, ``result/a3f9c1d2``, links to its eval's line, whose id is `eval-e12`, open or not. In the conversation an eval is one collapsed line (`.seon-eval`, ```seon.render.ui/evaluation```, the 2026-10-24 mockup's `▸ (form) · 12 ms`): the text beside it, its code's first line, its time and its handle, and what came of it (the error's message, or its value in one line), opening to the eval's own render (```seon.render.ui/evaluation```: its code and its value); the agents are a column beside it on a wide screen and a strip of chips above it on a narrow one; text (a model's reply, a message) reads in the system's text face (`--font-text`), code and data in mono. A cut opens where it stands: its marker is a button whose click posts `/open` with the id of the element it sits in and the form the cut prints, `(drop 1 (get-in result/a3f9c1d2 [:value :proofs]))`, and that element renders what that form reads from the record (`seon.print/read-rest`, the operators continuations are made of), so the page shows a cut's rest as the model would read it, under that form as the button that closes it (a button, not a `<details>`: the element's re-render would close a details, whose toggle would post the close); the form is read once, at the edge (`seon.web/open-form`), and an element renders again only when its set of opened cuts changes (its component key). An evaluation's line renders its response's value this way, its cost and the functions it called beside it; a value not held as data (`:printed`) shows as it was printed. `seon.print-test/a-map-is-key-and-value-rows`, `maps-sharing-keys-are-a-table`, `code-and-text-read-as-themselves`; `seon.render-test/an-eval-row-renders-its-value-as-structure`, `a-page-an-agent-built-renders-nested`.

## A render is a value, printed once

A view that chooses what to show makes a value, never text: an array map of what matters, in its order, and the one printer prints it once at the reader's budget. Nothing is cut before the printer: a long list is the printer's cut, which says what it left. Where a list's whole lives elsewhere, the value carries the form that reads it as data (`:all-in (seon.task/agents (deref (:conn sys)))`). It replaces the bounded lists (a list cut to a config key's first items with a `+N more` line, deleted with their keys) and the per-field budgets that cut each part before the printer (clipping audit, 2026-10-25).

A value too large or too host-bound to print whole declares a model render on its schema (`{:seon.render/model sym}`, ```seon.render/model```): a function of opts and the value, `(f {} v)`, answering the value to show in its place, which the printer prints like any other (its cuts, its budget). The agent's process state is one (`:seon.agent/state`, ```seon.agent/state-summary```): a bare `(swap! seon.agent/state ...)` answered 42,000 characters, and answers each key with a scalar's value, a collection's count or a host object's type, and the form that reads it whole.

A render's budget, when its env names none, is config too: `:seon.config.render/value-budget` for a value and `:seon.config.render/root-context-budget` for root's context (root's page's hiccup, printed by the render proc).

## The page

Every page is the render of a ctx through the one walk (```seon.render/walker```): the root render's own output is the page, its columns and regions ([a layout places its lists](#a-layout-places-its-lists)), set in root's frame (```seon.render.ui/page-chrome```: the top bar, the agents list, the page, the caption and the input), each placed component a unit whose input is its revision (owner, 2026-10-26: "There is only one context rendering system and it needs to be built from the parts"; 2026-10-25: the web UI finished from docs/render.md and the mockup of 4624f2f4f, not redesigned).

- **A location is a ctx.** `/` is for whoever is signed in: their focus, else root's page ([users](users.md#whats-on-screen)); `/root` is root's: the page of root's session, the agent keyed `root` made at boot (```seon.render.proc/location```). **Each page is its entity's render** (```seon.render/render-var-of```): the `:seon.render/hiccup` its entity schema declares (an agent's and a user's ```seon.render.ui/agent```, the system entity's ```seon.render.ui/root```), or the schema it extends does, and every walk is rooted on it with the entity as its argument: a user's and a branchless agent's kept walks, root's system walk, root's cold draw of a branch, the model's request (```seon.ctx.wire/render```) and an agent's own walk (```seon.repl/the-walk```). A branch that holds no entity yet is named by its agent's key. No caller chooses a page's render (owner, 2026-11-08: "The layout does come from the entity"; `seon.render-test/an-entitys-schema-names-its-layout`, `each-page-draws-its-entitys-layout`). One render answers top or nested: where a parent's pull joins an entity, the walk places it as it places a tile (```seon.render/entity-render``` marks it `:seon.render/nested`), and a page's render answers with the entity's entry (an agent's: a link, what it works on, how it stands, what its agent last told whoever started it, the agents it started under it). Every page shows the signed-in user's agents list, drawn by the user's one walk (```seon.render.ui/agents-list```, its `#c-side`, placed by ```seon.render.proc/user-sides```): root's line, then what the user started, by the entry; only the middle is the page's own. `/agent/{name}` is an agent ([a session's address](#a-sessions-address-and-the-agents-list)). Any other location is a `:seon.render/no-location`, answered 404 (`seon.render.proc/location`).
- **A user's page** is `/user/{name}`: an agent found by its `:seon.user/name` and read from main, as an agent with no branch is, drawn by the agent's render (```seon.render.ui/agent```: a user is an agent). Its pull (```seon.task/user-pattern```, written on the user at each boot) joins the agents it started to `:seon.config.render/agent-tree-depth` levels; an agent at the last level says how many it started below it, never a silent cut. They are its tiles and its agents list, each by its entry, those that need the person first ([users](users.md#whats-on-screen)).
- **Root's page** is root's session's page, drawn by the agent's render like any agent's: its conversation, its tiles, among them the user who started it (its pull joins `:seon.agent/_agents`, as the user's own pull does), drawn as the person Seon works for with the agents it started under it, each by its entry with the ones it started below it (```seon.render.ui/agent```, nested; root's own session, the page itself, is not listed). Beside it the frame places the system's own view, from the system entity's walk (```seon.render.proc/root-walk```), by the mechanism that places the agents list: its head says what is going on in a sentence, from the tasks' states (```seon.render.ui/root-head```: "2 parked, 1 running."); its tiles are root's process (```seon.render.ui/process-tile```), main's open problems (`seon.problems/health`), what needs fixing apart from what is upkeep (`:seon.problems/attention`), and the evals sent to root (```seon.render.ui/root-evals```). Root's process (the writer's, the fork server's and the store's numbers, each proc's defects and the newest events, ```seon.render.proc/process-value```) is root's own data, part of the system walk's ctx (`:process`) beside its db pull, never written (root's ruling, 2026-10-27): the render proc assocs it in when it changed and flushes the walk, so only the tile that reads it runs again. A stored value may no longer fit the schema it names: it is then drawn and printed as the data it is (`seon.contract/fits?`), so an old record never breaks a page.
- **The input is at the top**: an agent's REPL, messages, interrupt and release (```seon.render.ui/agent-input```), root's request box (```seon.render.ui/root-input```; its spawn and evaluate-in-every-agent are on root's debug page, ```seon.render.ui/root-tools```), each a UI call of root's request table ([dashboard](dashboard.md#callbacks-are-data)).
- **An agent's page is one layout, read by the model and the person** (owner, 2026-10-28: "Is there no rendered chat ui that is user facing and you're showing me the debug page?"; 2026-10-29: "build with both the context render and the web ui render in mind so we don't let one get out of sync with the other"). `/agent/{name}` is the agent's render (```seon.render.ui/agent```), of the agent's ctx: a chat column (`#c-rows`: the example sessions it reads, then a component for each turn, ```seon.render.ui/conversation-turn```, holding the model call's one message (`:seon.model-call/reply`) in Markdown with its thinking folded and the evals it ran under it (the call's own render, ```seon.render.ui/model-call-view```), and each eval of another hand as a line that opens to its value, a call of several forms showing its vector of values; how the agent stands at the end). The task's list (`#p-task`: the task with each proof's status from the `:seon.test/*` facts its record holds, each var its plan cites, the namespaces the work touches, how its work stands ([how the work stands](#how-the-work-stands)), its turn, its open problems, the keys the agent added) are what the model reads, placed in the column beside the chat, the same components, so a person sees what the agent was told (owner, 2026-11-08: "What happened to the sidebar on the right with all the rendered context parts?"); the `@ctx` tab shows each beside the text the model reads of it. What the model reads is the same components, so the two cannot drift (`seon.render-test/the-model-and-the-page-read-the-same-parts`): the task's list as parts (```seon.render/page-lists```), the conversation as each record's model render (```seon.render/openai-compat```). While the agent's process runs, the page is what it draws (```seon.repl/render-ctx```, asked by the render proc for a watched page) when it drew at the branch root last read or later; otherwise root draws it from the branch with the same walk. A process works its whole run as one request, so its answer comes when the run ends, and until then root's draw shows a person's message the moment it is delivered and each eval as it lands (owner, 2026-11-08: "the user message doesn't show up until the agent has finished their turn"; `seon.render-test/a-working-agents-page-follows-its-branch`). `/agent/{name}/ctx` is not a second layout: it is `@ctx` printed, the agent's record as data by the one printer (```seon.render.ui/ctx```, the `:seon.ctx/ctx` render), drawn by root from its branch.
- **The chat reads as a chat** (owner, 2026-10-29: "a friendly chat window that my mom could use"; 2026-11-06: "show the eval intent markdown descriptions and collapse the eval statement and the output by default"). It opens with what was asked (```seon.render.ui/chat-ask```): its start, then the whole as Markdown when "Read all" is asked. Each turn number is one component of the column (```seon.render.ui/conversation-turn```), holding what the turn took and did in the model's order (a message, the model call, the evals of other hands: what its model call holds in ctx, [turn](turn.md#the-turn-is-a-number)). A model call is one message, what the agent said, its reply in Markdown (```seon.render.ui/model-call-view```, placed by the call's own view, so one component answers the page and the model), its thinking folded, then each eval it ran as a step (```seon.render.ui/evaluation```, placed by the eval's own view, so one component answers the page and the model; a model's eval is its call's, `:seon.eval/call`): one line, a mark only when it threw, its intent as Markdown; opened, its code, then for the person alone how long it ran, what it costs the context and its handle and what came of it, its value by the render its record names (`:seon.eval/schema`, ```seon.render.ui/eval-output```). Seon's own evals and context reads are not drawn: they are the model's alone, an element the page's writer leaves out, and name no model call; the debug tab shows what went on the wire. The end is a card from the agent's end facts (`chat-end`). The task's blocks are beside the chat, in the right column. Counts are tokens (```seon.print/tokens-text```), never characters. Opening a step is the one expand: its result is then whole, with no cut left to open (```seon.render.ui/eval-output```). A person-only page draws its Markdown inline (```seon.render.ui/markdown``` with `{:inline? true}`: code spans, links and `**`/`*` emphasis, from the offsets ```seon.ref/scan``` gives its code and link spans and ```seon.ref/emphasis```); what the model reads keeps its delimiters, since a plan's delimiters pick what it cites. - **Every page says which system it is.** The top bar holds the system's source: the checkout main was last indexed from, the branch checked out there and its commit (root's `:seon.root/source` fact, which an index of the checkout and a landing write), drawn by that value's schema render (```seon.render.ui/source-line```) in the system walk (```seon.render.ui/system-source```) and placed by the frame on every page, as the agents list is (owner via Point, 2026-11-11: "I want that data pulled and rendered with a render function for it"). ### A session's address and the agents list

A session's address is its key (`:seon.agent/key`, the agent's id: a digest of a fresh UUID, seon.lib/unique-id; ```seon.render.ui/session-address```), the one name that survives a root's restart, so every link on a page is a bookmark. ```seon.render.proc/session-of``` resolves whichever name a person holds, the stable one first: the key (which is the agent's id), the task's id, its branch (`/agent/main/task-x`: the newest agent that worked it, so an agent of an earlier boot, ended or not, opens from the store; owner via root, 2026-10-28), else nothing, a 404. ```seon.render.ui/focus-of``` keeps the address a page was asked by for its feed and toggles.

The agents list is the signed-in user's, the same on every page (```seon.render.proc/user-sides```), read from the user's one walk: its page's own list (```seon.render.ui/agents-list```, drawn for an entity holding `:seon.user/name`): root's line, then the agents the user started, each by its entry, each with the ones it started under it, as deep as the user's pull joins them, read forward from each entry's own `:seon.agent/agents` (written from a task's `:seon.task/started-by` when its agent starts: [users](users.md#whats-on-screen)), so the list is the tree of who started what and an entry costs its own children. Root's page lists the same tree, from its session's pull (above); root's session is not listed in either, root's line is its entry.

The head and the list read main, so they say what main judged. The task tile's line (```seon.render.ui/task-view```) is drawn from the agent's branch, which holds no task outcome, so it says how the agent's own end left it, and only when that end is what `standing` answers. So a merged task's head reads "merged" and its panel "done": each is true of what it reads.

An eval's printed output is drawn beside its value, its `:out` and `:err` each cut only with the form that reads the rest.

### How the work stands

A turn decides from what the page's status component kept with its hiccup (```seon.render/kept-of```), one reaction for both, so a status nothing moved costs nothing. How an agent's work on its task stands is one value, ```seon.ctx.status/status```, a fact of its branch at a t (task seon.ctx/the-context-is-the-agents-evals-and-seons, R2b-1; owner, 2026-10-29: "Store information we need and it's presence means something"): each proof, of the task's plan accumulated over its needs (```seon.task/pulled-accumulated```), by its var as the agent's record pulls it, the task's and its needs' `:proved` (```seon.ctx.status/task-of```: the verdict, `:seon.test/status`, its failing assertions as data, `:seon.test/failures`, and its form; [verdicts are a cache](merging.md#verdicts-are-a-cache)), never read again from the db (`seon.render-test/the-status-proofs-are-what-the-record-pulled`); the done rule's reasons (```seon.reconcile/done-explain```) and each as what to do (`:refused`, with the form that does it), and what the branch's work did since its merge base, all from one diff of the branch against `:seon.agent/base-commit` (```seon.merge/content-datoms``` read once, the changes made from it): the functions without a contract, the problems it caused and the sections it made stale (```seon.problems/caused-split```), what its merge carries, and, for a task that merges itself, whether it can merge now; its unmerged entries; a test run that failed as a whole (`:seon.agent/test-error`). It reads facts about the work only, never the conversation (its turns, evals and messages), so a turn's own record does not draw it again; a turn's number and a cut reply are the conversation's. What reads other commits stays the db's: the done rule's scan of every verdict the branch holds (a stray red, a regression), the diff against the merge base, and a red proof's callees. The component that draws it, ```seon.render.ui/status```, answers the hiccup of that data (```seon.render.ui/status-hiccup```), which the page and the model read, and a move of main's content draws it again only for a task that merges itself: the status reads `:seon.agent/main-program`, main at its last move of content (```seon.merge/content-commit```), not main's commit, which root moves at each eval by noting the agent's status. Read from the commit, every eval ran the whole status again for the same output, about 19.6 MB on a branch with nothing done and 57 MB at 75 names (2026-11-06, commit message). Knowing the content did not move costs 1.3M ticks at a turn where main moved, one descent per content attribute. What a merge's readiness answers is a function of that content alone, so the same at either commit. A turn reads the data itself (`seon.turn/status-now`), once a turn; it holds nothing of it. The branch's diff is read once a status. A red test outside the task's proofs needs main's claims (regression or stray red), the reconciler's index: in an agent its own, advanced by what differs (```seon.agent/reconcile-index```), else one built cold (measured on a demo branch: 14.8M ticks, 70 MB), and only then. A test red here is the agent's to clear, whoever caused it (owner, 2026-11-07); when it was red at the merge base too the status says so, as a fact (`:also-red-on-main`). A stray red is offered the form that registers it as a proof only when the branch wrote or changed that test (its source differs from the base's): a live session was told to register a test of main's that its environment failed (```seon.ctx.wire-test/a-red-main-was-red-on-too-is-the-agents-and-is-said```). It reads no turn: for a design task alone it reads the plan its branch began with (its merge base's), so a turn taken never runs it again (`seon.ctx.wire-test/a-new-turn-does-not-run-the-status-again`).

A message delivered after the plan last changed is not repeated here: the model reads it as a user message at its next turn (its history), and the person in the chat.

A request is made again from the records at its turn's commit ([the render is an eval](#the-render-is-an-eval)).

### In-flight output streams

What an effect is still producing (a model's reply, an eval's output) is shown live and written once: the effect sends its text to one Flow channel keyed by the id of an entity already in the db, the web proc appends it to the element the render drew with that id, and the commit of the final value redraws the component, which replaces the element (owner, 2026-11-08: "Can we get a stable ID for the streaming point to append to and then we can just fire message update data to a channel?"). Nothing in flight is held, rebuilt or written; a restart or a point in time draws what the db holds ("The db is the source of truth").
- **The message:** `{:stream id :in e :part p :agent a :text t}`, t the part's whole text so far (owner, 2026-11-08: "the simpler for us option that is always right"), as the vector of its pieces the producer already holds (shared, so a message costs O(1) to make) or a string; then `{:stream id :agent a :end true}`. e is the entity whose in-flight element the render drew (a model call's `:seon.model-call/id`), p the kind of text (reasoning, content, message, intent, code, out, err). Sent to `[:web :streams]` (Flow's dynamic route, no conn), a sliding buffer of `:seon.config.web/streams-buf`, so a producer never waits; a message it drops costs nothing, since the next carries everything. `:agent` is the agent's stable key (`:seon.agent/key`, never root's per-boot id like `:a1`); the part id is unique within e (`<call>/<k>/eval-<i>/code`).
- **An eval's output** is a part of its model call: `<call>/<k>/eval-<i>/out` (`:in` the call's :seon.model-call/id, `:part "out"`; what it writes to *err* is `.../err`, opened by its first write), k and i the eval's place in the reply, its tool call's index and its position in that call's `evals`, which `seon.model/reply-of` puts on each eval as data (`:seon.model/at`). The turn puts call, k and i on each eval's request as data (`:stream`, ```seon.turn/act!```), and *out*, *err* and clojure.test's *test-out* are a writer (```seon.repl/streaming```) that keeps the text for the record, unchanged, and sends each write's piece as `{:op :stream ...}` over the agent's socket (which drops nothing, so a frame stays the size of its write); root's agent proc (```seon.agent-proc/agent-frame```) appends it to the part's whole text so far and puts that on `[:web :streams]`, letting it go at the part's `:end`. One `:end` per opened part when the eval ends, however it ends (its value, its error, an interrupt). Nothing is written to the db for it in flight (owner, 2026-11-08): an eval with no model call (outside, inserted, a person's) sends nothing, and only the REPL's own thread sends, since ```seon.sock/send!``` frames can interleave across OS threads: a write from an eval's future or `a/thread` is recorded and never sent.
- **The web proc** (```seon.web/stream-in```) holds each open part's latest text (memory only, dropped at `:end` or the agent's end: in-flight text may be lost) and, for each tab of that agent's chat whose page has e's element, draws the element whole in its place (```seon.web/container-frame```: ```seon.render.ui/stream-container```, the one render of it, with every open part's text, as one Datastar `replace`, since the element is `data-ignore-morph`). Which elements a page has it learns from each patch and keyframe a tab is given (`data-stream-in`, ```seon.web/drawn```): found live on 7888 (2026-11-08), the model streams as soon as its call is committed and the page draws its element about 2 s later, so a tab gets the text so far the moment the element appears. A tab that cannot take a frame is stale, and its keyframe brings the latest. Cost: one draw of the call's text a message, 770 ticks and 5.9 KB a hundred characters plus 7.9k ticks (```seon.web.html/escape``` is one pass: 54 to 9 ticks a character, for every page); `seon.web-cost-test/a-stream-message-costs-its-text`. Selectors are by attribute, `[id="…"]` (```seon.web/id-sel```), and no element id holds a `.` (```seon.render/key-id```). The feed reconnects whenever its response ends (`retry: 'always'`).
- **The feed is compressed** (```seon.web/feed-encoding```, ```seon.web/deflate-chunks```): each tab's SSE stream is one zlib stream (`Content-Encoding: deflate`), flushed at each event so the browser has it at once, its 32 KB window shared across events, so the text an update repeats costs a back-reference (Datastar's own advice: "Compression ratios of 200:1 are not uncommon when compressing streams using Brotli"). `:seon.config.web/feed-encoding :none` sends it plain, to read a stream when debugging. `seon.web-test/a-feed-is-one-deflate-stream-that-a-browser-reads-as-it-comes`, `seon.web-test/a-lost-message-costs-nothing`, `seon.web-test/a-stream-that-starts-before-its-element-is-drawn-reaches-the-tab-when-it-is`, `seon.web-test/a-tab-opened-mid-stream-gets-the-text-so-far`, `seon.web-test/a-stale-tab-is-caught-up-by-its-keyframe`.
- **The render** (```seon.render.ui/model-call-view```, placed by ```seon.render.ui/conversation-turn```) draws the in-flight element, `aria-busy="true"` with a pulsing cursor after its parts and `data-ignore-morph` (Datastar keeps it as it is through the turn's redraws, so the reply's commit leaves a running eval's intent, code and output in place; measured in the browser), for the page alone, from the model call's commit until its evals have all run (`:seon.model-call/forms`, which seon.turn writes after the last) or it failed (`:seon.model-call/error`), while its agent's process lives; the committed reply and evals draw beside it, and the streamed copy of the reply's own text is hidden once that is drawn (a CSS rule on ```seon.render.ui/stream-part```). That is the in-transit status, read from the db; the redraw at `:forms` drops it. No eval's start is written for it: committing one cost +148k ticks and +478 KB an eval (Context). An eval with no model call (an outside agent's, a person's) has no element, so its output does not stream. `seon.render-test/a-call-in-flight-draws-its-stream-element-until-its-evals-ran`, `seon.render-test/a-call-in-flight-keeps-its-committed-evals`, `seon.web-test/a-stream-draws-its-element-whole-with-the-text-so-far`.

## Components

A component is a call in hiccup, `[f opts & children]` (Reagent's form), of a render whose opts declare what it reads: `:seon.ctx/ctx`, ctx as a tracking view ([reactive renders](#reactive-renders)), or `:seon.db/db`, the branch's db, read under `d/with-reads`. The walk (```seon.render/render!```, ```seon.render/flush!```) fills those keys in, runs the render in its reaction, and draws its output with its root element's id its key (```seon.render/key-id```: its render's name and opts' `:key`, Reagent's, the name of what it shows, else its children's keys: never a raw entity id, since the model reads ids and does not guess them). One cache holds each component's reaction, args, output and db reads, in the process whose page it is (the agent's walk, held in its state). A component runs again when its children are not `=` to last time's, when a change of ctx reaches a path it read, or when a transaction's datoms touch its db reads; otherwise it is skipped, and a run whose output is `=` to the last one's changes nothing. A component is held by the parents that draw it: a rerun that no longer draws a child stops holding it, and at the end of the flush a child no parent holds goes, with what it alone held (```seon.render/unmount!```). Not before: a flush draws in mount order, so a child moved to a parent drawn earlier was drawn there before its old parent let go, and going at once lost it; one the root no longer reaches is not run on its way out (`seon.render-test/a-child-moved-between-parents-stays`). The datoms are matched once, by their keys, against the walk's index from a read key to the components that read it (```seon.render/flush!```; ```seon.render/render!``` matches none again), so a transaction costs its datoms and the components it reached, never each datom against each component. A call drawn before whose component nothing queued is its marker and nothing more: the walk keeps the marker of each plain form it drew (```seon.render/emit```), so a list of a thousand members costs a lookup for each one that did not move. A flush (Reagent's batching flush) draws the components a change queued in mount order, parents first, after the ratom flush: one a commit, and the agent's page walk once a turn, given every datom its db moved by since it last drew (`seon.ctx/take-moved!`, ctx's own diff of each move). Each component's runs are counted by its render's var (```seon.render/ledger```: ran with a new output, ran with the same, skipped, and the bytes its runs allocated). A call of a render that declares neither is not a component: it stays a call in the hiccup, the page's writer expands it and the model reads it as the call. A component whose render throws draws its error's render in its place, a `:seon.render/component-defect` (a [failure point](failure-points.md)); every other component draws. `seon.render-test/a-component-re-runs-on-what-it-read`; `seon.ctx.wire-test/a-db-component-runs-again-on-what-it-read`, `a-cited-var-redefined-shows-in-the-next-view`, `the-task-draws-what-it-needs`; cost `seon.render-cost-test/a-change-costs-its-components`: a change draws its components, flat in the page (137 contracted calls, about 100 KB from 100 to 4,000 evals), beside ctx's diff, which walks every key of the collection it changed. A kept walk moved to a later value of its branch draws a turn's component and the lookups of the turns before it, whose count it grows by: a step and back costs 1,057 contracted calls at 10 turns, 1,177 at 40 and 1,657 at 160, and 10.7, 12.5 and 20.7 MB (`seon.render-cost-test/a-step-costs-what-changed`; one step on the same input before the read index and the turn's component: 11,073 calls and 80.9 MB at 640 turns), and the walk moved any way (forward, back, across turns) draws what a cold draw at that value draws (`seon.render-test/a-kept-walk-steps-any-way`); a record of another turn is read by no other turn's component (`seon.render-test/a-record-of-another-turn-reads-nothing-this-turn-read`).

### What a render is handed

A render is `(f opts node)`: opts, then the pulled node. Everything else it reads is a key of opts, and a helper it calls takes what it needs from those as arguments.

| key of opts | what it holds | given |
|---|---|---|
| `:seon.render/index` | the entity index: what every schema lookup takes as `ix` (```seon.render/schema-property```, ```seon.render/entity-pattern```, ```seon.render/entity-schema```) | always, by the walk (```seon.render/render!```) |
| `:seon.ctx/ctx` | the whole pull, as a tracking view | only when the render's contract names it in its opts map |
| `:seon.db/db` | the branch's db, read under `d/with-reads` | only when its contract names it |
| `:seon.render/drawn` | the renders this walk has drawn, each var with its function: not what they drew | only when its contract names it |
| `:seon.render/nested` | true where a parent placed this entity; absent at the page's top | by the walk |
| `:key` | the name of what it shows, its element's id | by whoever placed it |

A contract names a key as `[:and :seon.render/opts [:map [:seon.ctx/ctx :any]]]` in place of opts' `:map` (```seon.render/inputs``` reads it). Another render's output is never handed to a render: a render reading what others drew would depend on the order they are drawn in, and two reading each other would never end; what a whole walk drew is `(my.render/tree)` after it, and the page at a point is `(my.render/page p)`. An agent reads this beside its own render, as `:seon.render/hiccup`'s description, which its pull view draws at that clause (```seon.render.ui/pull-clause```). At a REPL the index is `(seon.agent/branch-index)`, so a render is tried on one node as `(f {:seon.render/index (seon.agent/branch-index)} node)`.

### A component answers hiccup

A component answers hiccup and nothing else, the one state, with the meaning in it: it reads ctx and the db and transforms them, filtering and adding what it needs from the db, and what it answers is what the page draws and what the model reads ([a part prints as its render](#a-part-prints-as-its-render)), so there is no second function per component to drift from it (owner, 2026-11-06: "I don't want to go back to dual renders for everything"). Data a reader decides from is a function of the facts, read by that reader: the turn reads ```seon.ctx.status/status``` itself, and the page's ```seon.render.ui/status``` draws the same function's data. A value's schema may still declare a model render (`{:seon.render/model sym}`, ```seon.render/model```), for a value an eval answers, which is printed ([a render is a value](#a-render-is-a-value-printed-once)); a component has none.

A component whose render answers nothing (nil: ```seon.render.ui/own-problems``` with no problem open) draws nothing: no element holds it and no part is placed for it, so the page shows none and the model is sent none (```seon.render/placed```; task seon.render/an-empty-part-draws-nothing). When it draws again, its part is placed in the layout's order like a new one.

A component that throws draws its error in its place: first its line as text, the render, what was thrown and the fn it was thrown in (```seon.error/thrown-in```, the reading an eval's error uses too: `seon.render-test/a-components-defect-says-what-threw-and-where-in-a-line`), then a call of the error's render on the error as data (`:seon.render/component-defect`: the render that threw, its message, and the thrown error's own data under `:seon.render/threw`, a contract's problems among them), which the page's writer expands and the model reads as the call, the map in it, every other part drawn beside it (```seon.render/render!```; owner, 2026-10-29: "it's okay if some are errors just make sure it's visible to the agent"). An agent that breaks code its own page runs (the parser, a render) reads what broke where its part was.

The agent's page parts (```seon.render.ui/agent-parts```: all of its page but its conversation, a render of the agent's pull whose `:seon.ctx/pattern`, metadata on its var, is what it reads, so a past point's parts are pulled by that and compared in a turn's diff), each one hiccup, the same for the page and the model:
- **The task** (```seon.render.ui/task-view```, hiccup like every part, the same render wherever a pull joins a task): its kind, namespace and how its work stands, its name as the title, how its kind is worked (its instructions, folded), its plan accumulated over its joined needs (```seon.task/pulled-accumulated```) as Markdown, and the line naming its id; then what it joins (its cites, its search, its needs), each by its own render inside it. No map keys; which proofs are written is the status's.
- **The agent's turn** (```seon.render.ui/turn```): its heading is all the model is sent of it, `You're in seon.program.`, the namespace the REPL is in (```seon.ctx/current-ns```, a fact of the branch: ```seon.repl/record-tx``` writes `:seon.agent/ns` only when it moved). Each eval's answer carries the same `:ns`. It is an ordinary component, placed with the others at the end of the task's list, so the line is sent again when the namespace moves. The turn number is `:seon.agent/turn` ([turn](turn.md#the-turn-is-a-number)); a turn cap stops a run and is not announced. ```seon.render.ui/agent-state``` is the person's alone (`:wire/for "page"`): how its work stands (```seon.render.ui/standing```), its task, the form it runs, its proofs green, the tokens its requests sent and the time they took; the model is sent none of it. A move into a namespace whose own var hides a REPL helper answers `:helper-shadowed` (```seon.repl/shadowed```).
- **Everything the task, its needs and the agent cite** (```seon.render.ui/citations```, one section headed "What your task points to", each thing a ```seon.render.ui/cited``` part of its own, drawn by ```seon.render.ui/cite-hiccup``` by what it is): a function at `:doc` or `:code` depth as its whole source in a fence (its docstring and contract are inside it), the tests that reach it and the functions that call it a few names each, and one real call taken from a test or caller as written (```seon.render.ui/call-in```); at `:summary` its arglists and the first line of its doc; a wiki section as its heading and address, its text at its depth and how to read the rest; a schema key or setting as its form and `:description`, and for an attribute the db holds what kind of entity holds it, that entity's other attributes and one real value (for a ref, the entity it refers to and what that holds: two index reads); a namespace as its doc and how to read it. Not on the part: how it was fetched (`:cites :depth :symbol :read`), how to change it (taught once), part ids.
- **A proof's failures** (```seon.ctx.status/failures```): failing assertions that got the same value with the same message are one entry, `{:asserts [...] :got v}`, so nine assertions that threw one error are read once.

Each view renders on its own (```seon.render.proc/view-pass```, a [failure point](failure-points.md)): a view whose render throws is that error as its page, a `:seon.render/view-defect`, and every other view of the pass renders (`seon.render-test/a-view-that-throws-answers-its-page-with-the-error`).

### An entity may name its own render

What draws an entity's page is the render its schema names (`:seon.render/hiccup`), unless the entity names one of its own: `:seon.render/hiccup` is an attribute too, as `:seon.ctx/pattern` is both a schema's pattern and an entity's own (```seon.render/render-var-of``` reads the entity's first, when this process has that var, then its schema's). So one agent's page can be presented differently from another's over the same pull, with no kind and no second walk: an agent sets its own by an eval, `(swap! ctx assoc :seon.render/hiccup 'its.ns/its-render)`, its render defined on its branch like any, the one writer of that fact; a nested entity is drawn by its schema's render always (an entity's own is its page's alone, ```seon.render/entity-render```); a kept walk whose entity changed its render is walked again from the new root over the same ctx (```seon.render.proc/advance-walk!```). The example is the stage (```seon.render.ui/stage```), which root's session is made with at boot: the same lists as `agent`, so the model reads exactly what it reads there, and in front of them, for the person, ```seon.render.ui/stage-front```: a welcome when nothing has been said (and what it holds), else the last ask and its answer in large type, the values that turn made drawn inline by their schemas' renders, the earlier exchanges folded, and a fold that shows the same page as the conversation instead: the person's view, kept by the page as any fold's (`data-preserve-attr`), never a write of the agent's render. A part an entity's own render places is read by the model as every part is, unless its own call is marked `:wire/for "page"` (```seon.render/page-lists```): the stage marks its front so, a layout for a person; the pull view does not, so an agent that puts it on itself reads its own pull in its request. A second example is the pull view (```seon.render.ui/pull-view```, ```seon.render.ui/pull-front```): an entity shown as its data model, where its pattern comes from (its own or its schema's), each clause with what the pull holds for it (a value, a join's members and how many of them answer each clause of the join's own pattern, the transaction a datom was written in when the pull holds it), and the attributes its schema names that the pattern does not ask, from the pull and the entity index alone (`seon.render-test/an-entity-shown-as-its-data-model`). That reading has one producer, ```seon.render/pulled```, a plain map: the pull view lays it out and computes nothing, and an agent reads the same map at its REPL (`(my.db/pulled @ctx)`, [looking at what you pulled](agent.md#looking-at-what-you-pulled)), so a sub-pattern given by a schema's name is shown as the pattern it stands for (`seon.render-test/an-entity-as-its-data-model-has-one-producer`); an agent puts it on itself with `(swap! ctx assoc :seon.render/hiccup 'seon.render.ui/pull-view)`. The render's output is the page, so a layout makes its regions itself: the stage and the pull view put their front at the top of the agent's chat column (```seon.render.ui/agent-page```, which `agent`, `stage` and `pull-view` share), and a render that places a list in an element of its own gets that list's members there (`seon.render-test/a-render-places-its-own-regions`); the frame keeps only the top bar, the agents list and the input ([a layout places its lists](#a-layout-places-its-lists)).

### The hiccup is checked

A render's output is the intermediate both readers take, the page's html and the model's page, so what it may hold is a schema: an element's attributes are ``:seon.render/hiccup-attrs`` (unqualified keys with plain values, a `:key` the identity value of what it shows; never `:class` or `:style`, whose look is CSS keyed on the render's name, never a mark for one reader, `:wire/*`, never an entity map: a value with a render is a call of that render). ```seon.render/misfits``` counts what one output holds against it, by kind, through its own elements and never a child's (a child is a marker); ```seon.render/misfits-by-render``` sums a walk's by render. Nothing is refused yet: the pages the test world draws hold each render's count, pinned so it only goes down (`seon.render-test/every-render-fits-the-hiccup`, 16 renders on 2026-11-11, the walk's own class on each component's root among them), and each later change moves one render's look to CSS. The check costs one output's elements (`seon.render-cost-test/the-hiccup-check-costs-the-components-own-output`: about 4 contracted calls and 3 KB an element), so it will run in the walk for the one component that just ran, never over the page. The plan, by step: task ``seon.render/the-hiccup-is-a-schema-checked-intermediate``.

### A part prints as its render

The model reads each part as the hiccup its render returned, headed by the function that drew it and the ctx path it read: ``[seon.render.ui/status {:ctx [:seon.agent/task :proved]} [:h2 "Where your work stands"] ...]`` (```seon.render/part-form``` from the walk's own cache entry, printed by ```seon.render/part-text```). The head is the cache entry's `:f`, so it names the function that drew the part; `:ctx` is the `:at` its layout gave the component, a real path of the agent's `@ctx` (`(get-in @ctx path)` answers the data it read; an entity id in the path is fine). A child component is a part of its own, nested; presentation (class, style) is the page's and is not printed, and an id names an element, so it is, and so is a `:key`, Reagent's, which names a child ([a change is edits by name](#a-change-is-edits-by-name)) and which the page's writer leaves out; an element or a component call for the page alone carries `:wire/for "page"` and is left out (a walk only the model reads does not draw it: ```seon.render/draw```'s `:model-only`, until ```seon.render/draw-all```), and an element for the model alone carries `:wire/for "model"`, which the page's writer leaves out. A walk read once and let go (`:once`, a request drawn cold) makes no reaction and reads ctx as plain data. Source is a verbatim block, `[:pre [:code src]]` in the hiccup, printed in a Markdown fence longer than any run of backticks inside it (```seon.render/fence```), never escaped; a string with a line break or a quote is text, printed as written. The page writes a symbol head by resolving it (```seon.web.html/html```): one expansion, not a second render path. A test reads that a real page's heads name functions and its paths answer data (`seon.render-test/a-parts-head-is-the-function-that-drew-it-and-its-path-is-real`); nothing refuses a part.

### The agent's turn

The turn line is the heading of ```seon.render.ui/turn``` (see the parts that answer data, above): a part like any other, placed at the end of the task's list, sent when it changed ([a change is edits by name](#a-change-is-edits-by-name)).

### Cost is shown one way

Wherever work is shown it is one line from one function, ```seon.print/cost-text``` (```seon.print.emit/cost-text```): `5.2 ms · 873k ticks · 4.1 MB · ~1.2k tok`, time, ticks, bytes allocated and what the result costs the context in tokens (the one sizer). An eval's text carries it as its last entry, `:cost "..."` (```seon.print/response-text```), `"not run"` when the eval recorded none, and the line counts inside the printer's budget; the numbers stay data (`:ms :ticks :bytes` on the record, readable under the handle). The page's eval row, a proof's row in the status, a part's head (`:tok`, the model's own reading of it) and the tree (`:tokens`) use the same wording and the same sizer. Every origin goes through `seon.repl/eval-string`, so a model's call, an inserted, an outside agent's, the page's and the context's eval carry a cost, and a form that threw cost what it did before it threw (`seon.repl-test/every-eval-carries-its-cost-whatever-asked-it-and-whether-it-threw`).

### A search is a part

A search is data a context holds, a `:seon.search/search-fact` (its query, and `:seon.search/k` when it asks other than `:seon.config.render/search`) of a task or an agent, joined by their patterns beside their cites, so `@ctx` holds it and an agent changes or adds one with `swap!` as any member ([ctx](ctx.md)). Its component, ```seon.render.ui/searched```, reads the db and answers one compact hiccup, which the page shows and the model is sent as it is (owner, 2026-11-01: one render that the person and the model both see, not a data render beside the page's): its query searched by `seon.ctx.search/search` (words, meaning and the names it holds), a line a hit (a function's name, a section's address, a schema key), drawn only once the vector pipeline has embedded its query (owner, 2026-11-08: words alone matched as weakly when nothing was to be found, 0.29-0.36 relevance, as when something was; a search cost 10-17M ticks and 37-57 MB, about 70% of a page drawn cold), and with no line for the hits left out, whose count moved each turn and resent it (`my.agent/search` answers them). A request's own search names it in its heading rather than repeating the plan the task part shows. A changed query redraws that part alone (`seon.ctx-test/a-search-is-a-member-a-swap-adds-and-changes`). What it was measured to find: [vector](vector.md#what-the-work-is-likely-to-need-as-an-eval).

## One rendering system, drawn from the data

There is one rendering system, and the data describes the page (owner, 2026-10-26: "There is only one context rendering system and it needs to be built from the parts"): an agent's record is a name chain, an agent has a conversation of turns, each turn holds the agent's message and its evals, each eval has a response ([vocabulary](vocabulary.md)), and the page and the model's request are both renders of that record through ctx, whose [pull pattern](ctx.md#the-pattern) (`:seon.ctx/pattern`, data an agent edits by `swap!`) says which of it is drawn. Nothing about a page is stored beside the data it shows, and no render queries the db for what the pattern can join (owner, 2026-10-30: "Please stop building parallel systems ... No special treatment"): what a text cites is entities its write made, joined by the pull and drawn by their schema's renders ([an entity cites](references.md#an-entity-cites)); what exists only when rendered, such as the sections an embedding search relates, is a render that declares `:seon.db/db`, and the db ranges it read are what invalidate it. The model reads the same render: the page's parts beside the records, in each request ([the model's context](#the-models-context-a-cached-prefix-then-the-turn)).

It is re-frame's model, which is Reagent's, which is React's memo, proven in production Clojure: one immutable value (`@ctx`) is the app-db, a transaction patches it, and a component is a pure function of its slice, run again only when its slice changed and passing nothing on when its output is `=` to before. Immutability makes "did my input change" a pointer check (`identical?` 1 µs; `=` on 1 MB 0.2 ms), so nothing is guessed and no render knows the data's shape. A render is a function and the data it renders, never a registered object: to make one cheaper, hand it a smaller slice, with nothing to invalidate by hand. The one addition is that the source is a database, not an atom, hence `d/with-reads` for renders that query. Measured on a live agent, a new eval rebuilt 2 entities in 0.23 ms and reused 19 of 22 render calls by identity, against 102 entities and 0 of 191 for a fresh build (28-35 ms); a patch's cost grows with the transaction, not with ctx.

One pass over the pull renders every output asked of it ([users](users.md#the-stages-agreed-2026-11-09), stage 2a). A walk holds the set of outputs it renders, `:outputs`, data on the walk: the page's hiccup alone by default, and the model's messages too when it holds `:seon.render/openai-compat`. An entity's schema names a render for each output as a property (```seon.render/render-for```); in one component run its hiccup render runs, then, when asked, its model render, `(f {:seon.db/db db :seon.render/index ix} entity)`, whose answer is messages and the entities and `[f opts & args]` calls it places, each run as a component of its own (the one its hiccup placed is a cache hit). A bridge until stage 2b's root swap: the walk's root called with no entity (a layout, `[f {}]`) takes the walk's source, the pull it walks, as its entity, so an agent's walk answers the agent's own model render; 2b with 2a's step 7c roots the agent's walk on its render (`[#'seon.render.ui/agent {} view]`) and deletes this case and its test. A pulled entity placed in hiccup is rendered the same way, by its schema's render as its own component (```seon.render/entity-render```). Each answer is kept on the component under its output's name, so no output but hiccup is named in the walk, and an output's answer is read by ```seon.render/answer-of```. The request is the root's model output with each placed component's in its place (```seon.render/openai-compat```), as ```seon.render/resolved``` places hiccup, so the order is each render's. A past point is read by ```seon.render/render-pull```: a pull rendered in one pass and let go, keeping no walk. A walk asked for the page alone runs no model render and pays nothing for it. An entity is recognized as the write check reads it: of the schemas owning the attributes it holds, the best match, inherited attributes counted, a tie an error value (```seon.db/most-specific```).

## Reactive renders

Your page and your model's context are renders of `@ctx`, and a render runs again only when a path it read changes: read the narrowest path you need, and give each member of a list its own component, so a change redraws what it reached and nothing else. Your page is one walk of your record; what moved of it between two points is what `(my.render/diff p0 p1)` answers ([the render is an eval](#the-render-is-an-eval)). A rerun indexes only the reads it gained or lost (```seon.ratom/index-reads!``` from the reaction's `-update-watching`): one that read what it read before, a layout over every member rerun by one change, indexes nothing again (`seon.ratom-test/a-rerun-indexes-only-the-reads-it-gained-or-lost`; one eval added to a kept page at 100 evals: 37.7 MB to 13.0 MB). Its own body still reads every member it lists, so a layout that lists the session reruns at O(members): give each list its own component.

**A render is an input of what it draws, as the data is** (owner, 2026-11-04: "when data changes OR THE FUNCTION THAT RENDERS IT changes then you re-render"). A move of a definition (`:var/form`) queues each component whose render reaches it through `:form/refs` (`seon.render/queue-moved-renders!`, `seon.render-test/a-render-that-changes-draws-again`). It watches nothing and costs nothing until a definition moves. Measured on the real program: about 2 MB for a render reaching 2-4 vars; `seon.contract/error` reaches 1,659 vars at 52 MB, `seon.config/value` 3,530 at 122 MB, and `seon.print/text` 3,441 at 559 MB, the first of the run, so that one includes reading the index in.

**Writing one.** A render is a function `[opts & args]` answering hiccup; it is a component when its opts contract names `:seon.ctx/ctx` (it reads ctx) or `:seon.db/db` (it queries the branch's db), and the walk fills those keys in. A call `[#'f {} arg]` in a render's hiccup draws f there as a component of its own, keyed by f and its args (its root element's id is that key, `seon.render/key-id`, whatever id you gave it):

```clojure
(defn eval-code "An eval's code." {:malli/schema [:=> [:cat [:map [:seon.ctx/ctx :map]] :int] :any]}
  [{c :seon.ctx/ctx} id] [:li (get-in c [:seon.eval/_agent id :seon.eval/code])])
(defn page "The plan, then the code of each eval." {:malli/schema [:=> [:cat [:map [:seon.ctx/ctx :map]]] :any]}
  [{c :seon.ctx/ctx}] [:div [:p (get-in c [:seon.agent/task :seon.task/plan])] (into [:ol] (for [id (keys (:seon.eval/_agent c))] [#'eval-code {} id]))])
```

A flush (`seon.render/flush!`) answers each component it ran, `:miss` when its output is new and `:same` when it ran and answered what it did before (which passes nothing on: its parent and the page are untouched); a component it skipped is not named. A path that names nothing reads `nil` and draws it, with no error: check a render's output once. A render that throws draws its error in its place, a `:seon.render/component-defect` naming the render and the message, and every other component draws. To change your own page, register your render as the layout or one of its parts ([ctx](ctx.md#the-agents-entity-holds-its-work), [adding a datum and its render](ctx.md#adding-a-datum-and-its-render)). `seon.render-test/a-flush-answers-what-it-redrew`.

**Your page, changed at your REPL.** Your page is one walk of your record (`seon.repl/page-walk`), whose parts at two points of your branch are what `(my.render/diff p0 p1)` compares. Two levers move it, and the next turn shows the change:

```clojure
;; a part's render, read and redefined: the walk watches every render it drew, so its parts redraw
(clojure.repl/source seon.render.ui/own-problems)
(in-ns 'seon.render.ui)
(defn own-problems "…" {:malli/schema [:=> [:cat [:and :seon.render/opts [:map [:seon.db/db :seon.host/db]]] :int] :any]}
  [{db :seon.db/db} _aid] [:section [:h2 "problems"] [:p "what I want here"]])
(in-ns 'agent.a1)
;; what your plan cites, changed through ctx: the write derives what the new text cites (seon.agent/transact!),
;; so the cited part appears in the same turn
(swap! ctx update-in [:seon.agent/task :seon.task/plan] str " See `seon.print/text`.")
```

Each part is headed by the name of the render that drew it (``seon.render.ui/cited``, ``seon.render.ui/status``), so a line you see leads to the function you redefine. `seon.render-test/a-redefined-render-redraws`, `seon.ctx-test/the-page-reads-every-write-since-it-was-drawn`.

**What a read costs**, measured in that test and in `seon.ratom-test/inferred-paths`: a render runs again when a change reaches what it read.
- `(get-in c [:seon.agent/task :seon.task/plan])`, `(:k m)`: that value changed, or something above it was replaced.
- `(contains? m :k)`, `(get m :k nf)`: the same as reading the value; a key's presence is not cheaper.
- `(count m)`, `(keys m)`, `(seq m)` of a collection: a member added, removed or replaced, never a change inside a member.
- `(for [[id e] evals] (:seon.eval/code e))`: any member's attribute; the same list with `[#'eval-code {} id]` runs only the `eval-code` whose eval changed.
- `seon.ratom/unwrap`, `seon.ratom/realize`, printing a value: anything below it.
- A component call whose arguments hold a view (`[#'agent-parts {} c]`) is never looked up among the forms drawn before (```seon.render/emit``` asks only of plain arguments): the lookup hashes the form, and a view's hash reads all of its value in the parent's reaction, so a layout ran again at any change of its ctx (found 2026-11-11 when the agent's layout placed its task's list after its conversation).
- A first draw, as any flush, ends with nothing queued (```seon.render/flush!```): a component drawn before a later one changed what it read (the rules, before the renders drawn after them) is drawn again in the same flush, not left for the next.

ctx's diff (`seon.ctx/changes`) is by entity: a map holding `:db/id` is diffed key by key, and any other map is one value, replaced whole, so everything that read inside it runs again. `@ctx` is entities throughout; an atom you build by hand needs `:db/id` on its maps to be read as one. A db render (`:seon.db/db`) is run under `d/with-reads` and runs again when a transaction's datoms touch the ranges it read: pass those datoms to `flush!` (`seon.ctx.wire-test/a-db-component-runs-again-on-what-it-read`).

**How it works.** ```seon.ratom``` is reagent.ratom ported (`RAtom`, `Reaction`, `run-in-reaction`, `flush!`, `dispose!`; Reagent's own tests, `seon.ratom-test`), with the cursor inferred (owner, 2026-10-26: "I'd rather infer the cursor than require it"). A render declaring `:seon.ctx/ctx` gets a tracking view of ctx: a map that delegates to the real value and records each path it looks up, a map's presence (shallow, reached by a change at or above its path), a value read whole (deep, reached by a change at, above or below it), or a node iterated (its key set and direct values), as Vue 3's reactive proxy and MobX's observable map do. The printer and the page's writer take the real value (`seon.ratom/unwrap`, `seon.ratom/realize`), each such read whole. A source read through views has one watch: its reset! (ctx's patch) runs its diff once (`seon.ctx/changes`) and reaches only the reactions whose read paths a changed path reaches, by index (`seon.ratom/source-changed`). Reagent's scheduler (requestAnimationFrame) is the commit on the server: the queued reactions run at a non-reactive deref and at each flush of the walk (`seon.render/flush!`). `seon.ratom-test/inferred-paths`, `a-view-is-a-map`.

The frame is the one part with no value behind it: the document (`seon.web/page-doc`), its head and scripts (`seon.render.ui/shell`). It is fixed hiccup, the same on every page, served once with the page. Its script is Datastar's bundle, `resources/public/datastar.js`, a copy of `bundles/datastar.js` at the pin of `reference-code/datastar` (v1.0.4, 2026-11-08, from 1.0.0-RC.7): an upgrade moves the pin and copies the file, its git blob checked against the tag's, and the page is checked in a browser.

### What draws what

`seon.render/tree` reads a walk's cache as data, from its root: each component `{:render :args :id :tokens :reads? :children}`, `:tokens` the one sizer's over the entry's own output (its children stand there as markers, so a parent is not charged for them), `:reads?` present only for a component that read the db. It prints nothing, so it chains: `(->> (my.render/tree) :children (sort-by :tokens) last)`. An agent's own is `my.render/tree`, over its live walk, brought up to date by the same flush a request makes (the lists drawn so far: the model's, and every other once a person's page has asked); root's draw of a branch (`seon.render/draw`, the page root builds for an ended agent) answers alike, checked on a real agent's branch (144 components).

## Tailwind

The page is laid out by Tailwind's classes in each render's hiccup, responsive at every width, with no hand-written stylesheet beyond the plain CSS rules a render may state itself ([Style](#style)) (owner, 2026-10-23: "I want responsive html and css so why not tailwind?"). `resources/public/css/input.css` holds every directive, token and source glob (Tailwind v4, CSS-first, no config file): `source(none)` with an explicit `@source` over `src/**/*.clj` (automatic detection walked the reference-code tree: v1 measured 42 s against 1 s), the Phosphor theme's tokens (dark, light when the system asks), a base layer for semantic hiccup and the one printer's classes, and a safelist of the utilities an agent may use, since a render an agent defines at its REPL is in no scanned file: the common layout, spacing, type, list, border and theme-color utilities, responsive where layout is (117 KB, 16 KB gzipped; a rebuild on each agent render's classes was the alternative, priced and not taken). `bin/build css` (a step of `bin/build seon`, and so of the `:build` effect after merges) runs Tailwind's standalone binary, pinned by version and checksum and fetched once into `target/tailwind/`, into `target/css/app.css` (`:seon.config.web/stylesheet`, served at `/app.css` and read per request); its stamp is the digest of `input.css` and the scanned sources, so unchanged inputs regenerate nothing (68 ms when they changed, v1's port of its `bin/css`). Add a class to a render, or a token or safelist entry to `input.css`, and build: the stylesheet regenerates.

### Where things go

A page is a bar over columns: the agents on the left (the frame's, `seon.render.ui/page-chrome`), then the page's render's own columns, an agent's large chat in the middle and what its model reads, and on root's page the system's tiles, in blocks on the right (`seon.render.ui/agent-page`); the right column is shown only when it holds a part (an agent's `@ctx` and debug tabs have two columns, with nothing beside the record), each column scrolling on its own on a wide screen. `resources/public/css/input.css` styles them by name, so the hiccup says where a thing goes rather than how it looks: the frame's classes `seon-page`, `seon-bar` and `seon-columns`, and the layout's element ids `#p-agents`, `#c-side`, `#p-chat`, `#c-rows`, `#p-context`, `#p-task` and `#p-tiles` (a layout writes no class: [the hiccup is checked](#the-hiccup-is-checked)); the page (`#p-page`) and its render's own element are no box, so each column is the grid's. Each child of `#p-task` and `#p-tiles` is a block, headed by what it is; its `:data-render`, which only the page's html carries (`seon.render/styled`), names the render that drew it for whoever inspects the page. On a narrow screen the columns stack and the page scrolls. The common styling is named there too: `seon-note`, `seon-stack`, `seon-stack-2`, `seon-row`, and `muted`, `kicker` and `box` in its components layer. A render's styling is read from its source, with ``source`` at the REPL, and a name in `input.css` reads from there.

### Style

A component's root element carries its render's name as its first class, then any classes the render wrote on its root (owner, 2026-11-08: the home page's messages touched, since a root's own classes, its layout, were replaced; the model reads no class at all), and its render's var states its style, plain CSS rules for the renders of the agent's and root's pages (a look several share stated once, on one of them) and an element inside it Tailwind's classes; what the model reads holds the name only (owner, 2026-10-26: "make it so the fully printed hiccup is compact and everything earns it's spot"; DECISIONS, compact hiccup). The walk gives each component's root its key as id and its render's name as class (``seon.render/render!``), in place of any class the render gave its root. A render states its style as `:seon.render/style` on its var, literal text in `src/` (so the `@source` scan above builds it), its descendants by Tailwind's arbitrary variants (`[&>h2]:uppercase`); render-ctx's components share a panel's and a tile's (``seon.render.ui/task``, ``seon.render.ui/process-tile``). When a unit's html is written, ``seon.render/styled`` appends each drawn render's style to its root's class: the style of every render on the page, gathered by reference from the renders the walk drew, never spelled in the tree. Semantic classes a render uses inside (`seon-text`, `muted`, `err`, the printer's own) stay, styled once in `input.css`. On a4's first page (15 components) the class text fell 355 -> 194 chars, 9,171 -> 9,094 tokens (`seon.ctx-test/a-component-is-styled-by-its-renders-name`).

The walk keeps the classes a render writes on its root, after its name, and adds its render's `:seon.render/style` when its html is written (```seon.render/styled```); none of them reaches the model, which reads no class (`seon.render-test/a-components-root-keeps-its-classes`), and no `:data-*` or `:aria-*` attribute either, what the page's script and a screen reader read; a link's `:href`, a `:title` and an image's `:alt` stay (```seon.ctx.wire/presentation-free```; `seon.ctx.wire-test/the-models-page-holds-no-attribute-of-the-pages-alone`). The model reads the same hiccup the page draws, so a plan's text stays verbatim, backticks included (parsing inline code spans turned the context's tests red; only fenced blocks are detected, by their marks).

A render's style may be CSS rules in place of Tailwind classes: plain CSS on its var's metadata (`:seon.render/style`), scoped by its render's name and using the theme's colours, `.task > h2 { color: var(--color-text-400); }` (`seon.render/css?`). It needs no build, so it lives where the render does, and an agent works with it at its REPL as with any definition (docs/prompt.md says how): each part of its page is headed by its render's name, `(:seon.render/style (meta #'seon.render.ui/task))` reads that render's rules, `source` shows them beside what they style, and `edit!` changes them on its branch, recorded as the definition and merged and written back with it. ```seon.render.ui/page-rules``` is a component of the walk, which derefs the walk's ratom of the renders it has drawn (`:seon.render/drawn`, a var to its definition, updated when one is first drawn or redefined) and answers the rules of every render in their namespaces, one style element a render keyed by its name (```seon.render/rules```), in a list of its own (```seon.render.ui/rules-list```) so a change of a rule draws nothing else. It is for the page alone: the model's request holds no CSS (owner, 2026-11-08: "ONly the RELEVANT CSS is supposed to be pulled in. Ugh I guess if we don't have agents actively working on the CSS we can leave it out if that's easier"; it had been about 400 tokens of a 1,900-token first page on a small task, for every agent). The relevant rules in the request, those of the renders an agent's work changes, are the shape to build when agents work on CSS; until then an agent reads them where they live. What moves the page's rules is a rule edited, never a render's first draw (`seon.ctx-test/the-rules-move-only-when-a-rule-does`). Renders move to rules one at a time; `seon.render/styled` leaves a render with rules alone.

An agent reads and changes a style at its REPL as any definition: `(:seon.render/style (meta #'seon.render.ui/task-view))` reads it, `(source seon.render.ui/task-view)` shows it beside what it styles, and `(seon.repl/edit! 'seon.render.ui/task-view "padding: 0.5rem" "padding: 1rem")` changes it on its branch. Which renders style something: `(for [[s v] (ns-publics 'seon.render.ui) :let [css (:seon.render/style (meta v))] :when (and css (clojure.string/includes? css "chat"))] s)`. No style reaches the model's request.

## A value draws itself

An eval in the chat is one line, its intent; its value appears when the person opens it (```seon.render.ui/eval-output```, through the one render, `seon.render/hiccup`), html only (owner, 2026-11-10: "If the user expands the UI > for the evals then yeah render it inline too"). A value that has a render is also a tile of the agent's page parts (```seon.render.ui/eval-tile```), which the person sees and the model reads expanded: "the rendered tile is the only version of the rendered value that is seen by the model"; the eval's tool result keeps the real value as data. It takes the render it has, else the value printer, with the printer's budget and cuts. A value has a render three ways: it holds hiccup under `:seon.render/hiccup` (an SVG chart, an `<img>`), it names a render function there, or its record names a schema that declares one, so a render an agent has just defined draws its next value; one this process doesn't hold falls to the printer, so root's first draw of a live agent's page shows it as data until the agent's own draw replaces it. Closed, an error shows its message; opening a step adds its code, its time and its output, and makes its value whole, never drawing it twice. The component answers only hiccup, so a render that needs to run its own code is a later step, which has to keep that code away from the page's calls.

## Tiles are data; the context reads the page's derivations

Each fact the page and root's context both show has one producer they share:
- **A lifecycle is declared once, on its enum's schema,** and read through one reader, `seon.contract/properties` (an enum's members, in order: `seon.contract/enum-values`):
  - `:seon.agent/status` carries its live, stopped and gone sets (`seon.root/gone-statuses`, read by root, the web, the server and the check harness; `seon.render.ui/live`);
  - `:seon.task/outcome` its finished, judged and failed sets, read once, by `seon.task` (`seon.task/finished`, `judged`, `failed`; with `seon.task/done?`, a task's done on a db, and `seon.task/running`, the running tasks by one index seek), which the reconciler, problems, the render UI and the server require (`seon.main-test/a-tasks-outcomes-are-read-once`);
  - `:seon.task/state` a task's observed states with each state's meaning (its `:seon.status/title`, read with `seon.contract/properties`). A task's state is derived once, from the reconciler's index (`seon.reconcile/task-state`), which every reader of a task's state calls.

  A new status is one enum entry. Not this: a status set typed out at each site that asks.
- **How an agent is:** `seon.render.ui/shown-status` and `seon.render.ui/ended-as`; its newest events are the stream's own words (`seon.render.ui/event-detail`); a cost verdict's lines are `seon.cost/verdict-lines`. The writer, the fork server and main are root's process (```seon.render.proc/process-value```), drawn by ```seon.render.ui/process-tile```.
- **Test runs, merges and evaluations:** a test run's words are `seon.render.ui/run-words` and its redness `seon.proofs/red?`; a merge is its task's outcome (`:seon.task/outcome` `:merged`, shown on its task); an evaluation is one render, ```seon.render.ui/evaluation```, for its entity, its record and a reply item.
- **Errors:** an error or failure shown reads `:seon.error/message` of the one error map ([errors](errors.md#errors)), never a second `{:error "text"}` shape.
- **Numbers:** root's view numbers (p50s, transactions per commit) are `seon.root/view-numbers`, read by `seon.root/state` and the render proc alike.
- One-line text in a list entry or the context is `seon.print/line`. A root function called from the page is recorded on main by the render proc when root answers it (origin `:ui`), with that answer ([dashboard](dashboard.md)).

## Health is what flows

Nothing is pinged and nothing runs on a beat. A render pass happens on an event, an api answer or a tab's request. What is wrong has one producer, what is recorded or derived from main's facts: root's page reads root's defects (its process tile) and main's open problems (`seon.problems/health`: [health](health.md)), never re-derive them from the live view; root records an agent's death (`seon.root/end-agent`), and a refused spawn, or a red test run or refused merge of an agent with no task (a task's agent records its own), as it folds it into the agent's view (`seon.root/set-agent`). A value only a ping carried is its owner's to emit when it changes. `bin/check idle` proves an idle root with a tab open steps nothing, and that a spawn and a commit still reach the tab.

## The model's context: a cached prefix, then the turn

A model request sends what does not change first, so the provider serves it from its prefix cache, and sends nothing twice.

### What the agent reads is its native history, and everything else through the hiccup

The agent's history is its raw data in its native format, and everything processed or looked up reaches it through the hiccup render (owner, 2026-11-10; [decisions](decisions.md#the-agents-history-is-native-and-what-is-looked-up-goes-through-the-hiccup-owner-2026-11-10)):
1. Its messages, its eval calls and their results are system, user and assistant messages and tool calls, made from `@ctx`'s data by each entity schema's model render (`:seon.render/openai-compat`). Nothing derived from the page changes or replaces them.
2. What is processed or looked up (the task, its proofs and their status, what it cites, its search, references, what changed, the turn, the agent's state) is the hiccup render.
3. That hiccup is an intermediate format, not HTML: each part headed by the function that renders it, so an agent finds and edits it, and no styling in it (style is CSS keyed on render names). It renders to html for the person and to the model's page message, whole once and then what changed, a removal one line.
4. The page's view of the messages and evals is a repeat of (1): in the hiccup each is an unexpanded call, `[render-fn args children]`, which the html expands and the model never reads again.
5. A part may render differently for the model than for the page, never at the cost of (1).

How far this is built is in task ``seon.render/a-model-render-draws-each-turns-diff`` (1 and the page message) and ``seon.render/one-tree-is-read-by-the-page-and-the-model`` (3 and 4).

The request is a reading of the agent's one walk (owner, 2026-11-06: "I want one render mechanism and for us to use it from beginning to end"): each entity schema names its model render, `:seon.render/openai-compat`, as it names its html one, and the walk asked for that output answers it from the same components (```seon.render/openai-compat```, read by ```seon.ctx.wire/request```). The agent's (```seon.ctx.wire/agent-msgs```) answers the system message and the session's opening, and places its records in the conversation's order (`seon.ctx.wire/turn-entities`): each turn's messages as it took them, its page message, its model call, the call's evals, then those of other hands. Each placed record is a component whose model render answers its messages (```seon.ctx.wire/eval-msgs```, ```seon.ctx.wire/message-msgs```, ```seon.ctx.wire/model-call-msgs```), run in the record's own component alone, never once for each part drawn from the same view, and drawing no html, which nothing placed for the model reads (```seon.render/render!```). An eval's result is printed when its messages are made (```seon.render/result-text```, the one printer, over ```seon.ctx.wire/result-mark```), against the walk's db for a value rebuilt at its basis. A component's answer is kept on its cache entry by its revision, as its html is: computed the first time the model reads it, a lookup while nothing moved, never by a walk no model reads. A model render that throws answers, in its place, the error's own model render (```seon.ctx.wire/defect-msgs```): the model is told its context lost a part. ```seon.model/wire-messages``` turns the messages into the wire shape (```seon.model/wire-groups```: a reply's assistant messages folded into one, its text and reasoning first and then its calls in order; `:reply` never reaches the wire; reasoning sent back unless `:seon.config.ai/replay-reasoning` is false, which a config with thinking on refuses at load).

What only a person wants is in the html render alone (an eval's cost and its structured value, a fold's summary). What came of an eval is read two ways from one value: its response as the one printer prints it, the model's tool message, and its value drawn by the render its record names, the person's (```seon.render.ui/eval-output```).

The tree's order is the conversation's, so nothing sorts it (`seon.ctx/placed-messages`, `seon.ctx/turn-evals`):
1. **The system message** (```seon.render.ui/system-message```): the doc sections the agent links (`:seon.agent/system`), else `docs/prompt.md` (```seon.ctx.wire/agent-system-text```): the same bytes for every agent and every turn.
   **Example sessions**, when the task of the agent's first model turn names any (`:seon.task/examples`, refs to agents keyed `example/<id>`, loaded by `my.root/load-example!` from the EDN `seon.ctx.session/session-tx` writes; ```seon.render.ui/session-examples```, ```seon.render.ui/example-session```): each (in key order) a user message `<session id="example/<id>" kind="example" from="seon">` saying it is a finished session of another task, not the agent's, and the request it answered (Seon's framing in a user message, the one turn every provider renders in place: a system message after the first is moved to the front or refused by several), its records by the same hiccup as the agent's own (```seon.render.ui/evaluation```, ```seon.render.ui/message```, ```seon.render.ui/model-call-view```), drawn as of its last t, and a user message `</session>`; their refs are `[:example key t]`.
   Then a user message `<session id="<agent key>" from="seon">` opens the agent's own session (`[:session key]`), in every request, so a conversation never opens on a blank assistant message.
2. **The page**, among the conversation's records as calls Seon makes before each model call ([the render is an eval](#the-render-is-an-eval)): `(my.render/page p)` at the first turn, `(my.render/diff p0 p1)` after, never a message of its own.
3. **The conversation**, the agent's turns in the order of their numbers ([turn](turn.md#the-turn-is-a-number)), read from what its @ctx holds (the owner's ruling of 2026-10-26: what its pattern leaves out its model does not read): each turn (```seon.render.ui/conversation-turn```) the messages it took, then its reply and the evals it ran under it (```seon.render.ui/model-call-view```; the model's ```seon.ctx.wire/model-call-msgs```, so an eval of another hand made between them cannot split a reply), then the evals of other hands. A request is made on the db at its turn's commit, which holds no reply or eval of that turn yet, so nothing cuts it. A message is `{:from :body}` (```seon.ctx.wire/message-msgs```; the page's, the message's own render ```seon.render.ui/message```, one component for both); an eval an assistant message with the call and a tool message with the response as printed (```seon.ctx.wire/eval-msgs```; one nobody's reply made has no reply to name, and one with no intent is one user message); a reply one assistant message with its text and reasoning as returned, when it has either and its evals or its text remain. A record's text is a function of that record alone (no fold, no answer marked as a repeat, DECISIONS 2026-10-29), so an older message is the same bytes while its record is and the provider's cache holds; a re-eval updates its own message in place and busts the cache from there on purpose (owner, 2026-11-06; `seon.ctx.wire-test/a-re-eval-updates-its-own-message-in-place`). All of it is sent, every turn, as a REPL keeps its scrollback (owner, 2026-10-28: no history budget): nothing is collapsed or left out, so each request is the one before and what was added. An agent whose conversation passes the model's window (1,048,576 tokens for DeepSeek's) gets the provider's error as a typed `:seon.model/provider-error`, which ends the turn as data ([failure points](failure-points.md)).

Measured against the request it replaced, in ticks, at 10, 40 and 100 evals: a turn (flush, read) 333k, 389k, 499k against 1.0M, 1.17M, 1.49M; the first read (draw, read) 2.5M, 6.03M, 13.2M against 1.54M, 3.5M, 7.41M, the print of each response the same in both and the rest a reaction and its read index a component; a cold read 3.24M, 7.08M, 15.1M against 2.1M, 5.68M, 11.98M, a walk read once making no reaction; held by the walk, 62, 33, 31 KB an eval against 11, 9.7, 7.5 KB of `:printed`: about 9 KB of reactions and their read index, 8 KB of cache entries, 5 KB of output with its text, the rest the walk's indexes. A new turn is 330 contracted calls at any size, 0.4k ticks of it a marker lookup for each earlier turn.

A response is the map ``:seon.eval/response`` declares, each key only when present (`seon.repl/response`; docs/prompt.md lists them for the model): one per eval call, its forms run in order and stopped by the first exception, its value one form's as Clojure answers it, or, for several top-level forms, `:forms` (how many ran) and `:value` the vector of their values, as a REPL prints each, printed by the one printer under its handle, the var `e` plus the eval's id in the `result` namespace (`seon.print/response-text`), which holds it. The wire id of a call is its eval's id (an id of `seon.lib/id`'s form, which any provider takes as it is), never the provider's, which a provider may reuse across replies. An eval keeps the response as the attributes `:seon.eval/response` (its handle, cost, namespace and warnings) and `:seon.eval/result` (a ref to its result entity, [users](users.md#what-each-thing-is): its value, error, output and forms), `seon.db/response-of` answering the whole; the value as plain data (```seon.contract/plainly```: a value that is not data is its members as data, or what it was, `{:seon.value/type <class>}`; past `:seon.config.store/max-value-chars` it is `{:seon.value/gone {:type :over}}`, which the transcript prints like any map), and its code, text, call id, reasoning, schema and basis as attributes beside it (```seon.repl/record-details```); nothing printed for a reader is stored, so an eval is the same whatever came before it: its text is a function of that eval alone (and of the db, for an eval of `@ctx`, which names its basis and is rebuilt as of its t), (its ref is `[:eval id]`). A reply with text and no call ends the turn, and the agent waits for the user (tool_choice auto: DeepSeek refuses `required` with thinking on).

So each request starts with the whole of the one before (`seon.ctx.wire-test/the-request-is-a-conversation-of-evals-and-the-page`, `seon.ctx.wire-test/the-prefix-stays-byte-identical-across-turns`), and the plan, its references and its sections go out once a request (`seon.ctx.wire-test/each-section-is-told-once-on-the-page`). Not this: a part sent twice a request, or a note that edits an earlier message, which breaks the prefix for every later turn. v1 measured the same split live: stable session sections of about 8.5k tokens, turn sections of about 0.75k, 85-91% cache hits. Measured through the server on three open tasks (printer estimate, `:seon.config.ai/chars-per-token-prior`): the help page is 2,132 tokens, the same for every agent; the session sections 1,639-1,887 (the references 2.1-2.4 KB); the turn sections 45-76 before any proof has run. A first request is 3.9k tokens, 54% of it shared by every agent; each later turn adds its scrollback and about 60 tokens of turn sections, so with 2k tokens of scrollback a turn sends about 2.1k uncached tokens and the cached prefix is 65% of the second request and 79% of the fourth. What the provider served from its cache is recorded on each turn's model call (`:seon.model-call/cache-hit-tokens`, `:seon.model-call/cache-miss-tokens`, by `seon.turn/usage`; [the record is the agent's work](ctx.md#the-agents-entity-holds-its-work)), absent when it did not say.

DeepSeek's prefix cache ([its guide](https://api-docs.deepseek.com/guides/kv_cache)) serves a request only from a stored prefix unit it fully matches. Units are made at the end of each request's input and output, at prefixes several requests share (found lazily: the third request hits what two earlier ones shared), and at fixed intervals inside a long input; the cache is best effort, takes seconds to build, and is dropped hours to days after its last use. Since each request drops the one before's last message, the newest scrollback turn sits on no unit boundary and hits only through the shared-prefix units.

A short cache hit is a problem. Each turn compares its request with the one before it (```seon.turn/cache-miss```): the leading messages both hold equal are the prefix the cache should serve, sized as the provider's own prompt count apportioned by the one sizer (```seon.ctx.wire/messages-tokens```) and rounded down to the provider's block (`:seon.config.ai/cache-block-tokens`; DeepSeek's 128, measured: every recorded hit is a multiple of it). A hit more than one block short of that is a `:seon.turn/cache-miss` error the agent folds and sends with its next commit, counted under one signature in the `:eval` class (`seon.model-test/a-turn-whose-cache-misses-its-prefix-is-a-problem`). Measured 2026-10-25 on 100 turns of 6 agents' work: 75.6% of all prompt tokens hit the cache, 78.4% after each agent's first turn; each hit was 0.87-1.12 of the prefix so sized, and none was short. Turn 1 shares only the system prompt and the task's data (turn 0's request after them is all screen, evaluated again each turn), so it hits about 900 tokens by design.

A reply cut at `:seon.config.ai/max-tokens` (the call holds `:seon.model-call/truncated`; `seon.model/reply-of` keeps the cut text and the forgiving reader repairs it) is almost always a repetition loop, not long work. Over 370 deepseek-flash turns with thinking off and a 65,536-token bound, 66 (18%) ended "length" at 184k-415k characters, each repeating 2-47 distinct forms (typically one ``clojure.repl/source`` call 300+ times), every form evaluated (up to 4,206 in one turn); they spent 45% of all tokens and 168 of 181 model-minutes (median 151 s against 2 s for an ordinary turn). 18 of 33 first turns looped, so the loop is not only history fed back. The largest ordinary reply was 19,809 characters (about 5k tokens).

The field's evidence for this shape: SWE-agent (arXiv 2405.15793, SWE-bench Lite, 18.0% resolved) lost 3.0 points with full history instead of collapsing all but the last 5 observations, 5.3 with a whole-file viewer instead of 100 lines, 6.0 with iterative instead of summarized search and 1.7 with no demonstration, and its successes took a median of 12 steps against a mean of 21 for its failures. CodeAct (arXiv 2402.01030) found code as the one action up to 20% more successful in fewer turns; Seon's one `eval` tool is CodeAct ([model](model.md#one-tool-repl)). aider ranks a 1k-token map of symbols by references, and Manus calls the KV-cache hit rate the first metric and keeps its context append-only and deterministically serialized.

**What grows a request is the conversation, not the page** (measured 2026-11-01 by re-rendering one agent's recorded requests): the page is about 3k tokens and most turns add about 70 characters of it, while a request went from 5k tokens to 54k by turn 25, single eval answers (a source read, a whole namespace) running 16-27k characters. The field's best-replicated finding agrees: tool outputs were about 84% of a turn's tokens, and masking old ones while keeping the actions matched or beat summarizing them at about half the cost (JetBrains, arXiv 2508.21433; SWE-agent's last-5-observations, arXiv 2405.15793). Here an old eval's answer could become one line naming its handle (``result/a3f9c1d2``) and how to read it back, in steps of k turns so the prefix breaks once per k. That is an experiment for the evaluation (L1.5), not a change: the owner's ruling of 2026-10-28 sends the whole conversation.

### The render is an eval

The page is not a message. Before each model call the agent's model render places the page as a call Seon made and its answer (```seon.ctx.wire/page-diff-msgs```), generated from the call's basis and the basis before it, never written to the db: the first turn's is `(my.render/page p)`, answered with the agent's page parts whole (```seon.render.ui/agent-parts```, stripped of presentation), and each later turn's `(my.render/diff p0 p1)`, answered with the edits between the parts at the two points ([a change is edits by name](#a-change-is-edits-by-name)). A turn that moved nothing the parts show places none. Its id is a digest of its two points, so a request made again from the same records is the same bytes (`seon.ctx.wire-test/the-recorded-requests-come-out-the-same`). The agent runs either at its REPL whenever it wants (```my.render/page```, ```my.render/diff```).

It goes to the model as an ordinary call, its code alone, so it reads like the agent's own: a model's reply text falls silent after an empty assistant message (197 of 197 replies), and it copies its own history, so a reply's message is its text, written when the agent has something to say, stored as `:seon.model-call/reply` and sent back as the model wrote it ([one tool](model.md#one-tool-repl)), and a code-only history taught no agent to drop its `intent` (100% of calls on 24 tasks and over 12 turns, deepseek-flash).

So the context accumulates: each request is the one before and the records added, the page among them (`seon.ctx.wire-test/the-prefix-stays-byte-identical-across-turns`). A request on a branch whose turns hold no basis yet (an outside agent's first read) is drawn at the branch as it is (```seon.turn/context-block```), and a cold one at a turn's commit (```seon.ctx.wire/render```). A tree that draws no system message is refused, `:seon.ctx/no-system-message`, never sent without one, while another component's defect reaches the model in its place as a user message saying what threw. A cold draw for a model reads what the model reads and nothing for the page alone (```seon.render/draw```'s `:model-only`, `seon.render-cost-test/a-cold-request-draws-what-the-model-reads`).

What the walk does not know, so a page diff cannot say: config read inside a render; the printer's own code. A render redefined is known (one render serves the page and the model).

A revision follows the hiccup a component answers, so a turn that moved nothing the page shows places no page message: the turn line (```seon.render.ui/turn```) moves only with the REPL's namespace.

### A change is edits by name

What moved of a component reaches the model as [editscript](https://github.com/juji-io/editscript)'s edits over its old and new hiccup, in names, or the component whole when that is shorter, so the full structure is not printed again and the model can tell where the change is (owner, 2026-11-06: "There must be a clear way for the model to understand where the change is happening and then we only show the changed parts"; "I like editscript. I want the gains"). `docs/prompt.md` teaches it once.

One generic function reads a component's hiccup before the diff (```seon.render/keyed```): an element's children become a map in their order, each under a name and read the same way, and under `:own` the element without them. A child's name is what identifies it, with no case for any component: its `:key`, else its `:id` (a nested component's name-based id), else, among those with neither, its tag when no sibling shares it and its first words when one does, so a heading, a scaffold or an example unchanged is never sent again because something beside it moved. Names that are not distinct stay in `:own`. An element holding text directly is text, one value, and so is an element holding a single child with no name of its own (`[:pre [:code src]]`). So no path holds a position (```seon.render/named-edit``` cuts a path where it enters a value; recall probes on a model with paths of positions were 125 of 315 right, with names 273-288). Strings are never opened (`:str-diff` off, editscript's default: long-text edits scored worse). Each edit's path starts with the component's id, and the three operations are `[path :r value]`, `[path :+ value]`, `[path :-]`, a value being the hiccup. A new component is `[[id] :+ form]`, one that left `[[id] :-]`, a whole one `[[id] :r form]`: the whole answer is one vocabulary. Named children that changed places are that element replaced at its name (```seon.render/settled```: a map's keys hold no order). What a render says about many things gives each a name: ```seon.render.ui/status-hiccup``` keys a proof, what blocks a merge and each item of it, and its example is its namespace's, read from the merge base, so it neither moves when a proof is written nor quotes the agent's own test back.

No clock decides what comes out: editscript's `:vec-timeout` defaults to one second and is read by `:quick` as well as `:a-star` (`editscript.util.common/with-vec-deadline`), so `seon.render/component-edits` passes `:vec-timeout nil`, which reads no clock at all; [clocks](clocks.md) names the site, which the law's text mark sees. `seon.render-test/a-change-speaks-in-names`.

A turn's page message is the edits between the agent's page parts at two bases (```seon.ctx.wire/page-diff-msgs```, placed before each model call by the agent's model render, keyed by its two points, so a walk holding the turns runs only a new turn's pair). The parts along the turns' bases are drawn by one walk (```seon.ctx.wire/page-parts-through```): drawn at the first point, then advanced to each later one (```seon.ctx/moved```, ```seon.ctx/patch```, the moved components flushed), so a cold request of T turns costs one draw and what moved at each turn, never a draw a point; each pair's two pages are compared by `page-edits` over `forms-moved`. A point whose commit collection dropped is read as of its t, and the diff of that value reads the whole range rather than what the two commits hold apart ([sharing](sharing.md#what-each-operation-should-cost)). The first turn has no point before it: the page whole. An agent asks the same at its REPL (`my.render/diff`). Nothing is stored. (owner, 2026-11-08: "We shouldn't be saving rendered data if we can re-render it from a specific point in time".) The edits between two points are one function of them (```seon.ctx.wire/page-edits-between```), what the page message prints and `my.render/diff` answers; what a turn's diff costs is `seon.render-cost-test/a-turns-page-edits-cost-the-same-at-any-length`.


What it costs and saves. A diff costs the component that moved: flat 9 or 10 contracted calls, 60-90 KB and 11k-18k ticks on the largest real components (a status, a cited var of 3 KB); about 12.5 KB a named child, 27k ticks at 10 children and 326k at 100 (`seon.render-cost-test/edits-cost-the-component`; the read is an array map's, so ticks reach 17.6M at 1,000 children, far past any page). On three real tasks worked by an outside agent (`:since`, `:t` and the wrapper left out), an update's bytes as today's status keys them, against what the logs had: see the merge message of `jolt/agent-feedback`. What stays whole: a source the agent changed, a string being one value, and a red's message, whose text the test's author wrote and which may hold a measured number.

### A layout places its lists

A layout lays its page out as lists, and each list is a component of its own: a render whose var carries `:seon.render/list`, the id of the container element its output is (```seon.render.ui/agent-parts``` is `"p-task"`, `conversation-list` `"c-rows"`). Its root element keeps that id (every other component's root takes its key, `seon.render/key-id`), and the components directly in it are placed in it: ```seon.render/placed``` walks through a list component to its list, so the parts a reader takes (`placed-units`, `placed-hiccup`) are the list's members, as when the list was an element of the layout. A reader of some lists walks only those (`placed` with sels). Placement reads the components, never their hiccup: each component's placements (the children its output holds, each with the nearest element id above it, ```seon.render/places```) are kept on its cache entry by its revision and made again only after its output moved, so placing a page whose one leaf changed costs its components and that leaf's output, whatever the rest of the page holds (`seon.render-cost-test/a-flush-places-what-moved`: 2 calls and under 20 KB at 10, 100 and 1,000 elements of an unchanged member, where the prewalk it replaces grew as n^0.43). A unit that changes place is moved, never its container sent: the page's view keeps each container's order of units, and a step's units against it give the ones that moved (```seon.render.proc/moves```: in each container the held units that keep their order are the longest run that does, each other one is taken out and put back by element id after the unit now before it, or before the one now after it, so it lands in whatever element holds its neighbour), while a unit whose html changed only in which child each slot holds, every slot where it was, is not sent at all (`seon.render-test/a-reordered-unit-is-moved-not-its-container-sent`). A page's units are keyed by element id, so each element is named once on a page: the agents list the frame puts beside another walk's units comes from the user's walk, which names its elements apart (`:id-prefix` "u-", ```seon.render.proc/user-walk```), since an agent the user started is also an entry of root's sessions on root's page (`seon.render-test/a-page-names-each-element-once`). **The root's own output is the page** (owner via Point, 2026-11-11: the frame places the page render): ```seon.render/placed-units``` answers it first, a unit in ```seon.render/root-container``` (`#p-page`), its output as the page writes it with each list it places drawn as that list's own element, and in every element with an id a region (```seon.render/region```, its ids the unit's `:regions`), where the units placed in that element that no parent holds go when the page is composed (```seon.render.proc/compose```, in the view's order): a list's members, and what another walk places there (an agent's head in `#p-head`, root's system view in `#p-head` and `#p-tiles`), so the layout names an element and never who fills it. Any other component of its output is placed by its container in the same way. It is written again only when the root's own revision or a list's moved, and its revision is its html's, so a member added is an append into its list and never sends the page; when the page is sent its regions' units go with it (```seon.render.proc/finish-patch```: a region's units are held by the page). The frame (```seon.render.ui/page-chrome```) keeps the top bar, the agents list (`#c-side`, the signed-in user's walk, unless the page holds its own: a user's page draws it in its own column), the one slot for the page, and the caption and the input, at the end of the page's chat column (`#p-chat`) when it has one; a page no walk draws (the sign-in page, an agent's `@ctx` tab, an agent whose branch is not read yet) is ```seon.render.ui/bare-page```'s head and rows, and a frame the tab does not hold is sent whole (```seon.render.proc/pass-view```). The agent's page holds the elements and units the frame drew by hand before (`seon.render-test/the-agent-page-holds-what-the-frame-held`). Which lists the model reads as parts, and which as messages, is the lists' own: ```seon.render/page-lists``` answers each list component the root drew that holds no messages (`:seon.render/messages` on its var) and is not for the page alone (`:wire/for "page"` on its call), and the model reads the others' records through their model renders (```seon.render/openai-compat```). An agent's own walk draws what its model reads until a person's page asks for the rest (`:model-only`, ```seon.repl/whole-walk```, ```seon.render/draw-all```: each component that left a piece out runs again), and it then keeps drawing them while its process lives: it holds no count of who is watching. Measured 2026-11-04, one scripted run of 12 turns: 303 MB and 58 component runs in the walk unwatched, 475 MB and 298 watched. What a layout must do: put each list in a list component that reads only what that list shows, so a change of one list's members reruns that list alone (an eval added reruns its turn's component, and the tiles only when its value has a render of its own, never the task's list, whose parts the model is sent; the conversation's list reads the agent's turn number and no record, so a new turn reruns it and costs a lookup of each earlier turn's marker, no contracted call); the layout itself reads nothing (```seon.render.ui/agent```). Split 2026-11-03: what the model is sent and the person's page are the same bytes (every unit, part and message of three test sessions, recorded before and after).

### A page is a kept walk

A page root draws is a walk kept across moves, advanced by what each move changed: root's own (its root walk) and, for each agent a tab watches, one walk of its page on its branch, held with the branch's one read (`:branch-reads`) and disposed with it. `seon.render.proc/kept-walk` builds one (the ctx, `seon.ctx/build`, in a reactive atom, drawn once by its layout); `seon.render.proc/advance-walk!` moves it to a later value of its branch (the ctx patched by the datoms that moved, `seon.ctx/patch`, given when the caller knows them, else `seon.ctx/moved` diffs the two values, and those datoms flushed), so a move draws the components its change reached; `seon.render.proc/branch-walk!` is an agent's, at the same db nothing at all. An agent's chat drawn from its branch (no process to ask, none that answered, or one whose last draw is older than the branch) and its @ctx read it. The debug page's turn to come draws the tree cold (`seon.ctx.wire/render`): the kept walk would be flushed over the turn the request writes and back, two moves, measured dearer (41.2 MB against 37.3 at 100 evals). A move of a kept walk that adds a record reruns the component of the turn that took it (```seon.render.ui/conversation-turn```, which reads its records through its model call) and the new record's own; the turns before it are a marker each, so a step costs a fixed part and a lookup for each earlier turn (cost in [components](#components)). The agent's own walk (seon.repl/page-hiccup) pays the same each turn. The model's page (```seon.ctx.wire/page-parts-through```, the walk of its page parts the page messages compare) is kept the same way, in the process that draws it, at the last point it drew: a later point of the same branch (a commit that reaches the kept one, within ```:seon.config.ctx/kept-walk-steps``` parents) advances it, and the same commit at the same t moves nothing and diffs nothing; an earlier point, another agent's or another lineage's is drawn again, and that walk is the one kept (```seon.ctx.wire-test/a-later-point-advances-the-kept-page-walk-and-answers-a-cold-draw```). The slot also holds the page at its last chain's first point, which goes with the walk: a flush between turns (a :context read, a person's page, an eval's own) draws the pending turn's page at the db's own point, one transaction past the last basis, so the next turn's pair starts behind the walk; that pair takes its first page from the slot and advances the walk from where it is (```seon.ctx.wire-test/a-flush-between-turns-leaves-the-next-turns-pair-to-advance```). It drew the page cold at every such turn: 2.62M ticks, 6.6 MB and 1,450 calls a pair at 10 turns on the test store, against 106k ticks, 423 KB and 15 calls now, flat in turns (```seon.ctx.wire-cost-test/a-turns-pair-after-a-flush-costs-flat-in-turns```); on an agent's live walk, about 7.1M ticks a :context read. A turn's page message reads the db at its two points alone: each read is of a db value at a fixed past point (a commit, an immutable value, or a past t), which no later write can change, and none is of the current db. Only those reads are not recorded, so the walk runs a pair again only when its points change, never at each later write (```seon.ctx.wire/page-diff-msgs```); the render that places the pairs reads the current db, tracked as every render read is, and runs again at a write (```seon.ctx.wire-test/a-write-reruns-the-placing-render-and-no-earlier-page-pair```). Before both, a test's context read, which writes its own model call, drew the page cold twice a read: about 165 ms a read end to end on Seon's program, then about 80 ms.

### The debug page is the wire request

The debug page shows what a turn put on the wire, made again from its records at its commit with today's renders (the page is among them, as evals), never a second render (owner, 2026-11-03: "I want debug to be what we would send to the model right now"; task seon.render/the-debug-page-is-the-wire-request). A turn records its basis (`:seon.model-call/basis`): the commit that holds the turn, the main and merge base it heard, and the agent's model. Everything its request is made from is a fact of that commit. ```seon.ctx.wire/wire-turn``` makes the request body again there: the messages (`seon.ctx.wire/render`) under the provider (`seon.ctx.wire/provider-of`), on the wire by `seon.model/request-body`. The turn itself calls `provider-of` at its basis, so the turn and its replay name one provider by construction (`seon.ctx.wire-test/a-turns-wire-request-is-made-again-at-its-basis`: three turns, a change of the task's config between them, each made again byte for byte).

The page (```seon.render.ui/debug```) is the raw wire, a timeline of the branch's model calls: a bar a turn (the turn number in a request's header is its bar's), its height the context that turn sent against the largest turn's and split by what the provider's cache served (each call's `:seon.model-call/tokens` and `cache-hit-tokens`), previous, next and latest (`/at`, the view's `:at` in the render proc). One request is drawn at a time (```seon.render.ui/debug-turn``` over ```seon.render.ui/debug-input```): a bar of its tokens by role, then each message of the body in order, one row typed by its wire role (`system`, `user`, `assistant`, `tool`), with a line of its text and its size. A size reads quiet, amber or red against `:seon.config.render/tokens-warn` and `tokens-over` (a whole request against `request-tokens-warn` and `request-tokens-over`): only the colour changes at a bound. Nothing is grouped, renamed or joined: this page is the wire, and a person's reading of it is the agent's page. Opening a row posts `/open` (unit `d-turn-o<i>`), which draws the one request again with that row's fields as sent in place of its line: the records that made it, `content` (a system message's as Markdown, a tool's highlighted), and each tool call's name, id and arguments by their wire names, read from the JSON the wire holds. Open is whole: a large message is found by its size in red, and nothing inside it is cut again. The body's JSON stays whole at the end, so what the page draws is checked against the bytes. A message made by a record the request before did not hold (a turn after its number) is marked new; a turn hashes the bytes it sent (`:seon.model-call/sent-hash`, `seon.lib/digest` of its messages) and the page says when its redraw hashes to something else (`:differs?`: a render or a record changed since), and that one hash can't say where; a turn whose commit the store no longer keeps (`seon.db/retain!`) is drawn from the branch's head, and the page says so; the envelope (every field but the messages) and, opened, the body's JSON whole. A chosen turn's input is its model call's eid, so it is drawn once and never changes. Latest, while the agent works, is the request the next model turn would send now: drawn at the branch's head as the turn after the newest, as `seon.turn/act!` draws it, again each time the branch moves, and only while a tab watches the view. Nothing is kept between draws (`seon.render-cost-test/drawing-latest-costs-one-request`: 4,920 calls and 9.4 MB at 10 evals, 32.4k and 34.2 MB at 100). A page of no units, before any model turn, is held with none and says so. The turn to come is drawn with what the branch records the agent heard of main: a commit to main the agent has not merged yet shows in the request its next turn makes, which records it (`seon.turn/act!`'s main-base facts), not in latest before it. A turn chosen that is no request of the branch any more (the branch replaced) is said on the page, and latest is shown. What a tab chose of a view (the entries it scrolled to, the units it opened, the turn it stepped to) is one map, the view's `:tab` in the render proc, which decides a walk whole with the view's dbs: a step on a branch that no longer moves draws the turn chosen. A turn is to come while its agent has written no end on the branch (```seon.render.ui/to-come?```, over `seon.reconcile/pull-end`); an ended agent's latest is its newest turn.

## One path to the model

Everything a model is sent is read from the tree, through one conversion, and an action on the page is in the model's reading or is named here with what the model has for it (owner, 2026-11-06: "I want one render mechanism and for us to use it from beginning to end"; "actions are in the data, never only in a look").

`seon.render-test/one-path-to-the-model` reads the compiler's facts (`:form/refs` of src imported) and each candidate form as data: ```seon.ctx.wire/request``` is referenced by ```seon.ctx.wire/render``` alone; ```seon.model/request-body``` by the provider's call and the debug page's replay; and a form holding a message (a map of `:role` and `:content`) outside the schemas' model renders, or a request (`:messages` with `:turn` or `:model`) that does not read ```seon.ctx.wire/render```, is red. It is shown red on a second path planted in a test world. What it cannot see: a message built from a map whose keys are computed, and text sent by a process that is no part of src.

`seon.render-test/an-action-on-the-page-is-the-models-too` lists every render whose hiccup holds an action (`:seon/call`, a callback as data, or a `data-on` handler). Each is named below; a new one is red until it says what the model has for it, and one that holds none leaves the list.

- `seon.render.ui/agent-input`: a person's REPL, messages, interrupt and release. The model's REPL is its eval tool, and a message reaches it as a message; interrupt and release act on it, not for it.
- `seon.render.ui/root-input`: a person's request on their own page, a sentence that becomes a task an agent starts on (``seon.root/ask!``); on root's page a person talks to root's session (```seon.render.ui/agent-input```). - `seon.render.ui/root-tools`: root's spawn and evaluate-in-every-agent, on root's debug page, for whoever works on Seon itself. An agent messages root, or a person's `seon_eval root` does the same by the same call.
- `seon.render.ui/debug`, `seon.render.ui/debug-turn`: stepping through recorded requests and opening one's rows. The model reads its own conversation whole.
- `seon.render.ui/more`: a long list's next members as it scrolls. The model is sent the list whole.
- `seon.render.ui/toggle`: a fold's open and close. The model reads what is in it.
- `seon.render.ui/evaluation`, `seon.print.emit/elided-hiccup`: a cut opened where it stands. The model has the form the cut prints, which reads the same rest.
- `seon.render.ui/eval-step`: a person's opening of an eval, recorded for root's page (`seon.root/opened!`). The model reads the eval whole.

## How a value is printed

A value is printed in two passes, selection under one token budget and then layout, so its text and its hiccup come from one selection and every cut names the form that reads the rest.

```seon.print/print-value``` is the one entry: a value, a handle the cuts read through (``result/h3``, or a form), a budget in tokens (```seon.print/budgets```: a reply's, a part's, a form's and the context's, each a `:seon.config.render*` key), a depth and a width. ```seon.print.select/show``` selects: it allots the budget breadth before depth (every child of a collection shows before any one deepens), identity keys first, and builds a print-node tree whose cut nodes carry their continuation forms; a value whose metadata holds ``:seon.print/full`` prints whole, and ``:seon.print/budget`` raises its own budget. Members of one class are the exception to breadth: a collection whose members are all alike (```seon.print.select/row-class```: maps, vectors or sets of one class, a sequence's strings, a map's values under keys that are not keywords) shows each whole in its order while it fits, then one cut that counts the rest and reads them (`…144 (drop 33 (get-in result/a3f9c1d2 [:value :classes :stale-section :rows]))`); a member at its least is a cut that shows nothing, so breadth over 177 of them printed 144 lines of `{…13 (get-in ..)}` (```seon.print.select/fill-rows```; `seon.print-test/rows-show-whole-then-one-cut`; no member past the cut is read, `seon.print-cost-test/printing-rows-costs-what-it-shows`). A keyword-keyed map is one record's attributes and keeps breadth. Members indent one column inside their opener at every depth (a flush deeper level read as its parent's); a namespace-lifted map's and an `#error`'s still indent from the group, not past `#:ns{` (`seon.print-test/a-lifted-map-indents-its-keys-past-its-opener`). ```seon.print.emit/emit-both``` lays the tree out as fipp does (begin, end, nest, line, text over one operation stream) and answers the text, and the hiccup the page's value panel shows when asked; fipp itself is only the layout's test oracle (`seon.print-test/the-layout-is-fipps`). Printing through fipp cost 45.4 KB and 16-17 µs per entry of a flat map, the printer 2.41 KB and 1.8 µs. Not this: Jolt's `clojure.pprint`, which would give that back. ```seon.print.select/estimate``` is the one sizer of tokens. `seon.print/text` (the printed text, or the error's message when even the first part does not fit), `seon.print/line` and `seon.print/plain` are the printer at a budget for text, a line and text ([Text](#text-and-the-one-string-cutter), [A render is a value](#a-render-is-a-value-printed-once)). A map of two or more keys of one namespace prints as `#:ns{:a 1, :b 2}` (Clojure's `*print-namespace-maps*`): ```seon.print.select/lifted-namespace``` decides it once, when the map is classified, over every key the map holds, so the selection charges the opener `#:ns{` and the unqualified keys it lays out, the emitter reads that decision (`:seon.print/lift`) and nests the members past the whole opener, and charge and layout agree by construction. A map whose shown keys share a namespace but whose cut keys do not is therefore printed qualified, not lifted (`seon.print-test/a-lifted-map-indents-its-keys-past-its-opener`).

## One printer

There is one value printer, `seon.print`, and nothing is cut before it. A value a person or a model reads is its schema's declared render (`seon.render`) or the printer's text; a value that is not text reaching the page's serializer (`seon.web.html/html`), a one-line text (`seon.print/line`) or text (`seon.render.ui/plain`) is printed by the printer, never `str`. The REPL answers every value by the printer, as the data it is; an error map is printed whole (its message, fix, variant and where; Jolt's diagnostics are keys of the map, printed once, [errors](errors.md#an-eval-errors-diagnostics)), and the page draws it by its declared render. An evaluation on the page (`seon.render.ui/evaluation`) is its recorded value drawn from its data, the printer's hiccup under its handle ([A value on the page](#a-value-on-the-page-is-its-structure)); shown inline it is its record printed as its reply reads, so its cut is the printer's (whole members, the form that reads the rest), never its reply's text cut again as text; an MCP answer that root's REPL can answer again (an op's `:again` form in `seon.server/ops`, `seon_agents`) is printed under the reply budget with that form as its handle, not whole.

`seon.render-test/one-printer-and-no-cut-before-it` reads the compiler's facts (`:form/refs` of src imported, `seon.program/live-forms`; each var's form, and each method's): every var outside `seon.print` that references `pr-str`, `prn-str`, `print-str`, `with-out-str`, `pr`, `prn`, `printf` or `clojure.pprint`'s `pprint`, `pp`, `write` or `cl-format` is named below; every var of a display namespace (`my.*`, `seon.render.*`, `seon.web*`, `seon.ctx`, `seon.server`, `seon.cost`, `seon.repl`, `seon.agent`, `seon.problems`) that references `subs`, `take`, `take-last` or `drop-last` is named below; and every var outside them that calls the printer with a budget (`seon.print/text`, `line`, `text`: a cut where a value is made) is named below. An unnamed one is red, and so is a name here that no longer does it. (`butlast` is left out: destructuring's expansion references it in every function. Not covered: `str`, `print`, `println` and `format` on data, and `first` or `drop` on members shown, which the compiler's facts cannot tell from their use on data; review reads for them.)

### Printing beside the printer: the wire

Text for the wire, storage, a digest, a file, a URL, a command line or code to evaluate is `seon.edn/encode` (EDN that reads back, whole: no print limits), and only that var prints beside the printer:

- `seon.edn/encode`: EDN for storage and the wire, whole.
- `seon.program/form-ids`: the text of a form's code digest (`:form/code`), the form `pr-str` writes under `seon.edn/encode`'s bindings, whole: a digest's text, not output; inline, not `seon.edn/encode`, because that is one contracted call more than the `account` proof's estimate holds ([source](source.md#what-a-test-takes-of-a-forms-text)).
- `seon.render.ui/table-cells`: each cell's text read to tell a Markdown table's rule row from its rows (`subs` of the cell's offsets), a cut of data, not of output: the cells are drawn whole from the one scan's spans.
- `seon.render/result-text`: the EDN envelope of a user message (`{:by .. :code .. :response ..}`) around a response the one printer already printed: the wire, not output.
- `seon.ctx.search/search`: the call in its last hit's `:more` (`(my.agent/search q {opts})`, q and the options as `pr-str` writes them): code to evaluate that returns the hits it left out, not output.
- `my.schema/registration`: the part of a schema form that is no EDN, and where it is, in the invalid registration's message (`pr-str` of the value and its path, whole): the message tells the agent what to quote.
- `seon.config/resolved`: the config keys a refused combination names, in its error message.
- `my.root/first-moves!`: the code text it sends an agent to evaluate (the call to `seon.judge/first-move` on a task id): code to evaluate, not output.
- `seon.server/verdict-line`: the form in its `:handle` (`(seon.server/verdict @(:conn sys) task)`, the task id as `pr-str` writes it): code to evaluate that reads the whole verdict, not output; the line beside it is the one printer's.

An agent's namespace refers `clojure.pprint`'s `pp` and `pprint` (`seon.agent/make-ns!`), as a plain Clojure REPL does ([processes](processes.md#an-agent-is-never-gated), "what would a plain REPL do"); what they write reaches the model as the evaluation's `:out`, budgeted as text. What an eval prints to `*out*` and `*err*` is its `:out` and `:err` marked verbatim (`seon.print/code`, made in `seon.repl/eval-code`), as a REPL shows them, never a string literal: printed as one, a definition's `\(` would read `\\(`, and a reader copying it back as code would copy the escapes. A check's console lines are the printer's whole text (`seon.main/shown`).

### Cut where a value is made

The places that cut a value where it is made, not in the printer, each with its reason.

- `seon.main/shown`: names a budget only to print whole (the value's ``:seon.print/full`` metadata).
- `seon.contract/kept`: root keeps no live value of another process's error ([errors](errors.md#an-error-keeps-data)); a value past the part budget is kept as the printer's cut (`print/plain` for a string, `print/text` marked code for the rest), which says what it omitted.
- `seon.contract/problems`, `seon.task/file-declarations`: a refused value (a function's argument, a task file's entry) may be infinite, lazy or a host object, and travels on the wire as text, so its error keeps the printer's cut, which says what it omitted; the live value stays with the caller.
- `seon.turn/tell-error!`: the error a turn threw (or the missing status) becomes its message's text where the message is made, printed whole (`:seon.print/full`), never cut: the agent reads all of it, as it reads any message.
- `seon.db/invalid-entity`: the refused entity's identity in a write's refusal (its upsert key and value, or its id), `print/text` at the part budget, as a contract error names its value: a value may be any size, and the refusal travels on the wire as text ([the write checks every entity it touches](storage.md#the-write-checks-every-entity-it-touches)).
- `seon.contract/first-problem`: the offending value in a contract error's message, `print/text` under 60 tokens (the part budget is for the error's `:value`, whole in `:seon.error/problems`): one line of where, what it got and what was expected, so the reader finds the first problem without opening the map.
- A test child's reports: a child process prints an assertion's expected and actual at its pipe, a process boundary, and the reports are kept as it sent them; `seon.proofs/failures` keeps every one, whole (owner, 2026-10-29: "do not put any artificial limits or cuts on agents context or evals"), the facts on its var entity hold that data (`:seon.test/failures`), and the one printer prints it where it is shown (the owner, 2026-10-29: "keep everything as data until it's at a print boundary").

### Cuts in a display namespace that are not cuts of output

Uses of take, subs and the like in display code that choose what to find or read, not what to cut from output.

- `my.schema/unknown-key`: a registered key's text without its colon, to name the nearest keys of a key no schema registers by Jolt's ranking: a lookup, not a cut of output.
- `seon.render.ui/kname`: a keyword's text without its colon.
- `seon.ctx.status/form-at`: a form (a real call, a namespace's `:require`) is a slice (`subs`) of a test's, caller's or namespace's own source from its opening delimiter to its closing one: text the db holds, found by position; a find, not a cut of output.
- `seon.render.ui/markdown`, `seon.render.ui/inline`, `seon.render.ui/task-title`: Markdown text split into its blocks and spans by the offsets its parse (`seon.ref/scan`) gives (a fenced block's content and a list's items too), each kept as written; a name's first letter made capital: text rearranged, nothing left out.
- `seon.ctx.search/relevance`: the first `cap` of a search's scan of each kind's nearest (`take`), the pool it scores: a score's input, never shown.
- `seon.ctx.search/search`: a search's answer, its first `:k` hits (`take`) with a count of the rest and the form that returns them, that form printed as code to evaluate (`pr-str` of the query and its options): not a cut of output.
- `seon.ctx.search/neighbours`: the first `cap` of who names a var or key (`take`), a bounded read of the reference graph for a score (a var every form names would cost thousands of datoms): work bound, not output.
- `seon.agent/embed-written!`: the first `:seon.config.vector/texts` of the texts due go in one `:embed` request (`take`), the rest stay due for the next: a batch bound on work, not a cut of output.
- `my.agent/file-source`, `seon.repl/form-src`: a form's own text out of its file or its reply (`subs` at a reader's offsets).
- `my.agent/lines`: the lines a to b of a text the agent asked for (`sed -n`'s range, `drop` and `take` over its lines): a selection of data it named, not a cut of output.
- `seon.repl/do-parts`: a top-level form written `(do ...)` (its text opens with `(` and the token `do`, so a reader macro that expands to do is not one) as its inner forms, each the form the reader already returned, with its exact text and leading comments from the reader's own positions in the do's text (no pattern, no cut by text), each then evaluated as a top-level form as Clojure's compiler takes them: code read, not output.
- `seon.repl/edit!`, `seon.repl/place`: the offsets of the old text in a place's recorded text (`subs` rebuilds the source around the change, `line-of` counts the lines before an offset): text rearranged, nothing left out; a refused edit names every line that could be meant.
- `seon.repl/file-name`: a path relative to a root it is under (`subs` off the root).
- `seon.repl/streaming`: a Writer's `write(str, off, len)` slice (`subs` takes exactly the characters the caller writes; the record and the stream keep every one).
- `seon.web/handler`, `seon.web/view-of`, `seon.server/mcp-reply`: parsing a request's path and a tool's name.
- `seon.ctx.search/near`: the whole line a repaired delimiter is on, the printer budgets it.
- `seon.render.proc/pass`: root's process keeps the newest `:seon.config.render.list/stream` events, and its tile (`seon.render.ui/process-tile`) draws the newest `:seon.config.render.list/history` of them: a window of data, as ctx's are.
