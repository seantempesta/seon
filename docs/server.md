# The server

Root's server is one socket on 127.0.0.1 where outside agents (a Claude session through MCP, a person with `nc`) send requests, one per line, and read one answer per line: `seon.server`.

A line opening `{"` is MCP's JSON-RPC; every other line is an EDN request, a keyword-keyed map `{:op k ...}` (```seon.server/respond```, the protocol rule). Both reach the same table of ops, so MCP and EDN callers get the same answers. The server is an outside caller of root's API, as `bin/check` is: each op calls `seon.root` functions (`seon.root/submit!`, `seon.root/spawn!`, `seon.root/judge!`), which put requests on the api proc's `:ext` channel ([root](root.md#the-root-graph)).

```seon.server/serve!``` listens on `:seon.config.root/server-port` (`bin/ports` gives each checkout its own; 0 serves none): the accept loop and each connection run on edge threads, because accept and reads block ([failure points](failure-points.md)). ```seon.main/root-serve``` is what `bin/root run` starts: root booted, the server listening, until stdin closes or a signal arrives ([root](root.md#boot)).

## Ops

The ops are one table, ```seon.server/ops```, keyed by a request's `:op`; each entry holds its description and its arguments as JSON Schema, and its answer is the method of its key of ```seon.server/op-answer```, a multimethod on `:op` (one method per op, so a test's reach takes the answers of the ops it sends and no other: [source](source.md)); nothing else lists them, and `seon.server-test/each-op-has-its-answer` holds the table and the methods to one set of keys: a new op is a new MCP tool `seon_<op>` (`seon_agents`, `seon_eval`, `seon_context`, `seon_message`, `seon_attach`, `seon_done`, `seon_prove`), and `bin/check mcp` compares the tools the server lists with the table, never a count.

`:prove` runs the tests a branch's change reaches, once per branch and tx however many ask ([merging](merging.md#the-test-service)): it names an agent (its branch at its head) or main, and optionally the test namespaces.

- `:agents`: live agents and what is live on main (```seon.server/live-tasks```): each task running or with runs, newest first, by its summary (`seon.server/task-summaries`: execution, done, blocked-by, its runs, its failure), every other task counted by execution, and the form that lists them all.
- `:eval`: Clojure evaluated in a running agent's process (recorded on its branch, origin `:outside`) or as `"root"` in root's process, with `sys` bound to root (`seon.server/*sys*`). Both go through the one REPL path, `seon.repl/eval-string` ([processes](processes.md#the-agent-process)).
- `:context`: the request of the task an agent works as a model is sent it now, system prompt, its page and its conversation as one text (`seon.turn/context-block`; it names an agent or a task, attaching one if none works it), recorded with origin `:context`, a row of the agent's page like any evaluation ([render](render.md#the-page)).
- `:message`: the owner's words to a running agent (`seon.root/message!`, the page's message bar sends the same request): root delivers them, and the agent's next turn reads them in its block ([render](render.md)).
- Who may act on an agent: `bin/mcp` stamps every message with its session's client id (`"seon/client"`), and `:attach` records it on the run (`:seon.run/holder`). `:done`, `:eval` and `:message` on an agent whose run has a holder answer only that client, or a request that names the run's task (`task`); any other is refused, `:seon.server/held`, naming the agent, its task and the holder, and the run stays open (```seon.server/held```). One session's `seon_done` once named another session's agent and ended its run red. A request with no client (`bin/ask`, a test) attaches with no holder.
- `:attach`: root starts an agent on the task's branch with model `"outside"`, so no turn loop runs in it, and answers its id once the agent is ready (its hello), or the end it met first, which is the run's death ([root](root.md#holders-and-refused-spawns)); a task whose run is live answers that run's agent, with `:shared true`: the caller has the branch, shared with whoever attached it, and that agent lives until its `seon_done` or an end. A branch another live agent holds is `seon.root/spawn!`'s refused request, answered as a value (it was a server defect), naming the agent, the task it works and its run (```seon.server-test/an-attach-gives-the-caller-the-branch-or-names-who-holds-it```). A prove never ends the agent it proves (```seon.server-test/a-prove-never-ends-the-agent-it-proves```): a `seon_done` does, when its run is judged, held or not. `:fresh true` resets the task (its `:seon.task/branch` a new one cut from main, so the reconciler kills the run on the old branch as its env changed; no session key, so the conversation starts empty; the old branch and runs stay). `:from` forks a live agent through `seon.root/clone!` (the clone's branch is cut after its parent's writes commit), working a sibling task with the same plan and proofs; the clone has its own key, since an agent's entity on main is its key's and two live agents of one key would overwrite each other's facts. The fork's task reaches its branch when it begins its run (`seon.agent/begin-run!` writes a task its branch lacks as main declares it).
- `:prove`: the tests a branch's change reaches, run once per branch and tx however many ask, through the one test service (`seon.prove`, [merging](merging.md#the-test-service)); it names an agent's branch, else main.
- `:done`: the agent ends its run as a turn loop does (```seon.turn/hand-back!```: its proofs run, its end `:green` or `:red` with the reasons, committed on its branch), then the run goes to the reconciler's `:judge` port and is judged ([root](root.md#runs-and-judging)). It answers the verdict once main holds it (```seon.server/verdict```, waiting on the fact with `seon.root/await-db`, a watch on main's connection, no clock): the run's status (`:done` or `:merged` when the done rule had no reason, `:closed` with its task held when it had some), outcome and reason, and for a held task the failure the judge wrote, which names the reasons; a defect of the reconciler that stopped the judge answers as that defect. It waits as long as the judge does (the run's proofs, a gate, a merge: minutes), so a client's read timeout must allow it: the one-line `nc -w 10` of AGENTS.md section 6 is for the quick ops; `bin/mcp` sets none.

```seon.server/answer``` dispatches one EDN request to its op's method of ```seon.server/op-answer```; an unknown op is the `:default` method's, the one error map. A line that does not read, or an op that throws, answers that request as the typed `:seon.server/defect`: the server is an entrant boundary ([failure points](failure-points.md)).

## MCP

MCP is the same table seen through JSON-RPC: ```seon.server/mcp-reply``` answers `initialize`, `ping`, `tools/list` (each op as the tool `seon_<op>`) and `tools/call`, and a method or tool it does not know is the JSON-RPC error that names the ones it has.

A tool's text is what a model should read: `seon_context`'s is the block itself, an evaluation's text is its response as the one printer prints it (`seon.print/response-text`), an error is its render, and anything else is the whole value by the one printer ([render](render.md)). `seon.server/protocol-versions` lists the protocol versions it answers.

`bin/mcp` is the stdio relay a client runs: stock perl, a few MB, one connection per message to the port in `runs/root.port`, so a root restarted between calls (`bin/root next`) costs the client nothing. A message root does not answer (none running, not listening, died mid-request) gets a JSON-RPC error saying why. `seon.check/mcp-proof` (`bin/check mcp`) proves it end to end from a separate process, with the relay's footprint under `:seon.config.machine/relay-mb`.

Working a task this way is the turn loop's path with the model outside: [turn](turn.md#an-outside-agent).
