# Live drive spec — 2026-08-13

The pre-authorized live drive (README spine step 3; ruling 26 of the
[design-ideas ledger](design-ideas-ledger-2026-08-13.md) moved it AHEAD
of W3–W5): real DeepSeek agents on the current system, measured, so the
open pricing and budget decisions are made against evidence instead of
taste. The owner's framing governs: the goal is GOOD DERIVED CONTEXT —
the drive measures fidelity first, cost second.

## Drive series (owner deferred to orchestrator judgment, 2026-08-14)

As many drives as the measurements need are authorized. **Drive 1**
(first, on the proven machinery): the contracted-function task against
a real `my.plan` with `:about` refs, a mid-session message, one
rebirth, settle — zero shared-tree risk. **Drive 2** (after
green-to-install lands): a real filed issue, the agent's edits gated by
tests before landing. Later drives iterate on what the measurements
surface.

## Preconditions (in order, all required)

1. The [walk-history wedge blocker](../../seon/issues/walk-neighborhood-under-history-can-wedge-cluster-stop.md)
   is fixed with its class regression (entity-flag-deletion lane).
2. R3 store layout is committed with its isolated-root live proof.
3. One `bin/seon reset --force` of the shared root (also retires the
   stale default JVM). Fresh `bin/seon status` green.
4. The [live-pull blocker](../../seon/issues/generated-opening-live-pull-does-not-return-after-help.md)
   is diagnosed against the fresh root — fixed if the cause is in
   reach, or its reproduction conditions named exactly so the drive
   avoids conflating it with generation behavior.
5. The render-cost recording seam is landed (ledger 24) so the drive
   accumulates per-(shape, profile) token facts as it runs.

## Shape

- **Model**: flash only (`deepseek-v4-flash` through the one `seon.ai`
  owner); cheapest probe first; no paid escalation without the owner.
- **Cluster**: a fresh scratch cluster on the reset root — never
  someone else's; the drive's episode facts are PRESERVED afterward
  (no sweep) as the session's primary evidence.
- **Driver**: one lane drives a real generated-opening evolving
  session: boot → generated opening → a small task exercising my.plan
  with `:about` refs (so T3 membership and first-use demonstrations
  appear live) → inbound messages mid-session (so delta generation and
  basis-t rendering appear live) → one rebirth (compaction) → continue
  → settle.
- **Observer**: an INDEPENDENT second lane (never the driver) reading
  the database facts and the web UI while the drive runs; files one
  issue per ugly render, wrong fact, hang, or surprising cost — the
  standing ugly-output order applies with fresh eyes.

## Measurements (recorded in the drive report, all from facts)

1. Opening composition: total estimated tokens; closure vs
   beyond-closure split; per-entry shape and cost (the new cost facts).
2. The live pull under named conditions: wall time and call counts
   against the [attribution baseline](../research/live-pull-attribution-2026-08-13.md).
3. Delta economics: for each mid-session change, the delta the
   generator emitted vs what the full re-render would have cost — the
   evidence for the parked pricing decision (ledger #8: owner leans
   full-then-diffs-until-compaction).
4. Rebirth in vivo: lived vs reborn tokens, determinism, and WHAT THE
   AGENT DID NEXT — did behavior survive compaction (the fidelity
   check that ratios cannot show).
5. Agent behavior against the context: did it replay shown forms, use
   `doc`/`dir`, follow the first-use demonstration, operate my.plan,
   anchor on rendered basis-t values.
6. Cost: total provider spend for the session (flash pricing;
   peak-hour rule respected).
7. **Basis-`t` display comprehension** (owner, 2026-08-14): does the
   agent anchor its own temporal forms on the rendered `t=<basis>`
   values, and does the tag-before-value line read unambiguously to a
   live model — evidence for keeping or reshaping the display.
8. **The #11 case measurement** (owner, 2026-08-14): how often does the
   live planner name a resolvable subject in item TEXT while omitting
   the structured `:about` ref? That frequency decides auto-derived
   suggestions — ruled D-for-now (explicit-only, demonstration
   teaches); adoption would be B (suggest-and-confirm in the `plan!`
   result) or C (read-side weaker membership signal, budget-ordered
   after explicit refs), never silent auto-attach.

## Acceptance / stop

- Every turn bounded by the shipped config bounds; the observer stops
  the drive on any unbounded wait (that is a new wedge issue, not a
  retry).
- The drive is DONE when one full evolve→rebirth→continue cycle has
  clean measurements, not when the numbers look good — bad numbers are
  a successful drive with valuable evidence.
- Deliverables: the drive report under `../research/` with every
  measurement; preserved episode facts named by cluster + basis; the
  owner reviews before any pricing/budget ruling is proposed.
