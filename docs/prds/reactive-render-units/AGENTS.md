# Datahike reactive reads — working context

This PRD owns Datahike's general reactive-read and lazy immutable-result
protocol. Page rendering, ordinary agent views, canvas/context surfaces,
debug, and `/data` are consumers. Read [[roadmap]], architecture UI and
context, the `datastar-web-ui` skill for the page consumer, and the closest
source authorities before research or code. Use `data-oriented-clojure`
before the plan and `datahike` for every read, parser, cache, database value,
and committed-report assumption.

Begin with an exact dependency ledger for Datahike indexes/listeners, SCI,
ClojureScript/Shadow analyzer behavior, Datastar/idiomorph, Hiccup rendering,
gzip/SSE, token estimation, and any proposed bounded cache. Record selected
versions/SHAs, `reference-code/` paths, and idiomatic current call sites. The
existing runtime-reliability cache, routing, allocation, and root audits are
inputs, not authority over current source.

Datahike's execution-aware parsed read plan is correctness authority. Declared
source keywords may rank focus/recency candidates but never veto actual read
evidence. One reactive registration owns its last delivered Clojure value,
dependency plan, active evaluation, newest pending database value, equality
suppression, and final-consumer cleanup. Do not add a page-specific semantic
parser, second cache, renderer-authored cache API, or cache mutation on write.

Datahike's bounded weighted cache owns immutable eager results at exact database
source identities. Reactive registrations retain only live delivery state;
closed registrations do no query, SCI, Hiccup, serialization, or token work
and must not pin obsolete database values. Clojure `=` is semantic equality;
hashes are accelerators only.

Research belongs in `research/`; current source/gap/order and graduation proof
belong in [[roadmap]]. Default-cluster proof precedes any ACME coordination.
