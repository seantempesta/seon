# Dynamic context and HTML Canvas as a UIX layer

> **Version placement (added 2026-05-23).** When this research
> graduates to a PRD, the surface lands across the
> agent-runtime tracks like this:
>
> - **v1 (MVP track)**: AI surface only, six section composer
>   joined into `:seon.turn/prompt-text`. HTML surface stays
>   whole-tile per agent (one `:seon.render/html` slot, already
>   live in V0 via `seon.web.broadcast`). See v1.md §5.4.
> - **v2 (MVP track)**: Per-section HTML composer mirror.
>   Section fns grow their return map with
>   `:seon.render/hiccup` alongside v1's `:seon.render/text` —
>   one fn per section, multiple output surfaces. **No new
>   `:seon.ctx/*` slot.** Six default sections in
>   `seon.render.default` grow hiccup output. AI-only sections
>   hit the fallback (wrap `:seon.render/text` in `<pre>`).
>   Plus the per-entity Malli-specificity dispatch the JVM
>   side already runs. See v2.md "Per-section HTML composer"
>   + "Per-entity dispatch".
> - **v2/v3**: `:seon.render/canvas` as the third surface —
>   sections grow `:seon.render/canvas` in the same return map.
>   Same pattern, no new slot. Default canvas-emitting sections
>   + the webview-side replay JS land when this doc becomes a
>   real PRD with concrete first views.
> - **Platform track Phases 8-10**: cross-platform delivery
>   (Tauri desktop shell pointing at the pod's loopback,
>   LAN/Tailscale remote access, mobile pod-in-webview). The
>   webview is the consumer of whichever surfaces are wired —
>   no platform work blocks Canvas, no Canvas work blocks
>   platform.
>
> Multi-agent + multi-view are **architectural givens, not
> future work**: V0 already iterates per-running-agent in
> `seon.web.broadcast`, fans out to all open SSE connections,
> and morphs per-agent tiles independently by id. Every version
> below preserves that — no plan calls for global rendering or
> single-view assumptions.

Two design questions that turn out to be the same question wearing
different clothes. First: how should the agent's rendered context be
produced — by hand-composing named sections, or by letting the graph
pick a renderer from data shape alone? Second: should HTML Canvas
join the list of surfaces a renderer can target?

The short version: start with the simple, hand-composed model that
the v1 spec already specifies. Treat shape-driven auto-discovery as
an opt-in second tier — the same dispatch idea, but acting on the
section's data instead of the agent's hand-picked symbol. Canvas
slots into this layering as another output key alongside
`:seon.render/ai` and `:seon.render/html`; it does not replace HTML
and it does not force a choice of dispatch tier.

## TL;DR

- **The simple ctx model is already specified and partly built.**
  v1 says context is `fn(DB state)`: each agent owns a vector of
  `:seon.ctx` section entities, each names a `:seon.ctx/fn` symbol,
  the composer resolves and calls them in priority order, joins the
  strings. The agent picks the section fns.
- **The advanced model is the renderer-discovery algorithm already
  shipping on the JVM side** (`src/seon/render.clj`). Given data and
  a target output key, query the code graph for functions whose
  required input keys are a subset of the data; rank by specificity;
  namespace proximity tiebreak. The graph picks the section fn.
- **They layer cleanly.** The simple model calls section fns by
  symbol. A section fn can choose to delegate to the discovery
  algorithm — `(render entity :seon.render/ai)` — and let the graph
  resolve the most specific renderer for whatever shape `entity`
  happens to have. v2.md already describes this as the per-entity
  dispatch extension.
- **Canvas joins the list of output keys.** `:seon.render/canvas`
  alongside `:seon.render/html` and `:seon.render/ai`. The dispatch
  story does not change; only the return shape does. Canvas is one
  more thing renderers can produce, not a new architecture.
- **Recommended starting position.** Ship the v1 simple ctx model
  end-to-end. In parallel, prototype a single Canvas-rendered view
  in the Tauri shell (the code-graph visualizer is the natural
  candidate) and let it consume the same Datahike state the
  Datastar/SSE pages already read. Defer per-entity discovery and
  generalized Canvas-shape dispatch until the simple pieces are in
  agents' hands.

## 1. The simple position: ctx as fn(DB state)

v1.md §1 puts it directly:

> The rendered prompt the LLM sees each turn is **derived freshly
> from current DB state** by running the section fns. It is not a
> transcript that grows; it is a projection.

The data model (v1.md §2.1):

```clojure
::seon.agent/ctx [:vector :seon.db/ref {:seon.db/component true}]
;; → :seon.ctx entities, ordered by :seon.ctx/priority

::seon.ctx/name     :keyword
::seon.ctx/priority :long
::seon.ctx/fn       :symbol   ; e.g. 'seon.agent/system-section
```

The composer (v1.md §5.3) pulls the agent's `:seon.agent/ctx`,
sorts by priority, resolves each `:seon.ctx/fn` symbol, calls it
with `{:seon.db/db db :seon.agent/id id :seon.agent/ctx-entity section}`,
joins the non-blank results with blank-line separators, and writes
the joined string to `:seon.turn/prompt-text` on the open turn.
That string is the prompt the LLM sees.

Six default sections ship in v1: `system`, `messages`, `current-ns`,
`warnings`, `recent-evals`, `prompt`. Each is a plain function in
`seon.agent` taking the input map and returning a string. Empty
string omits the section.

Three things are load-bearing in this design:

1. **The agent owns its layout.** `:seon.agent/ctx` is component-owned
   by the agent entity. Two agents in the same pod have completely
   independent layouts (commit `606e2d2` made this explicit by
   moving section ownership onto the agent record).
2. **Layout is data, not code.** Changing what the LLM sees on the
   next turn is a transact: swap a `:seon.ctx/fn` symbol, change a
   `:seon.ctx/priority`, retract a section, add a new one. The
   agent can do this from its own REPL.
3. **The function is a string-builder.** The contract is
   `input-map -> string`. Composition is concatenation. Failure is
   "empty string, skip the section."

What is implemented today (commit `b5054d0`):

- `seon.render.cljs` (the CLJS dispatch surface) is in place. It
  exposes `ai-render` and `html-render` against per-agent slot
  symbols, with `resolve-symbol` walking globalThis + a placeholder
  bootstrap-compile-state path.
- The render contract on the CLJS side currently registers
  `:seon.render/ai` as `[:fn symbol?]` — function symbols only, no
  literal strings. The dispatcher falls through to a `pretty-ai`
  default if the slot doesn't resolve.
- `seon.agent.cljs` ties the composer call into `run-turn!`. The
  agent record carries a single `:seon.render/ai` slot today; the
  six-section composer specced in v1.md §5.2–§5.3 is the work item
  this part of the spec is pointing at.

So today's runtime is a degenerate case of the v1 design — one slot
instead of a vector of sections. The v1 work is filling in the
vector and the six default section fns. No new mechanism, just more
of it.

## 2. The advanced position: render by data shape + auto-discovery

The JVM side has been running a different model in production. From
`docs/seon/concepts/renderer-discovery.md`:

> Renderer discovery is a zero-registration pattern for connecting
> data to visualization. A render function declares what data it
> needs (input keys) and what it produces (`:seon.render/html` or
> `:seon.render/ai` in the output schema) via standard
> `:malli/schema` metadata. The code-graph scanner extracts this
> metadata and indexes it in Datahike. At render time, a specificity
> algorithm finds the best match.

The algorithm (paraphrased from `src/seon/render.clj`):

1. Query the code graph for functions whose output schema contains
   the target format key (`:seon.render/html`, `:seon.render/ai`,
   eventually `:seon.render/canvas`).
2. Filter to candidates whose required input keys are a subset of
   the keys present in the data being rendered.
3. Rank: most required keys matched wins. Tiebreak by namespace
   proximity (same ns → `.render` child → sibling → distant), then
   alphabetical.

The differences from the simple position are pointed:

| Dimension | Simple (v1) | Advanced (M4, JVM today) |
|---|---|---|
| Who picks the function | The agent (via `:seon.ctx/fn` symbol) | The graph (by input-key subset + specificity) |
| Registration | Transact a section entity with a symbol slot | Author a fn with the right `:malli/schema`; scanner indexes it |
| Failure mode | Symbol doesn't resolve → pretty-print floor | No candidate found → fallback (pprint-clipped) |
| Composition | Concat strings from priority-ordered sections | Per-piece-of-data dispatch, called from inside a renderer |
| Where it lives today | CLJS pod, partly built | JVM `seon.render`, in production for HTML pages |

The advanced position is what powers the namespace-page renderer on
the JVM dashboard: data lands at a route, the renderer looks at its
keys, picks the most specific match. The agent never has to know
"the render fn for a workout is `seon.health.workout.render/workout-view`."
The graph knows. The agent just hands over the data.

v2.md §"Per-entity dispatch" makes the bridge explicit:

> Section fns can `(render entity)` and get the most specific
> renderer for whatever shape `entity` has. Strictly additive —
> section fns still return strings. … V2 lifts that dispatch into
> the CLJS pod.

That is the layering point — the advanced model isn't a replacement,
it's a helper a section fn can opt into.

## 3. The layering

The two positions are not in tension when you frame them as two
levels of dispatch:

1. **Outer dispatch (always the simple model).** The agent's ctx is
   a vector of named sections. Priority order is data. The composer
   resolves the section's `:seon.ctx/fn` symbol and calls it. This
   layer never changes.

2. **Inner dispatch (opt-in, advanced).** A section fn can choose
   to compose its result from per-entity renderers. Instead of
   writing the formatting by hand, it pulls the entities it wants
   to surface and calls `(render entity :seon.render/ai)` for each.
   The graph picks the best renderer per entity by shape.

A concrete sketch — `recent-evals-section` today (v1.md §5.2)
hand-formats each eval with `format-eval-row`. The advanced version
would delegate:

```clojure
;; Simple
(defn recent-evals-section [{:seon.agent/keys [id ctx-entity]}]
  (let [n     (or (:seon.agent/n ctx-entity) 20)
        evals (seon.agent/evals {:seon.agent/n n :seon.agent/id id})]
    (str "<recent-evals>\n"
         (str/join "\n\n" (map format-eval-row evals))
         "\n</recent-evals>")))

;; Advanced (opt-in)
(defn recent-evals-section [{:seon.agent/keys [id ctx-entity]}]
  (let [n     (or (:seon.agent/n ctx-entity) 20)
        evals (seon.agent/evals {:seon.agent/n n :seon.agent/id id})]
    (str "<recent-evals>\n"
         (str/join "\n\n"
           (for [e evals]
             (:seon.render/text (render/ai-for-data e))))
         "\n</recent-evals>")))
```

The outer dispatch never knew anything changed. The advanced inner
dispatch can be added on a per-section basis when it earns its keep
— a section that shows mixed entity types (eval / message / warning
/ test result) benefits the most.

A third toggle worth naming: **enable-discovery-default**. Per-agent
on the agent entity:

```clojure
::seon.agent/auto-discover? :boolean {:optional true}
```

When `true`, the default `pretty-ai` floor inside `ai-render` runs
the discovery query first and only falls through to pretty-print if
no candidate matched. The simple section fns still win when they
explicitly resolve. The discovery layer is a more-useful default
for slots the agent hasn't populated.

Three properties of this layering matter:

- **Simple ships first; advanced is additive.** The advanced layer
  cannot ship without the program-graph scanner storing
  `:seon.render/*` output keys in the agent-side Datahike (v1 ships
  `:seon.fn` / `:seon.schema` / `:seon.ns` entities but the
  reference-graph / output-spec extraction is on the v2.md list).
  Until that exists, the discovery query has nothing to query.
- **Advanced is a strict superset of simple.** Anything the agent
  could express by transacting a `:seon.ctx/fn` symbol, the advanced
  layer can express by authoring the function with the right
  `:malli/schema` and letting the graph find it. The agent retains
  the symbol-pinning escape hatch for cases where it wants exact
  control.
- **The CLJS pod and the JVM dashboard share one model.** The same
  algorithm that resolves a namespace-page renderer on the JVM
  dashboard resolves an inline entity renderer inside an agent's
  context section. One mechanism, two consumers.

## 4. HTML Canvas as a Tauri UIX layer

Canvas in a Tauri webview is a real surface with real tradeoffs.
The relevant facts:

**Webview backing varies by platform.** Tauri 2 ships system
webviews — WebView2 (Chromium-based) on Windows, WKWebView on
macOS / iOS, webkit2gtk on Linux. Canvas 2D is universally
supported. WebGPU shipped across all four engines through 2025–2026
(Chrome / Edge 113, Firefox 141 on supported platforms, Safari 26),
but webview availability lags browser availability — WebGPU in
WebView2 in particular has been an open Tauri issue
(`tauri-apps/tauri#6381`). Plan for Canvas 2D as the baseline; treat
WebGPU as a per-platform opt-in.

**Hardware acceleration is per-webview.** There's a long-standing
report that WebView2 doesn't always GPU-accelerate Canvas or CSS
filters the same way the standalone browser does
(`tauri-apps/tauri#4891`). For modest dashboards this is invisible;
for sustained 60fps animation across thousands of shapes it bites.

**Canvas loses semantic HTML.** This is the real architectural cost.
A `<canvas>` element to a screen reader is a blank rectangle. The
mitigations are well-trodden: fallback DOM inside the `<canvas>`
tag, mirror keyboard-actionable elements as off-screen native
buttons, `role="img"` + `aria-label` for static visualizations.
Chart.js documents the pattern; tldraw chose the opposite
architecture (DOM-all-the-way-down on top of a "canvas surface")
specifically to keep semantics for free.

**Tauri IPC is async message passing.** Mouse, keyboard, touch,
file-drop — all routed through `invoke()` or the event system as
JSON-serialized messages. There is no zero-copy framebuffer
hand-off; the Rust side either renders to a window the webview
doesn't own (a separate Tauri window) or hands the webview the
data and lets the webview do the drawing.

**Datastar / SSE plus Canvas is a hybrid, not a fight.** Datastar
mutates the DOM via SSE-streamed HTML fragments. Canvas inside one
of those fragments is fine — the `<canvas>` is just an element; the
SSE stream can push a `data-on-load` directive that calls a JS
function which redraws. The agent's Datahike state still drives
everything; the difference is what the renderer emits at the leaves.

The honest comparison:

| Surface | Best at | Cost |
|---|---|---|
| Datastar / SSE HTML | Forms, tables, structured text, links, the bulk of any dashboard | Layout is browser-driven; bespoke spatial layouts are awkward |
| Canvas 2D | Custom spatial layouts, free-drawing, dense visualization, drag-zoom-pan, generative visuals | Accessibility work is on you; layout primitives are pixels |
| WebGPU | Volumetric / 3D, very-large-scale particle / graph visualizations | Platform support thin in webviews; complexity ramp is steep |

Most of the Seon dashboard wants HTML. A few corners — code-graph
visualization, the Primer's spatial scenes, a future drag-rearrange
of section ordering — want Canvas. The answer is "both, side by
side, picked per view," not "choose one."

## 5. Canvas as a render-shape target

The renderer dispatch model already accommodates new output keys.
Today the JVM scanner indexes `:seon.render/html` and
`:seon.render/ai`. Adding `:seon.render/canvas` is the same shape:

```clojure
;; Schema for the canvas render result
(schema/register! :seon.render/canvas
  [:map
   [:seon.render.canvas/w           :int]       ; logical width
   [:seon.render.canvas/h           :int]       ; logical height
   [:seon.render.canvas/dpr         {:optional true} :double]
   [:seon.render.canvas/commands    :seon.render.canvas/command-vector]
   [:seon.render.canvas/interactive {:optional true}
    [:vector :seon.render.canvas/hit-region]]])

(schema/register! :seon.render.canvas/command-vector
  [:vector :seon.render.canvas/command])

(schema/register! :seon.render.canvas/command
  [:or
   [:tuple [:= :fill-rect]    :int :int :int :int :string]
   [:tuple [:= :stroke-rect]  :int :int :int :int :string :int]
   [:tuple [:= :text]         :string :int :int :string :string]   ; text x y font fill
   [:tuple [:= :path]         :seon.render.canvas/path-spec :string]
   [:tuple [:= :image]        :string :int :int :int :int]          ; blob-ref x y w h
   ...])
```

Two reasons to make commands data, not raw JS calls:

1. **The agent lives in the WASM pod.** The pod can't reach into a
   webview canvas context directly. A data-shaped command list is
   serializable across the WIT host boundary and replayable by the
   webview-side JS that owns the canvas. (The Tauri host receives
   the command list over its event bus and hands it to the webview;
   the webview JS does the `ctx.fillRect(...)` calls.)
2. **The same command list is a blob.** v2.md's blob subsystem will
   store turn-prompt blobs and large eval results; a canvas
   command list for "what the agent drew on turn 142" persists for
   free, replays for free, diffs for free.

A render function then looks identical to the HTML pattern in v1:

```clojure
(defn workout-canvas
  {:malli/schema
   [:=> [:cat [:map
               [:seon.health.workout/exercises ...]
               [:seon.health.workout/date ...]]]
        [:map [:seon.render/canvas :seon.render/canvas]]]}
  [{:seon.health.workout/keys [exercises date]}]
  {:seon.render/canvas
   {:seon.render.canvas/w 800
    :seon.render.canvas/h 400
    :seon.render.canvas/commands
    (concat
      [[:fill-rect 0 0 800 400 "#0e0c0a"]
       [:text (str date) 20 30 "12px monospace" "#d6cdb4"]]
      (exercise-rows exercises))}})
```

Inside the v1 layering: the agent can hold an `:seon.render/canvas`
slot on the agent entity the same way it holds `:seon.render/ai`.
The dispatch model is identical (`canvas-dispatch` mirrors
`html-render`). The advanced inner dispatch — graph picks the
most-specific canvas renderer for a piece of data — works the
moment the scanner indexes the new output key.

Interactivity travels back over the IPC channel. Pointer events
inside the canvas element fire JS handlers that map to hit regions
in the `:seon.render.canvas/interactive` list and forward
canonicalized events (`{:seon.event/kind :click
:seon.event/target :workout/squat-set-3 ...}`) to the agent via
the same Datahike-write path Datastar uses today. The agent's
listener wakes; the next turn renders with the new state.

## 6. Advanced rendering capabilities — what Canvas unlocks

Five concrete uses that map to things either spec'd or already in the
repo:

1. **Code-graph visualizer.** The program-graph entities (v1 §2.2:
   `:seon.ns`, `:seon.fn`, `:seon.schema`, eventually `:seon.fn/refs`
   for edges) are the obvious first canvas view. Nodes laid out by
   force-directed or hierarchical algorithm, edges drawn as bezier
   curves, namespace clusters as translucent regions, hover to see
   the source. The dashboard renderer queries Datahike, the canvas
   draws the result, the user pans / zooms / clicks. The same code
   the agent uses to introspect its own callable surface becomes a
   thing the user can stare at.

2. **Live data dashboards.** Anything that wants ticks per second
   without a full DOM diff — trading P&L, system metrics, the
   shape-graph as it grows. SSE pushes the new datapoint, a
   canvas-side handler appends to a sparkline. The renderer
   abstraction still owns the look; the canvas owns the cycle.

3. **Spatial layouts for the Primer.** The Primer (Sean's
   niece/nephew tutor) needs scenes, characters, simple animation —
   things HTML+CSS can do but Canvas does cleanly. The agent
   constructs `:seon.render/canvas` command lists per scene; the
   webview replays them. Touch events come back as canonical
   Datahike writes the agent's narrative loop can read.

4. **Direct-manipulation interactions.** Drag-rearrange the agent's
   own section ordering — pick up a section tile, drop it elsewhere,
   the `:seon.ctx/priority` of every affected ctx entity updates in
   one tx. Same pattern works for any user-arrangeable surface.
   HTML+CSS drag/drop exists but is brittle across platforms;
   canvas hit-regions are uniform.

5. **Generative / ambient visuals.** A status display that conveys
   the agent's load via slow-moving color, particle density, or
   waveform. Cheap, expressive, not load-bearing. The kind of thing
   that gives the agent a body in the UI without becoming a
   chatbot avatar.

The thread running through all five: the agent does not need to
become a graphics engineer. It returns a data shape; the dispatch
model picks the renderer; the renderer turns the shape into
commands; the canvas replays the commands. Same as HTML, different
leaf.

## 7. Recommended starting position

Build the simple ctx model end-to-end first. Five visible steps:

1. **Fill out `:seon.agent/ctx` as a vector of section entities.**
   v1.md §5 is the spec; the work is wiring six section fns +
   transacting six ctx entities into the agent record on `create!`,
   then changing the composer to walk them. The CLJS `ai-render`
   stays the outer dispatcher.
2. **Ship the six default section fns** (`system`, `messages`,
   `current-ns`, `warnings`, `recent-evals`, `prompt`). String in,
   string out. No discovery, no graph queries beyond the obvious
   pulls v1.md already specifies.
3. **Verify the spec on the live pod.** The risks in v1.md §11 are
   still real (defn-name extraction across all legal shapes,
   intra-tx lookup refs in `bootstrap.edn`, ALS propagation in
   wasm-rquickjs). Each gets its 15–30 minute REPL probe before its
   feature commits.
4. **Land the program-graph output-key index.** The v1 scanner
   stores `:seon.fn` entities with their `:source`; add a parse
   step that extracts the `:malli/schema` output map's `contains`
   keys and stores them as `:seon.fn/output-keys`. This is what
   the discovery query reads.
5. **Then, and only then, ship per-entity dispatch.** Port
   `find-renderer` from `src/seon/render.clj` into the CLJS pod.
   One section fn (likely `recent-evals-section`) switches to the
   advanced inner dispatch as the first proof. Measure whether the
   agent's prompt quality improves.

Canvas runs as a parallel track, not blocked on the above:

6. **One Canvas view in the Tauri shell.** The code-graph
   visualizer is the highest-leverage candidate — it reads the
   same Datahike state the namespace dashboard already reads, it
   has clear visual value HTML can't easily match, and it
   exercises the IPC path (click a node → emit an event → SSE
   refresh).
7. **Define `:seon.render/canvas` as a command-list schema.** Per
   §5. The renderer-discovery scanner picks up the new output key
   without code changes once the schema is registered.
8. **Defer general Canvas inside agent ctx** until at least one
   user-facing Canvas view is running. The agent's prompt is
   text; emitting canvas commands as `:seon.render/ai` is a
   future, not a starting point.

Tradeoffs of starting here:

- **Pro: the agent gets real value on turn one.** Six sections
  beats one slot. The user gets the rendered prompt and the
  introspection surface immediately.
- **Pro: Canvas validates the Tauri shell without coupling to ctx.**
  A code-graph viewer is interesting on its own; if the dispatch
  layering doesn't ship, the viewer still works.
- **Con: the advanced dispatch story stays a hypothesis longer.**
  We can't validate "the agent prefers shape-discovered renderers
  over hand-picked ones" until the index is in place.
- **Con: two separate Datahike read paths** (JVM dashboard reading
  the seon DB; CLJS pod reading its own agent DB) live in parallel
  longer. The Tauri Canvas view, for now, reads whichever DB its
  Rust host is bound to. The unification question is real but not
  blocking.

The smallest experiment that validates the layering end-to-end:
one section fn using the advanced inner dispatch on the CLJS side
+ one Canvas view on the Tauri side reading the JVM-side
Datahike. If both work and feel consistent, the design layers as
described.

## 8. Open questions

- **Canvas-in-WASM-pod feasibility.** The pod runs in wasm-rquickjs
  inside wasmtime. It can emit data — the canvas-command list is
  data — but it cannot reach DOM. The host (Rust → Tauri webview)
  must own the canvas element and replay commands. The open
  question is the latency / bandwidth budget for command-list
  shipping during interactive use. Probe: 60fps panning of a
  10,000-node graph over the Tauri event bus. If the event bus
  pinches, the answer is "canvas-command stream over a custom
  Tauri protocol with binary encoding" — not architecturally
  different, just heavier.
- **Accessibility as a first-class concern.** Any Canvas view that
  matters needs the off-screen-DOM fallback pattern. Should the
  `:seon.render/canvas` schema require an `:seon.render/html`
  sibling for accessibility, or is that a per-view decision? Lean
  toward "required for any view shipped to end users; optional for
  agent-internal visualizations."
- **WebGPU vs Canvas 2D.** WebGPU's webview support is uneven
  enough in 2026 that Canvas 2D is the default. Worth re-checking
  in 6–12 months; the API is more pleasant for any view that wants
  shaders, and Safari 26 / Chrome 121+ already ship it. For now,
  scope to 2D.
- **Datastar / SSE coexistence with canvas redraws.** Datastar
  mutates the DOM; canvas redraws are independent. The boundary is
  clean as long as canvas-side state lives in Datahike (one source
  of truth) and the SSE channel ships only the events the canvas
  side then re-reads. A muddier design (SSE pushing partial draw
  commands inside HTML fragments) would invent a new protocol; not
  recommended.
- **Per-agent vs per-pod canvas.** If two agents are running in the
  same pod, do they share one canvas surface or get separate
  windows? Today the CLJS pod is single-agent in practice; the
  multi-agent story implied by v1's `:seon.agent/ctx` being
  per-agent extends naturally to "each agent gets its own
  canvas-rendered ctx view in its own Tauri window or tab."
  Deferred.
- **Where does the advanced output-key index live in the CLJS
  pod?** v1 puts `:seon.fn/output-keys` extraction on the v2 list
  (alongside `:seon.fn/input-spec` / `:seon.fn/output-spec` /
  `:seon.fn/refs` per v2.md §"Reference-graph attrs"). The
  per-entity dispatch in CLJS can't ship before that does. Worth
  noting the sequencing dependency loudly.
