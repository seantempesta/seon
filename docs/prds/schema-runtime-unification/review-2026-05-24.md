# Review of prd-draft.md (2026-05-24)

Reviewer posture: critical pass. Goal is to find issues, simpler representations, and missing dependencies — not endorse.

Reviewed against: `prd-draft.md` (v2), `agent-runtime/v1.md` §7, `agent-runtime/research/eval-batch-fragility-2026-05-23.md`, current `src/seon/eval.cljs` body. Cross-checked PRD claims against the source.

## TL;DR

The PRD is roughly correct in scope and aligned with v1.md after the rewrite. Six issues found, ordered by severity:

1. **Ordering bug in §6.4 boot sequence**: `(instrument/start!)` runs BEFORE `(replay-program-graph!)`. Replay re-binds globalThis vars for every fn it replays — clobbering the instrumentation wrappers from step 8. PRD's open question #6 already flags this; the fix is to swap the order (instrument AFTER replay) or do `instrument/refresh!` at end. Pick one explicitly in the PRD body; don't leave as TBD.
2. **eval-batch fragility (a) is a prerequisite, not a sibling step.** The ALS-routed warning handler fix from `eval-batch-fragility-2026-05-23.md` MUST land before detect-and-tee modifies `eval-batch!` (PRD step 3), otherwise we layer new logic on a known-broken `set!`-based path. PRD §10 mentions it; should be a hard prereq, not a reference.
3. **`fn-schema/seed-from-db!` (boot step 7) has a chicken-and-egg with the eval-time global mutation.** `m/-register-function-schema!` mutates `-function-schemas*` which is a private atom; seeding from DB writes to it directly, fine, but then `(mi/instrument!)` reads it ONCE at step 8. Subsequent replay (step 9) re-defines globalThis fns. Subsequent agent eval re-defines globalThis fns. Both need to call `instrument-fn!` per-fn after each rebind. The PRD has this for agent eval (§6.3) but NOT for replay. Either replay calls `instrument-fn!` per fn after it succeeds, OR step 8 moves after step 9 + becomes the single global instrument pass.
4. **Tx-listener mirror path has a re-entrancy hazard NOT in the PRD's risk list.** When the agent calls `(schema/register! ::k v)` from inside `cljs.js/eval-str` (which is inside `eval-batch!`'s `with-tx-context`), the body transacts a `:seon.schema` entity. The listener fires SYNCHRONOUSLY on tx commit (per datahike JVM semantics; CLJS unknown — PRD already flags). The listener body calls `(swap! *schemas assoc k schema-edn-form)` — fine. BUT if the listener is naive and reads `:seon.schema/source` and EDN-decodes it, the decode itself doesn't have eval semantics, so the schema-as-data round-trips correctly. So this is not a hazard for `:seon.schema`. IT IS a hazard for `:seon.fn/malli-schema` — same listener pattern; the schema FORM in the EDN may reference unregistered keys, and `m/-register-function-schema!` accepts any value, but instrument-time validation runs `m/schema` which resolves refs. If a fn-schema references an as-yet-unregistered ::key, instrumentation throws. Order of writes within a tx matters; PRD doesn't address.
5. **`:seon.transient` auto-tag check is too narrow.** PRD §6.3 detects `(satisfies? IDeref value)` for new vars. But `(def !foo {…})` (a plain map) is ALSO transient state from the agent's perspective — the value is bound to a var that won't survive resume of just the source (the source IS in the DB, but `(def !foo {…})` literally re-creates the map on resume; the binding survives, the IDENTITY doesn't). Distinct concern from "atom that gets reset on resume" but easy to conflate. Recommend: tag everything that's NOT a fn (`:fn-var false` from analyzer) as transient. Atoms are a special case worth surfacing as `:kind :cache` vs plain refs as `:kind :other`.
6. **No probe yet of `d/listen!` semantics in datahike-cljs.** PRD §8 risk lists this; high-leverage probe before committing to the tx-listener architecture. Should be a step 0.

Plus 4 simpler representations / over-engineering call-outs in §B, and 3 missing dependencies in §C.

## A. Issues, severity-ordered

### A1. Boot-sequence ordering bug (§6.4 step 8 vs 9)

PRD §6.4 boot sequence:

```
7. (fn-schema/seed-from-db! conn)
8. (instrument/start! {...})    ← patches globalThis wrappers
9. (replay-program-graph! ...)  ← rebinds globalThis fns from :seon.fn/source

```

resume-findings §Q4 ordering (which the PRD adopts) is correct for the SHIPPED design (no instrumentation): replay re-defines fns; nothing to clobber. With instrumentation added, step 9 emits raw JS that overwrites step 8's wrappers. After replay, the var on globalThis is the bare fn, not the instrumented wrapper. **Functions defined in `:seon.fn` entities are NOT validated post-resume** unless we re-instrument.

PRD §9 question 6 mentions this. The PRD should pick a fix in the body:

- **Fix A (recommended): swap order.** Move `instrument/start!` to AFTER `replay-program-graph!`. One global pass over `-function-schemas*` (which was seeded in step 7) wraps all globalThis bindings, substrate AND replayed. Substrate bindings exist from the host bundle load; replayed bindings exist post step 9; both wrappable in a single pass at step 9.5.
- **Fix B: instrument per fn after replay.** In `replay-program-graph!`, after each `:fn` replay succeeds, call `instrument/instrument-fn!`. Doubles the work; preserves clean step boundaries. Worse.

Pick A. Update §6.4 in the PRD.

### A2. eval-batch fragility (a) is a hard prereq for step 3

PRD §10 cites `eval-batch-fragility-2026-05-23.md` as "cross-cutting concern; should land BEFORE step 3."

This is too weak. Read what (a) is: `raw-eval` does `set!` on a CLJS dynamic var without a binding frame. In single-agent v1 it's mostly harmless (one warning-handler at a time, the captured `prev-h` happens to be the original). In **multi-agent v1**, it's data loss + false negatives + false positives on the undeclared-var safety check.

The detect-and-tee change (PRD step 3) extends `eval-batch!`'s per-form loop. We are about to layer instrumentation reporter calls on top of the already-broken warning-handler code path. Even single-agent, an instrumented fn that throws during eval, when intersected with concern (a)'s `set!`/restore window, can scramble warning state in unpredictable ways.

**Make step 3 of the PRD's migration explicitly depend on the (a)-fix landing first.** Per `eval-batch-fragility-2026-05-23.md` §"Option 1" the fix is ~30 LOC + uses the same AsyncLocalStorage pattern as `seon.db/with-tx-context`. Pull it forward as step 0 (or 2.5, after the bundle add).

### A3. Instrumentation needs to be re-applied after EVERY new fn binding

§6.3 has the right shape for agent-defined defns: detect-and-tee runs per form; per-fn `instrument-fn!` wraps just the new one. But for **replay** (which bypasses `eval-batch!` and thus bypasses detect-and-tee, per resume-findings §Q5) — replay re-evals the source, globalThis fn gets rebound, no wrapping happens.

Coupled with A1, the fix is:

- Step 7 (`fn-schema/seed-from-db!`) populates `-function-schemas*` from DB.
- Step 9 (replay) re-evals every `:seon.fn/source`, rebinding globalThis. Each rebind is a bare fn.
- Step 9.5 (single `instrument/start!`) walks `-function-schemas*` and patches every globalThis binding to its wrapped version.

This is the same as Fix A in A1. State it once, in the PRD body.

For runtime additions (post-boot, agent eval'ing new fns): detect-and-tee's per-fn `instrument-fn!` per §6.3.

### A4. Tx-listener and fn-schema dependency order

PRD §6.1 install-registry-sync! mirrors `:seon.schema/source` writes into `*schemas`. PRD §6.7 adds `:seon.fn/malli-schema :string`. A parallel listener would mirror `:seon.fn/malli-schema` writes into `-function-schemas*`.

Consider a single agent eval that defines BOTH a new schema AND a new fn referencing it, in one batch:

```clojure
(do
  (schema/register! :alice.foo/n :int)
  (defn add-one {:malli/schema [:=> [:cat :alice.foo/n] :alice.foo/n]} [n] (inc n)))

```

Detect-and-tee writes both `:seon.schema` and `:seon.fn` entities, ideally in one tx. The listener fires once with both datoms. Order of listener handling matters:

- If `*schemas` is updated FIRST, then `-function-schemas*` and instrument, fine.
- If `-function-schemas*` is updated first and instrument fires before `*schemas` is updated, `mi/instrument!` calls `m/schema` on `[:=> [:cat :alice.foo/n] :alice.foo/n]`, which resolves `:alice.foo/n` against the registry → MISS → throw.

Mitigation: the listener processes `:seon.schema` writes BEFORE `:seon.fn/malli-schema` writes within a single tx. Either two listeners (registered in order) or one listener that partitions tx-data by attr and does schemas first.

Add to PRD §6.3 detect-and-tee section: "if the same tx writes both `:seon.schema` and `:seon.fn` entities, the listener processes schemas first."

### A5. `:seon.transient` heuristic is too narrow

PRD §6.3 auto-tags atoms (`satisfies? IDeref`). But the v1.md / reactive-context principle is broader: ANY `(def x val)` where `val` isn't a fn IS transient state. The DB has the source; on resume the source re-evals and produces a FRESH value. If the agent does `(def !cache (atom (load-data)))`, the atom binding is re-created on resume (fresh atom, fresh data — semantically a different identity).

**Two-tier heuristic:**

- `:fn-var true` (the analyzer flag) ⇒ persistent (this is what we're computing) — also persistent regardless: re-eval produces a fn that's the same as far as observers care.
- `:fn-var false` ⇒ transient. Subdivide by value type:
  - `(satisfies? IDeref v)` ⇒ `:kind :cache` (or `:counter` if numeric).
  - `(instance? js/Promise v)` ⇒ `:kind :connection` (loosely).
  - everything else ⇒ `:kind :other`.

§6.3 should describe this, not just the IDeref check. Render section then can collapse `:kind` clusters visually.

### A6. Datahike-cljs listener probe is a step 0 prereq

PRD §8 risk lists this; PRD §7 migration step 5 depends on it. Promote to step 0:

```
0. REPL probe (one session): write a :seon.schema entity; assert the listener
   callback fires synchronously post-commit. Verify tx-data shape matches JVM
   ({:tx-data [[e a v t added?] ...]}). Verify nesting/component-attrs are
   represented correctly. If divergence: fix before any other step.

```

Without this we're committing the whole architecture on an assumption.

## B. Simpler representations

### B1. Combine the two seeds

PRD §6.4 steps 5 + 7 are two passes ("seed *schemas from :seon.schema"; "seed -function-schemas* from :seon.fn/malli-schema"). One pass with a switch on which attr is present is simpler:

```clojure
(defn seed-runtime-from-db!
  [conn]
  (let [db @conn
        rows (d/q '[:find ?e ?key ?schema ?fn-sym ?fn-schema
                    :where
                    [?e :seon.db/id _]
                    (or-join [?e ?key ?schema ?fn-sym ?fn-schema]
                      (and [?e :seon.schema/key ?key]
                           [?e :seon.schema/source ?schema])
                      (and [?e :seon.fn/sym ?fn-sym]
                           [?e :seon.fn/malli-schema ?fn-schema]))]
                  db)]
    (doseq [[_ k s fn-sym fn-schema] rows]
      (when k (swap! *schemas assoc k (edn/read-string s)))
      (when fn-sym (let [[ns sym] (str/split fn-sym #"/")]
                     (m/-register-function-schema!
                       (symbol ns) (symbol sym)
                       (edn/read-string fn-schema)
                       {:metadata-schema? true} :cljs identity))))))

```

One query, one pass, one fn. Reduces §6.4 steps.

### B2. The listener installer can be the same fn

Same logic — one listener that handles both attrs, partitions tx-data accordingly. PRD §6.1's `install-registry-sync!` should also install the fn-schema sync. Single fn registration; single point of failure to debug.

### B3. `:seon.{ns,fn,schema}/substrate? :boolean` could be a single property of the source

PRD §6.7 adds `:substrate?` to three entity kinds. Same value across them. Alternative: a single `:seon.entity/source :enum [:substrate :agent :replay]` attr. More expressive (replay-generated entries — though resume-findings says we don't write those — and forward-compatibility for "pinned" or "published" states). Same storage cost; better query ergonomics.

Reject this if it conflicts with v1.md's schemas; I haven't checked.

### B4. Reporter contract should be a registered schema, not free-form ex-data

PRD §9 question 5 lists the namespaced keys; PRD §6.2 says the reporter throws ex-info. Make the reporter's ex-data shape a registered `:seon.dev.instrument/failure` map schema. Then the renderer can `(m/decode :seon.dev.instrument/failure data ...)` to get typed values, and any drift in the reporter's output is caught by the schema itself (turtles all the way down).

## C. Missing dependencies

### C1. Detect-and-tee already has a PR-in-progress at the analyzer-research

The analyzer-driven extraction research §Q9(a) IS the detect-and-tee implementation Sean's about to ship as MVP task #12 (per Sean's research-launch context). PRD step 3 SHOULD point at that as the implementation; this PRD adds the instrumentation hook ON TOP of it.

### C2. `seon.bootstrap` is partially specified

PRD §6.5 says "defer to v1.md §7.3." v1.md §7.3 specifies `bin/emit-bootstrap` reads source files, parses with rewrite-clj, emits the EDN. PRD says the emitter needs ALSO to extract `:malli/schema` metadata into `:seon.fn/malli-schema`. That's a 1-LOC addition to the emitter; specify it concretely (line where it goes in `bin/emit-bootstrap`) so MVP can plan it.

### C3. The `:seon.transient/at` attr

PRD §6.6 lists schema attrs but no `:at` (creation timestamp). Without it, agent-side transient entries have no ordering; can't tell "agent declared this 3 evals ago" from "agent declared this last turn". Add `:seon.transient/at :inst`.
