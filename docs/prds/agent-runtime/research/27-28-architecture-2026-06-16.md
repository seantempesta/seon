# #27 on-reply hook + #28 seed-dir — architecture

Design research for the two architectural asks in
[[docs/prds/agent-runtime/substrate-asks-batch-2026-06-16]]. Read-only;
every claim cites real source. Recommends one approach per ask.

## TL;DR

- **#27 fire-site:** `seon.agent/ask-and-eval!`, the SUCCESS branch
  (`src/seon/agent.cljs:1066-1069`) — the one place per turn that holds
  the raw assistant completion text (`reply-text`, derived in
  `ask-and-eval-reply!` at `agent.cljs:959`), the agent id, and the
  turn id, BEFORE the turn closes. Fire a registered hook fn there,
  async + fail-soft (fire-and-forget `js/Promise.resolve` with a
  `.catch` that only logs), passing `{:seon.agent/id … :seon.agent.turn/id …
  :seon.agent.reply/text …}`. The hook transacts its own rows
  (`:my.virtue/*` etc.) keyed to the turn; it is NOT awaited and CANNOT
  affect the turn outcome.
- **#27 panel:** a third pane in the consumer-shell grid
  (`inspector.cljs:1106-1111`) whose body is a section fn querying the
  rows the hook wrote — pure reactive-context, self-healing. The
  SVG-radar is hiccup `[:svg …]` produced by a `:my.virtue/*` fn living
  in the #28 seed dir, rendered through the same panel.
- **#28 seed-dir:** recommend the **recorded path** as the primary
  mechanism (`SEON_SEED_DIR`), with the already-designed **compiled
  path** (`SEON_EXTRA_SRC`, task #36) as the sibling for code a
  downstream wants instrumented/exemplar-grade. The seed dir's
  `*.cljs` files flow through `seval/eval-batch!` AS a system-origin
  boot turn (exactly like `creation-evals!`, `client.cljs:1842-1906`),
  so detect-and-tee persists `:seon.fn`/`:seon.ns`/`:seon.schema` rows
  that replay on every subsequent boot.
- **#28 ↔ #29 coordination:** seeding re-runs the file's forms on
  FIRST boot only; on later boots the rows are already present and
  REPLAY (not the seed eval) reconstitutes them. #29's fix (don't
  replay effectful bare `def`s) is exactly what keeps a re-seed from
  re-firing `message!`/`transact!` side effects. The seed eval must be
  idempotent-guarded: skip files whose defs are already in the program
  graph (same shape as `substrate-index-tx`'s conn-dedup,
  `client.cljs:1399`).

## #27 — on-reply hook

### Where reply emission actually happens (the fire-site search)

There are three distinct "assistant produced text" events, and only
one is the right ambient hook point:

1. The raw LLM completion for the turn — `reply-text` in
   `ask-and-eval-reply!` (`agent.cljs:959`,
   `(or (:text resp) "")`). This is the FULL assistant output,
   including the `;; narration` + Clojure forms, BEFORE parsing. It is
   stored verbatim as a self→self `:seon.agent.turn/messages` row
   (`agent.cljs:982-988`).
2. A user-facing `reply!` — only when the model emits a
   `(seon.agent/reply! …)` form (`message.cljs:322-341`). NOT every
   turn produces one; the agent decides. Hooking here would miss
   turns that only eval code, which defeats "fires on EVERY reply".
3. The turn close — `with-turn-body!` (`agent.cljs:927-953`) folds the
   result into the close-tx. The text is no longer in scope here
   except via the folded `:seon.agent.turn/messages`.

**Chosen fire-site: option 1, in `ask-and-eval!`.** The success branch
already has `reply-text` reachable (it is the input to
`ask-and-eval-reply!`), the `id` and `id-of-turn` are function args
(`agent.cljs:1040-1041`). Firing here means the hook sees the assistant
output of EVERY turn that called the LLM, independent of whether the
model chose to `reply!` — exactly the "independent of agent
cooperation" requirement (PRD #27).

Concretely: lift `reply-text` so `ask-and-eval!` can pass it to the
hook (today it is local to `ask-and-eval-reply!`; either return it in
the result map under `:seon.agent.reply/text` or recompute
`(or (:text resp) "")` in `ask-and-eval!` — the latter is a one-liner
with zero coupling). Fire after the success cond-> (`agent.cljs:1066`),
NOT on the `:seon.ai/error` branch (a failed LLM call has no reply to
post-process).

### Async + fail-soft contract

The hook MUST NOT change the turn outcome and MUST NOT throw into the
turn loop. Pattern (mirrors `persist-prompt!`'s fail-soft posture,
`agent.cljs:1071-1089`, and `creation-evals!`'s "logged loudly but
never abort", `client.cljs:1895-1906`):

```clojure
(defn- fire-on-reply-hooks!
  "Fire every registered on-reply hook for this assistant reply.
   Fire-and-forget — never awaited, never throws into the turn loop.
   Each hook runs in its own try/Promise so one bad hook can't sink
   the others or the turn."
  [{:seon.agent/keys [id] :seon.agent.turn/keys [id-of-turn]
    :seon.agent.reply/keys [text]}]
  (doseq [hook @!on-reply-hooks]
    (-> (js/Promise.resolve
          (db/with-agent id
            #(hook {:seon.agent/id          id
                    :seon.agent.turn/id     id-of-turn
                    :seon.agent.reply/text  text})))
        (.catch (fn [e]
                  (log/error-console! "seon.agent/on-reply"
                                      "hook threw — ignored" e))))))
```

- Not awaited: `ask-and-eval!` returns its result map immediately; the
  hook's transacts land on their own tx (and trigger the panel's SSE
  push via the existing inspector tx-listener, `inspector.cljs:1774`).
- `with-agent` re-entry: the hook runs outside the turn's ALS scope
  once it is on its own microtask, so wrap in `db/with-agent` so the
  hook's transacts carry the right agent id (same reason the kick
  handler re-enters, `agent.cljs:586-593`).
- Registration is a genuinely-stateful runtime artifact (a process
  atom of fn values), which reactive-context explicitly permits
  ("genuinely stateful runtime artifacts … the AsyncLocalStorage
  instance", `reactive-context.md:93`). It is the SAME shape as
  `seon.warn`'s check registry and `!on-reply-hooks` parallels
  `install-user-trigger!`'s listener registry. A downstream registers
  its hook from its seed file (#28): `(seon.agent/register-on-reply!
  'my.virtue/score-reply)` — store the SYMBOL, resolve late via
  `seval/lookup-value` at fire time (same late-resolution discipline as
  `:seon.render/ai` slots, `agent.cljs:872-877`), so a hot-reload of
  the hook fn takes effect without re-registration.

### Hook data shape (Malli, fully namespaced)

```clojure
(schema/register! :seon.agent.reply/text :string)

(schema/register! :seon.agent/on-reply-input
  [:map
   [:seon.agent/id         :seon.agent/id]
   [:seon.agent.turn/id    :seon.agent.turn/id]
   [:seon.agent.reply/text :seon.agent.reply/text]])
```

The hook's OUTPUT is its own concern (it transacts directly); the
substrate does not constrain it beyond "errors are values / fail-soft".
For the virtue case the hook writes `:my.virtue/*` rows keyed to the
turn:

```clojure
;; lives in the #28 seed dir, NOT in src/ (IP boundary)
(schema/register! :my.virtue/id         [:string {:seon.db/identity true}])
(schema/register! :my.virtue/turn       :seon.db/ref)
(schema/register! :my.virtue/dimension  :keyword)
(schema/register! :my.virtue/score      :int)
(schema/register! :my.virtue/at         :inst)
```

The turn ref (`[:seon.agent.turn/id id-of-turn]`) is the join key — the
panel section fn queries `:my.virtue/*` rows ordered by `:my.virtue/at`.

### The panel beside the chat

The consumer view (`/agent/<id>`) is a 2-column CSS grid: chat+input
left, the live tile right (`consumer-shell`, `inspector.cljs:1106-1111`,
`grid-template-columns: minmax(0,1fr) minmax(0,1fr)`). Two mount
options:

- **Recommended: a stacked pane in the existing tile column.** Add the
  virtue panel above or below `tile-pane-fragment` in the right grid
  cell. Zero new SSE wiring beyond a new fragment in `consumer-payloads`
  + `consumer-snapshot` (`inspector.cljs:969-985`, the snapshot that
  feeds `push-agent!`'s consumer branch, `inspector.cljs:1700`). The
  panel is NOT the agent's own tile — it is a substrate-owned pane that
  reads the hook's rows, satisfying "beside the chat, not the agent's
  own tile" (PRD #27).
- Alternative: a third grid column (`1fr 1fr minmax(0,…)`). More
  horizontal real estate but reflows the whole consumer layout; defer
  unless the radar needs the width.

The panel body is a section fn — pure reactive-context
(`reactive-context.md:29-69`): query the turn's `:my.virtue/*` rows for
this agent, render the SVG radar, return nothing when no rows exist (the
panel vanishes on a fresh world, self-healing). It is discovered the
same way the tile is: a registered render fn resolved by symbol. The
cleanest wiring that needs NO inspector edit is to make the panel a
`:seon.render/html` section the consumer snapshot already renders; the
minimal-edit version is one explicit call in `consumer-snapshot` to the
downstream's panel fn (resolved by a configurable symbol, defaulting to
absent → no panel for non-virtue deployments).

### Porting `DecisionSpectrumRadar` to hiccup-SVG

`docs/2026-06-12-virtue-tile.md` does NOT exist in this tree (checked),
and the angelic `DecisionSpectrumRadar` source is not vendored here — so
the port is from the visual spec only. The shape ("pure-SVG
polygon-per-cluster") maps directly to hiccup:

- `[:svg {:viewBox "0 0 200 200" …}]` root.
- Axis spokes + grid rings as `[:line …]` / `[:polygon …]` with
  computed `cx/cy + r·cos/sin` points (plain `cljs` math, no deps —
  same "pure divs/SVG, no deps" posture as `activity-sparkline`,
  `inspector.cljs:452-467`).
- One `[:polygon {:points "x1,y1 x2,y2 …" :fill … :fill-opacity …}]`
  per cluster/dimension set.
- Phosphor-terminal palette: amber accents on warm black
  (`bg-base-*`, `text-amber-*`), per the UI rules in CLAUDE.md.

The radar fn lives in the seed dir (`my.virtue/radar-svg`) so it is the
downstream's product code; the substrate only provides the panel mount
+ the hook.

### #27 implementation checklist

1. Register `:seon.agent.reply/text` + `:seon.agent/on-reply-input`
   schemas in `seon.agent` (alongside the turn schemas).
2. Add `!on-reply-hooks` process atom + `register-on-reply!` /
   `unregister-on-reply!` verbs (store SYMBOLS; resolve via
   `seval/lookup-value` at fire time). Re-export on the
   `seon.agent` face if the agent-taught surface needs it.
3. Add `fire-on-reply-hooks!` (fail-soft, not awaited, `with-agent`
   re-entry). Call it from `ask-and-eval!`'s SUCCESS branch
   (`agent.cljs:1066`), threading `reply-text`.
4. Add a consumer-view panel fragment + extend `consumer-snapshot` /
   `consumer-payloads` so the existing inspector push carries it; the
   panel body resolves a configurable downstream panel symbol
   (default absent = no panel).
5. (Downstream, in the #28 seed dir) `my.virtue` schemas, the hook fn
   that scores + transacts `:my.virtue/*`, and `radar-svg`.

### #27 open questions

- Should the hook also fire on the user-facing `reply!` specifically
  (richer "the human saw THIS" signal) IN ADDITION to per-turn? The
  per-turn fire is the more general "moderation/sentiment/cost" surface
  the PRD names; recommend per-turn only for v1.
- Panel mount: stacked-in-tile-column (recommended, zero layout reflow)
  vs third grid column. Sean to confirm the visual he wants.
- Hook concurrency: a slow hook on a fast agent could pile up promises.
  v1 fire-and-forget is fine; if it becomes a problem, a per-agent
  single-flight latch (like `!kick-scheduled`, `agent.cljs:526`) bounds
  it. Flag, don't pre-build.

## #28 — boot-seed downstream `my.*` from a consumer dir

### The two existing precedents

This ask sits between two mechanisms that already exist:

- **Compiled path — `SEON_EXTRA_SRC` (task #36).** Fully designed in
  [[docs/prds/agent-runtime/research/extra-src-research-2026-06-12]] and
  PARTIALLY wired: `client.cljs` already has `!extra-substrate-vars`
  (`client.cljs:966`), `extra-substrate-ns-strs` (`client.cljs:1012`),
  the reserved-prefix guard (`client.cljs:996`), `read-src-file`'s
  `SEON_EXTRA_SRC` probe root (`client.cljs:1068-1078`), and
  `substrate-ns-set` already unions the extra vars
  (`client.cljs:1052`). This compiles the downstream's `.cljs` into the
  pod bundle and indexes them as exemplar-grade `:seon.fn`/`:seon.ns`
  rows that are REPLAY-SKIPPED (they are substrate, rebuilt from var
  meta each boot).
- **Recorded path — detect-and-tee + replay.** Agent evals run through
  `eval-batch!` → `build-tee-entities` (`eval.cljs:876`) → persisted
  `:seon.fn`/`:seon.ns`/`:seon.schema` rows → `replay-program-graph!`
  (`client.cljs:780`) on every boot. This is how AGENT-authored corpus
  survives restart, and it is exactly the "evaluated through the
  recording path at startup, persisted as replayable rows" the ask
  describes.

### Recommendation: recorded path primary, compiled path sibling

`SEON_SEED_DIR` should drive the **recorded path** — eval each
`$SEON_SEED_DIR/*.cljs` through `eval-batch!` as a system-origin boot
turn, so its defs land as replayable program-graph rows. Rationale:

- It is the durable home the ask wants: the rows persist in the cluster
  store and replay every boot, so the downstream's `my.virtue` is
  reconstituted even if the seed file is later removed — matching how
  agent corpus already survives.
- It needs NO build integration (no `deps.edn`, no `--config-merge`),
  which the ask flags as the consumer's blocker ("no build of its own").
- It is the natural home for the #27 hook's code: the seed file calls
  `(seon.agent/register-on-reply! 'my.virtue/score-reply)` as one of
  its forms, so the hook is wired by the same boot eval that defines it.

Keep `SEON_EXTRA_SRC` (compiled) as the sibling for downstreams that DO
have a build and want their fns instrumented + indexed as exemplar
nses. The two are not redundant: compiled = "part of the substrate,
re-derived from source each boot, never replayed"; recorded = "part of
the agent corpus, persisted as rows, replayed each boot". The PRD's
"OR" is a real choice; recommend recorded as the default the ask asks
for, compiled as the power-user path already in flight.

### How the seed-dir flow threads the recording path

Mirror `creation-evals!` (`client.cljs:1842-1906`) — it already evals a
source string AS the primary agent through `eval-batch!` inside a
`{:seon.db/origin :system}` turn, which is precisely the recording
path. New step in `start-agent!`, AFTER `replay-program-graph!`
(`client.cljs:1985`) and BEFORE the per-agent boots:

1. Read `SEON_SEED_DIR` via the established `env-val` pattern
   (`brand.cljs:88-94` / `platform.cljs:62-67`). Absent/blank = no-op
   (byte-identical default behavior, the `SEON_*` family invariant).
2. List `*.cljs` files in the dir (sorted for deterministic order; Node
   `fs.readdirSync`), read each via `fs`.
3. For each file, eval its full text through `seval/eval-batch!` (the
   same call `creation-evals!` makes) inside a
   `{:seon.db/origin :substrate-seed}` (or a new `:seed-dir`) tx-context
   so the rows carry an auditable provenance distinct from agent
   evals. detect-and-tee then writes the `:seon.fn`/`:seon.ns`/
   `:seon.schema` rows automatically — no separate "persist" code.
4. Files live under a downstream root prefix (e.g. `my.virtue`), NOT
   `seon.*`. Reuse the reserved-prefix posture: `my.*` is the
   human/downstream corpus prefix per `reserved-extra-nses`
   (`client.cljs:982-994`) — note `my.*` is RESERVED for `SEON_EXTRA_SRC`
   (compiled) precisely because a compiled `my.*` would replay-skip what
   should be agent corpus; for the SEED dir the opposite is true —
   `my.*` is the CORRECT prefix because we WANT these to be
   replayed-as-corpus. (This asymmetry is a genuine open question — see
   below.)

### The #29 coordination (critical, do not re-fire side effects)

The recording/replay path is shared machinery, and #29 is being fixed
in parallel. Two failure modes to avoid:

1. **Re-seed re-firing side effects.** On the SECOND boot the seed
   file's defs are ALREADY program-graph rows; re-evaling the file would
   re-run any effectful top-level forms (a bare
   `(def x (seon.agent/message! …))` — exactly the #29 ghost-message
   bug, PRD lines 57-79). FIX: the seed step must be idempotent —
   BEFORE evaling a file, check whether its defs are already in the
   program graph (query `:seon.fn/sym` / `:seon.schema/key` for the
   file's ns, the same conn-dedup `substrate-index-tx` does,
   `client.cljs:1417-1456`); skip files whose corpus already exists.
   First boot seeds; later boots let REPLAY reconstitute, not the seed
   eval.
2. **Replay re-firing side effects.** Even on first boot, if the seed
   file contains an effectful bare `def`, #29's replay fix is what
   prevents the next boot's `replay-program-graph!` from re-running it.
   So #28's correctness DEPENDS on #29 landing: the seed dir is a new
   SOURCE of exactly the rows #29 makes safe to replay. The seed file
   author should use `register-on-reply!` (a verb call, captured as a
   `:seon.eval` not a replayable `:seon.fn`) for wiring, and `defn`/
   `def` of pure values for code — never `(def x (effectful …))`.
   Document this in the seed-dir contract; #29's guard is the backstop.

Net: implement #28 AFTER #29, and make the seed step idempotent by
program-graph presence (not a stored "seeded?" flag — derive, per
reactive-context).

### Env var name + precedence

- Name: `SEON_SEED_DIR` (absolute path), matching the ask and the
  `SEON_*` family (`SEON_RUNTIME_ROOT`, `SEON_EXTRA_SRC`,
  `SEON_BRAND_*`). Default absent = no seeding.
- Read via the `env-val` helper pattern (`brand.cljs:88`), NOT routed
  through `artifact-path` (the seed dir is the consumer's, not a seon
  artifact — same call-out `read-src-file` makes for `SEON_EXTRA_SRC`,
  `client.cljs:1076-1078`).
- Precedence vs compiled: if BOTH `SEON_SEED_DIR` and `SEON_EXTRA_SRC`
  name the same ns, the compiled one wins (it is in `substrate-ns-set`,
  so the seed-dir rows for that ns would be replay-skipped). Document:
  use one path per ns, not both.

### Compiled-vs-recorded tradeoff (the recommendation, restated)

| Aspect | Recorded (`SEON_SEED_DIR`) | Compiled (`SEON_EXTRA_SRC`) |
| --- | --- | --- |
| Build needed | none | downstream `deps.edn` + preload |
| Persistence | rows in store, replayed each boot | re-derived from source each boot |
| Instrumentation | only if the fn carries `:malli/schema` and replay re-registers it | full Malli instrument via `index-substrate!` |
| Survives file deletion | yes (rows persist) | no (source must be present) |
| Side-effect risk | needs #29 guard | none (substrate, never replayed) |
| Best for | product code with no build (Aria's `my.virtue`) | exemplar nses a downstream wants agents reading whole |

**Recommend `SEON_SEED_DIR` (recorded) as the answer to #28** — it is
what the ask literally requests ("evaluated through the recording path
… persisted as replayable rows"), needs no build, and is the home for
the #27 hook code. `SEON_EXTRA_SRC` stays the documented power-user
sibling.

### #28 implementation checklist

1. `seed-dir` helper: `env-val "SEON_SEED_DIR"`; nil/blank → no-op.
2. List + read `*.cljs` (sorted) via Node `fs`.
3. Idempotency guard: query the program graph for each file's ns; skip
   files whose defs already exist (conn-dedup shape from
   `substrate-index-tx`).
4. Eval each remaining file through `seval/eval-batch!` as a
   system-origin boot turn (mirror `creation-evals!`), inside a
   `{:seon.db/origin :seed-dir}` tx-context for auditable provenance.
   detect-and-tee persists the rows.
5. Call the seed step in `start-agent!` AFTER `replay-program-graph!`,
   BEFORE the per-agent boots (`client.cljs:1985-1995`).
6. Depends on #29: the guard against replaying effectful bare `def`s
   must be in place first.
7. Document the seed-dir contract: `my.*`-prefixed nses, `defn`/pure
   `def` only, wiring via verb calls (`register-on-reply!`), no
   `(def x (effectful …))`.

### #28 open questions

- `my.*` prefix asymmetry: `SEON_EXTRA_SRC` REJECTS `my.*`
  (`reserved-extra-nses`, `client.cljs:982`) because a compiled `my.*`
  would replay-skip agent corpus; the seed dir WANTS `my.*` because it
  IS replayed corpus. Confirm `my.*` is the right seed-dir prefix and
  reconcile the two guards (a seed-dir ns must NOT also be in
  `substrate-ns-set`).
- Provenance origin: reuse `:substrate-seed` (so seed rows count as
  machinery, FACTS=0 on a fresh world — the demo-polish posture,
  `client.cljs:1733-1743`) or a distinct `:seed-dir`? Recommend a
  distinct origin so audit can tell consumer-seeded from
  substrate-seeded.
- Re-seed on file CHANGE: `substrate-index-tx` re-emits a row when
  source differs (`client.cljs:1419-1456`). Should the seed dir behave
  the same (re-eval a file whose source changed since last boot)? v1:
  no — first-boot-only is simplest; flag the upgrade.
