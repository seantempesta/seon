# N4 implementation plan — `seon.cluster.render`, the in-process render pipeline

This is the implementation PLAN for the N4 rung. It EXTENDS
`jvm-render-design-2026-07-26.md` rather than re-deriving it; §2 records
exactly which of that audit's conclusions the O14 dissolution overturned and
which survive. The orchestrator authors the sealed contracts; §10 lists the
contract candidates and §11 the crash-walk rows they must carry.

## 0. Verdict in one paragraph

N4 is buildable after one owner-ruling batch, but it is not a freestanding
render subsystem. It composes today's landed owners: `seon.sci.admit/admit`
is the one outgoing value projection; `:seon.error/value` is the one flat
error shape; `seon.cluster.store/transact!` is the write/refusal boundary;
`seon.schema` owns the renderer catalog; `seon.cluster.prompt` owns prompt
assembly; `seon.ai` is non-streaming; and `seon.cluster.wake` remains the
payloadless run-loop wake. N4 adds one explicitly separate render-interest
listener because invalidation needs the committing report's exact immutable
`:db-after`. That listener matches registrations before coalescing, so a later
unrelated report cannot erase an earlier relevant invalidation. Completed
renders are process-local success values or the closed flat error value;
nothing rendered is stored. The unresolved taste calls are gathered in §14.

handoff and zero-evaluation reconnect
(`research/jvm-render-design-2026-07-26.md:49-65,320-361`). Merging web-render

second to a process-restart question.

taste call are decision 1; the semantic ownership below is fixed regardless
of file split.

| Owner | Owns | Constraint |

There is no fresh `seon.reactive` registry. The five useful quarry transitions
become pure registration functions; the old generic multi-consumer/Promise

render-result attribute, or render-local message/lifecycle/result entity.

## 4. The render-unit data model

### 4.1 The wake is the hard constraint — MEASURED

`d/listen`'s callback is invoked from `datahike.writer`'s commit path at
`reference-code/datahike/src/datahike/writer.cljc:384-385`, inside the same
`go` block that delivers the transacting caller's promise at `:386`. Datahike's
own API doc warns that synchronous writer operations inside the callback
deadlock (`reference-code/datahike/src/datahike/api/specification.cljc:1077`).

The probe (`tmp/n4_listen_probe.clj`, run `clojure -M:dev
tmp/n4_listen_probe.clj`, JDK 26.0.1, Datahike at the vendored local root,
`:memory` backend) makes the cost exact:

```
:caller-thread  main
:listener       [{:thread async-mixed-1}]
:transact2-ms   1503      ; listener does (Thread/sleep 1500)
:transact3-ms   1504      ; the NEXT transaction pays it again
```

A listener that takes 1.5 s adds 1.5 s to EVERY subsequent `d/transact`, on
core.async's shared `:mixed` executor. This is a stronger constraint than the
prior audit's thread-classification table stated.

`seon.cluster.wake` already owns the run loop's payloadless “look” signal and
uses `offer!`; N4 does not alter or reuse that payload contract. The render
listener is a separate database-interest owner because it must retain the
committing report's exact `:db-after`.

**Sealed invariant:** while still on the commit path, the render listener only
(a) extracts changed attributes, (b) reads the process-local reverse interest
index, (c) atomically replaces each selected registration's pending database
value with the exact newest `:db-after`, and (d) `offer!`s one payloadless
scheduler wake. It never queries, renders, parks, transacts, or calls user
code. A dirty-registration map is the durable-in-process handoff; the wake is
only “drain it,” so saturation cannot lose which units are dirty.

### 4.2 What flows on the wake channel

Datahike's report is `{:db-before :db-after :tx-data :tempids :tx-meta}` with
`:db-after` a real immutable Datahike database value (probe
`tmp/n4_report_probe.clj`). Its `:max-tx` can order current reports from one
connection, but it is not a complete render identity and is never exposed as
one. N4 retains the exact `:db-after` and projects the complete identity named
in §7.3; it never aliases branch or temporal views by a number.

The report itself never enters a `(sliding-buffer 1)`. That design was lossy:
report B could overwrite relevant report A before A's attributes were matched.
Matching happens first in the listener. Coalescing happens second, per selected
registration, by retaining the newest exact `:db-after`; the accumulated dirty
unit set is drained by the scheduler. Missing read evidence maps to `:all`.
Historical registrations are frozen and are not selected by current commits.

### 4.3 The render unit — DERIVED, never registered

A **render unit** is the addressable computation a tab subscribes to and a
registration owns. Its identity is a generic stable ordinary-data address:

```clojure
;; the identity — a closed ordinary value, the mult/tap and tab-route key
{:seon.render.unit/id    <stable qualified keyword or string>
 :seon.render.unit/route <normalized route>
 :seon.render.unit/slot  <stable DOM element id>
 :seon.render.unit/agent <agent-id, optional>}
```

This identity addresses root cards, canvas, context surfaces, debug, `/data`,
and the shared header without inventing a third surface noun. Canvas and
surface remain placement vocabulary, not an exhaustive unit taxonomy.

N4 registers one durable attribute if decision 2 keeps the pin-based
falsifier: `:seon.render.canvas/content`, the authored canvas selector. It
enters the canonical schema EDN population and therefore
`populate-ancestor!`'s established declarations → core process → canonical
rows sequence with core provenance. `:seon.render/ai` and
`:seon.render/html` remain schema metadata/renderer selections already owned by
`seon.schema`; completed renders are not datoms. If decision 2 selects a
fixture-supplied unit instead, N4 registers zero attributes and makes no
pinned-canvas boot claim.

### 4.4 The unit VALUE — and the containment hole that must close first

One completed render is a closed success value OR the already-registered flat
error value:

```clojure
{:seon.render/unit       <unit identity>
 :seon.render/database   {:db-name ... :t ... :as-of ... :since ...
                          :history ... :datahike/commit-id ...}
 :seon.render/text       <prompt string>           ; optional output
 :seon.render/hiccup     <admitted hiccup>         ; optional output
 :seon.render/evidence   <attribute set | :all>
 :seon.render/diagnostic <the :seon.eval record>}
;; OR exactly :seon.error/value
```

The input block's `:seon.render/ai` and `:seon.render/html` keys remain literal
or late-resolved renderer selections. They are never reused as output keys.
Success requires at least one of `:seon.render/text` or
`:seon.render/hiccup`; failure is the separate closed error alternative, never
an error map merged into a success map.

`171a94e02` already closed the containment hole:
`seon.sci.admit/admit` deeply realizes once, calls the `:interrupt-fn` at every
node, applies the four result caps from config, never dereferences `IDeref`,
returns `:seon.cluster.eval/result-edn`, and preserves the
`:seon.eval/*` diagnostic record. N4's evaluator dependency must call it
inside the armed boundary before disarm. C5 is therefore deleted as an N4
contract; the N4 suite verifies composition through the evaluator rather than
retesting admission's internal grammar.

## 5. Pipeline topology

```
 d/listen render-interest callback
 changed attrs → interest match → pending exact :db-after per selected unit
                                        │ offer! “drain dirty units”
                                        ▼
                            ┌──────────────────────────┐
                            │ scheduler proc           │  registration memory:
                            │ pure registration/wake,  │  interest, dirty-at,
                            │ due?, settle windows     │  last-value, exact db
                            └───────────┬──────────────┘
                                        │ one due unit at a time
                                        ▼
                            ┌──────────────────────────┐
                            │ render proc   (:compute) │  ONE seon.sci.eval
                            │ guarded eval + admission │  per due unit
                            └───────────┬──────────────┘
                                        │ completed unit value
                                        ▼
                            ┌──────────────────────────┐
                            │ equality gate            │  = against last-value
                            │ (in scheduler, pure)     │  in registration memory
                            └───────────┬──────────────┘
                       unequal only     │
             ┌──────────────────────────┴──────────────────┐
             ▼ (ai projection)                             ▼ (html projection)
    seon.cluster.prompt                         fanout owner: mult per unit
    reads the same registration                          │
    at the exact db value (§9)             tap: (sliding-buffer 1) per TAB
                                                          │
                                              per-tab fixed Flow graph
                                              writer tag: decision 4
                                                          │
                                            datastar/patch-elements! → 1 SSE
```

### 5.1 Which parts are flow, and which are not

- The scheduler and render procs are ordinary `flow/process` procs in the
  cluster's per-cluster graph (`research/flow-per-cluster-2026-07-27.md:9-33`).
  The render proc is declared `:compute`; flow runs a `:compute` proc's loop on
  `:io` and submits each transform separately to `:compute`
  (`.../flow/impl.clj:243-270`, cited via
  `research/flow-per-cluster-2026-07-27.md:99-104`).
- The per-tab fan-out owns dynamic taps outside the cluster graph; each tab
  itself is a small fixed Flow graph. See §5.3.

### 5.2 Why the scheduler is a proc and not the timer thread

`src-old/seon/reactive.cljc:83-91` runs a single-threaded
`seon-reactive-settle` scheduled executor whose callback calls
`start-evaluation!` at `:197-220`, and the CLJ branch computes the whole render
synchronously at `:547-556`. The timer thread thus BECOMES the render worker —
the defect the prior audit named
(`research/jvm-render-design-2026-07-26.md:200-208,463`). In N4 the timer only
publishes readiness onto the scheduler proc's input; the scheduler only decides;
the render proc only computes. This is also the plan's standing rule that a
constant must stand in for an observable event where one exists
(`plan/README.md` runtime contracts; `CLAUDE.md` "Timeouts and magic numbers").

### 5.3 Per-tab fan-out and graph lifecycle

`create-flow` validates and closes over a FIXED conn map
(`.../flow/impl.clj:38-70`), and `start` allocates every channel and every
`mult` from that map: `needs-mult?` is computed once at `:113-115` and the
mults are built once at `:135-140`. There is no API to add a conn to a running
graph. Tabs arrive and leave at runtime.

Static conns prove that one already-running graph cannot gain a tab; they do
not prove that tabs must bypass Flow. N4 follows `ui.md`: the cluster component
owns one `mult` per unit, and opening a tab creates one small fixed graph whose
input is that tab's `(sliding-buffer 1)` tap and whose writer proc owns the SSE
connection. Closing the tab stops that graph and untaps it. The existing
`src/seon/flow.clj:515-583` mult/tap owner is the precedent for fan-out
custody; the tab graph restores Flow reporting and lifecycle.

### 5.4 Streamed reply partials are dead scope in N4

Today's `seon.ai/request-body` sends `"stream" false`, and `complete` performs
one synchronous request. N4 therefore has no partial producer and adds no
process-local prefix channel or no-history attribute. Quarry
`:seon.ai.attempt/partial-text` and its settle dial remain deletion candidates,
not code to port. Restoring streaming would first revise `seon.ai` C10 and the
loop C9; only that provider-owned revision may feed the already-defined render
pipeline. Decision 6 asks whether N4 merely records this deletion or reopens
those sealed owners.

### 5.5 Workload tags require one measurement and ruling

`reference-code/core.async/src/main/clojure/clojure/core/async.clj:515-519`:
`:io` "may do blocking I/O but must not do extended computation"; `:compute`
"must not ever block"; `:mixed` "anything else". The per-tab writer takes from
a channel (blocks) AND builds the SSE frame, optionally gzipping it (computes).
That is `:mixed` by definition, matching the prior audit's table
(`research/jvm-render-design-2026-07-26.md:462`).

The architecture currently says `:io`; this draft previously inferred
`:mixed` from gzip/frame construction without measuring whether that work is
extended computation. Decision 4 seals the tag after a benchmark records
frame/gzip cost under representative morph sizes. The render proc is
`:compute`; no implementation lane chooses the writer tag by taste.

## 6. The http-kit / SSE seam, in SDK vocabulary

### 6.1 Server

One `org.httpkit.server/run-server` in the cluster JVM, bound to loopback, with
a bounded `:worker-pool` and `:max-body`, exactly as
`src-old/seon/web/server.clj:304-311` already does. Port is dynamic and
published by extending the advertisement assembled in
`src/seon/cluster.clj:385-470` — not a new port file. The render/web component
attaches after `stack-tower!` has a branch connection and is stopped before
that connection/store is released.

### 6.2 One SSE connection per tab

`starfederation.datastar.clojure.adapter.http-kit/->sse-response` with the
option keys the adapter exposes at
`.../adapter/http_kit.clj:9-20`: `on-open`, `on-close`, `on-exception`,
`write-profile` (`basic-profile` / `gzip-profile` / the buffered variants).
`on-open` receives the SSE generator, `on-close` receives it plus http-kit's
status code (`.../adapter/http_kit.clj:55-80`).

Per tab, `on-open` taps demanded units with fresh `(sliding-buffer 1)` channels,
creates and starts the fixed tab graph, and requests an initial paint from the
resolved current or historical database value. `on-close` stops that graph,
untaps, and closes the tap channels. `src-old/seon/web/feed.clj:90-158` is
quarry evidence for SDK lifecycle only; its hand-owned writer thread is not
ported.

### 6.3 Patch vocabulary

`patch-elements!` with no options uses the SDK's default `outer` patch mode
(`.../clojure/api.clj:222-224,268-285`), which is what a complete morph of one
element wants. The element id IS the render unit's DOM identity; the shell
places the feed opener OUTSIDE the morphed element, the lesson recorded at
`src-old/seon/web/datastar.cljs:611-620` — a `data-init` inside the morphed
element is stripped by the first whole-element morph. `src-old/seon/web/data.clj:86-106`
is the minimal working shell and is the `adapt` source for it.

Not used by N4: `patch-signals!`, `execute-script!`, `remove-element!`. Adding
them is a later decision, not a rung requirement.

### 6.4 "Bounded writes" — what is true and what is not

Bounded IN SEON: at most one un-sent value per tab, because the tap is
`(sliding-buffer 1)`; `.clear`-then-`.offer` in
`src-old/seon/web/feed.clj:22-25` is the same semantics expressed by hand, and
made the configured `::mailbox-depth` structurally unreachable — delete that
dial, do not port it.

NOT bounded below the SDK. `SSEGenerator.send-event!`
(`.../adapter/http_kit/impl.cljc:74-88`) calls `hk-server/send!`, which reaches
`AsyncChannel.send` — returning `true` after handing buffers to the write path,
never a completion (`reference-code/http-kit/src/java/org/httpkit/server/AsyncChannel.java:251-293`).
`HttpServer.tryWrite` appends the unwritten remainder to
`atta.toWrites` at `:378-385` and appends every later send while any write is
pending at `:395-399`. `toWrites` is `final LinkedList<ByteBuffer>`, package
private, with no accessor (`ServerAtta.java:6-7`; the only readers are inside
`HttpServer.java:332-350`). There is no signal a userspace writer can consult
and no completion to await.

Consequences the plan states plainly rather than papering over:

- a paused-read tab accumulates complete morph frames on the JVM heap;
- `send-event!` returning `false` only tells us the connection is already
  closed — it is not backpressure;
- no arrangement of core.async buffers fixes this, because the unbounded queue
  is downstream of every channel we own.

Options are sealed by decision 7.

## 7. Equality suppression and registration memory

### 7.1 The memory

One process-local atom per cluster holding `{unit → registration}`. Legitimate
under the atoms rule: this is invocation-local coordination over derived
presentation state, and nothing in it is durable
(`CLAUDE.md` "The database, not atoms, owns important durable state").

```clojure
{:seon.render/unit        <unit identity>
 :seon.render/last-value  <the completed unit value, or absent>
 :seon.render/database    <complete database identity it was rendered at>
 :seon.render/interest    <attribute set | :all>
 :seon.render/pending     <newest exact immutable database value, or absent>
 :seon.render/dirty-at    <monotonic ms, or absent>
 :seon.render/active      <evaluation id, or absent>}
```

Absent keys, never stored nil (`CLAUDE.md` data-oriented rules).

### 7.2 The transitions, ported as pure functions

Five ideas in `src-old/seon/reactive.cljc` are genuinely good and survive as
pure functions of (registration, event, now):

| Idea | Old site | Port verdict |
|---|---|---|
| newest-pending replacement after interest selection (a slow render never queues database values) | `:110-118`, `:252-290` | `adapt` — retain exact `:db-after`, never numeric ordering |
| settle window bounded by max latency: `due-at = min(dirty-at + max-latency, now + settle)` | `:192-195` | `adopt` as a pure fn |
| one active evaluation per registration; the newest pending wins | `:504-556` | `adapt` — the proc replaces the direct call |
| equality suppression against the previously DELIVERED value | `:486-492` | `adopt` |
| evidence signature drives interest re-installation only when it CHANGED | `:120-129`, `:496-501` | `adopt` |

Everything else — the consumer registry, `observe!`/`unobserve!`, the ready
promise, the failure-evidence suppression, the Promise branches — is `dead`
(§8). In the merged process there is exactly one consumer of a registration
(the fan-out owner), so multi-consumer normalization is machinery for a problem
that no longer exists.

### 7.3 What suppression compares

`=` on the whole completed unit value MINUS `:seon.render/database` and
`:seon.render/diagnostic`. Those two change on every render by construction; a
naive whole-value `=` would suppress nothing and send a morph per commit.
Comparing the projections only is the semantics the falsifier needs.

The complete render coordinate is
`{:db-name :t :as-of :since :history :datahike/commit-id}`. Reuse is exact
equality on all fields; “at or after” is forbidden. Current registrations
receive the exact report `:db-after`; historical registrations are resolved
once and ignore current wakes. Branch/history views that share a numeric
ordering therefore never alias.

Instrumentation, following `src/seon/flow.clj:423-451`'s counted-dropping-buffer
precedent: per unit, count evaluations started, evaluations completed,
suppressed-equal results, newest-pending replacements, and per tab, tap drops.
`src-old/seon/reactive.cljc:668-680` is the shape of the bounded `measurements`
surface — `adopt` the shape.

## 9. Prompt composition in the landed owner

The `ai` projection has NO channel, NO tap, and NO writer. This asymmetry is
the point of "two projections on one unit": the html projection is PUSHED to a
socket because a browser cannot ask; the ai projection is PULLED by prompt
derivation because an agent asks exactly when it builds a turn.

N4 revises `seon.cluster.prompt/prompt` in place. A small render-owned pure
query supplies one unit at the exact database value:

```clojure
(defn ai-projection
  "Return one unit's admitted prompt text at the exact database value."
  {:malli/schema [:=> [:cat :seon.render/unit :seon.render/database]
                  [:or :string :seon.error/value]]}
  ...)
```

Three properties the sealed contract must pin:

1. **One value, two readers.** A unit rendered for a tab is not rendered again
   for the prompt at the exact same complete database identity. The
   registration's `last-value` serves
   both. This is the strongest argument for keeping ONE registration per unit
   rather than separate ai/html registrations.
2. **The prompt never waits on a socket.** `ai-projection` renders through the
   same guarded evaluator and seeds/uses the registration regardless of tabs.
   Whether pins keep registrations warm is decision 5, but a tab is never a
   prerequisite.
3. **Errors are values.** A failed render is the exact flat error alternative.
   `seon.cluster.prompt` formats it as legible prompt text; no render-local
   acknowledgement/result shape and no throw enters the run loop.

`src-old/seon/agent/ctx.cljc:1677-1689` and `:1820-1855` remain quarry evidence
that key presence selects the AI render. The fresh prompt owner and its
schemas/tests are revised in the N4 contract; there is no post-hoc request to
an already-finished N3 lane.

## 12. Risks, ranked

**R1 — http-kit's unbounded pending queue (blocker-severity, unchanged).**
Issue `docs/seon/issues/http-kit-streaming-writes-have-an-unbounded-socket-queue.md`
already states the acceptance criteria. Options:

1. *Measure and accept, with the number recorded.* Commit a paused-read SSE
   probe (the issue's own acceptance test) and report heap growth per morph per
   stalled tab. Cheap; leaves the claim "bounded writes" partly false but
   HONEST and quantified.
2. *Fork http-kit minimally.* `reference-code/http-kit` is currently a vendored
   UPSTREAM submodule (`70432d3`, remote `http-kit/http-kit`), and the
   coordinate resolves from Maven through `sdk-http-kit/deps.edn:2-3`. A
   minimal, upstreamable change adds a pending-bytes accessor on `AsyncChannel`
   and an optional per-channel cap that closes the socket loudly when crossed.
   The repo already maintains forks of Datahike, konserve, and shadow-cljs, so
   this is in-idiom — but it means forking, repointing `dev.data-star.clojure/http-kit`'s
   transitive dep with `:override-deps`, and owning the fork.
3. *Do nothing.* Rejected: it makes the ruling's "bounded writes" false with no
   measurement behind it.

Recommendation: option 1 INSIDE N4 (the probe is a sealed acceptance item under
C6), option 2 as a named follow-on the measurement either justifies or
retires. Do not let it gate the rung.

**R2 — evaluator composition is still required, but admission is landed.**
`seon.sci.admit/admit` owns deep realization and caps. N4 is blocked only until
the selected fresh evaluator calls that owner before disarm; N4 must not edit
admission or revive the old walker.

**R3 — attribute-only interest fan-out cannot be fixed in N4.**
`query-dependency-plan` returns per-source attribute sets and nothing else
(`reference-code/datahike/src/datahike/query.cljc:2877-2903`). Two agents' units
reading one attribute both wake. In-process this is cheaper than it was (no
serialization before suppression, no gzip per connection), but it is still
avoidable work. Keep issue
`attribute-only-feed-interest-recomputes-unrelated-agent-views` open; the fix is
a Datahike plan change (carry bound entity constraints), not a Seon change. §5.4
keeps the old partial-text producer dead under today's non-streaming
`seon.ai`, which is a real reduction in exposure.

**R4 — the wake callback is a shared-fate hazard.** §4.1 measured a listener
directly extending every transaction. One careless future edit inside that
callback degrades the whole writer. Mitigation is structural, not vigilance:
the callback receives only immutable report data, the reverse-interest atom,
dirty-state atom, payloadless scheduler channel, and fault channel. It has no
connection or renderer. C4 holds the scheduler, saturates the signal, observes
transaction completion by event, and then proves every selected dirty unit is
drained; its clock is only a loud deadlock backstop.

**R5 — flow topology is static; lifecycle must stay explicit.**
The cluster owner follows `src/seon/flow.clj:515-583` for the mult/tap
component, while every tab is a separately created fixed graph. The risk is a
lane reviving a hand-owned writer thread or trying to mutate a running graph.

**R6 — "one authored evaluation for 32 tabs" depends on demand lifetime.**
Decision 5 settles whether a pin keeps a registration warm or last disconnect
releases it. The simultaneous-tab invariant holds either way; reconnect cost
and boot work differ and are asserted according to that ruling.

## 14. Owner decisions required before seal

### Decision 1 — namespace split and landed-owner composition

**Option A (recommended):** keep `seon.schema`, `seon.cluster.wake`,
`seon.cluster.prompt`, `seon.ai`, `seon.sci.admit`, and
`seon.cluster.store` as the owners already landed; add only a small
`seon.render` contract/engine and a `seon.cluster.render` family for
registration, interest, graph, and web leaves. This avoids duplicate catalogs,
wakes, prompts, admission, and writes. **Option B:** put every new function in
one `seon.cluster.render` namespace; fewer files, but pure render contracts and
transport lifecycle become entangled. **Option C:** revive old render/reactive
namespaces wholesale; fastest mechanically, but ports the system N4 exists to
delete.

### Decision 2 — schema homes and the canvas pin

**Option A (recommended):** register ordinary process-local schemas for unit,
success, registration, and tab state under their code owners; keep
`:seon.render/ai`/`:seon.render/html` as `seon.schema` metadata; add only
`:seon.render.canvas/content` as a durable attribute in canonical schema EDN
and ancestor population. This makes the pin-based falsifier honest and stores
no render. **Option B:** use a contract-supplied render unit for N4 and defer
the canvas pin; zero attributes now, but N4 cannot claim pinned-canvas boot
behavior. **Option C:** store unit/result rows; rejected because renders are
derived and O14 forbids them.

### Decision 3 — complete database-value representation

**Option A (recommended):** make the render request and registration schema
carry the complete identity
`{:db-name :t :as-of :since :history :datahike/commit-id}` plus the exact
in-process immutable database value; reuse only on exact identity equality,
and freeze historical registrations from current wakes. This matches
architecture and prevents branch/history aliasing. **Option B:** retain only
the complete ordinary identity map and resolve the immutable database value at
each call; more portable, but adds resolution work and a new refusal seam.
**Option C:** use `:max-tx`/`>=`; rejected as incomplete and historically
incorrect.

### Decision 4 — tab graph and writer workload

**Option A (recommended):** one fixed Flow graph per open tab, as `ui.md`
specifies; measure representative plain/gzip frame construction and keep
`:io` unless the measurement proves extended computation, in which case change
both plan and architecture to `:mixed`. This preserves Flow lifecycle and
grounds the tag. **Option B:** rule `:mixed` now; fail-closed, but contradicts
the maintained architecture without evidence. **Option C:** use a hand-owned
virtual thread; fewer graph objects, but bypasses Flow reporting/control and
recreates a second lifecycle pattern.

**Option A (recommended):** a pinned canvas is demand: register/render it once

surface units exist only while subscribed. This matches `ui.md` while avoiding
permanent retention for every route unit. **Option B:** only connected tabs
are demand; lowest idle cost, but contradicts pinned-canvas boot semantics and
re-renders after every full disconnect. **Option C:** every declared unit is
permanent demand; simplest reuse, but retains idle interests and values for
debug/data/routes nobody opened.

**Option A (recommended):** keep N4 non-streaming, classify quarry partial

**Option A (recommended):** keep upstream http-kit for N4, put the paused-read
