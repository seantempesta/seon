# Can we cache the sci eval state? Parked ctx vs replay-on-wake — measured

Research lane, 2026-08-01. The owner's question, from
`plan/repl-session-context-2026-08-01.md` ("Owner directions, midday
batch"): an agent evals `(def x <large computed value>)` in turn 1 and
expects `x` to simply BE there in turn 10, like any REPL session. Today
every run forks a fresh ctx from the base and installs program rows, so
anything that is not a contracted `defn` silently vanishes between runs.

**The three-sentence answer.** Yes — the "sci eval graph" is exactly the
ctx's `:env` atom, and keeping one alive per agent is nearly free
(a fork is ~135 bytes and 0.04 us; a parked session's marginal cost is
the bytes of the values the agent defined, measured at ~280 B per small
`def`, ~2.1 KB per interpreted `defn`, and for a big value exactly the
value itself with no ctx overhead). But it cannot be serialized and it
cannot be safely branched: an interpreted fn is a JVM closure over the
creating ctx and its analyzed body nodes, and `sci/fork` shares Var
objects, so a fork's `def` of an existing name writes THROUGH into the
parent. So route A (park the hot ctx) is the right in-process answer and
route B (replay/rehydrate from the transcript) is the required recovery
and branch path — and route B is cheap: a 200-form transcript replays in
**68 ms**, once one unrelated defect is fixed.

Every number below comes from a script committed under
`tmp/sci-session/` (`probe1_heap.clj`, `probe2_replay.clj`,
`probe3_defn_cost.clj`, `probe4_surface.clj`, `probe5_isolation.clj`,
`probe6_scale.clj`), each run in a fresh `clojure -M:dev` JVM against its
own store root (`tmp/sci-session/clusters`) — no live cluster was
touched. Machine: this laptop, JDK 26, `:dev` alias (`-Xmx512m`). Sci
revision: `reference-code/sci` @ `937d392`.

## 1. Anatomy: what "the sci eval state" actually is

For the owner, plainly:

**A ctx is a map with one mutable cell in it.** `sci/init` returns an
ordinary Clojure map whose `:env` key holds an **atom**
(`reference-code/sci/src/sci/core.cljc:304-311`; our `ctx?` predicate is
literally "a map containing `:env`", `src/seon/sci/eval.clj:121-128`).
Inside that atom is `{:namespaces {ns-sym {sym Var, …}, …}, :class->opts
…, :imports …}` — the namespace table is reachable as an ordinary value
through `sci/namespace-state` (`core.cljc:721-732`, one of our fork's
additions). So "the eval graph" is: **namespaces -> names -> Vars ->
values.** There is no hidden compiler state, no separate AST store, no
per-session machinery. That is the good news, and it is why parking one
is cheap.

**`sci/fork` is a shallow copy of that cell.** `(update ctx :env (fn
[env] (atom @env)))` — `core.cljc:318-323`. A new atom holding the SAME
persistent map, therefore the SAME `sci.lang.Var` objects. 0.04 us
(`research/sci-precomputed-analysis-2026-07-31.md` §0), 0.13 KB retained
(p1).

**A Var's value is an ordinary value for `def`, and a JVM closure for
`defn`.** Measured directly (p4):

```
(def data {:a 1 :b [1 2 3]})
  var class:  sci.lang.Var        value class: clojure.lang.PersistentArrayMap
(defn twice [x] (* 2 x))
  var class:  sci.lang.Var        value class: sci.impl.fns$fun$arity_1__76612
```

That second class is generated by `sci.impl.fns/fun`
(`reference-code/sci/src/sci/impl/fns.cljc:88-140`, built by the `gen-fn`
macro at `fns.cljc:60-83`). The returned function closes over: the
creating **`ctx`**, an `enclosed-array` of captured locals, the analyzed
**body node objects**, and — read once at creation, `fns.cljc:39-40,
63-64` — the creating ctx's `:interrupt-fn`.

**So: can the eval state be serialized? Data vars, yes; function vars,
no.** A `defn` value is a live JVM object graph pointing at analyzer
nodes and at the ctx that made it. It reports `Serializable` only because
`clojure.lang.AFunction` is; writing it out would capture the entire
interpreter context, and reading it back into a different process would
be meaningless — the nodes resolve free names through Var objects that
exist only in the ctx that created them. The honest statement for the
owner: **an agent's session is a live object graph, not a document. It
can be kept, not saved.** What CAN be saved is what created it — the
ordered source forms, which we already store.

**Redefinition follows Var IDENTITY, exactly as in Clojure.** Two
measured consequences (p5), both load-bearing:

1. `(def x …)` on a fork, where `x` was already interned upstream,
   `bindRoot`s the SHARED Var: the parent's `x` changes too. A name the
   fork interns first IS isolated. Filed as
   `docs/seon/issues/sci-fork-does-not-isolate-redefinition-of-existing-vars.md`.
2. An interpreted fn resolves its free names through the Var objects
   captured at analysis time. Interning a FRESH var with the same name in
   a fork does not redirect functions created earlier — they keep reading
   the original. So a "deep snapshot" that re-interns every var with its
   current value (cheap, ~6 us for a small namespace) is **not** a
   semantically faithful copy of a session.

Together these say: **you cannot branch a live sci session.** The only
faithful branch point is re-execution into a fresh ctx — which is route B.

## 2. Our lifecycle today

- one process-wide base ctx, built once, `defonce` + `delay`
  (`src/seon/sci/eval.clj:147-205, 216-222`);
- one fork PER RUN, in the fold at `src/seon/cluster/loop.cljc:992`, with
  the comment that states the contract: "sci's fork copies the env, so a
  ctx per FORM would lose every def between forms… One fork per run is
  what makes a plan read like a REPL session: form 2 sees what form 1
  defined";
- `acquire!` (`eval.clj:726-890`) then installs, into that fork, the
  loaded first-party namespaces as host Vars plus every agent-authored
  `:seon.ns`/`:seon.fn`/`:seon.test` row, interpreted;
- the fork is dropped when the run ends. **Everything not a program row
  dies there.** That is precisely the owner's complaint.

Two costs of that shape, both measured (p1, p2): **78 KB and 183 ms per
run** for `acquire!`. The 183 ms is paid on every single turn of every
agent and buys a ctx that is discarded minutes later.

The crash model (`AGENTS.md`: "nothing re-executes; recovery = reopen the
store, mark dangling receipts `:interrupted`, re-derive") is not in
conflict with either route, but the boundary must be stated explicitly,
because replay-on-wake does re-execute something. The line is:

| Never re-executed | May be re-executed on wake |
|---|---|
| driver actions (claims, receipts, terminal transactions) | pure in-ctx `def`/`defn` forms |
| capability crossings (today: none exist; tomorrow: fs, web, llm, db writes) | pure computation over values |
| committed facts (messages the driver sent, program rows) | rebinding of scratch names |
| anything whose effect was already recorded | reads whose results are re-derivable |

The invariant survives verbatim for anything OUTSIDE the interpreter. The
relaxation is confined to the agent's own scratch namespace, and it must
be phrased that way in the architecture: **the driver never re-executes;
the agent's session may be re-derived.**

## 3. Route A — park the live ctx

Keep one forked-and-acquired ctx alive per agent, between episodes,
alongside the parked flow procs (`research/flow-mechanics-2026-07-28.md`:
two procs, ~8.5 KB per parked agent).

**Cost, measured (p1, k units built and held, GC'd before/after):**

```
bare fork (no acquire!)                    k=200  per-unit 0.1 KB
fork + acquire!                            k=200  per-unit 78.3 KB
fork + 20 tiny defs                        k=100  per-unit 5.6 KB
fork + 20 defns (interpreted)              k=50   per-unit 41.9 KB
fork + (def big (vec (range 10000)))       k=50   per-unit 285.2 KB
fork + (def big (vec (range 100000)))      k=20   per-unit 2872.2 KB
the same value alone, no ctx (control)     k=20   per-unit 2876.3 KB
```

Read those bottom two lines together: **a parked ctx costs the values the
agent chose to keep, and essentially nothing else.** That is the honest
answer to "is parking expensive?" — it is exactly as expensive as the
agent's own data, which is the same bill a real REPL session pays.

Extrapolated: 100 parked agents with 20 defs and 20 defns each ≈ 100 x
(78 + 5.6 + 42) KB ≈ **12.5 MB** today; under the interpreted-corpus
target (corpus installed once into the shared base,
`research/sci-precomputed-analysis-2026-07-31.md` §1.4) the 78 KB
`acquire!` share collapses toward zero and it is ≈ **5 MB**. Against
`-Xmx512m` that is not a constraint. The constraint is agents holding big
values, which is a per-agent policy question, not an architecture one.

**Route A's real prize is latency, not memory:** parking removes the
183 ms `acquire!` from every turn.

**What route A cannot do:**

- **Survive the process.** The ctx dies with the JVM. After any crash,
  restart, or hot-reload of `seon.sci.eval`, the session is gone unless
  it is also re-derivable — so **route B is required regardless**.
- **Be branched.** §1 and p5: forking a parked ctx does not isolate
  redefinition of names it already holds. A grader forking an agent's
  ending session would write into the agent's session. The grader's fork
  must be a REPLAY into a fresh ctx.
- **Survive a reload of its own namespace.** `docs/seon/issues/
  sci-eval-namespace-is-not-hot-reloadable.md`: reloading `seon.sci.eval`
  invalidates the `deftype` arm class, breaking every subsequent
  evaluation. That issue is a blocker for parking specifically because
  parked ctxs raise the cost of the failure from "next eval fails" to
  "every agent's session is lost, and we must be able to rebuild them" —
  another argument that route B is the floor.

**When is it safe to drop a parked ctx?** Never *needs* to be dropped for
correctness, because it holds no durable truth — this is exactly the
transport law's "losable by construction" tier (`AGENTS.md`). So the
lifecycle is an eviction policy over a re-derivable cache: drop on agent
pause/retire, drop under heap pressure, drop on corpus-basis change
(the ctx is keyed by the corpus attribute revisions,
`sci-precomputed-analysis-2026-07-31.md` §4.3). Every drop is safe
exactly because route B can rebuild it.

## 4. Route B — replay (and rehydrate) on wake

The replay artifact already exists: the run loop stores every form's
exact source with its ordinal and its receipt. Ruling #24's "one
artifact, two verbs" (print / eval) is literally this — replay is the
second verb over the bytes the transcript printer already reads.

**Cost, measured (p6, through the real door on a freshly acquired ctx):**

```
200 scratch forms (defs, defns, computations)   68.5 ms   0.342 ms/form
20 CONTRACTED defns                            609.7 ms  30.487 ms/form
```

and per class (p2, median of 9):

```
scratch def (small)                      0.127 ms
pure computation (reduce + (range 1000)) 0.224 ms
string work                              0.172 ms
message value (my.message/send)          0.204 ms
defn + :malli/schema                     21.6 ms      <- §5
```

So an ordinary form replays in **~0.3 ms**, of which the READER is the
bulk (0.31 ms measured standalone for a metadata-carrying defn source) —
consistent with `sci-door-ctx-sharing-2026-07-31.md`'s finding that the
reader, not the interpreter, is this pipeline's cost. **A realistic
200-form agent history replays in well under 100 ms** once §5 is fixed.
That is smaller than one `acquire!`.

**The large-value case — rehydrate, do not recompute.** Measured (p2):

```
recompute (vec (range 200000)) through the door        5.96 ms
rehydrate as an EDN literal (def big <1.29 MB of edn>) REFUSED:
  "Clojure source exceeds the declared character bound"
rehydrate by interning the host-side value (no eval)   0.027 ms
  and the next form sees it:  (count big) => 200000
```

Three findings in three lines:

1. recomputation is proportional to the original work and unbounded (the
   agent's `(def x (expensive-thing))` might have taken a minute);
2. **rehydration through source is a dead end** — the reader's character
   bound refuses a large literal, and even without the bound, round-
   tripping through EDN text is the slowest possible path;
3. **rehydration by interning the value is 0.027 ms and works**:
   `sci/add-namespace!` with a `sci/new-var` binds a host-side value into
   the ctx and the very next form resolves it.

That is the mechanism ruling #25's blob tier makes possible: the result
of a `def` is already being kept as a generous projection (blob, digest
and size), so **replay of `(def x <expensive>)` becomes "load the blob and
intern it"**, and the transcript's own facts say which. Note the caveat
inherited from §1: this works for DATA. A `defn` has no blob and no data
projection — it must be re-evaluated, which is what the 0.3 ms/form
number covers.

**Replay policy, per form, derived from the form's own recorded facts:**

| Form's recorded facts | Replay action |
|---|---|
| program row (`:seon.fn`/`:seon.schema`/`:seon.test`) | **skip** — `acquire!` already installs it from the row |
| pure form, no capability crossing, result blob present and the value is data | **rehydrate** — intern the blob-loaded value |
| pure form, no capability crossing, no blob (small/derivable) | **re-eval** |
| capability crossing recorded on the receipt | **do not re-eval** — intern the recorded result |
| errored / interrupted receipt | **skip** — it defined nothing |

Note the first row: the contracted `defn`s an agent wrote are ALREADY
persistent and already re-installed by `acquire!`. Replay is only ever
about the scratch tier — which is exactly the tier the owner is
complaining about, and is a small fraction of a real transcript.

## 5. The defect that dominates replay today

`(defn f {:malli/schema …} …)` through the door costs **21.6-30.5 ms**;
the identical `defn` without a contract costs **0.32 ms**. Broken down
(p3):

```
seon.sci.reader/read                          0.312 ms
seon.program/declaration-row                  0.004 ms
schema/projection-with-function-contract     44.596 ms   <- everything
full door eval                               27.695 ms
```

`projection-with-function-contract`
(`src/seon/schema.cljc:1965-1991`) rebuilds the WHOLE projection from
every registered schema form to admit one function contract — O(registry)
per agent `defn`. Filed:
`docs/seon/issues/contracted-defn-rebuilds-the-whole-schema-projection.md`.

It is not a replay problem: it taxes every live turn too, and it will
dominate the grader's surface-preparation runs (which are almost entirely
contracted defns). But it is the reason today's 36-form replay measured
190 ms instead of ~20 ms, so any replay design must be costed AFTER the
fix, not before it.

## 6. Safety: derived, or decorated?

The owner's concern is the missiles case — a replayed form that fires
something twice. The intended derivation is: effects flow through the ONE
capability door, therefore a form whose receipt records no capability
crossing is replay-safe by construction, and a form that crossed has its
recorded RESULT rehydrated instead. That derivation is sound. **It is not
yet available, because the door does not exist yet.** Measured through
the real door today (p4):

```
(seon.db/q …)                      => reaches seon.db; failed here only for
                                      lack of a bound connection (custody binds
                                      it in a real run) — i.e. READS work
(resolve 'seon.db/transact!)       => nil
(resolve 'datahike.api/transact)   => nil
(resolve 'clojure.java.io/file)    => nil
(slurp "deps.edn")                 => Unable to resolve symbol: slurp
(resolve 'seon.cluster/refresh-source!) => a clojure.lang.Var  <-- REACHABLE
```

Two facts to hold together:

- **there is no `seon.effect` namespace in the tree.** The agent-facing
  surface today is `my.message/send`, `my.message/decline`, `my.run/wait`,
  `my.run/complete` — all PURE functions returning values the driver
  interprets (`src/my/message.cljc:14-20`). By construction, an agent's
  eval performs no effect at all today, so *everything* in a current
  transcript is replay-safe;
- **but `acquire!` binds `ns-interns` of every loaded first-party
  namespace** (`eval.clj:655-679`, ruling #20 "agents call any
  function"), so effectful compiled functions ARE reachable by qualified
  name — `seon.cluster/refresh-source!` resolved in the probe. Nothing
  routes them through a door, and nothing records that they were called.

So the honest statement: **replay safety is derivable in the target
architecture and is trivially true today, but there is currently no
recorded fact that would let you derive it for a form that called a
compiled effectful function directly.** The derivation's prerequisite is
not decoration — it is that the crossing be recorded. Concretely, the
receipt needs a capability-crossing fact (present exactly when the form
crossed; presence is the state, per ruling 2026-07-28), written by the
one door.

**Do we still need a do-not-replay decoration?** The `^{:seon.workload
:io}` precedent (`research/workload-classification-2026-07-28.md`) is
instructive but points the other way: workload is annotated at *key
capability leaves* and DERIVED everywhere else by reachability over
`:seon.fn/calls`. The same two-seam shape applies here and needs no new
decoration at all:

- the door records the crossing on the receipt (the leaf fact);
- replay reads receipts, not annotations — the policy table in §4.

The one place a `^:seon.replay/never`-style marker might seem necessary
is a compiled first-party function that is effectful but does not pass
the door. That is not a case to decorate; it is a case to close, and the
closing rule already exists in ruling #20's shape: an effect that is not
recorded is an effect the crash model cannot see either. Recommendation:
**no hand decoration.** If an escape hatch turns out to be needed, it
should be one derived fact ("this fn's call graph reaches a capability
leaf"), computed the way workload is computed, not a list.

**Edge cases, checked:**

- **Nondeterminism is pinnable.** `(rand-int 1000)` works in the ctx;
  shadowing it per fork with `sci/add-namespace!` + `sci/new-var` made it
  return `7` (p2). So replay can pin randomness per ctx if it ever
  matters. It probably does not: replay's goal is to restore *bindings*,
  not to reproduce a bit-identical history, and the honest rule is that a
  rehydrated value beats a recomputed one wherever the value was kept.
- **Wall-clock is not even reachable.** `System/currentTimeMillis` =>
  "Unable to resolve symbol"; `(java.util.Date.)` => "Unable to resolve
  classname" (p2). Neither is in the base ctx's `:classes`
  (`eval.clj:194-197`). Time-dependent replay divergence is currently
  impossible by construction — worth preserving deliberately rather than
  by accident.
- **Reader state IS carried.** Namespace aliases, refers, imports and
  requires are projected per form into `:seon.ns` rows
  (`eval.clj:448-509`, `namespace-context-row`), so a `require` replays
  with the same resolver context it originally had. This is already
  built and is one of the reasons replay is faithful.
- **`defonce`**: sci's `clojure.core` provides it and it is idempotent by
  definition, so replay of `defonce` is a no-op on an already-populated
  ctx and correct on a fresh one. No special handling.
- **Ordering**: replay must preserve ordinal order (the transcript is
  ordered) and must run AFTER `acquire!`, since scratch forms may call
  contracted functions installed from rows.

## 7. The cache framing, and the recommendation

The framing that makes both routes one design: **the ctx env is a
materialized view of (base ctx + program rows + this agent's scratch
transcript).** Route A caches that view hot; route B rebuilds it from the
facts and blobs. Same view, two derivations — which is the ordinary Seon
shape (derive; cache the measured-expensive derivation; never bifurcate
into a stored-fast and a derived-slow *truth*).

**Recommended design.**

1. **Park the hot ctx per agent**, held beside the agent's parked flow
   procs, keyed by `[agent-id corpus-basis]`. Marginal cost ≈ the agent's
   own values; saves 183 ms per turn.
2. **Never fork a parked ctx.** The run uses the parked ctx AS GIVEN (the
   same rule `evaluate` already states for the per-run fork,
   `eval.clj:924-927`). One agent's runs are serialized by the run claim
   already, so there is no concurrent-writer problem to solve — and this
   sidesteps the §1 leak entirely.
3. **Rebuild by replay whenever the ctx is absent** — after a crash, a
   restart, an eviction, a corpus-basis change, or a
   `seon.sci.eval` reload. Replay is: fresh fork -> `acquire!` -> the
   agent's ordered scratch forms under the §4 policy table.
4. **Branch by replay, never by fork.** A grader that wants the agent's
   ending state replays that agent's transcript to the chosen ordinal on
   its own fresh ctx, on a Datahike branch forked from the corresponding
   commit (`plan/grader-in-fact-space-2026-08-01.md`). This is the
   answer to that plan's mid-run-probe question, and it is the only
   correct one given §1.
5. **Rehydrate blob-backed data defs** instead of recomputing them, by
   interning the loaded value (0.027 ms), once ruling #25's blob tier
   lands.

**Slice 1 (smallest thing that gives the owner the observable
behavior).** Park the ctx. Nothing else. Concretely: hold the
forked+acquired ctx on the agent's parked flow state instead of creating
it in the `:resume` branch of `loop.cljc:992`, re-acquire when the corpus
basis moved, and drop it when the agent stops. Acceptance: an agent
`(def x …)`s in turn 1 and reads `x` in turn 10 of a live drive; the
turn's `acquire!` cost disappears from the second turn onward. This slice
is small, is immediately visible to the owner, and commits us to nothing
about replay.

**Slice 2** is the §5 fix (it blocks honest replay costing and taxes
every live turn today). **Slice 3** is replay-on-wake with the §4 policy
table restricted to its trivially-safe subset (no capability door exists
yet, so every stored form qualifies) plus the loud refusal when a form's
receipt carries a crossing that the future door will record.

## 8. Open owner decisions

1. **Does a parked session survive an agent PAUSE, or only the gaps
   between turns?** The measurements say either is affordable; the
   question is semantic — is a paused agent's scratch state part of its
   identity, or does pausing mean "you will wake fresh, with your history
   readable"? Replay makes both implementable; only one should be the
   promise we teach.
2. **Do we promise session persistence across a restart at all?** Route B
   can rebuild it, but replay costs real time for expensive forms and can
   diverge if a form read the database (the world moved). The alternative
   promise — "your defs survive while the process lives; your HISTORY
   always survives, and re-running is one form away" — is simpler and
   never lies. Recommend the simpler promise first, with replay used for
   the grader's branch path where determinism is a non-issue.
3. **Is `acquire!`'s wholesale `ns-interns` binding of effectful
   first-party functions (ruling #20) intended to stay unrecorded?** It
   is the one hole in the derived-safety story, and it is also the one
   hole in the crash model's "nothing re-executes" claim: today an agent
   CAN call `seon.cluster/refresh-source!` and nothing records that it
   did.
