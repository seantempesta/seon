# Branch retirement and GC cost, 2026-07-27

## Verdict

Branch retirement is cheap enough to perform directly at cluster teardown;
full-store GC is not. Across three fresh-store executions, retiring five warm
clusters took **49.3–62.2 ms total** (9.9–12.4 ms per branch), reclaiming their
unreachable storage took **158.7–255.2 ms**, and an immediate no-op full-store
pass still took **57.0–100.0 ms**.

Run retirement casually, but coalesce and schedule GC at the process/store
level rather than running it after every cluster teardown. This small store
already pays a visible fixed full-reachability walk, and
`datahike.gc/gc-storage!` documents that its cost scales with all reachable
nodes across the roster. Scheduling is a latency decision, not a safety
workaround: the live branch heads remained intact.

## Reproduction

The durable script is
[`research/scripts/gc-cost-2026-07-27.clj`](scripts/gc-cost-2026-07-27.clj).
From the repository root:

```bash
clojure -M:dev -e \
  '(load-file "docs/prds/sci-execution-runtime/research/scripts/gc-cost-2026-07-27.clj")'
```

The script:

- recreates one `:file` store under `tmp/gc-cost/store`;
- builds a real schema-populated ancestor through
  `seon.cluster.ancestor/ensure!` and
  `seon.cluster/populate-ancestor!`;
- creates ten clusters through `seon.cluster.registry/ensure-cluster!`;
- writes 400 distinct `:seon.cluster.agent/id` datoms to each cluster in four
  100-datom transactions;
- releases every branch connection, retires five branches through
  `retire-branch!`, and collects through `collect!`;
- reopens and queries all five survivors after collection, comparing each
  exact 400-ID set rather than checking only a count;
- immediately runs a second collection with no additional retirees; and
- releases the store and deletes `tmp/gc-cost/` in `finally`.

The executions used Datahike fork commit
`357ffc87c8009f342b239145802e1385d4a18ca9` on Java 26.0.1, macOS/aarch64.

## Results

The primary run supplied the recorded size and safety evidence. Two independent
executions of the same command verified the result and exposed the wall-time
variance.

| Measurement | Primary | Verify 1 | Verify 2 |
|---|---:|---:|---:|
| Warm clusters | 10 | 10 | 10 |
| Retired / surviving clusters | 5 / 5 | 5 / 5 | 5 / 5 |
| Distinct workload datoms per cluster | 400 | 400 | 400 |
| Distinct workload datoms total | 4,000 | 4,000 | 4,000 |
| Retired / surviving workload datoms | 2,000 / 2,000 | 2,000 / 2,000 | 2,000 / 2,000 |
| Retirement time, five branches | 62.155 ms | 49.340 ms | 57.540 ms |
| Retirement time per branch | 12.431 ms | 9.868 ms | 11.508 ms |
| Reclaiming GC time | 255.249 ms | 158.653 ms | 191.291 ms |
| Objects swept | 331 | 331 | 331 |
| Immediate no-op GC time | 99.980 ms | 57.004 ms | 73.908 ms |
| Objects swept by no-op GC | 0 | 0 | 0 |
| Store size before retirement | 4.707 MB | 4.707 MB | 4.707 MB |
| Store size immediately before GC | 4.707 MB | 4.707 MB | 4.707 MB |
| Store size after GC | 2.559 MB | 2.559 MB | 2.559 MB |
| Bytes reclaimed | 2.148 MB (45.6%) | 2.148 MB (45.6%) | 2.148 MB (45.6%) |
| Store size after no-op GC | 2.559 MB | 2.559 MB | 2.559 MB |

Retirement itself changed only the roster record (4,706,989 bytes before
retirement and 4,706,878 bytes before GC). The collection reclaimed the
retired branches' unreachable tails.

## Safety proof

After GC, the five surviving branches remained in the roster and the five
retired branches were absent. Queries against survivors `gc-cost-5` through
`gc-cost-9` each returned exactly their expected 400 distinct IDs, for 2,000
surviving workload datoms total. The second GC swept zero objects and did not
change the store size.

No defect was observed, so this experiment files no issue note.
