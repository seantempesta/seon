## Naming — the one thing needing an owner word (ruling 5)

The r2 draft's key names were explicitly proposed, not ruled
(`ambient-injection-prd-2026-08-05-r2-draft.md:291-297` says "proposed"), and
`rg` finds no `:seon.ambient/*` anywhere in `src/`, `test/`, `resources/`, or
`config/`. Ruling 5 retires "ambient", so the implementation uses the literal
names the ruling itself supplies:

| r2 draft | landed | why |
|---|---|---|
| ambient injection | **call preparation** | sci's own name for the seam; ruling 5 verbatim |
| ambient value / battery | **supplied default** | ruling 5's "supplied defaults (not batteries)" |
| `:seon.ambient/key` | `:seon.call-preparation/key` | — |
| `:seon.ambient/schema` | `:seon.call-preparation/schema` | — |
| `:seon.ambient/provider` | `:seon.call-preparation/supplier` | see below |
| `seon.db/ambient-database-value` | `seon.db/supplied-database-value` | — |
| `seon.db/ambient-connection` | `seon.db/supplied-connection` | — |

**"provider" was deliberately not reused.** The maintained vocabulary table
already binds *provider descriptor row* to one hosted model provider's config
row under the config singleton. Two unrelated meanings of "provider" living in
`config/default.edn`'s initialization vector, three lines apart, is exactly the
drift the names-grounded rule exists to stop. "Supplier" is the verb form of
ruling 5's own "supplied defaults".

The ROW STRUCTURE is the sealed r2 structure unchanged: three facts (key,
value-schema ref, supplier ref), joined through `:seon.schema/shape`. Renaming
the keys later is a mechanical sweep of one schema resource, one namespace, one
config block, and one test.

## Amendments the implementation had to absorb

### 1. A supplier takes one argument: the environment (ruling 2)

r2 specifies a ZERO-argument provider reading `seon.db/*conn*`
(`:329-338`). Ruling 2 deletes that dynamic var and says providers read the
runtime ctx's environment. A zero-argument function cannot. So the coherence
contract becomes: **exactly one argument, declared `:seon.env/environment`**,
returning `[:or <the row's value schema> :seon.error/value]`. Everything else
about the coherence proof is r2's, and all of it is a query — argument count,
argument shape fingerprint, return type `:or`, and the exact two-arm child
fingerprint set.

This is the smallest faithful change: the environment is still not handed to
agent code (the container is a host record absent from sci `:classes`), the
supplier is still ordinary contracted data, and hot reload is still visible
because the symbol resolves live.

### 2. `snapshot` takes the projection

Validating a supplier's result against its declared value schema needs a
compiled validator, and derived state hangs off the value it derives from — so
the snapshot compiles one validator per admitted row from the acquired
projection and carries it. A value schema the projection **cannot** compile is
a refused row, not an exception: found by the suite, fixed at the seam.

## Two `seon.cluster.clj` defects found on the way

Both are the "first time this branch ever ran" species.

1. **The lookup-ref refusal builder never worked** (`src/seon/cluster.clj:851`).
   It composed bare `distinct` — the one-argument COLLECTION arity — into a
   transducer `comp`, so instead of naming the unresolved lookups it threw
   `ClassCastException: LazySeq cannot be cast to IFn`. Fixed to `(distinct)`;
   the very next run printed the honest refusal, which is how the second defect
   was found in one step.

   Residual honesty gap, NOT fixed (out of slice, worth an issue): the refusal
   lists every lookup ref of every waiting row, resolved or not, so it
   over-reports. The four names it printed included two that resolved fine.

2. **Initialization rows were transacted BEFORE program rows**, so a declared
   row could never name a function by lookup ref. Moved to the end of
   `populate-source!`. Nothing earlier in that population reads a config fact —
   `rg "config/" src/seon/fn.clj src/seon/cluster/instruction.clj` is empty —
   so the move costs no dependency.

   **This is the sequencing incident the orchestrator flagged mid-lane.** The
   config rows were briefly in the working tree before the reorder landed and
   refused every db-backed fixture at `cluster.clj:443`. `config/default.edn`
   was restored to HEAD within a minute of the flag, the fix landed as its own
   committed slice, and the rows were re-added last with a fixture-boot proof
   in the same beat. The general rule this establishes: **a declared row that
   names a program row by lookup ref may only be added after a publication
   containing that function.**

## The plan derivation, and what the facts actually support

Probed live on cluster `default` before writing any code — every join below
returned real rows at basis 536871068:

- **positional address**: `:seon.schema/key` → `:seon.schema/shape` →
  `:seon.fn.argument/schema` → argument index. 33+ first-party functions
  declare `:seon.db/database-value` as a complete positional slot, including
  `seon.sci.kernel/ensure-function!` at index **1** — a middle slot, so the
  unique-expansion rule (Choice 2 Option A) is load-bearing, not theoretical.
- **map-entry address**: argument shape `:seon.schema.shape/entries` →
  `:seon.schema.map-entry/key-keyword` + `:seon.schema.shape.entry/schema`.
- **the ruled two-part join is necessary, with a live counterexample**:
  `seon.cluster.wake/route!` declares a required key
  `:seon.cluster.wake/connection` whose value shape IS `:seon.db/connection`.
  Matching on shape alone would fill a key nobody declared as a default.
  Selection therefore joins BOTH the declared key and the value shape, exactly
  as r2 says (`:341-343`).
- **return-arm coherence**: `:seon.fn.arity/return-schema` →
  `:seon.schema.shape/type` `:or` → two `:seon.schema.shape.child` shapes.
  Verified on `seon.db/connection-identity`: children
  `a36fe1e6…` (its value) and `6ad943d5…`, which is exactly
  `:seon.error/value`'s registered shape fingerprint. Refs converge on the same
  content-addressed shape, so the equality test is sound.
- **`get-else` and a blank attribute position both work in Datahike**:
  `[(get-else $ ?arity :seon.fn.arity/max -1) ?max]` distinguishes variadic
  arities, and `[?function _ _ ?tx]` gives the contract transaction.

### Cache key and the basis boundary

Key is r2's `[function-identity contract-t row-basis-t]`, held one entry per
identity so a redefinition replaces rather than accumulates. `contract-t` is
`(max ?tx)` over the function entity's own datoms; `row-basis-t` is `(max ?tx)`
over the declared row attributes, read from the **history** view so a
RETRACTION moves it (a store without history falls back to the current value,
which still moves on every assertion). The watched attribute set is read from
the `:seon.call-preparation/row` declaration — a query, not an embedded list.

The listener is registered but is explicitly the optimizer. Correctness is the
per-invocation basis comparison, and the suite proves both directions with no
sleep: a row committed after a warm plan is seen synchronously, and an
unrelated transaction re-derives the snapshot once while leaving the row basis
— and therefore every compiled plan — unchanged.

## The finding S2 most needs

**sci's hook fires only when the resolved callee is a `sci.lang.Var`**
(`reference-code/sci/src/sci/impl/analyzer.cljc:1752`, `utils/var?` at
`utils.cljc:381-382`). A raw `clojure.lang.Var` placed directly into
`:namespaces` is never prepared — the first probe silently no-opped for
exactly this reason.

Production is FINE: `seon.sci.eval/forwarding-host-var` (`:819-825`) installs
every loaded first-party function as `sci/new-var` over the real JVM Var, with
`:ns` set to a sci namespace whose name is the first-party namespace. So
`var-symbol`, which reads `:ns`/`:name` from the callee's metadata, returns the
true program identity for both interpreted and compiled first-party functions.
But it means **r2's "compiled first-party" behavior-matrix row is a real test,
not a formality**, and any future binding path that hands sci a bare JVM Var
silently opts that function out of call preparation. The S1 probe binds its
callees the production way for this reason.

## Ugly output observed (standing order)

1. **The declaration-population fallback warning is a wall.** One four-query
   REPL probe emitted ten `DECLARATION POPULATION FALLBACK ×N` stderr lines
   before its result; `bin/test` interleaves them into test output. Already a
   dispatched follow-up on the seon.env PRD; this lane is another data point,
   and the specific new caller it named (`seon.call-preparation`
   `row-attributes`) was fixed by reading the declaration once behind a
   `delay`, the same shape `seon.env/declared-members` uses.
2. **A `ClassCastException` where a refusal belongs** (`cluster.clj:851`,
   fixed here). The failure face for "your initialization rows do not resolve"
   was a Clojure internals cast error naming neither the rows nor the lookups.
3. **The lookup-ref refusal over-reports** (above): it lists resolved lookups
   alongside unresolved ones, so the reader cannot tell which one blocked.
4. **`seon.db`'s missing-custody error exposes `seon.db/*conn*`** in its
   message and its `:seon.db/binding` data — r2's own output-quality finding
   (`:815-824`). The new suppliers do not: `:seon.db/unsupplied-custody` names
   the environment and the remedy, and the suite asserts the absence of the
   binding key so the old face cannot creep back.

No token-size explosion observed: the plan value for a two-arity function is a
few hundred bytes and the snapshot holds two rows.

## A publication blocker this slice exposed, isolated by experiment

`bin/seon init` on the SHARED root refuses while the same tree publishes
cleanly on a fresh root. The decisive pair, run minutes apart at commit
`01acb17ba`:

| Root | Result |
|---|---|
| `bin/seon --root tmp/p17-verify init`, no live JVM | publishes, twice — the second into the branch the first created |
| `bin/seon init`, shared root with a live `default` cluster | `:malli.core/register-function-schema` for `seon.call-preparation/plan` fails with `:malli.core/invalid-schema {:schema :seon.call-preparation/state}` |

So it is neither the tree nor an existing-branch problem. Registering a
function schema whose contract names a NEW `[:fn]` schema resource resolves
against the registry a LIVE cluster acquired at boot, which predates the
resource. `(require 'seon.call-preparation :reload)` in that JVM makes
`(m/schema :seon.call-preparation/state)` succeed and does NOT fix the
publication, so it is the bound projection, not namespace loading.

This is the standing issue
[a schema resource edit bricks value admission in every running cluster](../../../seon/issues/a-schema-resource-edit-bricks-value-admission-in-every-running-cluster.md)
observed at the publication seam rather than the admission seam. Remedy for
the shared root today is a JVM bounce; the durable fix belongs to that issue's
owner, not to P17. Any lane adding a new predicate-backed schema resource will
hit it, so it is worth pricing there.
