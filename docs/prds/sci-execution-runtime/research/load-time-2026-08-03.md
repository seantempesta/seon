# Load time after dependency-closure caching

## Owner acceptance boundary

The 2026-08-03 ruling supersedes the flat ten-second first-boot law. A cold
boot may spend time deriving and compiling the dependency closure when all
work is visible. The active acceptance criteria are:

- second and later boots reuse the dependency class cache;
- every published boot-tower boundary is visible on operator stdout; and
- the standalone artifact carries the same dependency classes so reopening a
  production root benefits too.

First-party Seon namespaces remain source-loaded for hot redefinition. The
whole-tree AOT option remains rejected: this core.async pin compiles `go`
blocks to IOC and does not provide the virtual-thread behavior that whole-tree
AOT was expected to preserve.

## Starting point

Commit `9bb559df9` supplied the essential derived mechanism: a fresh child JVM
requires `seon.artifact`, observes dependency source namespaces actually
loaded, compiles those namespaces into an empty candidate directory, rejects
missing loader classes or any first-party loader class, and atomically admits
the validated directory. It also put the admitted directory first on the
development classpath.

What remained was boot-time reuse and invalidation. Nothing checked whether an
admitted cache still matched the current project inputs, the operator did not
prepare a missing or stale cache, and the standalone artifact did not include
the admitted dependency classes. The initial admitted cache also predated the
current closure: it held 362 namespaces while a refresh derived 405.

The 2026-08-02 source-load profile measured 11.8 seconds total. The largest
exclusive contributors were `konserve.tiered` at 1,154 ms,
`datahike.connector` at 851 ms, and `superv.async` at 588 ms, versus the
first-party `seon.cluster` at 259 ms. This is why the cache owns the stable
dependency closure and leaves first-party source alone.

## Measurement method

Each sample used a fresh JVM and timed `(require 'seon.artifact)`. The
source-only condition removed `target/dev-dependency-classes` from the
effective development classpath. The stale-cache condition used the admitted
362-namespace directory already present on this tree. The refreshed condition
followed `clojure -T:dev-cache refresh`, which derived and compiled 405
dependency namespaces. “Load” is the inner Clojure elapsed time; “wall” is the
whole child-process time.

| Condition | Run | Load | Wall |
|---|---:|---:|---:|
| Source only | 1 | 10,162.688 ms | 10.54 s |
| Source only | 2 | 10,612.236 ms | 11.00 s |
| Source only | 3 | 10,328.367 ms | 10.75 s |
| Stale 362-namespace cache | 1 | 5,825.187 ms | 6.22 s |
| Stale 362-namespace cache | 2 | 5,443.903 ms | 5.86 s |
| Stale 362-namespace cache | 3 | 5,364.382 ms | 5.77 s |
| Refreshed 405-namespace cache | 1 | 4,108.954 ms | 4.52 s |
| Refreshed 405-namespace cache | 2 | 3,114.065 ms | 3.53 s |
| Refreshed 405-namespace cache | 3 | 3,201.128 ms | 3.62 s |

The load-time medians are the concise result: **10.3 seconds from source, 5.4
seconds with the stale cache, and 3.2 seconds with the refreshed cache**. The
load-time means are 10.368, 5.544, and 3.475 seconds respectively. Refreshed
cache reuse reduced median load by 7.127 seconds, or 69.0%, relative to source.

The first refresh observed during this work took 21.822 seconds. Later refresh
runs under shared-tree load took approximately 25–28 seconds. The final
invalidation proof under current shared-machine load rebuilt 405 namespaces in
39.898 seconds; its immediate second `ensure-cache` invocation returned
`:current` in 0.6 seconds wall time. That variable cold cost is accepted only
because it is announced and reused.

## Implemented boundary

Cache format version 2 records both the derived dependency-source digest and a
project-input digest over `deps.edn` plus first-party `.clj` and `.cljc`
sources. `ensure-cache` admits an existing cache only when the format, project
inputs, selected dependency source bytes, and every expected loader class
match. Otherwise it visibly rebuilds the closure. Recording the project digest
before compilation is deliberate: source churn during a long build makes the
result stale on the next check instead of silently declaring it current.

Cold operator launch invokes that one target and streams its output. Cache
discovery and compilation therefore no longer look like a silent Java hang.
The standalone artifact build invokes the same target and copies the admitted
dependency classes before first-party source and resources; it does not compile
first-party namespaces.

The existing boot publication seam now derives a phase from each successively
published cluster instance and emits exactly one event when that phase changes.
The operator carries those events over its existing readiness socket and
prints one line for `namespaces`, `repl`, `store`, `branch`, `recovery`,
`config`, `program`, `work-launcher`, `agents`, `web`, and `ready`. Adding a
cluster to an existing JVM observes the same publication seam through its
existing prepl output.

## Deferred coherent-boundary proof

Per the 2026-08-03 orchestration boundary, this lane does not claim the two
remaining checks:

- build and inspect the standalone artifact, then measure artifact cold boot
  and reopening an existing isolated root; and
- rerun the focused `seon.cluster.boot-test` and
  `seon.dev.fresh-operator-test` gate after the other lane's in-flight
  `seon.effect/request!` arity change becomes coherent.

Earlier production artifact evidence remains only the motivating baseline:
20.7 seconds cold and 13.4 seconds reopening. The new artifact/reopen delta is
intentionally unmeasured here and must not be inferred from the development
require measurements.
