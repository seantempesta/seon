# B2 implementation plan — config→facts, schema EDN, and the shared bootstrap ancestor (2026-07-27)

This is the PLAN for the B2 rung, written for the orchestrator to review and
fix before it authors sealed contracts. It contains no production code
changes. Every claim is grounded in `file:line` from the quarry, from
`reference-code/`, or from an executable probe committed under `tmp/b2-probe/`
whose output is pasted below.

**AMENDED 2026-07-27 (owner design challenge + new standing ruling: Datahike is
PART of Seon — calling internal functions is sanctioned, a small fork change is
acceptable when it buys real isolation, konserve stays the default backend).**
Section 0 evaluates one physical store with clusters as BRANCHES against the
clone design. **Branches win, conditional on one named fork change.** The clone
design survives as the fallback and as the permanent mechanism for export,
import, and moving a cluster to another process — read §0 first, then §5.

**The one-sentence answer to the original question:** a Datahike `:file` store
directory CAN be cloned to a new path and opened as a distinct store, but only
after its `:db` branch head's stored `[:config :store :id]` is rewritten —
otherwise `d/connect` refuses with `:store-identity-mismatch`
(`reference-code/datahike/src/datahike/connector.cljc:160-169`). Measured:
clone + re-identify + connect = **68 ms** for a 15,000-datom ancestor, against
**2,261 ms** to create and re-transact the same rows — a 33× fork. A branch-off
of the same ancestor is **17 ms and writes one blob**.

## 0. Branch-per-cluster evaluation

Probes: `tmp/b2-probe/branch_probe.clj`, `tmp/b2-probe/branch_gc_probe.clj`.

### 0.1 Verdict first

**ADOPT branch-per-cluster, conditional on one named fork change**
(§0.6). Keep clone for export, import, base-building, and moving a cluster to
another process (§0.8).

The isolation gate is the requirement "one cluster must never take down or
corrupt another." The evaluation turned on one question — *how much mutable
state do two branches of one store actually share?* — and the answer from
source is: **exactly one key, `:branches`, touched only on cluster
create/delete.** Everything a running cluster writes is either a
content-addressed immutable value or **its own** branch-head key
(`reference-code/datahike/src/datahike/writing.cljc:503-552`: values first,
commit record content-addressed, then `k/assoc store (:branch config)
db-to-store` — the branch's own key and nothing else). Two clusters transacting
concurrently touch **no** shared mutable durable state.

That one shared key is currently unsafe, and the probe proves it (§0.3). It is
also the smallest possible fork fix, and the fork already contains the exact
idiom to fix it with (§0.6).

### 0.2 Shared-state inventory, with blast radius

| Shared point | Source | Mutated by | Blast radius |
|---|---|---|---|
| **`:branches` roster** | `versioning.cljc:257` (`k/update … conj`), `:289` (`disj`), `writing.cljc:711` (genesis) | every `branch!` / `delete-branch!`, from ANY connection to the store | **CATASTROPHIC and PROVEN (§0.3):** read-modify-write race silently drops a branch from the roster; GC's whitelist is the roster (`gc.cljc:136-143`), so the dropped cluster's data becomes collectable. Silent loss of a whole cluster |
| **GC mark set** | `gc.cljc:136-143` unions `reachable-in-branch` over EVERY branch in the roster | any `gc-storage` call | **SAFE BY CONSTRUCTION.** Collection can never take data reachable from another branch's head, because the mark is a union over the whole roster. A branch head is seeded unconditionally (`gc.cljc:26,60-70`), so even a dormant cluster's head data is always retained; `remove-before` gates only whether *parents* are followed (`gc.cljc:41-42,72`), i.e. history depth, never head data. **Proven in D'** |
| GC cost | same | any GC | Shared: one pass walks every cluster's reachable set. Cost and pause scale with TOTAL data, not per cluster |
| GC write guard | `gc_guard.cljc:52` — `in-flight` atom keyed by store-id | `branch!`, `force-branch!`, `commit!`, `create-database` | Correctly shared and correctly keyed; its own comment (`gc_guard.cljc:47-50`) documents that separate connections to one physical store hold DIFFERENT konserve store instances — which is precisely why §0.3 races |
| konserve `DefaultStore` (cache, handlers, `:locks`, write-hooks) | `konserve/impl/defaults.cljc:736-774` | per connection | **NOT shared between branch connections** — `(identical? (:store @cl) (:store @cr))` is **false** (probe C'). So per-key application locks do not serialize across branches. Same resource-coupling profile as separate stores |
| konserve per-blob `FileLock` | `konserve/impl/defaults.cljc:303-351`, `filestore.clj:365-436` | every key write | Held across the read-modify-write inside one `io-operation`, but the write completes by atomic-move over the key (`filestore.clj:196-200`), so the lock is on the replaced inode — it does **not** make `k/update` atomic across store instances. §0.3 is the empirical proof |

| `delete-database` | `writing.cljc:717-731` | any caller with a config | Whole store. Under branches, "reset one cluster" must be `delete-branch!` + `branch!`, **never** `delete-database` |

### 0.3 THE DEFECT: concurrent `branch!` silently loses clusters

Twelve concurrent `branch!` calls issued alternately from two branch
connections of one store:

```
C'. two connections share one raw konserve store? false
C'. {:attempted 12, :outcomes {:ok 11, :err 1},
     :in-roster 9, :lost 3, :head-blobs-written 12}
C'. ORPHAN RISK: head records written but missing from :branches = 3
```

Eleven callers were told `:ok`; **nine branches exist**. Three head records
were written and then erased from the roster by a concurrent read-modify-write
on `:branches`, leaving three orphan blobs that the next GC sweeps. A caller
that successfully created a cluster can find it gone.

This is the L6 scar reproduced at branch granularity, and — importantly — it
occurs **inside one process**, which the flock does not fence.

### 0.4 The L6 scar and the process topology

The 40/40 commit loss was two JVMs writing one store, on the same `:db` branch;
Datahike states the model plainly — all writers for a database run in one JVM
and coordinate in memory, not through the store
(`gc_guard.cljc:36-41`, `gc.cljc:105-115`, `writing.cljc:321-348`).

Branch-per-cluster **plus one process-level flock on the whole store** covers
L6 *more* completely than the clone design does: one lock instead of N, and the
"orphan JVM" accident cannot reach any cluster. What it does **not** cover is
§0.3, which is a new in-process hazard that the clone design does not have (two
separate stores have no shared roster). Hence the fork change is not optional.

**Topology consequence, stated plainly:** one store means every cluster on it
lives in one process, permanently — they cannot later be split across processes
without an export/import. Given O1 (agent evals co-located with the database)
and B0 (one JVM already hosts N cluster instances, sharing heap, executors and
Datahike's process-wide caches), this matches the shape the system already has:
cluster isolation today is *durable-data* isolation, never liveness isolation.
The escape hatch is real and cheap — clone/export moves one cluster to its own
store and process (§0.8) — so this is an accepted constraint, not a trap.

### 0.5 Lifecycle costs, measured

```
A. ancestor branch :db built: 1720.7 ms, rows: 5000, blobs: 358, bytes: 2980201
A. branch! cluster-a: 17.9 ms   cluster-b: 16.7 ms
A. blobs after two branch-offs: 360   bytes: 2983421   roster: #{:cluster-a :db :cluster-b}
B. distinct connections? true   a-rows: 5000   b-rows: 5000
B. after divergent writes  a: 5500  b: 5500  base: 5000
B. a sees b's rows? false   b sees a's rows? false
E. two BRANCHES of one store, 2x2000 rows: 1463.4 ms
E. two SEPARATE stores,     2x2000 rows: 1329.9 ms   (ratio 1.10)
```

Branch-off is **17 ms and +1 blob (+1.6 KB)** — genuinely zero-copy and
backend-agnostic, against clone's 68 ms which depends on APFS/XFS/btrfs
reflink and degrades to a full byte copy elsewhere. Two branch writers are
independent (`writer.cljc:282-306`: one `LocalWriter` per connection) and cost
10% against two separate stores, attributable to the shared store-directory
fsync after every atomic move.

### 0.6 The named fork change (the condition on the verdict)

**Serialize `:branches` mutation per physical store, in Datahike.**

`branch!` and `delete-branch!` must take a process-level lock keyed by
**store-id** around their `k/update store :branches …`
(`versioning.cljc:255-257`, `versioning.cljc:289`). The fork already owns this
exact idiom for exactly this reason: `gc_guard.cljc:52` keeps an `in-flight`
atom keyed by store-id, with a comment
(`gc_guard.cljc:47-50`) stating that separate connections to one physical store
hold different konserve store instances and must therefore coordinate on the
store id rather than the store object. The fix is that comment applied one key
over: ~15 lines, one new keyed lock, two call sites.

Rejected alternative: sharing one `DefaultStore` per physical path in konserve.
It would fix the race via the per-key lock, but it merges caches, handlers and
write-hooks across branches — a much wider change with its own coupling, for
the same result.

Additional Seon-side conditions, enforced by construction rather than
discipline:

1. **Branch lifecycle has one owner.** `seon.cluster.registry` holds the only
   connection that ever calls `branch!` / `delete-branch!`. Cluster code
   receives a branch connection and never the branch API, so cluster A holds
   no handle that can delete cluster B.
2. **`delete-database` is never called.** Cluster reset is `delete-branch!` +
   `branch!` from the ancestor commit. Store deletion is an operator-only
   whole-system action.
3. **GC has one owner per store**, the process, not a cluster.

### 0.7 GC isolation, proven

`delete-branch!` removes the branch from the roster only; data survives until
GC (`versioning.cljc:261-289`). Then:

```
D'. ancestor rows: 5000   blobs: 358   bytes: 8126727
D'. after both tails: {:blobs 636, :bytes 15426243}   keep: 7000   doomed: 7000
D'. roster after delete-branch!: #{:db :keep}
D'. gc swept objects: 139
D'. blobs 636 -> 497   bytes 15426243 -> 11776478
D'. keep branch rows: 7000  sees ancestor 4999? true  sees own 101999? true
D'. base :db rows: 5000     sees ancestor 4999? true
D'. reconnect to DELETED :doomed -> {:err "Database does not exist.", :type :db-does-not-exist}
D'. second gc swept: 0   (idempotent)
D'. keep still whole? 7000   base still whole? 5000
```

The doomed cluster's unshared tail (3.65 MB, 139 objects) was collected; the
surviving cluster kept both its own writes and the shared ancestor rows; the
ancestor branch was untouched; a second pass swept nothing. **This is the
requirement's strongest evidence in favour of branches** — collection isolation
is structural, not a policy we have to maintain.

### 0.8 What clone is still for

Clone + `reidentify!` (§5.5) stays in the design, unchanged, for the three jobs
branches cannot do:

- **export / backup** — a self-contained store directory for one cluster;
- **import / move to another process or machine** — the escape hatch from
  §0.4's topology constraint;
- **building a new base system** — an ancestor store produced offline and
  shipped, then adopted as a branch source.

It is not the per-cluster creation path.

### 0.9 Scorecard against the gate

| Property | Branches (+ fork change) | Clone-per-store |
|---|---|---|
| one cluster corrupts another's data | shared mutable surface = 1 key, fenced | impossible — no shared file |
| one cluster collects another's data | impossible by construction (§0.7) | impossible |
| one cluster takes another down (liveness) | same JVM either way | same JVM either way |
| whole-directory disaster | all clusters | one cluster |
| creation cost | 17 ms, 1 blob | 68 ms, reflink-dependent |
| ancestor stored | once, structurally shared | once per CoW clone; N copies without reflink |
| backend-agnostic | yes | no — OS/filesystem specific |
| needs stored-data rewriting | no | yes (`reidentify!`) |
| clusters splittable across processes later | no (export required) | yes |
| write throughput, 2 concurrent | 1.10× | 1.00× |

## 2. The decisive experiments

### 2.1 A cloned store refuses to open under a path-derived id

`ensure-stored-config-consistency` compares the stored `[:store :id]` against
the connect-time `[:store :id]` and raises when both are present and differ
(`reference-code/datahike/src/datahike/connector.cljc:160-169`). The rest of
`:store` — including `:path` — is deliberately excluded from the comparison
(`connector.cljc:171-174`). B1 derives `:id` from the canonical path
(`src/seon/cluster/store.clj:139-140`), so a clone at a new path always
mismatches.

```
== 2. stored config of A (what the clone carries) ==
{:ok {:backend :file, :path ".../stores/a", :id #uuid "f35ddf4e-...-6b9a47e82812"}}

== 4. connect B with PATH-DERIVED id (B1's datahike-configuration) ==
{:err "Store identity mismatch: connecting to wrong database.",
 :type :store-identity-mismatch,
 :data {:stored-id #uuid "f35ddf4e-...", :connect-id #uuid "769a5e15-..."}}
```

### 2.2 `:allow-unsafe-config` is NOT the fix — it poisons the store

Setting the flag skips the whole check, but the flag then rides the live
config into the next commit's stored `:config`
(`reference-code/datahike/src/datahike/writing.cljc:48-70` persists the db's
`config`), so every later flag-free connect fails a *different* way:

```
== 6. connect B with path-derived id + :allow-unsafe-config true, transact, release ==
{:ok {:stored-store {...}, :stored-unsafe true}}

== 7. reconnect B WITHOUT the flag ==
{:err "Configuration does not match stored configuration...",
 :type :config-does-not-match-stored-db,
 :data {:diff (nil {:allow-unsafe-config true} {...})}}
```

**Verdict: reject.** It converts a one-time fork problem into a permanent
config asymmetry.

### 2.3 Konserve-level re-identify works, is durable, and is fast

Rewriting `[:config :store :id]` (and, for honesty, `[:config :store :path]`)
in the `:db` branch head with one `k/get` + `k/assoc` before the first
`d/connect` makes the clone an ordinary store. Reads, writes, history, and
plain reopen all behave:

```
== 8. clone A -> C, konserve-level re-identify, then PLAIN connect ==
{:ok {:facts-before 1, :facts-after 2}}
== 9. reopen C plainly again (durability of the re-identify) ==
{:ok {:facts 2}}
```

At scale (5,000 indexed functions = 15,000 datoms, 3.2 MB on disk):

```
ancestor build ms: 2527.0   datoms: 15000   on-disk bytes: 3200271
FORK  clone-ms: 52.3  reidentify-ms: 13.8  connect-ms: 1.5  query-ms: 189.5
      fns-found: 5000  after-write: 5001  history-visible: 5001
FORK  total-to-usable-ms: 67.6
REOPEN fork ms: 14.0  fns: 5001
ANCESTOR after fork, fns: 5000        <- ancestor untouched (O2 holds)
RETRANSACT create+load ms: 2260.9     <- the alternative we are replacing
```

### 2.4 A shared `:id` across two paths refuses loudly (so it is not an option)

If the ancestor's id were simply reused, two clusters in one JVM would collide
on Datahike's `[store-id branch]` connection id
(`reference-code/datahike/src/datahike/store.cljc:50-61`). Probe 10 confirms
the second open is refused, not silently aliased:

```
== 10. two stores, SAME :id, different paths, both open in one JVM ==
{:err "Configuration does not match existing connections.",
 :type :config-does-not-match-existing-connections}
```

Good news for safety; fatal for a shared-id design. **Re-identify is mandatory,
not optional.**

### 2.5 "Converged = zero writes" cannot mean "transact an empty plan"

This is the result that shapes the config contract. Datahike commits a
transaction entity even for empty tx-data, and even when a `[:db.fn/call …]`
returns no operations:

```
after write : {:t 536870914, :datoms 11}
empty tx-data -> {:t 536870915, :datoms 12}  same-as-before? false   (report tx-data count: 1)
db.fn/call -> [] -> {:t 536870916, :datoms 13}  same-as-after-write? false
re-assert identical value -> {:t 536870917, :datoms 14}
```

Two consequences:

1. **The converged check must happen BEFORE any transact.** `reconcile!`
   computes its plan purely against a database value; an empty plan returns
   `{::converged? true ::operations 0}` and issues **no transaction at all**.
2. Re-asserting an identical value writes no *domain* datom (13→14 is only the
   tx's `:db/txInstant`), so per-attribute equality diffing is partly free —
   but the transaction is not. The acceptance measure is "basis transaction
   `:t` is unchanged after a converged re-apply", which is directly
   observable.

## 4. Data model sketch

### 4.1 Bootstrap phase (pre-store, closed, already exists)

`:seon.boot/config` in `src/seon/cluster.clj:67-74` — five keys, closed. B2 adds
**one** key, and only because the fork must happen before the store opens:

```clojure
; the ONE physical store this process owns; every cluster is a branch of it.
; Derived from :seon.boot/root by convention, overridable for tests.
[:seon.boot/store-dir {:optional true} [:string {:min 1}]]
; the ancestor branch a NEW cluster branches from; absent = :db
[:seon.boot/ancestor-branch {:optional true} :keyword]
```

Note what this replaces: under branch-per-cluster the store is **per process
root**, not per cluster, so B0's `cluster-paths` keeps the cluster directory
(logs, advertisement) but its `:seon.boot/store-dir` moves up to the root. That
is a B0 contract revision, named in §11.

A `--config <path>` manifest path is a *launch argument*, not a bootstrap
config key: it is consumed once by `bin/seon start` and never read again
(runtime reads the database).

### 4.2 Database phase — the config singleton

One entity per store, identified by the cluster name so the upsert handle is a
real identity attribute rather than a magic sentinel:

```clojure
:seon.config/cluster    [:string {:min 1 :seon.db/identity true}]
:seon.config/applied-manifest-digest [:re "[0-9a-f]{64}"]   ; provenance, not a gate
```

Every dial is its own attribute on that entity, each with its own registered
schema — the pattern quarried from `src-old/seon/config/resolve.cljc:98-103`
("register once, reference everywhere"), which is right and survives. The dial
population itself starts near-empty in B2: the honest list today is
`seon.flow`'s 60 registrations (`src/seon/flow.clj`) plus
`:seon.config/on-core-error`. **B2 does not port State A's 39
`operational-keys`** (`src-old/seon/config/resolve.cljc:542-580`); those name
transport, UDS, executor and pod machinery that no longer exists.

### 4.3 Ancestor facts (written by the build, read by every fork)

```clojure
:seon.ancestor/digest   [:re "[0-9a-f]{64}"]   ; identity of the indexed inputs
:seon.ancestor/built-at :inst
```

These ride in the ancestor store itself, so a forked cluster can answer "what
was I born from?" as a query with no file read.

### 4.4 What is deliberately NOT an attribute

- no `:seon.config/converged?` — converged is a computed comparison, never
  stored;
- no `:seon.ancestor/forked?` boolean — B1's `:seon.store/created?` plus the
  ancestor digest fact already carry it;
- no applied-manifest *file*. State A's `publish-applied-manifest!` /
  `delete-applied-manifest!` (`script/seon/dev/cluster.clj:505`) is a second
  state authority beside the database. **Dead.**

## 5. The shared bootstrap ancestor — branch-per-cluster

**Rewritten for §0's verdict.** One physical store per process root; the
ancestor is a branch; each cluster is a branch off it. Clone survives as §5.5.

### 5.1 The shape

```
data/store/                     ONE physical store, ONE flock, ONE process
  branch :ancestor-<digest>     built once, never written to again
  branch :cluster-default       branched from :ancestor-<digest>
  branch :cluster-alice         branched from the same ancestor commit
data/clusters/<name>/           logs + prepl advertisement only (B0 keeps this)
```

The ancestor is a **branch**, not a directory, so a cluster's creation is one
konserve write (17 ms) instead of a file copy, and the ancestor's bytes are
stored exactly once for every cluster that descends from it — structural
sharing, on any backend.

### 5.2 Ancestor identity — a digest of the inputs, not of an artifact

State A keyed the template by `(application-digest, cluster-name)`
(`script/seon/dev/cluster.clj:43-56`). Both halves are baggage:

- the *application digest* came from the AOT/Shadow artifact chain, which the
  2026-07-27 build ruling condemns and which does not exist in dev;
- the *cluster name* was needed only because State A derived the store id from
  the database name (`src-old/seon/db/backend.clj:105-109`), so a template had
  to be built per name. A branch is name-free.

**Proposed:** `ancestor-digest` = SHA-256 over the sorted sequence of
`[resource-path, sha256(source-bytes)]` for every indexed `.clj`/`.cljc` under
`src/`, plus every `src/seon/schema/*.edn`. Pure, cheap (the indexer already
computes per-file digests — `script/seon/dev/program_indexer.clj:40-47,75-91`),
and true in dev with no build artifact. The ancestor's branch name is
`:ancestor-<digest>`, so the digest is discoverable from the roster alone.

### 5.3 Build half

One deliberate command (`bin/seon build-ancestor`, or `bin/seon start`'s
first-run path), all of it under the store's one flock:

1. compute `ancestor-digest`; if `:ancestor-<digest>` is already in `:branches`,
   stop — the roster is the whole cache;
2. branch a scratch `:building-<uuid>` off `:db` (the empty genesis branch);
3. connect to it and transact, in order: the schema population from
   `src/seon/schema/*.edn` (§6), the program-graph rows from the indexer, the
   ancestor facts (§4.3);
4. release the scratch connection, then `branch!` `:ancestor-<digest>` from
   the scratch branch's head commit and `delete-branch!` the scratch —
   the rename-by-branch that makes the ancestor appear complete or not at all;
5. a killed build leaves a `:building-*` branch in the roster; boot deletes any
   `:building-*` older than this process and GC reclaims it.

What lands in the ancestor: `:seon.schema` rows, `:seon.ns`/`:seon.fn` rows,
`:seon.test` rows, ancestor facts. **Not** config facts — config is per-cluster
and reconciles after the branch-off (§7), so one ancestor serves every cluster
and every manifest.

### 5.4 Fork half — the exact mechanism

```
open the ONE store        (B1's open-store!, flock FIRST, once per process)
ensure the ancestor       (§5.3, no-op when :ancestor-<digest> is in the roster)
per cluster, through the ONE registry owner:
  :cluster-<name> in :branches?
    no  -> branch! from :ancestor-<digest>        (17 ms, 1 blob)
    yes -> resume: nothing to do
  connect (assoc store-config :branch :cluster-<name>)
```

- **All `branch!` / `delete-branch!` calls go through `seon.cluster.registry`,
  which holds the single connection used for branch lifecycle** (§0.6
  condition 1). No cluster's own connection can mutate the roster.
- The **fork change** of §0.6 makes the roster mutation safe even if that
  discipline is ever bypassed; both are required, because one is
  construction-in-Seon and the other is correctness-in-Datahike.
- `branch!` refuses `:branch-already-exists` (`versioning.cljc:233-235`), which
  makes creation idempotent under retry.
- Branching from a **commit id** rather than a branch keyword is supported and
  needs `:commit-graph? true` (`versioning.cljc:222-228`) — the default. Use it
  when the ancestor branch has been retired but clusters must still descend
  from its commit.

### 5.5 Resume, reset, and retirement

- **Resume**: the branch is in `:branches`; connect and go. No ancestor
  consulted, nothing detected — the roster is the fact.
- **Reset one cluster**: release its connection, `delete-branch!`, `branch!`
  from the current ancestor. Never `delete-database` (§0.6 condition 2). GC
  reclaims the old tail (proven §0.7). This is L18 exactly: reset to current
  code and pages, never migrate.
- **Retire an old ancestor**: once no cluster branch descends from it,
  `delete-branch!` it; GC reclaims whatever no live branch shares. A dormant
  ancestor costs one roster entry and its head data until then.

### 5.6 Clone + re-identify — retained for export, import, and base-building

Not the per-cluster path any more (§0.8), but unchanged as a mechanism and
still needed. Given a target directory:

```
clone   <source>/store -> <target>/.store.<uuid>.tmp     (/bin/cp -cR | cp --reflink=auto -a)
reidentify!  <target>/.store.<uuid>.tmp                  (k/get :db, rewrite [:config :store :id], k/assoc)
atomic move  -> <target>/store
```

- Clone is quarried verbatim from `script/seon/dev/cluster.clj:58-90`
  (temp-then-atomic-move included). Its refusal on an unrecognised OS becomes a
  **loud fallback to create + re-transact**, so no host is unstartable.
- `reidentify!` is one `k/get :db` / `k/assoc :db` pair setting
  `[:config :store :id]` and `[:config :store :path]` (proven §2.3, 13.8 ms),
  run BEFORE any `d/connect` and before the directory takes its final name — so
  a mis-identified store never exists at a path anything opens.
- Exporting ONE cluster from a multi-branch store is clone-then-prune:
  clone the whole store, then `delete-branch!` every branch but the exported
  one and GC. Cheap on a CoW filesystem; correct everywhere.

## 6. Schema EDN + the one admission gate

### 6.1 What `register!` already does (do not rebuild it)

`src/seon/schema.cljc:739-812` already enforces that a schema form is
**readable EDN that round-trips** (`:seon.schema/unreadable-form`,
`:seon.schema/non-round-tripping-form`), rejects nilable value schemas
(`internal/assert-non-nilable-value-schema!`), and runs
`assert-complete-contract!` against the whole candidate population, so
declaration order cannot change acceptance. `build-projection`
(`schema.cljc:828-851`) validates the complete population and derives the
dependency indexes and entity catalog. The registry facade
(`schema.cljc:341-352`) and `activate!` (`schema.cljc:1551-1562`) are the one
publication point.

**Because forms are already EDN-only by construction, moving them to `.edn`
files is a relocation of the same values, not a new format.**

### 6.2 What the EDN loader must add

| Requirement (from the sealed ruling) | Why `register!` does not cover it | Design |
|---|---|---|
| duplicate attribute refused ACROSS files | `register!` ends in `(update-candidate-forms! assoc k v)` (`schema.cljc:811`) — a silent overwrite | the loader merges file-by-file and refuses on a key already contributed by another file, naming both files |
| all references resolve | `build-projection` does this for the population it is given | the loader hands `build-projection` the WHOLE merged population once, not per file |
| every `[:fn]` names a registered core predicate | today a missing predicate degrades through `runtime-predicate` returning nil | a post-merge check over `predicate-symbols-in` against `core-predicate-functions`; refuses with the symbol and the file that used it |
| generative-honesty lint | not present anywhere in fresh `src/` | port the static rules from `research/malli-generative-patterns-2026-07-26.md:42,682-729`: every `[:fn …]` carries `:gen/schema` or `:gen/gen`; no bare `:fn`, `fn?`, or dishonest override |
| one gate shared with agents' `register!` | `register!` is the agent producer already | make the gate ONE function, `seon.schema.edn/admit`, called by the loader over a merged population and by `register!` over `(assoc population k v)` |

### 6.3 Load ordering — the one real hazard

`[:fn 'seon.flow/executor?]` and friends bind through
`register-core-predicate!` in code (`src/seon/cluster.clj:112`,
`src/seon/cluster/store.clj:84-87`). If the EDN loads before those namespaces,
the `[:fn]` check fails. Resolution: **the `[:fn]` check runs at ACTIVATION,
not at load.** The boot sequence becomes: load namespaces (predicates register)
→ `schema.edn/load!` (merge + duplicate refusal) → `schema/activate!` (full
population validation, including the `[:fn]` and honesty checks). This is
strictly better than today's load-order-sensitive per-`register!` assertion and
should be named in the contract.

Classpath enumeration of `seon/schema/*.edn` must handle both a `file:` URL
(dev, source classpath) and a `jar:` URL (publish). ~15 lines over
`(.getResources (clojure.lang.RT/baseLoader) "seon/schema")`. Risk row in §11.

### 6.4 The conversion list — every `register!` in fresh `src/`

| File | `register!` | `register-core-predicate!` | verdict |

| `src/seon/flow.clj` | 60 | 6 | convert forms → `src/seon/schema/flow.edn`; predicates stay |

## 7. Config reconciliation

### 7.1 The algorithm, quarried

`src-old/seon/runtime/state.cljs` is the prior art and its core is right
(docstring, `state.cljs:1-13`): the managed slice is defined by **provenance,
not a taxonomy**; reconcile takes no "kind" argument and runs no id-attr
registry loop; it operates in attribute space. Concretely
(`state.cljs:263-344`):

1. every desired entity map carries exactly ONE `:db.unique/identity`
   attribute — the upsert handle; zero or two is refused, not guessed
   (`state.cljs:61-70`);
2. the current managed population is enumerated by the first-assertion
   transaction's process being in the managed scope, plus explicitly adopted
   identities (`state.cljs:282-296`);
3. per entity, the exact diff: attributes present-in-one-and-not-the-other, or
   present in both and unequal, are retracted (`:db.fn/retractAttribute`) and
   the desired values re-asserted (`state.cljs:226-261`);
4. managed entities whose identity is absent from the desired population are
   `:db.fn/retractEntity`'d (`state.cljs:332-343`);
5. a desired identity already owned by an entity OUTSIDE the managed scope is
   a refusal, never a silent adoption (`state.cljs:302-321`).

### 7.2 What changes

| Old | New | Why |
|---|---|---|
| `^:async`, `<!`, wire query members (`state.cljs:414-462`) | plain synchronous Clojure over a database value | O1: reads are a pointer into an immutable value |
| `max-reconcile-attempts 3` + full-head staleness retry (`state.cljs:72,510-514`) | **deleted**: the plan recompiles inside the writer via `[:db.fn/call #'reconcile-call request]` | the N2 idiom (`src/seon/cluster/run.cljc:307`); there is no stale basis inside the serial writer |
| `db/decode-edn-value` per attribute (`state.cljs:111`) | deleted | that was the wire codec's inverse; nothing crosses a wire |
| `:seon.db/managed-scope` as a caller argument | the ONE core process identity B2 owns | one producer today; a scope argument is a generality nobody uses |
| response is `{::ok? true ::changed? … ::operations … ::attempts …}` | `{::converged? bool ::operations int}` (no `::attempts`, no `::ok?` — refusals throw at this layer, per B0/B1's house style) | §2.5 makes `::converged?` the load-bearing fact |

### 7.3 The converged=zero-writes contract

```
plan  = (reconcile/plan db request)     ; pure, no transaction
empty? -> {::converged? true ::operations 0}       ; ZERO transactions issued
else   -> (d/transact conn {:tx-data [[:db.fn/call #'reconcile-call request]]})
          {::converged? false ::operations (count …)}
```

The acceptance measure is observable and cheap: **`(:max-tx (d/db conn))` is
identical before and after a converged re-apply** (§2.5 shows why any
transaction, even empty, would break it).

### 7.4 Provenance scoping and drift repair

Provenance is Datahike transaction metadata, already the house mechanism
(`:seon.db/user` / `:seon.db/process`). The managed scope for config is one
process identity. Note the quality review's B2 input: `seon.schema`'s
`core-process-identities` (`src/seon/schema.cljc:261-265`) is a three-element
hand list and violates L17. **Computed replacement proposed:** a transaction is
core-provenance iff its `:seon.db/process` entity was itself asserted by the
ancestor build or by a transaction that is already core-provenance — i.e.
core-ness is inherited from the ancestor's genesis rather than matched against
a literal set. This needs its own falsifier and is the one piece of B2 I am
least confident in; see §11.

Drift repair is not a separate feature: a hand-edited fact simply appears in
the current population and diverges from desired, so the next explicit apply
retracts and re-asserts it. Nothing detects drift; reconcile just converges.

### 7.5 The defaults document

`bin/seon start` with no `--config` uses the shipped default manifest, which is
THE defaults document: complete, explicit, every constant with units and
calibration provenance. `(or x 60000)` stays banned. A user manifest declares
only overrides. This is the s3 ruling verbatim and needs no new mechanism —
but note it means B2 must WRITE that default manifest, and today the honest
dial population is `seon.flow`'s 60 plus `:seon.config/on-core-error`, not
State A's 39 transport/executor keys.

### Crash-walk rows

Rewritten for branch-per-cluster. Every row is `kill -9`; the store's flock is
released by the OS on process death, so the next boot always re-acquires it.

| Kill point | Durable state left | Next boot detects / does |
|---|---|---|
| before the store flock | nothing | ordinary first boot |
| after flock, before `create-database` | empty or partial dir, no `:db` | B1's existing recreate (`store.clj:244-253`) |
| mid-genesis (`:db` present, `:branches` absent) | the first-create window | B1's existing detect-and-recreate |
| mid ancestor build, before the scratch branch is published | scratch head blob, not in `:branches` | invisible; GC sweeps it. `ensure!` rebuilds |
| mid ancestor build, after `:building-<uuid>` is in the roster | a partial ancestor under a scratch name | `:building-*` whose owning process is dead is `delete-branch!`d at boot, then GC. `ensure!` rebuilds. **The `:ancestor-<digest>` name only ever appears complete** |
| between the ancestor's `branch!` head write and its `:branches` update (`versioning.cljc:255-257`) | orphan head blob | not in the roster → GC sweeps. `ensure!` re-runs and re-creates |
| after `:ancestor-<digest>` lands in the roster | complete ancestor | nothing to do |
| mid cluster `branch!`, before the roster update | orphan head blob | cluster branch absent → `ensure-cluster!` branches again (idempotent; `:branch-already-exists` guards the retry) |
| after the cluster branch is in the roster, before first connect | a complete cluster branch | resume path: connect and go |
| mid `delete-branch!` (`k/update … disj`) | one key write; either happened or not | roster is the fact; reset re-runs `delete-branch!` (refuses `:branch-does-not-exist`, treated as done) |
| mid GC sweep | some unreachable objects deleted, some not | nothing to detect: the safe point (`gc.cljc:88-105`) guarantees everything deleted was already unreachable. A later pass finishes |
| mid cluster commit | values written, branch head not flipped | Datahike's values-then-pointer barrier: reopen sees the old head; the orphan values are GC'd |
| after the store opens, before config `apply!` | branch with schema+program facts, no config facts | apply runs, `::converged? false`, writes the config |
| mid config `apply!` | one Datahike commit | fully applied or not at all; re-apply converges |
| after a converged `apply!` | nothing changed | re-apply is zero writes, `:max-tx` unchanged |
| **mid concurrent `branch!` from two connections (no fork change)** | **a branch head written and silently absent from the roster** | **NOT DETECTABLE — the caller was told `:ok`. §0.3. This row is why §0.6's fork change is a condition, not an improvement** |

Clone-path rows (export/import only, §5.6): mid-clone leaves a partial
`.store.<uuid>.tmp`; after clone but before `reidentify!` leaves a temp dir
carrying the SOURCE's id — neither is ever named `store/`, so nothing can open
a mis-identified store, and both are garbage the next export overwrites.

## 10. Falsifiers for the rung

1. **Branch-off is near-instant and isolated.** Build an ancestor; create
   clusters `a` and `b` in ONE JVM; both see every ancestor fact, both accept
   writes, neither sees the other's writes, the ancestor branch is unchanged.
   Under 100 ms per cluster (measured 17 ms), one blob written.
2. **Concurrent cluster creation loses nothing.** N concurrent
   `ensure-cluster!` calls from N threads → N branches in the roster, zero
   orphan heads. This is §0.3 turned into the standing regression, and it must
   be written BEFORE the fork change so it is seen failing first.
3. **Deleting one cluster leaves the others whole.** §0.7's walk as a suite:
   two cluster branches plus the ancestor, delete one, GC, assert the survivor
   and the ancestor are byte-complete and the deleted tail was reclaimed.
4. **Restart resumes, never re-branches.** Stop cluster `a`, retire the
   ancestor branch, restart `a` — it opens from its own branch.
5. **Converged re-apply is zero writes.** Apply the default manifest twice;
   `(:max-tx (d/db conn))` is identical after the second apply.
6. **Drift repairs.** Transact a wrong dial value directly; re-apply; the fact
   is back and `::operations` is non-zero.
7. **Duplicate attribute refuses.** Two EDN files declaring one key fail
   `load!` naming both files.
8. **A `[:fn]` without a registered predicate refuses at activation**, with the
   symbol named.
9. **Crash walk**: `kill -9` a child JVM at each row of §9 and prove the "next
   boot" column, in the style of B1's `test/seon/cluster/store_child.clj`.
10. **Generative property** over reconcile: for any generated (current,
   desired) pair, applying the plan yields a database whose managed population
   equals desired exactly, and re-planning yields the empty plan (convergence
   in one step is the property; two-step convergence is a bug).

## 11. Risks and open questions, ranked

1. **The `:branches` fork change (§0.6) is a blocking precondition, not a
   nice-to-have.** Until it lands, concurrent cluster creation silently loses
   clusters (§0.3, reproduced). Order: write falsifier 2 first, watch it fail,
   then make the fork change, then build on branches. If the owner does not
   want the fork touched in B2, the verdict flips to clone-per-store — the
   plan is written so that switch is a §5 swap, not a redesign.
2. **One store is one process, forever.** §0.4. Accepted given O1 and B0, with
   export as the escape hatch, but it is the decision that is hardest to
   reverse later. Worth an explicit owner acknowledgement rather than my
   inference.
3. **GC becomes a whole-system operation.** One pass walks every cluster's
   reachable set (`gc.cljc:136-143`); its cost and pause scale with total data,
   not per cluster, and it must run in the writers' process. Nobody has
   measured a GC pass over ten warm clusters. **Experiment owed** before the
   cluster count grows.
4. **The `core-process-identities` replacement (§7.4).** A computed
   core-provenance rule *inherited from the ancestor's genesis* is elegant but
   unproven; a wrong answer means agent-authored schemas get core strictness.
   **Recommend: keep the literal set in B2, file the computed rule as its own
   bounded unit.** Owner call.
5. **Store-id derivation matters less now.** With one store per process root,
   B1's path-derived `:id` (`store.clj:139-140`) is unambiguous and the §2.4
   collision case disappears. It still matters for the export path, where
   `reidentify!` handles it. No change recommended.
6. **Clone on an unrecognised OS** (export path only now). State A refused
   (`cluster.clj:91-97`). **Recommend: fall back to create+re-transact,
   loudly**, so no host is unstartable. Owner call.
7. **Classpath enumeration of `seon/schema/*.edn` in a jar.** Dev is a source
   classpath and trivially works; the publish build must be proven. Mitigation:
   the runtime normally reads schema FACTS from the forked store, so the jar
   path matters only for `(schema/reload!)` and the ancestor build — both of
   which run from source. Low risk, but it must be stated rather than assumed.
8. **Ancestor digest scope.** Digesting every `src/**.clj{,c}` plus the schema
   EDN means any source edit invalidates the ancestor and the next *fresh
   cluster* pays one rebuild (1.7–2.5 s at today's size). Running clusters are
   unaffected (hot reload). Old ancestor branches accumulate until retired, so
   a dev loop that creates many clusters wants `retire-branch!` on a schedule.
   Measure again at N5.
9. **B0 and B1 both take revisions.** B1's `open-store!` becomes
   per-process-root and map-argument and gains `open-branch!`; B0's
   `cluster-paths` loses `:seon.boot/store-dir` to the root. Both are sealed
   and green, so both are orchestrator-authored revisions, and
   `store_test.clj` + `store_child.clj` + `boot_test.clj` move with them. This
   is the largest non-technical cost of the branch verdict.
10. **The re-identified head diverges from its content-addressed commit
    record** (export path only). `reidentify!` rewrites the mutable `:db` head;
    the immutable commit blob keyed by `cid` still carries the source's
    `:config` (`writing.cljc:707-709` writes both from one value). Nothing in
    the read path consulted it in the probe (history worked, 5,001 rows), but a
    future audit/commit-graph feature could. Cheap mitigation: rewrite the
    `cid`-keyed blob too. Flagged, not solved.
11. **`:seon.boot/store-dir` and `:seon.boot/ancestor-branch` enter the closed
    bootstrap schema.** The rung's own rule is that a key the database could
    own does not belong in bootstrap. These two genuinely cannot: they are
    consumed to REACH the database. Worth an explicit sentence in the contract
    so the next reader does not read them as drift.

## 12. Out-of-scope findings

- `src/seon/schema.cljc:261-265` — `core-process-identities` is a
  hand-maintained literal set, an L17 violation already noted by
  quality-review-1. Covered by risk 1 above; if the owner defers the computed
  rule, it needs its own issue note under `docs/seon/issues/`.
- `src/seon/schema.cljc:235-252` — `*verified-release-identity*` reads
  `SEON_APPLICATION_DIGEST` / `SEON_PREPROCESSED_RELEASE_IDENTITY` from the
  environment at namespace load, and short-circuits the registration gate when
  they match. That is both an environment read at runtime (banned) and a
  release-artifact coupling from the condemned build chain. B2's schema work
  should delete it; it is not on any current path.
- **Datahike defect, ours to fix**: `branch!` and `delete-branch!` mutate
  `:branches` with an unsynchronized read-modify-write
  (`reference-code/datahike/src/datahike/versioning.cljc:257,289`). Two
  connections to one physical store hold different konserve store instances
  (`gc_guard.cljc:47-50` says so explicitly), so konserve's per-key lock does
  not apply and the per-blob `FileLock` does not survive the atomic-move
  replacement. Reproduced: 12 concurrent creations, 11 reported success, 9
  landed, 3 head blobs orphaned (`tmp/b2-probe/branch_gc_probe.clj`). This is
  upstream-reportable and needs an issue note under `docs/seon/issues/`
  regardless of which B2 verdict the owner takes.
