### H4 — the would-fall-to-floor filter and the show-everything checkbox

**Owner:** `src/seon/render/web.clj` (`shell` + `page-of`),
`resources/public/css/input.css`.

**Mechanism (recommended — client-side reveal).** `page-of` emits EVERY unit,
including floor units, each carrying `data-floor="true"` when its node says
`:seon.render/would-fall-to-floor?`. The shell adds one checkbox bound to a
Datastar signal (`data-signals__ifmissing="{showEverything:false}"`), and floor

flip — zero round-trip, zero server state, exactly the `$selected` idiom
already shipping at `agent.clj:306,319-323`.

Why not a server-side variant: `page-of` produces ONE complete snapshot multed
to every tab (`web.clj:1-45`, `cluster.clj:1148-1150`). A per-tab membership
variant forks that snapshot per tab and re-introduces the per-tab derivation
the delivery tier exists to avoid (and that U9 is separately trying to remove).
The debug tab's per-tab derivation is the deliberate exception W3 already paid
for, and ruling #8's addendum says the per-agent debug view IS the raw surface —
so the checkbox does not need to become a second debug view.

The cost is real and must be measured: floor bytes ride the wire even when
hidden (§5 gate).

**Acceptance.** With the box unchecked, no floor unit is visible and the DOM
still contains it. Checking the box reveals every floor unit with **zero
network bytes** (verify with `read_network_requests` or the server log: no SSE
event and no request follows the toggle). A unit with an explicit
`:seon.render/html` declaration that happens to name `data-panel` stays visible
(W3's non-symbol-comparison guarantee, `render.clj:170-173`).

**Tests.** One `web_test.clj` regression per branch of the boolean: floor unit
carries the attribute, specialist unit does not, explicit-`data-panel` unit does
not. Plus the negative: `rg 'showEverything' src/` finds no database attribute
and no server-side read — the signal is client-only by construction.

### H5 — rank-driven primary/rail layout, and the promote morph

**Owner:** `src/seon/render/web.clj` (page assembly),
`resources/public/css/input.css:1243-1325`,
`src/seon/render/agent.clj` (`focus-html`, `focal-panel`, `rail-card`,
`unit-label`, `focus-entity-ids`, `selection` — DELETED).

**The mechanic, named precisely.** A Datastar patch morphs the element at a
stable id **in place**; it cannot reorder that element's siblings. So a
reordering page has exactly two honest implementations:

- (a) morph the CONTAINER — one big fragment per reorder, defeating per-block
  suppression entirely; or
- (b) keep DOM order STABLE and drive VISUAL order with CSS.

**Take (b).** DOM order is the walk's path order (stable while the graph shape
is stable). Each unit's wrapper carries `style="order:N"` where N is its rank
from H1's reversed `units`, plus a rank class (`seon-rank-primary`,
`seon-rank-rail`, `seon-rank-deep`). The page container is a CSS grid:
`grid-template-columns: minmax(0,2fr) minmax(15rem,1fr)` (the existing
`.seon-focus-layout` rule, `input.css:1250`), primary occupies column 1, rail
units column 2 with `overflow-y:auto` (the existing `.seon-rail` scrollback,
`:1284-1291`), deep units continue the rail's scroll.

**Therefore a promote is not a repaint.** When a commit makes unit X the newest,
only the RANK ATTRIBUTES of the units whose rank changed differ — typically two
(X gains primary, the old primary becomes rail-1) plus the ranks that shifted
down. `changed` sends one morph per changed id; each is that unit's own bytes,
which are unchanged except the `order`/class attributes. The measured 1.2–1.5 ms
p95 Chrome block morph (`render-pipeline-design-2026-07-29.md`) applies per
morph, so a promote is bounded by the number of rank-shifted units, never by
page size.

**One renderer, one distance.** Today `focal-panel` renders at d1 and
`rail-card` at d0 — the SAME unit twice, doubling bytes and making promotion a
genuine content re-render. That doubling dies: every unit renders once, at the
walk's distance, and "primary is large" becomes CSS (a bigger cell) while the
rail card is the same bytes clamped by `max-height`/`overflow:hidden` (the
existing `.seon-rail-preview` rule, `:1303-1310`). `$selected` and the two-copy
`data-show` trick die with `focus-html`.

**Rail bound.** The owner wants ~last 3 in the rail. That is a presentation
rank, not a collection cap: ranks 1..3 get `seon-rank-rail`, rank 0 primary,
4+ `seon-rank-deep` and continue in the same scrolling column. No new dial, and
`:seon.config.eval.result/max-collection` stops being reused as a UI number
(`agent.clj:335-339` dies with `focus-html`).

**Acceptance.** (1) Commit one fact touching unit X on a live cluster with 12
units; capture the SSE events: the number of morph events equals the number of
rank-shifted units plus X, and no event carries the page container's id. (2)
The promoted unit's bytes differ from its previous bytes ONLY in the
`order`/class attributes when its own facts did not change. (3) `rg 'focus-html|rail-card|focal-panel|\$selected' src/`
returns nothing.

**Tests.** `test/seon/render/agent_test.clj`'s focus/rail tests DIE. Replaced by
one `web_test.clj` property (P4, html side): for two database values differing
by one transaction, the set of changed element ids equals the set of units whose
rank or bytes changed — and the container id is never among them.

## 7. Owner gates — ask before the unit that depends on them

a. **The floor reveal's cost model (H4).** Client-side reveal (recommended:
   one shared snapshot, zero round-trip, `$selected` idiom) carries floor bytes
   to every tab always. Alternatives: (b) omit floor units entirely and let
   `/agent/{id}/debug` be the only reveal — cheapest, and ruling #8's addendum
   arguably already says this; (c) per-tab server variant — matches the checkbox
   wording most literally but forks the shared snapshot. Recommendation: (a),
   with (b) as the fallback if the measured overhead is material. Blocks H4's
   exit, not its start.

b. **Primary detail vs one-distance rendering (H5).** Ruling #12(b) makes detail
   inverse to distance, which argues the primary should be richer than a rail
   card. Rendering one unit twice (as today) doubles bytes and makes promote a
   content re-render. Recommendation: one render per unit, "large" is CSS, rail
   is the same bytes clamped. Confirm before H5 lands, because it decides
   whether promote is cheap.

c. **The rail's ~3 bound (H5).** Presentation rank (recommended: three rail
   ranks, everything else continues the same scroll) versus a config fact.
   Recommendation: rank, no new dial — a UI count is not a system dial, and the
   current reuse of `max-collection` for it is the recorded smell.

d. **`changed-at`'s known defect (H1).** The in-flight derivation is
   `(max :tx)`, which moves on no-op re-asserts (falsification R3) and will
   reorder the page on writes that changed nothing. W4-html consumes the key and
   the cache wave's U5 replaces the derivation. Confirm that sequencing rather
   than fixing it here — fixing it here would put the digest-transition
   mechanism in the walk before the cache that owns digests exists.

e. **Schema deletion vs ruling #14 (H7).** Delete from the current per-family
   files now, or wait for the one-file consolidation? Recommendation: delete
   now, against whichever layout is on disk when H7 dispatches. Blocks nothing
   if answered at dispatch.
