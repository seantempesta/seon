CONFIRMED BUG (W0.7 gap-7 vector reproduced it live, NOT hypothetical):
concurrent schema registration silently loses data. When agent A snapshots
the schema, agent B registers a NEW schema successfully, then A's eval
fails and A restores its stale snapshot — B's registration is WIPED. This
is fleet data-loss: at 100 concurrent agents, failed evals routinely drop
other agents' successful registrations.

GROUNDING (verified by the orchestrator; re-confirm each):
1. `src/seon/schema.cljc:625-633` — `restore!` does
   `(update-candidate-forms! (constantly before))`: a WHOLESALE reset of
   the process-global schema state to the caller's snapshot. This is the
   defect — it reverts EVERYTHING to `before`, including keys a concurrent
   agent added after the snapshot.
2. `src/seon/schema.cljc:610-623` — `snapshot` (the `{schema-key form}`
   map) and `changed-keys` (keys differing from `before`); the
   process-global `!schema-state` and `update-candidate-forms!` /
   `candidate-forms` are the state owner (read them).
3. `src/seon/host.clj:740-751` — the call site: `schemas-before`
   snapshot before the eval, `(schema/restore! schemas-before)` on
   failure. This runs per-form on a shared JVM worker; multiple host
   sessions/agents mutate the ONE `!schema-state` concurrently.
4. `snapshot-state`/`restore-state!` (`schema.cljc:635-646`) are
   test-only exact captures — not the concurrency seam.

GOAL — a failed eval reverts ONLY the schema keys IT changed, never a key
a concurrent agent changed:
1. Replace the wholesale `(constantly before)` restore with a DELTA
   revert: on a failed form, revert exactly the keys THIS eval
   added/redefined back to their `before` values (remove keys this eval
   newly added; restore keys this eval redefined), applied atomically to
   the CURRENT state — leaving every key this eval did not touch
   (including a concurrent agent's new registration) exactly as it is.
   The mechanism is the implementer's choice as principal engineer —
   candidates: (a) compute this eval's own changed keys and revert just
   those in one `swap!` over current state; (b) a per-eval staging overlay
   that registers into an isolated layer, merged on success / discarded on
   failure; (c) a CAS. Read `!schema-state`/`register!`/
   `update-candidate-forms!` and choose; REPORT the seam and why. HARD
   CONSTRAINT: do NOT serialize all evals behind a global lock — the
   common case (A and B register DIFFERENT keys) must stay fully
   concurrent (a global lock kills fleet parallelism and defeats the whole
   W0 goal).
2. Same-key genuine conflict (A and B register the SAME key concurrently):
   last successful registration wins (the last-version-wins teaching
   contract), but a FAILED eval's revert must NEVER win over a concurrent
   SUCCESS — a failure only removes/reverts its own contribution, and if
   that key was subsequently re-registered by a success, the success
   stands. State the exact chosen semantics.
3. `changed-keys` (or an equivalent this eval-scoped delta) already exists
   for the success path (host.clj:752-753) — reuse the same notion for the
   failure path so success and failure compute "what this eval changed"
   the same way. One mechanism.
