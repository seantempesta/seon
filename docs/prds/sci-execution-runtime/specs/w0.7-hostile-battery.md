BATTERY VECTORS (each = attack form + containment assertion; behavior,
never message strings — assert envelope kinds, `:seon.error.sci/class`,
facts, and the OTHER agent's successful turn):
1. CPU runaway: `(reduce + (range))` and a `(loop [] (recur))` under a
   short deadline → interrupt lands ~deadline, worker recovered, next eval
   on the SAME host serves.
2. Memory bomb: a giant vector/string allocation → error value or
   process-contained OOME per the documented posture; other agents
   unaffected (assert survivor behavior, not kill-certainty).
3. Oversize error text: a thrown message > frame cap → bounded error frame
   (W0.6), session survives.
4. Print flood: a large print loop → capped `:seon.eval/output` with
   truncation marker, zero host-stdout bytes (capture the process stream).
5. Shared-var attack: `alter-var-root`/`def` on a `:sci/built-in` var and
   an `in-ns` escape attempt → `:refusal` class, var unchanged, OTHER
   agent's use of that var still correct.
6. Cancel ghost: queue evals, cancel before start → zero receipts, zero
   writes (W0.3's assertions, re-run as battery members).
7. Deadline-at-return race: deadline firing at eval completion → next form
   uninterrupted, terminal recorded (W0.6 interrupt hygiene).
8. Connect-and-silence: a socket that connects and sends nothing →
   released at the startup-read timeout; acceptor still accepting.
9. Malformed frames: garbage bytes, truncated frame, wrong-database
   startup → session refused/faulted, acceptor + other sessions unharmed.
10. CONCURRENT schema registration (weakness q6): two agents register!
    different schemas simultaneously, repeatedly → BOTH schemas present
    afterward (this is EXPECTED TO FAIL per audit gap 7 — if it fails,
    mark the vector with the audit citation and report it as the W0.8
    trigger; do not fix it here, do not delete the vector).
11. Resolution/arity/runtime error storm: a rapid burst of failing evals
    from one agent while a second agent does real work → second agent's
    latency/results unaffected (structural: completion + correctness, not
    wall-clock thresholds).
12. Writer-pool starvation: one agent saturating db reads (long queries ×
    pool size) while another agent evals → the second agent's calls
    complete (bounded wait or fair service; assert completion).

## Addendum — round 2 (source-grounded amendments, all accepted)

The implementer's grounding exposed four gaps; all resolved:

1. **Vector 10 rewritten to actually test gap 7.** The race is
   failed-form stale-restore, not two successes: agent A snapshots the
   schema → agent B registers successfully → A's form THROWS → A
   restores its stale pre-form snapshot, dropping B's registration
   (host.clj:740). Assert B's schema is MISSING afterward (the defect)
   → mark with the audit citation as the W0.8 trigger. Two concurrent
   successes do NOT exercise the defect.
2. **Vector 2 scoped to bounded allocation pressure + survivor
   behavior** in this in-process JVM suite (a real OOME could kill the
   test runner). Actual process-contained OOME recovery is a supervised
   drill deferred to the q2 host-supervisor work (added as q18).
3. **Steering-quality floor scoped to eval-originated vectors only**
   (1, 3, 5, 7, 11). Cancel, protocol, and startup errors carry no
   `:seon.error.sci/class` (host.clj:473, 994); successful
   print/schema/starvation vectors produce no error. Assert class/head
   only where an eval exception is the product.
4. **Vector 12 asserts the bounded-rejection containment W0.4 actually
   provides:** full pool saturation returns bounded `:pool-exhausted`
   (host_pool_writer_test.clj:285), the pool does not lock up, and it
   recovers after the saturating reads drain — NOT guaranteed service
   for the second agent (that was never W0.4's contract). The
   capacity-reservation/fairness question is q5, not invented here;
   reference it in the vector comment.
