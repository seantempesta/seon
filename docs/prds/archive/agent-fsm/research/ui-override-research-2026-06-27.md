# UI Override Research — can a third party completely override the UI from the DB?

Research date 2026-06-27. 5-lane Ultracode workflow (layout/views/shell/CSS/client + acme-build) + synthesis. One lane (views) hit the structured-output retry cap; views are covered in the synthesis scorecard.

# VERDICT — Can a third party override the UI from the DB today? Mostly NO.

Only **what renders inside a tile** is truly DB-driven. Everything that defines the *page* — the tile layout, the shell, the routes, the CSS, the client — is hardcoded code and requires forking. The owner's "all DB-driven, no scattered hooks" goal is **not** met today; it is roughly one keystone schema change + one shell-as-symbol refactor away from being achievable.

(Note: 4 dimension-findings were supplied, not 5; they map onto the 5 scorecard axes below — "views" is split out of findings 1 & 4.)

| Axis | Status | One-line reason |
|---|---|---|
| **Views** (what renders in a tile) | ✅ data-driven | `:seon.render/html` / `:seon.render.live-canvas/content` is a SYMBOL resolved at render via `core-views`/SCI; consumer symbols index via `SEON_EXTRA_*` (`tile.cljs:780-799`; acme `widget.cljs`). Caveat: a new *core* symbol still needs the `core-views` table edit (`tile.cljs:643-652`). |
| **Layout** (which tiles, order, span) | ❌ needs forking | `:seon.canvas/*` schema is never registered/seeded, so the `console-tiles` gate at `tile.cljs:728` is permanently false → `default-tiles` always wins (`tile.cljs:700-722,737`). Live proof: `console=false id=false span=false`. |
| **Shell** (head/body/grid/header/routes) | ❌ needs forking | `head`/`console-shell`/`header-bar` are private hardcoded hiccup (`tile.cljs:1228,1333,1284`); routing is 3 hardcoded dispatchers (`serve.cljs:594-634`). No symbol, no route registry. |
| **CSS / theme** | ⚠ partial | name/tagline/theme STRINGS are a DB row, but CSS is an env+disk file (`SEON_BRAND_CSS`, `brand.cljs:149-170`), inlined only on **inspector** pages — the DB-driven **canvas/console** pages omit it (`tile.cljs:1228` has no `brand-css-style`). `data-theme` is inert (0 selectors key off it). |
| **Client** (transport) | ❌ needs forking | One hardcoded `packetstar.js`; `<script src="/js/packetstar.js">` is baked into private shell fns (`tile.cljs:1234`); no `SEON_EXTRA_PUBLIC` static root; no DB/env selects the client (`serve.cljs:116-118`). |

# THE GAPS — hardcoded blockers, ranked by how much they block

1. **`:seon.canvas/*` schema is never installed → layout is dead data.** The gate (`tile.cljs:728`) never opens; `default-tiles` always wins. Compounded by two sub-bugs: `:seon.canvas/id` isn't unique, so `find-tile`'s lookup-ref `[:seon.canvas/id …]` *throws* (`tile.cljs:744`); and a pod `db/transact!` of a tile entity **resolves as success but silently no-ops** at the `:write`-flexibility store (live proof: store stays clean). This is the single keystone for the whole "layout from DB" story.
2. **The page shell is private, hardcoded hiccup, not a resolved symbol.** `head`, `console-shell`, `header-bar`, `debug-shell` are `defn-` (`tile.cljs:1228,1333,1284,1399`). Because they're private, the *proven* `set!` late-binding override (which reaches public fns) **cannot** reach them — a different shell means forking `tile.cljs`.
3. **CSS lives in a file + env, not the DB, and is applied non-uniformly.** `SEON_BRAND_CSS` is a path read per-render (`brand.cljs:149-170`); the inline hook exists only in the 4 inspector heads (`inspector.cljs:706`), **not** the canvas/console heads. So acme's CSS reaches `/agents` but not the primary agent surface. Directly contradicts "everything in the DB."
4. **No route registry.** All routing is three hardcoded `case`/`cond`/`re-matches` dispatchers (`serve.cljs:594-634`, `inspector.cljs:1585+`, `tile.cljs:1527-1583`). Adding/replacing a route = editing `serve.cljs`. `SEON_EXTRA_SRC` injects agent-core code but has **no** hook to register a route or shell.
5. **The client is baked in.** `<script>` src is a literal in private shell fns; no `SEON_EXTRA_PUBLIC` analog to serve a consumer's own `/js/*`; nothing in the DB makes the shell reference an alternate client (`serve.cljs:116-118`).
6. **Coarse/static CSS internals.** `:seon.canvas/span` is only a boolean `(>= span 2)` hero/rail split (`tile.cljs:1340-1361`); grid is literal Tailwind; `output.css` is one static Tailwind build (`package.json:11`, `input.css`). Token overrides work via cascade; structural restyle needs a rebuild.
7. **`core-views` is a hardcoded 9-entry table** (`tile.cljs:643-652`) — new *core* view symbols need an edit (consumer symbols are fine via SCI/`!extra-core-vars`).
8. **SMELL (flag, not in scope):** `packetstar.js` POSTs typed forms to `/eval?agent=`, but `serve.cljs` has **no** `/eval` POST branch (`serve.cljs:616-628`) — typed forms 404. Either packetstar is stale or the route was dropped.

# PROPOSED SOLUTION — layered

### (a) Quick wins / already-90%-there

**ALREADY WORKS (confirm + document as the stable seam):**
- **Views as DB symbols + consumer code injection.** `SEON_EXTRA_SRC`/`SEON_EXTRA_PRELOAD`/`SEON_CLIENT_OUT` compile `acme.*` onto the pod and register fns via `!extra-core-vars`; consumers wire live tiles by transacting a symbol and override public fns via `set!` late-binding — **zero seon-src edits, build verified 0 warnings** (acme `pod.cljs`/`widget.cljs`/`overrides.cljs`). This is the working backbone; build on it, don't reinvent it.

**SMALL, HIGH-LEVERAGE BUILDS:**
- **[R's lane] Install + boot-seed `:seon.canvas/*`.** `schema/register!` `:seon.canvas/id [:string {:seon.db/identity true}]` (fixes the lookup-ref throw), `:seon.canvas/console :string`, `:seon.canvas/span :int`; install in the boot-seed lane (`seon.server.boot`, beside `seed-subscription-schema!`). **Turn `default-tiles` into a SEED** — transact the 9 rows on agent creation so `console-tiles` always reads data and "default" becomes editable rows. This single change flips **Layout ❌→✅** and removes the hardcoded-vs-derived bifurcation.
- **[R's lane] Propagate the silent write rejection.** Pod `db/transact!` must surface the wire-server `:write`-flexibility refusal so an unregistered-attr write *throws* instead of resolving success (`db.cljs` write path). Without this, consumers believe overrides worked.
- **[U's lane] Unify all 6 page heads onto ONE head fn that injects `brand-css-style`.** Today only the 4 inspector heads get the CSS override; adding it to `tile.cljs:1228`/`page.cljc` makes CSS overrides reach the primary agent surface. Highest-leverage CSS fix, no new schema.

### (b) Medium

- **[U+R] CSS as a datom.** Add `:seon.web.brand/css-text :string` (and/or `::css-vars [:map-of :keyword :string]`) on the brand row; add a `/css/brand.css` route in `serve.cljs` serving it; keep `SEON_BRAND_CSS` as the env→row SEED via the existing `sync!`. CSS becomes per-render reactive data — a runtime transact re-themes, no file on disk.
- **[U] `:seon.canvas/span` → real `lg:col-span-N`** (whitelist 1..3 in the Tailwind safelist) instead of the boolean hero/rail.
- **[U+R] `:seon.console/*` config entity** carrying columns/gap/body-class/stylesheet-href, read by `console-shell` so the grid + document chrome are data, not literal `grid-cols-1 lg:grid-cols-3`.
- **[U] `SEON_EXTRA_PUBLIC` static root** (analog to `SEON_EXTRA_SRC`) merged into `static-roots` so a consumer serves their own `/js/*` `/css/*`.
- **[U] `:seon.web.shell/scripts` (or `SEON_EXTRA_SCRIPTS`)** iterated by `head` — consumer points at their own client without forking. `brand-css-style` is the proven template, generalized from CSS to scripts.

### (c) Larger architectural

- **[U+R] Shell-as-symbol (matches the tile pattern).** Store `:seon.console/shell` + `:seon.console/head` symbols per console/cluster; `console-shell` resolves them through the existing `resolve-view`/`core-views`/SCI path, defaulting to the shipped symbol. Promote the shell fns from `defn-` to `defn` (or route through one overridable `render-shell` var) so the proven `set!` override reaches the skeleton. "A different page shell" becomes data/late-binding, not a fork.
- **[U+R] DB-seeded route registry** consulted before the hardcoded `cond`: rows of `{:seon.route/method :seon.route/pattern :seon.render/html handler-symbol}`; `serve.cljs handler` matches first, resolving the symbol (SCI-bounded for agent-authored). Mirrors tile dispatch.
- **[R] Per-cluster brand/theme/CSS keying** instead of the single global `::id "brand"` singleton, so one wire-server themes N clusters differently.
- **[U+R] Make `data-theme` real:** generate `[data-theme="<name>"]` custom-property blocks from `:seon.web.theme/*` rows so flipping `::theme` actually re-skins.

**Lane summary:** R owns schema/seed/ctx (install+seed `:seon.canvas/*`, `default-tiles`→seed, route-registry schema, per-cluster keying, write-rejection propagation). U owns `web/**` + CSS/JS (head unification, CSS-as-datom route, span→col-span-N, shell-as-symbol, `SEON_EXTRA_PUBLIC`, scripts-as-data, console-config entity).

# OPEN QUESTIONS FOR THE OWNER

1. **Shell: data or symbol or fork?** Three options for a totally different page: (a) **shell-as-symbol** — promote shell fns to public, consumer transacts their own symbol resolved like a tile (cheapest, matches existing pattern); (b) **shell-as-data** — DB rows describing head/body/grid (purest "everything in DB", biggest lift); (c) **accept a `tile.cljs` fork** for radically different chrome. Which target?
2. **Install `:seon.canvas/*` NOW as a standalone quick win?** It's small, isolated, and flips Layout ❌→✅ (register + seed + uniqueness fix + write-rejection surfacing). Approve independently of the bigger shell decision?
3. **Per-consumer CSS mechanism?** Go all-in on **CSS-as-datom** (`/css/brand.css` from the brand row), keep the current **env+file** `SEON_BRAND_CSS`, or formalize **"bring your own built `output.css`"** via `SEON_RUNTIME_ROOT` (token tweaks via DB, full restyle via runtime-root)? Pick the contract.
4. **Routes: data or code-hook?** Must adding a route be **DB data** (full route registry, larger build), or is an `SEON_EXTRA_SRC` **code hook** that registers routes acceptable (cheaper, still no `serve.cljs` fork)? Is forking `serve.cljs` ever acceptable for a consumer?
5. **One wire-server, many consumers?** Should a single wire-server serve multiple clusters with **different UIs simultaneously**? If yes, the global `::id "brand"` singleton must be re-keyed per-cluster — this changes the schema design *now*, not later.
6. **Custom client transport — stable contract or HTML-only?** Do we commit to the server↔client wire (per-tile `data:` frames, console `event: patch {id,html}`, `#tile-<id>`, the POST endpoints) as a **public surface** so a third party can ship a conformant client (once the shell can load it)? Or is HTML-string-over-SSE the only supported transport (no JSON/state-diff client)?

(Side note for the queue: the `/eval` route smell — `packetstar.js` POSTs typed forms to `/eval` but `serve.cljs` has no such branch, so typed console input 404s. Worth a focused look regardless of the override work.)

## Raw per-dimension findings

### Console LAYOUT — which tiles, their order, and spans (the grid composition at /canvas/console/<id>)

**Override via DB today:** no — the `:seon.canvas/*` schema is never registered or seeded, so `installed-schema` lacks it, the `console-tiles` gate stays closed, and layout ALWAYS falls back to the hardcoded `default-tiles`; the grid/span-semantics/page-shell are CODE in `console-shell`, not data.

**Mechanism:** Intended path (per the ns docstring, tile.cljs:13-17): transact `:seon.canvas/*` entities for a console — `:seon.render/html` symbol, `:seon.ctx/priority` for order, `:seon.canvas/span` for width — and `console-tiles` (724-737) would query them instead of `default-tiles`. In reality this path is dead: `console-tiles` only runs the query when `(contains? (db/installed-schema db) :seon.canvas/console)` (line 728), and that attr is never registered/installed, so it ALWAYS returns `(default-tiles agent-id)`. A consumer's only working levers today are (a) override the render of an EXISTING default tile (the `:seon.render/html` symbol IS DB-driven), or (b) fork/edit `default-tiles` + `console-shell` in code. There is no working data path to add/remove/reorder/respan tiles.

**Hardcoded:** The default layout itself: `default-tiles` (tile.cljs:700-722) is a hardcoded vector of 9 tiles with fixed order (:seon.ctx/priority 10..40) and fixed spans (hero=2, rest=1); The grid CSS + 2-column strategy in `console-shell` (1340-1362): `grid grid-cols-1 lg:grid-cols-3` (1361), hero `lg:col-span-2` (1345), rail `lg:col-span-1` (1354) — all literal Tailwind classes, not data; Span SEMANTICS are coarse + hardcoded: `:seon.canvas/span` only feeds a boolean `(>= (span %) 2)` to split hero-column vs rail (1340,1343,1348). A span of 3 behaves identically to 2; there is no arbitrary N-column span; The entire page shell: `head` (1228-1234) with a hardcoded `/css/output.css` link (1233) and packetstar script, `<body>` classes (1366-1367), `header-bar`/masthead (1284-1314), `input-form` (1316-1331), and the debug overlay (1379-1384) — all hardcoded hiccup, no DB lookup; `core-views` resolution table (643-652): the set of renderable CORE view symbols is a hardcoded 9-entry map; a consumer cannot add a new core view symbol without editing this map (agent-authored symbols can route via SCI, but only if a tile entity could carry them — which it can't); No `schema/register!` for any `:seon.canvas/*` attr exists anywhere in src/ — the docstring claim 'UI-data schema registered here by convention' (line 26-28) is aspirational; nothing registers it

**Blockers:** `:seon.canvas/console`, `:seon.canvas/id`, `:seon.canvas/span` are never registered via `schema/register!` (grep: zero hits in src/) and never boot-seeded, so they are absent from `installed-schema`. LIVE PROOF (pod): `console=false id=false span=false`. The `console-tiles` gate (line 728) is therefore permanently false → `default-tiles` always wins (737), and `find-tile` (743) always uses the default spec (747-749); `:seon.canvas/id` would need `:db/identity`/`:db/unique` for `find-tile`'s `[:seon.canvas/id tile-id]` lookup-ref (744), but it isn't unique. LIVE PROOF: a lookup throws `Lookup ref attribute should be marked as :db/unique: [:seon.canvas/id "probe:test"]`. So even with data present, find-tile would throw; Pod `db/transact!` of a `:seon.canvas/*` entity resolves its promise as success but the durable `:schema-flexibility :write` store never gains the attrs (LIVE PROOF store: console/id/span all false, flex :write) — the override SILENTLY no-ops with no surfaced error (a write-path smell: the wire-server rejection isn't propagated to the caller); Even if the schema were installed, span semantics (boolean hero/rail) and the grid CSS + page shell remain hardcoded in `console-shell` — DB tiles would control selection/order but not the column arrangement, gaps, CSS, or document chrome

**Refinement ideas:** Register + boot-seed the tile schema so the gate actually opens: add `schema/register!` for `:seon.canvas/id` as `[:string {:seon.db/identity true}]` (fixes the lookup-ref-not-unique throw), `:seon.canvas/console` `:string`, `:seon.canvas/span` `:int`, and install them in the boot-seed lane (e.g. seon.server.boot alongside `seed-subscription-schema!`) so `installed-schema` contains them on a fresh store; Turn `default-tiles` from a code FALLBACK into a SEED: on agent creation, transact the 9 default tiles as real `:seon.canvas/*` rows. Then `console-tiles` always reads data, the 'default' is just editable rows a consumer can retract/replace, and there is ONE code path (no hardcoded-vs-derived bifurcation); Make `:seon.canvas/span` an actual column-span integer that maps to a literal `lg:col-span-N` (whitelist 1..3 classes for the Tailwind source scan) instead of the coarse `(>= span 2)` hero/rail boolean — so arbitrary grids are expressible from data; Make the grid container + page shell data-driven: a `:seon.console/*` entity carrying columns, gap, body/shell classes, and a `:seon.console/stylesheet` href — so `console-shell` reads the document chrome + CSS link from the DB rather than hardcoding `grid-cols-1 lg:grid-cols-3` and `/css/output.css`. That is what lets a consumer ship totally different CSS/layout with zero forks; Surface the silent write failure: have the pod `db/transact!` propagate the wire-server's `:write`-flexibility rejection so an unregistered-attr tile write throws at the caller instead of resolving as success — otherwise consumers will think their override worked when it silently no-opped; Make `core-views` extensible from data (or fold it into the SCI-resolution path) so a consumer can register custom view symbols for tiles without editing the hardcoded resolution table
