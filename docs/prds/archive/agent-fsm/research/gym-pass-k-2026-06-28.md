# Gym pass^k — noise-robust scoring (single paid sample is a noisy judge)

The gym scorecard graded a single paid sample per scenario. That made it a
NOISY judge: the `canvas-goal-board` drive
(`research/canvas-drive-validation-2026-06-28.md`) single-sample-FAILED in a
build where two sibling agents passed — model variance the scorecard read as a
real regression. Fix: run each paid scenario **k times** and report the
pass-RATE, so variance can't masquerade as a regression (the `pass^k` pattern —
`reference_agentic_benchmarks_survey`: single-run noise is the documented
problem, `pass^k` cures it).

## TL;DR

- **Mechanism shipped + proven.** `seon.gym.scorecard` takes an optional
  `:seon.gym/k` (default 1). A paid battery drives each REAL paid scenario k
  times and reports, per scenario, a `:seon.gym.scorecard/pass-k` summary
  (rate + per-axis distribution) plus a battery `:seon.gym.battery/pass-rate`.
  k=1 / FREE / stub is byte-identical to before (k is a no-op there —
  deterministic).
- **canvas-goal-board at k=3 (DeepSeek): rate = 1/3, NOT a clean average-out.**
  The honest result is the OPPOSITE of the hoped "the 0 was noise, it mostly
  passes": pass^k reveals the scenario is **genuinely high-variance** (~33% pass)
  — so a single sample (whether 0 OR 1) is an unreliable verdict. THAT is the
  point: the rate + distribution is the signal, the boolean was always noise.

## The design + line format

`:seon.gym/k` (default 1) threads `request → run-battery! → aggregate`. Per
scenario, `run-battery!` drives `run-scenario!` k times **only when the drive
actually spends** (`allow-paid?` ∧ `:paid` tier); FREE-mode + stub tiers are
deterministic, so they run once (k a no-op). The k run-cards per scenario are
carried as `:seon.gym.battery/card-runs` (a vector-of-vectors, parallel to
`:seon.gym/scenarios`); at k=1 each inner vector has one card — flattening it is
the identity, so every existing axis is unchanged.

`aggregate` stays PURE (unit-tested with injected card-runs) and ANTI-CHEAT
(reads only axes — pass?/canvas/toolkit/eval-error/judge-score — never an
answer). Per scored scenario it emits ONE pass^k summary:

```clojure
{:seon.gym.scorecard/scenario          :canvas-goal-board
 :seon.gym.pass-k/k                     3        ; scored runs
 :seon.gym.pass-k/passes                1
 :seon.gym.pass-k/rate                  0.333    ; passes / k — the headline
 :seon.gym.pass-k/canvas-updated-count  1        ; distribution: drove canvas 1/3
 :seon.gym.pass-k/toolkit-calls-min     0        ; toolkit-call range across k
 :seon.gym.pass-k/toolkit-calls-max     7
 :seon.gym.pass-k/eval-error-rate-mean  0.0      ; mean over k
 :seon.gym.pass-k/judge-mean            33.3}    ; mean over REAL judge verdicts
```

The battery line gains three keys (additive; the rest unchanged):

```clojure
:seon.gym.battery/k         3
:seon.gym.battery/pass-k    [<one pass^k summary per scored scenario>]
:seon.gym.battery/pass-rate 0.333   ; mean of the per-scenario rates
```

The existing battery axes (per-competency / canvas-updated-count / toolkit-calls
/ eval-error-rate / judge-mean) aggregate over ALL k run-cards — byte-identical
at k=1, and INTERNALLY CONSISTENT at k>1 (the battery judge-mean equals the
pass^k judge-mean, never a misleading representative-first sample).

Anti-cheat preserved: `aggregate` reads axes only, never answers; the pass^k
rollup is a pure fn of the cards, unit-tested with injected fixtures
(`aggregate-pass-k-rolls-noise-robust-rate`).

### Driving it

```bash
# FREE — every loop iteration; k is a no-op (deterministic stubs)
bin/gym-scorecard

# pass^k on the paid scenarios — report the RATE
bin/gym-scorecard --paid --k=3

# FOCUS on one scenario ×k (cheap targeted paid run, not the whole battery)
SEON_AI_PROVIDER=deepseek bin/gym-scorecard --no-build --paid --k=3 \
  --only=canvas-goal-board --log=tmp/gym-passk-verify.edn
```

New gate env on the runner: `SEON_GYM_K` (k), `SEON_GYM_ONLY` (comma-sep
scenario ids).

## The proof — canvas-goal-board at k=3 (DeepSeek, sha 394520d1)

```
:seon.gym.battery/k         3
:seon.gym.battery/pass-rate 0.3333
:seon.gym.battery/pass-k
  [{:seon.gym.scorecard/scenario          :canvas-goal-board
    :seon.gym.pass-k/k                     3
    :seon.gym.pass-k/passes                1
    :seon.gym.pass-k/rate                  0.3333
    :seon.gym.pass-k/canvas-updated-count  1
    :seon.gym.pass-k/toolkit-calls-min     0
    :seon.gym.pass-k/toolkit-calls-max     7
    :seon.gym.pass-k/eval-error-rate-mean  0.0
    :seon.gym.pass-k/judge-mean            33.33}]
```

| run | pass? | canvas-updated? | toolkit (my.ui) | judge |
|---|---|---|---|---|
| 1 | **true** | true | 7 | 100 |
| 2 | false | false | 0 | 0 |
| 3 | false | false | 0 | 0 |
| **rate** | **1/3** | 1/3 | 0–7 | mean 33.3 |

The variance is in the **canvas-driving behavior**: in 1 of 3 runs the agent
designed its goal schema, composed `my.ui` (7×), and wired a status board onto
its own canvas (judge 100); in the other 2 it never drove the canvas
(`drove-its-canvas` mechanical predicate RED → pass? false; the judge, seeing no
board, scored 0). The mechanical `pass?` hinges on `:canvas-updated`, so the
scenario's pass-rate IS its canvas-drive rate.

(Side signal: the one passing run used `my.ui` 7× — the
`canonical-full-my-ns` toolkit-render fix landed since the validation drive,
where the agent hand-rolled `my.ui` 0×. The toolkit IS now reachable; the open
gap is that the agent doesn't RELIABLY reach for the canvas.)

## Takeaway — report rates, not booleans

**Was the earlier single 0 "noise"? Yes — but not in the way hoped.** The hope
was "it mostly passes, the 0 was a fluke." The honest k=3 data says the scenario
is **genuinely ~33% on DeepSeek** — high-variance, not mostly-passing. So:

- A **single sample is unreliable in BOTH directions**: the validation drive's
  pass AND a regression-looking 0 are both single draws from a ~1/3 Bernoulli.
  You cannot distinguish a flaky 33% scenario from a real regression with one
  sample — exactly the failure this fixes.
- **Report the RATE + distribution.** pass^k turns "canvas-goal-board REGRESSED
  (0)" into "canvas-goal-board is 1/3, canvas-driven 1/3, toolkit 0–7" — a number
  that moves meaningfully across SHAs instead of flickering 0/1 on model noise.
- **Follow-up (separate lane, flagged):** canvas-goal-board's true pass-rate is
  low because the agent inconsistently drives the canvas on a planning ask. That
  is a real agent-behavior finding for the UI/context lane (the live-tile prompt
  doesn't reliably trigger canvas-as-primary on planning), now MEASURABLE as a
  rate — not a scorecard bug.
