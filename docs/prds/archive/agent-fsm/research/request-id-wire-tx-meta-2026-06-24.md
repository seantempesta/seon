# `:seon.db/request-id` — what it is, where it comes from, and whether we track the right thing

## TL;DR verdict

`:seon.db/request-id` is **genuine, live, correct write-correlation provenance** — NOT
stale-build cruft and NOT redundant. It is a per-write-request UUID generated by the **pod**
(`seon.store.wire/-dispatch!`, `wire.cljs:235`), shipped over the UDS wire as the protocol field
`"request-id"`, and threaded by the **wire-server** (JVM, `seon.server.wire`) into the committed
tx's `:tx-meta` under `:seon.db/request-id` so it survives the async hop to the `::raw-broadcast`
listener thread and rides back out on the `tx` broadcast event. Its job is **echo suppression**:
the pod records each id it dispatched in `!own-request-ids` and, when the broadcast feed returns a
tx tagged with one of its own ids, **skips re-firing the native listeners** (the own-tx already
fired them via the local writer). Live proof: the running adapter shows `:own-skips 7` — the
mechanism is actively doing its job right now.

The literal `:seon.db/request-id` is NOT in `tx-meta-attrs` and `(schema/registered?
:seon.db/request-id)` → `false`, yet it still appears on stored tx-meta. That is the real defect,
but it is a **registration/declaration gap on the JVM side**, not stale-build cruft. There is **no
`:seon.db/n` anywhere in the repo** — that part of the task premise is incorrect (see §3).

**Recommendation: (b) keep it, but register/declare it properly** — and the registration belongs on
the **wire-server (JVM)**, where the attr is actually invented and seeded, not in the pod's
`tx-meta-attrs`. Plus the general fix: tx-meta keys crossing the wire should be a declared,
validated set just like domain attrs (§5).

## 1. Is the running pod bundle STALE? — NO

The pod execs `out/client/main.js` (`bin/seon:190,868`). That bundle contains **zero**
`request-id`:

```
$ grep -c "request_id\|request-id\|requestId" out/client/main.js
0
```

This is NOT evidence of staleness — it's evidence that **the symbol is munged**. CLJS compiles
`request-id` (a `let`-bound local in `-dispatch!`) and the string-keyed map literal `"request-id"`
into minified output; the local name disappears and the wire string survives only as an
obfuscated/relocated literal. The decisive proof that the mechanism is LIVE, not dead build
residue, is the running runtime itself:

```clojure
;; eval'd against the live pod 2026-06-24
{:own-request-ids-count 1
 :adapter {:seon.store.wire/started? true
           :seon.store.wire/handle 16
           :seon.store.wire/own-skips 7}   ; <-- 7 own-tx echoes suppressed since boot
 :request-id-registered? false
 :n-registered? false}
```

`:own-skips 7` can only be nonzero if request-ids are being generated, dispatched, returned on the
broadcast feed, and matched. The feature is running.

`git log -S ':seon.db/request-id'` shows it was **added** (019d594 "conn-routing + listen! hook",
through bb06be6/cdc0819) and never removed — its history is additive, ending at the current
agent-runtime stability work. It is current code.

The pod-side string `"request-id"` lives in CLJS source that compiles INTO the bundle:

- `src/seon/store/internal/wire_node.cljs:144-146` — low-level transact builder accepts
  `{:keys [tx-meta request-id]}` and sets `"request-id" (or request-id "")`.
- `src/seon/store/wire.cljs:235-240` — the real generator (see §2).

## 2. What IS request-id — its purpose? (echo suppression / own-tx correlation)

### Generated in the POD, per dispatch

`seon.store.wire/SeonWireWriter` `-dispatch!` (`wire.cljs:225-281`) is the pod's sole write path —
it forwards every `transact!` over the UDS to the wire-server:

```clojure
;; src/seon/store/wire.cljs:232-241  (verbatim)
(let [arg-map    (first args)
      tx-data    (if (map? arg-map) (:tx-data arg-map) arg-map)
      tx-meta    (when (map? arg-map) (:tx-meta arg-map))
      request-id (str (random-uuid))
      req        (cond-> {"op"         "transact"
                          "tx-data"    (wire/T tx-data)
                          "request-id" request-id}
                   (seq tx-meta) (assoc "tx-meta" (wire/T tx-meta)))]
  (swap! !own-request-ids conj request-id)        ; <-- record OUR id
  (-> (wire/rpc sock-path req ...) ...))
```

It is a fresh `random-uuid` **per write request**, recorded in:

```clojure
;; src/seon/store/wire.cljs:214-218  (verbatim)
(def !own-request-ids
  "request-ids of txs THIS pod dispatched — the listen adapter skips
   their feed events (own txs already fire the conn's native listeners
   via datahike.writer/transact!)."
  (atom #{}))
```

### Threaded through the wire-server (JVM) into tx-meta and back out

The JVM `handle-op "transact"` reads the protocol field and **injects it into the committed tx's
tx-meta** so the writer-thread listener can see it after the request thread has returned:

```clojure
;; src/seon/server/wire.clj:398-419  (excerpt)
request-id (let [r (get req "request-id")] (when (and r (not= "" r)) r))
...
;; Carry request-id through tx-meta so the per-conn ::raw-broadcast
;; listener emits it on the pub event ... ensure-db! seeds the
;; :seon.db/request-id attr so :schema-flexibility :write accepts it.
tx-meta*   (cond-> (or tx-meta-in {})
             request-id (assoc :seon.db/request-id request-id))
report     (if (seq tx-meta*) (d/transact conn {:tx-data tx* :tx-meta tx-meta*}) ...)
```

The `::raw-broadcast` `d/listen!` callback — which runs on the writer thread, AFTER the request
thread — pulls it back out of tx-meta and stamps it onto the broadcast event:

```clojure
;; src/seon/server/wire.clj:343-355  (excerpt)
(fn [report]
  (let [request-id (:seon.db/request-id (:tx-meta report))      ; <-- read back from tx-meta
        r          (assoc (tx-report->ok-map report nil) :request-id request-id)]
    (bcast/broadcast! (ok-event-from-report db-name-str r))))   ; <-- "request-id" on the event
```

This is exactly WHY it must ride in tx-meta rather than a local: the broadcast is decoupled from the
request handler (a `d/listen!` on the writer thread), so the only channel that survives the async
hop from "request thread" to "writer/listener thread" is the committed tx-meta itself. The
wire-server `seed-base-schema!` (`wire.clj:74-83`) installs `:seon.db/request-id` as a
`:db.type/string`/`cardinality-one` datahike attr precisely so `:schema-flexibility :write` accepts
it in tx-meta.

### Consumed back in the POD — the actual point

```clojure
;; src/seon/store/wire.cljs:324-334  (excerpt) — the listen! feed adapter
(defn- handle-feed-event! [conn ev]
  (let [rid  (get ev "request-id")
        own? (boolean (and rid (contains? @!own-request-ids rid)))]
    (if own?
      ;; Own tx already fired the native listeners via writer/transact!;
      ;; just advance the chain + drop the id.
      (do (swap! !own-request-ids disj rid)
          (swap! !adapter #(-> % (update :own-skips (fnil inc 0)) ...)))
      ;; FOREIGN tx: synthesize a report and fire the native listeners.
      ...)))
```

**Purpose, precisely:** `request-id` is a per-write-request **echo-suppression / own-vs-foreign
correlation token**. The pod is BOTH a writer (forwards txs) and a subscriber (consumes the
broadcast feed to fire local `listen!` handlers for FOREIGN writes from other agents/clients).
Without request-id the pod would double-fire its own listeners — once locally via
`datahike.writer/transact!`, once again when its own commit comes back on the feed. The id lets the
adapter recognize "this returning tx is mine, I already handled it" and skip it. It is correlation
+ idempotency-of-listener-firing, not durable provenance.

PROTOCOL.md documents it as caller-supplied and optional (`client-runtime/docs/PROTOCOL.md:140`,
`:159`, `:176`, `:334`) and explicitly names "request-id dedup" as part of the feed's gap list
(`:367`).

## 3. Relationship to `:seon.db/n` — `:seon.db/n` DOES NOT EXIST

The task premise states `:seon.db/n` is "a known caller-supplied wire sequence/correlation number."
That is **not true of the current codebase**:

```
$ grep -rn ":seon.db/n\b" src/ client-runtime/ docs/
(no matches)
```

`(schema/registered? :seon.db/n)` → `false` on the live pod. There is no wire sequence number named
`:seon.db/n`. The ordering/identity primitives that DO exist on the wire path are:

- **`basis-t`** (`"basis-t"` / `"basis-t-before"`) — datahike `:max-tx` of db-after/db-before. This
  is the real monotonic tx sequence; the pod's RYOW deref (`ryow-deref!`) waits for a local db value
  at/past the ack'd `basis-t`, and the feed adapter advances `:last-db` by basis-t. **This is what
  "n" would have been** — datahike already provides it.
- **`db/commitId`** — a per-commit UUID datahike stamps into tx-meta (documented in PROTOCOL.md's
  worked example, `:351`). This is datahike-native commit identity.
- **`request-id`** — the pod-generated per-request UUID described above.

So there is no n-vs-request-id question to settle as posed. The honest framing: `basis-t` is the
ordering sequence (datahike-owned), `db/commitId` is the commit identity (datahike-owned), and
`request-id` is the **request** identity (pod-owned, for echo suppression). They are three distinct,
non-redundant things. If the intent of "`:seon.db/n`" was a caller wire-sequence, it isn't
implemented — `basis-t` covers ordering and nothing needs a separate `n`.

## 4. Are we storing the RIGHT thing? — Yes, the value; no, the declaration

For the pod↔wire-server async write path, the tracking we actually NEED is:

1. **Match a forwarded write to its commit** so the dispatcher's promise resolves with the right
   report → handled by the synchronous RPC reply (`basis-t` + tempids in the response), NOT by
   request-id. request-id is not load-bearing for the reply.
2. **Distinguish own commits from foreign commits on the broadcast feed** so the pod doesn't
   double-fire listeners → THIS is exactly what request-id does, and it is correct and live
   (`:own-skips 7`).
3. **Ordering / read-your-writes** → `basis-t` (datahike), correct.

So request-id is serving the right job and the stored *value* is right. The defect is purely that
the attr is **undeclared on both sides**:

- On the **pod**, it never enters `seon.db`'s `tx-meta-attrs` (`#{:seon.db/agent-id :seon.db/eval-id
  :seon.db/session-id :seon.db/resume-marker? :seon.db/turn-id :seon.db/replay? :seon.db/origin}`)
  and is not `schema/register!`'d — because the pod never *stores* it through `seon.db/transact!`;
  the pod injects it directly into the wire protocol map in `store/wire.cljs`, bypassing the
  `seon.db` tx-meta machinery entirely.
- On the **wire-server**, it IS seeded as a datahike attr (`seed-base-schema!`) but via raw
  `d/transact` of a `:db/ident` map — it is **not** a `schema/register!`'d Malli attr, so
  `(schema/registered? :seon.db/request-id)` is false even though datahike accepts it.

That mismatch is why it "rides in unvalidated." It is real provenance that escaped the
register-everything discipline because it's injected at the wire layer, beneath `seon.db`.

---

## 5. Recommendation

**Adopt (b): keep request-id, register/declare it — on the side that owns it (the wire-server).**

Concretely:

1. **Register `:seon.db/request-id` as a Malli attr** (`schema/register! :seon.db/request-id
   :string`) in the wire-server, alongside (or replacing the raw `:db/ident` form in)
   `seed-base-schema!`, so the JVM's own `register-everything` discipline covers it and
   `(schema/registered? :seon.db/request-id)` is true. This is the home-namespace owner: the attr is
   invented, seeded, threaded, and read back entirely within `seon.server.wire`.
2. **Declare the wire tx-meta key-set explicitly.** Today the pod's `tx-meta-attrs` is the declared
   auto-stamp set for `seon.db`-routed writes, but request-id enters BELOW that, in
   `store/wire.cljs`. Make the wire layer's injected tx-meta keys a named, documented set (request-id
   today; room for more) so they aren't "merged unvalidated" silently. The general rule the task
   asks to confirm — **tx-meta keys crossing the wire must be registered/declared like domain
   attrs** — is correct and should hold; the nuance is that the *declaration site* for
   request-id is the wire-server, not the pod's `tx-meta-attrs` (the pod doesn't store it, it
   transmits it).
3. **Do NOT rename, do NOT drop.** The name is accurate (it correlates a write *request*).
   It is not redundant with `basis-t` (ordering) or `db/commitId` (commit identity) or any
   `:seon.db/n` (which doesn't exist). Dropping it would reintroduce double-fired listeners.
4. **No restart needed for correctness** — the running pod is not stale; it's working. The only
   change is closing the registration gap so the attr stops looking like unexplained, unregistered
   tx-meta to future agents.

Rejected options: (a) stale-build cruft — false, it's live; (c) rename — the name is right;
(d) redundant with `:seon.db/n` — `:seon.db/n` doesn't exist and basis-t/commitId cover the other
roles; (e) need more/different tx-meta — the set is sufficient for the three tracking needs;
only the *declaration* is missing.
