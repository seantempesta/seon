# Tasks and templates

All work is task entities on main, linked by `:needs`; a template turns what someone asked into the linked set that works it, and root writes the whole set in one transaction before any agent of it forks.

## A request is one transaction

A request becomes its whole linked task set in one transaction on main, released, and the reconciler forks the set's first agent only from a main that holds all of it, so every agent of it reads the same data from its first form.

By default (`my.root/request!`), ```seon.template/request``` makes the request one task of kind `:whole` on its own branch, which one agent works through in one session: it reproduces what the plan says is wrong, writes the red proof, makes it green, merges main at each green and keeps it green, and its green branch merges into main as a merge task's does (```seon.task/merges?```); its runs start as work does, not one at a time as merges do ([decisions](decisions.md#a-request-is-one-whole-task-for-now)). For an experiment, `my.root/request!` takes another template in its place:
- ```seon.template/design-build``` makes the request its **design-build** task (kind `:work`, the `:work` instructions: the red proof, then green on its branch, no merge of its own) followed by `<name>-merge` (kind `:merge`, `seon.template/with-merge`), needing it on its branch; the two are one session there (```seon.task/session-key```);
- ```seon.template/stages``` makes the staged set from the same declaration:
- the request itself as the **design** step (kind `:design`, its plan the request's words);
- `<name>-implement` (kind `:implement`), needing design;
- `<name>-merge` (kind `:merge`), needing implement: the template adds it, explicit in the graph from the start.

All three check out design's branch, so implement holds design's schemas, stubs and red proofs, and merge holds both. The request's proofs are design's and reach the later steps along `:needs` (`seon.task/accumulate`).

```seon.template/request-tx``` is the one transaction: `seon.task/create-tx` of the set (any template's), then `seon.task/execution-tx` releasing it. `my.root/request!` writes it with one `seon.root/transact-main!`. Since the reconciler reads only committed main, no agent of the set sees part of it. Not this: create held, then `my.root/run!` (two transactions), or adding `:needs` afterwards.

`seon.template/with-merge` makes a linked set the same way, for the experiment templates only (`design-build`, `stages`): it follows each work task with its merge task, gives a task with no branch its default one (`seon.task/default-branch`), and points a `:needs` on a work task at that task's merge. A task file's declaration (`my.root/task-files`) is one `:whole` task (`seon.template/request`) that merges itself, no merge task beside it; a task file's tasks are written held (`seon.task/load-tx` over `seon.task/create-tx`: new entries created held, changed ones updated, removed ones cancelled), so nothing loaded from a file runs until root releases it with `my.root/run!`.

A merge whose branch's change reaches process tests (```seon.program/process-tests```, recorded as `:seon.run/deferred`) is gated first, nobody asking (a root with no checkout to run them on holds it, saying so): the reconciler's `:gate` writes the changed namespaces' files over a worktree of the merges head and runs those tests there (the `:tests` effect, ```seon.fx/run-tests```; prove's entry, `bin/prove --tests`, through ```seon.fx/test-command```), records `:seon.run/deferred-results`, and a red is refused as a red proof is. An agent's turn and root's judge run only the in-process tests, in a fork of the agent, never a process test that is none of the task's proofs ([merging](merging.md#a-merge-runs-what-the-change-reaches)).

## Releasing and cancelling

A task is written held, released once and cancelled by root's functions; nothing autoruns.

```my.root/create!``` writes declarations as held tasks and answers the writer's answer, or the error. ```my.root/run!``` is the one release: each held task becomes `:running` by compare-and-swap on main, so a cancel between its read and its write refuses the write; an id that is not held (unknown, running, cancelled) is answered `:seon.root/not-held` under `:not-held`, and only the held ones are written. ```my.root/cancel!``` writes `:cancelled`: a live run is killed, and the tasks that need it stay blocked. The writes are ```seon.task/execution-tx``` (the desired execution) and ```seon.task/env-tx``` (the desired environment: branch, model, max turns). ```seon.reconcile/desired-env``` states, from the task, the environment its runs must run in (the turn bound through the one config resolver), and a run in another environment is restarted clean; a merge task's limits are ```seon.reconcile/merge-limits```, through the same resolver. The run's lifecycle is [root's](root.md#runs-and-judging).

## Task files

A task file is one EDN vector of declarations named by its owning namespace, and root keeps main's tasks equal to the files.

```my.root/task-files``` reads the files under `:seon.config.root/tasks-dir` as `{owning-ns declarations-or-error}`; ```seon.task/file-declarations``` reads one file's text, and text that is not exactly one vector is the `:seon.task/refused` error, data and not a throw. ```my.root/load-tasks!``` reconciles the read into main: new entries created held, changed ones updated, removed ones cancelled, unchanged ones nothing, each task made to state exactly its declaration by ```seon.task/entity-tx``` (the values an entity holds that the declaration lacks retracted, the ones it lacks asserted). A good read writes root's `:seon.root/tasks` outcome; ```my.root/load-errors``` picks the typed errors out of the loaders' answers (a refused file, a refused load), each to be recorded and never dropped. Root loads the files when they change ([health](health.md#every-writer-root-loads-what-changed)).

## The agent knows its task

An agent holds the task and run root forked it for from its first form: `my.task/current` reads the task through `seon.turn/current-task`. Both ride `seon.root/spawn!`'s opts (`:branch`, `:task`, `:run`) into the writer's `:spawn` request and the fork server's `:fork` message, and `seon.agent/init!` keeps them in the agent's state (nil for an agent forked with none). A turn loop, a context read and an attached outside agent read it the same way.

## Task content reaches main at the run's end

When a run ends, every task whose content its branch changed since the branch's base is written onto main, and one that main also changed, differently, is a conflict for root: a task edited on two live branches should not happen, and when it does, root resolves it.

`seon.task/carry-tx` compares the merge base, the branch and main over the carried task attributes (`seon.merge/carried-platform-attrs`: the plan, instructions, proofs and a stall task's cause that `my.task/update!` edits). Tasks main does not hold are left. A member the branch changed and main did not overwrites main's; one equal on both sides writes nothing; one main changed too, to another value, is never resolved: it goes on the run as `:seon.run/task-conflicts` and `seon.problems/report` shows it in its `:task-conflict` class. Root's judge (`seon.reconcile/judge-tx`) calls it with the base the writer's branch read answers, so it is the one carry: a design step's plan reaches main before implement starts, on the same branch. Merging merges the program only (`:data-attrs #{}`), so main's task edits never put a merge behind. Not this: carrying only the run's own plan, or merging task data at merge, where every judged plan on main would make each merge `:seon.merge/behind`.

## A refused run is held for root

A task whose run was refused, or that its agent marked failed, is held for root: its failure and evidence are data on it, the problems read shows it, and nothing retries it on its own.

Every failure takes the one hold. The reconciler judges an ended run by the done rule; a reason (a red or unrun proof, a regression, a stray red, a contract gap, an unmerged key, `:no-design`, whatever the run's outcome), a dead agent, or a merge the octopus merge refused is its `:hold` action, and `seon.reconcile/hold-tx` is its one write: `:seon.task/failure` (the reason as the reconciler states it, and the run), `:seon.task/evidence` (the run's conflicts, unmerged keys, red proofs and the reason), `:seon.task/execution :held`, and the run `:closed`, answered once. The hold is a compare-and-swap from `:running`, so a cancel that merged first refuses it. An agent calls `my.task/fail!` instead: the failure (with a counterexample) goes on its task on its branch and its turn loop ends; `seon.reconcile/judge-tx` carries a failure of *this* run onto main with the task held (an earlier run's failure on a reused branch is not carried), and the judged rule closes the run. No task is created and none cancelled.

`seon.reconcile/task-state` reads held-with-a-failure as `:failed`; `seon.problems/report` lists it in its `:failed` class with its evidence, open while held; at quiescence `seon.reconcile/root-causes` names it as a root cause with the released tasks it blocks (as it does a run that parked its session, waiting for a message, and a merged run whose write-back failed). An idle system then does nothing: a held task is not ready, and root's own commits do not end a quiet spell.

Root, or the owner through root, decides: release it with `my.root/run!`, edit the task first, or cancel it. A released task's next run runs on the same branch (the writer resumes a kept branch; its agent, forked holding main's program, loads the branch's own changes since its merge base on top, ```seon.agent/init!```, and the run merges main first, ```seon.turn/work!```, so a branch behind main holds what main gained, its tests included: `seon.agent-test/a-resumed-branch-holds-what-main-gained`), and `seon.task/onto-tx` puts the task onto it as main holds it, its failure and evidence included, so the agent starts from the evidence (its context's `:evidence`). The failure stays as a record after a release. Not this: a refinement chain (design → implement → test → merge on a fresh branch, the failed chain cancelled) attached while a budget lasted, then a "budget spent" fact; or a send-back carried as a string in the run's end.

## The done rule

`seon.reconcile/done-explain` says why a run's measured facts do not make its task done; empty means done. A proof with no result never ran: it refuses as `:proof-unknown`, not `:proof-red` (v1's reading), so the reason names what was not measured. A proof left out of a run (a process test that was not run) is neither red nor unknown; an open problem the branch's work made true (`seon.problems/caused`) refuses it too, and a `:design` task may leave its proofs red but not unknown, until its plan differs from the one its run began with. Every task, a design too, is refused `:no-proofs` until it has one: a design that only rewrote its plan was green at its first plan edit, the proofs it named never written (live agents, 2026-10-25), and the reason shows the form that registers one.

A task's proofs are content its agent may improve, like its plan: a design made from a request carries none, so it registers each red proof it writes with ``(my.task/update! :seon.task/proofs conj 'ns.x-test/a-proof)`` (`seon.task/member-tx`), and a red test it has not registered is a `:stray-red` whose reason shows that form. The judge carries the proofs onto main with the plan (`seon.task/carry-tx`, a set compared as a set), so the done rule sees them red at design and green at implement (owner, 2026-10-25, DECISIONS Dogfood rulings).

A contract gap is a function the branch's own changes define without a contract: `seon.merge/uncontracted` over the three-way merge's `:ours`, one answer for the writer's merge gate and for root's judge (which reads it from the writer's `:branch-diff`), so the done rule never refuses what the merge would take, or the reverse. The agent's own done check (`seon.turn`) asks the same function of its branch's changes since its merge base.

## A task's facts and how they are read

Tasks, runs and root's boot are entities on main, written by functions that answer transaction data and read back as plain values.

Writes: ```seon.task/task-id``` is a task's handle (`ns/name`, derived from its namespace and name), ```seon.task/default-branch``` the branch a task without one checks out (`task-<ns>-<name>`), ```seon.task/run-id``` a run's id (numbered from 1 in start order). A run is written by ```seon.task/run-start-tx``` (root observed it spawn its agent, or refused the spawn and no agent exists; the run refs the agent's entity by its key), moved by ```seon.task/status-tx``` (Datahike's compare-and-swap, so a racing observer that already moved it leaves it) and ended with ```seon.task/end-members``` (a count nobody measured is absent, never 0). ```seon.task/message-tx``` is the one message fact, written by root on main and by the turn that takes it on its branch. ```seon.task/placeholder-assertion``` is the assertion `seon.context` writes into a proof's test that does not exist yet, so `seon.problems/uncited-tasks` can read a proof still holding it.

Reads: ```seon.task/tasks``` and ```seon.task/task``` answer a task with its accumulated plan and proofs, ```seon.task/accumulate``` computing them over its needs (a task inherits its prerequisites' plan and proofs and adds its own, so a refinement only tightens; each prerequisite once, first). ```seon.task/runs``` and ```seon.task/run``` answer runs (a run a branch only names by reference is no run record there), ```seon.task/running``` the running ones by one seek of the status. A run's lifecycle sets are declared once on `:seon.run/status`'s schema and read once: ```seon.task/finished``` (makes its task done), ```seon.task/judged``` (the done rule judges it) and ```seon.task/failed``` (a death). ```seon.task/done?``` asks whether a task has a finished run by one seek, and the reconciler's index answers the same from its own facts ([root](root.md#the-reconcilers-index)). ```seon.task/root``` is root's boot and config keys, and ```seon.task/entity-value``` and ```seon.task/entity-ids``` are what the index reads: the task, run or root an entity now is, and every such entity before the index watches.

## Where a task's state lives

A task's state is derived from its runs on main (```seon.reconcile/task-state```: `:cancelled`, `:merged`, `:done`, `:running`, `:blocked`, `:failed`, `:held`, `:open`), never stated. Work a worktree session merges has no run, so the merge that completes it says so, a `Completes: ns/name` line, and removes its task file entry in the same commit ([a merge says what it completes](merging.md#a-merge-says-what-it-completes)). A run's own lifecycle (its outcomes, judging, root causes) is [root's](root.md#runs-and-judging); its turns are [turn](turn.md)'s.
