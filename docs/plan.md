# The plan

What Seon is for, where it stands, the one step being worked now, and the steps after it. [AGENTS.md](../AGENTS.md) is how a session works; the [map](README.md) is how the system works; [decisions](decisions.md) are the owner's rulings; git is the history.

## The goal

**A user asks for something, and a Seon agent does it, end to end, while the user watches.** In full:

1. **A request becomes a task**: its plan (what to change and why) and its proofs (the tests that say it's done).
2. **An agent works the task at a real REPL**, in its own forked process on its own branch, in few turns:
   - it sees its world as data (`@ctx`, pulled from the db), with the task, the code its plan cites and what it last did;
   - every eval answers small: its value or an error, plus one line of what changed;
   - main's difference from its branch is in that line every time, so nothing at the end is a surprise;
   - the tests its change reaches run by themselves, by digest; a failure comes back as data it can fix.
3. **Done means green and merged**: the done rule checks the proofs at the branch's commit; the branch merges into main; main runs the result next.
4. **The user watches it live**: the agent's page is a chat (the task, the agent's reply, each eval with a one-line outcome), and the agent sees what the user sees.

**Measured as** turns to green and tasks merged. **Held to:** nothing crashes or hangs (every failure is data to the agent); everything shown is derived from the db at t; one mechanism per job; every change earns its place; a v1 capability is present or dropped on purpose ([parity](parity.md)).

## Now: one step

**One tree of data that renders itself, read by two clients.** The model's context goes through the same ratom components as the page: a component transforms its data, filtering it and adding what it needs from the db, into hiccup: the one state, drawn to html directly and read by the model. How it works: [the model's context](render.md#the-models-context-a-cached-prefix-then-the-turn); what the model knows is its record (task `seon.render/what-the-model-knows-is-its-record`).

In flight, each on its own branch and merged when proved:
- **The data model** (docs/sharing.md; the Optimization session by the owner's word, 2026-11-07: "take control and finish this up"). Built: facts by where they can differ, messages as platform records an agent writes onto its branch, a merge by key with parents the commits merged, a form's place a sort key, test facts only where read, slow tests last, a merged tree analyzed with no worktree, a red in the daily run told, a function's cost as a fact. Next, approved by the owner 2026-11-08: content-hashed nodes and a new store (seon.db/a-branch-is-main-plus-its-own-changes) and a cheap d/schema (seon.db/the-schema-map-is-read-once-a-value), both Datahike fork changes; a test keyed by the vars it called, since not knowing what it executed is a bug (seon.program/a-tests-digest-reads-what-it-ran); user-branch merges (seon.merge/what-a-side-never-held-is-no-change, seon.merge/a-merge-takes-options); a task per red in the daily full test (seon.prove/a-red-in-the-daily-full-test-is-a-task); the word sweep (seon.agent/the-words-are-clojures). The Web session: each attribute of an agent's entity set on one branch, and one reading of how it stands. No bound on agents messaging each other until it is seen. On main 2026-11-08: a merge leaves no name unbound (seon.merge/dangling), an agent's pull after its own merge starts from what main merged, :var/meta in place of :var/kind (the store erased for it), a function's cost written once a run. A diff of two stored commits costs the leaves they hold apart, flat in the store's size; its O(index) cost was the in-memory test store, where nothing is stored (docs/sharing.md#what-each-operation-should-cost). Open: a task merging from its data, withdrawn on a regression (seon.task/a-task-merges-from-its-data).
- **Agents merging real tasks, the first priority (the Context session).** Three real tasks merged on flash with their proofs written in the plan first, each proof red without the change: an outside context's max-turns in 11 calls, the banner's count in 26, the config panel's layers in 60 (runs 12 and 13, 2026-11-07/08; about $0.11; small samples, no rate claimed). What made them merge: a failing proof in the plan, `edit!` on an ns form, every merge's candidate analyzed ([merging](merging.md#a-merge-runs-what-the-change-reaches)), every eval of a reply running. What still costs turns: reads (42% of a 60-call agent's prompt was its own `source`/`grep` results; a broad `grep` fills the whole 16,000-token result budget whether printed or not), and docstring citations for code outside Seon's wiki. An A/B of nine real runs: with a status line saying a person's message came after the plan last changed, plans tracked the person 3 of 3, without it 0 of 3; no agent in any arm saw its proof red (Optimization proposes the proof's verdict on the branch's base as the fact). Next, the owner's goal "go from a fresh chat session to work being done and merged": Context the status's next steps and one instruction text, Optimization merging by data and reopening a merged task on a message, Web the end-to-end test in a browser.
- **What the model is sent (the Context session), 2026-11-08 evening:** a reply is its text and its calls, each eval its own `{intent, code}` call (an A/B on flash: the message kept on 10 of 22 replies, each good; the owner: a message only when there is something to say), and every model reply and eval output streams to the page as the whole text so far, nothing written in flight (jolt/arm-content, reviewed, landing). Next: the hiccup's diffs derived per turn from each turn's recorded commit through a `:seon.render/changes` input, with the stored page evals and the redo deleted (task `seon.render/what-the-model-knows-is-its-record`, building in steps); ids by content where the same content is the same thing and by a UUID's hash where a thing is always new, with one live process per agent (task `seon.root/an-agent-is-named-by-its-key`, building).
- **What the model knows is its record (Context, after Web's render rename):** a restart sent the whole page again (14,269 to 18,608 chars on one small task), since what the model was shown lived in the walk's process memory. Task `seon.render/what-the-model-knows-is-its-record`.
- **False greens (owner: "We need to be able to trust the test system"):** the Context session. A test with no assertions is stored green; whether that becomes red waits on the owner's go. A nightly full run on main with an empty result cache, its reds becoming tasks, is agreed and not built.
- **One test system, and time from a proved change to main:** the Optimization session. Landing (owner, 2026-11-08: "fix this asap"; "just batch it for now"): every session works in its own worktree and the main tree stays on main; `bin/land` proves and lands a branch ([merging](merging.md#a-branch-lands-with-binland)). Each session proves its own branch with a bare `bin/prove`, which runs every test its change reaches, process and slow tests last, and lands it itself; `bin/land` answers at once from that green (owner, 2026-11-08: "I want to remove all bottlenecks"). A slow test is a bug (owner: "Slow tests should be treated as bugs and fixed"): next, a root boots and a first agent spawns in what they need, and each slow test is fixed or cut. A root's and a checkout's digests match on one tree, process tests too (0 of 1,428 differ), and a process test green at its digest asks no gate; how often that saves a real agent's gate is not yet measured. `agent-tests`' own cache and the several selectors are what else is outside it. A long gate shards by its work; a prove stops on a red `laws` or `health`; a merge of the wiki, tasks or tests skips the steps that run the binary ([merging](merging.md#a-merge-runs-what-the-change-reaches)). A turn that writes no form does not wait on the embedding model, and an outside agent's reply merges main as a model's turn does. Open flakes: `seon.agent/a-proof-child-that-died-says-why`, `seon.check/a-check-step-sits-idle-until-its-limit`.
- **Users, worlds within worlds:** the Web session: messages, then users, sessions and the home page ([users](users.md), with its steps and who owns what). Merges, eval ids and how results are stored are the Optimization session's (owner, 2026-11-07).
- **The web pages:** the agent's chat, `@ctx` and raw-wire debug tabs and root's work list are on main. An opened step has Run, To here, Copy, Edit ([run again](turn.md#an-eval-can-be-run-again)) and Back to here ([going back](turn.md#an-agent-goes-back-to-an-eval)). Source editing is paused until agents merge at all: its design is on `seon.render/an-edit-reaches-disk-when-asked`. A handle names its value, so the same answer has the same handle. A failed run's page says why it failed and how its proof went ([the page](render.md#the-page)). Next: source editing with an explicit disk sync (`seon.render/an-edit-reaches-disk-when-asked`).

- **Seon's own files move by branch (the Context session):** `edit!` takes any path, and `bin/*` is on main as files of the program: indexed at import, merged per key, written back with its mode after a passed merge, each file checked first as its reader reads it, on the mechanism schema files use ([decisions](decisions.md#seons-key-files-are-facts-on-one-mechanism)). The config file is on main as entries too, read by a process from its own branch ([config](config.md#a-process-holds-its-branchs-config)), and a boot names a file it can't load and goes on. Task `seon.source/seon-files-move-by-branch`.

- **A test's digest is what it read, and a branch is main plus its own changes:** the Optimization session. Verdicts name all a test ran; selection is unchanged (`seon.program/a-tests-digest-reads-what-it-ran`). A tree-level merge is prototyped on a scratch store, correct by datoms, 21 percent private nodes against 89 after 200 merges, not landed, and it needs the owner's go (`seon.db/a-branch-is-main-plus-its-own-changes`).

Open with the owner: starting agents in a scratch REPL so a try-out `def` isn't program; whether a task's gate runs only what it names; a second `:tests` worker's memory; a problem class for bare names and `path:line` in plans, and for tasks whose proofs are all green already; the print budget; `seon.reader/forgive`; `:seon.error/fix` hints; what happens when a chat render breaks; `seon.repl/type-findings-are-an-evals-warnings`' go; surfacing a red from the nightly full run. From the web session's audit of unmerged work, held for the owner: the staged kinds (`docs/decisions.md` still says they go, and they are on main; only the old branch was deleted); the demo root on port 12871; worktrees `bench-b` and `ctx-ui-review` (uncommitted scripts) and `meas-step6` (1.8 GB of runs).

## After that

These follow once the tree works, in this order.

1. A Seon agent works real tasks on the standing root, on the owner's yes, end to end. Measured as tasks merged, turns to green and time from a proved change to main.
2. The backlog: 309 tasks kept after a first pass, not all shown valid; 15 wait on the owner, one decision at a time.
3. Compaction, once the tree works: an eval is data, so removing or reducing one is a change the tree re-renders.

What happened and when is in git's merge messages, and how the system works is in the [map](README.md).
