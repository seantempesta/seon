# References

A reference is what a text cites, read by one parser from the text itself, never from a declared list.

Every text Seon reads as prose (a task's plan, a wiki page, a docstring) goes through ```seon.ref/parse```, and what it cites (```seon.ref/references``` keeps each once, and only what names something on the db) becomes that text's references: a plan's are its task's, a section's are its own, a docstring's are its definition's. The context pulls each one at the depth its citation asks for. The rule is v1's (`~/src/seon/docs/seon/schedule/cards/TASK-CHAIN.md` §3a), ported onto next's program facts.

## One parse

```seon.ref/parse``` reads Markdown once (given its path, or nil for a plan or a docstring) and returns its sections and its citations. A section has an address `path#anchor` (GitHub anchors), a heading, a level, a line span, a parent, a lead (the heading's next block when it is a paragraph) or an opening (any other first block), and its own text (the lines after its heading up to the next heading). A citation is a name, or a path with an optional anchor, with its depth and line, one per mention. ```seon.ref/scan``` is the scanner under it, one pass over the characters: ATX headings, fenced and indented code, code spans by CommonMark's equal-length backtick rule, inline links, and paragraphs ended by blank lines. A fenced code block carries its content's offsets (`:seon.ref/text-from`, `:seon.ref/text-to`, between its opening and closing lines) and a list block its items' (`:seon.ref/items`, each item's content after its marker, and `:seon.ref/ordered`), so a renderer cuts them with `subs`, never by a regex over the block. Setext headings, reference links and HTML blocks are out of scope; the subset was proven against 70 examples of the CommonMark 0.31.2 spec (`seon.ref-test/commonmark-examples-for-the-subset`). No Markdown library on Jolt gives a tree, which is why the scanner exists.

## The delimiter picks the depth

The delimiter around a citation decides how much of what it cites is pulled.

- A bare word holding a `/` is its **summary**, and counts only when it names something. A var's `#'` before it is punctuation, so `#'seon.context/printed-run` cites the var. A word read inside a `"..."` string is data, as quoted output is, never a citation: a reproduction's `"docs/flow.md"` names no page (`seon.ref-test/a-string-literal-in-prose-cites-nothing`). A code span between quotes is still a citation.
- One backtick, or a link, is its **doc**.
- Three or more backticks are its **code**.
- Two backticks are a literal, never a reference: write ``ns/name`` to mention a name without citing it.

Only a span of exactly one qualified symbol or keyword is a name. A form, an alias form such as `str/join`, a name followed by more words, and a name ending in `*` are code or prose. A span whose first segment is a top-level entry of the checkout is a path. A `path:N` or `path:A-B` citation is that file, marked `:line-reference`: line numbers go stale, so cite the var instead. ```seon.ref/cited``` keeps each name once, at its strongest depth, where it is first mentioned.

## Resolving and showing

```seon.ref/references``` resolves names against the program's `:var/name` facts, keywords against the schema registry and paths against the checkout; ```seon.ref/names``` is the qualified symbols alone (what `seon.reconcile/hairy` and the context use). ```seon.ref/view``` shows a section at a depth: at summary its heading and its lead's first sentence, at doc its lead and the headings below, at code the whole section. A section with no lead answers `:no-lead` at summary and doc depth, so every section should open with one sentence that stands alone.

A var is shown by the same depths (```seon.docs/resolve-ref```): at summary its arglists and its docstring's first sentence, at doc its arglists, docstring and contract, at code its recorded source and `:change`, the form that changes part of it (```seon.repl/edit!```, [changing a definition](agent.md#changing-a-definition)). The source is whole: the one printer cuts it where it is shown, breadth first under the context's budget, so every cited var shows before any one source is read far, and the cut reads its rest through the form that answers the task's data as data (`(subs (get-in (my.task/data) [:write-set 0 :source]) n)`, ```my.task/data```); a var with no docstring shows its source at doc depth. (It was swapped for the doc past `:seon.config.render/reference-tokens`, a cut before the printer, until the clipping audit of 2026-10-25; whole sources had been 82-88% of a measured task's context with no budget at all.)

A namespace at code depth is its ns form as recorded, so its requires and aliases, then a line for each definition, privates included, in file order (```seon.docs/namespace-source```); `(source ns)` shows the same text, so a citation and the REPL give one answer. At summary and doc depth it is the docstring and the definitions as before ([files and namespaces on demand](#files-and-namespaces-on-demand)).

A schema key is shown by ```seon.docs/schema-view``` from the db's schema entry, never the resource file it merges into (an agent has no checkout): at summary the form that reads it; at doc and code its form as written, `:keys-it-names` (the form of each other key it names, one level, so the agent does not read them one a turn) and `:change` (how the key changes at the REPL: ``(my.schema/register! k form)``, starting from ``(get (my.schema/forms) k)``). A key no schema registers is not nil: ``(my.schema/forms k)`` answers `:seon.schema/unknown-key` naming the keys its namespace registers, and a registration whose form is no EDN is refused naming the value and where it is (```seon.program/non-edn```).

## Cost

One parse is linear in the text, about 70 bytes allocated per byte of it (the 37 pages of the wiki, 0.9 MB: 54 MB, of which the scan 26 MB; 2026-10-29). A candidate name is read by its characters (```seon.ref/qualified-name```; `seon.ref-test/a-name-is-read-as-the-reader-reads-it` holds it equal to the reader), where `seon.reader/read-text` took about 13 µs and 18 KB a name, half of it `seon.reader/opts` rebuilt per call, and 3,328 spans of the wiki reach it: edamame on Jolt allocates about 2 KB per symbol it reads, so a read per span was most of a parse. The proof is `seon.ref-test/one-parse-costs-one-pass`.

## Task references

A task's references are the names its plan and instructions cite, derived by the task writer and never authored.

```seon.task/create-tx``` stores them as `:seon.task/references` (the program's names from ```seon.ref/names```, taken from the plan and instructions; no names, no key), and ```seon.task/load-tx``` restates them from the declaration when a plan changes, so the context and the write set read one derivation. Beside them it stores `:seon.task/citations`, every citation the text makes at its depth (```seon.ref/cited``` of the one parse), and an agent's own write of its plan or instructions (`my.task/update!`) derives all three again (```seon.task/rederive-tx```). Every draw of the agent's page reads that fact (```seon.context/plan-citations```, which keeps those db holds now, ```seon.ref/kept```) and never parses the plan again: the parser is program an agent may be changing, and md-scan #10's redefined `scan`, run by the layout each frame, left the page with no status (2026-10-29). A citation that resolves to nothing is a problem on the task, never an error (v1's rule, TASK-CHAIN §3): ```seon.task/citation-problems``` answers `{:task id :name sym :problem :unresolved}` for each, and `my.root/create!` and `my.root/load-tasks!` carry them as `:problems` beside the write, so whoever wrote the plan sees it when they write it. In the agent's context the same name shows `:unresolved true` with `:problem`, the message from ```seon.ref/problem-messages```: it resolves to nothing on the branch, what the task intends is its plan's to say, and two backticks mention a name without citing it. A plan that cites the function its proof calls, not the task's own name, is the cheapest way to a good context. A reference to another task by its id is shown by its plan (`seon.ref/task-view`) and is not a var of the write set.

The names are the program's (```seon.program/program-names```: a namespace the program holds). A reproduction's test helper, library call and handle (`result/e1`) are its entry and data, not its subject, so the task cites none of them, and the page's cited vars are the same set (ctx's `:cited` joins `:seon.task/references` by name, each drawn by ```seon.render.ui/cited```, a source under its own budget so a long one never crowds the tests out) (`seon.task-test/the-writer-cites-the-programs-names-not-the-reproductions`). A name in a namespace the program does not hold yet is not cited until it is. A test the plan names on purpose is its proof (`:seon.task/proofs`), shown with its status, not a cited var.

## The wiki in the store

The wiki's sections are entities on main, so who cites a section or a var is a database query.

```seon.docs/load-tx``` reads the pages it is given with the one parse and makes the db hold one entity per heading of each, leaving every other page as it is, `:seon.section/fact`: its address (the parse's `path#anchor`, so ``docs/flow.md#idioms``), heading, lead, own text (the lines after its heading up to the next heading of any level) and parent. Its `:seon.section/names` are the qualified names its text cites that name something at load (a prose word only when it names something, a backticked name always; ```seon.docs/load-tx``` through `seon.ref/kept`), and its `:seon.section/read` the form id of each such var when the text was written ([health](health.md#a-stale-section)). Its `:seon.section/references` are what its own text cites, resolved on the db: a link, or a cited `path#anchor`, reaches a section (a link with no anchor reaches the page's first section), and a name reaches its var by `:var/name`. A section's backlinks are therefore a query, the sections whose `:seon.section/references` hold it (`seon.docs-test/backlinks-are-a-sections-instances`): a pattern's home knows its instances with no key of its own. A var's home is the backlink citing it at code depth, read from that section's own text by the same parse, so no depth is stored. ```seon.docs/load-dir-tx``` is the one load of `docs/`, and the one that retracts the sections of a page gone from the checkout (md-scan 29's agent loaded one page with load-tx, which then also swept the rest, and its branch lost 556 sections and its system prompt): root's boot writes it in the boot fact's commit (`seon.root/wiki-tx`, [root](root.md#boot)), and `my.root/load-docs!` writes it on demand.

Loading writes only what differs, as task files do (```seon.task/load-tx```): each section's stated attributes are made exactly what its text says by the one `seon.task/entity-tx` (a value main holds that the text dropped is retracted, one it lacks asserted), a section no page holds any more is retracted, and an unchanged wiki answers `[]`. A changed section rewrites only itself, because nothing stored depends on line numbers. A link, or a cited `path#anchor`, that reaches no section does not refuse the load: it is kept on the section that makes it as `:seon.section/dead-links` (the target's address), every other section loads as usual, and while the target is still no stored section it is a derived `:dead-citation` problem naming the page, the section and the target ([health](health.md#a-dead-citation)); adding the target section closes it with nothing written (`seon.docs-test/a-link-to-no-section-is-a-dead-link-and-the-rest-loads`, `seon.root-test/a-dead-link-in-the-wiki-is-a-problem-and-the-boot-goes-on`). A schema key, a file citation and a name that names nothing are not stored as references, since there is no file entity; a name that names nothing stays in `:seon.section/names`, and once it stops naming anything it is a `:dead-citation` ([health](health.md#a-dead-citation)). `seon.root/wiki-tx` takes a `baseline` for sections with no record of the code they were written against (```seon.root/wiki-baseline```, from git).

Cost, measured on a wiki of 8 pages, 60 KB and 60 sections on a test branch: a first load 12.6 ms and 17 MB, an unchanged reload 19 ms and 23 MB, of which the parse is 9 ms and 13 MB. Per section, an unchanged reload costs about 200 KB, most of it the seeks of what main holds (one per stated attribute, `seon.task/entity-tx`) (Datahike seeks on Jolt allocate ~33 KB each, `seon.db/avet-seek-allocates`); the proof is `seon.docs-cost-test/an-unchanged-reload-costs-a-parse-and-a-pull-per-section`. Measured 2026-10-29 on the wiki as it is (37 pages in the two dirs, 567 sections, 0.9 MB), an unchanged load is 217 MB, 92 M ticks and 0.25 s: the parse 54 MB, a seek or two for each of 4,284 citations and 567 sections the rest. It was 1.47 GB, 490 M ticks and 1.25 s, for three causes, each fixed at its source: each dir loaded twice (a link from one dir's page to another's was dead until the second pass; one load of both dirs resolves it at once, `seon.docs/load-dir-tx` over a vector of dirs); a section's names were `seon.ref/kept` over every citation, and a prose `path#anchor` is kept by parsing that file, so every such citation parsed a page (170 extra parses; `seon.docs/section-names` keeps only the names, the only citations it stores); and the reader per span (above). `seon.docs-cost-test/an-unchanged-reload-costs-a-parse-and-a-pull-per-section` has a section name a file's section by its address, which is 1.2 MB a section when a page is parsed for it. Root's boot loads nothing at all when main holds the digest of what the load reads: the pages, the program and the task ids (```seon.root/wiki-digest```, on root's fact as `:seon.root/wiki`; ```seon.root/wiki-boot-tx```). A boot after a change to the program or a page loads again (the load is a function of exactly that input), and ```my.root/load-docs!``` drops the digest, since it writes what the digest does not describe.

## Sections in a task's context

The context shows each wiki section the task's plan or instructions cite, at the depth the citation asks for.

Beside them, the task's data's `:write-set` shows each var the plan cites with its source and its callers (```seon.docs/callers```, the program vars whose recorded definitions name it), and the wiki sections that cite it (```seon.docs/citing-sections```: their addresses, at most `:seon.config.ctx/cited-by`, the decisions page last: the sections the change owes an edit to and the ones that explain it), and `:to-prove` each proof with the form that runs it, or what the plan says it should assert when it is not written (```seon.context/task-data```). Helpers the plan does not name are the agent's to ask for at its REPL (`my.agent/callees`, `my.agent/callers`, `my.agent/similar`): shown to every run, they were mostly unrelated source.

```seon.context/task-data``` keeps the citations that carry a path, a dotted simple symbol (a namespace) and a task id (```seon.ref/references``` over the plan and instructions) and shows each as `:sections`: ```seon.docs/view``` reads the section main holds and ```seon.ref/shown``` renders it, the one rule `seon.ref/view` also uses for a freshly parsed document. A link or one backtick shows the lead (or opening) and the sections below; three backticks show the section whole (its own text); a section main does not hold is read from the checkout as a file reference (below), and shows `:unresolved` beside the same message as an unresolved name when the checkout has none either. Stored sections keep no opening block, so a section whose first block is not a paragraph shows no lead at doc depth, and its sections below come in the order the wiki was written. A link with no anchor (a whole page) shows the page's first section, read from the checkout like a file (main stores no page entity). A prose bare address is a summary, and `seon.ref/references` keeps it only when it names a file, so a bare section address does not reach the context; write the link.

## A section read at a depth, with its edges

Every page and section is on main, reloaded when a page changes, and readable at three depths, each with the sections it cites and those citing it.
- ```seon.ref/shown``` is the one rule for a section at a depth; at :summary it is the heading and the lead's first sentence, and when the lead holds more, `:seon.ref/left` (its characters past that sentence) and `:seon.ref/read-at` (the address that reads it at :doc), so a summary says what it left (`seon.ref-test/a-summary-names-the-citation-that-reads-the-rest`).
- ```seon.docs/view``` shows a section at :summary, :doc or :code, and at every depth its :references (what its text cites, sections and vars) and :cited-by (the sections citing it), each at summary depth, from the stored edges (`seon.docs-test/a-view-at-summary-lists-references-and-cited-by`). ```seon.docs/page``` reads a page at a depth through the same view (`seon.docs-test/a-page-reads-at-a-depth`), and ```my.agent/help``` is that view: the help page at summary, any address at :code, a page's path at summary, and on a miss the nearest addresses (the help page's sections, pages named by a word of it and the sections the search finds for it, ```my.agent/help-nearest```) and the forms that read one, never nil (`seon.repl-test/help-reads-any-address-and-lists-on-a-miss`). A view costs the pulls of its section and its edges, flat in the wiki's size (`seon.docs-cost-test/a-view-costs-its-section-and-its-edges`).
- Every section has a lead, so its summary and its embedding say what it is about; one without is a `:leadless-section` ([health](health.md#a-section-with-no-lead), `seon.docs-test/every-section-of-the-wiki-has-a-lead`).

## Files and namespaces on demand

A file or a namespace the plan cites is read when the context is built and never stored; only Seon's own `docs/` is (above).

A backticked dotted simple symbol (`seon.ref`) is a namespace candidate, resolve-only as v1's rule: ```seon.ref/references``` keeps it when it names a namespace on the db (`:ns/name`) or one loaded, otherwise it stays prose (`seon.ref-test/a-namespace-is-read-as-a-namespace`); its `:seon.ref/name` is the simple symbol. ```seon.ref/namespace-view``` shows it by the one rule `seon.ref/shown`: the docstring is its lead and its definitions, privates included, are the sections below (those of the db; a namespace only this process loaded lists its public names), so summary is the docstring's first sentence and doc adds the definitions.

A cited path that is not a stored section is a file reference: ```seon.ref/file-view``` reads it from the checkout now. A Markdown file goes through `seon.ref/parse` and `seon.ref/view` (the anchor's section, else the first, and at code depth its own text, the lines up to the next heading, as the stored section shows it: `seon.docs-test/one-address-shows-one-text-through-ref-and-docs`); any other file shows its address and line count, and its text whole at code depth. A file under ``reference-code/<project>`` also carries ``:seon.ref/pin``, the revision main's source pins that submodule at: its gitlink (`git ls-files -s`), which root's import records on its `:seon.root/source` fact (`seon.fx/read-source`), never written by the author and never read from git per render. It is not the submodule's checked-out HEAD, which `bin/build` copies. `seon.context/task-data` puts all three kinds, and a task cited by its id (shown by its plan), in `:sections` (`seon.context-test/a-cited-file-is-read-on-demand`); a path with a `:line-reference` is not shown, and one that reaches nothing shows `:unresolved`.

Cost: a cited file is read and parsed on every context build, linear in its size. A task citing `src/seon/ref.clj` (30 KB) at code depth makes a context of about 11,000 tokens, `bin/env` about 430 and one `docs/references.md#cost` section about 480 (printer estimate). Cite a section or a var rather than a whole file.
