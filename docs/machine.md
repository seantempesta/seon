# The machine

The machine Seon is built on and for, and the rules that keep builds, disk and processes bounded. The short form, with the git rules, is [AGENTS.md §8](../AGENTS.md); how a branch merges is [merging](merging.md).

## Seeing what runs

`bin/worktrees` shows everything running across every checkout at once: each worktree's branch and how far it is from main, its root, the processes under it (count, CPU, memory, threads), its stores' size; then seon processes no checkout claims (orphans: a parent of 1, or a checkout that is gone), the heaviest processes on the machine, and its load and free memory. `bin/worktrees -w` repeats it every 5 s.

Native profiling of our own processes needs no root: `sample PID SECS -file F` and `xcrun xctrace record --template 'Time Profiler' --attach PID`. Native frames resolve (liblmdb to `mdb.c` lines through ``target/lib/liblmdb.dylib.dSYM``, and the probe library), while Chez and Jolt code shows as `???`, since its code objects carry no Mach-O symbols; Clojure-level counts and times are `seon.profile`'s. `vmmap` and `vm_stat` need no root, but `vmmap` walks pages and is slow on the store's 64 GiB map; `dtrace`, `fs_usage` and `spindump` need root and SIP is on, so do not plan on them. Root reads it when worktree sessions run in parallel and before a session ends; a worktree session reads it before it reports that nothing of its own is running.

## The target: a 16 GB MacBook M1

Seon is built to run well on a 16 GB MacBook M1: it stays within `:seon.config.machine/memory-mb` (4096: root, the fork server and the default number of agents), and `bin/check scale` fails past it. A cost that grows with something other than the work (a probe walking a 64 GiB address-space reservation took 100 agents from 0.6 s to 18 s) is found by a cost proof sized by what it walks ([storage](storage.md#the-map-is-address-space)). A process's memory is what macOS charges it, its `phys_footprint` (`seon.lib/real-mb`): a forked child is charged every inherited page it touches, though only what it writes is a real copy, and the parent keeps its own charge ([cost](cost.md#how-we-measure)). Like every bound, the key lives in `resources/seon/config/default.edn` ([config](config.md)).

## The clock

Seon has one clock: `seon.profile/now-ns`, the machine's monotonic CLOCK_UPTIME_RAW read by a Chez foreign procedure (9.5 ns a read, nothing allocated, 41 ns resolution), and `seon.profile/ms-since` for "milliseconds since t0". Every process reads the same timeline, so a stamp one process sends (the writer's `:main` commit, a message's `:ns`) is a t0 another can subtract from. The profiler's samples use the same read. `System/nanoTime` (Jolt's, 1 µs and counted from the process's start) and Chez's `current-time` are not used; a new reading of time goes through `seon.profile`. A cost proof measures the calling thread alone ([cost](cost.md)): `seon.profile/cpu-ns`, its CPU time (CLOCK_THREAD_CPUTIME_ID), and `seon.profile/alloc-bytes`, the bytes it allocated (Chez's per-thread count on our branch ``jolt/thread-bytes``), so another thread's work and a scheduler pause are never the measured call's, and neither is a collection's copying in its bytes; a collection that runs on the measured thread is in its time (task `seon.cost/a-proof-measures-only-its-own-thread`). Time is measured and recorded, never acted on ([AGENTS.md §4](../AGENTS.md)); [clocks](clocks.md) names every function that reads it.

## Builds and checks

Builds need a C compiler and make (the Xcode command line tools), git, curl and cmake (llama.cpp's build, `bin/build embed`, [vectors](vector.md#the-model)); nothing else is installed, and every download lands under `target/` (the embedding model once, in the main tree's `target/cache`). Builds run as `nice -n 15 bin/build`, in parallel, with no lock: each worktree builds into its own `target/`, so builds share no mutable state, and a build peaks under ~2 GB. Every process on a store must use the same LMDB build (`target/lib/liblmdb.dylib`, robust locks); stop a store's processes before a build that changes it. Every step decides by its stamp (``target/NAME.stamp``, the pin of the sources it was built from: a submodule's commit, `native/probe.c`'s git hash), never by its output existing, and each step calls the ones it needs: after a sync to a new Jolt pin, `bin/build seon` rebuilds Jolt first (a target/jolt left from the old pin made every root-booting test fail on a var the new source needs), and with no pin moved every step says "up to date". `hello` and `seon` are stamped by the tree (`bin/tree`: HEAD's tree plus every changed and untracked file) and the chez and jolt pins, so an unchanged tree relinks neither (0.6 s, was 32 s) and any edit rebuilds both.

The release binary is the program's: `bin/build seon` runs `jolt build -m seon.main`, so ```seon.main/-main``` serves `bin/root` (its `root` mode, ```seon.main/root-serve```) and `bin/ports` (```seon.main/ports```), and every `bin/check` step loads the check driver (`test/seon/check.clj`, outside src) from the checkout at run time ([checks](checks.md)), and the drivers (`seon.check`, `seon.e2e`, `seon.fixtures`) are in `test/`, outside src and the binary: a root whose provider's config is `:scripted` adds the checkout's source before it starts (```seon.main/checkout-roots!```) and loads its script by name (```seon.model/scripted```); the e2e loop's subject is ```seon.generation/generation```, in src. The drivers have left src (task `seon.main/drivers-leave-src`).

Full checks run niced, each in its own worktree, once per worktree session when its task is done ([AGENTS.md §3](../AGENTS.md)). Iterate with single modes.

A check mode is its body over one harness, `seon.check/run-check`: it boots root, runs the body, prints the body's report and its checks map, stops root, and ends on the one verdict line `NAME OK` or `NAME FAILED` with the exit status to match (`:then :kill` makes the mode phase 1 of a kill/reopen pair). A mode waits only on what the system emits: root's events on a tap taken before their cause (`seon.check/ready!` for spawns and clones, `seon.check/await-agents`, `seon.check/await-event`), or a watch on a reference (`seon.check/await-ref`, `seon.root/await-db`). An agent's records are applied ahead of its commit (`seon.agent/transact!`), so a mode reads them from its branch at the agent's `:commit` events (`seon.check/await-records`), never right after the eval answered: `mcp-proof` read too early under load. Where a mode meant "the thing happened", the producer that knows says so: an agent's eval began (`:started`, sent by `seon.repl/agent-step`, awaited (`seon.check/started`) before a kill, an interrupt or a pause arrives; several awaited at once by `seon.check/await-each`, since awaiting one at a time drops the others' events), its test child forked (`:tests-started` with the child's pid, `seon.agent/run-tests-forked`), a declared proc took a message (`seon.check/probe-proc` on root's events), a tab's view is current (the render proc has nothing in flight: ``: settled``, an SSE comment on the feed, `seon.web`), the fork server has applied main's commits and its answers have passed through (`seon.check/fork-server-caught-up`: a `{:op :stats}` behind them on its in-order socket, its `:t` checked against main's); a Flow pause needs no wait at all (a proc's control channel is FIFO, so the next ping reads it). It never polls and has no deadline, so what it waits for must be a fact on its way. The time left is named in [clocks](clocks.md): measurement windows (`:seon.config.check/hold-ms`, `:seon.config.check/pages-ms`, idle's window) and a ping's bound, past which a proc is recorded `:blocked` (`seon.check/ping`). An outside client a mode drives reads its stdin from a file, so its EOF cannot hang on a pipe end held elsewhere (`mcp-proof`).

## What a process owns in memory

An idle agent owns about 120 MB, a test child of it about 10 MB, root about 2.9 GB and the fork server about 0.5 GB, and because macOS charges a forked child only the pages it writes (`phys_footprint`, `seon.lib/real-mb`), the footprints add up to the machine's real use: root 2,854 MB + fork server 544 MB + standby 33 MB + one agent 122 MB = 3.55 GB (`footprint -p`, a root on a fresh store).
- **An agent's 120 MB is start-up garbage, not inherited pages.** A standby that runs nothing is 33 MB and an idle test child 9.7 MB, so opening the store, receiving the reach graph and the index, and the first evals write about 90 MB; the agent's non-static live data is only 5.8 MB (generations 0-1). A diff of `vmmap -v` against the standby shows 98 MB of dirty pages spread thin over 816 mostly 2 MB regions: free heap pages the start-up filled. After `System/gc` the live non-static data falls to 3.7 MB and the footprint stays at 134 MB, because Chez keeps freed pages (`current-memory-bytes` 1,151 MB against `bytes-allocated` 1,064 MB). `ps` rss undercounts a forked child (pages not touched are not mapped), so an "idle agent rss of 618 MB" was the fork server's.
- **An agent allocates 2 MB to be ready; its pages are written far past what it allocates.** Measured per spawn phase 2026-10-29 (`seon.agent/spawn-phases` bytes, footprint at each mark, a collection count of 51 throughout the start-up, so no collection ran): from the fork to the hello an agent allocates 2.1 MB (`d/connect` 1.1 MB, `make-ns!` 0.06 MB, the first state 0.45 MB) and its footprint grows from 15 MB to 55 MB: `make-ns!` +8 MB, `d/connect` +17 MB, `begin-run!` +10 MB. The first request's reply adds 13 MB more for 2 MB allocated. `vmmap -v` before and after shows those pages in 70-170 of the 2 MB heap regions, a few at a time, in the boot image's regions as well as the free ones: writes scattered over inherited objects, a 16 KB page each on Apple silicon, not garbage the start-up allocated. Contracts and their counters are not the cause (`:seon.config.contract/instrument :off` gives the same curve), and an agent forked from an agent that has run an eval pays the same first eval again. The one allocation that was real: an agent's first commit hashed Seon's whole schema (100 KB printed) because Datahike kept the last schema key only by hashing (`datahike.writing/last-schema-meta`), empty in a process that only opened a db: 31.5 MB allocated once, the second commit 1.8 KB. `stored->db` now seeds that key from the store (our fork, `jolt/stored-db-knows-its-schema-key`, `datahike.test.schema-key-seed-test`), for every process that opens a db, and an agent's bytes from its state mark to its first request fell from 38.5 MB to 6.5 MB (`seon.agent-test/an-agent-allocates-little-from-ready-to-its-first-request`); its footprint did not fall (78.7 MB at the first request against 80.2, within the 10 MB spread between roots), because the pages the garbage touched are reused by the allocation that follows.
- **A collection does not privatize inherited pages.** Everything inherited is in the static generation (an agent's `(bytes-allocated 'static)` reads 1,008 MB with generations 0-4 holding 1.3 + 4.5 MB at start), because ```seon.fork-server/server-step``` makes the heap static (`seon.lib/static!`) before a fork when it is due (```seon.fork-server/static-due?```: main's program moved, or what an agent would inherit outside static, live after a collection, passed `:seon.config.agent/inherited-bytes`, 16 MiB), and a collection traces only what is outside static. An agent that allocated 486 MB and kept 23 MB grew 134 to 161 MB, and its test child's `System/gc` cost 61 MB, the agent's own 56 MB of non-static data copied plus 5.
- **The fork server's static grew with every fork; it grows only with main's live data now.** It is 1,008.2 MB in one agent and 1,009.75 MB in the next, 269 MB above root's 740 MB, because the reach graph, the reconciler index and the commits since boot were frozen at every fork, and the superseded versions never leave static (about 1.1 MB a fork: 22.6 MB over 20 forks). Freezing only when due, what forks replace is freed by an ordinary collection first, and the server freezes once per ~16 MB of main's live growth: 1 freeze in 20 forks, measured 2026-10-28 (`seon.agent-test/a-fork-servers-static-grows-only-with-the-program`). Only the fork server's death frees them.
- **The agent's heap cap bounds growth, not memory.** ```seon.lib/heap-cap!``` sets `JOLT_MAX_HEAP` to `(bytes-allocated)` (static included) plus `:seon.config.agent/heap-extra-bytes` (1 GiB), so static cancels and an agent may privately grow 1 GiB; a collection runs when the total passes max(0.75 of the ceiling, live + a quarter of the room) and raises only if the total is still over afterwards, so garbage never trips it and a burst can overshoot by up to the trip. `heap-cap!` also sets `:seon.config.agent/trip-bytes` (4 MiB) as Jolt's nursery floor (`JOLT_NEW_SIZE`), because Jolt's adaptive nursery raises any trip set directly back to its 16 MiB floor (an agent read 16,777,216 before; `seon.agent-test/an-agents-collect-trip-is-the-configured-one`). A test child forked from an agent sets its own ceiling from its own heap at its fork, so a grown agent's child keeps the full allowance (`seon.agent-test/a-test-childs-ceiling-is-its-own`). One setting still undoes the small-pages intent: the heap-reserve ratio is fitted to bytes including static (0.505 measured), so Chez may keep free pages up to about half the inherited heap (about 530 MB, estimated; 87 MB seen).

### Root's heap

An idle root is its boot image, its program and the node cache, and nothing else: on a resumed scratch store it is 1,106 MB footprint (static 934 MB, live outside static 132 MB, 99 MB of free pages kept), and its fork server 381 MB. It was 1,438 MB and 438 MB before jolt/root-memory moved the preload and returned free pages (the same store, the same second boot).
- **The boot image is about three times its file**: bare Jolt's static is 69.7 MB, `target/hello` (Jolt and Datahike, a 120 MB file) peaks at 386 MB footprint, and `./seon ports`, which opens no store, peaks at 731 MB footprint and 967 MB rss: 740 MB of root's static is the image. `bin/build` passes no size flags, and a type split needs `enable-object-counts` before the boot-time static collect (not done).
- **Root does not preload main.** The fork server reads every node of main's indexes once, after its fork, through its own store (`seon.fork-server/main`, `seon.db/preload!`), so the agents it forks inherit them decoded and never read the store at a spawn. Root preloaded them before forking it and froze them into static at boot, where they stayed for its life though its cache had evicted them within minutes: about 300 MB of root's static, 104 MB on the scratch store.
- **Root returns its free pages.** Chez keeps, after a full collection, free memory up to its reserve ratio of the non-static heap in use and returns the rest. Jolt's collector policy sets that ratio after every collection, fitted to the room under the heap ceiling and capped by `JOLT_MAX_HEAP_FREE_RATIO` (the JVM's `-XX:MaxHeapFreeRatio`, P% free = P/(100-P) of the heap in use; Jolt's default 50 keeps 1x). Root sets it to `:seon.config.root/max-heap-free-ratio` (10, a ratio of 0.11) through ```seon.lib/max-heap-free-ratio!``` once the fork server is forked, so the fork server and agents keep the default (it also bounds a nursery's headroom over the live set by the same share, 1/9 of it, which an allocating agent would feel; not measured there). The boot's static collect, before it, leaves almost nothing outside static to keep free. Chez returns pages only in a full collection, and root makes one at boot (the static collect) and at each quiescence: the writer's `:collect`, which the reconciler asks for once per quiet spell, collects root's heap in full after the store. No clock: a root that never goes quiet keeps its pages until it does. A ratio set on Chez directly did not hold: the policy refitted it to 1.0 at root's next collection.
- **The node cache is bounded by what its nodes retain.** `:seon.config.store/node-cache-bytes` (128 MiB) is weighed per node by `datahike.index.node-cache/node-bytes` (our Datahike fork): a Datom at 80 bytes, a string at 4 bytes a character, a byte array at its length, a symbol read from the store at its own record and name (Jolt does not intern them; `:form/refs`, 35% of datoms, carries one per ref), a branch's child addresses. That alone left the bound at half: **a branch kept every child it restored** (`node-child` stored it in `_children`), so a cached branch, and the roots a db value holds, retained whole subtrees the cache had evicted. A cache weighing 372 KB held 12.7 MB through the db's roots (34x), and a root's weighed 125.7 MB and retained 204-226 MB (pvec 97 MB, vector 63 MB, strings 39 MB: the evicted leaves' keys, the datoms themselves 3 MB). persistent-sorted-set's Jolt port now takes the ref type Datahike already passes (`:weak` when it caches nodes by their bytes) and keeps no restored child under it, so the cache is the one holder of nodes read back and a branch retains its keys and addresses. Counted through the static generation (`compute-size` stops at it by default, and the boot image froze 57% of a root's nodes into it, which made the first recount read 69 MB), a root that had read all of main weighed 134.2 MB and retained 127.6 MB, and a test's store read through a cache a third of its size weighs within 10% of what it retains (`datahike.test.node-cache-weight-test/a-cache-weighs-what-the-nodes-it-holds-retain`: 372 KB weighed against 12.7 MB retained before, within 10% now).
  - **A hit costs a seek one more branch lookup, not a map update.** A branch that keeps no child reaches it through the cache at every step of a seek. Recency by a persistent-map update on each hit took a seek from 3.7 to 7.3 us (30,000-entity file store, 9,000 seeks, two runs each); the cache is now a clock (a hit sets the entry's flag and allocates nothing, an eviction gives a flagged oldest entry a second chance) and a seek takes 4.5-5.2 us.
  - **Sizing, measured 2026-10-29** on a scratch root of main at 200,744 datoms (540,000 index entries): at boot the root reads every node of main (7,400 reads, 16,500 nodes, 136 MB weighed under a 1 GiB bound, no evictions) and the next three minutes add 1.6 nodes and 200 hits a second to an idle root (a reader that should be asked what it polls). The 128 MiB bound holds 94% of that. A root's hot set is main's index size, about 0.7 KB weighed a datom, so the bound is main's size, not a constant: it holds while main is under about 190,000 datoms. The fork server reads main once for the agents it forks (`seon.db/preload!`) and an agent inherits that cache and adds what it reads; an agent's own reads are not measured, and the one key serves them all.
- **A held db value costs what its version does not share.** The cache is shared by every db value of a store, so a proc holding main's db adds about 6 MB at idle (its tree's nodes outside the cache), not the cache it reaches; a stale version pins the nodes later transactions rewrote. So main's commit notice from the writer (`seon.writer/main-commit`) is `{:t :prev :ops :commit :ns}`, a reference, never a db: a notice queued behind a slow reader (the reconciler's blocking buffer, the vectors proc's kept latest) is plain data, and each consumer (the reconciler, the test service, the vectors and render procs, through their `:conn` argument) makes the db with `seon.db/at-commit` when it takes the notice (the conn's own head when the notice is its head, else `d/commit-as-db`) and lets it go when the next replaces it, as the fork server does. A group commit is one stored commit and one notice (`:prev` is main's t before it: the reader's next-commit test). The vectors proc's `:clean`, `:latest` and `:embedded` ask are `{:t :commit}` too: a round makes the base db from `:clean`, diffs, and lets both go ([vector](vector.md#what-is-embedded)).

Measured with read-only evals over a scratch root's own store, `footprint -p`, `(bytes-allocated 'static)`, `current-memory-bytes` and a walk that counts each reachable object once; the type split of the static generation and about 200 MB of malloc outside Chez are not attributed.

### Ten agents at once

Ten agents working at once cost root, the fork server and about 140 MB each: `bin/check swarm 10 10` (scripted agents, a scratch store, 2026-10-29) peaked at 2,415 MB with all ten live (root 845 MB, fork server 124 MB, standby 31 MB, agents 138-144 MB each), and `bin/check scale 10` reports about 97 MB an agent. On the standing store root is about 1.1 GB with the model out of it (it was 1.7 GB with the model loaded; the model now runs in a helper process, 350-550 MB, only while embedding work is queued: [vector](vector.md#the-model)) and the fork server 670 MB, so ten light agents there are about 4.1 GB. Agents running their tests were not measured, and each may grow 1 GiB (`:seon.config.agent/heap-extra-bytes`). The target is an ordinary MacBook: root idle at or under 650 MB, the fork server under 300 MB, ten working agents under 3 GB ([plan](plan.md)).

## Processes

Anything that can make threads or processes starts at n ≤ 100 under `nice -n 15`. Watch `ps -M -p PID | wc -l`, and kill your own process past 200 threads. One experiment at a time.

A process that must outlive your tool call is double-forked, which `bin/root` does. The tool host kills a background task's whole process tree when the task stops or its agent exits.

Leave nothing running when you finish, and say so in your report. Kill only PIDs you started; never `pkill` or `killall`. Delete only paths you created.

## Disk stays bounded

Disk stays bounded by these rules, and by everyone cleaning up garbage when they see it, whoever left it: a merged worktree, a leftover process or a finished experiment's output is removed on sight, after checking nothing live uses it (by PID, path and working directory, never by pattern; a worktree is live when a session works in it or any config names it, as the main tree's `config/local.edn` names `.worktrees/merges`, its merges' write-back tree, whose branch is always merged), and what went is said (AGENTS §8, the machine). The rules:
- a worktree session's worktree is removed in the merge that merges it (`bin/worktree --remove NAME`, run by root after the merge; the branch stays in git); one found merged and clean later is removed then (`bin/worktree --remove-at DIR`), unless a live session works in it;
- a worktree session's scratch lives inside its worktree (`target/`, `runs/`) and goes with it; nobody creates a new top-level directory in the root or beside it: the main tree's `test-results/` (the old results files, which nothing reads now: the owner's to remove), `target/results` (the verdict cache every checkout shares: [merging](merging.md#verdicts-are-a-cache)) and `config/worktree-ports` (the worktrees' port blocks; `bin/ports`) are gitignored, and the worktrees are `.worktrees/NAME` inside the root, gitignored (`bin/worktree --path NAME`);
- what is kept is what git and the store record (commits, task facts, notes); a store holds its history. Until Seon holds a user's data, the standing store (`runs/store`) is test data: when its schema changes it is erased on the owner's go, never migrated. Build output, compile caches and finished experiments' stores are regenerable and are deleted when their checkout or experiment ends;
- `target/prove/<run-id>` is removed by the run that wrote it when it ends green (a plain `bin/prove` or `bin/test`). A red or killed run's directory, a `--merge` run's and one `--out` names are kept, and nothing bounds them since `prune-runs!` was deleted: a red run's logs are the evidence of its defect, kept until that defect is fixed, and then removed by whoever fixed it (`rm -rf` the directory its first line names, after checking nothing live reads it); a `--merge` run's are removed with its merge, and an `--out` directory by its caller;
- no code prunes ``target/check/`` (each run's logs) or a root's old generations (each a tree and a binary, ~200 MB): deleting them is a manual act, keeping the generation running and the one before it.

Your scratch: under your worktree (`target/`, `runs/`) or a folder named for your worktree. The session scratch folder is shared.

## Secrets and paid runs

Secrets are never printed. Check the context before any paid model call. Paid runs spend from the owner's standing budget ($50), on productive work only, and root may start them without asking while it stays inside it; past it, they need the owner's go ([model](model.md#paid-runs)). Install nothing system-wide. Never write in `~/src/seon`.
