# The machine

The machine Seon is built on and for, and the rules that keep builds, disk and processes bounded. The short form, with the git rules, is [AGENTS.md §8](../AGENTS.md); how a branch merges is [merging](merging.md).

## Seeing what runs

`bin/worktrees` shows everything running across every checkout at once: each worktree's branch and how far it is from main, its root, the processes under it (count, CPU, memory, threads), its stores' size; then seon processes no checkout claims (orphans: a parent of 1, or a checkout that is gone), the heaviest processes on the machine, and its load and free memory. `bin/worktrees -w` repeats it every 5 s.

Native profiling of our own processes needs no root: `sample PID SECS -file F` and `xcrun xctrace record --template 'Time Profiler' --attach PID`. Native frames resolve (liblmdb to `mdb.c` lines through ``target/lib/liblmdb.dylib.dSYM``, and the probe library), while Chez and Jolt code shows as `???`, since its code objects carry no Mach-O symbols; Clojure-level counts and times are `seon.profile`'s. `vmmap` and `vm_stat` need no root, but `vmmap` walks pages and is slow on the store's 64 GiB map; `dtrace`, `fs_usage` and `spindump` need root and SIP is on, so do not plan on them. Root reads it when worktree sessions run in parallel and before a session ends; a worktree session reads it before it reports that nothing of its own is running.

## The target: a 16 GB MacBook M1

Seon is built to run well on a 16 GB MacBook M1: it stays within `:seon.config.machine/memory-mb` (4096: root, the fork server and the default number of agents), and `bin/check scale` fails past it. A cost that grows with something other than the work (a probe walking a 64 GiB address-space reservation took 100 agents from 0.6 s to 18 s) is found by a cost proof sized by what it walks ([storage](storage.md#the-map-is-address-space)). A process's memory is what macOS charges it, its `phys_footprint` (`seon.lib/real-mb`): a forked child is charged every inherited page it touches, though only what it writes is a real copy, and the parent keeps its own charge, so `bin/check scale` charges each agent the machine's drop in free plus inactive memory (`seon.lib/sysmem`, `host_statistics64`) and root and the fork server their footprints, never the sum of the agents' footprints ([cost](cost.md#how-we-measure)). Like every bound, the key lives in `resources/seon/config/default.edn` ([config](config.md)).

## The clock

Seon has one clock: `seon.profile/now-ns`, the machine's monotonic CLOCK_UPTIME_RAW read by a Chez foreign procedure (9.5 ns a read, nothing allocated, 41 ns resolution), and `seon.profile/ms-since` for "milliseconds since t0". Every process reads the same timeline, so a stamp one process sends (the writer's `:main` commit, a message's `:ns`) is a t0 another can subtract from. The profiler's samples use the same read. `System/nanoTime` (Jolt's, 1 µs and counted from the process's start) and Chez's `current-time` are not used; a new reading of time goes through `seon.profile`. A cost proof measures the calling thread alone ([cost](cost.md)): `seon.profile/cpu-ns`, its CPU time (CLOCK_THREAD_CPUTIME_ID), and `seon.profile/alloc-bytes`, the bytes it allocated (Chez's per-thread count on our branch ``jolt/thread-bytes``), so another thread's work and a scheduler pause are never the measured call's, and neither is a collection's copying in its bytes; a collection that runs on the measured thread is in its time (task `seon.cost/a-proof-measures-only-its-own-thread`). Time is measured and recorded, never acted on ([AGENTS.md §4](../AGENTS.md)); [clocks](clocks.md) names every function that reads it.

## Builds and checks

Builds need a C compiler and make (the Xcode command line tools), git, curl and cmake (llama.cpp's build, `bin/build embed`, [vectors](vector.md#the-model)); nothing else is installed, and every download lands under `target/` (the embedding model once, in the main tree's `target/cache`). Builds run as `nice -n 15 bin/build`, in parallel, with no lock: each worktree builds into its own `target/`, so builds share no mutable state, and a build peaks under ~2 GB. Every process on a store must use the same LMDB build (`target/lib/liblmdb.dylib`, robust locks); stop a store's processes before a build that changes it. Every step decides by its stamp (``target/NAME.stamp``, the pin of the sources it was built from: a submodule's commit, `native/probe.c`'s git hash), never by its output existing, and each step calls the ones it needs: after a sync to a new Jolt pin, `bin/build seon` rebuilds Jolt first (a target/jolt left from the old pin made every root-booting test fail on a var the new source needs), and with no pin moved every step says "up to date". `hello` and `seon` are stamped by the tree (`bin/tree`: HEAD's tree plus every changed and untracked file) and the chez and jolt pins, so an unchanged tree relinks neither (0.6 s, was 32 s) and any edit rebuilds both.

The release binary is the program's: `bin/build seon` runs `jolt build -m seon.main`, so ```seon.main/-main``` serves `bin/root` (its `root` mode, ```seon.main/root-serve```) and `bin/ports` (```seon.main/ports```), and every `bin/check` step loads the check driver (`test/seon/check.clj`, outside src) from the checkout at run time ([checks](checks.md)), and the drivers (`seon.check`, `seon.e2e`, `seon.fixtures`) are in `test/`, outside src and the binary: a root whose provider's config is `:scripted` adds the checkout's source before it starts (```seon.main/checkout-roots!```) and loads its script by name (```seon.model/scripted```); the e2e loop's subject is ```seon.generation/generation```, in src. The drivers have left src (task `seon.main/drivers-leave-src`).

Full checks run niced, each in its own worktree, once per worktree session when its task is done ([AGENTS.md §3](../AGENTS.md)). Iterate with single modes.

A check mode is its body over one harness, `seon.check/run-check`: it boots root, runs the body, prints the body's report and its checks map, stops root, and ends on the one verdict line `NAME OK` or `NAME FAILED` with the exit status to match (`:then :kill` makes the mode phase 1 of a kill/reopen pair). A mode waits only on what the system emits: root's events on a tap taken before their cause (`seon.check/ready!` for spawns and clones, `seon.check/await-agents`, `seon.check/await-event`), or a watch on a reference (`seon.check/await-ref`, `seon.root/await-db`). An agent's records are applied ahead of its commit (`seon.agent/transact!`), so a mode reads them from its branch at the agent's `:commit` events (`seon.check/await-records`), never right after the eval answered: `mcp-proof` read too early under load. Where a mode meant "the thing happened", the producer that knows says so: an agent's eval began (`:started`, sent by `seon.repl/agent-step`, awaited (`seon.check/started`) before a kill, an interrupt or a pause arrives; several awaited at once by `seon.check/await-each`, since awaiting one at a time drops the others' events), its test child forked (`:tests-started` with the child's pid, `seon.agent/run-tests-forked`), a declared proc took a message (`seon.check/probe-proc` on root's events), a tab's view is current (the render proc has nothing in flight: ``: settled``, an SSE comment on the feed, `seon.web`), the fork server has applied main's commits and its answers have passed through (`seon.check/fork-server-caught-up`: a `{:op :stats}` behind them on its in-order socket, its `:t` checked against main's); a Flow pause needs no wait at all (a proc's control channel is FIFO, so the next ping reads it). It never polls and has no deadline, so what it waits for must be a fact on its way. The time left is named in [clocks](clocks.md): measurement windows (`:seon.config.check/hold-ms`, `:seon.config.check/pages-ms`, idle's window) and a ping's bound, past which a proc is recorded `:blocked` (`seon.check/ping`). An outside client a mode drives reads its stdin from a file, so its EOF cannot hang on a pipe end held elsewhere (`mcp-proof`).

## What a process owns in memory

Measured 2026-10-29 by `bin/check scale` (100 agents): root 649 MB and the fork server 133 MB by footprint, and each agent 20.6 MB of real memory (the machine's drop in free plus inactive), so root, the fork server and ten agents come to about 1 GB against the ~4 GB budget. An earlier reading on a fresh store's first root (below) was larger. A forked child's footprint (`phys_footprint`, `seon.lib/real-mb`) counts every inherited page it touches, so the footprints of root and the fork server (they hold their own pages) are the machine's real use and the agents' are an upper bound (their drop in free plus inactive memory is the real cost, 20.6 MB an agent across 100): root 2,854 MB + fork server 544 MB + standby 33 MB + one agent 122 MB = 3.55 GB (`footprint -p`, a root on a fresh store).
- **An agent's 120 MB is start-up garbage, not inherited pages.** A standby that runs nothing is 33 MB and an idle test child 9.7 MB, so opening the store, receiving the reach graph and the index, and the first evals write about 90 MB; the agent's non-static live data is only 5.8 MB (generations 0-1). A diff of `vmmap -v` against the standby shows 98 MB of dirty pages spread thin over 816 mostly 2 MB regions: free heap pages the start-up filled. After `System/gc` the live non-static data falls to 3.7 MB and the footprint stays at 134 MB, because Chez keeps freed pages (`current-memory-bytes` 1,151 MB against `bytes-allocated` 1,064 MB). `ps` rss undercounts a forked child (pages not touched are not mapped), so an "idle agent rss of 618 MB" was the fork server's.
- **An agent allocates 2 MB to be ready; its pages are written far past what it allocates.** Measured per spawn phase 2026-10-29 (`seon.agent/spawn-phases` bytes, footprint at each mark, a collection count of 51 throughout the start-up, so no collection ran): from the fork to the hello an agent allocates 2.1 MB (`d/connect` 1.1 MB, `make-ns!` 0.06 MB, the first state 0.45 MB) and its footprint grows from 15 MB to 55 MB: `make-ns!` +8 MB, `d/connect` +17 MB, `begin-run!` +10 MB. The first request's reply adds 13 MB more for 2 MB allocated. `vmmap -v` before and after shows those pages in 70-170 of the 2 MB heap regions, a few at a time, in the boot image's regions as well as the free ones: writes scattered over inherited objects, a 16 KB page each on Apple silicon, not garbage the start-up allocated. Contracts and their counters are not the cause (`:seon.config.contract/instrument :off` gives the same curve), and an agent forked from an agent that has run an eval pays the same first eval again. The one allocation that was real: an agent's first commit hashed Seon's whole schema (100 KB printed) because Datahike kept the last schema key only by hashing (`datahike.writing/last-schema-meta`), empty in a process that only opened a db: 31.5 MB allocated once, the second commit 1.8 KB. `stored->db` now seeds that key from the store (our fork, `jolt/stored-db-knows-its-schema-key`, `datahike.test.schema-key-seed-test`), for every process that opens a db, and an agent's bytes from its state mark to its first request fell from 38.5 MB to 6.5 MB ([an agent's first write](#an-agents-first-write) has what it costs now); its footprint did not fall (78.7 MB at the first request against 80.2, within the 10 MB spread between roots), because the pages the garbage touched are reused by the allocation that follows.
- **A collection does not privatize inherited pages.** Everything inherited is in the static generation (an agent's `(bytes-allocated 'static)` reads 1,008 MB with generations 0-4 holding 1.3 + 4.5 MB at start), because ```seon.fork-server/server-step``` makes the heap static (`seon.lib/static!`) before a fork when it is due (```seon.fork-server/static-due?```: main's program moved, or what an agent would inherit outside static, live after a collection, passed `:seon.config.agent/inherited-bytes`, 16 MiB), and a collection traces only what is outside static. An agent that allocated 486 MB and kept 23 MB grew 134 to 161 MB, and its test child's `System/gc` cost 61 MB, the agent's own 56 MB of non-static data copied plus 5.
- **The fork server's static grew with every fork; it grows only with main's live data now.** It is 1,008.2 MB in one agent and 1,009.75 MB in the next, 269 MB above root's 740 MB, because the reach graph, the reconciler index and the commits since boot were frozen at every fork, and the superseded versions never leave static (about 1.1 MB a fork: 22.6 MB over 20 forks). Freezing only when due, what forks replace is freed by an ordinary collection first, and the server freezes once per ~16 MB of main's live growth: 1 freeze in 20 forks, measured 2026-10-28 (`seon.agent-test/a-fork-servers-static-grows-only-with-the-program`). Only the fork server's death frees them.
- **The agent's heap cap bounds growth, not memory.** ```seon.lib/heap-cap!``` sets `JOLT_MAX_HEAP` to `(bytes-allocated)` (static included) plus `:seon.config.agent/heap-extra-bytes` (1 GiB), so static cancels and an agent may privately grow 1 GiB; a collection runs when the total passes max(0.75 of the ceiling, live + a quarter of the room) and raises only if the total is still over afterwards, so garbage never trips it and a burst can overshoot by up to the trip. `heap-cap!` also sets `:seon.config.agent/trip-bytes` (4 MiB) as Jolt's pinned nursery (`JOLT_GC_TRIP_BYTES`, which turns the adaptive nursery off), because the adaptive nursery rewrote any trip once a collection had run (8-17 MB seen with the floor `JOLT_NEW_SIZE` set; `seon.agent-test/an-agents-collect-trip-is-the-configured-one`). A test child forked from an agent sets its own ceiling from its own heap at its fork, so a grown agent's child keeps the full allowance (`seon.agent-test/a-test-childs-ceiling-is-its-own`). One setting still undoes the small-pages intent: the heap-reserve ratio is fitted to bytes including static (0.505 measured), so Chez may keep free pages up to about half the inherited heap (about 530 MB, estimated; 87 MB seen).

### How to read an out-of-memory error

An `OutOfMemoryError` from Jolt's heap ceiling says what holds the memory, as data, the way the JVM's `HeapDumpOnOutOfMemoryError` leaves a dump: its `ex-data` is `{:jolt/heap {:live :static :dynamic :ceiling :top [{:type :count :bytes :gens} ...]}}`. `:top` is the 20 types holding the most collectable bytes, descending, `:type` a Chez type name (`bytevector`, `pair`, `string`, a record type by its record name), `:gens` the generation-to-bytes split; `:static` is the boot image (never freed, never the leak) and `:dynamic` the counted collectable total. The error map of an eval keeps it as `:jolt/heap` (```seon.agent/error-map```), so an agent's report carries it, never the Throwable. Read it by the first entries: one type holding most of `:dynamic` is the culprit (a vector of strings is `string` and `vector`/`pvec`; a held db is its index nodes). `(jolt.host/heap-histogram 20)` answers the same shape at any REPL and forces one full collection with Chez's per-type counts on, so it costs a full collection (`jolt/an-out-of-memory-says-what-holds-it`: measured in the commit). The ceiling's error takes one more in-place full collection with the counts on, only when it is about to raise; a collection that does not raise pays nothing. The GC overhead limit's `OutOfMemoryError` carries no histogram.

### Root's heap

An idle root is its boot image, its program and the node cache, and nothing else: on a resumed scratch store it is 1,106 MB footprint (static 934 MB, live outside static 132 MB, 99 MB of free pages kept), and its fork server 381 MB. A fork server's footprint counts the pages it shares with root copy-on-write, which are in RAM once: on main 3348c59cee its footprint was 625 MB, of which 577 MB were root's pages (`vmmap -wide`, SM=COW) and 48 MB its own (SM=PRV), 2026-10-30. Read a forked process's own cost from its SM=PRV pages or the machine's available-memory drop (`seon.lib/sysmem`), never its footprint. It was 1,438 MB and 438 MB before jolt/root-memory moved the preload and returned free pages (the same store, the same second boot).
- **The boot image is about three times its file**: bare Jolt's static is 69.7 MB, `target/hello` (Jolt and Datahike, a 120 MB file) peaks at 386 MB footprint, and `./seon ports`, which opens no store, peaks at 731 MB footprint and 967 MB rss: 740 MB of root's static is the image. `bin/build` passes no size flags, and a type split needs `enable-object-counts` before the boot-time static collect (not done).
- **The image keeps no inspector expressions and no frame variable names.** `bin/build` strips each release unit with our Chez's `inspector-expressions` (a procedure's expanded source, -210 MB per root) and `inspector-variables` (each code-info's `live` vector, each return point's live mask, and the return points with no source object; a frame loses its variable names only, and its name and file:line are unchanged). Measured 2026-10-29 on one tree, before and after the second option: `target/seon` 112.1 -> 79.7 MB, `./seon ports` peak footprint 454.9 -> 349.8 MB, an idle scratch root's static generation 519.7 -> 420.6 MB (footprint 681.5 -> 613.6 MB), the root of `bin/check e2e calc` 617 -> 518 MB; the fork server and every agent inherit the cut. The eval errors compared (a seon fn, a library fn, `ex-triage`'s line and symbol, `.getStackTrace` strings) are identical. Task seon.main/the-image-keeps-no-inspector-information.
- **A namespace's init is data in the image, not code.** Each namespace's init (`jolt-app-init$ns$N!`) runs once at boot and stays in the static image; its code was 47% of the image's code (1,319 chunks, 52.6 MB, ~108 MB with its return points), mostly one call and its inspector data apiece for every call-site registration (70,944), every keyword, var cell, seed root and call-site cache cell (about 170,000) and every constructor of a constant collection literal (var metadata and `:malli/schema` vectors). Jolt (`jolt/init-emits-data-not-code`) now emits a def's registrations as one quoted table (`jolt-register-callsites!`), a constant collection literal as one quoted datum read back with the same constructors (`jolt-datum`), and a def's keywords, var cells, seed roots and cache cells as one call over a table (`jolt-consts`); and `seon.contract/checked` is `:redef`, so the wrapper (`wrap`, `schema`, `seon.profile/counted`) is called from each contracted definition instead of spliced into it 1,500 times. Measured 2026-10-29 on one tree (13,300 vars), `./seon ports` peak footprint (store-free, three runs within 0.1 MB): 349.9 MB before; each change alone: call-site tables 336.9 (-12.9), constant literals as data 325.6 (-24.3), constants tables 320.0 (-30.0), `checked` not inlined 335.8 (-14.1); all together 282.6 (-67.3). `target/seon` 79.9 -> 63.9 MB, `./seon ports` 0.24 -> 0.21 s, an idle scratch root's static generation 374.7 -> 308.8 MB, the root of `bin/check e2e calc` 527.2 -> 461.9 MB (`root-real-mb`). Every var's metadata (13,300 compared, key order included) and the eval errors compared (the same cases as above) are identical. The Jolt gates (the ten, `traceemit`, `emittedheads`, `selfhost`) pass. Not done: the remaining `jolt-symbol` constants, `jolt-register-source!` calls and per-site `jolt-site!` stores, and the rest of the inspector data (return points' source objects), which the second cut under "keeps no inspector expressions" left.
- **Root evaluates no test code.** `test/` is imported as facts and its namespaces are loaded by the fork server, which every agent inherits; root's boot and writer pass `{:tests? false}` to `seon.program/load-all!` and `load-changes!`. A resumed scratch root's live heap outside static is 264 MB, against 406 MB with the 1,822 test forms evaluated (-142 MB; footprint 901 against 1,023 MB): [source](source.md#a-process-holds-the-tests-only-when-it-runs-them).
- **Root does not preload main.** The fork server reads every node of main's indexes once, after its fork, through its own store (`seon.fork-server/main`, `seon.db/preload!`), so the agents it forks inherit them decoded and never read the store at a spawn. Root preloaded them before forking it and froze them into static at boot, where they stayed for its life though its cache had evicted them within minutes: about 300 MB of root's static, 104 MB on the scratch store.
- **Root returns its free pages.** Chez keeps, after a full collection, free memory up to its reserve ratio of the non-static heap in use and returns the rest. Jolt's collector policy sets that ratio after every collection, fitted to the room under the heap ceiling and capped by `JOLT_MAX_HEAP_FREE_RATIO` (the JVM's `-XX:MaxHeapFreeRatio`, P% free = P/(100-P) of the heap in use; Jolt's default 50 keeps 1x). Root sets it to `:seon.config.root/max-heap-free-ratio` (10, a ratio of 0.11) through ```seon.lib/max-heap-free-ratio!``` once the fork server is forked, so the fork server and agents keep the default (it also bounds a nursery's headroom over the live set by the same share, 1/9 of it, which an allocating agent would feel; not measured there). The boot's static collect, before it, leaves almost nothing outside static to keep free. Chez returns pages only in a full collection, and root makes one at boot (the static collect) and at each quiescence: the writer's `:collect`, which the reconciler asks for once per quiet spell, collects root's heap in full after the store. No clock: a root that never goes quiet keeps its pages until it does. A ratio set on Chez directly did not hold: the policy refitted it to 1.0 at root's next collection.
- **The node cache is bounded by what its nodes retain.** `:seon.config.store/node-cache-bytes` (128 MiB) is weighed per node by `datahike.index.node-cache/node-bytes` (our Datahike fork): a Datom at 80 bytes, a string at 4 bytes a character, a byte array at its length, a symbol read from the store at its own record and name (Jolt does not intern them; `:form/refs`, 35% of datoms, carries one per ref), a branch's child addresses. That alone left the bound at half: **a branch kept every child it restored** (`node-child` stored it in `_children`), so a cached branch, and the roots a db value holds, retained whole subtrees the cache had evicted. A cache weighing 372 KB held 12.7 MB through the db's roots (34x), and a root's weighed 125.7 MB and retained 204-226 MB (pvec 97 MB, vector 63 MB, strings 39 MB: the evicted leaves' keys, the datoms themselves 3 MB). persistent-sorted-set's Jolt port now takes the ref type Datahike already passes (`:weak` when it caches nodes by their bytes) and keeps no restored child under it, so the cache is the one holder of nodes read back and a branch retains its keys and addresses. Counted through the static generation (`compute-size` stops at it by default, and the boot image froze 57% of a root's nodes into it, which made the first recount read 69 MB), a root that had read all of main weighed 134.2 MB and retained 127.6 MB, and a test's store read through a cache a third of its size weighs within 10% of what it retains (`datahike.test.node-cache-weight-test/a-cache-weighs-what-the-nodes-it-holds-retain`: 372 KB weighed against 12.7 MB retained before, within 10% now).
  - **A hit costs a seek one more branch lookup, not a map update.** A branch that keeps no child reaches it through the cache at every step of a seek. Recency by a persistent-map update on each hit took a seek from 3.7 to 7.3 us (30,000-entity file store, 9,000 seeks, two runs each); the cache is now a clock (a hit sets the entry's flag and allocates nothing, an eviction gives a flagged oldest entry a second chance) and a seek takes 4.5-5.2 us.
  - **Sizing, measured 2026-10-29** on a scratch root of main at 200,744 datoms (540,000 index entries): at boot the root reads every node of main (7,400 reads, 16,500 nodes, 136 MB weighed under a 1 GiB bound, no evictions) and the next three minutes add 1.6 nodes and 200 hits a second to an idle root (a reader that should be asked what it polls). The 128 MiB bound holds 94% of that. A root's hot set is main's index size, about 0.7 KB weighed a datom, so the bound is main's size, not a constant: it holds while main is under about 190,000 datoms. The fork server reads main once for the agents it forks (`seon.db/preload!`) and an agent inherits that cache and adds what it reads; an agent's own reads are not measured, and the one key serves them all.
- **A held db value costs what its version does not share.** The cache is shared by every db value of a store, so a proc holding main's db adds about 6 MB at idle (its tree's nodes outside the cache), not the cache it reaches; a stale version pins the nodes later transactions rewrote. So main's commit notice from the writer (`seon.writer/main-commit`) is `{:t :prev :ops :commit :ns}`, a reference, never a db: a notice queued behind a slow reader (the reconciler's blocking buffer, the vectors proc's kept latest) is plain data, and each consumer (the reconciler, the test service, the vectors and render procs, through their `:conn` argument) makes the db with `seon.db/at-commit` when it takes the notice (the conn's own head when the notice is its head, else `d/commit-as-db`) and lets it go when the next replaces it, as the fork server does. A group commit is one stored commit and one notice (`:prev` is main's t before it: the reader's next-commit test). The vectors proc's `:clean`, `:latest` and `:embedded` ask are `{:t :commit}` too: a round makes the base db from `:clean`, diffs, and lets both go ([vector](vector.md#what-is-embedded)).
- **A kept older db is a point, and the guard reads every proc's state for one.** The branch's current db is free to hold (its conn holds it); an older one pins its own version of the index. So what a process derives from an older db is a cache keyed by `seon.db/point` (`[commit-id max-tx]`) and the db is made again with `seon.db/at-commit` or `d/commit-as-db` when it must be read: the agent's `:base-graph`, `:branch-graph` and `:branch-changes` (they held the db each was made for until the next ask, so after a commit or a merge of main they pinned the previous one), and the fork server's main index (`{:commit :index}`, brought to main at a fork or a standby: it held the db it was listed at through every commit between forks; an agent is handed `{:db :index}` by `seon.fork-server/index-for-agent`, main's current). Root's render proc kept `:branch-reads b` for every branch a page ever showed (a db each, for root's life); `drop-view` and a late answer now let it go when no view shows the branch. Measured 2026-10-29 on a scratch store after 30 commits of 400 notes: stale db values held, fork server 1 to 0, agent caches 2 to 0 (the extra bytes a stale handle pinned were 0.01 MB: the nodes it reached were all in the node cache, 31 MB of 128 MiB, so the count is the guard and the bytes appear when the cache is churning). Kept as values on purpose: the reconciler's `:db`, the fork server's `:db`, the render proc's `:main-db` and `:root-walk :at` (each is main's current, replaced by the next commit), the render's per-view branch read (the branch as last read, replaced when it moves), the agent's `:db` and `:tx` (`commit!` drops `:tx`), and the agent's `:base` and `:main` (the merge base and main as last heard, read as dbs by `seon.turn`, `seon.render.ui` and `my.branch`: a follow-up when those readers take a commit). The guard: `seon.procs-test/no-proc-keeps-a-db-older-than-its-branchs-current` and `seon.agent-test/an-agent-keeps-no-db-older-than-its-branchs-current` run commits through the fork server, the reconciler, the render proc and an agent, then walk the state as data (`seon.test-store/stale-dbs`) and fail naming the proc and key path of any db older than its branch's current; `seon.render-test/a-dropped-page-lets-go-of-its-branchs-db` is the render proc's. A db inside a closure, and the writer's union (`seon.union`, a history db that grows with the store), are not walked: the union is a design question, not changed here.
- **A view keeps handles, not values.** Root's view of an agent keeps each of its last `:seon.config.root/view-window` evals as `seon.root/eval-head`: the handle (the form that reads the value, on the agent), the printed head (`:text`, the printer's own cut), the cost and, for an error, its type and message; never the response's `:value`, `:out`, `:err` or an error's `:data`, which the agent's record holds. Before, `:evals-add` pushed the response whole (measured 2026-10-29: 20 MB for one agent's probe evals); now the entry's bytes do not depend on what the evals returned (`seon.procs-test/root-view-of-an-agents-evals-holds-handles-not-values`: identical printed size at 10 and 100,000 elements, red before). No src reader read the entries' other keys. The REPL's `*e` is held the same way: `seon.repl/error-kept` keeps a new exception carrying the error map (`seon.agent/error-map`) with the original's message and no cause, so `ex-message`, `ex-data` and `pst` read it and the thrown exception's frames are let go (`seon.repl-test`). Not changed: `*1 *2 *3` still hold their values, as at any REPL; and `:root-errors` entries merge an error's `:data` only as `seon.contract/bounded` keeps it (the one root-kept site; an agent's own errors and an asker's replies carry full data; [errors](errors.md#an-error-keeps-data)).

Measured with read-only evals over a scratch root's own store, `footprint -p`, `(bytes-allocated 'static)`, `current-memory-bytes` and a walk that counts each reachable object once; the type split of the static generation and about 200 MB of malloc outside Chez are not attributed.

### An agent's first write

**What an agent's start reads of main, the fork server reads first, once, so an agent's start costs the same however long its root has run.** An agent inherits the fork server's decoded index nodes, and a read the server never made is made cold in every agent it forks (an agent's reads stay in its own process, so they never warm the server, nor mark its nodes used). Three such reads grew with a root's history (measured 2026-11-01, 40 agents in turn in one shared test root, each agent's bytes from its `:state` mark to its first request: 11-13 MB at the first, 15-21 MB from the 25th):
- **the leaves main's commits wrote:** the writer holds what it wrote in memory, so those leaves are cold in the server, and an agent whose first reads land on one decodes it (about 300 KB a leaf; `begin-run!`'s cache misses went 2 to 14 over 12 agents);
- **the leaves every agent reads, evicted:** the server's node cache is full (`:seon.config.store/node-cache-bytes`, 134 MB), and a leaf the server does not read again ages out of it, so every agent decoded the sections it cites (a section's pull 40-70 KB warm, 0.5-1 MB cold) and the schema entries ```seon.program/schema-changes``` scans (1.1 MB warm, 3.8 MB cold).

```seon.fork-server/warm-start``` makes the start's reads itself before each fork, for the agent it forks: its first write (```seon.agent/begin-run-tx```, the agent's own, on its task, run and key, then its cites) applied with `d/with`, its record built on that (```seon.ctx/build```), and once per move of main the schema changes; the agent inherits those leaves decoded, and the server's reads keep them in its cache. It reads only what that agent reads: reading every leaf each commit wrote instead (tried first) grew the server's heap past `:seon.config.agent/inherited-bytes` so often that it froze 6 times in 20 forks, keeping 113 MB more in static (`seon.agent-test/a-fork-servers-static-grows-only-with-the-program`), since a freeze keeps the cache's nodes for the server's life;
- **every eval main records:** ```seon.repl/eval-n!``` read every `:seon.eval/id` on the branch to number its evals, linear in all the evals main ever recorded (8.6 KB at the first agent, 377 KB at the 40th). The server keeps main's highest (```seon.fork-server/evals-max-after```, from each commit's ops) and hands it to each agent at its fork; a resumed branch reads its own once.

After them the same 40 agents read 13.3 MB at the first and 13.8-14.5 MB from the 10th on: the 7-10 misses left are leaves an agent's first write reaches that the server holds none of, a steady state. The baseline is a cost proof: `seon.agent-test/an-agents-start-costs-the-same-however-long-its-root-has-run` grows main by the history of 10, 100 and 1,000 agents between agents (a small node cache, so a full one is reached) and judges their bytes as constant at the measured :fixed (6.0 MB: 5.86 at the root's start, 6.04, 5.96, 5.88 MB; on the code before, 9.7, 10.8, 12.2, 12.7 MB). An eval no longer reads the schema entries to learn nothing changed: ```seon.repl/branch-registry``` (up to three calls an eval: wrap-registry, instrument, the page walk) answers the registry the agent holds, main's from its fork, until a write moves a `:schema/` datom (```seon.agent/schema-moved```, in `transact!` and the merge of main), where each call read all 748 entries (1.08 MB) before (`seon.agent-test/an-eval-reads-the-schema-entries-only-after-one-moved`; two trivial evals 9.26 MB apart before, 7.07 after). What the baseline holds, to lower next: each eval's commit (```seon.agent/commit!```, 2.7 MB to commit a record of a few datoms: the paths it rewrote in every index, current and history), `begin-run!`'s two transactions (0.9 MB, most of it writing the nodes they changed) and its record's build (`seon.ctx/own`'s 12 pulls, 0.7 MB).

### An agent keeps every result

An agent keeps every eval's whole response (value included) for its process's life, in its state's `:results` and as the var `result/e<n>`, so `result/e3` and `(my.agent/$ :e3)` always read it (owner, 2026-10-29: "do not put any artificial limits or cuts on agents context or evals"). An agent's memory is its process's: no window evicts a result. 100 evals returning 1 MB each hold 100 MB, in its own process. What other processes keep of an agent's results is a reference: root's view keeps handles (above, in [root's heap](#roots-heap): a view keeps handles, not values). The same pass that tried a window kept: the agent's page walk keeps no db at all, taking the datoms its db moved by since it last drew (`seon.ctx/take-moved!`), and an eval's reply carries the error as data from the moment it is made (`seon.repl/error-data`), never the Throwable ([errors](errors.md#an-error-keeps-data)).

### What a spawn costs

`bin/check spawn-phases N` (`seon.check/spawn-phases`) spawns N agents at once, twice, on a scratch main holding Seon's own program (2,616 forms, an import of 155,987 datoms), and prints each agent's phases (`seon.agent/spawn-phases`). Measured 2026-10-29, load 3:

| | 1 agent, first | 10 agents, first wave | 10 agents, second wave (main unmoved) |
|---|---|---|---|
| request to the fork server taking the fork (`fork-server-in`) | 9,438 ms | 10,335-10,349 ms | 0.02 ms (all ten ready in 172 ms) |
| graph brought to main (`reach-graph`, once, the first fork) | 1,377 ms | 1,385 ms | 0 |
| index, freeze (`index`, `static`) | 9 + 88 ms | 9 + 83 ms | 0 + 0.1 ms |
| the agent's own start (`child-init` to `hello`) | 15 ms | 12-20 ms each | 12-20 ms each |

A spawn on an unmoved main costs the agent's own start, about 17 ms, and the fork server forks ten one after another without queueing behind any heavy work (the second wave's ten were ready within 172 ms of the request). The 9-10 s of the first wave is not a spawn's: it is the fork server loading the program the writer committed (`seon.program/load-changes!` of the import, 9.6 s for 2,616 forms, timed in the server's loop), which the first fork waits behind because commits and forks arrive on one FIFO pipe (an agent forked after commit k sees exactly k). With 25 s between the import and the first spawn the first wave took 1.7 s (the graph's 1.4 s and the freeze). So a spawn pays per main move: the load of the forms that move changed (1.6-5 ms a form) and the graph's update at the next fork (20-45 ms for a merge's forms, 1.4 s for the whole program), never per fork.

### What a turn costs

One scripted agent turn (task `swarm/s1`'s kind, green, one code call, on a root whose binary is built from its own tree, `--profile scripted`, a scratch store of Seon's own program: 1,140 tests, 3,967 forms) was measured 2026-10-29 as the agent's one work eval (its `:seon.eval/fns`, `form-top-fns` 300) and root's whole-process allocation (Chez `sstats-bytes`) from the release to quiescence. Before: the agent 1,003 MB and 206 M ticks, root 2,957 MB. After (one render proc change, one verdict-read change): the agent 914 MB and 170 M ticks (two other turns 728 MB, 138 M and 758 MB, 145 M: a turn varies by about 15%), root 674 MB (two more 596 and 702 MB).

- **Root printed its own context on every pass, for nobody.** The render proc's quiet pass (a main commit or an event, no tab open, 0 patches) printed root's context and, with it, read main's health (`seon.problems/health-moved`, 17 to 22 times a turn, about 157 MB): about 1.7 GB of the 2.96 GB, as `seon.render/resolved` and `placed-hiccup`. Now both are derived data read when a reader is there: ```seon.render.proc/with-context``` (the print, kept by the walk's value and main's t) for a tab on `/root/debug` or a `:context` request, and ```seon.render.proc/health!``` (kept with the point it was read at, `seon.db/point`, and brought to main by the datoms between that commit and this one) for any tab, waiting page or `:context`. A quiet pass costs p50 0.24 ms (it was 19-33 ms). Root's page and `/context.txt` show the same tiles as before.
- **The plan read every verdict file.** `seon.agent/test-plan` asks for each test's verdict at its digest; each green was slurped and parsed (41 KB and 11 K ticks a file, for a verdict that is a file's existence). Now ```seon.fx/stored-results``` checks existence ([merging](merging.md#verdicts-are-a-cache)): 76.8 MB and 25.1 M ticks to 2.1 MB and 0.8 M ticks.
- **`seon.sock/recv!` is not a cost.** Its 190 to 270 MB in the agent's work eval is the allocation of the agent's other fibers while the intake fiber's `recv!` is parked on the socket (one thread, the profile counts a call's bytes over its whole span, a parked wait included). A fresh agent's frame buffer is 4 KB, and it grows only to the largest frame the agent receives (`seon.sock/conn`); the profile's per-call bytes are not a cost where fibers share a thread.
- **An agent's first-turn index is main's, handed with the graph.** `seon.program/graph-index` was 104 MB and 16.3 M ticks (19.2 M and 136 MB on 4,713 forms and 1,138 tests measured again 2026-10-29, `seon.lib/digest` 29 MB of it) in every agent's first turn: the fork server handed the graph, and an agent made the index over it. The graph now holds its tests' index (```seon.program/reach-indexed```, [source](source.md#tests-run-by-reach)), moved with main by the fork server (```seon.fork-server/graph-at-fork```), so an agent whose base is main at its fork finds it made (2.2k ticks, 1.2 KB), and one whose base is older recomputes only the tests the update left stale (```seon.agent/base-graph```). A merge that changes a schema entry no longer rebuilds the graph either (154M ticks and 892 MB, now 47M and 271 MB). What is left of it is a change to what most tests reach. The turn's other named cost: `seon.agent/transact!`, `commit!`, `seon.program/live-ids`, `seon.stage/stage-tx` and `seon.merge/content-datoms` are 12 to 20 MB each, once a turn.

The import and the wiki are the two phases that grow with the program, and a main made from `:db` repeated both for every root. `seon.root/seed-program!` (`bin/root seed STORE`, which `bin/test` runs once after it builds the binary, on the process store its plan made, `seon.test-store/process-store`) brings `:db` up to the tree: the wiki, the program and the `:seon.root/source` fact with the tree's digest, the wiki loaded again until it states nothing more (once the program exists its citations resolve to it, and a root's second boot reached that by itself). ## Processes

Anything that can make threads or processes starts at n ≤ 100 under `nice -n 15`. Watch `ps -M -p PID | wc -l`, and kill your own process past 200 threads. One experiment at a time.

A process that must outlive your tool call is double-forked, which `bin/root` does. The tool host kills a background task's whole process tree when the task stops or its agent exits.

Leave nothing running when you finish, and say so in your report. Kill only PIDs you started; never `pkill` or `killall`. Delete only paths you created.

## Disk stays bounded

Disk stays bounded by these rules, and by everyone cleaning up garbage when they see it, whoever left it: a merged worktree, a leftover process or a finished experiment's output is removed on sight, after checking nothing live uses it (by PID, path and working directory, never by pattern; a worktree is live when a session works in it or any config names it, as the main tree's `config/local.edn` names `.worktrees/merges`, its merges' write-back tree, whose branch is always merged), and what went is said (AGENTS §8, the machine). The rules:
- a worktree session's worktree is removed in the merge that merges it (`bin/worktree --remove NAME`, run by root after the merge; the branch stays in git); one found merged and clean later is removed then (`bin/worktree --remove-at DIR`), unless a live session works in it;
- a worktree session's scratch lives inside its worktree (`target/`, `runs/`) and goes with it; nobody creates a new top-level directory in the root or beside it: the main tree's `test-results/` (the old results files, which nothing reads now: the owner's to remove), `target/results` (the verdict cache every checkout shares: [merging](merging.md#verdicts-are-a-cache)) and `config/worktree-ports` (the worktrees' port blocks; `bin/ports`) are gitignored, and the worktrees are `.worktrees/NAME` inside the root, gitignored (`bin/worktree --path NAME`);
- what is kept is what git and the store record (commits, task facts, notes); a store holds its history. Until Seon holds a user's data, the standing store (`runs/store`) is test data: when its schema changes it is erased on the owner's go, never migrated. Build output, compile caches and finished experiments' stores are regenerable and are deleted when their checkout or experiment ends;
- `target/prove/<run-id>` is removed by the run that wrote it when it ends green (a plain `bin/prove` or `bin/test`). A red or killed run's directory, a `--merge` run's and one `--out` names are kept, and nothing bounds them since `prune-runs!` was deleted: a red run's logs are the evidence of its defect, kept until that defect is fixed, and then removed by whoever fixed it (`rm -rf` the directory its first line names, after checking nothing live reads it); a `--merge` run's are removed with its merge, and an `--out` directory by its caller;
- no code prunes ``target/check/`` (each run's logs) or a root's old generations (each a tree and a binary, ~200 MB): deleting them is a manual act, keeping the generation running and the one before it.

Your scratch: under your worktree (`target/`, `runs/`) or a folder named for your worktree. The session scratch folder is shared.

## Secrets and paid runs

Secrets are never printed. Check the context before any paid model call. Paid runs spend from the owner's standing budget ($50), on productive work only, and root may start them without asking while it stays inside it; past it, they need the owner's go ([model](model.md#paid-runs)). Install nothing system-wide. Never write in `~/src/seon`.
