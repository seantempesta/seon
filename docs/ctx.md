# ctx: the agent's record as one map

An agent reads its own record with `@ctx`: one map of its agent entity pulled by a pattern (its runs with their task, the vars the task cites, turns and messages, and its evals), with `:t`, `:branch` and `:commit` beside them (``seon.ctx/ctx``). It is a plain Clojure atom, kept current as the agent works, so a read is a deref and nothing is built for it. The design, the measurements and the owner's rulings behind it are in `notes/design-ctx-atom-2026-10-25.md`; the task is `seon.ctx/the-record-is-an-atom`.

## The pattern

The map is the agent's entity pulled by a pattern: Datahike's pull syntax, held as data (``seon.render/pattern`` reads it, for the walk and for the page's units alike). An entity schema declares its record's pattern in its `:seon.ctx/pattern` property (the agent's, a run's, a task's, a var's, root's), and an agent edits its own by `swap!`ing `:seon.ctx/pattern` on ctx: the edit is an attribute of its entity, written as any `swap!` is, and the record is built again by it (``seon.ctx/pattern-of``). Nothing else says what ctx holds.
- `'*` is the entity's own attributes, every one it holds: a cardinality-many one as a set, a [plain value](storage.md#plain-values) as itself (a vector keeps its order).
- `{attr sub}` joins: `sub` is a pattern, or an entity schema's name, its declared pattern. A join's key is its `:as` (`:evals`, `:runs`, a run's `:task`, `:turns` and `:messages`), else its attribute. A collection (a reverse ref, a cardinality-many attribute) is a map of its members by their ids, sorted greatest first: for ids issued in time order (evals, turns) newest first; a member keeps its own name in its value (`:seon.eval/id`, `:var/name`), which the printer shows beside the id where a person or the model reads a path (root's ruling, 2026-10-26); a ref attribute's value gives way to its members, a looked-up attribute's symbols stay beside them.
- A window, `:limit n :reverse true`, holds the newest n. Members whose ids are issued in time order (evals, turns) are read newest first by [our Datahike's `:reverse`](forks.md#datahike), which stops at n; members whose ids derive from their content (runs, messages, forms) are read whole and the newest n kept by the transaction that wrote each ref (their map is ordered by id, as every collection is; a render that wants them in time order sorts by first-t). A limit may name a config key (``:seon.config.ctx/window``, ``:seon.config.ctx/callers``): no limit is a literal. A `:limit` takes `:reverse true`: a window is the newest n, never the oldest. A patch moves a window of time-ordered ids by its transaction's datoms (``seon.ctx/window-moves``): the member that joined assoc'd, the one that left dissoc'd, the oldest past the limit dropped, the window read again only to fill it from below its oldest when one left.
- `:by` joins by name, **ctx's one option beside Datahike's pull syntax** (everything else is pull's own, `:reverse` our Datahike's): forward, each symbol a lookup ref (`{[:seon.task/references :by :var/name :as :cited] […]}`: the vars a plan cites, a symbol naming none joins nothing until it is defined); reverse, the entities whose attribute holds this one's name (`{[:form/_refs :by :var/name :as :callers …] […]}`: a var's callers). The references stay the author's symbols; the lookup is a pure function of stored data.
- Every entity is held once, at the first path the walk reaches it by (the pattern's order, a window's newest member first); every other path holds `{:db/id e}`. So the task a session's runs share is held under its newest run.

The page's walk reads the same declaration: ``seon.render/units`` is a schema pattern's joins ([render](render.md)).

## Kept by the change, never rebuilt

``seon.ctx/build`` walks the pattern once, when the agent's state first holds its db (a spawn, a resume, a clone), and ``seon.ctx/patch`` keeps it from each transaction's datoms, which ``seon.agent/transact!`` records with the db they made. The walk's state (`:ix`) knows where each entity is held, its pattern, and which `[attribute value]` each join watches (a reverse join's ref to it, a lookup's name). A datom touches a held entity (its own attributes, a forward join) or a watched join; the patch rebuilds each touched entity where it is held, shortest path first, as a build would, keeping every join and member nothing touched, and copies the path above it. A rebuild that changes nothing keeps the old node. A move with no transaction (a merge of main, a resume) is patched from the datoms the two values differ by. A change of the pattern, or one that moves where an entity is held (a new run reaching the task, the holder leaving its window), builds the record anew, as a fresh build places it, and shares back every subtree it did not change (the same objects): that patch costs the record, once a run.

A patch costs its change, flat in the session (at 100 and 1,000 evals): a new eval 25 contracted calls and 159 KB, its window moved by an assoc and a dissoc and flat in the window's size too (`seon.ctx-test/the-patch-costs-the-change-not-the-session`, `seon.ctx-test/a-window-moves-by-its-change`; 815 KB while the window was read again and its map rebuilt); a cited var redefined 23 calls and 118 KB, a new caller 22 and 113 KB, a plan edit 10 and 86 KB (`seon.ctx-test/a-lookups-patch-costs-its-change`). A content-id window (a var's callers) is read whole and ordered: a new caller of a var named by n forms costs those n datoms read and sorted (`seon.ctx-test/a-callers-window-costs-its-forms`). After each of 150 random changes of a session's kinds (evals, runs, turns, messages, a cited var redefined, a caller added, a var defined or gone, a reference added or dropped, the agent's pattern edited), the patched record, its map, its state and every collection's order, equals a fresh build; every path no change reached is the same object (``seon.ctx/changes``, the one diff, reads what moved) (`seon.ctx-test/ctx-is-the-record-after-every-transaction`). The atom lives as long as the agent's process, across the runs of its session.

**What changed, and what did not.** A patch answers `:changed`, the paths its transaction changed: an attribute's, or a member's that joined or left. It changes only along those paths. So every value at a path not at, under or above one of them is the same object it was (`identical?`), and a part's memo is a pointer test. The same property test holds this after each of the 150 changes. The environment (`:t`, `:branch`, `:commit`) is the root map's, new each transaction and no path of `:changed`, so nothing caches on the root map. A build answers `:changed #{[]}`, the root path: every value is new, and a memo misses once, everywhere. The test counts the paths it checked (over 1,000 in 150 changes), so a patch that reported everything changed could not pass it.

**What changed over a turn is data.** ``seon.ctx/diff`` answers what changed of the record from a turn's start to its end, in the record's own shape: `{path [old new]}`, old nil for a member that joined, new nil for one that went. It is pure in the record at the two t's. ``seon.ctx/advance`` patches the start's record by the datoms the start and end db values differ by (the net change of the turn's transactions, read from the db alone), so its `:changed` bounds where they are compared. A path equal at both ends is dropped (a change undone within the turn), and so is one under another the diff holds. The start's record with the diff applied is the end's, and the advanced record equals a build at the end t (`seon.ctx-test/a-turns-diff-is-what-changed-between-its-ts`, twelve turns of random changes). `diff` costs its changed paths, never the record: one contracted call for an eval added, at 100, 1,000 and 3,000 evals (`a-turns-diff-costs-its-changed-paths-not-the-record`); `advance` costs the patch of the net datoms. A patch applies every entity's retractions before any assertion, so a member retracted and made again under its key within a turn comes out as the end's.

**ctx is the db's data, nothing derived.** (owner, 2026-10-26: "no we don't store derived data in the db or the ctx atom".) What a view needs beyond the pull is a render over the db, memoized by what it read, never a member of ctx. The conversation's order is each entry's first transaction, ``seon.context/first-t`` (one seek; it never changes, so a view memoizes it by entity).

**Any entity, any branch.** ``seon.ctx/build`` takes an entity id: an agent's (its `@ctx`), root's, the user's, a task's, a run's. ``seon.ctx/follow`` patches a record from one of the writer's commits as main's readers receive them (`{:t :ops :db}`), as an agent's follows its own transactions. A run or task retracted leaves its environment alone, as a build of no entity does (`seon.ctx-test/any-entitys-record-follows-mains-commits`, 60 commits, two records).

**The task's part and related are renders.** The task's part is ``seon.render.ui/task-page``, a function of the task as ctx holds it and the db as of t (``seon.context/task-data`` over them, without its write set: each cited var is a part of its own, ``seon.render.ui/cited`` over ``seon.context/cited``), with ``seon.context/task-key`` its memo key: the accumulated plan, instructions and proofs, and the newest transaction of each entity the task's data reads beside its cited vars (each proof's var, each cited section); a cited var's own key is ``seon.context/cited-key``, its var, its form and the forms that name it. Equal keys, an equal part (`seon.context-test/the-task-key-moves-with-what-it-reads`, `seon.context-test/a-cited-var-redefined-shows-in-the-next-view`). Not read: what task-data reads beside the db (a cited file's text on disk, a namespace's meta in the process). Related is ``seon.context/related`` over the plan's vectors, with ``seon.context/related-key`` its memo key (the task's key, its cited vars' keys, the count, and the newest vector by one seek of the indexed `:seon.vector/text-t`). A view reads the db only through these (``seon.context/renders``). The request reads the page as it was at each turn's commit (`seon.context-test/the-prefix-stays-byte-identical-across-turns`).

The other facts a view reads:
- A catch-up (``seon.agent/merge-main!``) is a `:seon.catch-up/*` entity written in the merge's own transaction: the branch and t merged, what applied and what conflicted. It is the agent's join `:catch-ups` (`seon.agent-test/after-merge-main-the-agent-judges-against-the-new-base`).
- Proof results and the done rule's reasons are each turn's `:seon.turn/basis` `:observed`, already in ctx under `[:runs id :turns tid]`. A message the turn takes is written on the branch (``seon.turn``'s `take!`) and sits under `[:runs id :messages]`.

## What the model reads, and what the page draws

`@ctx`'s value carries `{:seon.render/schema :seon.ctx/ctx}` as metadata. ``:seon.ctx/ctx`` declares a page render, ``seon.render.ui/ctx``, and none for the model, so the model reads `@ctx` as it reads any value, through the one printer, cut where it is large with the form that reads the rest. The page draws the same eval as a block: a row per key, each value by the render its key's own schema declares (``seon.render/render`` with the key as its schema), else the printer's structure.

An eval of `@ctx` is recorded as its basis, never as a copy: the value's metadata names it (`:seon.render/basis`, the branch and t it is the record of), and ``seon.repl/record-details`` keeps `{:schema :basis}` and the text the model read (a session of 3,000 evals has a 3.9 MB record, which a copy would store again at every `@ctx`). The page renders what exists: ``seon.render.ui/evaluation`` rebuilds the map from the agent's branch as of t (``seon.ctx/build``) and draws it.

A key whose schema the branch registered or changed is drawn by the agent, since its render may be defined only there and root cannot call it. ``seon.render.ui/ctx`` shows that key's structure, naming its render, and notes what it wants drawn; the render proc asks the agent for it while the page is viewed (``seon.render.proc/comp-entry``, an `{:op :render}` request through root's api to the agent, answered by ``seon.repl/agent-step`` under the branch's schemas, recording nothing), holds the answer, and renders the component again with it. An agent that is gone answers nothing, and its key keeps its structure, saying so, until the agent runs again or its render merges to main and root calls it. Nothing of the block is stored, so the model never reads HTML.

## Adding a datum and its render

An agent adds to its record, and to what it sees of it, with four evals (`seon.ctx-test/an-agent-adds-a-datum-and-its-render`):

```clojure
(my.schema/register! :lab.ctx/steps '[:vector {:seon.render/html lab.ui/steps} :string])
(ns lab.ui) (defn steps "The plan's steps, numbered." {:malli/schema [:=> [:cat [:vector :string] :map] :any]} [v _] [:ol (for [s v] [:li s])]) (in-ns 'agent.a1)
(my.db/transact! [{:seon.agent/key (:seon.agent/key @ctx) :lab.ctx/steps ["read the plan" "write the test"]}])
@ctx
```

A registered key is an attribute at once when no entity map lists it (``my.schema/registration`` carries its declaration). The next `@ctx` holds it, and its block draws it by `lab.ui/steps`, drawn by the agent, unmerged. A class a render names is styled only if the page's stylesheet was built with it.

## Changing it: swap!

An agent changes its record as it changes any atom: `(swap! ctx assoc :lab.ctx/steps [...])`, `(swap! ctx update :evals dissoc 1753)`, `(swap! ctx assoc-in [:runs id :seon.run/status] :done)`. The atom's validator (``seon.ctx/write!``) turns the change into one transaction on the branch: each attribute set or retracted (a cardinality-many one member by member), each join's member new (with its own joins, naming its parent by the join's ref and keyed by its identity), gone (retracted whole) or changed; a member a lookup (`:by`) holds follows the attribute it reads, and one held at another path is changed there. Every value is checked by its schema, the platform's or one the branch registered; a dry run (`d/with`) checks the db would hold what the swap! says at each path it writes; then it is applied (``seon.agent/transact!``), and when the swap! ends the record is the db's (its new entities with their ids). Finding the change costs the change: a unit identical to its old self is skipped by one `identical?` (`seon.ctx-test/a-write-costs-its-change-not-the-record`: one attribute of the agent's entity, 5 contracted calls and 2,709 ticks at 100 and at 1,000 evals); a unit that differs is walked member by member, each identical member skipped the same way. The write itself adds one `d/with` and the patch of its datoms, which costs the change (the patch's own proof); `write!` as a whole is not measured.

Refused, nothing written, with the error that says why (`seon.ctx-test/a-swap-writes-the-record`):
- ``:seon.ctx/invalid``: a key with no schema (register it, a qualified keyword), or a value its schema refuses, each with its path and why;
- ``:seon.ctx/not-held``: the db would not hold what the swap! says;
- ``:seon.ctx/basis``: the map's `:t`, `:branch` or `:commit` is not the record's: the swap!'s function wrote the db (it is refused once, never retried, which closes the livelock a retrying swap! would be), or wrote the environment; or it is no map (a `reset!`).

The record's environment is read-only; everything else is writable, and history keeps what a write retracts.

**The page is the agent's to change.** The page is render-ctx, the render :seon.render/render-ctx declares (```seon.render/render-ctx```, the layout), composed of keyed sub-renders, each declared on its schema; an agent overrides the layout or any sub-render by registering its own render on its branch, and its model reads the same output (```seon.repl/page```).

## Provenance: who made each fact

Who made a fact is a query on the tx-meta of its transaction, Datomic's reified transactions. Every transaction Seon makes names its branch (`:seon.tx/branch`, ``seon.db/tx-meta``). An agent's write during an eval also names that eval (`:seon.tx/eval`, its `:seon.eval/id`, "e5"): ``seon.repl/eval-string`` holds the running eval's id on the agent's state while its forms run, and ``seon.agent/transact!`` writes it, so a `swap!`, any `transact!` its code makes, and the eval's own record all name it. A catch-up (``seon.agent/merge-main!``) also names the branch it merged (`:seon.tx/merged`), so a fact main made reads as main's after the agent caught up, though the agent's branch wrote the merge.

``seon.ctx/made-by`` answers it for one attribute of one entity: the tx-meta of its newest datom's transaction, by two seeks (`(seon.ctx/made-by (my.db/db) (:db/id @ctx) :lab.ctx/steps)`). The page's ctx block shows it beside each attribute, as of the eval's t: the eval that wrote it, else "from :main" for a fact the agent was forked holding, and "merged from :main" for one a catch-up brought (`seon.ctx-test/a-change-names-its-eval`; the tx-meta itself, `seon.agent-test/an-agents-transactions-name-their-runtime` and `after-merge-main-the-agent-judges-against-the-new-base`).

Not covered: root's own writes (``seon.root``'s transactions on main) name no eval; a join's members show no provenance on the block (each eval is its own record); a removed member is not shown as removed.
