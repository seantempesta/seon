# ctx: the agent's record as one map

An agent reads its own record with `@ctx`: one map of its agent entity pulled by a pattern (its task with the vars it cites, its turns, its evals and its messages), with `:t`, `:branch` and `:commit` beside them (``seon.ctx/ctx``). It is a plain Clojure atom, kept current as the agent works, so a read is a deref and nothing is built for it. The design, the measurements and the owner's rulings behind it are in `docs/ctx.md`; the task is `seon.ctx/the-record-is-an-atom`.

## The pattern

The map is the agent's entity pulled by a pattern: Datahike's pull syntax, held as data (``seon.render/pattern`` reads it, for the walk and for the page's units alike). An entity schema declares its record's pattern in its `:seon.ctx/pattern` property (the agent's, a task's, a var's, root's), and an agent edits its own by `swap!`ing `:seon.ctx/pattern` on ctx: the edit is an attribute of its entity, written as any `swap!` is, and the record is built again by it (``seon.ctx/pattern-of``). Nothing else says what ctx holds.
- `'*` is the entity's own attributes, every one it holds: a cardinality-many one as a set, a [plain value](storage.md#plain-values) as itself (a vector keeps its order).
- `{attr sub}` joins: `sub` is a pattern, or an entity schema's name, its declared pattern. A join's key is its `:as` (`:evals`, `:calls`, `:messages`, the agent's `:task`), else its attribute. A collection (a reverse ref, a cardinality-many attribute) is a map of its members by their ids, sorted greatest first: for ids issued in time order (evals, model calls) newest first; a member keeps its own name in its value (`:seon.eval/id`, `:var/name`), which the printer shows beside the id where a person or the model reads a path (root's ruling, 2026-10-26); a ref attribute's value gives way to its members, a looked-up attribute's symbols stay beside them.
- A window, `:limit n :reverse true`, holds the newest n. Members whose ids are issued in time order (evals, model calls) are read newest first by [our Datahike's `:reverse`](forks.md#datahike), which stops at n; members whose ids derive from their content (messages, forms) are read whole and the newest n kept by the transaction that wrote each ref (their map is ordered by id, as every collection is; a render that wants them in time order sorts by first-t). A limit may name a config key (``:seon.config.ctx/window``, ``:seon.config.ctx/callers``): no limit is a literal. A `:limit` takes `:reverse true`: a window is the newest n, never the oldest. A patch moves a window of time-ordered ids by its transaction's datoms (``seon.ctx/window-moves``): the member that joined assoc'd, the one that left dissoc'd, the oldest past the limit dropped, the window read again only to fill it from below its oldest when one left.
- `:by` joins by name, **ctx's one option beside Datahike's pull syntax** (everything else is pull's own, `:reverse` our Datahike's): forward, each value a lookup ref (`{[:seon.cite/name :by :var/name :as :var] […]}`: the var a cite names, a name naming none joins nothing until it is defined); reverse, the entities whose attribute holds this one's name (`{[:form/_refs :by :var/name :as :callers …] […]}`: a var's callers). The references stay the author's symbols; the lookup is a pure function of stored data.
- Every entity is held once, at the first path the walk reaches it by (the pattern's order, a window's newest member first); every other path holds `{:db/id e}`. So the agent's task is held under `:task`, and a reference to it elsewhere is its stub.
- A task's record holds what its work needs on the first page (`:seon.task/task-fact`'s pattern):
  - `:proved`, its proofs, each with its `:form`, whose `:form/refs` names every var the proof calls (first: a proof's form is held here, and a page fills its stub elsewhere from here);
  - `:cites`, what its text cites, each a cite entity (``:seon.cite/cite-fact``, [an entity cites](references.md#an-entity-cites)) with what it names joined: a section (`:section`, its heading, lead, text, references and the sections `:below` it), a var (`:var`, its `:form` whole and `:callers`, the newest ``:seon.config.ctx/callers`` forms naming it, each with the vars it `:defines`: the tests among them are the var's existing tests), a task (`:task`, by `:seon.cite/task`), a schema key's entry (`:schema`) or a namespace (`:ns`);
  - `:needs`, the tasks it waits on, each with its `:proved` and its `:cites` (one level: a pattern does not reach itself, so a need's needs are not joined), joined before the task's own `:cites`, so every proof is held at a `:proved`;
  - an agent's errors are no join of the task: they reach its context once, from one producer, the page's problems part (`seon.problems/own`: every error last raised in its task, one row per signature with its count), sent the model grouped by its report's model render, each row its count, type, first line and the form that reads it whole (```seon.render.ui/problems-model```, ```my.agent/problem```; the owner, 2026-10-30);
- The agent's record joins its own `:cites` the same way (what it reads beside its task: ``my.agent/cite!``). It holds no run (the agent is the unit, and there are no runs; the owner, [decisions](decisions.md)): its task is `:seon.agent/task` and its turn the agent's own number ([turn](turn.md#the-turn-is-a-number)), which its turn line, the chat's start and end and the status read on the agent; before its first turn the number is 0.

Every render of ctx reads what this declaration holds ([render](render.md#the-page)).

## What the scorer reads from a pulled node

The scorer (```seon.context/relevance```, embed-lab) ranks the nodes the pull holds; web-ui's render shows the ranked set. The pull is the candidate pool and carries **stored facts only** (the next section: nothing derived), each node's `:db/id` and its schema (the walk hands both); the scorer computes what it needs beyond them from the record and the existing producers, and a node it cannot score by its stored vector it scores by the text of its summary render. One contract, agreed with embed-lab:

- **A node's facts.**
  - *test result* (held, see below): `:seon.proof/test`, `status` (`:pass` `:fail` `:error`), `failures` (every failing assertion), `ms`, `digest`, `var` (a ref to the test's `{:var/name}`);
  - *eval*: `:seon.eval/id`, `by`, `code` and `response` (`:ex` present when it threw), each its own attribute, which it reads (an eval's code and a task's plan have a stored vector, the one index, so the scorer's focus is read from the evals the pull holds by `:db/id`, and nothing is pulled for it); *var and form*: `:var/name`, `:var/form`, `:form/src`, `:form/refs`; *task*: plan, proofs, cites, needs, `failure` and `evidence` (values); *section*: address, heading, text.
- **What the scorer derives, from the record and the producers, never from a field.** Whether a test is a proof of the task (its name among the task's `:proved`); whether a var is cited (a cite's `:var`); whether a var changed on this branch (the turn's branch changes, ```seon.merge/divergence```); whether a test's reach includes such a var (```seon.program```'s reach). A producer that wants one as data writes it as a fact. The scorer is pool-relative (its meaning and word features are z-scores over the candidates), so the render calls ```seon.context/relevance``` once with every pulled node it may show, never per node: a node's chance changes with what else is in the pool.
- **An agent's own record is never windowed**: every eval, turn and message the agent has is held (the owner, 2026-10-30: "deliver all messages and errors"); root's own record windows its copies of other processes' data (``:seon.config.ctx/window``). **A join through the program is bounded** by a config `:limit`, newest first, and reads from the current task or agent, never from a var or a section back to its history: `:callers` (``:seon.config.ctx/callers``). A test result's join is **held**: the owner's ruling is that an agent has turns and evals and no run, so the result must point at what asked for it, which the context inventory decides;

## Kept by the change, never rebuilt

``seon.ctx/build`` walks the pattern once, when the agent's state first holds its db (a spawn, a resume, a clone), and ``seon.ctx/patch`` keeps it from each transaction's datoms, which ``seon.agent/transact!`` records with the db they made. The walk's state (`:ix`) knows where each entity is held, its pattern, and which `[attribute value]` each join watches (a reverse join's ref to it, a lookup's name). A datom touches a held entity (its own attributes, a forward join) or a watched join; the patch rebuilds each touched entity where it is held, shortest path first, as a build would, keeping every join and member nothing touched, and copies the path above it. A rebuilt entity keeps every attribute equal to before as the object it was, and a rebuild that changes nothing is the old node. A move with no transaction (a merge of main, a resume) is patched from the datoms the two values differ by. A change of the pattern, or one that moves where an entity is held (a new run reaching the task, the holder leaving its window), builds the record anew, as a fresh build places it, and shares back every subtree it did not change (the same objects): that patch costs the record, once a run.

A patch costs its change, flat in the session (at 100 and 1,000 evals): a new eval 25 contracted calls and 159 KB, its window moved by an assoc and a dissoc and flat in the window's size too (`seon.ctx-test/the-patch-costs-the-change-not-the-session`, `seon.ctx-test/a-window-moves-by-its-change`; 815 KB while the window was read again and its map rebuilt); a cited var redefined 23 calls and 118 KB, a new caller 22 and 113 KB, a plan edit 10 and 86 KB (`seon.ctx-test/a-lookups-patch-costs-its-change`). A content-id window (a var's callers) is read whole and ordered: a new caller of a var named by n forms costs those n datoms read and sorted (`seon.ctx-test/a-callers-window-costs-its-forms`). After each of 150 random changes of a session's kinds (evals, runs, turns, messages, a cited var redefined, a caller added, a var defined or gone, a reference added or dropped, the agent's pattern edited), the patched record, its map, its state and every collection's order, equals a fresh build; every path no change reached is the same object (``seon.ctx/changes``, the one diff, reads what moved) (`seon.ctx-test/ctx-is-the-record-after-every-transaction`). ``seon.ctx/changes`` walks two collections' entries in step through their one order, passing a member that is the same object with one key compared and no path made, so a change of one member of 1,000 costs 392 KB and 75k ticks, and of 4,000 1.55 MB (2.95 MB and 12.8 MB when it walked the union of every key): the rest is the sorted map's seq, 193 bytes an entry on each side in Jolt (`seon.ctx-test/changes-answers-what-every-pair-walked-answers`, `seon.ctx-test/changes-step-costs-are-current`). The atom lives as long as the agent's process, across the runs of its session.

**What changed, and what did not.** A patch answers `:changed`, the paths its transaction changed: an attribute's, or a member's that joined or left. It changes only along those paths. So every value at a path not at, under or above one of them is the same object it was (`identical?`), and a part's memo is a pointer test. The same property test holds this after each of the 150 changes. The environment (`:t`, `:branch`, `:commit`) is the root map's, new each transaction and no path of `:changed`, so nothing caches on the root map. A build answers `:changed #{[]}`, the root path: every value is new, and a memo misses once, everywhere. The test counts the paths it checked (over 1,000 in 150 changes), so a patch that reported everything changed could not pass it.

**What changed over a turn is data.** (The model's request no longer sends it: a turn's request carries the parts whose drawing changed, docs/render.md#the-page-is-sent-as-what-changed; the diff stays the record's primitive for a reader that wants paths.) ``seon.ctx/diff`` answers what changed of the record from a turn's start to its end, in the record's own shape: `{path [old new]}`, old nil for a member that joined, new nil for one that went. It is pure in the record at the two t's. ``seon.ctx/advance`` patches the start's record by the datoms the start and end db values differ by (the net change of the turn's transactions, read from the db alone), so its `:changed` bounds where they are compared. A path equal at both ends is dropped (a change undone within the turn), and so is one under another the diff holds. The start's record with the diff applied is the end's, and the advanced record equals a build at the end t (`seon.ctx-test/a-turns-diff-is-what-changed-between-its-ts`, twelve turns of random changes). `diff` costs its changed paths, never the record: one contracted call for an eval added, at 100, 1,000 and 3,000 evals (`a-turns-diff-costs-its-changed-paths-not-the-record`); `advance` costs the patch of the net datoms. A patch applies every entity's retractions before any assertion, so a member retracted and made again under its key within a turn comes out as the end's.

**ctx is the db's data, nothing derived.** (owner, 2026-10-26: "no we don't store derived data in the db or the ctx atom".) What a view needs beyond the pull is a render over the db, memoized by what it read, never a member of ctx. Derived data may be cached elsewhere, in memory or in the store, keyed by its inputs: anything may evict it, so its reader regenerates it from the db as of t (owner, 2026-10-28; AGENTS §5). Config is read as of now, not as of t (task: the schema design, the scratch paper handoff/schema-design-2026-10-28.md (git history)). The conversation's order is each entry's first transaction, ``seon.context/first-t`` (one seek; it never changes, so a view memoizes it by entity).

**Any entity, any branch.** ``seon.ctx/build`` takes an entity id: an agent's (its `@ctx`), root's, the user's, a task's. ``seon.ctx/follow`` patches a record from one of the writer's commits as main's readers receive them (`{:t :ops :db}`), as an agent's follows its own transactions. A task retracted leaves its environment alone, as a build of no entity does (`seon.ctx-test/any-entitys-record-follows-mains-commits`, 60 commits, two records).

**The task's part is a render.** It is a component of render-ctx, a function of ctx and the db, run again when what it read changes ([render](render.md#components)). The task's part, ``seon.render.ui/task-data``, draws the plan as prose, and ``seon.context/task-data`` without its write set. Each thing the task cites is a component of its own over ctx alone, ``seon.render.ui/cited``, drawn by its cite's renders: a var's source, its tests (the callers' vars ctx holds that are tests), then its other callers (`seon.ctx-test/the-page-draws-what-the-task-record-holds`). Its callers are ctx's: the newest ``:seon.config.ctx/callers`` forms whose `:form/refs` name it, so a form that only quotes it is not among them ((my.agent/callers 'x) reads them all).

The other facts a view reads:
- A catch-up (``seon.agent/merge-main!``) is a `:seon.catch-up/*` entity written in the merge's own transaction: the branch and t merged, what applied and what conflicted. It is no join of the agent's pull (the pull holds the agent's task, every turn and eval, and its newest messages): a reader queries it, or adds `{[:seon.catch-up/_agent :as :catch-ups] [*]}` to its pattern (`seon.agent-test/after-merge-main-the-agent-judges-against-the-new-base`).
- Proof results are facts on each test's var entity on the branch (`:seon.test/*`), which ctx holds under the task's proofs; how the work stands is ```seon.context/status``` of the branch's facts, drawn by the page, never held (a turn's model call's basis is the commit it read, not what it measured). Every message the turn takes, an entry or another agent's send, is written on the branch (``seon.turn``'s `take!`, with `:seon.message/agent`) and sits under `[:messages]`.

## What the model reads, and what the page draws

`@ctx`'s value carries `{:seon.render/schema :seon.ctx/ctx}` as metadata. ``:seon.ctx/ctx`` declares a page render, ``seon.render.ui/ctx``, and none for the model, so the model reads `@ctx` as it reads any value, through the one printer, cut where it is large with the form that reads the rest. The page draws the same eval as a block: a row per key, each value by the render its key's own schema declares (``seon.render/render`` with the key as its schema), else the printer's structure.

An eval of `@ctx` is recorded as its basis, never as a copy: only the value that is the ctx itself (the one object `seon.ctx/ctx` holds, `identical?` to it) names it, by its `:branch` and `:t`; a map made of it (`select-keys`, `assoc`, which keep metadata) is the data it holds and is kept as any value, and ``seon.repl/record-details`` keeps `:seon.eval/schema` and `:seon.eval/basis`, no copy and no text (a session of 3,000 evals has a 3.9 MB record, which a copy would store again at every `@ctx`). Both readers render what exists: ``seon.context/basis-value`` rebuilds the map from the agent's branch as of t (``seon.ctx/build``), and ``seon.context/eval-messages`` (the model's text, the same bytes cold as live) and ``seon.render.ui/evaluation`` (the page) draw it.

A key whose schema the branch registered or changed is drawn by the agent, since its render may be defined only there and root cannot call it. ``seon.render.ui/ctx`` shows that key's structure, naming its render, and notes what it wants drawn; the render proc asks the agent for it while the page is viewed (``seon.render.proc/comp-entry``, an `{:op :render}` request through root's api to the agent, answered by ``seon.repl/agent-step`` under the branch's schemas, recording nothing), holds the answer, and renders the component again with it. An agent that is gone answers nothing, and its key keeps its structure, saying so, until the agent runs again or its render merges to main and root calls it. Nothing of the block is stored, so the model never reads HTML.

## Adding a datum and its render

An agent adds to its record, and to what it sees of it, with four evals (`seon.ctx-test/an-agent-adds-a-datum-and-its-render`):

```clojure
(my.schema/register! :lab.ctx/steps '[:vector {:seon.render/html lab.ui/steps} :string])
(ns lab.ui) (defn steps "The plan's steps, numbered." {:malli/schema [:=> [:cat :map [:vector :string]] :any]} [_ v] [:ol (for [s v] [:li s])]) (in-ns 'agent.a1)
(my.db/transact! [{:seon.agent/key (:seon.agent/key @ctx) :lab.ctx/steps ["read the plan" "write the test"]}])
@ctx
```

A related entity works the same way when its pattern joins it: a search the page draws on the db is one ([render](render.md#a-search-is-a-part)), a member added or changed by `swap!`. A registered key is an attribute at once when no entity map lists it (``my.schema/registration`` carries its declaration). The next `@ctx` holds it, and its block draws it by `lab.ui/steps`, drawn by the agent, unmerged. A class a render names is styled only if the page's stylesheet was built with it.

**Your own render, or the shared one.** To try another way of drawing something, declare your own, as above: a key of your own with its render changes only what your record shows. You can also redefine a shared render, or re-register `:seon.render/render-ctx`, on your branch ([your page, changed at your REPL](render.md#reactive-renders)), but once that merges it changes what every agent reads, so experiment with your own first ([decisions](decisions.md#2026-11-05-rulings)). Every function is a query away: `:var/form` is its source and `:var/contract` its inputs and output, so a render is found by what it takes:

```clojure
(d/q '[:find ?n ?c :where [?v :var/contract ?c] [?v :var/name ?n] [(clojure.string/includes? ?c ":seon.ctx/ctx")]] (seon.agent/db))
```

## Changing it: swap!

An agent changes its record as it changes any atom: `(swap! ctx assoc :lab.ctx/steps [...])`, `(swap! ctx update :evals dissoc 1753)`, `(swap! ctx assoc-in [:task :seon.task/plan] "...")`. The atom's validator (``seon.ctx/write!``) turns the change into one transaction on the branch: each attribute set or retracted (a cardinality-many one member by member), each join's member new (with its own joins, naming its parent by the join's ref and keyed by its identity), gone (its ref retracted, the entity kept: a removal unlinks, so a message removed is not delivered again and a `swap!` can bring it back) or changed; a member a lookup (`:by`) holds follows the attribute it reads, and one held at another path is changed there. Every value is checked by its schema, the platform's or one the branch registered; a dry run (`d/with`) checks the db would hold what the swap! says at each path it writes; then it is applied (``seon.agent/transact!``), and when the swap! ends the record is the db's (its new entities with their ids). Finding the change costs the change: a unit identical to its old self is skipped by one `identical?` (`seon.ctx-test/a-write-costs-its-change-not-the-record`: one attribute of the agent's entity, 5 contracted calls and 2,709 ticks at 100 and at 1,000 evals); a unit that differs is walked member by member, each identical member skipped the same way. The write itself adds one `d/with` and the patch of its datoms, which costs the change (the patch's own proof); `write!` as a whole is not measured.

Refused, nothing written, with the error that says why (`seon.ctx-test/a-swap-writes-the-record`):
- ``:seon.ctx/invalid``: a key with no schema (register it, a qualified keyword), or a value its schema refuses, each with its path and why;
- ``:seon.ctx/not-held``: the db would not hold what the swap! says;
- ``:seon.ctx/basis``: the map's `:t`, `:branch` or `:commit` is not the record's: the swap!'s function wrote the db (it is refused once, never retried, which closes the livelock a retrying swap! would be), or wrote the environment; or it is no map (a `reset!`).

The record's environment is read-only; everything else is writable, and history keeps what a write retracts.

**The page is the agent's to change.** The page is the render :seon.render/render-ctx declares (```seon.render.ui/render-ctx```, the layout), composed of components keyed by what they show ([render](render.md#components)); an agent overrides the layout or any sub-render by registering its own render on its branch, and its model reads the same output (```seon.repl/render-ctx-hiccup```). The agent's walk holds the layout it was made with, and is made again when the branch declares another (`seon.ctx-test/a-layout-declared-after-the-first-draw-is-the-page`).

## Deleting, compacting and resetting are changes of data

Deleting, editing, compacting or forgetting part of what an agent has read is a `swap!` on `@ctx`, and its next request is drawn from the record as it then is, so the provider's cache breaks only where the history changed. A delete unlinks ([changing it](#changing-it-swap)), so the entity stays, is not delivered again and can be put back, and history keeps everything. To compact, replace the first record of a range with a summary and unlink the rest; to forget from a point, unlink everything after it; to edit, `swap!` the record. A live agent tried each by data alone on 2026-11-04, one test each, and the messages before the change stayed byte-identical; only unlinking has a test on main, and page controls for the rest are in [the plan](plan.md#where-it-stands-2026-11-04-what-an-agent-reads). Resetting to a point is a new branch from that point's commit under the same agent key, which rewinds the record and the program together and destroys nothing (task seon.agent/reset-an-agent-to-any-point).

## The record is the agent's work

The agent's record holds facts about its work, and telemetry and derived data live on their own entities pointing at what they describe, so `*` never pulls them and the agent's ctx diff moves only when its work does (owner, 2026-10-29: "The agent's record is facts about its work ... a model call at its turn"; task seon.ctx/the-record-is-facts-about-the-work, whose move 3 is the embedding). A turn is a number on each record ([turn](turn.md#the-turn-is-a-number)), not an entity. The agent's pull joins its **model calls** (`:seon.model-call/*`, one entity a turn keyed `<agent key>/<n>`, `:seon.model-call/agent` its ref) by naming their attributes (``:seon.db/agent-fact``'s pattern): the words of the model and the facts that place them (`id`, `n`, `origin`, `run`, `reply`, `reasoning`, `finish`, `truncated`, `error`, `forms`), never `*`. The rest of the call is the request's bookkeeping, written by ``seon.turn/act!`` and ``seon.turn/context-block`` and left out of the pull, so a call's tokens, refs and times never move the agent's ctx: the basis its context was built from, the refs it sent, where its time went, its tokens and prefix-cache counts, its model, and the counts of its errors and red proofs. The debug page reads it by its own entity (``seon.render.ui/debug-input``) and the context page, which replays what a request sent, by the model call's `:seon.model-call/sent` (``seon.context/parts-of``). A message names its agent (`:seon.message/agent`); an embedding is a `:seon.vector/of` entity pointing at what it embeds. An agent's **process** (`:seon.process/*`, one entity a spawn keyed by the agent's key and the pid, `:seon.process/agent` its ref) holds its pid, memory, the form it evaluates, when it forked and ended and a stall it shows, written by ``seon.task/agent-tx`` when root's view of the agent changes; the agent keeps its key, id, root, branch, task, status and description. The agent's current process is its newest (``seon.task/newest-process``), and only a process that has not ended has a pid to show; root's agents card joins them (`:processes` in `:seon.root/root-fact`'s pattern), and ``seon.problems/stalled-agents`` reads the stall from the process. `seon.ctx-test/an-agents-record-holds-only-its-work`.

## Provenance: who made each fact

Who made a fact is a query on the tx-meta of its transaction, Datomic's reified transactions. Every transaction Seon makes names its branch (`:seon.tx/branch`, ``seon.db/tx-meta``). An agent's write during an eval also names that eval (`:seon.tx/eval`, its `:seon.eval/id`, "e5"): ``seon.repl/eval-string`` holds the running eval's id on the agent's state while its forms run, and ``seon.agent/transact!`` writes it, so a `swap!`, any `transact!` its code makes, and the eval's own record all name it. A catch-up (``seon.agent/merge-main!``) also names the branch it merged (`:seon.tx/merged`), so a fact main made reads as main's after the agent caught up, though the agent's branch wrote the merge.

``seon.ctx/made-by`` answers it for one attribute of one entity: the tx-meta of its newest datom's transaction, by two seeks (`(seon.ctx/made-by (my.db/db) (:db/id @ctx) :lab.ctx/steps)`). The page's ctx block shows it beside each attribute, as of the eval's t: the eval that wrote it, else "from :main" for a fact the agent was forked holding, and "merged from :main" for one a catch-up brought (`seon.ctx-test/a-change-names-its-eval`; the tx-meta itself, `seon.agent-test/an-agents-transactions-name-their-runtime` and `after-merge-main-the-agent-judges-against-the-new-base`).

Not covered: root's own writes (``seon.root``'s transactions on main) name no eval; a join's members show no provenance on the block (each eval is its own record); a removed member is not shown as removed.
