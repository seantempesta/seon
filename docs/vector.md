# Vectors

Semantic search is part of the store and its query language. Each form's, wiki section's, schema entry's and task plan's text is embedded once by a small local model in a helper process of root's. Its vector is kept as facts on an entity of its own ([a vector is its own entity](#a-vector-is-its-own-entity)), and `seon.vector/near` is a Datalog function, so similarity is one more relation a query joins. An agent asks it at its REPL (`my.agent/similar`). The ruling: DECISIONS "Embeddings join the context: fused, small and measured".

```clojure
[(seon.vector/near $ ?q 10 {:of :form/id}) [[?e ?score]]]   ; ?q an entity with a vector, or a vector
```

## The model

EmbeddingGemma-2 (768 dims, Matryoshka, mean-pooled, normalized) runs through llama.cpp. `native/embed.c` puts its encoder behind a C ABI of pointers and ints (open, embed a batch of texts as one UTF-8 buffer and offsets, close); `bin/build embed` builds llama.cpp from `reference-code/llama.cpp` (static, Metal, no OpenMP) with it into `target/lib/libseon-embed.dylib`. The model file is ggml-org's Q8_0 GGUF, fetched once by `bin/build` into the main tree's `target/cache/models/`, named by its sha256 and checked against it. `bin/env`'s `SEON_EMBED_MODEL` is the one place the pin is written (`:seon.config.vector/model` reads it); its name, with the version of the texts it embeds, is the model id on every vector (```seon.vector/model-id```), so a model change makes every vector due again. Nothing is installed outside `target/`; cmake is the one added prerequisite.

The model runs in an exec'd helper, never in root or a fork: ggml and Metal start threads, and macOS aborts a process forked from a threaded one that touches them ([failure points](failure-points.md#physics-who-may-run-threads)). `target/seon embed-worker` (```seon.vector/serve!```, a mode of the one binary) loads the library and the model and answers framed requests on its pipes. Root's side is the `:embed` effect kind (`resources/seon/system.edn`), a batch kind with one worker; its host object (```seon.vector/open```) holds no process.

- **Start.** The first batch of a spell of work starts the helper over this checkout's binary with root's config layers, and waits for its first frame, `{:ready {:dims n}}` or `{:error e}` (`:seon.vector/model-unopened`).
- **Protocol.** Frames are `seon.sock`'s ([u32 length][fasl body]), written with ```seon.sock/frame``` and read with ```seon.sock/recv-stream!```. A request is `{:texts [...]}` (every text of the batch, in order, one request in flight); the answer is `{:vectors [...] :tokens [...]}` or `{:error e}` (`:seon.vector/encode-failed`). ```seon.vector/embed``` splits it back into each request's `{:value {:model :vectors :tokens}}`. A search's query is an ordinary request, so every asker goes through the one effect.
- **Stop.** When the owner's queue is empty and nothing is in flight, the owner tells its worker `{:idle true}` (```seon.fx/owner-proc```, for a kind declaring `:close`), and ```seon.vector/close``` closes the helper's stdin; it exits 0. No clock ends a helper. A request saying `:more` (the vectors proc's backlog) keeps it up; when the proc's spell ends after a `:more` request, it sends an empty `{:texts []}` without `:more`, which ```seon.vector/embed``` answers without a helper and which closes it (```seon.vector-test/a-more-round-followed-by-nothing-due-releases-the-helper```). The helper also ends with root (`seon.lib/end-with!`), and its pipes are not inherited by root's other children (Jolt spawns with `POSIX_SPAWN_CLOEXEC_DEFAULT`).
- **Death.** A helper's death is its pipe's EOF: every request in flight is answered `:seon.vector/helper-died` with its exit and the last `:seon.config.vector/stderr-bytes` of its stderr (a file under `target/tmp`, never a pipe), and the next batch starts a new one (```seon.vector-test/a-helper-that-dies-mid-batch-answers-an-error-and-the-next-batch-works```). One that died while idle fails the next write before any answer: `embed` starts one new helper and asks once more (```seon.vector-test/a-helper-killed-while-idle-is-replaced-and-the-request-answered```).

A batch is encoded in pieces of at most `:seon.config.vector/batch-tokens` tokens and `:seon.config.vector/batch-texts` texts; the kind takes up to `:seon.config.vector/batch` queued requests a step; ggml's CPU pool is `:seon.config.vector/threads` (Metal does the encode). The helper holds 350-550 MB while it runs and nothing after; root holds no model (```seon.vector-test/root-holds-no-model-after-an-embed```), and `bin/check scale` counts root, the fork server and the agents, not the helper.

## What is embedded

Each kind's text is its attribute's value with the model's prompt: a form's `:form/src` titled by its var's name, a section's `:seon.doc/text` by its heading and a schema entry's `:schema/form` by its key, as documents (```seon.vector/document```); a task's `:seon.task/plan` as a query (`seon.vector/query-prompt`). An eval's code is not embedded. The texts' version is part of the model id, so changing how texts are made makes every vector due once. A text over `:seon.config.vector/max-tokens` keeps its first tokens.

A vector is these facts: `:seon.vector/f16` (the whole vector), `:seon.vector/coarse` ([the pyramid](#the-pyramid)), `:seon.vector/model`, `:seon.vector/text` (the digest of the text the model read, title included) and `:seon.vector/tokens` (the text's whole token count).

`seon.vector/due` lists the texts whose vector is missing, made from another text (its `:seon.vector/text` is not the text's digest now) or by another model. Two branches that embed one text hold one value, so a merge never conflicts on it.

`seon.vector/vectors-proc` keeps main current. At the writer's commit notice it sends the first `:seon.config.vector/texts` due to `:embed` and writes their vectors to main through the writer; that commit's notice starts the next round, and an idle main asks nothing. Once caught up it keeps the commit it scanned at (a reference `{:t :commit}`, never a db value) and reads only what later commits wrote (```seon.vector/written```, a `datoms-diff`), so a backlog is caught up by seeks, never a scan a round (```seon.vector-cost-test/a-backlog-is-caught-up-by-seeks-not-scans```). A failed embedding is the effect owner's recorded error and the next notice tries again; texts llama.cpp cannot encode are kept out of later rounds (`:unembeddable`, in the proc's ping).

An agent's branch reads main's vectors as of its fork and embeds its own writes: at each turn's observe, ```seon.agent/embed-written!``` sends the forms, sections and plans the branch wrote since the last turn, those due, to root's `:embed` in one request over the agent's socket, and writes their vectors on the branch. A turn that wrote nothing due asks nothing.

## A vector is its own entity

An embedding is derived data, so it lives on its own entity pointing at what it describes (DECISIONS, owner 2026-10-29), never on the form, section or plan, where a pull would carry it: `{:seon.vector/of e :seon.vector/model :seon.vector/text :seon.vector/f16 :seon.vector/coarse}` (```seon.vector/fact```; ```seon.vector-test/a-vector-is-its-own-entity```).

Its identity is `:seon.vector/of`, a unique-identity ref: one vector entity per embedded entity, upserted in place when the text or model changes. Retracting the embedded entity retracts its vector in the same write ([the one transaction path](storage.md#the-write-checks-every-entity-it-touches)), so none is left behind (```seon.vector-test/a-retracted-entitys-vector-ends-with-it```). `due` and `vector-of` find a vector by one AVET seek of `:seon.vector/of`; `near` merge-joins its scans of `:seon.vector/of` and `:seon.vector/coarse`.

## The pyramid

A Matryoshka vector's prefix is itself an embedding, so one stored vector serves two levels (`native/vector.c`, in libprobe: no threads, every process loads it). The coarse vector is the first `:seon.config.vector/coarse-dims` dims renormalized and scaled to int8 with its scale (`seon.vector/pack`). The coarse level scans every coarse vector with integer dot products and keeps the best `:seon.config.vector/shortlist` in a heap; the fine level ranks those at f16 over `:seon.config.vector/fine-dims` dims. A query option changes either (`{:shortlist n :fine-dims d}`); a shortlist of every vector is the exact search. `near` reads the coarse vectors from the db value each call (no cache) and only the shortlist's f16 vectors.

At the defaults (128 coarse dims, shortlist 400, 768 fine) recall@10 against the exact search is 0.998 on Seon's own text; `bin/check vectors` proves it each run, and ```seon.vector-test/the-pyramid-ranks-as-an-exact-search``` on made vectors. The datom reads and copies, not the C levels, are nearly all of `near`'s cost; the coarse vectors kept as one buffer per db value is the lever if a store grows past about 100k vectors.

## Search

**A search answers as grep does.** `my.agent/search` answers its hits as `my.agent/grep`'s rows (```my.agent/hit-rows```): each `{:at "name:n" :kind :text}`, the line of the hit's text that holds a word of the query, with its `:name` and `:relevance`. Agents trust grep because it shows the line. A line of a namespace's ns form, or of a form that defines no var (a `defmethod`, an `extend`), is the namespace's, at the line its file holds it on, which `(lines 'the.ns)` reads (`seon.doc-test/grep-finds-a-method-at-its-namespaces-line`).

The text ranking is SQLite's FTS5 (```seon.doc/tokens```): BM25 over the Porter stems of the query's words (```seon.doc/words```: lower case, split at every character that is no letter or digit, so `datoms-diff` is `datoms` and `diff`), quoted and joined by OR; a text's score is its z above the mean of every text of the kinds asked. A word matches a whole term by its stem: "watching" finds `watch!`, and "it" is no part of "edit". The index's idf is over the whole table; relevance scores its pool apart with ```seon.doc/bm25``` ([relevance](#relevance)).

```seon.doc/text-index``` is the one index: two in-memory FTS5 tables over every text attribute's texts (a form's source, a section's text, a task's plan, a schema entry's form) (```seon.sqlite/fts-open```), and a table `r` naming each text's rowid by its entity and attribute, so one text is one seek. `t` is `porter unicode61` and ranks; `g` is `trigram` and finds a substring, so `grep` with a string of three characters or more asks it for the texts holding the string anywhere, then matches lines exactly; a shorter string or a regex reads every text. ```seon.sqlite``` is the one namespace that names libsqlite3 (`:seon.config.native/sqlite-lib`), bound with ```seon.lib/defc```; its per-text inner calls are `ffi/cfn` locals of one macro, since a contracted call is counted work. A return code that is not OK is `:seon.sqlite/refused`, a library that will not load `:seon.sqlite/unloaded` ([failure points](failure-points.md)).

The index is derived data ([derived data](data-modeling.md#derived-data-is-a-cache-never-relied-on)): built for a db value, rebuilt whenever it is gone. A move that writes a text replaces that text's rows in the held index (```seon.sqlite/replace-rows!```, from `seon.doc/carry-index!`, told the entity and attribute of each datom written), so a definition costs its form, never the program (```seon.program-cost-test/a-definition-costs-the-form-never-the-program```; ```seon.doc-test/a-carried-index-answers-as-a-built-one```). A write the index was not carried to builds it again whole. Its memory is native, so `text-index` retires the index it replaces (```seon.sqlite/retire!```), closed at once when no reader holds it and by the last reader's release otherwise (readers go through `seon.sqlite/using`; ```seon.doc-test/a-superseded-index-is-closed-once-nothing-uses-it```). The index is keyed by `(:hash db)` with `(:max-tx db)`, since a branch's db value is a new object at every deref.

**The index is built once, in the fork server, and carried by every move that writes no text.** `seon.fork-server/warm-start` builds main's index, so each forked agent inherits it (in-memory SQLite is plain copy-on-write memory; the fork server is one thread). `seon.doc/carry-index!` keys the held index to a move's db when the move wrote no text attribute; its callers are the ones that know what a move wrote: `seon.agent/transact!`, an agent's merge of main, and the fork server's commit of main (```seon.agent-test/an-agents-first-search-reads-the-index-it-inherited```, ```seon.doc-test/a-text-index-is-carried-past-a-move-that-writes-no-text```).

**The request's search on the first page** (```seon.render.ui/searched```) is a part the agent's ctx holds: the request's text searched on main as the branch last merged it (`:seon.agent/base-commit`), a line a hit, each its name and the line holding a word of the query (its arglist when that line only opens its definition). The agent's own writes move no hit (```seon.render-test/a-definition-matching-the-request-moves-no-search-hit```). The query's vector is read on the branch: the agent's first turn embeds its task's search queries with its plan (```seon.vector-test/a-requests-search-gets-its-vector-on-the-branch-before-the-first-page```); a query with no vector yet is drawn as searched by its words.

## Fused with the call graph

```seon.vector/rrf``` fuses rankings by reciprocal rank (k `:seon.config.vector/rrf-k`). Fusing the call graph's one-hop helpers of a task's cited vars with the forms nearest its plan did no better than embeddings alone (recall@10 0.451 against 0.495 on 283 commits), so search does not use it; `rrf` stays for exploration. A call-graph neighbour weighs by its rarity, 1/(1 + the forms naming it, to 16), so plumbing every contracted form names (`seon.contract/checked`, `seon.db/eid`) does not rank first; [relevance](#relevance) weighs a link to a seed the same way.

## Relevance

How relevant an item is to an agent's work is one calibrated number, the chance it is worth reading for that work (```seon.ctx.search/relevance```), on one scale for functions, sections and schema keys. `my.agent/search` shows a hit with its chance from `:seon.config.render/relevance-summary` (0.4) and, below that, only a count with the call that lists them. The context is the plan's vector and words, what it cites (the seeds) and what the branch changed (the touched items).

**The score.** For each kind, the pool is the `:seon.config.render/relevance-pool` nearest by meaning (`seon.vector/near`), the seeds, and the seeds' neighbourhood in the reference graph (a form's calls, names and keys; a section's names, links, parent and children; a key's readers, by `:form/keywords`). Each item gets five features:
- `zc`, its cosine with the query, as a z-score over the pool;
- `zb`, its BM25 (```seon.doc/bm25```) for the query's identifier tokens (```seon.doc/terms```: `near-of` and `nearOf` are `near` and `of`), its idf over the pool itself;
- `zt`, its cosine with the touched items' mean vector, a z-score;
- `g1`, the seeds it neighbours, each link weighed by its rarity;
- `ppr`, its personalized PageRank from the seeds, by local push (Andersen, Chung and Lang 2006) at `:seon.config.render/relevance-eps`.

A logistic over them, one weight set a kind (`:seon.config.render/relevance-weights`), gives a logit fitted to what merges changed; a table per kind (`:seon.config.render/relevance-calibration`) reads it as the chance an independent judge finds the item worth reading. On held-out plans it beat cosine, BM25, their fusion and a contrastive adapter (recall at 5: functions 0.43, sections 0.80, schema keys 0.40, against 0.30 / 0.61 / 0.30 for cosine alone). Lines at 60% or more were judged useful about 0.8 of the time, at 40-60% about 0.57.

Tried and left out: the 128-dim prefix as the ranking (sections 0.48 against 0.65), a contrastive adapter (too few query-shaped pairs; agents' searches are the data to train one on), gradient-boosted trees, BM25 over names alone, a 2-hop count, and a local cross-encoder (bge-reranker-v2-m3: AUC 0.61 against 0.72, 1.5 GB).

**Cost.** A call costs `near`'s scan of the coarse vectors (linear in the store) and a part bounded whatever the store's size: the pool, each item its vector's seek and its text's term counts, kept beside the text index's row (```seon.doc/text-terms```: counted on first read, dropped when a move writes that text), so a search costs the words it ranks, not the texts' length (```seon.doc-cost-test/a-search-costs-flat-in-its-texts-length```); at most 1/(alpha eps) pushes, and a hub's degree counted by seeks, never read whole (```seon.ctx.wire-cost-test/a-push-reads-what-its-threshold-reaches```, ```seon.ctx.wire-cost-test/a-push-counts-a-hub-and-reads-it-not```).

## What the work is likely to need, as an eval

A task that starts from a request holds a search of the request's words (written by ```seon.template/request-tx```), and its page draws it as a part (```seon.render.ui/searched```, [render](render.md#a-search-is-a-part)): what the work is likely to need, found by `seon.ctx.search/search` on main at the branch's merge base and ranked by `seon.ctx.search/relevance`. On 49 changes from Seon's history, with requests that named no code, a changed item ranked first in 41% and in the top ten in 78% (8% first by words and references alone); given the ten hits' names, a model named a changed item in 30 of 49 against 2 without. A hit's first sentence added tokens and no measurable gain, so hits show names. Expanding by the call graph or by earlier sessions' work found little.

### What was compared, and what it left out

What the comparison of search methods settled.

- **Grep is not fused in:** it helped sections only at 10 and needs a stop-word list; `my.agent/grep` stays a query. Tasks rank weakly by every method and stay a query (`my.agent/similar`).
- **A function's schema keys earn their tokens, a key's functions do not.** `:form/keywords` (the qualified keywords a form's code and contract name) makes a function's keys one EAVT seek and a key's functions one AVET seek; relevance reads it.
- **Rendered hiccup is not embedded:** each turn's renders would be most of what is embedded and none of it reused.
- **Biases of these measurements:** the db was main after the merges (flattering embeddings and grep), and the truth was what a merge changed, not what its worker read.
