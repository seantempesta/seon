# Vectors

Semantic search is native to the store and its query language: each form's, wiki section's, schema entry's and task plan's text is embedded once by a small local model in a helper process of root's, its vector is kept as facts on an entity of its own pointing at it ([a vector is its own entity](#a-vector-is-its-own-entity)), and `seon.vector/near` is a Datalog function, so similarity is one more relation a query joins. An agent asks it at its REPL (`my.agent/similar`). The ruling is DECISIONS "Embeddings join the context: fused, small and measured".

```clojure
[(seon.vector/near $ ?q 10 {:of :form/id}) [[?e ?score]]]   ; ?q an entity with a vector, or a vector
```

## The model

EmbeddingGemma-2 (768 dims, Matryoshka, mean-pooled, normalized) runs in process through llama.cpp: `native/embed.c` puts its encoder behind a C ABI of pointers and ints (open, embed a batch of texts given as one UTF-8 buffer and offsets, close), and `bin/build embed` builds llama.cpp v0.7.0 from `reference-code/llama.cpp` (static, Metal, no OpenMP) with it into `target/lib/libseon-embed.dylib`. The model file is ggml-org's Q8_0 GGUF, fetched once by `bin/build` into the main tree's `target/cache/models/`, named by its sha256 and checked against it (`bin/env`'s `SEON_EMBED_MODEL`); its name, with the version of the texts it embeds, is the model's id on every vector (`seon.vector/model-id`), and `bin/env` is the one place the pin is written (`:seon.config.vector/model` reads it), so a model change makes every vector due again. Nothing is installed outside `target/`; cmake is the one added prerequisite.

The model runs in an exec'd helper, not in root and not in a fork. ggml and Metal start threads, and Apple's runtime aborts a process forked from a threaded one that touches them ([failure points](failure-points.md#physics-who-may-run-threads)), so `target/seon embed-worker` (```seon.vector/serve!```, a mode of the one binary) loads the library and the model (```seon.vector/open-model```) and answers framed requests on its pipes. Root's side is the `:embed` effect kind (`resources/seon/system.edn`), a batch kind with one worker; its host object (```seon.vector/open```) is a handle with no process in it:

- **Start.** The first batch of a spell of work starts the helper (```seon.vector/start!```: `ProcessBuilder` over this checkout's `target/seon embed-worker` and root's `--config` and `--set` layers, so it reads root's config) and waits for its first frame, `{:ready {:dims n}}` or `{:error e}` (the model missing or unloadable: `:seon.vector/model-unopened`).
- **Protocol.** The frames are `seon.sock`'s ([u32 length][fasl body]), written with ```seon.sock/frame``` and read from the pipe with ```seon.sock/recv-stream!```. A request is `{:texts [...]}` (every text of the batch's requests, in order, one request in flight), the answer `{:vectors [[x ...] ...] :tokens [n ...]}` or `{:error e}` (`:seon.vector/encode-failed`); ```seon.vector/embed``` splits it back to its requests' `{:value {:model :vectors :tokens}}`, the same data in root and across an agent's socket. A search's query is an ordinary request, so every asker (the vectors proc, an agent's turn, `my.agent/search`) goes through the one effect.
- **Stop.** When the owner's queue is empty and nothing is in flight, the owner tells its worker `{:idle true}` (```seon.fx/owner-proc```, for a kind declaring `:close`), and the worker calls ```seon.vector/close```: the helper's stdin is closed, it reads the end of its input and exits 0, and its pid, exit status and start and exit stamps are the worker's facts (the ping's `:closed` and `:host`). That event is the only thing that ends a helper in service; no clock does. A request that says `:more` (main's backlog: the vectors proc asks the next round when this one's vectors are written) keeps it up. Release rule: wherever the vectors proc ends its spell while its last request said `:more` (a round finding nothing due, an embedding that failed with nothing to record, a write that failed and so starts no next round), it sends an empty request `{:texts []}` without `:more`; ```seon.vector/embed``` answers it without starting a helper, and its answer is the event that closes the helper (```seon.vector-test/a-more-round-followed-by-nothing-due-releases-the-helper```). A normal exit (status 0 after `close`) is only the worker's ping (`:closed`, `:host`); a death reaches the error facts (`:seon.vector/helper-died` with its exit and the last `:seon.config.vector/stderr-bytes` bytes of stderr (```seon.lib/tail-bytes```), which the helper writes to a file under `target/tmp`, never a pipe that could fill). A helper that died while idle fails the next request's write before any answer: ```seon.vector/embed``` starts one new helper and asks again once (```seon.vector-test/a-helper-killed-while-idle-is-replaced-and-the-request-answered```). The helper's pipes are not inherited by root's other children: Jolt spawns with `POSIX_SPAWN_CLOEXEC_DEFAULT` on macOS, so a build or test child starts with only its own stdio, and the fork server was forked before any helper. The helper also ends with root (`seon.lib/end-with!` on its parent), and a request that arrives after the close starts another.
- **Death.** A helper that dies is its pipe's EOF: every request of the batch in flight is answered `:seon.vector/helper-died` (`:exit`, `:stderr`) and the next batch starts a new one (```seon.vector-test/a-helper-that-dies-mid-batch-answers-an-error-and-the-next-batch-works```). 

Measured 2026-10-29 on a scratch root (a new store, 5,593 texts at boot, machine load 11-16, M5 Max): root's footprint after the backlog was 1,675 MB with the model in process and 1,128-1,149 MB with the helper, which is gone (no process, no `.gguf` in root's `lsof`) once the queue emptied (```seon.vector-test/root-holds-no-model-after-an-embed```). The backlog took about 70 s either way with `:more` (one helper for all 89 batches); without it, a helper per round took about 210 s, which is what an idle root pays per request: a search on an idle root waited 1.24 s (start, load and query, at load 14; 0.45 s on a quiet machine, 3.7 s for the first load of a session) and a warm query 7 ms. While it runs, the helper holds 350-550 MB, and none of it once it has exited: closing the model inside a process left about 180 MB (the Metal driver) behind.

The model is EmbeddingGemma-2 (768 dims, Matryoshka, mean-pooled, normalized) through llama.cpp: `native/embed.c` puts its encoder behind a C ABI of pointers and ints (open, embed a batch of texts given as one UTF-8 buffer and offsets, close), and `bin/build embed` builds llama.cpp v0.7.0 from `reference-code/llama.cpp` (static, Metal, no OpenMP) with it into `target/lib/libseon-embed.dylib`. The model file is ggml-org's Q8_0 GGUF, fetched once by `bin/build` into the main tree's `target/cache/models/`, named by its sha256 and checked against it (`bin/env`'s `SEON_EMBED_MODEL`); its name, with the version of the texts it embeds, is the model's id on every vector (```seon.vector/model-id```), and `bin/env` is the one place the pin is written (`:seon.config.vector/model` reads it), so a model change makes every vector due again. Nothing is installed outside `target/`; cmake is the one added prerequisite. One batch is embedded in encodes of at most `:seon.config.vector/batch-tokens` tokens and `:seon.config.vector/batch-texts` texts, and the kind takes up to `:seon.config.vector/batch` queued requests in a step. The open model keeps 4 threads (Metal's) beside the helper's own, and its load runs ~32 more until it has loaded (all in the helper); ggml's CPU pool is `:seon.config.vector/threads` (1: Metal does the encode). `bin/check scale` holds root's `seon.lib/real-mb`, the fork server's and the agents' within the 4,096 of `:seon.config.machine/memory-mb`; the helper is outside that sum while it runs, at most about 0.6 GB.

Memory with the model loaded in a process (macOS footprint, measured 2026-10-29, idle): 1,641 MB against 1,262 MB without it; of the 224 MB of malloc, 206 MB is llama.cpp and Metal, allocated once by `seon_embed_open` (the tokenizer's vocabulary 83.5 MB in 787 k blocks, ggml's scheduler 66.9 MB, Metal's shader cache 30 MB), with no leak seen; `:seon.config.vector/batch-tokens` 4,096 also maps 721 MB of virtual Metal buffers (210 MB at 1,024).

Measured on Seon's 1,393 src forms (M5 Max, Metal, machine load ~10): the model opens in 3.7 s; one text takes 5-15 ms warm; batched, 37k tokens/s (175 texts/s) at a 4,096-token encode (512: 122/s, 1,024: 167/s), 0.86 GB RSS; the BF16 file is no faster (34k tokens/s). v1 ran the same model in MLX over HTTP (5.7 ms one text, 66-105k tokens/s batched on short texts). mistral.rs (ericlbuehler/mistral.rs at `f512686`) was evaluated and not used: it has no EmbeddingGemma-2, did 32 texts/s on Qwen3-Embedding-0.6B in its place, and brings tokio and 461 crates.

## What is embedded

Each kind's text is its attribute's value with the model's prompt: a form's `:form/src` titled by its var's name, a section's `:seon.doc/text` by its heading and a schema entry's `:schema/form` by its key, as documents (```seon.vector/document```: the model card's title slot), a task's `:seon.task/plan` as what a search asks (`seon.vector/query-prompt`, the card's `search result`). Titled, with that prompt, 20 search queries found 0.58 of their functions and sections at 5 against 0.44 untitled with `code retrieval` ([relevance](#relevance)); the texts' version is part of every vector's model id (```seon.vector/model-id```), so a change to them makes every vector due once. A title changed with its text unchanged (a heading edited alone) keeps the vector of the old title until the text changes: a vector is due by its text's transaction, not its title's. A text over `:seon.config.vector/max-tokens` keeps its first tokens, and special-token text in it is read as text. A vector is five facts on the entity: `:seon.vector/f16` (the whole vector), `:seon.vector/coarse` (the [coarse level](#the-pyramid)), `:seon.vector/model`, `:seon.vector/text-t` (the transaction of the text it embeds) and `:seon.vector/tokens` (the text's whole token count: past the bound, what was left out).

`seon.vector/due` lists the texts whose vector is missing, made from an earlier text (its `:seon.vector/text-t` is not the text's transaction, so a text changed while its round was out stays due) or another model's. A form is content-addressed, so its text never changes and it is embedded once; a superseded form is retracted, and the proc retracts its vector (below). `seon.vector/vectors-proc` keeps main current: at the writer's commit notice it sends the first `:seon.config.vector/texts` due to `:embed` and writes their vectors to main through the writer; that commit's notice starts the next round, so a backlog is embedded round by round and an idle main asks nothing. Once a round has asked for everything due, the proc is caught up (`:clean`, the commit it was asked at: a reference `{:t :commit}`, the base db made from it with `seon.db/at-commit` (`d/commit-as-db`: about 100k ticks and 440 KB a round) when a round diffs, never a kept db value; [machine](machine.md#what-a-process-owns-in-memory)) and its next rounds look only at the texts the commits since changed (`seon.vector/written`, a `datoms-diff`: the cost of the commit, not of the store); the first round, a backlog, a failure and a restart scan every text. A failed embedding is root's problem (the effect owner records it) and the next notice tries again; texts llama.cpp could not encode are kept out of later rounds (the proc's `:unembeddable`, in its ping), so they never hold back those due after them. Seon's whole text (2,681 texts: 1,783 forms with the schemas, 321 sections, the task plans) embeds in 17-19 s at boot. An agent's branch reads main's vectors as of its fork, and embeds its own writes: at each turn's observe (```seon.agent/embed-written!```) the forms, sections and plans the branch wrote since the last turn (```seon.vector/written```, a `datoms-diff` from the db it last read: the cost of what changed) and its task's plan, those due, go to root's `:embed` in one request over the agent's socket (the model stays in its helper, root's), and their vectors are written on the branch; a turn that wrote nothing due asks nothing, and a failed embedding is the effect's recorded error with the texts still due. A merge carries no `:seon.vector/*` facts (they are platform records, `seon.merge/carried-tx`): main's `vectors-proc` embeds the merged texts again at the merge's commit notice, as it does any text new on main.

## A vector is its own entity

An entity's record is facts about its work, and an embedding is derived data (owner, 2026-10-29: "Telemetry and derived data live on their own entities, pointing at what they describe: a vector at its eval"). So a vector is not written on the form, section, plan or eval it embeds, where `*` pulled it into an agent's record and its diff showed it each time it was written: it is an entity `{:seon.vector/of e :seon.vector/model :seon.vector/text-t :seon.vector/tokens :seon.vector/f16 :seon.vector/coarse}` (```seon.vector/fact```), and the embedded entity's own pull holds none of it (`seon.vector-test/a-vector-is-its-own-entity`).

Its identity is `:seon.vector/of`, a unique-identity ref: one vector entity for each embedded entity, and writing a vector again (a changed text, another model) upserts that entity in place. A composite `[of model]` tuple (Datahike's `:db/tupleAttrs`) would keep a vector of each model, which nothing reads (a vector of another model is due again and replaces the old), and would add a tuple datom to every vector; one identity attribute is the means Datahike gives for exactly this. `due` and `vector-of` find a vector by one AVET seek of `:seon.vector/of`; `near` merge-joins its two scans (`:seon.vector/of` and `:seon.vector/coarse`, both in vector-entity order: advance the smaller, emit when equal), so a row costs one datom read more (measured 2026-10-29 at 1,000 vectors: 5.16 MB to 5.22 MB). Retracting an embedded entity (a superseded form: `seon.program`, `seon.source`, `seon.merge`) drops the `:seon.vector/of` datom that pointed at its vector and leaves the vector's facts (about 1.6 KB) behind. `seon.vector/vectors-proc` retracts them: each round reads one `datoms-diff` from the previous round's commit (`:seen`), which gives the texts added (what is due) and the datoms removed, and `seon.vector/orphaned` turns each removed `:seon.vector/of` the db does not hold again into retractions of that vector entity's `:seon.vector/*` facts, written with the embeddings, or alone when nothing is due. The diff is from the previous round, not from `:clean`, which is the commit before the proc's own write; a vector written and orphaned between two rounds that skipped a commit is retracted by the next full scan (a round with no `:seen`, after a start or a failure, finds every coarse row with no `:seon.vector/of`). Round cost unchanged: 302 k ticks / 1.01 MB / 15 calls at 100 texts, with one diff doing both jobs (`seon.vector-test/a-retracted-entitys-vector-is-retracted-by-the-round`).

A store that holds vectors written on their entities by an earlier version keeps them there: they have no `:seon.vector/of`, so no reader finds them, every text is due again and is embedded onto a vector entity; erasing the store drops the old ones from a pull (the standing store is test data).

## The pyramid

A Matryoshka vector's prefix is itself an embedding, so one stored vector serves two levels (`native/vector.c`, in libprobe: no threads, every process loads it). The coarse row is the first `:seon.config.vector/coarse-dims` dims renormalized and scaled to int8, with its scale (`seon.vector/pack`); the coarse level scans every row with integer dot products and keeps the best `:seon.config.vector/shortlist` in a heap; the fine level ranks those at f16 over `:seon.config.vector/fine-dims` dims, each prefix renormalized. A query option changes either (`{:shortlist n :fine-dims d}`); a shortlist of every vector is the exact search. `near` reads the coarse rows from the db value each call (no cache: a db value is its own index), copies them into one buffer, and reads only the shortlist's f16 rows.

Recall@10 against the exact 768-dim search:

| corpus | coarse | shortlist | fine | recall@10 |
|---|---|---|---|---|
| Seon's whole text, 2,681 (`bin/check vectors`, 207 queries) | 128 | 50 / 100 / 200 / 400 | 768 | 0.946 / 0.979 / 0.990 / **0.998** |
| src forms, 1,393 (every form a query) | 64 / 128 / 256 | 100 | 768 | 0.945 / 0.9975 / 1.0 |
| src forms | 128 | 100-400 | 256 | at most 0.83 |

The C levels take 0.08 ms at 1,393 vectors and 0.31 ms at 100k (v1's f32 brute force: 4.1 ms at 100k; em1's kernel 0.39 ms at 10k). The whole `near` in Jolt takes 1.9 ms at shortlist 100 and 4.6 ms at 400 on 1,737 vectors, nearly all of it the datom reads and copies; at 100k those would cost about 20 ms (estimated), the next lever if a store grows that large. `bin/check vectors` proves the default on Seon's own text each run, and `seon.vector-test/the-pyramid-ranks-as-an-exact-search` on made Matryoshka-shaped vectors. Proximum's HNSW was rejected in v1 (1.6-4.3 MB per commit, recall 0.16-0.62).

## Search

The text ranking of `my.agent/search` is SQLite's FTS5 (```seon.doc/tokens```): BM25 over the Porter stems of a query's words (```seon.doc/words```: lower case, split at every character that is no letter or digit, as the index tokenizes a text, so `datoms-diff` is `datoms` and `diff` and `SeonRun` is the one term `seonrun` in the query and the text alike) against every text, quoted and joined by OR, a text's score the negated `bm25` of the table, z its distance in standard deviations above the mean of every text of the kinds asked (a text holding no word scores 0). A word matches a whole term, by its stem: "watching" finds `watch!`, and "it" is no part of "edit". FTS5's bm25 (k1 1.2 and b 0.75, SQLite's own) measures a text's length in tokens, not characters, and takes its idf over the whole table, so a search restricted to some kinds is scored against the corpus of all of them. Relevance scores its pool apart (```seon.doc/bm25```, its idf counted over the pool itself, each item's name counted twice): the two answer different questions, which texts of the whole program hold the request's words and which of a pool of near neighbours they tell apart. Scoring the pool by the index's bm25 instead ranked a changed item first in 14 of 49 dev tasks against 23 (the context lab's L0, 2026-11-02); a name column weighed in the index's bm25 brought it back only to 5 of 16 against 7. A hit's line is the first holding a word as written; a text that holds only the stem of it has none. Over 51 requests, paired, with meaning fused, FTS5 ranked a changed item first 22 times against 19 for a substring-matching index and in the top ten 40 against 39, with no paired loss (measured with a table of the kinds asked, not of all of them); `seon.context/relevance` stays in the fusion (without it a changed item ranks first 3 times to 11).

```seon.doc/text-index``` is the one index: two in-memory FTS5 tables over the same rows, one for each text of every text attribute (a form's source, a section's text, a task's plan, a schema entry's form), in one corpus (```seon.sqlite/fts-open```). `t` is `porter unicode61` and ranks; `g` is `trigram` and finds a substring, so `grep` with a string pattern of three characters or more asks it for the texts holding the pattern anywhere (inside a term, across a separator: "val-n" in `eval-n!`, "code-st" in `decode-string`), then matches lines exactly; a string under three characters, or a regex, has no trigram to ask for and reads every text. ```seon.sqlite``` is the one namespace that names libsqlite3 (macOS's own, `:seon.config.native/sqlite-lib`), bound on first use with ```seon.lib/defc``` like every C function here; the six calls a loop makes per text or row are locals of one macro (`ffi/cfn`, not vars, since every var is contracted: `bin/check contracts`), because a contracted call is recorded work: through `defc` the same build is 21 contracted calls and 7.5 KB of Clojure bytes a text (1,279 calls at 60 texts, 11,409 at 600) against none and 3.7 KB. A return code that is not OK is `:seon.sqlite/refused` with SQLite's words, and a library that will not load `:seon.sqlite/unloaded` ([failure points](failure-points.md)). The index is derived data ([cost](cost.md), AGENTS section 5): built once for a value of the db, regenerated from it whenever it is gone, never relied on. A move that writes a text attribute has that attribute's rows replaced in the held index (```seon.sqlite/replace-attrs!```, from `seon.doc/carry-index!`), reading its texts alone: a task's plan written on main reads the plans, not every form, which matters because a whole read evicts the fork server's node cache and every agent forked after it decodes its start cold (an agent's start was 13M against 6M until the replacement; ```seon.agent-test/an-agents-start-costs-the-same-however-long-its-root-has-run```). A write the held index was not carried to builds it again, whole. **Its memory is native**: the collector does not see SQLite's allocations, so `text-index` retires the index it replaces (```seon.sqlite/retire!```), which is closed at once when no reader holds it and by the last reader's release otherwise (readers go through `seon.sqlite/using`; one that meets a closed index asks `text-index` for the current one, ```seon.doc-test/a-superseded-index-is-closed-once-nothing-uses-it```). The collector closing an index nobody holds is only the backstop: 50 rebuilds on this repository grew the process by 256 MB of resident memory with the collector alone and by 1.9 MB with the retirement. One index is 28.6 MB of native pages (`dbstat`): 8.3 MB the porter table and 20.3 MB the trigram table. The cost proofs count the Clojure bytes and calls of a build and a query, never SQLite's memory. Built on this repository's 4,300 forms and 592 wiki sections: 54 ms for the porter table alone and 351 ms with the trigram table, once per move of main in the fork server and again for a db the index was not carried to. Measured text and references, mean of 8 requests worded as symptoms, against a substring-matching index: the index build 182.6M ticks, 495.8 MB and 5,653 contracted calls then, 2.06M ticks, 14.4 MB and 19 calls now; one `seon.context/search` 17.6M ticks and 78.1 MB then, 10.9M ticks and 35.0 MB now. Proofs: ```seon.doc-test/tokens-match-stems-and-whole-terms```, ```seon.doc-test/grep-finds-a-string-inside-a-term-as-grep-does```, ```seon.doc-cost-test/tokens-cost-the-texts-holding-the-word```, ```seon.doc-cost-test/search-costs-its-texts```, ```seon.doc-cost-test/a-text-index-costs-its-texts```.

**The index is built once, in the fork server, and carried by every move that writes no text.** `seon.fork-server/warm-start` builds main's index, so each agent forked inherits it (an in-memory SQLite database is plain memory, copy-on-write like the rest; the fork server is one thread, and `seon.lib/fork!` refuses to fork with another active, so nothing touches the connection while it forks); `seon.doc/carry-index!` keys the held index to the db a move made when the move wrote none of the text attributes. Its callers are the ones that know what a move wrote: an agent's `seon.agent/transact!` and its merge of main, and the fork server's commit of main. An agent's first `my.agent/grep` allocates what a second one does, and the inherited table answers in the forked child (```seon.agent-test/an-agents-first-search-reads-the-index-it-inherited```; the carry, ```seon.doc-test/a-text-index-is-carried-past-a-move-that-writes-no-text```).

**What search finds, measured on uncontaminated tasks** (the context lab's L0, 2026-11-01: 60 of Seon's own commits, each built at its parent, a symptom-only request written without naming code, `docs/plan.md`): `seon.context/search`'s top 10 by text and references held a changed item in 63% of 49 tasks; with meaning fused, a changed item ranked first in 18 of 43 against 4 (McNemar p = 0.0005) and was in the top 10 in 74%. Meaning ranks the change first rather than finding more functions (a changed function in the top 10: 53% against 51%). Neither reaches much of what the commit's own solver read (T2 area 0.019 for text and references).

**The request's search on the first page** (```seon.render.ui/searched```) is a part the agent's ctx holds: the request's text searched on the branch, a line a hit, each hit its name alone. A hit's first sentence added nothing a model used (names alone named a changed item in 33 of 49 tasks, names with first sentences 31, at about 650 more tokens a task; the context lab, 2026-11-02). It ranks by meaning only once its query has a vector: the request writes the search fact on main just before the agent forks, before main's vectors proc embeds it, so the agent's first turn embeds its task's searches' queries on its branch with its plan (```seon.agent/embed-written!```, ```seon.vector-test/a-requests-search-gets-its-vector-on-the-branch-before-the-first-page```); a query still with no vector draws its heading saying it was searched by its words (without meaning a changed item ranked first in 8% of tasks against 47%).

A branch's db value is a new object at every deref, indexes included, so `identical?` on `(:aevt db)` never hits: the index is keyed by `(:hash db)` with `(:max-tx db)`.

## Fused with the call graph

The task's data once listed the program functions nearest its plan by meaning (`:similar`): off since step 6 measured no gain (green 8 of 15 with five listed, 7 of 15 with none), and deleted on 2026-11-02, the request's search part showing what is near the request. Fusing the call graph's helpers (the cited vars' and proofs' one-hop callees, tf-idf) with the forms nearest a task's plan by reciprocal rank (```seon.vector/rrf```, k `:seon.config.vector/rrf-k`) was measured below; embeddings alone did as well, so the task's data uses them alone, and the fusion stays for further exploration.

Measured on 283 pairs from main's history (each non-merge commit's message as the plan; the functions its diff touched, still in the program, less those the message names, as what it needed), recall@10:

| ranking | all (283) | message names functions (166) | names none (117) |
|---|---|---|---|
| call graph | 0.042 | 0.071 | 0 |
| embeddings | 0.495 | 0.482 | 0.514 |
| fused, k 10 (k 60: 0.448) | 0.451 | 0.407 | 0.514 |

Fused beat the call graph alone, and embeddings alone (`my.agent/similar`) did as well as fused. Two biases run the other way from each other: the embeddings read each form as it is today, after the change its commit describes (flattering them), and a commit pair has no proofs, the call graph's richest source (understating it). v1 measured 0.274 / 0.386 / 0.441 on its own corpus. Weighting the two rankings is the lever if a task-shaped corpus shows embeddings alone ahead.

A call-graph neighbour weighs by its rarity, 1/(1 + the forms naming it, to 16): plain counts ranked first what every contracted form names (`seon.contract/checked`, `on?`, `seon.db/eid`), 26 of the 155 fused lines over 31 merged tasks; weighed so, none, at the same recall (R@5 0.343 by counts, 0.346 so, 0.353 by log IDF, which needs every form counted; `docs/vector.md`). [Relevance](#relevance) weighs a link to a seed the same way.

## Relevance

How relevant an item is to an agent's work is one calibrated number, the chance it is worth reading for that work (```seon.context/relevance```), the same scale for functions, sections and schema keys, so a search can cut on it: `my.agent/search` shows a hit with its chance from `:seon.config.render/relevance-summary` (0.4) and, below that, only a count with the call that lists it. The context is the plan's vector and words, the vars, sections and schema keys it cites (the seeds) and what the branch changed (the touched items); the items are those of one kind near it.

**The score.** For each kind (function, section, schema key), the pool is the `:seon.config.render/relevance-pool` (100) nearest by meaning (`seon.vector/near`), the seeds, and the seeds' neighbourhood in the reference graph (a form's calls, names and keys, the forms and sections naming its vars; a section's names, links, parent and children; a key's readers). Each item gets five features:
- `zc`, its cosine with the query, as a z-score over the pool;
- `zb`, its BM25 (```seon.doc/bm25```) for the query's identifier tokens (```seon.doc/terms```: `near-of` and `nearOf` are `near` and `of`), its idf counted over the pool itself, so no index of the store is read: what tells near neighbours apart (scored over every text instead, rank 1 fell from 23 to 14 of 49);
- `zt`, its cosine with the touched items' mean vector, a z-score;
- `g1`, the seeds it neighbours, each link weighed by its rarity, 17/(1 + its degree to 16);
- `ppr`, its personalized PageRank from the seeds, by local push (Andersen, Chung and Lang 2006) at `:seon.config.render/relevance-eps`.

A logistic over them, one weight set a kind (`:seon.config.render/relevance-weights`), gives a logit, fitted to what merges changed; a table per kind (`:seon.config.render/relevance-calibration`) reads it as the chance an independent judge finds the item worth reading.

**How it was chosen** (the relevance-lab worktree, 2026-10-27; scripts and the truth set in `docs/vector.md/`). The truth was what each merged branch changed: 279 merges of main, the 59 whose task entry held its plan used as held-out queries (57 with an item still on main), the 220 others as training queries made of their commits' subjects; what a plan cites left out of both its pool and its truth. Items were main's 5,072 texts (3,465 forms, 450 sections, 686 schema entries, 471 plans). Recall at 5 over the held-out plans, cold (the plan alone):

| design | functions (44) | sections (49) | schema keys (20) |
|---|---|---|---|
| cosine, the stored vectors (`title: none`, `code retrieval`) | 0.304 | 0.612 | 0.295 |
| cosine, titled documents and the `search result` prompt | 0.330 | 0.652 | 0.292 |
| BM25 alone, identifier tokens | 0.364 | 0.730 | 0.325 |
| reciprocal-rank fusion of BM25 and cosine | 0.392 | 0.745 | 0.292 |
| the page's related part before (rrf of the cited vars' callers and callees by rarity, and cosine) | 0.367 | 0.651 | 0.410 |
| contrastive adapter (query side, rank 32), fused with BM25 | 0.395 | 0.732 | 0.383 |
| **relevance: the logistic above** | **0.427** | **0.798** | **0.403** |

With three of each task's changed items given as touched (warm, the agent mid-work), relevance found 0.481 of the rest of the functions, 0.837 of the sections and 0.326 of the keys, against 0.301, 0.697 and 0.160 by cosine alone: the touched items' neighbourhood and mean vector are where a working agent's next need is.

What lost, measured:
- **The 128-dim prefix as the ranking.** Sections 0.48 against 0.65 at 768 (functions 0.22 against 0.33); 256 dims ranked within 0.03 of 768. The Matryoshka prefix stays what it is good for, the coarse level that shortlists ([the pyramid](#the-pyramid)); the ranking is at full width over a pool of a hundred, where it costs one f16 row an item.
- **A contrastive adapter** over the frozen vectors (q' = q + B C q, rank 32 or 64, query side only so no document is embedded again; InfoNCE with in-batch and hard negatives). Trained on the graph's edges (calls, names, citations, a plan's citations), it lifted the 20 search queries (functions 0.32 to 0.48 on the old vectors) but cost the plans (0.28 to 0.19). Trained on 6k query-shaped pairs (commit subjects to what each merge changed), it lost on titled vectors too (sections 0.65 to 0.50, the 20 queries' functions 0.59 to 0.46) and gained only schema keys (0.29 to 0.38). There are too few query-shaped pairs yet; agents' searches and what they then read are the source to train it on.
- **Gradient-boosted trees** over the same features ranked below the logistic (functions 0.39 against 0.44): the features are near linear in the logit, and a weight set is data.
- **BM25 over names alone**, which needs no texts: below no lexical feature at all (functions 0.40, sections 0.67).
- **A 2-hop count** beside the PageRank: no gain, and the push at 1e-4 (376 nodes a plan) ranked no better than at 1e-3 (37 nodes).
- **Plain link counts**: 20 of 570 function lines were plumbing (`seon.contract/checked`, `seon.db/eid`); weighed by rarity, 1, at the same recall.

**Calibration: worth reading, not changed.** Fitted to what a merge changed, a chance meant the wrong thing for an agent: a function holds a few percent by base rate (a plan changes ~16 of 2,000), so on the 57 held-out tasks' pages, drawn by an outside agent through the related part the page then had, a 5% cut showed about two functions a task (recall at 5 of what the merge changed: 0.27 cut against 0.44 uncut) and its 5-20% band was mostly noise. An independent judge (Sonnet) labelled the first five of each kind on every page and on the 20 search queries, 1,185 lines, useful or noise ("an agent doing this work would read or change it"); the merge-change truth called 0.43 of the lines at 20% or more useful where the judge called 0.89. Per kind, sigmoid(a log c + b) over the merge-change chance c, cross-fitted by halves of the tasks, predicted 0.72 / 0.80 / 0.78 for the top band and the judge found 0.73 / 0.80 / 0.80 (functions, sections, schema keys), 0.26 / 0.16 / 0.20 at the bottom for 0.24 / 0.16 / 0.19. At 0.4 the shown lines were useful 0.57 / 0.66 / 0.68 of the time, at 0.6 0.73 / 0.80 / 0.80: those are the cuts. On the same agent's run after the change, the page showed about 8 lines a task (3.6 at doc depth) and found 0.52 of what the merges changed (0.48 before), functions 51 of 382 against 31; the 20 queries found 0.56 of their answers in the first ten above 0.4 (0.30 before), functions 22 of 45 against 3. The chance below each kind's fifth item is extrapolated (no label there), and the judge's labels are the calibration's only source until searches' opens join them. Judged again on 20 fresh pages the calibration never saw (merges whose commit subjects were the work, drawn at the cuts): lines at 60% or more were useful 33 of 41 (0.80), at 40-60% 47 of 82 (0.57); sections 0.77, functions 0.71, schema keys 0.40. Within functions the score separates useful from noise weakly (on those pages a useful function's median chance 54%, a noisy one's 49%; sections 66% and 47%): on the 1,278 judged lines a logistic refitted to the judge's labels over the same features reached AUC 0.738 for functions against the shipped 0.719 (sections 0.790 against 0.786), and the query's words in the item's namespace, the same namespace as a seed or the cosine to the seeds' mean vector lifted it at most to 0.749 (`docs/vector.md`). A local cross-encoder over each kind's first twenty was then measured and left out: bge-reranker-v2-m3 (Q8_0, by the pinned llama.cpp) scored AUC 0.61 on 1,133 of the judged lines against the shipped 0.72 / 0.79 / 0.68, and 0.72 / 0.76 / 0.68 summed with it, at 52 ms a pair and 1.5 GB resident (`docs/vector.md`).

**Under the work's focus.** The page once ranked against the work, not the plan alone: the plan's vector first, then each of the agent's evals, decayed with a half-life of one item. The judge labelled each kind's first five at 48 moments of 10 recorded runs, 720 lines more; the scale fitted on plan pages was overconfident there (its 60% band 0.56 useful). Refitted on all 1,905 lines as one table and cross-fitted, the 60% band holds in both states: plan pages 0.76 / 0.86 / 0.70 useful, the work's 0.76 / 0.81 / 0.67 (functions, sections, schema keys); a term for the state moved nothing at the cut. Search takes the query's vector, so a caller wanting the work's direction passes it.

**Cost.** A call costs `near`'s scan of the coarse rows (linear in the store, [the pyramid](#the-pyramid)) and a part bounded whatever the store's size: the pool (`relevance-pool` nearest a kind, the seeds, each seed's first `relevance-pool` neighbours by each read, and what the push reached), each item its vector's seek and its text tokenized once (```seon.doc/terms```, one pass over its characters); at most 1/(alpha eps) pushes, a node's degree counted by seeks to `:hub` before its neighbours are read, and a hub never read whole. On Seon's own store (5,095 texts, load about 20): relevance over the three kinds for a plan citing two vars took 115 ms, 54M ticks and 132 MB (the push 18 ms and 36 MB, from 65 ms and 114 MB before the hub bound and the counts; the pool's tokens 26 ms; each kind's `near` 10-18 ms). ```seon.context-cost-test/a-push-reads-what-its-threshold-reaches``` (a ring) and ```seon.context-cost-test/a-push-counts-a-hub-and-reads-it-not``` (a var n forms name) hold the push flat in the store's size; At 40,000 texts the bounded part stays; near's scan, about 5 KB a vector, is the part that grows (its lever: the coarse rows kept as one buffer per db value).

Not measured: whether an agent reads what the cut shows more often, or reaches green in fewer turns (a paid comparison); a z from the kind's coarse moments, which the C kernel could answer in its scan, scored schema keys 0.36 against the pool's 0.28 and is not built.

## What the work is likely to need, as an eval

A task that starts from a request holds a search of the request's words (`:seon.search/search-fact`, written by ```seon.template/request-tx```), and its page draws it as a part (```seon.render.ui/searched```, [render](render.md#a-search-is-a-part)): what the work is likely to need, found by `seon.context/search` on the branch's db, ranked by `seon.context/relevance`. Measured 2026-11-01 on 49 changes from Seon's own history, each request written from its diff by an agent told to name no code and searched on the change's parent: a changed definition, section or schema entry ranked first in 41% of them and in the top ten in 78%, where the request's first page otherwise showed no code; by words and references alone, first in 8% (paired, 20 against 4 tasks, McNemar p = 0.00014). Given the ten hits' names, deepseek-flash named a changed item among its five in 30 of 49, against 2 without them (p = 7.5e-9); with each hit's first sentence, 33 (+445 tokens, p = 0.25). Expanding from the hits by the call graph found little: two hops reach about the whole program, and the top 50 of a degree-weighted walk added about 16% of what changed. The three earlier sessions nearest the request by meaning, their changed and read items as hits, ranked a changed item first in 6% and in the top ten in 31% (paired against search, 1 against 24, p = 1.5e-6). What an earlier related part's comparison measured stays below.

Before relevance, the two rankings were fused by reciprocal rank (```seon.vector/rrf```), which found more of what 31 merged tasks changed than either alone: functions 0.51 at 5 against 0.38 by meaning alone, sections 0.71 against 0.67, schema keys 0.56 against 0.37; tasks were weak by every method and stay a query (`my.agent/similar`). Ranking by each sentence of the plan and fusing them did not help on those tasks (2026-10-25, 6.9 sentences a plan, with the graph and what the plan cites left out): functions 0.37 at 5 against 0.39 by the whole plan (1 task better, 3 worse), sections 0.73 against 0.77 (`docs/vector.md`), though on the live round 5's one-line big-map request it lifted `seon.print.select/first-at-least` from 13th to 2nd: a short request's own words seed it, a plan's whole text ranks better than its parts. Beside each function, the registry keys its code and contract name (its `:form/keywords`, one EAVT seek) took record keys from 0.31 to 0.53 at 5 for about 74 tokens, more than the next five keys (0.48); the other way, a key's functions (one AVET seek, `seon.doc/callers`), added 0.50 to 0.50 for about 400 tokens, and is not shown. The comparison, its biases and its data: `docs/vector.md`.

### What was compared, and what it left out

Related search was compared on 31 merged tasks (truth: what the merge changed, 9.3 functions, 4.3 sections, 3.3 schema keys a task) by embedding, the reference graph, grep (the plan's words of five letters or more) and their fusions, scored by recall at 5 and 10 and the printer's token estimate; the data and scripts stay in `docs/vector.md/`.
- **Grep is left out of the screen:** it helped sections only at 10 (all three methods fused: 0.89), costs a stop-word list, and the screen shows 5; `my.agent/grep` stays a query. Tasks are weak under every method (0.28 at best, by embedding), since what a merge changes in other tasks is mostly follow-ups its plan does not predict, so they stay a query (`my.agent/similar`).
- **A function's schema keys earn their tokens, a key's functions do not.** Adding the record keys the top 5 functions name lifted recall 0.31 to 0.53 for 74 tokens (the next five fused keys: 0.48), and the attributes they name 0.06 to 0.46 for 47; the functions naming the top 5 keys added almost nothing for 404 tokens. The db stores no such edge: `:form/refs` holds vars only, and `seon.program/schema-dependents` decodes every contract per call. The smallest fact that would store it is `:form/keywords` (the qualified keywords a form's code and contract name), an indexed set that makes a function's keys one EAVT seek and a key's functions one AVET seek; it awaits root's gate.
- **Other agents' work** (merged tasks that changed the same var or section, 3.9 partners for 28 of 32 tasks) is found by plan text at recall 0.28 at 3 and 0.40 at 5, 2.5x chance; embedding producer text (merge subject, changed names) adds 2 to 3 points, too little for a new kind of text.
- **Rendered hiccup is not embedded** (root, 2026-10-25): about five new records a turn at 400 to 2,000 tokens each is 2 to 10k tokens embedded per turn, none reusable, more than every other source together; renders as definitions (the `seon.render.*` forms are already embedded) and others' plans give the sharing for a fraction of it.
- **Biases:** the db is main after the merges, which flatters embedding and grep; truth is what a merge changed, not what its worker read, which understates every method; recall only, no precision.
