# Vectors

Semantic search is native to the store and its query language: each form's, wiki section's, schema entry's and task plan's text is embedded once by a small local model in a helper process of root's, its vector is kept as facts on an entity of its own pointing at it ([a vector is its own entity](#a-vector-is-its-own-entity)), and `seon.vector/near` is a Datalog function, so similarity is one more relation a query joins. An agent asks it at its REPL (`my.agent/similar`). The ruling is DECISIONS "Embeddings join the context: fused, small and measured".

```clojure
[(seon.vector/near $ ?q 10 {:of :form/id}) [[?e ?score]]]   ; ?q an entity with a vector, or a vector
```

## The model

EmbeddingGemma-2 (768 dims, Matryoshka, mean-pooled, normalized) runs in process through llama.cpp: `native/embed.c` puts its encoder behind a C ABI of pointers and ints (open, embed a batch of texts given as one UTF-8 buffer and offsets, close), and `bin/build embed` builds llama.cpp v0.7.0 from `reference-code/llama.cpp` (static, Metal, no OpenMP) with it into `target/lib/libseon-embed.dylib`. The model file is ggml-org's Q8_0 GGUF, fetched once by `bin/build` into the main tree's `target/cache/models/`, named by its sha256 and checked against it (`bin/env`'s `SEON_EMBED_MODEL`); its name, with the version of the texts it embeds, is the model's id on every vector (`seon.vector/model-id`), and `bin/env` is the one place the pin is written (`:seon.config.vector/model` reads it), so a model change makes every vector due again. Nothing is installed outside `target/`; cmake is the one added prerequisite.

The model runs in an exec'd helper, not in root and not in a fork. ggml and Metal start threads, and Apple's runtime aborts a process forked from a threaded one that touches them ([failure points](failure-points.md#physics-who-may-run-threads)), so `target/seon embed-worker` (```seon.vector/serve!```, a mode of the one binary) loads the library and the model (```seon.vector/open-model```) and answers framed requests on its pipes. Root's side is the `:embed` effect kind (`resources/seon/system.edn`), a batch kind with one worker; its host object (```seon.vector/open```) is a handle with no process in it:

- **Start.** The first batch of a spell of work starts the helper (```seon.vector/start!```: `ProcessBuilder` over this checkout's `target/seon embed-worker` and root's `--config` and `--set` layers, so it reads root's config) and waits for its first frame, `{:ready {:dims n}}` or `{:error e}` (the model missing or unloadable: `:seon.vector/model-unopened`).
- **Protocol.** The frames are `seon.sock`'s ([u32 length][fasl body]), written with ```seon.sock/frame``` and read from the pipe with ```seon.sock/recv-stream!```. A request is `{:texts [...]}` (every text of the batch's requests, in order, one request in flight), the answer `{:vectors [[x ...] ...] :tokens [n ...]}` or `{:error e}` (`:seon.vector/encode-failed`); ```seon.vector/embed``` splits it back to its requests' `{:value {:model :vectors :tokens}}`, the same data in root and across an agent's socket. A search's query is an ordinary request, so every asker (the vectors proc, an agent's turn, `my.agent/search` and `related`) goes through the one effect.
- **Stop.** When the owner's queue is empty and nothing is in flight, the owner tells its worker `{:idle true}` (```seon.fx/owner-proc```, for a kind declaring `:close`), and the worker calls ```seon.vector/close```: the helper's stdin is closed, it reads the end of its input and exits 0, and its pid, exit status and start and exit stamps are the worker's facts (the ping's `:closed` and `:host`). That event is the only thing that ends a helper in service; no clock does. A request that says `:more` (main's backlog: the vectors proc asks the next round when this one's vectors are written) keeps it up until its last round. The helper also ends with root (`seon.lib/end-with!` on its parent), and a request that arrives after the close starts another.
- **Death.** A helper that dies is its pipe's EOF: every request of the batch in flight is answered `:seon.vector/helper-died` (`:exit`, `:stderr`) and the next batch starts a new one (```seon.vector-test/a-helper-killed-mid-batch-answers-an-error-and-the-next-batch-works```). A helper left up on a `:more` that never came waits for the next request or root's end, holding its memory.

Measured 2026-10-29 on a scratch root (a new store, 5,593 texts at boot, machine load 11-16, M5 Max): root's footprint after the backlog was 1,675 MB with the model in process and 1,128-1,149 MB with the helper, which is gone (no process, no `.gguf` in root's `lsof`) once the queue emptied (```seon.vector-test/root-holds-no-model-after-an-embed```). The backlog took about 70 s either way with `:more` (one helper for all 89 batches); without it, a helper per round took about 210 s, which is what an idle root pays per request: a search on an idle root waited 1.24 s (start, load and query, at load 14; 0.45 s on a quiet machine, 3.7 s for the first load of a session) and a warm query 7 ms. While it runs, the helper holds 350-550 MB, and none of it once it has exited: closing the model inside a process left about 180 MB (the Metal driver) behind.

The model is EmbeddingGemma-2 (768 dims, Matryoshka, mean-pooled, normalized) through llama.cpp: `native/embed.c` puts its encoder behind a C ABI of pointers and ints (open, embed a batch of texts given as one UTF-8 buffer and offsets, close), and `bin/build embed` builds llama.cpp v0.7.0 from `reference-code/llama.cpp` (static, Metal, no OpenMP) with it into `target/lib/libseon-embed.dylib`. The model file is ggml-org's Q8_0 GGUF, fetched once by `bin/build` into the main tree's `target/cache/models/`, named by its sha256 and checked against it (`bin/env`'s `SEON_EMBED_MODEL`); its name, with the version of the texts it embeds, is the model's id on every vector (```seon.vector/model-id```), and `bin/env` is the one place the pin is written (`:seon.config.vector/model` reads it), so a model change makes every vector due again. Nothing is installed outside `target/`; cmake is the one added prerequisite. One batch is embedded in encodes of at most `:seon.config.vector/batch-tokens` tokens and `:seon.config.vector/batch-texts` texts, and the kind takes up to `:seon.config.vector/batch` queued requests in a step. The open model keeps 4 threads (Metal's) beside the helper's own, and its load runs ~32 more until it has loaded (all in the helper); ggml's CPU pool is `:seon.config.vector/threads` (1: Metal does the encode). `bin/check scale` holds root's `seon.lib/real-mb`, the fork server's and the agents' within the 4,096 of `:seon.config.machine/memory-mb`; the helper is outside that sum while it runs, at most about 0.6 GB.

Memory with the model loaded in a process (macOS footprint, measured 2026-10-29, idle): 1,641 MB against 1,262 MB without it; of the 224 MB of malloc, 206 MB is llama.cpp and Metal, allocated once by `seon_embed_open` (the tokenizer's vocabulary 83.5 MB in 787 k blocks, ggml's scheduler 66.9 MB, Metal's shader cache 30 MB), with no leak seen; `:seon.config.vector/batch-tokens` 4,096 also maps 721 MB of virtual Metal buffers (210 MB at 1,024).

Measured on Seon's 1,393 src forms (M5 Max, Metal, machine load ~10): the model opens in 3.7 s; one text takes 5-15 ms warm; batched, 37k tokens/s (175 texts/s) at a 4,096-token encode (512: 122/s, 1,024: 167/s), 0.86 GB RSS; the BF16 file is no faster (34k tokens/s). v1 ran the same model in MLX over HTTP (5.7 ms one text, 66-105k tokens/s batched on short texts). mistral.rs (ericlbuehler/mistral.rs at `f512686`) was evaluated and not used: it has no EmbeddingGemma-2, did 32 texts/s on Qwen3-Embedding-0.6B in its place, and brings tokio and 461 crates.

## What is embedded

Each kind's text is its attribute's value with the model's prompt: a form's `:form/src` titled by its var's name, a section's `:seon.section/text` by its heading and a schema entry's `:schema/form` by its key, as documents (```seon.vector/document```: the model card's title slot), a task's `:seon.task/plan` as what a search asks (`seon.vector/query-prompt`, the card's `search result`). Titled, with that prompt, 20 search queries found 0.58 of their functions and sections at 5 against 0.44 untitled with `code retrieval` ([relevance](#relevance)); the texts' version is part of every vector's model id (```seon.vector/model-id```), so a change to them makes every vector due once. A title changed with its text unchanged (a heading edited alone) keeps the vector of the old title until the text changes: a vector is due by its text's transaction, not its title's. A text over `:seon.config.vector/max-tokens` keeps its first tokens, and special-token text in it is read as text. A vector is five facts on the entity: `:seon.vector/f16` (the whole vector), `:seon.vector/coarse` (the [coarse level](#the-pyramid)), `:seon.vector/model`, `:seon.vector/text-t` (the transaction of the text it embeds) and `:seon.vector/tokens` (the text's whole token count: past the bound, what was left out).

`seon.vector/due` lists the texts whose vector is missing, made from an earlier text (its `:seon.vector/text-t` is not the text's transaction, so a text changed while its round was out stays due) or another model's. A form is content-addressed, so its text never changes and it is embedded once; a superseded form is retracted, and the proc retracts its vector (below). `seon.vector/vectors-proc` keeps main current: at the writer's commit notice it sends the first `:seon.config.vector/texts` due to `:embed` and writes their vectors to main through the writer; that commit's notice starts the next round, so a backlog is embedded round by round and an idle main asks nothing. Once a round has asked for everything due, the proc is caught up (`:clean`, the commit it was asked at: a reference `{:t :commit}`, the base db made from it with `seon.db/at-commit` (`d/commit-as-db`: about 100k ticks and 440 KB a round) when a round diffs, never a kept db value; [machine](machine.md#what-a-process-owns-in-memory)) and its next rounds look only at the texts the commits since changed (`seon.vector/written`, a `datoms-diff`: the cost of the commit, not of the store); the first round, a backlog, a failure and a restart scan every text. A failed embedding is root's problem (the effect owner records it) and the next notice tries again; texts llama.cpp could not encode are kept out of later rounds (the proc's `:unembeddable`, in its ping), so they never hold back those due after them. Seon's whole text (2,681 texts: 1,783 forms with the schemas, 321 sections, the task plans) embeds in 17-19 s at boot. An agent's branch reads main's vectors as of its fork, and embeds its own writes: at each turn's observe (```seon.agent/embed-written!```) the forms, sections and plans the branch wrote since the last turn (```seon.vector/written```, a `datoms-diff` from the db it last read: the cost of what changed) and its task's plan, those due, go to root's `:embed` in one request over the agent's socket (the model stays in its helper, root's), and their vectors are written on the branch; a turn that wrote nothing due asks nothing, and a failed embedding is the effect's recorded error with the texts still due. A merge carries no `:seon.vector/*` facts (they are platform records, `seon.merge/carried-tx`): main's `vectors-proc` embeds the merged texts again at the merge's commit notice, as it does any text new on main.

## A vector is its own entity

An entity's record is facts about its work, and an embedding is derived data (owner, 2026-10-29: "Telemetry and derived data live on their own entities, pointing at what they describe: a vector at its eval"). So a vector is not written on the form, section, plan or eval it embeds, where `*` pulled it into an agent's record and its diff showed it each time it was written: it is an entity `{:seon.vector/of e :seon.vector/model :seon.vector/text-t :seon.vector/tokens :seon.vector/f16 :seon.vector/coarse}` (```seon.vector/fact```), and the embedded entity's own pull holds none of it (`seon.vector-test/a-vector-is-its-own-entity`).

Its identity is `:seon.vector/of`, a unique-identity ref: one vector entity for each embedded entity, and writing a vector again (a changed text, another model) upserts that entity in place. A composite `[of model]` tuple (Datahike's `:db/tupleAttrs`) would keep a vector of each model, which nothing reads (a vector of another model is due again and replaces the old), and would add a tuple datom to every vector; one identity attribute is the means Datahike gives for exactly this. `due` and `vector-of` find a vector by one AVET seek of `:seon.vector/of`; `near` merge-joins its two scans (`:seon.vector/of` and `:seon.vector/coarse`, both in vector-entity order: advance the smaller, emit when equal), so a row costs one datom read more (measured 2026-10-29 at 1,000 vectors: 5.16 MB to 5.22 MB; `seon.context/related`, which makes three searches, 12.8 MB to 14.2 MB at 1,000 sections). Retracting an embedded entity (a superseded form: `seon.program`, `seon.source`, `seon.merge`) drops the `:seon.vector/of` datom that pointed at its vector and leaves the vector's facts (about 1.6 KB) behind. `seon.vector/vectors-proc` retracts them: each round reads one `datoms-diff` from the previous round's commit (`:seen`), which gives the texts added (what is due) and the datoms removed, and `seon.vector/orphaned` turns each removed `:seon.vector/of` the db does not hold again into retractions of that vector entity's `:seon.vector/*` facts, written with the embeddings, or alone when nothing is due. The diff is from the previous round, not from `:clean`, which is the commit before the proc's own write; a vector written and orphaned between two rounds that skipped a commit is retracted by the next full scan (a round with no `:seen`, after a start or a failure, finds every coarse row with no `:seon.vector/of`). Round cost unchanged: 302 k ticks / 1.01 MB / 15 calls at 100 texts, with one diff doing both jobs (`seon.vector-test/a-retracted-entitys-vector-is-retracted-by-the-round`).

A store that holds vectors written on their entities by an earlier version keeps them there: they have no `:seon.vector/of`, so no reader finds them, every text is due again and is embedded onto a vector entity; erasing the store drops the old ones from a pull (the standing store is test data).

## The pyramid

A Matryoshka vector's prefix is itself an embedding, so one stored vector serves two levels (`native/vector.c`, in libprobe: no threads, every process loads it). The coarse row is the first `:seon.config.vector/coarse-dims` dims renormalized and scaled to int8, with its scale (`seon.vector/pack`); the coarse level scans every row with integer dot products and keeps the best `:seon.config.vector/shortlist` in a heap; the fine level ranks those at f16 over `:seon.config.vector/fine-dims` dims, each prefix renormalized. A query option changes either (`{:shortlist n :fine-dims d}`); a shortlist of every vector is the exact search. `near` reads the coarse rows from the db value each call (no cache: a db value is its own index), copies them into one buffer, and reads only the shortlist's f16 rows.

Recall@10 against the exact 768-dim search:

| corpus | coarse | shortlist | fine | recall@10 |
|---|---|---|---|---|
| Seon's whole text, 2,681 (`bin/check vectors`, 207 queries) | 128 | 50 / 100 / 200 / 400 | 768 | 0.946 / 0.979 / 0.990 / **0.998** |
| src forms, 1,393 (every form a query) | 64 / 128 / 256 | 100 | 768 | 0.945 / 0.9975 / 1.0 |
| src forms | 128 | 100-400 | 256 | at most 0.83 |

The C levels take 0.08 ms at 1,393 vectors and 0.31 ms at 100k (v1's f32 brute force: 4.1 ms at 100k; em1's kernel 0.39 ms at 10k). The whole `near` in Jolt takes 1.9 ms at shortlist 100 and 4.6 ms at 400 on 1,737 vectors, nearly all of it the datom reads and copies; at 100k those would cost about 20 ms (estimated), the next lever if a store grows that large. `bin/check vectors` proves the default on Seon's own text each run, and `seon.vector-test/the-pyramid-ranks-as-an-exact-search` on made Matryoshka-shaped vectors. Proximum's HNSW was rejected in v1 (1.6-4.3 MB per commit, recall 0.16-0.62).

## Search

The text ranking of `my.agent/search` is BM25 over the identifier terms of a query (```seon.docs/tokens```). It reads postings, not the corpus: ```seon.docs/text-index``` holds for each text attribute (a form's source, a section's text, a task's plan, a schema entry's form) the `seon.docs/terms` of every text and how many times each occurs, with each text's length. A query word counts in every term that contains it (`fus` in `fused`), found by a scan of the attribute's vocabulary, and the texts that hold it come from the term's postings; the idf, the average length and the z-score's mean come from the index's counts, so a text holding no query word is never touched. A word across a camel-case boundary (`onr` in `SeonRun`) is no longer a match, nor is one across a separator or digit, and a term holding the word twice (`fusefuse`) counts it once, where the scan of a lower-cased text counted each non-overlapping occurrence. A hit's line is still the first substring match in its text.

The index is derived data ([cost](cost.md), AGENTS section 5): built once for a value of the attribute's `:aevt` index (one slot an attribute, replaced by the next change), regenerated from the db whenever it is gone, never relied on. A change to a text attribute rebuilds that attribute's postings (4.5 KB and one call a text); folding only the changed texts in is the next lever. Measured 2026-10-28 with ten texts of each kind holding the word: `tokens` 1.66 MB and 132 calls at 100 texts and at 300, 1.83 MB at 1,000 (the vocabulary scan, about 190 bytes a text), and a whole `search` 2.70 MB at 100 and 2.88 MB at 1,000, where the scan of every text cost 16 KB a text (67.68 MB at 4,000). The relevance pool's `seon.docs/bm25` is the same ranking over its own small corpus, with no index. Proofs: ```seon.docs-cost-test/tokens-cost-the-texts-holding-the-word```, ```seon.docs-cost-test/search-costs-its-texts```, ```seon.docs-cost-test/a-text-index-costs-its-texts```.

A branch's db value is a new object at every deref, indexes included, so `identical?` on `(:aevt db)` never hits: the index is keyed by content, or by `(:hash db)` with `(:max-tx db)`. Keying it by a fingerprint of the attribute's datoms costs about 950 B a text on every call and bent the cost proof to n^2.31 (```seon.docs-cost-test/tokens-cost-the-texts-holding-the-word```) until the fingerprint was skipped for an unchanged db.

## Fused with the call graph

The task's data shows `:similar` (```seon.context/similar```): the first `:seon.config.render/similar` program functions nearest the plan's vector, by an exact search (`near` with every vector its shortlist, at every dim), that the plan and proofs do not name, a line each. On Seon's own program (3,843 vectors) it costs about 9.7M ticks and 52 MB (40 ms) and 397 of a task's data's 1,749 tokens; ```seon.vector-cost-test/similar-ranks-every-form-once``` holds it. Step 6 measures how often agents read one; 0 turns it off. Fusing the call graph's helpers (the cited vars' and proofs' one-hop callees, tf-idf) with the forms nearest a task's plan by reciprocal rank (```seon.vector/rrf```, k `:seon.config.vector/rrf-k`) was measured below; embeddings alone did as well, so the task's data uses them alone, and the fusion stays for further exploration.

Measured on 283 pairs from main's history (each non-merge commit's message as the plan; the functions its diff touched, still in the program, less those the message names, as what it needed), recall@10:

| ranking | all (283) | message names functions (166) | names none (117) |
|---|---|---|---|
| call graph | 0.042 | 0.071 | 0 |
| embeddings | 0.495 | 0.482 | 0.514 |
| fused, k 10 (k 60: 0.448) | 0.451 | 0.407 | 0.514 |

Fused beat the call graph alone, and embeddings alone (`my.agent/similar`) did as well as fused. Two biases run the other way from each other: the embeddings read each form as it is today, after the change its commit describes (flattering them), and a commit pair has no proofs, the call graph's richest source (understating it). v1 measured 0.274 / 0.386 / 0.441 on its own corpus. Weighting the two rankings is the lever if a task-shaped corpus shows embeddings alone ahead.

A call-graph neighbour weighs by its rarity, 1/(1 + the forms naming it, to 16): plain counts ranked first what every contracted form names (`seon.contract/checked`, `on?`, `seon.db/eid`), 26 of the 155 fused lines over 31 merged tasks; weighed so, none, at the same recall (R@5 0.343 by counts, 0.346 so, 0.353 by log IDF, which needs every form counted; `docs/vector.md`). [Relevance](#relevance) weighs a link to a seed the same way.

A plan that cites no defined var (a user's request in prose) has no call graph of its own, and the functions nearest it by meaning are mostly not the program's: near a request, the forms nearest are its tests (for the request about a mixed collection, 19 of the 20 candidates `:seon.config.render/related-near` reads). So the graph's half starts from the first program functions among the `:seon.config.render/related-seeds-near` (50) forms nearest the plan, and fuses their callers and callees, by rarity, with meaning. On the 8 requests of the design-build run db1, each true site in the page's functions (cited, or related's five): 4 of 8 with no seed, 5 seeded from the 20 candidates, 6 from the 50 nearest forms (200: 6). The two it misses (a proof that never ran, a map's first entry) describe behaviour main had already fixed: the instructions' reproduce-first step finds that, not the page (`seon.context-test/a-prose-requests-functions-come-from-its-nearest-and-their-neighbours`).

## Relevance

How relevant an item is to an agent's work is one calibrated number, the chance it is worth reading for that work (```seon.context/relevance```), the same scale for functions, sections and schema keys, so a page can cut on it: the related part shows an item at doc depth from `:seon.config.render/relevance-doc` (0.6), a line with its chance from `:seon.config.render/relevance-summary` (0.4), and below that only a count with the form that lists it (`(my.task/related 0)`). The context is the plan's vector and words, the vars, sections and schema keys it cites (the seeds) and what the branch changed (the touched items); the items are those of one kind near it.

**The score.** For each kind (function, section, schema key), the pool is the `:seon.config.render/relevance-pool` (100) nearest by meaning (`seon.vector/near`), the seeds, and the seeds' neighbourhood in the reference graph (a form's calls, names and keys, the forms and sections naming its vars; a section's names, links, parent and children; a key's readers). Each item gets five features:
- `zc`, its cosine with the query, as a z-score over the pool;
- `zb`, its BM25 (```seon.docs/bm25```, the one text ranking, search's too) for the query's identifier tokens (```seon.docs/terms```: `near-of` and `nearOf` are `near` and `of`), its idf counted over the pool itself, so no index of the store is read;
- `zt`, its cosine with the touched items' mean vector, a z-score;
- `g1`, the seeds it neighbours, each link weighed by its rarity, 17/(1 + its degree to 16);
- `ppr`, its personalized PageRank from the seeds, by local push (Andersen, Chung and Lang 2006) at `:seon.config.render/relevance-eps`.

A logistic over them, one weight set a kind (`:seon.config.render/relevance-weights`), gives a logit, fitted to what merges changed; a table per kind (`:seon.config.render/relevance-calibration`) reads it as the chance an independent judge finds the item worth reading.

**How it was chosen** (the relevance-lab worktree, 2026-10-27; scripts and the truth set in `docs/vector.md/`). The truth was what each merged branch changed: 279 merges of main, the 59 whose task entry held its plan used as held-out queries (57 with an item still on main), the 220 others as training queries made of their commits' subjects; what a plan cites left out of both its pool and its truth. Items were main's 5,072 texts (3,465 forms, 450 sections, 686 schema entries, 471 plans). Recall at 5 over the held-out plans, cold (the plan alone):

| design | functions (44) | sections (49) | schema keys (20) |
|---|---|---|---|
| cosine, the stored vectors (`title: none`, `code retrieval`) | 0.304 | 0.612 | 0.295 |
| cosine, titled documents and the `search result` prompt | 0.330 | 0.652 | 0.292 |
| BM25 alone, identifier tokens | 0.364 | 0.730 | 0.325 |
| reciprocal-rank fusion of BM25 and cosine | 0.392 | 0.745 | 0.292 |
| the related part before (rrf of the cited vars' callers and callees by rarity, and cosine) | 0.367 | 0.651 | 0.410 |
| contrastive adapter (query side, rank 32), fused with BM25 | 0.395 | 0.732 | 0.383 |
| **relevance: the logistic above** | **0.427** | **0.798** | **0.403** |

With three of each task's changed items given as touched (warm, the agent mid-work), relevance found 0.481 of the rest of the functions, 0.837 of the sections and 0.326 of the keys, against 0.301, 0.697 and 0.160 by cosine alone: the touched items' neighbourhood and mean vector are where a working agent's next need is.

What lost, measured:
- **The 128-dim prefix as the ranking.** Sections 0.48 against 0.65 at 768 (functions 0.22 against 0.33); 256 dims ranked within 0.03 of 768. The Matryoshka prefix stays what it is good for, the coarse level that shortlists ([the pyramid](#the-pyramid)); the ranking is at full width over a pool of a hundred, where it costs one f16 row an item.
- **A contrastive adapter** over the frozen vectors (q' = q + B C q, rank 32 or 64, query side only so no document is embedded again; InfoNCE with in-batch and hard negatives). Trained on the graph's edges (calls, names, citations, a plan's citations), it lifted the 20 search queries (functions 0.32 to 0.48 on the old vectors) but cost the plans (0.28 to 0.19). Trained on 6k query-shaped pairs (commit subjects to what each merge changed), it lost on titled vectors too (sections 0.65 to 0.50, the 20 queries' functions 0.59 to 0.46) and gained only schema keys (0.29 to 0.38). There are too few query-shaped pairs yet; agents' searches and what they then read are the source to train it on.
- **Gradient-boosted trees** over the same features ranked below the logistic (functions 0.39 against 0.44): the features are near linear in the logit, and a weight set is data.
- **BM25 over names alone**, which needs no texts: below no lexical feature at all (functions 0.40, sections 0.67).
- **A 2-hop count** beside the PageRank: no gain, and the push at 1e-4 (376 nodes a plan) ranked no better than at 1e-3 (37 nodes).
- **Plain link counts**: 20 of 570 function lines were plumbing (`seon.contract/checked`, `seon.db/eid`); weighed by rarity, 1, at the same recall.

**Calibration: worth reading, not changed.** Fitted to what a merge changed, a chance meant the wrong thing for an agent: a function holds a few percent by base rate (a plan changes ~16 of 2,000), so on the 57 held-out tasks' pages, drawn by an outside agent through `related` as the page draws them, a 5% cut showed about two functions a task (recall at 5 of what the merge changed: 0.27 cut against 0.44 uncut) and its 5-20% band was mostly noise. An independent judge (Sonnet) labelled the first five of each kind on every page and on the 20 search queries, 1,185 lines, useful or noise ("an agent doing this work would read or change it"); the merge-change truth called 0.43 of the lines at 20% or more useful where the judge called 0.89. Per kind, sigmoid(a log c + b) over the merge-change chance c, cross-fitted by halves of the tasks, predicted 0.72 / 0.80 / 0.78 for the top band and the judge found 0.73 / 0.80 / 0.80 (functions, sections, schema keys), 0.26 / 0.16 / 0.20 at the bottom for 0.24 / 0.16 / 0.19. At 0.4 the shown lines were useful 0.57 / 0.66 / 0.68 of the time, at 0.6 0.73 / 0.80 / 0.80: those are the cuts. On the same agent's run after the change, the page showed about 8 lines a task (3.6 at doc depth) and found 0.52 of what the merges changed (0.48 before), functions 51 of 382 against 31; the 20 queries found 0.56 of their answers in the first ten above 0.4 (0.30 before), functions 22 of 45 against 3. The chance below each kind's fifth item is extrapolated (no label there), and the judge's labels are the calibration's only source until searches' opens join them. Judged again on 20 fresh pages the calibration never saw (merges whose commit subjects were the work, drawn at the cuts): lines at 60% or more were useful 33 of 41 (0.80), at 40-60% 47 of 82 (0.57); sections 0.77, functions 0.71, schema keys 0.40. Within functions the score separates useful from noise weakly (on those pages a useful function's median chance 54%, a noisy one's 49%; sections 66% and 47%): on the 1,278 judged lines a logistic refitted to the judge's labels over the same features reached AUC 0.738 for functions against the shipped 0.719 (sections 0.790 against 0.786), and the query's words in the item's namespace, the same namespace as a seed or the cosine to the seeds' mean vector lifted it at most to 0.749 (`docs/vector.md`). A local cross-encoder over each kind's first twenty was then measured and left out: bge-reranker-v2-m3 (Q8_0, by the pinned llama.cpp) scored AUC 0.61 on 1,133 of the judged lines against the shipped 0.72 / 0.79 / 0.68, and 0.72 / 0.76 / 0.68 summed with it, at 52 ms a pair and 1.5 GB resident (`docs/vector.md`).

**Under the work's focus.** The page ranks against the work, not the plan alone (```seon.context/focus```: the plan's vector first, then each of the agent's evals, decayed with a half-life of one item). The judge labelled each kind's first five at 48 moments of 10 recorded runs, 720 lines more; the scale fitted on plan pages was overconfident there (its 60% band 0.56 useful). Refitted on all 1,905 lines as one table and cross-fitted, the 60% band holds in both states: plan pages 0.76 / 0.86 / 0.70 useful, the work's 0.76 / 0.81 / 0.67 (functions, sections, schema keys); a term for the state moved nothing at the cut.

**Cost.** A call costs `near`'s scan of the coarse rows (linear in the store, [the pyramid](#the-pyramid)) and a part bounded whatever the store's size: the pool (`relevance-pool` nearest a kind, the seeds, each seed's first `relevance-pool` neighbours by each read, and what the push reached), each item its vector's seek and its text tokenized once (```seon.docs/terms```, one pass over its characters); at most 1/(alpha eps) pushes, a node's degree counted by seeks to `:hub` before its neighbours are read, and a hub never read whole. On Seon's own store (5,095 texts, load about 20): relevance over the three kinds for a plan citing two vars took 115 ms, 54M ticks and 132 MB (the push 18 ms and 36 MB, from 65 ms and 114 MB before the hub bound and the counts; the pool's tokens 26 ms; each kind's `near` 10-18 ms), and `related` with its view about 260 ms and 210 MB (the rank fusion's search was about 40 ms). ```seon.context-cost-test/a-push-reads-what-its-threshold-reaches``` (a ring) and ```seon.context-cost-test/a-push-counts-a-hub-and-reads-it-not``` (a var n forms name) hold the push flat in the store's size; ```seon.context-cost-test/related-ranks-each-kind-by-one-search``` holds related at 1.48 KB a section past near's shortlist and 12.4 MB, 845 calls fixed (the rank fusion before it: 7.8 MB, 447 calls). At 40,000 texts the bounded part stays; near's scan, about 5 KB a vector, is the part that grows (its lever: the coarse rows kept as one buffer per db value).

Not measured: whether an agent reads what the cut shows more often, or reaches green in fewer turns (a paid comparison); a z from the kind's coarse moments, which the C kernel could answer in its scan, scored schema keys 0.36 against the pool's 0.28 and is not built.

## What the work is likely to need, as an eval

The page's `[:related]` part (```seon.render.ui/related```), which the model reads with the rest of the page, and `(my.task/related)` at the REPL, show what the plan's work is likely to need beyond what the plan cites (```seon.context/related```). The page makes no relevance call: it draws the units the agent's last turn included (`:seon.agent/included`, ```seon.context/selected```), each whole with its chance, in the order they entered, and the turn decides them by the ranking below:
- the `:seon.config.render/related` wiki sections, program functions and schema keys nearest the plan: a program function is no test and no macro, in a namespace whose file is under `:seon.config.source/program-dirs` (```seon.program/program-nss```; `similar` and the failure-point law read the same), so test/'s fixtures and helpers stay out whatever their names (`seon.check`, `seon.fixtures`: the live round 5's big-map request was shown printer test helpers);
- each kind ranked by [relevance](#relevance) from the plan's vector and words, what it cites and names (the seeds: the cited vars' callers and callees, the sections naming a cited var, the sections a cited section references or is referenced by, the schema keys the cited vars name are their neighbours) and the vars the branch changed;
- those at `:seon.config.render/relevance-summary` or more a line with their chance, at `:seon.config.render/relevance-doc` or more a section's whole lead or a function's whole doc, the rest counted with the form that lists them, and the forms that read one whole and search further (```seon.context/related-view```).

Before relevance, the two rankings were fused by reciprocal rank (```seon.vector/rrf```), which found more of what 31 merged tasks changed than either alone: functions 0.51 at 5 against 0.38 by meaning alone, sections 0.71 against 0.67, schema keys 0.56 against 0.37; tasks were weak by every method and stay a query (`my.agent/similar`). Ranking by each sentence of the plan and fusing them did not help on those tasks (2026-10-25, 6.9 sentences a plan, with the graph and what the plan cites left out): functions 0.37 at 5 against 0.39 by the whole plan (1 task better, 3 worse), sections 0.73 against 0.77 (`docs/vector.md`), though on the live round 5's one-line big-map request it lifted `seon.print.select/first-at-least` from 13th to 2nd: a short request's own words seed it, a plan's whole text ranks better than its parts. Beside each function, the registry keys its code and contract name (its `:form/keywords`, one EAVT seek) took record keys from 0.31 to 0.53 at 5 for about 74 tokens, more than the next five keys (0.48); the other way, a key's functions (one AVET seek, `seon.docs/callers`), added 0.50 to 0.50 for about 400 tokens, and is not shown. The comparison, its biases and its data: `docs/vector.md`.

### What was compared, and what it left out

Related search was compared on 31 merged tasks (truth: what the merge changed, 9.3 functions, 4.3 sections, 3.3 schema keys a task) by embedding, the reference graph, grep (the plan's words of five letters or more) and their fusions, scored by recall at 5 and 10 and the printer's token estimate; the data and scripts stay in `docs/vector.md/`.
- **Grep is left out of the screen:** it helped sections only at 10 (all three methods fused: 0.89), costs a stop-word list, and the screen shows 5; `my.agent/grep` stays a query. Tasks are weak under every method (0.28 at best, by embedding), since what a merge changes in other tasks is mostly follow-ups its plan does not predict, so they stay a query (`my.agent/similar`).
- **A function's schema keys earn their tokens, a key's functions do not.** Adding the record keys the top 5 functions name lifted recall 0.31 to 0.53 for 74 tokens (the next five fused keys: 0.48), and the attributes they name 0.06 to 0.46 for 47; the functions naming the top 5 keys added almost nothing for 404 tokens. The db stores no such edge: `:form/refs` holds vars only, and `seon.program/schema-dependents` decodes every contract per call. The smallest fact that would store it is `:form/keywords` (the qualified keywords a form's code and contract name), an indexed set that makes a function's keys one EAVT seek and a key's functions one AVET seek; it awaits root's gate.
- **Other agents' work** (merged tasks that changed the same var or section, 3.9 partners for 28 of 32 tasks) is found by plan text at recall 0.28 at 3 and 0.40 at 5, 2.5x chance; embedding producer text (merge subject, changed names) adds 2 to 3 points, too little for a new kind of text.
- **Rendered hiccup is not embedded** (root, 2026-10-25): about five new records a turn at 400 to 2,000 tokens each is 2 to 10k tokens embedded per turn, none reusable, more than every other source together; renders as definitions (the `seon.render.*` forms are already embedded) and others' plans give the sharing for a fraction of it.
- **Biases:** the db is main after the merges, which flatters embedding and grep; truth is what a merge changed, not what its worker read, which understates every method; recall only, no precision.

Because it is an eval and not a part of the task's data, it follows the plan as the agent rewrites it, the task's data stays fixed for the prompt cache, and the agent refines it in its own words: `(my.agent/related "the test service's results" 10)` ranks the sections nearest any text (it embeds the text through root's `:embed`; the screen form asks no effect and reads the vectors the turn's observe has just written, so a test reaching the screen reaches no process). It is a render over the plan's vectors (``seon.context/related``, [ctx](ctx.md)), never held: a view memoizes it by what it read (`seon.context-test/related-sections-follow-a-rewritten-plan`). `:similar` stays the task data's count of functions (off); a plan with no vector says so, with the form that searches by text.

Measured on the five fit requests before the fusion, sections by meaning alone (the request set of that day, since replaced by `seon.fixtures/requests`; held tasks on a worktree root, an outside agent's read, 2026-10-25): the transport-failure docstring request got `model.md#failures` first, the two printer requests `render.md#prose-and-the-one-string-cutter`, `#no-clipping` and `#how-a-value-is-printed`, the summary request `references.md#sections-in-a-tasks-context`; the unrun-proof request started weak (`tasks.md#where-an-agents-run-falls-short-today`, `agent.md#what-you-read`) and, once its plan named turn-state and the test service, followed it to `turn.md#observe` and `health.md#a-red-test`. About one line in five was an owner ruling in `decisions.md`, whose lead is its date and quote and says little at summary depth. The five lines cost 250-470 tokens a turn (chars/4, estimated), the largest part of a one-line request's screen. Not measured: whether a model reads them, or turns to green with and without them (a paid comparison).
