# Vectors

Semantic search is native to the store and its query language: each form's, wiki section's and task plan's text is embedded once by a small local model in root, its vector is kept on that entity as facts, and `seon.vector/near` is a Datalog function, so similarity is one more relation a query joins. An agent asks it at its REPL (`my.agent/similar`). The ruling is DECISIONS "Embeddings join the context: fused, small and measured"; the work was task `seon.context/similar-finds-helpers-by-embedding`.

```clojure
[(seon.vector/near $ ?q 10 {:of :form/id}) [[?e ?score]]]   ; ?q an entity with a vector, or a vector
```

## The model

EmbeddingGemma-2 (768 dims, Matryoshka, mean-pooled, normalized) runs in process through llama.cpp: `native/embed.c` puts its encoder behind a C ABI of pointers and ints (open, embed a batch of texts given as one UTF-8 buffer and offsets, close), and `bin/build embed` builds llama.cpp v0.7.0 from `reference-code/llama.cpp` (static, Metal, no OpenMP) with it into `target/lib/libseon-embed.dylib`. The model file is ggml-org's Q8_0 GGUF, fetched once by `bin/build` into the main tree's `target/cache/models/`, named by its sha256 and checked against it (`bin/env`'s `SEON_EMBED_MODEL`); its name is the model's id on every vector (`seon.vector/model-id`), and `bin/env` is the one place the pin is written (`:seon.config.vector/model` reads it), so a model change makes every vector due again. Nothing is installed outside `target/`; cmake is the one added prerequisite.

The model runs only in root, as the `:embed` effect kind (`resources/seon/system.edn`): ggml starts threads, and agents and the fork server must stay single-threaded to fork ([failure points](failure-points.md#physics-who-may-run-threads)). The effect's worker loads the library and the model on its first request (`seon.vector/open`, an effect kind's `:open`) and keeps the handle in its own state; the kind is a batch kind, so one worker step embeds the texts of every request queued (up to `:seon.config.vector/batch`), in encodes of at most `:seon.config.vector/batch-tokens` tokens (`seon.vector/embed`). Its answer is plain data, `{:model id :vectors [[x ...] ...]}`, the same in root and across an agent's socket.

Root's memory with the model loaded (macOS footprint, whole program embedded): 1,460 MB against 856 MB without it, so the model costs about 600 MB (Metal's copy of the weights, its graphics buffers, llama.cpp's allocations); the 310 MB file itself is mapped clean. `bin/check scale` holds its need (root's `seon.lib/real-mb`, a process's phys_footprint, plus the fork server's and the agents') within the 4,096 of `:seon.config.machine/memory-mb`. The open model keeps 4 threads (Metal's) beside root's declared ones, and its load runs ~32 more until it has loaded; ggml's CPU pool is `:seon.config.vector/threads` (1: Metal does the encode).

Measured on Seon's 1,393 src forms (M5 Max, Metal, machine load ~10): the model opens in 3.7 s; one text takes 5-15 ms warm; batched, 37k tokens/s (175 texts/s) at a 4,096-token encode (512: 122/s, 1,024: 167/s), 0.86 GB RSS; the BF16 file is no faster (34k tokens/s). v1 ran the same model in MLX over HTTP (5.7 ms one text, 66-105k tokens/s batched on short texts). mistral.rs (ericlbuehler/mistral.rs at `f512686`) was evaluated and not used: it has no EmbeddingGemma-2, did 32 texts/s on Qwen3-Embedding-0.6B in its place, and brings tokio and 461 crates.

## What is embedded

Each kind's text is its attribute's value with the model's prompt: a form's `:form/src` and a section's `:seon.section/text` as documents (`seon.vector/document-prompt`), a task's `:seon.task/plan` as what a search asks (`seon.vector/query-prompt`). A text over `:seon.config.vector/max-tokens` keeps its first tokens, and special-token text in it is read as text. A vector is five facts on the entity: `:seon.vector/f16` (the whole vector), `:seon.vector/coarse` (the [coarse level](#the-pyramid)), `:seon.vector/model`, `:seon.vector/text-t` (the transaction of the text it embeds) and `:seon.vector/tokens` (the text's whole token count: past the bound, what was left out).

`seon.vector/due` lists the texts whose vector is missing, made from an earlier text (its `:seon.vector/text-t` is not the text's transaction, so a text changed while its round was out stays due) or another model's. A form is content-addressed, so its text never changes and it is embedded once; a superseded form is retracted with its vector. `seon.vector/vectors-proc` keeps main current: at the writer's commit notice it sends the first `:seon.config.vector/texts` due to `:embed` and writes their vectors to main through the writer; that commit's notice starts the next round, so a backlog is embedded round by round and an idle main asks nothing. A failed embedding is root's problem (the effect owner records it) and the next notice tries again; texts llama.cpp could not encode are kept out of later rounds (the proc's `:unembeddable`, in its ping), so they never hold back those due after them. Seon's whole text (2,681 texts: 1,783 forms with the schemas, 321 sections, the task plans) embeds in 17-19 s at boot. An agent's branch reads main's vectors as of its fork, and embeds its own writes: at each turn's observe (```seon.agent/embed-written!```) the forms, sections and plans the branch wrote since the last turn (```seon.vector/written```, a `datoms-diff` from the db it last read: the cost of what changed) and its task's plan, those due, go to root's `:embed` in one request over the agent's socket (the model stays in root), and their vectors are written on the branch; a turn that wrote nothing due asks nothing, and a failed embedding is the effect's recorded error with the texts still due. A merge carries no `:seon.vector/*` facts (they are platform records, `seon.merge/carried-tx`): main's `vectors-proc` embeds the merged texts again at the merge's commit notice, as it does any text new on main.

## The pyramid

A Matryoshka vector's prefix is itself an embedding, so one stored vector serves two levels (`native/vector.c`, in libprobe: no threads, every process loads it). The coarse row is the first `:seon.config.vector/coarse-dims` dims renormalized and scaled to int8, with its scale (`seon.vector/pack`); the coarse level scans every row with integer dot products and keeps the best `:seon.config.vector/shortlist` in a heap; the fine level ranks those at f16 over `:seon.config.vector/fine-dims` dims, each prefix renormalized. A query option changes either (`{:shortlist n :fine-dims d}`); a shortlist of every vector is the exact search. `near` reads the coarse rows from the db value each call (no cache: a db value is its own index), copies them into one buffer, and reads only the shortlist's f16 rows.

Recall@10 against the exact 768-dim search:

| corpus | coarse | shortlist | fine | recall@10 |
|---|---|---|---|---|
| Seon's whole text, 2,681 (`bin/check vectors`, 207 queries) | 128 | 50 / 100 / 200 / 400 | 768 | 0.946 / 0.979 / 0.990 / **0.998** |
| src forms, 1,393 (every form a query) | 64 / 128 / 256 | 100 | 768 | 0.945 / 0.9975 / 1.0 |
| src forms | 128 | 100-400 | 256 | at most 0.83 |

The C levels take 0.08 ms at 1,393 vectors and 0.31 ms at 100k (v1's f32 brute force: 4.1 ms at 100k; em1's kernel 0.39 ms at 10k). The whole `near` in Jolt takes 1.9 ms at shortlist 100 and 4.6 ms at 400 on 1,737 vectors, nearly all of it the datom reads and copies; at 100k those would cost about 20 ms (estimated), the next lever if a store grows that large. `bin/check vectors` proves the default on Seon's own text each run, and `seon.vector-test/the-pyramid-ranks-as-an-exact-search` on made Matryoshka-shaped vectors. Proximum's HNSW was rejected in v1 (1.6-4.3 MB per commit, recall 0.16-0.62).

## Fused with the call graph

The task story shows `:similar` (```seon.context/similar```): the first `:seon.config.render/similar` program functions nearest the plan's vector, by an exact search (`near` with every vector its shortlist, at every dim), that the plan and proofs do not name, a line each. On Seon's own program (3,843 vectors) it costs about 9.7M ticks and 52 MB (40 ms) and 397 of a story's 1,749 tokens; ```seon.vector-cost-test/the-story-ranks-every-form-once``` holds it. Step 6 measures how often agents read one; 0 turns it off. Fusing the call graph's helpers (the cited vars' and proofs' one-hop callees, tf-idf) with the forms nearest a task's plan by reciprocal rank (```seon.vector/rrf```, k `:seon.config.vector/rrf-k`) was measured below; embeddings alone did as well, so the story uses them alone, and the fusion stays for further exploration.

Measured on 283 pairs from main's history (each non-merge commit's message as the plan; the functions its diff touched, still in the program, less those the message names, as what it needed), recall@10:

| ranking | all (283) | message names functions (166) | names none (117) |
|---|---|---|---|
| call graph | 0.042 | 0.071 | 0 |
| embeddings | 0.495 | 0.482 | 0.514 |
| fused, k 10 (k 60: 0.448) | 0.451 | 0.407 | 0.514 |

Fused beat the call graph alone, and embeddings alone (`my.agent/similar`) did as well as fused. Two biases run the other way from each other: the embeddings read each form as it is today, after the change its commit describes (flattering them), and a commit pair has no proofs, the call graph's richest source (understating it). v1 measured 0.274 / 0.386 / 0.441 on its own corpus. Weighting the two rankings is the lever if a task-shaped corpus shows embeddings alone ahead.

## Sections nearest the plan, as an eval

`(my.agent/related)` is a form of the screen (`seon.screen/forms`), evaluated before each model request like `(my.task/status)` and recorded as an eval: the first `:seon.config.render/related` wiki sections nearest the plan's vector on the branch that the plan does not cite (```seon.context/related```), each a line at summary depth (`seon.docs/view`: its address and its lead's first sentence), with the form that reads one whole and the form that searches further (```seon.context/related-view```). Because it is an eval and not a part of the story, it follows the plan as the agent rewrites it, the story stays fixed for the prompt cache, and the agent refines it in its own words: `(my.agent/related "the test service's results" 10)` ranks the sections nearest any text, and redefining `seon.screen/forms` puts that query on its screen. With no argument it is made again only when the branch's vectors change (```seon.context/related-at```, keyed by the count shown and the branch's last vector write); `seon.context-cost-test/related-sections-cost-nothing-when-the-plan-is-unchanged` holds an unchanged plan to one pull. `:similar` stays the story's count of functions (off); a plan with no vector says so, with the form that searches by text.

Measured on the five fit requests (`seon.fixtures/fit-requests`, held tasks on a worktree root, an outside agent's read, 2026-10-25): the transport-failure docstring request got `model.md#failures` first, the two printer requests `render.md#prose-and-the-one-string-cutter`, `#no-clipping` and `#how-a-value-is-printed`, the summary request `references.md#sections-in-a-tasks-context`; the unrun-proof request started weak (`tasks.md#where-an-agents-run-falls-short-today`, `agent.md#what-you-read`) and, once its plan named turn-state and the test service, followed it to `turn.md#observe` and `health.md#a-red-test`. About one line in five was an owner ruling in `decisions.md`, whose lead is its date and quote and says little at summary depth. The five lines cost 250-470 tokens a turn (chars/4, estimated), the largest part of a one-line request's screen. Not measured: whether a model reads them, or turns to green with and without them (a paid comparison).
