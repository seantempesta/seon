# Seon's own source is the program

The self-improvement loop (owner, 2026-10-21): agents change Seon's own functions on their branches, the merge lands them on main, main's files are written back exactly and committed on a merges branch, and the next generation is built from that commit and resumed on the same store. This page is how each step works and what it records.

## Import: the running generation's source as main's program

With `:source {:root dir :dirs ["src"] :branch "jolt/seon-merges"}` (or the config's `:seon.config.source/root`, with `:seon.config.source/dirs` and `:seon.config.source/branch`; a run states it with `--set :seon.config.source/root=\"dir\"`), root reads the tree through the `:source` effect at boot, when main holds no imported namespace yet. Each file is read form by form with its exact text, the whitespace and comments before each form (`:form/lead`) and the text after the last (`:ns/tail`). Each form is analyzed by Jolt's compiler without running it, giving the same account an agent's REPL records. What happened is root's `:seon.root/source` fact (files, forms, ms, or the error).

A file is analyzed against its own ns form, whether the binary loaded its namespace or not (test/'s namespaces it never loads; a task's proofs live there, so a root imports `["src" "test"]`). As loading does: the ns form of a namespace whose lib the process has not loaded (`clojure.core/loaded-libs`, not merely `find-ns`) is run before the forms after it are read and analyzed, so its aliases resolve `d/q` and `::z/k`; and files are analyzed in require order (each after the imported files its ns form requires, by the compiler's analysis of that form; ties by path), so a namespace only the import defines is set up before a file requiring it. Running an ns form still loads the libraries it requires, so a file whose libraries the binary cannot load does not import (task `jolt.ns/a-built-binary-requires-a-stdlib-namespace-it-did-not-compile`: `seon.print-test` requires `fipp.engine`, which needs `clojure.core.rrb-vector` from Jolt's stdlib).

Imported forms carry `:form/source true`: the binary already holds them compiled. Root and the fork server never evaluate a namespace imported from a file (`:ns/file`); an agent does run its branch's changes to one (`load-diff!` skips only the imported text). Measured on next/src: 54 files, 1,168 forms, 418 ms of analysis and 1.0 s to transact in the test runtime; 1.5 s at a root's boot. With test/r3, test/next and test/build too (lane TESTS, 2026-10-21): 64 files, 2.26 s at a root's boot; the other 26 files of test/seon analyze in 228 ms in a booted root.

Schemas are program too (owner, 2026-10-21; v1's rule, the program is entities): with `resources/seon/schemas` among the dirs (shipped: `["src" "resources/seon/schemas"]`), each schema resource is imported as one `:schema.file` entity holding its text (the base write-back edits) and one `:schema/key` entity per entry, its form as EDN text, its `:schema/file`, and `:schema/source` (the binary holds it compiled, like `:form/source`). Measured: all 21 resources import and write back byte for byte.

```seon.root/start!``` asks for the import (`:seon.config.source/*` in ```seon.root/start!```'s opts or the config); ```seon.fx/read-source``` reads the tree; ```seon.source/read-forms``` keeps each form's exact text and lead (with a step taken before the next form is read), ```seon.source/accounts``` analyzes them through ```seon.source/analyze-form```, ```seon.source/import-tx``` orders the files by ```seon.program/topo```, ```seon.source/text-tx``` and ```seon.source/import-tx``` write `:ns/file`, `:ns/tail`, `:form/lead` and `:form/source`; ```seon.source/schema-tx``` writes a schema resource's facts (```seon.source/schema-resource?``` names one); ```seon.source/file-ns``` and ```seon.source/source-files``` name what was imported. ```seon.program/load-all!```, ```seon.program/load-diff!``` and ```seon.program/load-changes!``` skip the imported text.

## Schemas at the REPL

An agent changes a schema the way `defn` changes a function: `(my.schema/register! k form)` on its branch (v1's `seon.schema/register!`). The registration is judged against the whole population, the binary's forms with the branch's changes and this one: a form that is no EDN data, does not compile (a name resolving to nothing), or declares an attribute Datahike cannot store is refused as data (`:seon.schema/registration-refused`, naming why), and nothing is written. Accepted, the entry is written on the branch without `:schema/source` (the binary does not hold it), in the resource it came from, or for a new key the resource holding most keys of its namespace; a new or changed attribute's Datahike declaration comes with it, so the branch can store its facts at once. A key in a scratch namespace (`user`, the agent's own) gets no resource: it is seen at the REPL and is no program. `my.schema/unregister!` removes a key no schema names.

The agent's REPL binds malli's dynamic registry to its branch's population before each form (`seon.repl/wrap-registry`; `seon.contract/options` puts the dynamic registry first), so the function it defines next, `seon.contract/valid?`, and every schema naming the changed key see it at once: the population is recompiled (4.6 ms for 457 forms), not the one key, because a map compiled against the old key keeps it. The registry is reused while the branch's entries are unchanged (`seon.schema/change-key`, 0.7 ms per form; deriving it is 13 ms). Platform code compiled into the binary keeps the built schemas until the next generation builds the merged resource (owner, 2026-10-21).

```my.schema/register!``` and ```my.schema/unregister!``` are the verbs; ```seon.schema/registration``` and ```seon.schema/removal``` judge them; ```seon.schema/changes``` and ```seon.schema/branch-registry``` derive the branch's population; ```seon.contract/registry-of``` compiles one.

## Write-back: main's files, byte for byte

`file-text` is a namespace's live forms in their order, each after its lead, then its tail. A form recorded at a REPL has no lead: a blank line goes before it. A redefinition takes the place and the lead of the form it supersedes. With no merge, import then write-back is a zero diff over all of next/src (`seon.source-test/import-then-write-back-is-a-zero-diff`). After a merge, only the files its changes touch are written: the unit of write-back is a file path (`changed-files` of the train member's changes, which the writer puts on each merged member's answer as `:files`).

A schema resource is written entry by entry with rewrite-clj (v1's `schema-file-text`, ported unchanged but for the separator of an appended entry, which follows the file's last two entries): the imported text, with each entry whose form differs from what that text holds replaced in its old layout (a part that reads as before keeps its text), each key no longer held removed with its line, and each new key appended. Every other byte is as it was: adding `:refused` to `:seon.attempt/status` changes only those 9 bytes of `seon.facts.edn` (`seon.source-test/a-changed-schema-entry-rewrites-only-itself`).

```seon.source/file-text``` builds a namespace's file and ```seon.source/schema-resource-text``` a schema resource's (through ```seon.source/schema-file-text```); ```seon.source/files``` builds every changed file, from ```seon.source/changed-files``` of what ```seon.writer/merge-branch``` merged; ```seon.fx/write-file``` writes one.

## Commit: the merges branch

The reconciler asks for the write-back after a train lands: it reads main, computes the files, and asks the `:git` effect to commit them on the merges branch with a message naming each merged task and attempt. The commit uses git's plumbing (blobs, a tree from the branch's own, `commit-tree`, `update-ref` from the head it read), so no working tree or checkout moves; a branch not there yet starts at the tree's HEAD. The sha is recorded on each merged attempt as `:seon.attempt/commit`, or the refusal as `:seon.attempt/commit-error`. `bin/check loop` proves the turn on a clone of the repository.

```seon.reconcile/reconciler-proc``` asks for it, ```seon.source/commit-message``` names the merged work, ```seon.fx/git-commit``` commits; the answer lands on the attempt as `:seon.attempt/commit` or `:seon.attempt/commit-error`.
