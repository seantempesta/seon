# Seon's own source is the program

Seon's own source is main's program: agents change Seon's own functions on their branches, the merge brings them into main, main's files are written back exactly and committed on a merges branch, and the merge runs at once where main's program runs: root, the fork server and every agent forked after it load it in place, with no build and no restart. The db is the source: a boot resumes main and reads no file, and files are written from it, never read back (owner, 2026-11-09: "From that point on we are syncing data TO files not reading from them"). A tree is read only when it is indexed: a fresh store's seed, or a re-index a person asks for. This page is how each step works and what it records.

## Files and the db: two directions

Once a store is up the db is the source of truth, and files and the db meet in two directions only, each an act someone takes (owner, 2026-11-10: "dbboot is supposed to resume if the store is already there ... Once seon is up and running the db is the source of truth").
- **Outside in: files to the db.** A landing: `bin/land`'s bridge writes what git landed on the standing root's main as data (```seon.root/landed-tx```, [a landing enters main as data](#a-landing-enters-main-as-data)). A running root: a person re-indexes at root, ```my.root/import!```, ```my.root/load-docs!``` and ```my.root/load-tasks!``` ([indexing a tree](#indexing-a-tree)). The whole tree: `bin/root start --reindex`, refused while a root of the checkout runs (`bin/root stop` first), erases the checkout's store and starts, so the fresh store's first boot seeds main from the tree (bin/root's header).
- **Inside out: the db to files.** A merge writes main's changed files back into the merges tree, byte for byte, and commits them on the merges branch ([write-back](#write-back-mains-files-byte-for-byte), [commit](#commit-the-merges-branch)); `seon_write_back` (```my.root/write-back!```) repeats one that was lost, and its files reach git's main by the reviewed sync alone ([a merged task reaches main's files](#a-merged-task-reaches-mains-files)): `bin/update` brings main into the merges tree, never that branch into main.
- **A boot reads no file:** it resumes the store when one is there, and seeds it only when it is new ([a boot resumes from the db](#a-boot-resumes-from-the-db)).
- **A mismatch is never silent.** When the binary is another program than main's (```seon.root/stale-binary```), root resumes main and forks no agent, which would run the two mixed; the `:stale-binary` row shows on root's problems tile ([health](health.md#a-stale-binary)); and the root prints `ROOT STALE BINARY` before it listens, so `bin/root start` ends on that line and `bin/update`'s last line is `UPDATE FAILED: ROOT STALE BINARY ...`. Each names the same acts (```seon.problems/stale-binary-acts```): `bin/root start --reindex`, a re-index at root then a restart, or `bin/root next`. Proofs: `seon.root-test/a-root-on-a-binary-of-another-program-forks-no-agent`, `seon.render-test/a-stale-binary-is-on-the-problems-tile-with-its-acts`.
- **A main with no source fact is never refused:** a store no tree was indexed into (a check store seeded with an example program) holds no `:seon.root/source`, so nothing is compared and its agents fork.

## Import: the running generation's source as main's program

A tree's source becomes main's program when it is indexed: once, into a store that holds none (its seed), and again only when a person asks (a re-index); the boot as a whole is [root](root.md#boot). (A root started without `--profile` has no model provider: [model](model.md#no-default-model).)

The defaults: `bin/root start` with no store makes one and indexes the checkout's own source into it (`:seon.config.source/root` defaults to `SEON_SOURCE_ROOT`, which `bin/root` sets to its checkout); its dirs are `src`, `test` (a task's proofs and fixtures, which an agent holds only when main holds them) and the schema resources (```seon.config/value``` of `:seon.config.source/dirs`); with a store it resumes it; `--set` or `config/local.edn` override either (the main tree's names `.worktrees/merges`, the tree its merges write back into, so main's working copy stays the owner's). `bin/test`, `bin/check` and the roots tests take a branch of a seeded store, or index nothing unless they state a source. `bin/update` brings the standing root up to date with main, reading the write-back tree's path from the main tree's `config/local.edn` (`:seon.config.source/root`) and failing, not skipping, when that tree is not there: it merges ``jolt/merges`` (the main tree's merges branch, named in its `config/local.edn`; the shipped default is ``jolt/seon-merges``) into main, fast-forwards the write-back tree to main, runs git submodule update, builds, and restarts the root. A change landed in git enters main as data ([below](#a-landing-enters-main-as-data)); a disk edit acts on nothing until someone re-indexes.

With `:source {:root dir :dirs ["src"] :branch "jolt/seon-merges"}` (or the config's `:seon.config.source/root`, with `:seon.config.source/dirs` and `:seon.config.source/branch`; a run states it with `--set :seon.config.source/root=\"dir\"`), an index reads the tree (```seon.fx/read-source```): its files and its HEAD commit. Each file is read form by form with its exact text, the whitespace and comments before each form (`:form/lead`) and the text after the last (`:ns/tail`). Each form is analyzed by Jolt's compiler without running it, giving the same account an agent's REPL records. What happened is root's `:seon.root/source` fact (the tree's commit, the digest of the files read, files, forms, the program entities retracted, ms, or the error).

### Another tree's program, analyzed beside this image

A process may build the program of another git tree than its own (`test-runner/program-db`, cutting a tree's db from the nearest kept one with `seon.source/refresh-tx`), while its image holds this checkout's namespaces: the tree's `ns` forms run in the live image. Across a namespace rename that failed three ways, each now handled:
- a dependent whose file the change removes is never read again from the old db's text (`refresh-tx`);
- a namespace whose file the checkout lacks (`seon.source/in-checkout?`, judged by the checkout's files, never the classpath: `test/` is on no root of root's own process) is marked loaded once analyzed (`read-nss`, Jolt's `ldr-mark-loaded!`), so a later file's `require` of it answers from the analysis; and when the kept tree holds one unchanged, `test-runner/keep-tree!` reads it again from the target tree with the change;
- an `ns` form that points an alias at another namespace clears that one alias first (`analyze-form`), which Jolt otherwise refuses;
- a namespace's docstring is its ns form's own, `:ns/doc`, on a read of a file and an agent's eval alike, and moves with the form (`seon.program-test/a-namespace-holds-its-docstring`);
- a definition's docstring is its form's own (`seon.program/account`), never the image var's, so another tree's program says what its text said and not what this checkout's later definition says. A definition's contract and meta still read the live var first when it is bound (`:var/meta`, the var's own Clojure metadata keys, location keys and `:doc` left out, recorded by `seon.program/def-meta`: a test is a var whose meta holds `:test`, a macro `:macro`, a function a `defn` made `:arglists`; nothing stores a classification of a var): task `seon.program/another-trees-contract-is-its-own`.

Proofs: `seon.source-test/a-renamed-alias-target-analyzes-beside-the-image`, `seon.program-test/a-file-analyzed-keeps-its-own-docstring`. Measured 2026-11-01: Seon's post-rename tree imported whole in 15.7 s (4,027 vars), then a pre-rename tree refreshed from it in 7.4 s (3,999 vars), where both had failed. What still fails is the deeper cause, one image analyzing two programs: an old tree's code naming a var today's image lacks or holds private, about 16% of the context lab's parent trees.

### Indexing a tree

An index takes what the tree changed: when the files read differently from main's last index (the fact's `:digest`), only the files that differ from the tree it last indexed (the fact's `:tree`) are read and brought in, ```seon.source/refresh-tx```, so what main merged and the tree never held stays main's (owner, 2026-11-07: "The DB is the source of truth"); with no last tree, or one git can no longer find, the whole tree replaces main's program in one transaction, ```seon.source/replace-tx```. When they read the same, nothing is written. A form whose macro reads files as it expands (`seon.config/schema-forms` bakes the schema resources, `built-text` the shipped config file) holds what the macro read: when a changed file is no namespace's (a schema resource, the config file, a script), every file holding such a form is read again with it (```seon.source/file-reading-expansions```, found from the facts: a macro whose form refers to one of `seon.program/file-readers`), so a schema-only change moves `schema-forms`' keywords as a whole import would (`seon.source-test/a-refresh-reads-again-a-form-whose-macro-read-a-changed-file`). Re-importing changed files alone would not do: a form's identity is its text (`seon.program/account-tx`), so a changed file's new forms would join its old ones, and a removed function would stay live. `replace-tx` is ```seon.source/import-tx```, read against main without the forms of the imported namespaces (each form takes its file's order and lead), with every program entity of those namespaces and of the schema resources that the import no longer makes retracted: a changed function's old form, a removed function's form and var, a removed file's namespace. Data (tasks, agents, config and root facts) and the program of a namespace no file holds (an example program, a namespace an agent made) are untouched; history keeps the old program. The digest is of what was read (the files and the reference-code pins), not of the commit alone, so uncommitted edits in the tree count.

There are two indexes, and nothing else reads the tree (owner, 2026-11-09: "Of course we can re-index if we want. But I mean as a functioning system concept"):
- **The seed** (```seon.root/seed-program!```, `bin/root seed STORE`, and the first boot of a main nothing was indexed into): ```seon.root/import-tree!``` while the indexer is the store's only process, then the wiki with its baseline until it states nothing more (its citations resolve to the program, ```seon.root/wiki-tx```), then the task files (```seon.root/task-files```, ```seon.task/load-tx```), all written directly on the branch (`seon.root/seed!`).
- **A re-index**, a person's call on a running root: ```my.root/import!``` (with relative paths only those files, `:paths`), ```my.root/load-docs!``` and ```my.root/load-tasks!```, each through root's writer.

What an index of the source writes is computed once, by ```seon.root/import-of``` (the program facts, the files' modes and the source fact, or why it can't), from main and the read; the seed and a re-index differ only in how they write it. Proof: `seon.source-test/a-boot-resumes-main-and-reads-no-file` (a fresh store indexed at its first boot; a file written under a running root and commits made while it was down change nothing on main; `import!` brings them).

Measured on next/src and the schemas (80 files, 1,660 forms, test runtime): the same tree replaced on itself is 0 retractions, ```seon.source/import-tx``` 0.5 s, ```seon.source/replace-tx``` 3.6 s and its transaction 0.8 s; one changed form, 1 retraction. Of replace-tx's 3.6 s, 3.0 s is the in-memory retraction that reads main without the forms; reading main through `datahike.api/filter` instead gives the same transaction in 0.6 s, once `:seon.host/db` admits a filtered db. Proven by `seon.source-test/a-moved-tree-replaces-mains-program`.

A change re-imports only what it reaches, and writes only what changed. ```seon.source/refresh-tx``` (proven by `seon.source/an-import-reads-only-changed-files`) takes the files that changed (a removed one's text nil) and reads their namespaces again. It reads a namespace that requires one of them only when what dependents read of it was lost (```seon.source/interface```: each definition's name and meta, plus the text of its ns form and of each macro, protocol, type or inline function): a name removed or of other meta reads the dependents that reference it, and a changed macro, protocol, type or inline function reads every dependent; what was added breaks no form. A body edit therefore reads one file whatever requires it. Each form is then compared with what db holds (```seon.program/account-diff-tx```): an unchanged form writes nothing, a moved one only its order and lead, a changed one its facts with the stale ones retracted. The result is the same program as ```seon.source/replace-tx``` of the whole tree, which is the same diff over every file. Measured on Seon's src and test (110 files, 2,667 forms, load ~8): a body edit in the 29-form test/seon/cost_test.clj was 151 ms plus 25 ms to transact, and is now 33 ms plus 3 ms. That splits into read and analysis 20 ms, the interface gate 2 ms, the diff and tx 9 ms, and one form written. A body edit in `seon.edn`, which 21 namespaces require, costs 2 ms and reads none of them. Each phase's cost is flat from 10 to 1,000 forms of other files (```seon.source-test/a-fixed-change-costs-the-same-at-any-program-size```). A constant's value change is not in the interface (an account does not carry ^:const), so it does not re-read dependents.

Not this: re-importing the files that changed (old forms stay live). When main's merged forms and a worktree session's edits to the same function meet, the tree wins; there is no three-way merge of the tree's commit into main.

A file is analyzed against its own ns form, whether the binary loaded its namespace or not (test/'s namespaces it never loads; a task's proofs live there, so a root imports `["src" "test"]`). As loading does: the ns form of a namespace whose lib the process has not loaded (`clojure.core/loaded-libs`, not merely `find-ns`) is run before the forms after it are read and analyzed, so its aliases resolve `d/q` and `::z/k`; and files are analyzed in require order (each after the imported files its ns form requires, by the compiler's analysis of that form; ties by path), so a namespace only the import defines is set up before a file requiring it. Running an ns form still loads the libraries it requires, so a file whose libraries the binary cannot load does not import (task `jolt.ns/a-built-binary-requires-a-stdlib-namespace-it-did-not-compile`: `seon.print-test` requires `fipp.engine`, which needs `clojure.core.rrb-vector` from Jolt's stdlib).

Indexed forms carry `:form/source true`: a binary built from the tree holds them compiled. Every other form of main runs where main's program runs, platform namespaces included (see [a merge loads in place](#a-merge-loads-in-place)). Measured on next/src: 54 files, 1,168 forms, 418 ms of analysis and 1.0 s to transact in the test runtime; 1.5 s at a root's boot. With test/r3, test/next and test/build too: 64 files, 2.26 s at a root's boot; the other 26 files of test/seon analyze in 228 ms in a booted root.

Schemas are program too (v1's rule: the program is entities): with `resources/seon/schemas` among the dirs (shipped: `["src" "resources/seon/schemas"]`), each schema resource is imported as one file entity (`:file/path`, `:file/text`, the base write-back edits) and one `:schema/key` entity per entry, its form as EDN text, and its `:schema/file`; an entry is a branch's change when its form differs from the binary's (`seon.program/schema-changes`). All 24 resources import and write back byte for byte (`seon.source-test/import-then-write-back-is-a-zero-diff`).

The functions: ```seon.fx/read-source``` reads the tree; ```seon.source/read-forms``` keeps each form's exact text and lead (with a step taken before the next form is read), ```seon.source/accounts``` analyzes them through ```seon.source/analyze-form```, ```seon.source/import-tx``` orders the files by ```seon.source/load-order```, ```seon.source/text-tx``` and ```seon.source/import-tx``` write `:ns/file`, `:ns/tail`, `:form/lead` and `:form/source`; ```seon.source/schema-tx``` writes a schema resource's facts (```seon.config/file-kind``` names one); ```seon.source/file-ns``` and ```seon.source/source-files``` name what was imported; ```seon.source/replace-tx``` makes main's program the tree's, and ```seon.root/import-of``` records the digest on root's `:seon.root/source` fact. ```seon.program/load-diff!``` and ```seon.program/load-changes!``` skip the imported text.

### A boot resumes from the db

A boot opens main and resumes it, reading no file but those its checkout changed since main last indexed it ([below](#a-boot-catches-up-with-its-checkout)) (owner, 2026-11-09: "Boot's job is to resume the existing system or if it's fresh to index it and get it to the point that everything is running off the db"). In ```seon.root/boot!```, while root is the store's only process: the store opens, a main nothing was ever indexed into nor booted on (no `:seon.root/source` fact, no `:seon.root/boot`) is seeded once ([above](#indexing-a-tree): the wiki and the task files always, the program when root has a source tree), main's config is held (```seon.program/hold-config!```), main's program is digested (```seon.program/program-digest```, one read of five attributes' datoms), and the fork server forks; the fork server builds each agent's schema registry from main's entries (`seon.fork-server/warm-start`) and loads main's test namespaces. Nothing is imported to catch up, and nothing is loaded into root's image: root runs the program its binary was built from, and its boot fact states that program beside main's ([below](#the-binary-records-its-program)). What the binary needs that has no facts is baked into it when it is built: the shipped config (```seon.config/built-text```), the system declaration (```seon.system/built-text```, which ```seon.system/read-decl``` reads) and the dependency roots of `deps.edn` (`seon.fork-server/dev-classpath!`).

Why (2026-11-08, then 2026-11-09): the boot used to import the checkout's tree before it read main (`import-tree!` at boot) and to follow the checkout afterwards (a file watcher, and `follow-main` fast-forwarding the write-back tree), treating files as the source; that made the binary and main agree, but by reading files, and its git call (Jolt's `sh`, two future threads) was where the main carrier's stuck race fired. Proofs: `seon.source-test/a-boot-resumes-main-and-reads-no-file` (the source tree moved away), `seon.root-test/a-boot-on-a-binary-of-another-program-holds-mains-config`, `seon.root-test/a-boot-forks-with-mains-schema-registry`, `seon.root-test/a-boot-reads-no-file-a-commit-broke`.

### A boot catches up with its checkout

Sessions edit a checkout's files from outside, so a root resumed on its store would run the program main held before their edits (owner, 2026-11-10: "change the default to always be building the latest binary off the code and indexing it so agents are on the latest version of the code after changes are made. This should be done efficiently too so if very little has changed it doesn't take forever to start"). A boot of a root with a source tree that is not a seed catches main up (```seon.root/catch-up```, in ```seon.root/boot!``` before main's program is digested). ```seon.fx/changed-since``` reads git's diff of the tree main last indexed (`:seon.root/source`'s `:tree`) against the files as they are, submodules left out, with the untracked files: about 40 ms on this checkout when nothing changed, where the whole tree's id costs ~0.4 s, most of it git checking each submodule's files. A submodule's pin is a build input, which the binary's check below judges. The files that changed are indexed as a landing is (```seon.root/landed-tx```: code, pages and task files), in one transaction that moves the source fact to the tree as it is now, at the cost of those files' forms. Three kinds are left out and named, and the fact keeps its tree, so the next boot reads them again:
- a file that does not read as its reader reads it (```seon.fx/unreadable```);
- task files refused by ```seon.task/load-tx```;
- a file that a merged task main holds unsynced also changed ([below](#a-merged-task-reaches-mains-files)), where the checkout's text would replace the merge's.

The root prints `ROOT CAUGHT UP n files` and `ROOT CATCH-UP LEFT OUT path: why` before listening. When what it caught up reaches the binary's own code or a build input ([below](#the-binary-records-its-program): `ROOT STALE BINARY`), `bin/root start` runs `bin/build seon` and starts the root again, once. `:seon.config.root/catch-up-on-boot` false resumes main as it is, reading no file, for a Seon no one edits from outside. A test's root sets it false (```seon.test-store/start-args```): its main is the tree its run seeded. Proof: `seon.source-test/a-boot-catches-up-with-what-its-checkout-changed`.

### The binary records its program

`bin/build` records beside the binary the program of the tree it was built from (`target/seon.program`, written by the binary's `built-program` mode, ```seon.root/built-program```: the tree indexed as a seed indexes it, ```seon.root/import-tree!```, into a store the build keeps, so a build indexes only what its tree changed, and that index's ```seon.program/program-digest```). The kept index is the build's cache, regenerable from the tree at any time and never read by root: under `target/seon.index-<schema digest>` (```seon.db/kept-store!```: one another schema or layout made is dropped, never opened), one store named by the code that made it (```seon.program/index-code```, the reach digest of `import-tree!` and `program-digest` over the index's own program, with the runtime pins and config they read). A tree change that moves that code indexes the tree again into a new store, since an index brought up to date keeps what the old code made of each form whose text did not change, its id included (```seon.program/account-diff-tx```) and the tree's inputs that have no program facts (```seon.fx/inputs```). A program digest is a function of the program alone, since every program entity's id is a content id of its identity ([storage](storage.md#ids)), so a seed of the tree and the build agree on it. The record holds the git tree it was built from too (`:tree`, the tree as it is on disk, pins included). At boot root reads that record (```seon.root/binary-program```) and writes it on its `:seon.root/source` fact (```seon.root/booted-source```) beside the tree main was last brought to from outside, which only an import or a landing moves (`:tree`; what agents merged into main since is main's own and never a mismatch, since the db is the source of truth). Its agents key their test results by the inputs of the files the boot read: `bin/root start`, where git runs, computes them (the binary's `inputs` mode: ```seon.fx/inputs``` of the source root, else the checkout) into `runs/root-inputs.edn`, and the boot hands them on its source fact with the config in force (```seon.root/booted-source```, ```seon.agent/test-inputs```); an agent's plan adds the index class and the private checks its test child runs with, so an in-process test has one digest whichever runner plans it and agents share greens with every checkout of that tree (measured 2026-11-11: 41 of 41 of `seon.prove-test` agree; a process test's root digest does not yet, task `seon.prove/one-digest-whichever-runner-plans-it`). They were handed the inputs only when three tree ids agreed, and an empty default otherwise, which a merged task not yet synced to main made every boot's. A root under a starter (a test's) is handed none and keys by its binary's record. A branch whose program is not the binary's moves the tests that read the program ([verdicts](merging.md#verdicts-are-a-cache)). Two trees (a store left by another tree, as between a landing in git and its bridge's merge, or a worktree's store under a newer build): its agents share nothing, root forks no agent (```seon.root/stale-binary```: an agent would load main's forms over the binary's code and run the two mixed), and health shows a `:stale-binary` row ([health](health.md#a-stale-binary)) until `bin/update` rebuilds the binary or the store is erased. Never an import to catch up. Proofs: `seon.root-test/a-root-on-a-binary-of-another-program-forks-no-agent`, `seon.root-test/what-agents-merged-into-main-is-no-stale-binary`. Measured 2026-11-09 (load 6-8): the record of an unchanged tree 1.4 s, of a change the indexing code does not reach 2.2-2.3 s (the reach graph 0.9 s of it, 252 M ticks), of a change it reaches or a tree no index holds about 34 s; it was a whole index into an empty db at every build (analysis 1.23 G ticks and 5.4 GB, the checked transaction 2.34 G ticks and 4.9 GB, 10.7 s at load 2). Proofs: `seon.problems-test/a-root-on-a-stale-binary-is-a-problem`, `seon.source-test/a-builds-kept-index-holds-the-program-a-fresh-index-holds`.

**A binary is current for a tree** when what differs between the tree it was built from and that tree reaches none of the code root runs from its binary, and none of what the build bakes in (Point, 2026-11-10: one rule for the gate's build, the spawn refusal and the stale-binary row; ```seon.root/binary-current```). What differs is git's changed paths between the two trees (```seon.fx/tree-diff```): a pin, `native/`, `deps.edn`, `bin/build`, `.gitmodules`, the schemas, the shipped config or `system.edn` is not current; a source file is not current when a form whose text changed (its text on main, read against the file as the binary's tree holds it, ```seon.fx/tree-file```) defines a var of root's reach: ```seon.program/root-reach```, the closure over main's reach graph of every name root's binary runs code from, as data names it (```seon.program/root-roots```: the binary's entry `seon.main/-main`, system.edn's procs and effects, the renders schema entries name, the config's qualified symbols; none in a test namespace), never entering an agent's body (`seon.repl/run!` and the agent's process entries), which runs main's program from the db. On Seon's program it is 2,139 of 5,005 vars (2026-11-10). A changed path no rule places is not current, and neither is a binary that recorded no tree against a main that holds one (unknown is never current); a main with no source fact is. Tests, the wiki, task files, `bin/`'s scripts and agent-only code run from the checkout or are loaded from main by whoever runs them, so a binary built before them is current (`seon.source-test/a-binary-is-current-for-a-tree-unless-what-differs-reaches-root`). Every reader of the binary's tree asks this one rule: `bin/test` builds only when the plan's `out/build` names why (```test-runner/build-text```, empty when the binary is current, so a prove whose change reaches nothing root runs builds nothing, ~50 s saved); `bin/check` takes that `out/build` (its steps dir's, or the run's `SEON_PLAN_BUILD` under its own checkout) before it compares trees literally; and ```seon.root/booted-source``` hands agents the inputs of the tree main holds when the binary is current for it and built from another, never the binary's own (`seon.problems-test/a-root-on-a-stale-binary-is-a-problem`, `seon.check-test/a-stale-binary-is-refused`, `seon.check-test/a-failed-seed-says-failed`). Two trees' diff never changes, so ```seon.fx/tree-diff``` keeps it beside the checkout's builds (`target/tree-diffs/FROM-TO.edn`), and a prove's plan, which judges the binary current and then builds nothing, writes the tree's inputs beside the binary (`target/seon.inputs`): a root booting on that tree reads both as files and runs no git; one with no plan behind it runs git, on a fiber as every shell (docs/machine.md#processes).

### A landing enters main as data

A Claude session's landing changes files in git, so until Seon agents write the system's updates themselves it enters main through a temporary bridge (owner, 2026-11-09: "We have to accommodate you and your agents who primarily write the updates in files, but this is a temporary system -- I want seon agents writing updates inside the system and pushing them to disk"). After `bin/land` moves main in git, root writes on main, through its writer, the facts of every changed text file (`bin/land`'s `bridge`, also run as `bin/land --bridge REPO OLD NEW PORT`: one root eval of ```seon.root/landed-tx```: ```seon.root/changed-tx```, ```seon.source/refresh-tx``` and ```seon.source/modes-tx``` of the source dirs' files, then ```seon.doc/load-tx``` of the wiki's pages and ```seon.task/load-tx``` of the task files, as a seed indexes them, and root's source fact moved to the landed tree, so the next re-index reads only what differs from it). No task, agent or judge takes part: the change was proved before git landed it (it was an outside agent's `:done` until 2026-11-10, which a judge held for having no proofs). Then `bin/update` brings main into the write-back tree, and the system keeps running when nothing calls for a restart (```my.root/landed!```, ```seon.root/restart-for```): main holds main's tree as data (the bridge ran), and the running binary is current for that tree ([below](#the-binary-records-its-program): no build input and no form of root-reach changed) and was not stale at its boot. The change already loaded in place as a merge does ([a merge loads in place](#a-merge-loads-in-place)), so `bin/root inputs` writes the inputs of the files now and root writes its source fact again as a boot does (```seon.root/booted-source```): no build, no restart, and every agent keeps working (`UPDATE OK: kept running on tree T`). Anything else builds and restarts root, saying why (`restart: ...`), and the boot resumes main with those facts: every agent of the old boot ends, as before. Of the 11 landings of 2026-11-11, 7 changed nothing the binary runs. Proof: `seon.source-test/a-landing-keeps-the-system-running-only-when-nothing-calls-for-a-restart`. A path with no facts (native code, `deps.edn`, `system.edn`, a gitlink) is a build input, which `bin/update`'s build takes. Root reads no file for it. Proof: `seon.source-test/a-landing-through-the-bridge-is-a-zero-diff` (main indexed from one tree, then from what the next changed, holds the next tree's program digest and writes its files back byte for byte).

### A program file

A file the program holds that is no namespace is one file entity (`:file/path`, `:file/text`, `:file/mode` as git records it), named by the allow-list `:seon.config.source/things`, a path pattern to a kind (```seon.config/file-kind```), for a file under `:seon.config.source/dirs`. A kind differs only by data: the facts of its text and its text as a db holds it (```seon.source/file-kinds```), so the import, the write-back and the merge's keys (`stated-keys` in ```seon.merge/stated-content```'s namespace) have no branch per kind. A schema resource is the kind whose text splits into entries, each `[:schema k]`. The config file (`resources/seon/config/default.edn`) is another: each entry a `:config/key` entity holding `:config/form`, its value's exact text with its reader tags unread, and `:config/file`, keyed `[:config k]`, conflicting per key like a form, and written back through the same path with every comment kept (```seon.source/config-text```; `seon.source-test/a-config-entry-writes-back-only-its-own-bytes`). What a process does with them: [config](config.md#a-process-holds-its-branchs-config). A new key's entry holds its value, not the comment above it, so it writes back without one; its schema entry says what it means. A test fixture (`test/seon/*.edn`, the kind `:fixture`: ```seon.source/fixture-tx```) is a file with one entry, its text, so a branch's change to a recorded request or an expected value is a fact of that branch, and a test reads it through ``my.branch/file`` (the branch's text, or the checkout's with no branch), never from the disk of the process that runs it. A script (`bin/*`) is the kind with one entry, its whole text and mode, `[:script path]`: both sides changing one to different text is a conflict of the merge, which writes nothing until a resolution settles it ([agent](agent.md#merging)), and ``(my.branch/changes)`` lists it under `:scripts`. What it says of itself (```seon.source/script-tx```: `:seon.script/says`, its lead comment, and `:seon.script/usage`, the lines of that naming it) is derived from its text, for reading (```seon.render.ui/script```); no plan's citation reaches it yet (task step 3).

An edit of a script goes to the branch, at its name or its absolute path under this checkout or the source root ([agent](agent.md#changing-a-file)). An edit of the config file is the same: the file's text as the branch states it, its entries made the new text's (```seon.source/edit-tx```). A new script has no edit: until a form makes one, it comes in by the import. The disk does not move until the write-back, and a file changed on disk reaches main only at an import, as a namespace's does (when main's merge and the tree's edit meet, the tree wins: task ``seon.source/the-trees-commit-merges-three-way``).

Before a commit writes a file, ```seon.fx/git-commit``` reads it as its reader does (```seon.fx/unreadable```), and an edit of a script does the same: the shipped config validates, EDN reads as the EDN reader reads it and Clojure as Jolt's own reader loads it (nested `#()` and all; an alias its ns form does not declare does not read, as it does not load), a script passes its interpreter's syntax check (a file with no `#!` line, like the sourced `bin/env`, has none to ask). What doesn't read refuses the whole commit and names the file, so a merged change stays on main with its task's `:seon.git/commit-failed` error until a later merge fixes it and ```my.root/write-back!``` writes it. A write to a plain path is never refused.

### A file that does not load

An index that meets a file it can't load goes on with what main holds and says which file and which commit last worked. ```seon.root/import-tree!``` (the seed) and ```my.root/import!``` (a re-index) ask ```seon.root/unimportable``` before they write: each file of a kind on the allow-list reads (```seon.fx/unread-text```), and the config its entries would state is one the schema it would state allows (```seon.program/config-refused```). Refused, nothing is written and the answer names the file, the reason and the commit of the last index. A boot reads no file, so a commit that broke one stops nothing (`seon.root-test/a-boot-reads-no-file-a-commit-broke`). A process's own start reads no file but its `--config` layers ([config](config.md#a-process-holds-its-branchs-config)); a built-in config that doesn't validate (a binary built from a file that doesn't) has nothing to go on with, and refuses naming each key. A namespace's file that doesn't analyze takes the same `:error` path through ```seon.source/tx-of```, naming the error rather than the file. Proof: `seon.source-test/a-branchs-config-is-its-own-and-reaches-the-next-process`.

## A merge loads in place

A merge of main runs where main's program runs, at once: root's writer (`seon.writer`), the fork server (`seon.fork-server/server-step`) (so every agent forked after it inherits the change compiled, copy-on-write) and an agent merging main call ```seon.program/load-changes!``` with the commit's tx-data. It loads each live form the commit asserts but the binary's own text (`:form/source` in a namespace this process holds, every var it defines bound: a form a re-import adds to a test namespace loaded at boot is loaded, not left for an agent's stage to read as an unmap; `seon.source-test/a-form-imported-into-a-loaded-namespace-is-loaded-not-unmapped`), and removes each definition the commit leaves pointing to no form. A restart loads main's every form but the binary's own at boot (```seon.program/load-all!```; root leaves test namespaces out, [below](#a-process-holds-the-tests-only-when-it-runs-them)), so a binary older than main's merges catches up; a resumed agent loads its branch's difference (```seon.program/load-diff!```), which reads only the datoms that differ between the two dbs (```seon.program/diff-plan```), the cost of the diff, never of the program.

### A process holds the tests only when it runs them

A form an import replaces is loaded wherever the process has seen it, since a bound var says only that some version of the form ran. So a process that loaded before the import, such as a fork server forked for a resumed agent while the import was still reading, runs what main holds next.

Root holds `test/` as program facts (reach digests, an agent's plan and the task pages read them) and evaluates none of it: root loads nothing at boot, and `seon.program/load-changes!` in root's writer is called with `{:tests? false}`, which leaves out the forms of every namespace read from a file outside `:seon.config.source/program-dirs` (```seon.program/test-nss```; a namespace with no file, an agent's app or a test store's example program, is not one). Root never runs a deftest: tests run in an agent's test child and in `bin/test`'s shards. The boot fork server loads them once, at its start (```seon.fork-server/main```), while root writes its boot fact and imports its source, so a first spawn does not wait for them after root's boot (2026-11-08: about 1.3 s of a fresh root's first spawn); a commit the import writes after loads as changes, and the load's errors go to root as `:load-errors` with the first `:preload` or fork, and `bin/build seon` warms the binary's compile cache with them (```seon.check/warm-tests```, 9 s), as the cache is per binary and compiling them cold at a first fork was 6-18 s, each namespace whose live forms are all its file's as imported (its `:ns/file` under the tree main's program was imported from, as main states it on root's `:seon.root/source` fact, never the process's config: a root given its source as `seon.root/start!`'s options, as every `bin/check` mode is, holds none, and its fork server loaded every test namespace form by form, 12.2 s of its first fork against 1.06 s whole, 2026-11-10) loaded whole by `require` through Jolt's AOT cache (`JOLT_CACHE_DIR`, bin/env: compiled once by the first process, loaded compiled by every later one; main's 78 test namespaces 12.2 s evaluated form by form, 0.70 s loaded warm, 2026-10-30) and any other form by form (```seon.program/required!```), and then with each commit it hears of (`load-changes!`), so every agent and test child forked from it inherits main's tests compiled, as read-only pages that cost no RAM until written ([cost](cost.md#how-we-measure)); the first fork waits behind the load (about 15 s of compiling under load 12 on 1,822 forms; the load runs once per server, a standby inherits it). A root's REPL may load them on request (`(seon.program/load-all! @(:conn sys))`), as any REPL loads what it is about to call. Measured on a scratch root (resumed store, the same binary, live heap after a full collection): 714 MB allocated with 450 MB static and 264 MB outside it, against 856 MB and 406 MB once root also evaluates the 1,822 test forms (-142 MB live, -122 MB footprint of the same process, 901 against 1,023 MB); the fork server, which now holds them, is 622 MB footprint. Proven by `seon.source-test/root-loads-the-program-and-leaves-test-namespaces-unevaluated` and `seon.agent-test/root-holds-no-test-code-and-its-agents-hold-mains-tests`.

One load adds what a change reaches, as v1's declaration-reload-rule and clj-reload do: the forms a changed macro expanded in (its namespace and every namespace requiring it, since an expansion leaves no reference: ```seon.program/dependents```) and the forms whose contracts or code name a changed schema entry, through the schemas naming it, loaded against main's population so their contracts re-arm (```seon.program/schema-dependents```). A protocol or a record needs none on Jolt: a record's dispatch and an `instance?` test held by the binary see the redefinition. A redefinition reaches the binary's compiled callers because a direct-linked call reads its var's linked binding, which every redefinition writes through, and a contracted definition is never spliced (`bin/check hotreload`).

Measured by `bin/check loop` on a clone (1,646 forms): the merged `seon.generation/generation` answers 2 in root and in an agent forked after the merge; the turn from release to quiet is 13.4-13.9 s (the implement agent ~5 s, the merge agent ~7 s, the commit and quiescence ~1.6 s). What remains is whole-program reads per merge.

## An agent changes code at its REPL

An agent changes the program by `in-ns` and `defn` at its REPL: each form it evaluates there is its branch's change. An eval that redefines a macro also compiles again, in that process, every form that expanded it (```seon.program/reload-dependents!```, the act a spawn's ```seon.program/load-diff!``` does), since Clojure's eval leaves them on the old expansion: a test defined before its macro changed ran stale until then (```seon.repl-test/a-macros-redefinition-reaches-the-forms-that-expanded-it```). It removes a definition as Clojure does, `(ns-unmap 'n 's)`: the eval observes the var gone and retracts its definition on the branch, saying so (`:unmapped`, `seon.repl/unmapped`), as v1's REPL recorded it; nothing refuses an unmap a caller still needs, which fails where that caller loads and in its tests. `require` and `load-file` load as in Clojure and record nothing. Its working directory is a scratch dir with no repository above it (`:seon.config.agent/cwd`, made and entered by the boot server's ```seon.fork-server/main```; every agent forks from it): it reads and writes any file by its path, git finds nothing, and editing source files is not how Seon develops.

## A form's account is the program's facts

A form's account is what the compiler said of one top-level form, and the program is these accounts as entities: a form entity (its exact text, namespace and place) and, for each definition the form made (a var, a multimethod's method, a protocol extension, a namespace), a pointer to it. Nothing reads a form's text to learn what it is.

An eval is accounted by what the analyzer saw and what the run did. ```seon.program/tap``` is bound around the eval as the analyzer's unit tap: it collects each analyzed unit and the root each var it defines held before (```seon.program/root-of```, `::unbound` when none), and calls no contracted function, so the tap stays out of the eval's own cost. After the run ```seon.program/set-vars``` is the readback: the vars whose root is no longer the one before, in any namespace. ```seon.program/account``` joins the units, the exact text and the namespace, and answers nil when the form is none of the program's: its namespace is scratch (```seon.program/scratch-ns?```: `user`, or declared `^:scratch`), or it defines, declares and extends nothing and changes no environment. Its account also holds the calls of ```seon.program/banned``` vars (which `seon.merge/mutations` reports). A contract is stored as EDN text (```seon.edn/encode```, no print limits and no metadata; ```seon.edn/decode``` reads it back) when ```seon.program/edn-value?``` holds of the live value, else as the form was written.

Identities are content. ```seon.program/form-id``` is the namespace and the hash of the exact text (hasch's uuid, the one Datahike names content by), with the occurrence number for a repeated text of an imported file. A method is its ```seon.program/method-key``` (`[multi dispatch]`, printed), an extension its ```seon.program/impl-key``` (`[protocol type]`), and ```seon.program/pointer``` names the attribute by which each kind of definition points to its form. ```seon.program/def-eid``` finds a definition's entity on a db; ```seon.program/def-ref``` names it in a transaction (its entity, or an upsert by identity under a tempid, `seon.program/ns-tid` and `seon.program/form-tid` being the tempid texts, since Datahike allocates a tempid at the first place it is seen as a ref). ```seon.program/form-tx``` is one form as an entity map; ```seon.program/def-tx``` makes a definition point at a form and retracts what it held that the new content lacks; ```seon.program/account-tx``` joins them (the form keeps its order if db holds it, else takes the place of the forms it supersedes, else goes last) and retracts each form all of whose definitions it redefines; ```seon.program/record-tx``` is that for an eval on the branch's db, after every form so far.

What a definition says of itself that wiki text relies on is ```seon.program/meaning``` (its contract and its docstring). ```seon.program/meaning-changes``` reads an eval's definitions before they are transacted and answers, for each existing var whose meaning changes, what it was, what it becomes and the wiki sections citing it, at the cost of the tx-data and one entity read and one index seek a var.

A form is live when it defines nothing (a `declare`, a `require`, a comment kept from its file) or some definition still points to it (```seon.program/live?```); a form all of whose definitions point to later forms is superseded and no part of the program. ```seon.program/form-row``` reads a form entity as the loader and the merge read it (from one seek of the entity's datoms and one of each namespace, definition and declared var it names: 6.9 k ticks and 21 KB a form where the entity's attribute-by-attribute reads were 35 k and 96 KB), ```seon.program/live-forms``` every live form of a db in entity order. ```seon.program/attr-namespaces``` are the namespaces of the attributes that hold the program (forms, definitions, schema, the db's own schema): what a merge carries as program, and what a commit must touch to count as moving it (`moves-program?`, [merging](merging.md#the-test-service)). A file at an old commit has the same identities without analysis: ```seon.source/defining-ids``` finds the form defining each var by its head and name and gives the id the account would give, so a wiki baseline is read without loading anything.

## A var is private as the tree analyzed holds it

A file is analyzed against the running image (its namespaces' aliases and macros are the image's), but whether a file may name another namespace's var is the **tree's** answer, never the image's var: the image holds the privacy of whichever tree it was built or run from, and health analyzed a head and its base in one process (it no longer does: [health](health.md#checks-are-callers-of-seon)), so an analysis that changed the image's var (it used to, in ```seon.source/analyze-form```) left each tree seeing the other's privacy ("var: #'seon.db/index is not public" for a var the head made public). Analysis changes no var of the image. ```seon.source/tree-private``` is the analysis env's `:private?` function (Jolt's `jolt.host/ctx-for-ns` takes it; its analyzer asks it before a var's own `:private` meta): for a namespace the changed files define it answers by the defining form (`defn-` or `^:private`), for another program namespace by the tree's program (`:var/meta`, which ```seon.program/def-meta``` takes from the definition, never the live var), and nil for a namespace the tree does not define (clojure.core, a library: the image's var is right, the tree cannot change it). The one place analysis does change the image is on purpose: a namespace's `ns` form and a macro's definition run, since what follows is analyzed against them. The tree is every file the import read, not one round's: refresh-tx reads a dependent again in a later round when a namespace it requires lost a name, and that round asks the privacy of the files every earlier round read, a file read before keeping the text it was read with; asked of that round's files alone, the privacy fell back to the db's facts, which still held a var the same import made public as private (2026-11-09: a seed after jolt/index-arg failed "var: #'seon.db/index is not public", `seon.source-test/a-dependent-read-again-takes-the-privacy-of-every-file-the-refresh-read`).

## Tests run by reach

A test runs only when something it reaches changed since it was last green, in any checkout. ```seon.program/graph-index``` gives each test of a db its reach digest: its own form, its namespace's forms that define no var (the ns form, fixtures), and every live form their `:form/refs` reach (a var to the form that last defined it; a defined multimethod's methods and protocol's extensions), and every schema entry a reached var's contract names (and each entry the entry's form names, on, and the vars its form names: the renders its properties declare, such as `:seon.render/hiccup`, so a render's body edited moves the digest of every test reaching its entry, `seon.program-test/a-render-a-schema-entry-declares-is-in-its-tests-reach`), each form and entry digested once; plus the checkout's inputs with no program facts (`seon.fx/inputs`: deps.edn, bin/, resources/ with the schemas contracts name, test fixtures, and the pins and source groups its reach runs on; not task files or text; and the per-test tick bound), plus the values of the config keys its reach reads (```seon.program/config-reads```: the `seon.config.*` keys its reached forms name, every key for one referencing the config map from outside `seon.config`, such as root's boot; their values from the config in force, ```seon.fx/config-input```: the shipped file, the `--config` layers the command line names, the `--set` overrides and the `#env` values under the profile, with the checkout's path normalized and the place keys left out), plus the vars data names that root resolves by name (`seon.fx/declared-refs`: system.edn's procs, edges of `seon.system/read-decl`), and no tree: a test whose reached forms call a file reader or run the binary (`seon.program/tree-readers`; a test runs target/seon, bin/root or bin/check only through `seon.test-store/binary-sh`) is digested by what it reaches like any other (owner, 2026-10-27: "no tests should include all of src"; with the tree it was 286 tests rerun on any edit), and a file or a binary change outside its reach is found by the full run (`bin/test --all`, below). A check step whose reach reads the tree still takes it, and so does a test reaching a form of a test namespace that calls a reader of the checkout's files (`seon.program/file-readers`: `slurp`, `file-seq`, `io/resource`, and src's readers of a checkout directory, `seon.fx/read-source` and `seon.doc/load-dir-tx`; 51 tests, measured 2026-10-28; the `:scans` flag of ```seon.program/graph-index```): what such a test judges is the files themselves (the one-printer list in render.md, the wiki's leads), so one digest over a red tree and a green one made it flaky (2026-10-27, 2026-10-28). A test's digest moves exactly when a form or schema entry it reaches does. A direct constructor call, `(T. x)`, is a reference to the type's var, so a change inside one of its methods moves the digest of every test reaching the function that builds it, as `->T` and a protocol's extensions do (`seon.program-test/a-types-method-is-in-the-reach-of-what-constructs-it`; 2026-11-03, a change inside `seon.ratom`'s reaction moved nothing, and a stale green was reused). A literal name a form passes to `resolve`, `ns-resolve` or `requiring-resolve` is a reference (`seon.program/resolved`): the var it looks up at run time is one it reaches, so a test that resolves its var by name is no green reused after that var changes, or once it comes to exist. Any other name a form holds as data (quoted: `tree-readers`, `env-readers`, `seon.config/schema-forms`, whose `:seon.render/*` properties name every render, a form sent to an agent) is no reference, so reaching that form is neither using nor reaching what it names (below). A db that does not declare an attribute the graph reads (an agent's merge base cut before `:form/ops`, on a store kept from before it) holds none of its datoms (Datahike's `datoms` answers none, as DataScript's does: [datahike](forks.md#datahike)), and its forms are read with none (`seon.program-test/a-base-cut-before-an-attribute-has-a-reach-graph`).

A form's `:form/refs` are the answer of the code that derives them (`seon.source`, `seon.program`), and a kept tree reads only its changed files, so bin/test's kept program store reuses a tree only under the same importer (`test-runner`'s branch prefix holds its text): a change to it imports the program whole once, and no form keeps an edge an older importer missed.

How a reach digest is computed (the field's action keys: Bazel's, Nix's): the forms and schema entries are a graph by those edges, and each strongly connected component of it (```seon.program/components```, Tarjan's, iterative) gets, once per call and sinks first, a Merkle digest of its forms' own digests and the digests of the components it reaches, and whether it or they read the tree or reach a process (`:seon.config.source/process-vars`). A test's digest is of its key, `:env`, `:tree` when what it reaches reads the tree, and its starting forms' components (its own form and its namespace's plain forms), so it moves when a form it reaches changes and when the shape of what it reaches does (which form calls which); its `:process?` is whether any of those components reaches a process. One pass over the condensed graph answers every test, O(forms + edges) whatever their number (```seon.program-cost-test/the-reach-walk-is-one-pass-whatever-the-keys```): measured on Seon's program (484 tests), ```seon.program/graph-index``` takes 578 ms and 715 MB a call, of which reading the live forms is 407 ms and 393 MB; a walk per test took 1,079 ms and 1,691 MB. A live form is read as the walk reads it (```seon.program/reach-rows```: its id, namespace, definitions and references, each attribute read once over its index for all the forms, and its text never: a form's own digest is its `:form/code`, read as any attribute is, [what a test takes of a form's text](#what-a-test-takes-of-a-forms-text)), never its other facts: on the proof's chain that is 97 KB and 15.8k ticks a form, against 153 KB and 33k before. The graph is a value (```seon.program/reach-graph```; ```seon.program/graph-index``` answers from it), and a change to it is ```seon.program/reach-update```: the live forms the two values differ in (```seon.program/live-ids```, four index scans and no entity read, 7 ms), each form's neighbours recomputed only where its edges can have changed (an added form; a form referring to, or defining the methods, extensions or contract of, a var a changed form defines), and only the components of the changed forms and of the forms reaching them re-folded, the rest kept: O(changed + their ancestors) past the scan, with the digests a rebuild gives (```seon.program-test/an-update-gives-the-digests-a-rebuild-gives```). Measured on Seon's program (2,616 forms): a one-form edit of `seon.agent/test-plan` re-folds 187 forms in 15 ms, of `seon.lib/digest` (in the program's one large component) 1,767 in 40 ms, against 640 ms for the graph. A schema entry added, changed or removed is the same update (```seon.program/schema-moves```): its entry removed and added, and the forms whose edges it changes touched and re-edged: the entries naming it, the contracts naming it (`:contract` holds every name a contract names, an edge only where the entry exists), and the forms naming it as a keyword (`:form/keywords`, one AVET seek a key; their `:sedges` kept up), and the forms reading a config key they compute re-folded when the config keys entries name moved (`:computed`: the fold takes `:schema-config`, not the entry). Measured 2026-10-29 over a merge that added two config entries and edited the config map's (7 lines of resources/seon/schemas, `main~3` to main): the rebuild was 154M ticks and 892 MB, the update 47M and 271 MB, with the digests equal (```seon.program-test/a-schema-entry-added-changed-or-removed-is-updated-not-rebuilt```); what the edit reaches is re-folded all the same (3,218 of 4,707 forms: every reader of the config map reaches its entry). A namespace gaining its first test (an agent's new test namespace, or a deftest added to a src namespace) is the same update: the forms it already held are re-edged as added (their quoted names are edges in a test namespace), where it used to build the graph from nothing (721 MB and 135M ticks, and a 24 MB graph held by the agent); a namespace losing its last test, or losing a form while gaining one, still rebuilds (the step takes a removed form's edges out by the namespaces it now knows as tests). Measured 2026-10-29 in one agent whose eval defined a namespace with a test, then asked `my.agent/tests-reaching`: `seon.agent/branch-graph` 721.7 MB allocated and 114 MB of footprint before, 65.8 MB and 20 MB after ([machine](machine.md#ten-agents-that-work)).

**The graph holds its tests' index** (```seon.program/reach-indexed```, read with ```seon.program/index-of```: ```seon.program/graph-index```'s answers for the tests, under the inputs it was made for), which is derived data and regenerated whenever it is not held ([derived data](data-modeling.md#derived-data-is-a-cache-never-relied-on)). ```seon.program/reach-step``` keeps the answers of the tests a change cannot move and names the others `:stale`: a test whose form was re-folded (it reaches what changed), every test of a namespace whose plain forms were added, removed or re-folded, a test added; a test removed loses its answer. So `reach-indexed` on a graph updated from one that held its index answers only for the stale, and for none when the inputs are the held ones and nothing is stale (the graph itself, no allocation). The fork server holds main's graph with its index under the inputs an agent forked from its db takes (```seon.fork-server/graph-at-fork```), moved by the same update, so an agent's first turn finds its base's index made: measured 2026-10-29 on Seon's program (4,713 forms, 1,138 tests, 170 config keys), ```seon.program/graph-index``` 19.2M ticks and 136 MB a call, `reach-indexed` on the handed graph 2.2k ticks and 1.2 KB; for a base a commit or more older the update's stale tests only (a one-form edit: one test, 2.3k ticks and 16 KB whatever the program's size, ```seon.program-cost-test/an-index-is-recomputed-for-what-moved-only```; a change to a form most tests reach, or to the config map's schema entry, makes most of them stale and costs what it did: 19.1M ticks). The index equals a rebuild's after any chain of updates ```seon.program-test/an-index-held-by-the-graph-moves-with-it```, and on Seon's program across four commit pairs (2026-10-29, checked by script). The fork server makes the index whole under an agent's inputs when a program commit finds it held under others (a boot whose root had not yet recorded its source), once there, never in every agent. Not covered: an index under other inputs (the plan's `bin/test`, whose `:tree` moves with every edit) is made whole, as before.

A form's `:form/refs` (```seon.program/unit-account```) are the vars its IR resolves (its calls and `#'` references), plus what the IR does not show: in a macro, each qualified symbol its template quotes, which is the expansion's code; and each macro the form calls (```seon.program/macro-uses```, read from the form itself: an expansion names no macro, and a top-level call expanding to a `do` leaves its units no trace of it). So a changed macro body moves the digest of every test reaching a form that expands it, and a macro whose template names another macro reaches it too. Any other quoted name is data (```seon.program/quoted-names```, the form's `:form/quoted`, never a reference): a proc or render named in data, a form sent to another process, `(requiring-resolve 'x/f)`'s argument. A caller listing reads both (```seon.doc/callers```: who calls or names a render); the reach reads only the references, but in a namespace that holds a test, where a quoted name is one the test hands to what runs it by name (`(cost/proof {:of 'ns/f ...})`, a resolve, an agent's eval), it reads the quoted names as edges too (```seon.program/reach-graph```; measured 2026-10-27: 290 of 941 digests moved, and a cost proof that named `seon.program/reach-update` as data had hidden a red behind a stale green, ```seon.program-test/a-name-a-test-hands-over-quoted-is-what-it-reaches```). So is a name in a string constant (```seon.program/unit-account```, in any namespace; only a test's namespace makes it an edge): a string holding a slash (a qualified name needs one) is read once, its delimiters repaired, as the code it may be (`(in-agent ["(my.agent/tests-reaching 'x)"])`, `"  (def x 'app.x/f)"`), and the qualified names of its forms are quoted names, read only and never evaluated; one that does not read, or that `seon.reader/forgive` turns into a comment because it opens no form (a sentence naming `app.x/f`), names nothing (```seon.program-test/a-var-a-string-names-moves-the-test-holding-it```). Its qualified keywords count only when it opens with a paren: a message naming a config key is no read of it (read for every string, 1,567 of 1,615 digests moved with `:seon.config.ctx/window`). Before, only a string opening with a paren was read, so an eval string with leading blanks or a quote hid its var and a stored green outlived the change (Context, 2026-11-10). Cost: one read of each string constant holding a slash, at analysis; on Seon's program 7,109 strings (4,793 in the 72 test namespaces; 873 opened with a paren before), the 4,793 read in 0.4 s warm; the day it landed 586 of 1,616 digests moved, 579 because they reach `unit-account`, which that edit changed, and 7 for the names alone. It is recorded by name, never by whether its namespace exists yet, so a form's facts are the same however the program was analyzed: when the rule was "a reference if its namespace exists", a refresh, which loads only the changed files, dropped what a whole import kept, and one tree left out 240 tests refreshed and 250 imported (```seon.program-test/a-quoted-name-is-data-whatever-the-process-analyzed```; root's ruling, 2026-10-25). A test that resolves a name at run time reaches what it resolves only through what it calls. Measured on src and test (330 tests, 2,236 live forms): editing `seon.lib/defc`'s body moves 298 digests; refs are 33,916 datoms; the import is about 8 s and the digests 705 ms.

A form's `:form/keywords` are the qualified keywords its constants and its contracts name: the attributes, config keys and schema entries it reads or writes, the data it operates on, recorded by the same walk (```seon.program/unit-account```, a scalar keyword one set conj, no walk). A key's functions are one AVET seek (```seon.doc/callers``` with a keyword, `(my.agent/callers :ns/key)`), and a changed schema re-arms the forms naming it by that seek (```seon.program/schema-dependents```), where it decoded every contract before. 

`bin/test [NS ...]` (and `bin/prove`, which adds the `bin/check` steps) reads `:seon.config.source/dirs` as program facts, the dirs root imports, so a test's digest is the same on both sides (```seon.source/import-tx``` into an empty store, else the facts kept for the checkout's git tree brought current by ```seon.source/refresh-tx```: ```test-runner/program-db```, the facts root and agents record; a tree's branch exists only once its import committed (it is branched from a staging branch's committed head, in one step, so two runs importing one new tree each end with the whole branch and the second's refused branch is read, not thrown), so a file that does not read, or a transaction refused, leaves the store as it was, and a test namespace the program db holds no test of fails the plan with its name rather than selecting nothing and saying OK, ```seon.proofs-test/a-failed-import-leaves-no-branch```), reuses every result recorded at its digest and runs the rest, caching each verdict by its digest ([verdicts](merging.md#verdicts-are-a-cache)). The selection, the shards and the steps: [merging](merging.md#a-merge-runs-what-the-change-reaches).

An agent holds main's whole suite (the fork server loads test/ like any imported namespace, `seon.program/load-changes!`; root does not: [a process holds the tests only when it runs them](#a-process-holds-the-tests-only-when-it-runs-them)), so a test namespace opens no store at load: no top-level `def` that connects or makes a db. One that did (`seon.merge-test`'s `base`) hung the fork server, which answered neither `:stats` nor `:fork` and reported nothing. Its test run selects by the same digests: ```seon.agent/test-plan``` is `seon.proofs/plan` of its tests' digests against those of the main it forked from: the task's accumulated proofs, plus every test whose digest moved (a changed var, method, fixture, ns form, macro or schema entry it reaches), the changed tests among them. That is exactly what `seon.reconcile/done-explain` reads: the proofs, and the tests whose red would be a regression or a stray red. A test that reaches a process of its own (```seon.agent/test-plan```'s `:process`, from the same walk) is never selected automatically: it runs when named or when it is one of the task's proofs, and the others are listed as deferred ([merging](merging.md#a-merge-runs-what-the-change-reaches)); scratch namespaces' tests never judge. A selected test green at its digest among the results recorded on root's main is reused, not run (a `:pass` report marked `:reused`): the agent's digests take the inputs its root's boot recorded on `:seon.root/source` ([merging](merging.md#a-merge-runs-what-the-change-reaches)), so the turn after an unchanged turn, the judge's `:tests` and the gated merge rerun nothing. Root's `:tests` request names the agent's task; the turn loop passes its own; `(my.agent/prove)` is the judge's run (`seon.agent/run-tests-forked` in mode `:judge`) at the agent's REPL.

### What a test takes of a form's text

A test's digest takes a form's code, not its comments or its layout (owner, 2026-11-06: "make sure test reuse is working and we avoid re-running the same tests over and over again when nothing has changed"). It was the hash of the form's text, so a reflowed body or a comment reran every test reaching the form. ```seon.program/form-ids``` gives a form, when ```seon.program/account``` records it, its id (the hash of its namespace and exact text, which names the form) and its `:form/code`: the digest of its namespace and **the form as the reader read it, as EDN** (the text ```seon.edn/encode``` makes, printed inline in ```seon.program/form-ids```: one contracted call more is over the `account` proof's estimate, [render](render.md#printing-beside-the-printer-the-wire) names it), from the form `account` already holds, so the text is read once. The reader has dropped the comments and the whitespace; the encoding leaves out `:line` and `:column`. Two things the encoding does not hold are made to: the numbers the reader gives a gensym (`p1__12#`, `x__3__auto`, one counter for the process) are renumbered by first appearance, and the name's metadata (`^:private`) follows the encoding. A form stored without a `:form/code` (an older store's, a seeded fixture) is taken by its id, which moves with every byte. Checked across every form of src and test (3,831 forms, two reads of each): all encode, and none encodes differently the second time (```seon.program-test/a-comment-or-whitespace-edit-moves-no-test``` holds the cases: a comment, a reflow, a `#()`, a syntax quote's gensyms, a `^:private`, a `;` inside a string).

A definition's docstring is no code (owner, 2026-11-10: a test's digest takes code, not docstrings; [decisions](decisions.md#the-test-system-runs-inside-seon-the-outside-is-thin-wrappers-owner-2026-11-10)): ```seon.program/form-ids``` leaves out the string after the name of a `def`, `defn`, `defn-`, `defmacro`, `defmulti`, `defprotocol` or `ns` form when more follows it (a `def`'s only string is its value; a `defmethod`'s third element is a dispatch value, which is code). A one-sentence docstring edit to `seon.turn/act!` reran all 231 process tests reaching it. A test that reads the program's text takes the src class, `:seon.env/src` (the text of src/ and test/, below): one whose reach calls ```seon.test-store/kept-program-store``` or ```seon.contract/uncontracted``` (the laws of `seon.main-test`, the render and reach checks over src), and one reading a docstring, where a form of its namespace calls `clojure.repl/doc` or names `:var/doc` or `:ns/doc` (```seon.program/reach-step```'s `:docs`, which adds the class to that form's config reads as a registry walker adds the schema class). It is found from the forms and never declared, so no test can leave it out. Two readers it cannot see are the full run's to catch: `(:doc (meta v))`, since `meta` is in every `deftest`'s expansion and `:doc` is no qualified keyword a form's facts hold (`seon.model-test/a-transport-failure-is-answered-to-the-agent` is one), and a src function reading docstrings for a test (a render of a var), which is not a reader there, or every context test would be one. The src class is the checkout's files, so an agent's own edit does not move it and reruns no law (taking the program's text from the agent's branch instead made every agent edit rerun the ~19 whole-program laws, 2.47 G ticks; that waits for recorded reads). A docstring- or comment-only edit in a checkout reruns those readers and nothing else; a code edit reruns what it reaches, as before (```seon.program-test/a-comment-or-whitespace-edit-moves-no-test```).

A config key added is no input of a test that does not read it (a branch adding one key, with a small change beside it, ran 1,250 of 1,348 keys). The config map `:seon.config/config` lists every key as a field `[key key]`, and each reader of `seon.config/value` reaches the map's entry through `seon.config/config-schema`, so each new key moved nearly every digest (1,118 of 1,154). A `:map`'s fields that are config keys are neither its edges nor its digest's (```seon.program/less-config-fields```); a key's own entry says whether a map lists it (```seon.program/config-facts```, `:listed`), so a key taken out of the map, or an edit to its entry, moves the tests that name the key, and its value moves the tests that read it (`config-reads`); what the map says besides its fields still moves its readers (```seon.program-test/a-config-key-added-moves-no-test-that-does-not-name-it```). A test that walks the registry reads every entry without naming one, so a form of a test's namespace naming a whole-registry var (```seon.program/registry-walkers```) takes the schema class: `every-key-is-documented-by-its-schema` stayed green over a key with no unit until it did. A form of src naming one does not, or every schema edit would move nearly every test; a test of src's whole-registry walk (the entity index's `:entity-schemas` (```seon.db/entity-index```)) stays the full run's to catch.

Its cost: a change to what root runs reruns about 233 process tests. Every checkout and every root has its own place keys by design, and the source's content is `:tree`'s. A bound a test runs under (`:seon.config.store/branching-factor`, the tick budgets, the provider) stays in. So an agent's root and a checkout on one tree key a test alike, and a green either stores is the other's (```seon.program-test/a-test-digest-takes-only-the-config-keys-it-reads```, ```seon.program-test/a-test-takes-only-the-file-classes-its-reach-reads```, ```seon.agent-test/an-agents-greens-and-a-checkouts-are-one-store```).

Not this: a hand list of the tests a change touches, or a result keyed by time or by checkout path. What the digest does not see: a file a test reads, or the binary it runs, that its reached forms do not name (the full run, `bin/test --all`, catches it); a test reading files through a reader outside `tree-readers`, or resolving a var by a name it builds at run time (not a quoted symbol), is digested without it; digesting the branch costs a pass over its live forms per run (about 0.7 s on src and test; the base is digested once); the plan does not build the reach graph again each run: the graph the last plan left in the program store (`reach-graph.fasl` beside the kept store, decoded in about a sixth of the ticks a build takes: 23M against 146M on Seon's program) is brought to the tree by ```seon.program/reach-update```, which re-folds only what differs, and is stored again (`test-runner/reach-graph-of`; a store written under other code for the graph, named by the ids of `seon.program`'s forms, or other data-refs is built over); the decode and the scan of the live forms stay linear in the program; a config key read through a key a form builds at run time (no keyword any reached form names) is missed; a schema looked up by a key a form computes, a file read by a path built at run time and a library used through interop or a `:require` with no var reference are missed (the owner's ruling: the daily full run is the net); the import costs about 8 s per run.

### A result is a function of its digest

A green is reused forever, by any checkout or agent, so everything a result depends on is in its digest or out of the test (`docs/source.md`):
- **Seeds.** A generative check draws from a seed derived from its digest (```seon.proofs/seed```: the parts and `:seon.config.proofs/seed-salt`; ```seon.proofs/test-seed``` for the running test, bound by ```seon.proofs/run-tests!```; each mg-check contract from its var and its own reach digest ([checks](checks.md#the-generative-check-is-per-function))), so the same digest checks the same cases and a code change draws new ones; a failure prints its seed and a reproduction form. Before, mg/check drew from the wall clock (our malli fork ignored `:seed`; fixed on its `jolt/mg-seed`). A randomized property test draws `:seon.config.proofs/seeds` seeds, its test-seed and the next ones: one in the automatic run, five under `bin/test --all` (`SEON_SEEDS=5`, as the full run sets `SEON_COST_MAX_N`); `r3.inc-test`, 5 seeds of 150 steps, was 47 s of the automatic run's critical path.
- **Work, not time.** A cost proof is judged on ticks, bytes and calls (```seon.cost/exact```, [cost](cost.md)), so the same code on the same input measures the same at any load; an estimate stating and measuring none of them is red, and CPU time is shown, never red.
- **Dependencies as they are.** A submodule with uncommitted edits is its class by its content (```seon.fx/pin```: HEAD and the tree of its files), as bin/build builds it; a clean one is its gitlink.
- **The tree held.** A shard stores only if the tree is the plan's before and after its run.
- Still open, each with its fix in the findings: shard co-residency (a test leaving a thread or process state behind), the kept stores in `target/`, the inherited environment, render functions named by symbol in schemas, and deadlines and picked ports (which can only turn a result red).

## Schemas at the REPL

An agent changes a schema the way `defn` changes a function: `(my.schema/register! k form)` on its branch (v1's ``seon.schema/register!``). The registration is judged against the whole population, the binary's forms with the branch's changes and this one: a form that is no EDN data, does not compile (a name resolving to nothing), or declares an attribute Datahike cannot store is refused as data (`:seon.schema/registration-refused`, naming why), and nothing is written. Accepted, the entry is written on the branch, in the resource it came from, or for a new key the resource holding most keys of its namespace; a new or changed attribute's Datahike declaration comes with it, so the branch can store its facts at once. A key in a scratch namespace (`user`, the agent's own) gets no resource: it is seen at the REPL and is no program.

The agent's REPL binds malli's dynamic registry to its branch's population before each form (`seon.repl/wrap-registry`; `seon.contract/options` puts the dynamic registry first), so the function it defines next, `seon.contract/valid?`, and every schema naming the changed key see it at once: the population is recompiled (4.6 ms for 457 forms), not the one key, because a map compiled against the old key keeps it. The registry is reused while the branch's changes are equal (keying 0.7 ms per form; compiling the population 5 ms). Every process loading a db's forms (an agent merging main, root and the fork server after a merge, a test fork) compiles them against that db's schemas the same way (`seon.program/load-forms!`, `seon.agent/run-tests-here`). Platform code compiled into the binary keeps the built schemas until the next generation builds the merged resource.

The merge carries an entry per key, `[:schema k]` -> `{:form text :file path}`, like a var (v1's `[:seon.schema/key k]` identity): two branches changing different keys of one resource merge clean, one key changed two ways conflicts at its key, and a scratch entry (no resource) is never program. Applied to main, the entry is main's, and the Datahike declarations its population needs come in the same transaction (`seon.program/schema-declarations`). The changed resource is then written back like a namespace's file (`changed-files` names it). Reading 457 entries adds 8 ms to `seon.merge/program` (80 ms to 88 ms on the test store) (`seon.merge-test/a-schema-entry-merges-per-key`).

A registration also arms again the functions the agent's process already holds whose contracts reach the changed key (the key, or a schema naming it, on and on): their contracts were compiled before it, and Seon's own code would go on checking the agent's new values against the old form. `seon.program/rearm!` finds them by the reach closure and arms each again, one `seon.contract/arm!` armed over the raw root it kept (`seon.contract/rearm!`), one the `seon.contract/defn` macro armed (which keeps no raw root) by evaluating its definition again: the source the REPL kept on its var, the text this process runs, else the branch's recorded form. Its work is the reaching vars', never the program's. One that no longer compiles is named in the registration's `:seon.schema/rearm-errors`.

A key no schema registers is answered with the nearest that do (`my.schema/unknown-key`, by Jolt's did-you-mean ranking), never nil: `(my.schema/forms k)` and `my.agent/callers` of one say so.

```my.schema/register!``` is the function and ```my.schema/registration``` judges it; ```seon.program/schema-changes``` and ```seon.program/schema-registry``` derive the branch's population; ```seon.contract/registry-of``` compiles one.

## Write-back: main's files, byte for byte

`file-text` is a namespace's live forms in their order, each after its lead, then its tail. A form recorded at a REPL has no lead: a blank line goes before it. A redefinition takes the place and the lead of the form it supersedes. Forms are written in the order the image loads them (```seon.program/load-order```: each after the earliest form that defines or declares a var it references, unless both were read from the file, whose own order already loads; a name in its quoted data is no reference): a helper recorded at a REPL after the function that now calls it is written before that function, so the file loads fresh as the image ran; a file already in that order is written byte for byte (`seon.source-test/a-helper-recorded-after-its-user-is-written-before-it`, cost `seon.source-test/the-write-back-of-a-file-is-one-pass-over-its-forms`). With no merge, import then write-back is a zero diff over all of next/src (`seon.source-test/import-then-write-back-is-a-zero-diff`). After a merge, only the files its changes touch are written: the unit of write-back is a file path (`changed-files` of the octopus merge member's changes, which the writer puts on each merged member's answer as `:files`). A changed doc's page is one of them: ```seon.doc/files``` draws it from the store as ```seon.doc/markdown``` does, byte for byte (`seon.doc-test/a-loaded-page-draws-back-as-its-file`), beside the namespaces' files and schema resources.

A schema resource is written entry by entry with rewrite-clj (v1's `schema-file-text`, ported unchanged but for the separator of an appended entry, which follows the file's last two entries): the imported text, with each entry whose form differs from what that text holds replaced in its old layout (a part that reads as before keeps its text), each key no longer held removed with its line, and each new key appended. Every other byte is as it was: adding `:refused` to `:seon.task/outcome` changes only those 9 bytes of `resources/seon/schemas/seon.facts.edn` (`seon.source-test/a-changed-schema-entry-rewrites-only-itself`).

```seon.source/file-text``` builds a namespace's file and ```seon.source/schema-resource-text``` a schema resource's (through ```seon.source/schema-file-text```); ```seon.source/files``` builds every changed file, from ```seon.source/changed-files``` of what ```seon.writer/octopus-merge``` merged; ```seon.fx/write-file``` writes one.

## Commit: the merges branch

Main is the source of truth, and syncing it to disk is an act of its own (owner, 2026-11-07): with `:seon.config.source/write-back-on-merge` false a merge writes no file, its task names what waits under `:not-on-disk`, and ```my.root/write-back!``` (`seon_write_back`) reads those files from main as it is and commits them, answering the paths and the commit, or what it couldn't. A namespace made at a REPL takes a file by its name (```seon.source/namespace-path```) with its first form, on its branch, so it merges as any other. Files neither under `:seon.config.source/dirs` nor on its allow-list have no route; ```seon.fx/uncommitted``` shows them, in ``(my.branch/changes)`` and in `seon_done`'s answer.

The reconciler asks for the write-back after an octopus merge: it reads the changed namespaces' and schema resources' files from main (```seon.source/files```) and asks the `:git` effect to commit them on the merges branch (`:seon.config.source/branch`) with a message naming each merged task. The commit uses git's plumbing (blobs, each with the mode main holds of it, ```seon.source/modes```, a tree from the branch's own, `commit-tree` as the config's committer, `update-ref` only from the head it read), so no working tree or checkout moves; a branch not there yet starts at the tree's HEAD. A branch a worktree has checked out is committed through that worktree instead (the standing root's `jolt/merges`, checked out in `.worktrees/merges`, which `:seon.config.source/root` names): each file written there, added to its index and committed, so its files, index and HEAD move together, and a change of that tree's own (one staged, or an edit of a file the write-back writes) refuses the commit, overwriting nothing (`seon.fx-test/a-write-back-onto-a-checked-out-branch-leaves-that-tree-clean`). Moved by plumbing, that tree's HEAD left its index behind, each merged file a staged deletion, and `bin/update`'s merge of main into it failed (2026-11-11). The merge already runs where main's program runs, so nothing is built. The sha is written on each merged task as `:seon.task/commit`. A failed write-back is not lost: the task holds a `:seon.git/commit-failed` error in `:seon.task/error` naming the files (```seon.reconcile/commit-tx```), quiescence names each such task as a root cause (```seon.reconcile/root-causes```), and ```my.root/write-back!``` writes them again from main as it is now; a commit clears that error (a file main has no text for stays named in a new one) and leaves the task's note of forms that name no file. Worktrees share git's refs, so a worktree's roots and tests commit on `jolt/seon-merges-<worktree>` (`:seon.config.source/branch`'s `#seon/own-branch`, which the config loader resolves from the checkout), never the main tree's `jolt/seon-merges`. `bin/check loop` proves the turn on a clone of the repository.

```seon.reconcile/reconciler-proc``` asks for it, ```seon.source/commit-message``` names the merged work, ```seon.fx/git-commit``` commits; the answer merges on the task as `:seon.task/commit`, or as its `:seon.task/error` holding a `:seon.git/commit-failed` error (`seon.reconcile/commit-tx`), which a later commit clears.

## A merged task reaches main's files

A merge commits on the merges branch, never on main, so a Seon agent's merged work reaches main's files only through a session's review (owner, 2026-11-10: "agents updating the db and then us reviewing and syncing to the file system"). Until it does, the task is an `:unsynced` problem: a merged task whose entry main's files still declare (```seon.problems/unsynced?```: its `:seon.task/declared`, which a landing that removes the entry retracts through ```seon.task/load-tx```), its row naming the files its changes touch (```seon.problems/changed-paths``` of its `:seon.task/changed` keys, as main holds them now) and the act that syncs it. That act is ```my.root/sync!```: it commits those files from main, with the task's entry removed from its task file (```seon.source/task-file-text```, every other byte kept), onto `jolt/sync-<name>`, a new branch from git's main (```my.root/sync-req``` builds the request; the `:git` effect's `:base`), and its message says `Completes:` for each task. A session reviews that branch and lands it with `bin/land`, whose bridge retracts the entry, which closes the row. The work is in git from the sync on, so a store erase loses nothing synced, and while a task is unsynced its row says so on every health read. The row's owner is the task's own namespace: no data names which session's area a namespace is in. A task made in the store with no entry in a file is not covered: no entry, no row (task `seon.reconcile/a-store-made-tasks-merge-reaches-mains-files`).

## What isn't in the program yet

What `:seon.config.source/dirs` names moves by branch: `src`, `test`, `resources/seon/schemas`, `resources/seon/config` and `bin`, with the wiki beside them. A `spit` of any of them writes the disk, which a branch holds nothing of until an import. What's left of task `seon.source/seon-files-move-by-branch` is on the task.

## The next generation

A binary is a cold-start artifact, built only for what cannot load in place: a Jolt, Chez or dependency pin, `deps.edn`, native code. Root asks for it with ```my.root/build!```: the `:build` effect builds main's last merges commit, and what happened is root's `:seon.root/generation` fact, `{:commit :checkout :binary :ms}` or `{:commit :ms :error}` naming the step and its log (a failure is also an `:effect` problem naming that fact, `seon.error/asked-tx`, closed by the next good outcome). The performer (```seon.fx/build```) makes `<:seon.config.source/generations-dir>/<sha>` a worktree of the source repository detached at the commit (`bin/worktree --at`: this checkout's submodule repos at the commit's pins, its target/ cloned, so Chez and Jolt are already built, and the compile caches shared, see [Shared build caches](#shared-build-caches)) and runs `bin/build seon` there, niced, in that tree's own environment. `bin/root next` asks the running root for ```my.root/next-generation``` through the server (the generation's tree and ```my.root/resume-args```: `--set` arguments for `:seon.config.root/store-path`, `:seon.config.root/main`, `:seon.config.source/root` (now the generation's tree, a worktree of the same repository, so the next merge commits on the same branch), its dirs, branch and the generations dir), stops the root, and starts that tree's `target/seon` with them (the test that started this root, when one did, goes along as `:seon.root/started-by`) (`bin/root run`, the tree's own config, caches and LMDB build). `bin/root start` with ```my.root/resume-args``` restarts the same binary on the same store and main. Either way the resumed main still holds the imported program and the merged forms, and the merges load at boot; a generation's tree reads as main's merges commit, so its import replaces main's program with the same text (the merged forms keep their identity and stay loaded at boot).

Merges live in place are the merging tests' (`seon.agent-test`). The next generation (`my.root/build!`, then `bin/root next`) is no test of the suite: a whole `bin/build` of a tree no build has seen took about 55 s of every merge's slow tier (owner, 2026-11-08: remove or simplify the slow tests), so it is checked where it is used. Old generations' trees are kept with the run until the owner reclaims them.

```seon.fx/build``` builds, ```my.root/build!``` asks and records, ```seon.reconcile/generation``` and ```my.root/generation``` read the fact, ```my.root/next-generation``` is what `bin/root next` starts; ```seon.e2e/loop-turn!``` is the turn (`bin/check loop` runs it on a clone); ```seon.generation/generation``` is the function it changes.

## Dependencies

Fetching a library is an outside-world effect with one owner, like write-back: the `:deps` effect kind, performed by ```seon.fx/resolve-deps```, which passes a deps map (`{lib {:mvn/version "..."}}`, ``:git/sha`` or ``:local/root``) to Jolt's own `jolt.deps/resolve-deps` (no resolver of ours) and answers `{:value {:roots [absolute source roots]}}`, or `:seon.fx/unresolved` naming the libraries that did not resolve (see [failure points](failure-points.md)). It writes only the checkout's shared caches (`.m2`, gitlibs, `.cpcache` under `HOME`), so a second resolve of the same map is a cache hit that needs no network. The asker records the outcome and decides what to load; there is no `add-deps` or `sync-deps` at the REPL, and no checksum. The effect kinds are declared under `:fx` in `resources/seon/system.edn`, and `seon.fx/procs` makes their owners.

## Shared build caches

`bin/env` points Jolt's three compile caches at ``target/cache/`` of the main tree, found from git's common dir, so every worktree and generation (`bin/worktree --at`) shares them: `build` (`JOLT_BUILD_CACHE_DIR`, build units), `runtime` (`JOLT_RUNTIME_CACHE_DIR`) and `aot` (`JOLT_CACHE_DIR`, one artifact per namespace, keyed by its source, its requires' keys and what its compile read). No key holds a checkout's path: a unit is keyed by its text and the building runtime's fingerprint, and an AOT artifact's `.res` sidecar names each file its compile read (a schema `seon.contract` slurps) and each directory it listed (`resources/seon/schemas`, the checkout root `seon.ref/roots` lists) relative to the project root, so a checkout hashes its own files (Jolt ``jolt/cache-records-relative``). Entries and sidecars are published by temp+rename, so concurrent builds are safe; `JOLT_CACHE_GENERATIONS` (4) runtimes are kept, one per Jolt pin in use, and the AOT cache is kept under `JOLT_CACHE_MB` (the config key `:seon.config.build/jolt-cache-mb`, which bin/env reads from its line as it reads the compiler options; 32768 while we develop, so nothing is evicted: owner, 2026-11-11; measured 2026-11-11, one worktree's builds and tests on a new runtime filled 354 MB in 890 artifacts, and every session's on one runtime over a day and a half 3.2 GB, so 4 GB holds one checkout's working set about ten times over: task `jolt.loader/the-cache-bound-is-tested-at-the-targets-size-before-release`) across its generations, least recently used first: a hit moves its artifact's `.so` mtime to now, a process that publishes prunes once, nothing younger than a minute goes, and a `.so` goes before its `.scm`, so a reader sees a whole artifact or a miss, and an artifact deleted before its load recompiles (Jolt's `aot-prune-to-budget!`, gate `aotcachebudget`). `bin/worktree` clones neither these caches nor a checkout's old `target/home/.jolt` copies of them. `bin/build` clears nothing on a schema change: an edited schema file misses its 52 dependents of `seon.contract`, a schema file added to the directory moves the same keys. One sidecar holds the last compile's names, so two checkouts whose reads differ in which files exist (a worktree session that added a schema) take turns: each misses those namespaces once after the other built (measured: 41 misses, +6 s), never loading the other's artifact. Measured: an unchanged `bin/build seon` 25 s, pass 1 1.1 s, 263/263 hits; a fresh generation worktree (`bin/worktree --at`, 2.0 s, `target/home` 82 MB where the clone was 1.3 GB) builds from the shared cache in 24 s, pass 1 1.3 s, 263/263 hits; a namespace edited and built in one worktree is a hit in the next (16 misses there, 0 here); `bin/cache-smoke` checks that every checkout names the same three directories. `bin/env` also exports Jolt's compile options, `JOLT_COMPILER_OPTIONS` `{:image-fn-forms false}`, which Jolt reads into `*compiler-options*`' root at start: Seon writes no state image, so its build, tests, root and agents compile without registering fn literals' sources for one (a third less allocation a compile; task jolt.backend/image-registration-is-opt-in). The AOT key does not include it, so an artifact compiled with registration loads into a process without it and the reverse: harmless here, since nothing writes an image.
