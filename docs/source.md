# Seon's own source is the program

The self-improvement loop (owner, 2026-10-21): agents change Seon's own functions on their branches, the merge lands them on main, main's files are written back exactly and committed on a merges branch, and the merge runs at once where main's program runs: root, the fork server and every agent forked after it load it in place, with no build and no restart (BUILD plan P4). A binary is built only for what cannot load in place, and a restart catches up on main's merges at boot. This page is how each step works and what it records.

## Import: the running generation's source as main's program

With `:source {:root dir :dirs ["src"] :branch "jolt/seon-merges"}` (or the config's `:seon.config.source/root`, with `:seon.config.source/dirs` and `:seon.config.source/branch`; a run states it with `--set :seon.config.source/root=\"dir\"`), root reads the tree through the `:source` effect at boot, when main holds no imported namespace yet. Each file is read form by form with its exact text, the whitespace and comments before each form (`:form/lead`) and the text after the last (`:ns/tail`). Each form is analyzed by Jolt's compiler without running it, giving the same account an agent's REPL records. What happened is root's `:seon.root/source` fact (files, forms, ms, or the error).

A file is analyzed against its own ns form, whether the binary loaded its namespace or not (test/'s namespaces it never loads; a task's proofs live there, so a root imports `["src" "test"]`). As loading does: the ns form of a namespace whose lib the process has not loaded (`clojure.core/loaded-libs`, not merely `find-ns`) is run before the forms after it are read and analyzed, so its aliases resolve `d/q` and `::z/k`; and files are analyzed in require order (each after the imported files its ns form requires, by the compiler's analysis of that form; ties by path), so a namespace only the import defines is set up before a file requiring it. Running an ns form still loads the libraries it requires, so a file whose libraries the binary cannot load does not import (task `jolt.ns/a-built-binary-requires-a-stdlib-namespace-it-did-not-compile`: `seon.print-test` requires `fipp.engine`, which needs `clojure.core.rrb-vector` from Jolt's stdlib).

Imported forms carry `:form/source true`: the binary already holds them compiled. Every other form of main runs where main's program runs, platform namespaces included (see [a merge loads in place](#a-merge-loads-in-place)). Measured on next/src: 54 files, 1,168 forms, 418 ms of analysis and 1.0 s to transact in the test runtime; 1.5 s at a root's boot. With test/r3, test/next and test/build too (lane TESTS, 2026-10-21): 64 files, 2.26 s at a root's boot; the other 26 files of test/seon analyze in 228 ms in a booted root.

Schemas are program too (owner, 2026-10-21; v1's rule, the program is entities): with `resources/seon/schemas` among the dirs (shipped: `["src" "resources/seon/schemas"]`), each schema resource is imported as one `:schema.file` entity holding its text (the base write-back edits) and one `:schema/key` entity per entry, its form as EDN text, its `:schema/file`, and `:schema/source` (the binary holds it compiled, like `:form/source`). Measured: all 21 resources import and write back byte for byte.

```seon.root/start!``` asks for the import (`:seon.config.source/*` in ```seon.root/start!```'s opts or the config); ```seon.fx/read-source``` reads the tree; ```seon.source/read-forms``` keeps each form's exact text and lead (with a step taken before the next form is read), ```seon.source/accounts``` analyzes them through ```seon.source/analyze-form```, ```seon.source/import-tx``` orders the files by ```seon.program/topo```, ```seon.source/text-tx``` and ```seon.source/import-tx``` write `:ns/file`, `:ns/tail`, `:form/lead` and `:form/source`; ```seon.source/schema-tx``` writes a schema resource's facts (```seon.source/schema-resource?``` names one); ```seon.source/file-ns``` and ```seon.source/source-files``` name what was imported. ```seon.program/load-all!```, ```seon.program/load-diff!``` and ```seon.program/load-changes!``` skip the imported text.

## A merge loads in place

A merge of main runs where main's program runs, at once: root's writer, the fork server (so every agent forked after it inherits the change compiled, copy-on-write) and an agent merging main call ```seon.program/load-changes!``` with the commit's tx-data. It loads each live form the commit asserts but the binary's own text (`:form/source`), and removes each definition the commit leaves pointing to no form. A restart loads main's every form but the binary's own at boot (```seon.program/load-all!```), so a binary older than main's merges catches up; a resumed agent loads its branch's difference (```seon.program/load-diff!```).

One load adds what a change reaches, as v1's declaration-reload-rule and clj-reload do: the forms a changed macro expanded in (its namespace and every namespace requiring it, since an expansion leaves no reference: ```seon.program/dependents```) and the forms whose contracts a changed schema entry reaches, through the schemas naming it, loaded against main's population so their contracts re-arm (```seon.program/schema-dependents```). A protocol or a record needs none on Jolt: a record's dispatch and an `instance?` test held by the binary see the redefinition. A redefinition reaches the binary's compiled callers because a direct-linked call reads its var's linked binding, which every redefinition writes through, and a contracted definition is never spliced (`bin/check hotreload`, BUILD plan P3).

Measured on 2026-10-21 (lane INPLACE, `bin/check loop` on a clone, 1,646 forms): the merged `seon.fixtures/generation` answers 2 in root and in an agent forked after the merge; the turn from release to quiet is 13.4-13.9 s (the implement attempt ~5 s, the merge attempt ~7 s, the commit and quiescence ~1.6 s), down from 84-96 s with a build per merge. What remains is whole-program reads per merge (`seon.merge/program-cost-follows-what-changed`).

## A file an agent loads is its REPL's

An agent works the way a Clojure user does: it edits a file in its own directory (its private copy of the source root) and `(require 'that.ns :reload)` or `(load-file "src/that/ns.clj")`. Each form the load reads from a file in that directory goes through the agent's REPL path, as if typed at it: its REPL binds `jolt.host/*load-form*` (a loader hook, [forks](forks.md)) to ```seon.repl/loaded-form```, which evaluates the form through the same middleware that makes a typed form the branch's program (registry, record, admit) and keeps its exact text; a form that did not change records nothing new. Clojure's semantics stay: `require` answers nil, `*ns*` is restored, and a form that fails fails the load with its cause. A file written and never loaded is the agent's scratch; a library's file (the reference-code link resolves outside the agent's directory) loads as the loader would.

## Tests run by reach

A test runs only when something it reaches changed since it was last green, in any checkout (owner, 2026-10-21: "incremental tests even across worktrees based on test digest"; task `seon.program/tests-run-by-reach`). ```seon.program/reach-digests``` gives each test of a db its reach digest: its own form, its namespace's forms that define no var (the ns form, fixtures), and every live form their `:form/refs` reach (a var to the form that last defined it; a defined multimethod's methods and protocol's extensions), each form digested once; plus the checkout's inputs with no program facts (`test-runner/inputs`: deps.edn, bin/, resources/ with the schemas contracts name, test fixtures and every submodule pin, Jolt's included; not task files or prose), plus the whole tree for a test whose reached forms call a file reader (`seon.program/tree-readers`). A test's digest moves exactly when a form it reaches does, so the tests a change selects are `seon.program/reaching-tests` of what it changed.

`bin/test --reach [NS ...]` imports src and test as program facts (```seon.source/import-tx```, the facts root and agents record), reuses every result green at its digest and runs the rest, storing each result `{:test :digest :pass :fail :error :ms}` as `<digest>.edn` in the one directory every checkout and worktree shares (`:seon.config.source/test-results-dir`, `~/src/seon-jolt/test-results`, written temp-then-rename by ```seon.fx/write-file```). A checkout's store is its own (`runs/store`), so the store cannot be that home. A landing runs `bin/test --reach` on the merged tree: what the change reaches, minus what is green at its digest.

An agent holds main's whole suite (the fork server loads test/ like any imported namespace), and its test run selects by the same reach: ```seon.agent/test-vars``` is the task's accumulated proofs, plus the tests `seon.program/reaching-tests` finds from ```seon.program/changed-vars``` (each var whose `:var/form` differs between the main the agent forked from and its branch), the changed tests among them. That is exactly what `seon.reconcile/done-refusals` reads: the proofs, and the tests whose red would be a regression or a stray red. Root's `:tests` request names the agent's task; the turn loop passes its own. Measured 2026-10-22 on a root holding src and test (308 tests): one redefined function selected 2 tests (the proof and the one test reaching it) in 4 ms, and the forked run took 10 ms, where the whole suite never answered within 60 s.

Not this: a hand list of the tests a change touches, or a result keyed by time or by checkout path. Known gaps: a test reading files through a reader outside `tree-readers`, or resolving a var by name at run time, is digested without it; the import costs about 9 s per run (by file, incrementally, is the next step).

## Schemas at the REPL

An agent changes a schema the way `defn` changes a function: `(my.schema/register! k form)` on its branch (v1's `seon.schema/register!`). The registration is judged against the whole population, the binary's forms with the branch's changes and this one: a form that is no EDN data, does not compile (a name resolving to nothing), or declares an attribute Datahike cannot store is refused as data (`:seon.schema/registration-refused`, naming why), and nothing is written. Accepted, the entry is written on the branch without `:schema/source` (the binary does not hold it), in the resource it came from, or for a new key the resource holding most keys of its namespace; a new or changed attribute's Datahike declaration comes with it, so the branch can store its facts at once. A key in a scratch namespace (`user`, the agent's own) gets no resource: it is seen at the REPL and is no program.

The agent's REPL binds malli's dynamic registry to its branch's population before each form (`seon.repl/wrap-registry`; `seon.contract/options` puts the dynamic registry first), so the function it defines next, `seon.contract/valid?`, and every schema naming the changed key see it at once: the population is recompiled (4.6 ms for 457 forms), not the one key, because a map compiled against the old key keeps it. The registry is reused while the branch's changes are equal (keying 0.7 ms per form; compiling the population 5 ms). Every process loading a db's forms (an agent merging main, root and the fork server after a merge, a test fork) compiles them against that db's schemas the same way (`seon.program/load-forms!`, `seon.agent/run-tests-here`). Platform code compiled into the binary keeps the built schemas until the next generation builds the merged resource (owner, 2026-10-21).

The merge carries an entry per key, `[:schema k]` -> `{:form text :file path}`, like a var (v1's `[:seon.schema/key k]` identity): two branches changing different keys of one resource merge clean, one key changed two ways conflicts at its key, and a scratch entry (no resource) is never program. Applied to main, the entry is main's (its `:schema/source` retracted), and the Datahike declarations its population needs come in the same transaction (`seon.program/schema-declarations`). The changed resource is then written back like a namespace's file (`changed-files` names it). Reading 457 entries adds 8 ms to `seon.merge/program` (80 ms to 88 ms on the test store) (`seon.merge-test/a-schema-entry-merges-per-key`).

```my.schema/register!``` is the verb and ```my.schema/registration``` judges it; ```seon.program/schema-changes``` and ```seon.program/schema-registry``` derive the branch's population; ```seon.contract/registry-of``` compiles one.

## Write-back: main's files, byte for byte

`file-text` is a namespace's live forms in their order, each after its lead, then its tail. A form recorded at a REPL has no lead: a blank line goes before it. A redefinition takes the place and the lead of the form it supersedes. With no merge, import then write-back is a zero diff over all of next/src (`seon.source-test/import-then-write-back-is-a-zero-diff`). After a merge, only the files its changes touch are written: the unit of write-back is a file path (`changed-files` of the train member's changes, which the writer puts on each merged member's answer as `:files`).

A schema resource is written entry by entry with rewrite-clj (v1's `schema-file-text`, ported unchanged but for the separator of an appended entry, which follows the file's last two entries): the imported text, with each entry whose form differs from what that text holds replaced in its old layout (a part that reads as before keeps its text), each key no longer held removed with its line, and each new key appended. Every other byte is as it was: adding `:refused` to `:seon.attempt/status` changes only those 9 bytes of `seon.facts.edn` (`seon.source-test/a-changed-schema-entry-rewrites-only-itself`).

```seon.source/file-text``` builds a namespace's file and ```seon.source/schema-resource-text``` a schema resource's (through ```seon.source/schema-file-text```); ```seon.source/files``` builds every changed file, from ```seon.source/changed-files``` of what ```seon.writer/merge-branch``` merged; ```seon.fx/write-file``` writes one.

## Commit: the merges branch

The reconciler asks for the write-back after a train lands: it reads main, computes the files, and asks the `:git` effect to commit them on the merges branch with a message naming each merged task and attempt. The commit uses git's plumbing (blobs, a tree from the branch's own, `commit-tree`, `update-ref` from the head it read), so no working tree or checkout moves; a branch not there yet starts at the tree's HEAD. The sha is recorded on each merged attempt as `:seon.attempt/commit`, or the refusal as `:seon.attempt/commit-error`. `bin/check loop` proves the turn on a clone of the repository.

```seon.reconcile/reconciler-proc``` asks for it, ```seon.source/commit-message``` names the merged work, ```seon.fx/git-commit``` commits; the answer lands on the attempt as `:seon.attempt/commit` or `:seon.attempt/commit-error`.

## The next generation

A binary is a cold-start artifact, built only for what cannot load in place: a Jolt, Chez or dependency pin, `deps.edn`, native code. Root asks for it with ```my.root/build!```: the `:build` effect builds main's last merges commit, and what happened is root's `:seon.root/generation` fact, `{:commit :checkout :binary :ms}` or `{:commit :ms :error}` naming the step and its log. The performer (```seon.fx/build```) makes `<:seon.config.source/generations-dir>/<sha>` a worktree of the source repository detached at the commit (`bin/worktree --at`: this checkout's submodule repos at the commit's pins, its target/ cloned, so Chez and Jolt are already built, and the compile caches shared, see [Shared build caches](#shared-build-caches)) and runs `bin/build seon` there, niced, in that tree's own environment. `bin/root next` asks the running root for ```my.root/next-generation``` through the entrance (the generation's tree and ```my.root/resume-args```: `--set` arguments for `:seon.config.root/store-path`, `:seon.config.root/main`, `:seon.config.source/root` (now the generation's tree, a worktree of the same repository, so the next merge commits on the same branch), its dirs, branch and the generations dir), stops the root, and starts that tree's `target/seon` with them (`bin/root run`, the tree's own config, caches and LMDB build). `bin/root start` with ```my.root/resume-args``` restarts the same binary on the same store and main. Either way the resumed main still holds the imported program and the merged forms, so nothing is imported again and the merges load at boot.

Proven by `seon.source-test/a-restart-catches-up-and-a-new-generation-resumes` (lane INPLACE, 2026-10-21, a clone of this checkout): two merges live in place; root SIGKILLed and the same binary started on the same main runs both; `my.root/build!` then `bin/root next` runs both on the new binary, main holding its generation. 96 s for the whole test. Not yet: the tree's own commits made outside Seon do not reach a resumed main, and old generations' trees are kept with the run until the owner reclaims them.

```seon.fx/build``` builds, ```my.root/build!``` asks and records, ```seon.reconcile/generation``` and ```my.root/generation``` read the fact, ```my.root/next-generation``` is what `bin/root next` starts; ```seon.e2e/loop-turn!``` is the turn (`bin/check loop` runs it on a clone); ```seon.fixtures/generation``` is the function it changes.

## Dependencies

Fetching a library is an outside-world effect with one owner, like write-back: the `:deps` effect kind, performed by ```seon.fx/resolve-deps```, which passes a deps map (`{lib {:mvn/version "..."}}`, `:git/sha` or `:local/root`) to Jolt's own `jolt.deps/resolve-deps` (no resolver of ours) and answers `{:value {:roots [absolute source roots]}}`, or `:seon.fx/unresolved` naming the libraries that did not resolve (see `DRAGONS.md`). It writes only the checkout's shared caches (`.m2`, gitlibs, `.cpcache` under `HOME`), so a second resolve of the same map is a cache hit that needs no network. The asker records the outcome and decides what to load; `add-deps` and `sync-deps` at the REPL, and checksums, are later Jolt steps (the PKG plan, step one). Related: the other kinds in ```seon.fx/kinds```.

## Shared build caches

`bin/env` points Jolt's three compile caches at `target/cache/` of the main tree, found from git's common dir, so every worktree and generation (`bin/worktree --at`) shares them: `build` (`JOLT_BUILD_CACHE_DIR`, build units), `runtime` (`JOLT_RUNTIME_CACHE_DIR`) and `aot` (`JOLT_CACHE_DIR`, one artifact per namespace, keyed by its source, its requires' keys and what its compile read). No key holds a checkout's path: a unit is keyed by its text and the building runtime's fingerprint, and an AOT artifact's `.res` sidecar names each file its compile read (a schema `seon.contract` slurps) and each directory it listed (`resources/seon/schemas`, the checkout root `seon.ref/roots` lists) relative to the project root, so a checkout hashes its own files (Jolt `jolt/cache-records-relative`). Entries and sidecars are published by temp+rename, so concurrent builds are safe; `JOLT_CACHE_GENERATIONS` (4) runtimes are kept, one per Jolt pin in use. `bin/worktree` clones neither these caches nor a checkout's old `target/home/.jolt` copies of them. `bin/build` clears nothing on a schema change: an edited schema file misses its 52 dependents of `seon.contract`, a schema file added to the directory moves the same keys. One sidecar holds the last compile's names, so two checkouts whose reads differ in which files exist (a lane that added a schema) take turns: each misses those namespaces once after the other built (measured: 41 misses, +6 s), never loading the other's artifact. Measured 2026-10-21 (lane J2): an unchanged `bin/build seon` 25 s, pass 1 1.1 s, 263/263 hits; a fresh generation worktree (`bin/worktree --at`, 2.0 s, `target/home` 82 MB where the clone was 1.3 GB) builds from the shared cache in 24 s, pass 1 1.3 s, 263/263 hits; a namespace edited and built in one worktree is a hit in the next (16 misses there, 0 here); `bin/cache-smoke` checks that every checkout names the same three directories.
