# Seon's own source is the program

Seon's own source is main's program: agents change Seon's own functions on their branches, the merge brings them into main, main's files are written back exactly and committed on a merges branch, and the merge runs at once where main's program runs: root, the fork server and every agent forked after it load it in place, with no build and no restart. A binary is built only for what cannot load in place, and a restart catches up on main's merges at boot. This page is how each step works and what it records.

## Import: the running generation's source as main's program

At every boot root imports its checkout's source tree as main's program, replacing main's program when the files read otherwise than at the last import; the boot as a whole is [root](root.md#boot). (A root started without `--profile` has no model provider: [model](model.md#no-default-model).)

The defaults: `bin/root start` with no store makes one and builds main from the checkout's own source (`:seon.config.source/root` defaults to `SEON_SOURCE_ROOT`, which `bin/root` sets to its checkout); its dirs are `src`, `test` (a task's proofs and fixtures, which an agent holds only when main imported them) and the schema resources (```seon.config/value``` of `:seon.config.source/dirs`); with a store it resumes it; `--set` or `config/local.edn` override either (the main tree's names `.worktrees/merges`, the tree its merges write back into, so main's working copy stays the owner's). `bin/test`, `bin/check` and the roots tests boot import nothing unless they state a source. `bin/update` brings the standing root up to date with main, reading the write-back tree's path from the main tree's `config/local.edn` (`:seon.config.source/root`) and failing, not skipping, when that tree is not there: it merges ``jolt/merges`` (the main tree's merges branch, named in its `config/local.edn`; the shipped default is ``jolt/seon-merges``) into main, syncs submodules, builds, and restarts the root. The source tree follows main by itself: every read of it (boot, each `:source` load) first fast-forwards it to the ref of the branch `main` when it is an ancestor (`seon.fx/read-source`'s `:follow`, read in the main tree's repository: whatever branch the main tree has checked out changes nothing root reads, `seon.source-test/the-standing-root-follows-main-not-the-checkouts-head`), so main's program is never stale; a tree holding commits main lacks, or one git refuses to fast-forward, is imported as it is and the gap is a recorded `:seon.fx/io-error` naming why. A watched change reads only the files it names (`:paths`), and a read in a git repository also answers `:tree`, the id of the whole tree as it is on disk. Root's watch reads the source root's dirs and fires on the refs of the checkout's branch and of the source root's, so the watch and the import name one tree.

With `:source {:root dir :dirs ["src"] :branch "jolt/seon-merges"}` (or the config's `:seon.config.source/root`, with `:seon.config.source/dirs` and `:seon.config.source/branch`; a run states it with `--set :seon.config.source/root=\"dir\"`), root reads the tree through the `:source` effect at every boot: its files and its HEAD commit. Each file is read form by form with its exact text, the whitespace and comments before each form (`:form/lead`) and the text after the last (`:ns/tail`). Each form is analyzed by Jolt's compiler without running it, giving the same account an agent's REPL records. What happened is root's `:seon.root/source` fact (the tree's commit, the digest of the files read, files, forms, the program entities retracted, ms, or the error).

### Main's program follows the tree

Main's program is the tree's: at each boot, when the files read differently from main's last import (their digest differs from the fact's `:digest`, or none is recorded), main's program is replaced by the tree's in one transaction, ```seon.source/replace-tx```; when they read the same, nothing is imported or written. So a resumed main follows its tree when worktree sessions merge and the tree moves on in git, or the next generation's tree holds Seon's own merges commit. Re-importing changed files alone would not do: a form's identity is its text (`seon.program/account-tx`), so a changed file's new forms would join its old ones, and a removed function would stay live. `replace-tx` is ```seon.source/import-tx```, read against main without the forms of the imported namespaces (each form takes its file's order and lead), with every program entity of those namespaces and of the schema resources that the import no longer makes retracted: a changed function's old form, a removed function's form and var, a removed file's namespace. Data (tasks, runs, turns, config and root facts) and the program of a namespace no file holds (an example program, a namespace an agent made) are untouched; history keeps the old program. A form or schema entry main holds already keeps its `:form/source` as it is, so a form merged in (which the binary does not hold) is still loaded at boot, and a form new to main is the binary's. The digest is of what was read (the files and the reference-code pins), not of the commit alone, so uncommitted edits in the tree count, and a merges commit made by `update-ref` under a checked-out tree (its files unchanged) imports nothing.

Measured on next/src and the schemas (80 files, 1,660 forms, test runtime): the same tree replaced on itself is 0 retractions, ```seon.source/import-tx``` 0.5 s, ```seon.source/replace-tx``` 3.6 s and its transaction 0.8 s; one changed form, 1 retraction. Of replace-tx's 3.6 s, 3.0 s is the in-memory retraction that reads main without the forms; reading main through `datahike.api/filter` instead gives the same transaction in 0.6 s, once `:seon.host/db` admits a filtered db. A boot whose tree reads the same reads the files and digests them (no analysis). Proven by `seon.source-test/a-moved-tree-replaces-mains-program` and, three boots of a built root, `seon.root-test/main-follows-its-source-tree-across-restarts`.

A change re-imports only what it reaches, and writes only what changed. ```seon.source/refresh-tx``` (proven by `seon.source/an-import-reads-only-changed-files`; root's boot import still calls `replace-tx`) takes the files that changed (a removed one's text nil) and reads their namespaces again. It reads a namespace that requires one of them only when what dependents read of it was lost (```seon.source/interface```: each definition's name and kind, plus the text of its ns form and of each macro, protocol, type or inline function): a name removed or of another kind reads the dependents that reference it, and a changed macro, protocol, type or inline function reads every dependent; what was added breaks no form. A body edit therefore reads one file whatever requires it. Each form is then compared with what db holds (```seon.program/account-diff-tx```): an unchanged form writes nothing, a moved one only its order and lead, a changed one its facts with the stale ones retracted. The result is the same program as ```seon.source/replace-tx``` of the whole tree, which is the same diff over every file. Measured on Seon's src and test (110 files, 2,667 forms, load ~8): a body edit in the 29-form test/seon/cost_test.clj was 151 ms plus 25 ms to transact, and is now 33 ms plus 3 ms. That splits into read and analysis 20 ms, the interface gate 2 ms, the diff and tx 9 ms, and one form written. A body edit in `seon.edn`, which 21 namespaces require, costs 2 ms and reads none of them. Each phase's cost is flat from 10 to 1,000 forms of other files (```seon.source-test/a-fixed-change-costs-the-same-at-any-program-size```). A constant's value change is not in the interface (an account does not carry ^:const), so it does not re-read dependents.

Not this: re-importing the files that changed (old forms stay live). When main's merged forms and a worktree session's edits to the same function meet, the tree wins; there is no three-way merge of the tree's commit into main. `seon.program/load-all!` runs before the import at boot, so a namespace the binary does not build (test/'s) runs its old forms in root and the fork server until the next boot.

A file is analyzed against its own ns form, whether the binary loaded its namespace or not (test/'s namespaces it never loads; a task's proofs live there, so a root imports `["src" "test"]`). As loading does: the ns form of a namespace whose lib the process has not loaded (`clojure.core/loaded-libs`, not merely `find-ns`) is run before the forms after it are read and analyzed, so its aliases resolve `d/q` and `::z/k`; and files are analyzed in require order (each after the imported files its ns form requires, by the compiler's analysis of that form; ties by path), so a namespace only the import defines is set up before a file requiring it. Running an ns form still loads the libraries it requires, so a file whose libraries the binary cannot load does not import (task `jolt.ns/a-built-binary-requires-a-stdlib-namespace-it-did-not-compile`: `seon.print-test` requires `fipp.engine`, which needs `clojure.core.rrb-vector` from Jolt's stdlib).

Imported forms carry `:form/source true`: the binary already holds them compiled. Every other form of main runs where main's program runs, platform namespaces included (see [a merge loads in place](#a-merge-loads-in-place)). Measured on next/src: 54 files, 1,168 forms, 418 ms of analysis and 1.0 s to transact in the test runtime; 1.5 s at a root's boot. With test/r3, test/next and test/build too: 64 files, 2.26 s at a root's boot; the other 26 files of test/seon analyze in 228 ms in a booted root.

Schemas are program too (v1's rule: the program is entities): with `resources/seon/schemas` among the dirs (shipped: `["src" "resources/seon/schemas"]`), each schema resource is imported as one `:schema.file` entity holding its text (the base write-back edits) and one `:schema/key` entity per entry, its form as EDN text, its `:schema/file`, and `:schema/source` (the binary holds it compiled, like `:form/source`). All 24 resources import and write back byte for byte (`seon.source-test/import-then-write-back-is-a-zero-diff`).

`seon.root/start!` asks for the import with ```seon.root/import-source!``` (`:seon.config.source/*` in its `:source` opts or the config); ```seon.fx/read-source``` reads the tree; ```seon.source/read-forms``` keeps each form's exact text and lead (with a step taken before the next form is read), ```seon.source/accounts``` analyzes them through ```seon.source/analyze-form```, ```seon.source/import-tx``` orders the files by ```seon.source/load-order```, ```seon.source/text-tx``` and ```seon.source/import-tx``` write `:ns/file`, `:ns/tail`, `:form/lead` and `:form/source`; ```seon.source/schema-tx``` writes a schema resource's facts (```seon.source/schema-resource?``` names one); ```seon.source/file-ns``` and ```seon.source/source-files``` name what was imported; ```seon.source/replace-tx``` makes main's program the tree's, asked by `seon.root/import-source!`, which records the digest on root's `:seon.root/source` fact. ```seon.program/load-all!```, ```seon.program/load-diff!``` and ```seon.program/load-changes!``` skip the imported text.

## A merge loads in place

A merge of main runs where main's program runs, at once: root's writer (`seon.writer`), the fork server (`seon.fork-server/server-step`) (so every agent forked after it inherits the change compiled, copy-on-write) and an agent merging main call ```seon.program/load-changes!``` with the commit's tx-data. It loads each live form the commit asserts but the binary's own text (`:form/source` in a namespace this process holds, every var it defines bound: a form a re-import adds to a test namespace loaded at boot is loaded, not left for an agent's stage to read as an unmap; `seon.source-test/a-form-imported-into-a-loaded-namespace-is-loaded-not-unmapped`), and removes each definition the commit leaves pointing to no form. A restart loads main's every form but the binary's own at boot (```seon.program/load-all!```; root leaves test namespaces out, [below](#a-process-holds-the-tests-only-when-it-runs-them)), so a binary older than main's merges catches up; a resumed agent loads its branch's difference (```seon.program/load-diff!```), which reads only the datoms that differ between the two dbs (```seon.program/diff-plan```), the cost of the diff, never of the program.

### A process holds the tests only when it runs them

Root imports `test/` as program facts (reach digests, an agent's plan and the task pages read them) and evaluates none of it: `seon.program/load-all!` at boot and `seon.program/load-changes!` in root's writer are called with `{:tests? false}`, which leaves out the forms of every namespace read from a file outside `:seon.config.source/program-dirs` (```seon.program/test-nss```; a namespace with no file, an agent's app or a test store's example program, is not one). Root never runs a deftest: tests run in an agent's test child and in `bin/test`'s shards. The fork server loads them once, at its first fork (`seon.fork-server/serve`'s `:fork`, `load-all!` with no option, its errors sent to root as `:load-errors`; a root that forks no agent never loads them, and the server reads root's socket from its boot: a stop that came during the load waited 12-21 s for it), each namespace whose live forms are all its file's as imported loaded whole by `require` through Jolt's AOT cache (`JOLT_CACHE_DIR`, bin/env: compiled once by the first process, loaded compiled by every later one; main's 78 test namespaces 12.2 s evaluated form by form, 0.70 s loaded warm, 2026-10-30) and any other form by form (```seon.program/required!```), and then with each commit it hears of (`load-changes!`), so every agent and test child forked from it inherits main's tests compiled, as read-only pages that cost no RAM until written ([cost](cost.md#how-we-measure)); the first fork waits behind the load (about 15 s of compiling under load 12 on 1,822 forms; the load runs once per server, a standby inherits it). A root's REPL may load them on request (`(seon.program/load-all! @(:conn sys))`), as any REPL loads what it is about to call. Measured on a scratch root (resumed store, the same binary, live heap after a full collection): 714 MB allocated with 450 MB static and 264 MB outside it, against 856 MB and 406 MB once root also evaluates the 1,822 test forms (-142 MB live, -122 MB footprint of the same process, 901 against 1,023 MB); the fork server, which now holds them, is 622 MB footprint. Proven by `seon.source-test/root-loads-the-program-and-leaves-test-namespaces-unevaluated` and `seon.agent-test/root-holds-no-test-code-and-its-agents-hold-mains-tests`.

One load adds what a change reaches, as v1's declaration-reload-rule and clj-reload do: the forms a changed macro expanded in (its namespace and every namespace requiring it, since an expansion leaves no reference: ```seon.program/dependents```) and the forms whose contracts or code name a changed schema entry, through the schemas naming it, loaded against main's population so their contracts re-arm (```seon.program/schema-dependents```). A protocol or a record needs none on Jolt: a record's dispatch and an `instance?` test held by the binary see the redefinition. A redefinition reaches the binary's compiled callers because a direct-linked call reads its var's linked binding, which every redefinition writes through, and a contracted definition is never spliced (`bin/check hotreload`).

Measured by `bin/check loop` on a clone (1,646 forms): the merged `seon.generation/generation` answers 2 in root and in an agent forked after the merge; the turn from release to quiet is 13.4-13.9 s (the implement run ~5 s, the merge run ~7 s, the commit and quiescence ~1.6 s). What remains is whole-program reads per merge (`seon.merge/program-cost-follows-what-changed`).

## An agent changes code at its REPL

An agent changes the program by `in-ns` and `defn` at its REPL: each form it evaluates there is its branch's change. It removes a definition as Clojure does, `(ns-unmap 'n 's)`: the eval observes the var gone and retracts its definition on the branch, saying so (`:unmapped`, `seon.repl/unmapped`), as v1's REPL recorded it; nothing refuses an unmap a caller still needs, which fails where that caller loads and in its tests. `require` and `load-file` load as in Clojure and record nothing. Its working directory is a scratch dir with no repository above it (`:seon.config.agent/cwd`, made and entered by the boot server's ```seon.fork-server/main```; every agent forks from it): it reads and writes any file by its path, git finds nothing, and editing source files is not how Seon develops.

## A form's account is the program's facts

A form's account is what the compiler said of one top-level form, and the program is these accounts as entities: a form entity (its exact text, namespace and place) and, for each definition the form made (a var, a multimethod's method, a protocol extension, a namespace), a pointer to it. Nothing reads a form's text to learn what it is.

An eval is accounted by what the analyzer saw and what the run did. ```seon.program/tap``` is bound around the eval as the analyzer's unit tap: it collects each analyzed unit and the root each var it defines held before (```seon.program/root-of```, `::unbound` when none), and calls no contracted function, so the tap stays out of the eval's own cost. After the run ```seon.program/set-vars``` is the readback: the vars whose root is no longer the one before, in any namespace. ```seon.program/account``` joins the units, the exact text and the namespace, and answers nil when the form is none of the program's: its namespace is scratch (```seon.program/scratch-ns?```: `user`, or declared `^:scratch`), or it defines, declares and extends nothing and changes no environment. Its account also holds the calls of ```seon.program/banned``` vars (which `seon.merge/mutations` reports). A contract is stored as EDN text (```seon.edn/encode```, no print limits and no metadata; ```seon.edn/decode``` reads it back) when ```seon.program/edn-value?``` holds of the live value, else as the form was written.

Identities are content. ```seon.program/form-id``` is the namespace and the hash of the exact text (hasch's uuid, the one Datahike names content by), with the occurrence number for a repeated text of an imported file. A method is its ```seon.program/method-key``` (`[multi dispatch]`, printed), an extension its ```seon.program/impl-key``` (`[protocol type]`), and ```seon.program/pointer``` names the attribute by which each kind of definition points to its form. ```seon.program/def-eid``` finds a definition's entity on a db; ```seon.program/def-ref``` names it in a transaction (its entity, or an upsert by identity under a tempid, `seon.program/ns-tid` and `seon.program/form-tid` being the tempid texts, since Datahike allocates a tempid at the first place it is seen as a ref). ```seon.program/form-tx``` is one form as an entity map; ```seon.program/def-tx``` makes a definition point at a form and retracts what it held that the new content lacks; ```seon.program/account-tx``` joins them (the form keeps its order if db holds it, else takes the place of the forms it supersedes, else goes last) and retracts each form all of whose definitions it redefines; ```seon.program/record-tx``` is that for an eval on the branch's db, after every form so far.

What a definition says of itself that wiki text relies on is ```seon.program/meaning``` (its contract and its docstring). ```seon.program/meaning-changes``` reads an eval's definitions before they are transacted and answers, for each existing var whose meaning changes, what it was, what it becomes and the wiki sections citing it, at the cost of the tx-data and one entity read and one index seek a var.

A form is live when it defines nothing (a `declare`, a `require`, a comment kept from its file) or some definition still points to it (```seon.program/live?```); a form all of whose definitions point to later forms is superseded and no part of the program. ```seon.program/form-row``` reads a form entity as the loader and the merge read it (from one seek of the entity's datoms and one of each namespace, definition and declared var it names: 6.9 k ticks and 21 KB a row where the entity's attribute-by-attribute reads were 35 k and 96 KB), ```seon.program/live-forms``` every live form of a db in entity order. ```seon.program/attr-namespaces``` are the namespaces of the attributes that hold the program (forms, definitions, schema, the db's own schema): what a merge carries as program, and what a commit must touch to count as moving it (`moves-program?`, [merging](merging.md#the-test-service)). A file at an old commit has the same identities without analysis: ```seon.source/defining-ids``` finds the form defining each var by its head and name and gives the id the account would give, so a wiki baseline is read without loading anything.

## Tests run by reach

A test runs only when something it reaches changed since it was last green, in any checkout (task `seon.program/tests-run-by-reach`). ```seon.program/graph-index``` gives each test of a db its reach digest: its own form, its namespace's forms that define no var (the ns form, fixtures), and every live form their `:form/refs` reach (a var to the form that last defined it; a defined multimethod's methods and protocol's extensions), and every schema entry a reached var's contract names (and each entry the entry's form names, on, and the vars its form names: the renders its properties declare, such as `:seon.render/html`, so a render's body edited moves the digest of every test reaching its entry, `seon.program-test/a-render-a-schema-entry-declares-is-in-its-tests-reach`), each form and entry digested once; plus the checkout's inputs with no program facts (`seon.fx/inputs`: deps.edn, bin/, resources/ with the schemas contracts name, test fixtures, and the pins and source groups its reach runs on; not task files or prose; and the per-test tick bound), plus the values of the config keys its reach reads (```seon.program/config-reads```: the `seon.config.*` keys its reached forms name, every key for one referencing the config map from outside `seon.config`, such as root's boot; their values from the config in force, ```seon.fx/config-input```: the shipped file, the `--config` layers the command line names, the `--set` overrides and the `#env` values under the profile, with the checkout's path normalized and the place keys left out), plus the vars data names that root resolves by name (`seon.fx/declared-refs`: system.edn's procs, edges of `seon.system/read-decl`), and no tree: a test whose reached forms call a file reader or run the binary (`seon.program/tree-readers`; a test runs target/seon, bin/root or bin/check only through `seon.test-store/binary-sh`) is digested by what it reaches like any other (owner, 2026-10-27: "no tests should include all of src"; with the tree it was 286 tests rerun on any edit), and a file or a binary change outside its reach is found by the full run (`bin/test --all`, below). A check step whose reach reads the tree still takes it, and so does a test reaching a form of a test namespace that calls a reader of the checkout's files (`seon.program/file-readers`: `slurp`, `file-seq`, `io/resource`, and src's readers of a checkout directory, `seon.fx/read-source` and `seon.doc/load-dir-tx`; 51 tests, measured 2026-10-28; the `:scans` flag of ```seon.program/graph-index```): what such a test judges is the files themselves (the old-word scan, the one-printer list in render.md, the wiki's leads), so one digest over a red tree and a green one made it flaky (2026-10-27, 2026-10-28). A test's digest moves exactly when a form or schema entry it reaches does. A literal name a form passes to `resolve`, `ns-resolve` or `requiring-resolve` is a reference (`seon.program/resolved`): the var it looks up at run time is one it reaches, so a test that resolves its var by name is no green reused after that var changes, or once it comes to exist. Any other name a form holds as data (quoted: `tree-readers`, `env-readers`, `seon.config/schema-forms`, whose `:seon.render/*` properties name every render, a form sent to an agent) is no reference, so reaching that form is neither using nor reaching what it names (below). A db that does not declare an attribute the graph reads (an agent's merge base cut before `:form/ops`, on a store kept from before it) holds none of its datoms (Datahike's `datoms` answers none, as DataScript's does: [datahike](forks.md#datahike)), and its forms are read with none (`seon.program-test/a-base-cut-before-an-attribute-has-a-reach-graph`).

How a reach digest is computed (the field's action keys: Bazel's, Nix's): the forms and schema entries are a graph by those edges, and each strongly connected component of it (```seon.program/components```, Tarjan's, iterative) gets, once per call and sinks first, a Merkle digest of its forms' own digests and the digests of the components it reaches, and whether it or they read the tree or reach a process (`:seon.config.source/process-vars`). A test's digest is of its key, `:env`, `:tree` when what it reaches reads the tree, and its starting forms' components (its own form and its namespace's plain forms), so it moves when a form it reaches changes and when the shape of what it reaches does (which form calls which); its `:process?` is whether any of those components reaches a process. One pass over the condensed graph answers every test, O(forms + edges) whatever their number (```seon.program-cost-test/the-reach-walk-is-one-pass-whatever-the-keys```): measured on Seon's program (484 tests), ```seon.program/graph-index``` takes 578 ms and 715 MB a call, of which reading the live forms is 407 ms and 393 MB; a walk per test took 1,079 ms and 1,691 MB. A live form is read as the walk reads it (```seon.program/reach-rows```: its id, namespace, definitions and references, each attribute read once over its index for all the forms, and its text never: a form's own digest is its `:form/id`, the hash of its namespace and text), never its other facts: on the proof's chain that is 97 KB and 15.8k ticks a form, against 153 KB and 33k before. The graph is a value (```seon.program/reach-graph```; ```seon.program/graph-index``` answers from it), and a change to it is ```seon.program/reach-update```: the live forms the two values differ in (```seon.program/live-ids```, four index scans and no entity read, 7 ms), each form's neighbours recomputed only where its edges can have changed (an added form; a form referring to, or defining the methods, extensions or contract of, a var a changed form defines), and only the components of the changed forms and of the forms reaching them re-folded, the rest kept: O(changed + their ancestors) past the scan, with the digests a rebuild gives (```seon.program-test/an-update-gives-the-digests-a-rebuild-gives```). Measured on Seon's program (2,616 forms): a one-form edit of `seon.agent/test-plan` re-folds 187 forms in 15 ms, of `seon.lib/digest` (in the program's one large component) 1,767 in 40 ms, against 640 ms for the graph. A schema entry added, changed or removed is the same update (```seon.program/schema-moves```): its row removed and added, and the forms whose edges it changes touched and re-edged: the entries naming it, the contracts naming it (`:contract` holds every name a contract names, an edge only where the entry exists), and the forms naming it as a keyword (`:form/keywords`, one AVET seek a key; their `:sedges` kept up), and the forms reading a config key they compute re-folded when the config keys entries name moved (`:computed`: the fold takes `:schema-config`, not the row). Measured 2026-10-29 over a merge that added two config entries and edited the config map's (7 lines of resources/seon/schemas, `main~3` to main): the rebuild was 154M ticks and 892 MB, the update 47M and 271 MB, with the digests equal (```seon.program-test/a-schema-entry-added-changed-or-removed-is-updated-not-rebuilt```); what the edit reaches is re-folded all the same (3,218 of 4,707 forms: every reader of the config map reaches its entry). A namespace gaining its first test (an agent's new test namespace, or a deftest added to a src namespace) is the same update: the forms it already held are re-edged as added (their quoted names are edges in a test namespace), where it used to build the graph from nothing (721 MB and 135M ticks, and a 24 MB graph held by the agent); a namespace losing its last test, or losing a form while gaining one, still rebuilds (the step takes a removed form's edges out by the namespaces it now knows as tests). Measured 2026-10-29 in one agent whose eval defined a namespace with a test, then asked `my.agent/tests-reaching`: `seon.agent/branch-graph` 721.7 MB allocated and 114 MB of footprint before, 65.8 MB and 20 MB after ([machine](machine.md#ten-agents-that-work)).

**The graph holds its tests' index** (```seon.program/reach-indexed```, read with ```seon.program/index-of```: ```seon.program/graph-index```'s answers for the tests, under the inputs it was made for), which is derived data and regenerated whenever it is not held ([AGENTS](../AGENTS.md) section 5). ```seon.program/reach-step``` keeps the answers of the tests a change cannot move and names the others `:stale`: a test whose form was re-folded (it reaches what changed), every test of a namespace whose plain forms were added, removed or re-folded, a test added; a test removed loses its answer. ### A result is a function of its digest

A green is reused forever, by any checkout or agent, so everything a result depends on is in its digest or out of the test (`docs/source.md`):
- **Seeds.** A generative check draws from a seed derived from its digest (```seon.proofs/seed```: the parts and `:seon.config.proofs/seed-salt`; ```seon.proofs/test-seed``` for the running test, bound by ```seon.proofs/run-tests!```; each mg-check contract from its var and its own reach digest ([checks](checks.md#the-generative-check-is-per-function))), so the same digest checks the same cases and a code change draws new ones; a failure prints its seed and a reproduction form. Before, mg/check drew from the wall clock (our malli fork ignored `:seed`; fixed on its `jolt/mg-seed`). A randomized property test draws `:seon.config.proofs/seeds` seeds, its test-seed and the next ones: one in the automatic run, five under `bin/test --all` (`SEON_SEEDS=5`, as the full run sets `SEON_COST_MAX_N`); `r3.inc-test`, 5 seeds of 150 steps, was 47 s of the automatic run's critical path.
- **Work, not time.** A cost proof is judged on ticks, bytes and calls (```seon.cost/exact```, [cost](cost.md)), so the same code on the same input measures the same at any load; an estimate stating and measuring none of them is red, and CPU time is shown, never red.
- **Dependencies as they are.** A submodule with uncommitted edits is its class by its content (```seon.fx/pin```: HEAD and the tree of its files), as bin/build builds it; a clean one is its gitlink.
- **The tree held.** A shard stores only if the tree is the plan's before and after its run.
- Still open, each with its fix in the findings: shard co-residency (a test leaving a thread or process state behind), the kept stores in `target/`, the inherited environment, render functions named by symbol in schemas, and deadlines and picked ports (which can only turn a result red).

## Schemas at the REPL

An agent changes a schema the way `defn` changes a function: `(my.schema/register! k form)` on its branch (v1's ``seon.schema/register!``). The registration is judged against the whole population, the binary's forms with the branch's changes and this one: a form that is no EDN data, does not compile (a name resolving to nothing), or declares an attribute Datahike cannot store is refused as data (`:seon.schema/registration-refused`, naming why), and nothing is written. Accepted, the entry is written on the branch without `:schema/source` (the binary does not hold it), in the resource it came from, or for a new key the resource holding most keys of its namespace; a new or changed attribute's Datahike declaration comes with it, so the branch can store its facts at once. A key in a scratch namespace (`user`, the agent's own) gets no resource: it is seen at the REPL and is no program.

The agent's REPL binds malli's dynamic registry to its branch's population before each form (`seon.repl/wrap-registry`; `seon.contract/options` puts the dynamic registry first), so the function it defines next, `seon.contract/valid?`, and every schema naming the changed key see it at once: the population is recompiled (4.6 ms for 457 forms), not the one key, because a map compiled against the old key keeps it. The registry is reused while the branch's changes are equal (keying 0.7 ms per form; compiling the population 5 ms). Every process loading a db's forms (an agent merging main, root and the fork server after a merge, a test fork) compiles them against that db's schemas the same way (`seon.program/load-forms!`, `seon.agent/run-tests-here`). Platform code compiled into the binary keeps the built schemas until the next generation builds the merged resource.

The merge carries an entry per key, `[:schema k]` -> `{:form text :file path}`, like a var (v1's `[:seon.schema/key k]` identity): two branches changing different keys of one resource merge clean, one key changed two ways conflicts at its key, and a scratch entry (no resource) is never program. Applied to main, the entry is main's (its `:schema/source` retracted), and the Datahike declarations its population needs come in the same transaction (`seon.program/schema-declarations`). The changed resource is then written back like a namespace's file (`changed-files` names it). Reading 457 entries adds 8 ms to `seon.merge/program` (80 ms to 88 ms on the test store) (`seon.merge-test/a-schema-entry-merges-per-key`).

A registration also arms again the functions the agent's process already holds whose contracts reach the changed key (the key, or a schema naming it, on and on): their contracts were compiled before it, and Seon's own code would go on checking the agent's new values against the old form (md-scan #7, #8 and #11 met their own `:seon.ref/block` that way). `seon.program/rearm!` finds them by the reach closure and arms each again, one `seon.contract/arm!` armed over the raw root it kept (`seon.contract/rearm!`), one the `seon.contract/defn` macro armed (which keeps no raw root) by evaluating its definition again: the source the REPL kept on its var, the text this process runs, else the branch's recorded form. Its work is the reaching vars', never the program's. One that no longer compiles is named in the registration's `:seon.schema/rearm-errors`.

A key no schema registers is answered with the nearest that do (`my.schema/unknown-key`, by Jolt's did-you-mean ranking), never nil: `(my.schema/forms k)` and `my.agent/callers` of one say so (md-scan #6 asked twenty times of a nil).

```my.schema/register!``` is the function and ```my.schema/registration``` judges it; ```seon.program/schema-changes``` and ```seon.program/schema-registry``` derive the branch's population; ```seon.contract/registry-of``` compiles one.

## Write-back: main's files, byte for byte

`file-text` is a namespace's live forms in their order, each after its lead, then its tail. A form recorded at a REPL has no lead: a blank line goes before it. A redefinition takes the place and the lead of the form it supersedes. Forms are written in the order the image loads them (```seon.program/load-order```: each after the earliest form that defines or declares a var it references, unless both were read from the file, whose own order already loads; a name in its quoted data is no reference): a helper recorded at a REPL after the function that now calls it is written before that function, so the file loads fresh as the image ran; a file already in that order is written byte for byte (`seon.source-test/a-helper-recorded-after-its-user-is-written-before-it`, cost `seon.source-test/the-write-back-of-a-file-is-one-pass-over-its-forms`). With no merge, import then write-back is a zero diff over all of next/src (`seon.source-test/import-then-write-back-is-a-zero-diff`). After a merge, only the files its changes touch are written: the unit of write-back is a file path (`changed-files` of the octopus merge member's changes, which the writer puts on each merged member's answer as `:files`).

A schema resource is written entry by entry with rewrite-clj (v1's `schema-file-text`, ported unchanged but for the separator of an appended entry, which follows the file's last two entries): the imported text, with each entry whose form differs from what that text holds replaced in its old layout (a part that reads as before keeps its text), each key no longer held removed with its line, and each new key appended. Every other byte is as it was: adding `:refused` to `:seon.run/status` changes only those 9 bytes of `resources/seon/schemas/seon.facts.edn` (`seon.source-test/a-changed-schema-entry-rewrites-only-itself`).

```seon.source/file-text``` builds a namespace's file and ```seon.source/schema-resource-text``` a schema resource's (through ```seon.source/schema-file-text```); ```seon.source/files``` builds every changed file, from ```seon.source/changed-files``` of what ```seon.writer/octopus-merge``` merged; ```seon.fx/write-file``` writes one.

## Commit: the merges branch

The reconciler asks for the write-back after an octopus merge: it reads the changed namespaces' and schema resources' files from main (```seon.source/files```) and asks the `:git` effect to commit them on the merges branch (`:seon.config.source/branch`) with a message naming each merged task and run. The commit uses git's plumbing (blobs, a tree from the branch's own, `commit-tree` as the config's committer, `update-ref` only from the head it read), so no working tree or checkout moves; a branch not there yet starts at the tree's HEAD. The merge already runs where main's program runs, so nothing is built. The sha is recorded on each merged run as `:seon.run/commit`, or the error as `:seon.run/commit-error`. A failed write-back is not lost: the run holds a `:seon.git/commit-failed` error in `:seon.run/error` naming the files (```seon.reconcile/commit-tx```), quiescence names each such run as a root cause (```seon.reconcile/root-causes```), and ```my.root/write-back!``` writes them again from main as it is now; a commit clears that error (a file main has no text for stays named in a new one) and leaves the run's note of forms that name no file. Worktrees share git's refs, so a worktree's roots and tests commit on `jolt/seon-merges-<worktree>` (`:seon.config.source/branch`'s `#seon/own-branch`, which the config loader resolves from the checkout), never the main tree's `jolt/seon-merges`. `bin/check loop` proves the turn on a clone of the repository.

```seon.reconcile/reconciler-proc``` asks for it, ```seon.source/commit-message``` names the merged work, ```seon.fx/git-commit``` commits; the answer merges on the run as `:seon.run/commit` or `:seon.run/commit-error`.

## The next generation

A binary is a cold-start artifact, built only for what cannot load in place: a Jolt, Chez or dependency pin, `deps.edn`, native code. Root asks for it with ```my.root/build!```: the `:build` effect builds main's last merges commit, and what happened is root's `:seon.root/generation` fact, `{:commit :checkout :binary :ms}` or `{:commit :ms :error}` naming the step and its log (a failure is also an `:effect` problem row naming that fact, `seon.error/asked-tx`, closed by the next good outcome). The performer (```seon.fx/build```) makes `<:seon.config.source/generations-dir>/<sha>` a worktree of the source repository detached at the commit (`bin/worktree --at`: this checkout's submodule repos at the commit's pins, its target/ cloned, so Chez and Jolt are already built, and the compile caches shared, see [Shared build caches](#shared-build-caches)) and runs `bin/build seon` there, niced, in that tree's own environment. `bin/root next` asks the running root for ```my.root/next-generation``` through the server (the generation's tree and ```my.root/resume-args```: `--set` arguments for `:seon.config.root/store-path`, `:seon.config.root/main`, `:seon.config.source/root` (now the generation's tree, a worktree of the same repository, so the next merge commits on the same branch), its dirs, branch and the generations dir), stops the root, and starts that tree's `target/seon` with them (the test that started this root, when one did, goes along as `:seon.root/started-by`) (`bin/root run`, the tree's own config, caches and LMDB build). `bin/root start` with ```my.root/resume-args``` restarts the same binary on the same store and main. Either way the resumed main still holds the imported program and the merged forms, and the merges load at boot; a generation's tree reads as main's merges commit, so its import replaces main's program with the same text (the merged forms keep their identity and stay loaded at boot).

Proven by `seon.source-test/a-restart-catches-up-and-a-new-generation-resumes` (on a clone of this checkout): two merges live in place; root SIGKILLed and the same binary started on the same main runs both; `my.root/build!` then `bin/root next` runs both on the new binary, main holding its generation. The test's seconds (solo, 2026-10-29, load 4): 3 boots, the two turns with the merge gate of the first (one deferred process test, named exactly: [merging](merging.md#a-merge-runs-what-the-change-reaches)), and the generation's build, 31 s of Jolt's whole-program link of a tree no build has seen (the shared caches are warm; the tree is new by the two merges, so it is never a lookup) plus 9 s of `bin/worktree --at` (the `target/` clone). The tree's own commits made outside Seon reach a resumed main at its next boot ([Main's program follows the tree](#mains-program-follows-the-tree)). Old generations' trees are kept with the run until the owner reclaims them.

```seon.fx/build``` builds, ```my.root/build!``` asks and records, ```seon.reconcile/generation``` and ```my.root/generation``` read the fact, ```my.root/next-generation``` is what `bin/root next` starts; ```seon.e2e/loop-turn!``` is the turn (`bin/check loop` runs it on a clone); ```seon.generation/generation``` is the function it changes.

## Dependencies

Fetching a library is an outside-world effect with one owner, like write-back: the `:deps` effect kind, performed by ```seon.fx/resolve-deps```, which passes a deps map (`{lib {:mvn/version "..."}}`, ``:git/sha`` or ``:local/root``) to Jolt's own `jolt.deps/resolve-deps` (no resolver of ours) and answers `{:value {:roots [absolute source roots]}}`, or `:seon.fx/unresolved` naming the libraries that did not resolve (see [failure points](failure-points.md)). It writes only the checkout's shared caches (`.m2`, gitlibs, `.cpcache` under `HOME`), so a second resolve of the same map is a cache hit that needs no network. The asker records the outcome and decides what to load; there is no `add-deps` or `sync-deps` at the REPL, and no checksum. The effect kinds are declared under `:fx` in `resources/seon/system.edn`, and `seon.fx/procs` makes their owners.

## Shared build caches

`bin/env` points Jolt's three compile caches at ``target/cache/`` of the main tree, found from git's common dir, so every worktree and generation (`bin/worktree --at`) shares them: `build` (`JOLT_BUILD_CACHE_DIR`, build units), `runtime` (`JOLT_RUNTIME_CACHE_DIR`) and `aot` (`JOLT_CACHE_DIR`, one artifact per namespace, keyed by its source, its requires' keys and what its compile read). No key holds a checkout's path: a unit is keyed by its text and the building runtime's fingerprint, and an AOT artifact's `.res` sidecar names each file its compile read (a schema `seon.contract` slurps) and each directory it listed (`resources/seon/schemas`, the checkout root `seon.ref/roots` lists) relative to the project root, so a checkout hashes its own files (Jolt ``jolt/cache-records-relative``). Entries and sidecars are published by temp+rename, so concurrent builds are safe; `JOLT_CACHE_GENERATIONS` (4) runtimes are kept, one per Jolt pin in use. `bin/worktree` clones neither these caches nor a checkout's old `target/home/.jolt` copies of them. `bin/build` clears nothing on a schema change: an edited schema file misses its 52 dependents of `seon.contract`, a schema file added to the directory moves the same keys. One sidecar holds the last compile's names, so two checkouts whose reads differ in which files exist (a worktree session that added a schema) take turns: each misses those namespaces once after the other built (measured: 41 misses, +6 s), never loading the other's artifact. Measured: an unchanged `bin/build seon` 25 s, pass 1 1.1 s, 263/263 hits; a fresh generation worktree (`bin/worktree --at`, 2.0 s, `target/home` 82 MB where the clone was 1.3 GB) builds from the shared cache in 24 s, pass 1 1.3 s, 263/263 hits; a namespace edited and built in one worktree is a hit in the next (16 misses there, 0 here); `bin/cache-smoke` checks that every checkout names the same three directories. `bin/env` also exports Jolt's compile options, `JOLT_COMPILER_OPTIONS` `{:image-fn-forms false}`, which Jolt reads into `*compiler-options*`' root at start: Seon writes no state image, so its build, tests, root and agents compile without registering fn literals' sources for one (a third less allocation a compile; task jolt.backend/image-registration-is-opt-in). The AOT key does not include it, so an artifact compiled with registration loads into a process without it and the reverse: harmless here, since nothing writes an image.
