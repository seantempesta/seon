# Done is derived from proofs; root merges the merge request from main

## 1. The design in one page

**What exists.** The agent's loop derives an end (`seon.turn/task-end`), then performs the agent's own verb `my.program/request-merge!`, which writes a second entity (a merge task plus a merge request keyed `[assignment commit]`). Root's `db<->flow` copies cluster facts with `seon.cluster.squash/copy!` (fixed base, three-way computed before the writer, a transaction marker `:seon.squash/attempt` as the completion test, conflicts as prose tasks), and code reaches main through `seon.cluster.source/land!` (a Datahike merge commit with parents, then write-back and one git commit, no path after a crash). Two merge shapes, two bases, a marker, an agent verb, four catches. Both plans independently reach the same skeleton; the hybrid takes it and settles the four points where they differ (§2).

**The entity.** The **assignment** (`:seon.task/assignment`, `seon.id/id [task number]`, the entity `seon.task/attempt-tx` writes today) is also the **merge request**: one per assignment, open from the moment root assigns the task, closed once by root. The separate merge task (`:seon.task/kind :merge`), `:seon.task/merge-request-row` and `my.program/request-merge!` are deleted. Astra's `:seon.merge/request` entity and Opus's reuse of the assignment are the same identity; the hybrid keeps the entity that exists.

**The data** (schema `seon.task.edn` unless named; everything else is derived and never stored):

Retired: `:seon.squash/attempt`, `:seon.squash/copy`, `/datoms`, `/conflicts`, `/conflict` (the unmerged entity carries the values), `:seon.task/merge-request-row` with `:merge-request`, `:merge`, `:of-assignment`, `:proved`, `:red-first`, `:run-id`, `:program`, `:seon.task/kind :merge`, `:seon.task.attempt/fork`, `:seon.task.attempt/commit` as a fork basis (phase M9, owner Q-c), `:seon.config.root/land?`.

**Done, derived.** An assignment is done at source commit C when `seon.context/step-status` answers `:done` over the observation already built today (`step-observation`: head = C's latest results for proofs, product and reached reds by reach digest; fork point = results at the merge base, which `seon.turn/prove-turn` records before any model call and `seon.test/fork-point-red` reads or runs for a red), with one change to the `:implement` rule: **at least one proof was red at the merge base** (Astra's reading of the law; a task may tag an existing regression test beside its new red one). A proof set green at the base is reported as `:seon.context/green-before` (Opus) and, when it is the whole set, root closes the assignment `:closed` with reason `satisfied`: the task is already true on main and retires itself (R-8); no model call happens (`prove-turn` closes the pass and `task-end` finds no `:done`). `:prove` is unchanged (R-7). The agent's test step already writes this judgment on its branch and stops calling the model; root recomputes it on each wake only for branches whose head moved since it last judged them (one roster read), at about 1 ms per proof. Nothing is stored for done; the agent has no verb.

**One merge shape: a three-way per coordinate, squashed, base stored.** `seon.merge/three-way` is today's `squash-merge` with one addition: cardinality-many attributes merge member by member, `(ours − (base − theirs)) ∪ (theirs − base)`, as git merges lines (verified: today disjoint additions to a set conflict, §7 P3). Rules per coordinate `[attribute entity]`: changed on one side → that side; both to the same value → nothing; both to different values → the attribute's declared `:seon.cluster/conflict` (`:ours`/`:theirs`), else **unmerged**. The merged result is one plain transaction on main with one parent (ours) and the base advanced in the same transaction: Datahike's `merge-db!` records parents and computes nothing (`datahike.writing/merge-writer!` is `transact!` plus `:datahike/merge-parents` metadata, verified), and parents would keep the agent's lineage reachable inside the snapshot window for no reader (`datahike.gc/reachable-in-branch` follows parents only `in-range?`). `accept-merge!` drops `:parents`. The **partition** a merge covers (program and cluster facts whole, or the rule-trusted cluster facts separately and continuously as R-4 says) is declared on the entity schemas (`:seon.program/partition`, exists) and decided by the owner (Q-b): the mechanism is the same function over a declared attribute set with its own base attribute; whole = one partition, one base; separate = two partitions, two bases (Astra's `facts-commit`/`program-commit`), each advanced only by its own merge, a conflict in the fact partition stopping that partition whole (so no stage is lost when a base advances).

**Root's merge (`seon.merge/merge!`, called by `db<->flow` and by `my.root/merge!` at root's REPL; the same function).** (1) Fork a merge branch `merge/<assignment>` from main's head B; apply three-way(base, theirs = C, ours = B) there; conflicts become `:seon.merge/unmerged` entities on that branch and the merge stops there with the request open and the three values as data. (2) Gate: `step-status` on the merge branch with the fork point at B (proofs, product, the tests reaching the change, through the one runner, results reused by reach digest). This is P3's conversion: `seon.test/change-reds` is deleted; "a red is the change's unless main is red" is exactly `:seon.context/broken` judged at B, and a Prove step's designed reds pass as its product. (3) Transact `[[:db.fn/call seon.merge/merge-tx assignment C tested]]` on main. Inside the writer, on its own db value, the function recomputes three-way(base, C, db) and compares the merged digests of every touched coordinate and every definition the gated tests reached with `tested` (the merge branch's digests): equal → it writes the merged result, `:seon.task/merge-base C`, `:outcome :merged` and `:merge-commit`, in that one transaction; different → it returns `[]`, and the main transaction that moved them has already woken `db<->flow`, which re-derives (git's `update-ref new old`, per coordinate; verified: a root edit after capture becomes a conflict inside the writer, never an overwrite, §7 P4). Fast-forward is the trivial case: main unmoved since B, nothing unmerged, step 3 passes. (4) **Publication is derived due work, not a step of the merge.** Datahike is the authority; files are the write-back of accepted entities. `next-actions` derives `:publish` for an assignment with `:merged`, a program partition changed and no `:git-commit`; `seon.merge/publish!` runs `write-back!` (which already checks file bases and reindexes) and `commit!`, then writes `:git-commit`. A crash anywhere leaves a derivable state: accepted-not-published is due again, and a write-back finding equal bytes commits nothing. Astra is right that Datahike, files and git share no atomic commit; the hybrid keeps the three facts distinguishable (`:merge-commit`, `:git-commit`, the loaded commit) instead of calling them one. Git plumbing with a private index and a request ref (Astra §3) stays deferred by plan.md §6 until a collision in the shared checkout is observed (AGENTS.md: never build protection against a failure not observed).

**Merging main into the source branch.** Trigger: the source is done and the gate on the merge result is not (main moved under the change: a sibling's merge turned a reached test red, edge 16). Root runs the same three-way with source = main and target = the agent's branch, `update-tx` sets the base to M, unmerged coordinates go to the agent's branch as `:seon.merge/unmerged` entities for the agent, the branch's listen route wakes it, and its next pass reruns the proofs pending at the new reach digests (prove-first generalized from "keyed by assignment" to "pending at this program").

**Forking and joins (owner Q-c).** Recommended (Opus): every assignment forks **main** once all its `:seon.task/needs` are `:merged`; a Prove step's product (designed reds tagged with its successor's open task) merges into main like any change, so main holds the red proofs of every assignable task, which is exactly the state `seon.task/assign!` already requires. Joins are then ordinary, no predecessor branch is kept, `successor-waits?`, `seed-attempt!`, `attempt-rows-tx` and the octopus go. The alternative (Astra, R-6/F): fork the predecessors' merged commits, an octopus for joins, held successors pinning commits as GC roots. §4 prices both; phases M9 and part of M14 depend on the answer.

**Lifecycle, derived (`next-actions`, pure; absorbs P7–P10).** From main's facts and the roster: `:merge`/`:review` (done ∧ gate green ∧ nothing unmerged; Q-a decides which); `:update` (done ∧ gate not done); `:stop` (`outcome` present ∧ graph in roster, orderly: the pass finishes); `:cancel` (intent `:cancelled`: interrupt, await actual exit, then `close-tx` `:cancelled` and `:delete-branch`; no task for root, no end written by `follow!`); `:delete-branch` (`outcome` present ∧ graph exited ∧ (head = base ∨ ¬done(head)) ∧ no unmerged ∧ no publication due ∧ `keep-ended-branches?` false); `:publish`; `:close` with the end the branch holds at C (`:sent-back` with target, `:given-back`, `:capped`, `:stalled`, `:error` for a failed start or a refused action); `:relaunch` (P9: the closed assignment carries `:seon.task.attempt/relaunch`, so assignment n+1 is written, forking main or the named `relaunch-fork`); `:attempt`+`:start-flow` (one starter, P10: `plan` over assignments of `:running` tasks; `agents-to-start`, `host/start!`'s graph start and the held arm go). Every action is idempotent by identity or by `head = base`; a failed action is the assignment's `:error` close written by the entrant boundary (the Flow proc), never a catch-and-continue; the facts are unchanged so the next pass derives the same action once. A stopped task keeps its branch and open request; `:held` has no assignment and no model turn.

**Messages (U5, absorbed).** The sender transacts the message on its branch; root records it on main by `:seon.message/id` *before* its one `offer!`; a crash between leaves "unknown", never a second offer (in-flight loss accepted, R-4); an undeliverable offer is data on main's message entity.

**Retention.** Open assignments' merge bases (and, under Q-c alternative B, held successors' fork commits) are commit ids passed to `datahike.gc/gc-storage!` as `:datahike.gc/roots` (fork change, option A, R-4; absent from the pinned reference, zero hits). Until it merges, the `:base/<branch>` ref is moved to the stored base with `force-branch!` `:expected-current-commit` (exists) by root's `db<->flow` alone, the one writer of base refs, which satisfies the docstring's "exclusive write access".

**Words.** Clojure, Datahike, Malli, git only. One Seon word proposed for vocabulary.md: **assignment** (Astra): one task given to one agent on one branch, numbered within its task, the entity of `:seon.task/assignment`; it replaces "attempt" (no library names this relationship; the attribute already carries the word). "Merge request" (GitLab, already in vocabulary) names the same entity's merging role, so the vocabulary entry changes to "an assignment, as the thing root merges: source branch, target branch, merge base, outcome". Retired on this path: land/landing/landed/unlanded → merge/merged; copy/end copy → squash merge; settle (branch) → delete-branch; `:root` rule → **unmerged** (git); problem task → a task assigned to root; `seon.cluster.squash` → `seon.merge`; `retire-branch!` → `delete-branch!`; `frontier` → `ready` (CN-27). `step` stays (owner's word, vocabulary).

## 4. Questions for the owner

Each with priced options; the recommendation is marked. The design fits either answer; the phases that depend on it are named.

**Q-a. Auto-merge: supersede R-10 ("root reviews each diff before it merges")?** (depends: M6's `apply-actions!` arm, the dial's shipped default)
- A1 **(Opus; recommended)**: merge automatically whenever the source is done, the gate is green on the merge result, nothing is unmerged and `merge-tx` passes. Root reviews only unmerged coordinates. Guarantee: nothing merges that a test does not prove; cost: one gate run per candidate; sacrifice: review of every clean diff, R-10.
- A2 (Astra): keep R-10; `next-actions` derives `:review`, root runs `my.root/merge!` (the same function). Cost: review latency per merge request; no change to the design.
