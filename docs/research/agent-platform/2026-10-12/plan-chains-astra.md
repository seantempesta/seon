# Unattended chains

Seon already has task ingestion, branch-local refinement, a task-dependent completion rule, root's merge, publication and a listened Flow reconciler. Compose those owners: **merge task content, resolve its references, run the step, merge its whole proposal, then fork main for its successor**. Delete predecessor-branch succession and the second interpretation of test results. Do not build a chain runner, a handoff store or a prompt generator beside these owners.

This is an independent plan, not implementation. I did not read the other plan. Proposed symbols and schemas below are explicitly proposals; existing symbols were checked in source. Dated measurements distinguish live evidence, experiment reports, and inference. The owner's night rulings override older spec language about discretionary review, predecessor commits and all tests being green during Prove.

## 2. Task data and its movement

### One declaration, an effective value, and execution facts

Keep `resources/seon/tasks/<ns>.edn` and `seon.task/file-declarations` as the declaration entrance. A task's handle/symbol remain derived by `seon.task/task-handle` and `seon.task/task-sym`. `:children` is ownership/containment, `:needs` is prerequisite order, both refs to task entities. They are not names pasted into prompts. Keep cardinality-many sets and the existing writer's cycle/ownership checks. A parent is complete when its leaves have accepted outcomes, as `seon.task/done?` already derives.

Separate three existing concerns explicitly in the schemas:

| Data | Members and owner | Rule |
|---|---|---|
| Authored content (proposed named `:seon.task/content`) | `:seon.task/intent`, restored optional `:seon.task/instructions`; task file author and `my.task/refine!` | Sparse maps. Intent is the goal; instructions say what this step must produce. New domain content attributes, if actually needed, join this named schema. |
| Task identity and graph | name, derived ns/sym/id; optional step, children, needs | Local to each task. A child must not inherit its parent's id or children and thereby become its own parent. Graph edges select contributions; they are not merged into the content value. |
| Assignment/execution | existing execution, assignment, attempt, branch, end, outcome, merge and publication facts | Root/writer/Flow own these. Never inherit an earlier task's running state or an earlier assignment's outcome through content merge. |

This is a schema selection followed by `clojure.core/merge`, not a different merge operation for each attribute. Content collections replace wholesale; there is no union, string concatenation, deep merge or implicit “append an instruction”. Missing is inheritance. An authored empty value is still an authored value and must meet its schema. Required intent moves from **every file entry** to the **effective leaf value**: a child with no intent is useful and valid when it inherits one. Existing standalone tasks keep their intent and default Implement behavior.

**Proposed `seon.task/effective`**, pure `(database task-symbol) -> :seon.task/effective`:

1. Read the task's ancestor path and prerequisite closure, using the existing edges. Expand a needed parent to the completed leaves that produced its data. Include each contributing task once.
2. Order ancestors before descendants and needs before dependents. For unrelated ready contributors, sort by task symbol. The assigned task is last. Shared ancestors appear once, not again inside every predecessor's already-expanded value.
3. Project each declaration to the named content schema and `(reduce merge {} contributions)`. Attach the assigned task's own identity/step/edges separately, plus a derived `key -> declaring task` map for explanation. Validate the final owning value.
4. Derive references from **all text of this effective value**. `:seon.task/references` remains derived query data, never authored. Reference selection must use the effective text, so an overwritten intent contributes no obsolete references.

`seon.task/references` is a materialized symbolic index with live consumers: `seon.task/task-edges`, `seon.health`, `seon.contracts` and namespace rendering. Do not leave it stale while only the prompt understands inheritance. `seon.task/with-references` must derive that index from effective content at the task writer, including affected descendants and reverse needs when a contributor changes. After merging declarations, derive it from the merged value again, rather than union two opinions about a derived index. Keyword and document references remain typed resolver values; do not widen a symbol-valued dependency attribute to hold strings. The content/schema validation and the index update share the final owning task graph. Add the corresponding inherited-reference case to the health/contracts/task-edge consumers' tests; this is a required C1 caller conversion, not a new cache or a second resolver.

Cost: read the reachable graph once, O(V+E) plus stable ordering at joins; merge proportional to its content; resolve proportional to distinct selected references and their content. Do not query 808 task bodies on every call. Cache only by the content/read evidence already owned by `seon.cache`; an unrelated transaction must not invalidate it. Provenance is a derived explanation, not another editable declaration or stored prompt.

Two real tasks currently join two needs, so ordering is not hypothetical. **Recommended initial rule: stable task-symbol order at joins, then the join's own keys win.** The chain author writes the join's own intent when it needs to combine decisions rather than select the last value. This is honest right-biased merge; no “conflict” detector over prose. Q1 offers the alternative if ordered dependencies are worth changing the model.

## 3. Lifecycle: one chain from assignment to publication

### Assignment, completion and successor basis

A root assignment of the subject activates its leaves in one canonical writer operation (proposed `seon.task/start!`, the task writer called by root, with a thin `my.root/start!` entry). Initially use the existing `:seon.task/execution` facts: set the selected subject's leaf tasks running as part of assignment; parents are containers, not model agents. This is a bounded graph write, not a second inherited control-state system. New children of an active subject must be included by the same writer operation if dynamic decomposition is later enabled; the first chain has its full tree before assignment. Do not loosen every unrelated held task into runnable work.

`seon.task/ready` derives the next runnable leaves from accepted prerequisites. For a join, **both needs must have merged**. `seon.cluster.agent/plan-facts` reads admission obligations on main, not on whichever predecessor commit sorts first. Root writes the assignment and agent, captures the immutable main value containing them, and `seon.cluster.registry/fork!` forks **that exact commit**. The actual retained base is then recorded for the assignment before any model call. This must be true on the branch as well as on main: `seed-attempt!` currently does nothing when the row already exists, so simply deleting it is not proof of the branch's complete assignment data.

Keep `seon.cluster.agent/write-merge-base!` or fold its responsibility into the existing writer with the actual fork result. A fork commit cannot contain its own id; root's later assignment fact and the retained base ref legitimately describe it. Retain one immutable value for admission and fork instead of comparing two readings afterward. At restart, derive pending work from assignment facts and existing branch refs; no remembered launch operation is replayed.

Assignment identity is minted **once by the assignment writer**, through `seon.id/id`; an attempt number describes sequence, it does not provide identity. The writer returns an already-open assignment when the same due task is observed again. `plan` proposes the task to assign, not independently reminted agent/branch ids paired with a speculative start. Root then derives the start from the committed row. This removes duplicate identity derivation in `seon.task/next-attempt` and `seon.cluster.agent/plan`. The writer is already the serialization owner; add no lock or side registry. Prove repeated wakes and retraction/remint behavior explicitly.

Remove predecessor end-commit selection, predecessor roster checks and successor retention from `seon.cluster.agent/plan-facts`, `seon.cluster.agent/fork-attempt!` and lifecycle predicates. Keep `seon.task/attempt-rows-tx` for its **manual `seon.task/assign!` caller** and for a continuation from an older commit until those callers are converted. The older plan's blanket deletion would break assignment. Likewise, keep generic nested branching in `seon.cluster.registry/fork!`; it serves a same-step continuation.

### What done means for each step

Use **one observation and decision**, based on actual clojure.test reports and current definition/input/evaluator evidence, for the automatic step and the merge candidate. Extend `seon.context/step-status`'s existing rule, rather than add another all-green test to `seon.cluster.source/accept-merge!`. The observation must retain absent/unknown/red/green distinctly; do not reconstruct fork status from booleans that turn missing evidence into old red. Keep reaching tests in execution and merge checks. **Their source enters context only as required proofs or explicitly named references.** An actual failure report is delivered to the agent whose evaluation caused it; this does not automatically expand the failing test's source or its neighbors.

| Step | Durable product | Positive completion data |
|---|---|---|
| Design (new `:design`, introduced with C1) | Named schemas, interface contract and, where necessary, an explicitly unimplemented stub; refined intent naming those declarations, examples, assumptions and decisions | Its nonempty tagged design proofs pass on the actual declarations/examples and were not already satisfied at assignment. Existing required behavior is not broken. A proof merely checking that prose exists is insufficient. |
| Prove | New or strengthened proof declarations tagged to the **successor Implement task**, plus any needed test helper/contracts; refined goal names the tests | Own proofs (if supplied) pass; the product is nonempty and is exactly the newly introduced designed-red proof definitions for its successor(s); no unrelated new red or broken old green. A failure assertion or typed unimplemented error is a designed red; an unresolved symbol, contract error or fixture crash is not. |
| Implement | Bodies and any coherently changed helpers/schemas/tests, plus refined task text | Required proofs are current and green; no change breaks an existing green or introduces an unrelated red. All-green before assignment means already satisfied, not evidence this agent completed work. |

“New” above is about a proof **definition**, not solely a previously unseen symbol. Adding a case to an existing table test must be possible without pretending its old green result covers the new body. Compare test identity **and definition digest**, program/input evidence and evaluator; run the changed proof definition against the relevant pre-work program to observe its designed red, and against the candidate. Unchanged existing green proofs remain regression obligations. This lets the owner-required table-test reuse work; HEAD's symbol→boolean fork map cannot express it. Include a strengthened existing test as well as a brand-new deftest in C5's regression. Test evidence cannot infer the logical strength of arbitrary rewritten assertions; preserving the goal is part of Prove's explicit task and its executable domain examples, not a claim that a digest proves semantic quality.

Design is first scoped to **interface design with executable acceptance**: the proof can validate the chosen named input/output schemas against the required examples and the declared interface. It does not call an implementation that Design has not written. A checked stub can answer the already-declared unimplemented error. The existing system does not have a universal executable test of the quality of prose research; do not call a file's existence that proof. Q2 covers research/decision-only Design using the spec's future typed-answer entrance.

For Prove, the semantic gate is green while designated test results are red. That is the owner's designed-red merge, not an exemption from an all-green policy. Carry `seon.task/obligations` (step, own proofs, product) through `seon.cluster.source/prepare-merge!` and `seon.cluster.source/accept-merge!`; evaluate the **merged candidate** under the same rule. Delete `seon.merge/needed?`'s declarations exclusion and the unconditional red veto (`seon.test/change-reds`/`red-test-refusal` callers that it replaces). Convert their last callers and schemas in that slice, including empty own-proof Prove with a declared successor. Unknown coverage still has no positive completion result.

Run-owned test evidence is not program to merge. New test declarations, function/schema declarations, namespace changes, task refinements and deletions **all** belong to the proposal. No agent-authored selection list, scratch-definition exception or fixed path allowlist. Teach agents to use `let` for probes and unmap unwanted declarations before they finish.

### End → merge → publish → next step

After the evaluation and automatic tests, the agent records its end on its branch. Root's already-installed branch listener wakes `seon.cluster.agent/db<->flow`. Root joins the finished graph, prepares the entire proposal against current main, applies the common completion rule and writes the accepted merge plus assignment outcome through the writer. `seon.merge/publish!` performs the existing file-base check, write-back, re-index, exact-path Git commit and publication. Due publication remains a fact until complete; ordinary concurrent file claims are handled by the existing publication owner, not a new lifecycle lock.

Publication here has two existing meanings that must not be conflated: `seon.merge/publish!` writes files/Git and records `:seon.task/git-commit`; it does **not** itself call `seon.cluster/refresh-source!` to reload the host JVM. A Git commit is not proof that host-bound code is installed. The first chain is restricted to declarations its SCI branch can execute. The lifecycle must route any later host-bound successor through root's existing `seon.cluster/refresh-source!`/reload and `my.test/check-platform` owners, with actual installed-program evidence in context. End-to-end unattended host reload is **unverified**, and no result below claims it. A manual root restart would count as a hand act; root's existing batched operator work must be made due work before such a chain can claim zero. Do not restart default from a lane to paper over this gap.

A successor's required **semantic** condition is accepted needs on main. Its execution condition also includes the program it must use being available under its evaluator. For ordinary interpreted changes, the new main value can be forked immediately after acceptance; publication may finish concurrently. For a changed host-bound declaration, the successor cannot be told it runs the new definition before root's canonical reload makes it so. The context must name that execution evidence. **Recommendation for the first measured chain: finish publication before the successor starts**, so durable files, interpreter inputs and the predecessor's advertised artifact all agree. This is derived work order in the existing proc, not a polling fence. Q3 prices the later concurrency choice. A chain is never reported complete while publication is still due.

Eliminate `seon.cluster.agent/agents-to-start`, the second graph start in `seon.cluster.host/start!`, and the held-task model-turn clause only with their replacement tests and callers. Taskless REPL agents remain valid entrants; absence of a model assignment does not prevent their REPL or the cleanup of their ended branch. Root's background Flow work is not an unassigned model call. This is the existing M13 slice, not a prerequisite to invent a scheduler.

### Capped/stalled continuation and send-back

A continuation is **new execution over durable facts**, never resumption of a JVM stack, model stream or private result handle. After actual exit, root may create a new assignment under the chain's preauthorized call budget. Keep the same task identity, mint a new assignment/agent/branch, fork the old attempt's captured head C toward main, and **retain the proposal's existing merge base B**. `seon.cluster.registry/branch-fork-entity` and `seon.cluster.registry/fork!` already implement this nested base inheritance. Use those functions. Setting the merge base to C would silently discard the partial work B→C from the eventual proposal.

This is continuation of the **same step**, not succession to the next step: successors still fork main after needs merge. Keep the old branch/base until the new branch has captured them; Datahike owns retention thereafter. Seed the new assignment onto that older value with the existing assignment owner. Its first context says why the previous attempt ended, its final proof results, what changed, what is still outstanding, and which intent refinements were preserved. Private `result/...` bindings do not survive and are never artifacts.

Make the existing `:seon.task.attempt/relaunch` and `:seon.task.attempt/relaunch-fork` facts meaningful readers in readiness/plan, rather than leave them write-only schema promises. Terminal-history negation must consider the current authorized continuation, not veto a task forever because any past attempt capped. Root can write that fact automatically under a chain's grant; manual `my.root/relaunch!` is the same writer entrance for an exceptional decision, not the ordinary chain mechanism. The proposed subject attribute `:seon.task/call-limit` is the one declared chain allowance, defaulted at activation from a named configuration dial `:seon.config.task/max-chain-calls`; its numeric default needs the owner's choice, not an invented constant. Calls already recorded across the subject's descendant assignments supply consumption; their model-call admission uses the existing bounded execution owner. Context derives remaining calls, not a second mutable budget counter. Exhausted **chain** budget becomes a loud unresolved result with its task and branch retained; do not silently authorize infinite repeated calls. See Q4.

Persist the observed end before deriving its problem/notification, so a refusal constructing `ended-problem!` cannot erase completion evidence (P4). Replace the automatic “merge it” text with the real status and the appropriate continuation. No new retry loop: the existing listened facts are sufficient.

`my.task/send-back!` already accepts reason, target and counterexample. Include **all three** in `seon.context/send-backs` and resolve references in the reason by the common resolver. Root delivers it, derives the owning earlier step as due, and invalidates dependent completion through the task relation already in `seon.task/ready-rules`. The target's successful replacement merges to main, then later steps fork that main. Failed code stays a proposal; a send-back is not authority to merge failing implementation. If the goal/proof is wrong, the model must say so instead of weakening the proof. A root question uses `my.message/send` and `my.turn/wait`, not a successful end.

## 8. What not to do

- Do not optimize a zero-success benchmark by counting abandoned attempts as zero-hand chains, raising the cap alone, or repeatedly rerunning `scan` without changing the dominant measured failure.
- Do not reintroduce must-read/evidence copies, prompts stored on tasks, serialized predecessor chat, a handoff artifact registry, chain state machines or a second scheduler. Durable declarations and test evidence already carry the work.
- Do not add agent-side done/merge verbs or author-selected merge paths. The branch is the proposal; completion is observed and root owns the effects.
- Do not implement general free-form research acceptance, arbitrary dynamic task-tree generation, multiple-parent ownership, an ordered-DAG library, or a prose-conflict engine to get the first three-step chain working.
- Do not pull callers/reaching tests as reference context, trim a specific task's source, suppress unresolved references, or append one-off help caveats until a capture fits. Improve producer data, its render, or the general printer. Several accumulating edge cases mean stop for the requested audit.
- Do not implement a DSML interpreter from one model's invented tool names, add another no-forms retry, or silently switch model settings. Verify the wire cause and compare measured outcomes.
- Do not delete `attempt-rows-tx`, generic nested forks or the actual merge-base writer because their predecessor-chain callers disappear. Their remaining manual-assignment/continuation responsibilities have to survive the same commit.
- Do not merge a Prove branch's facts while dropping its tests, or call a nonempty capped diff mergeable. Judge the whole proposal by its step's actual rule.
- Do not redo write-back/adoption already delivered by 7c87 and d50eb5cec, repair foreign in-flight files, rewrite the issue index, or broaden this assignment into a core-size/rename campaign. No platform restart by an assigned lane.
- Do not claim that a CAN DO reviewer proves an implementation correct. It proves the agent was given the information required to attempt the step; executable proofs and the actual chain are separate evidence.

## 9. Questions for the owner

These are new choices, not requests to reconfirm the binding rulings. Recommended defaults allow the hybrid to be concrete; prices are relative engineering scope, not measured hours.

1. **Order at the two existing joins.** **A — recommended:** retain needs sets, deterministic task-symbol order, own join keys last; one content fold, no representation conversion, but a join author must explicitly synthesize conflicting conclusions. **B:** add an ordered input declaration while needs remain dependency refs; makes precedence author-chosen, but adds another authored relation to keep coherent. **C:** never inherit from needs, only children; smallest traversal, but loses the requested step-to-step refinement flow unless agents edit a shared parent. 3. **When may the successor start relative to publication?** **A — recommended initially:** accepted merge and publication/reload evidence first; clear first-call provenance and durable refinements, slightly greater serial latency. **B:** after accepted main merge for interpreted declarations, publication concurrent; better throughput, but context and chain completion must explicitly track due files and host-bound changes still await canonical reload. 4. **Automatic continuation's spending authority.** **A — recommended:** one declared finite call allowance for the whole subject, with per-attempt caps only scheduling fresh execution; 0 hand acts inside the grant and loud unresolved exhaustion. 5. **A redefinition that omits old comments.** **A — recommended:** exact authored source is the proposal, comments included; show the source/diff faithfully and make preserving meaningful documentation an explicit step obligation where needed. **B:** require a source-edit operation preserving unrelated syntax; useful for large functions, but a new editing capability needs its own design and data proof. 6. **Next reply-format experiment after chain 9.** **A — recommended:** verify the configured provider's current request semantics, run one bounded same-context probe of a supported setting, and change only a reproduced request defect. **B:** compare another already-supported model on the identical small task/context; cheaper than inventing a reply language if no request defect is found, but changes the model being benchmarked. **C:** formally support structured tool replies through the one reader; largest scope, requires a real declared operation/data contract and library parser, not guessed DSML-to-form substitutions.
