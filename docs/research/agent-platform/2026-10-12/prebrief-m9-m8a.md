## 2. How write-back and commit work today on default

**Where the checkout comes from.** `my.root/merge!` answers `(or root (some-> (:seon.config.fs/working-root effective) java.io.File. .getCanonicalPath))`, with `effective` from `seon.config/effective` on the cluster's database. Verified live: `"/Users/sean/src/seon"`, `checkout-root?` true. `user.dir` of the default JVM is `data/source/61b9534d7…` (verified), which is why a relative `"."` would land in the archive. The `:merge` action in `apply-lifecycle!` passes **nil** instead, so it never reaches the checkout (verified in code; not exercised).

**`write-back!`** (`seon.cluster.source/write-back!`, source.clj 1566–1606):
1. `root-refusal` (`:root-refused` unless `checkout-root?`); nil root refuses here.
2. `write-back-commits` (1519): `held-digests` of the merged and held declarations; `:row-changed` if the head moved since accept; `proven-files before after identities root` (candidate bytes proven against the merge commit, reindexed); `:file-changed` if a file's disk digest differs from its base digest; then `install!` (1169, atomic rename) per file, recording `:seon.source/candidate-digest` (1554) and the changed paths.
3. Returns `:seon.source/written`, or a `:seon.source/write-back-error` (declared refusal with `:seon.error/type`).
Nothing is written before the proof. The install is not atomic with the disk check (a lane editing the same file between the check and `install!` is overwritten; **unverified**, a race reasoned from the code).

**`commit!`** (source.clj 1693) → `call-with-commit-lock` → `commit-locked`:
- Lock: `perl -MFcntl=:flock` on `<git-dir>/lane-commit.lock` (the same file `bin/lane` takes in `commit`, which runs a perl `flock` on `$git_dir/lane-commit.lock`). Both block on the lock. `commit!` answers a refusal only if the lock cannot be taken.
- `git diff --cached --name-only`: refuses if any path outside `paths` is staged.
- `git commit --only --cleanup=whitespace -m <message> -- <paths>` through `babashka.process/shell` (`git` helper, source.clj ~1637; the helper is the seam, `babashka/process` pinned at `reference-code/babashka-process`, deps.edn 114/163). No JGit or other git library is in deps.edn (verified by grep).
- Verification: `git diff-tree --name-only` of the new commit must equal the written paths; otherwise `:seon.git/commit-error` naming the carried paths (history is not rewritten, so a wrong commit stays).
- **Missing today (verified by reading `commit-locked` and `git log -S candidate-digest`):** the commit's bytes are not checked against the proven candidate. 14b8ea164 added that check (refuse when a path's working-tree bytes differ from `:seon.source/candidate-digest`, and verify the parent); c53c9306e ("Revert the night's fences in one batch", cites AGENTS.md NO GUARDS OR FENCES) removed it. So `commit!` commits whatever the working tree holds for those paths at commit time. The only protection left is the lock plus the claims ledger, which the Clojure side does not read.
- Untracked new files are not added. `bin/lane`'s `commit_locked` runs `git add -- <path>` for untracked files under the paths, then `git commit --only` (which takes tracked files only), and resets its own adds on failure. The Clojure `commit!` does none of this. A landing that writes a **new** file (a namespace resource or source file that does not exist yet) makes `git commit --only` fail with the path not known to git: the files are already installed on disk and nothing is committed (**unverified** by running; reasoned from git's `--only` semantics and the code).
- Message: `commit-message` hardcodes the trailer `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>` and `Branch-evidence-runs:`. For Seon's own commits this is a root decision (the commit-attribution instruction for this session names Haiku for commits I make; the derived message is Seon's and says Opus).

**`bin/lane commit`** (bin/lane 457–630): claims are read from `tmp/orchestrator/lanes/<lane>.paths` (one checkout-relative path per line; `tmp/` is gitignored, so the ledger is not committed); `<lane>.base` holds HEAD at the first claim; `tmp/orchestrator/lanes/released.holders` holds `path<TAB>lane` for released paths. `claim` refuses a path another lane holds (`owner_of`) and a path with uncommitted changes nobody claimed (`dirty`: `git status --porcelain -- path`). `commit` requires the lane's claims file, proves the candidate (lint, `bin/seon check` or branch evidence), then `commit_locked` under the same lock. `release` moves paths to `released.holders` and removes the claim. `status` lists claims per lane.

**What `publish!` should reuse, not copy:** the lock (`call-with-commit-lock` already is it), the staged-other refusal, the `--only` commit and its name check, and the claims read (its rule: a path any lane holds, or a path `git status` shows dirty and unclaimed, is not written). It should add the untracked-add-then-reset step from `bin/lane` for new files, or refuse new files at prepare time (decide; see risk 1).

## 5. Three ranked risks

1. **Publication after facts, and the lane collision it leaves.** Facts reach main before files (section 0 item 3). Once `publish!` runs as due work, a path a lane holds or edits is written and committed under the landing unless publish checks the claims ledger and `git status` for that path first, and `commit!`'s byte check is gone (c53c9306e). Design the due-work rule to: (i) skip and wait as due work any path with a live claim or a dirty unclaimed status (the user's rule: a merge touching a lane-held path waits); (ii) write only when the path's disk bytes still equal the merged candidate's digest, checked immediately before install under the lock (a check at the owner, not a fence beside it); (iii) add new files with `git add -- path` and unstage them on failure, as `bin/lane` does, or refuse new files at prepare. A lane's staged index entry blocks every other commit, so publish must never leave one staged. **Unverified:** whether publish! can hold the lock across write-back and commit without deadlocking the JVM's own writer (write-back runs inside `merge!`, outside the Datahike writer; the lock is a file lock, so the same JVM re-entering it through `bin/lane`'s perl child is the case to test).
2. **A failed publication after an accepted merge marks the assignment `:error`.** In `apply-lifecycle!`, a `:merge` whose `merge!` answers a refusal throws, and `failed-pass!` writes `:seon.task.attempt/end :error` on the assignment; `seon.task/ready` reads `:error` as terminal. So a publication refusal ends an accepted, merged assignment as an error, and the next pass derives nothing for its files. The fix belongs at the owner: publication is a separate due-work action whose failure records its own refusal on the merge (as `seon.turn/landing-tx` did), not a throw from `:merge`. Until that holds, M8a must not ship. (Also `merge!` with nil root must not be reachable from `next-actions`.)
3. **Test evidence is thin where M9 lands.** The reaching tests `seon.cluster.merge-test` (four errors) are the proofs of the land path M9 replaces, their cause is not read, and `seon.cluster.write-back-test` (the largest reacher, ten `write-back!` calls) has no stored result at all. A green `publish!` could hide a broken write-back test. Before the commit, run `seon.cluster.write-back-test` alone and record its result; if it is red or unknown, classify it from stored runs first. The round's hang class (agent-test, the driver rebuilds) makes whole-round evidence unreliable for this change, so the named tests must run alone.

Not in the top three, noted: the `ended-problem!` notice text is wrong for non-merged ends; `seon.cluster.registry`/`seon.test` quoted operation symbols will need conversion if `publish!` is named differently; the `Co-Authored-By: Claude Opus 5.5` trailer is hardcoded in `commit-message` and is a root decision.
