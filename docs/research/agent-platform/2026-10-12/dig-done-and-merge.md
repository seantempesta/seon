# Dig: how an agent's work is done and how it reaches main

## 0. Summary for the planners

**The target** (owner, 2026-10-12): an agent's work is done when its task's proofs (deftests carrying the task in `:seon/tasks`) are green on its own Datahike branch. Nothing is called by the agent to say it is done. Something on root's side notices and merges the branch into main, git-style. The agent never pushes.

**What is live at HEAD today** is a different shape, and the planners must start from it:

- `seon.turn/task-end` derives the end of an attempt on the agent's branch. `:done` comes from `seon.context/task-done?` (the step's one rule, `seon.context/step-status`). A `:done` end on a terminal task makes the agent call `my.program/request-merge!`, which writes a merge task and a merge request on the branch (`seon.task/request-merge!`). Then `seon.turn/end-task-call` writes the end on the attempt.
- `seon.cluster.agent/db<->flow` is root's Flow process. It wakes on the branch's listen route, runs `seon.cluster.agent/unlanded-ends`, then `seon.cluster.agent/land-ends!`, then `settle-kept-branches!`, then `plan` and `apply-plan!`.
- `land-ends!` copies a `:done` or `:sent-back` end's cluster facts to main with `seon.cluster.squash/copy!`, which is one plain transaction with provenance as transaction metadata. Any other end becomes a problem task (`record-error-end!`).
- Code reaches main only through root: `my.root/merge!`, which calls `seon.cluster.source/land!`. That path runs the gate on a merge branch, merges with a Datahike merge commit (`d/merge-db!` with parents), closes the request with `seon.task/close!`, writes the bytes into the checkout and makes one git commit.
- The auto-merge dial `:seon.config.root/land?` is **false** in `config/default.edn` (commit f43646710, 2026-10-11). So at HEAD nothing merges code without root.

**What is designed but not built**: the push design (`docs/research/agent-platform/2026-10-12/hybrid-push.md`, phases U0 to U7, all still filed as tasks). Its first attempt (`mr-u0-u1-landing.md`) stopped because the design contradicts the code it deletes. None of its attributes exist yet: `:seon.task.attempt/merged`, `:seon.error.occurrence/attempts`, `seon.cluster.squash/auto-merge-tx` and `:seon.squash/attempt` removal are all absent or still in place as described.

**Five things the planners must not miss**

1. The copy basis is wrong today. `seon.cluster.squash/copy!` always squashes against the fixed fork commit and never advances it. Repeated copies double-count (occurrence counts 1 to 2 to 3 to 4; a conflict count 6 to 8). Any design must compute the three-way from the last copied commit, stored atomically in the same transaction. Astra #2, reproduced on default.
2. The decision is taken before the writer. `copy!` computes its squash on a captured main, writes conflict tasks in separate transactions, then transacts. A root edit between capture and transaction is silently overwritten. The three-way has to run inside the writer's own db value. Astra #3.
3. Two merge shapes coexist and disagree. Facts use `transact!` with no parent (git's `merge --squash`, deliberately: a parented copy pins the branch's lineage). Code uses `d/merge-db!` with parents (a real merge commit). The hybrid's "never `merge!`" claim is true only for facts. R1's join design proposes `datahike.api/merge!` for joins, which reintroduces the pinning. Decide the join shape explicitly.
4. Completion has no check that a proof was red before the work. `seon.context/step-status` for `:implement` accepts proofs already green at the fork point (no broken test, nothing new red, so `:done`). `seon.task/request-merge!` only attaches `:seon.task/red-first` when one exists and never refuses an empty one. CLAUDE.md's law "a task already green proves nothing" is not enforced at completion or at assignment (`seon.task/assign!` has no such refusal, though its docstring names `:no-proofs`, which is only in `my.program/request-merge!`).
5. Several designs are contradicted by code the planners will touch. A held successor keeps its predecessor's branch alive indefinitely (`successor-waits?` counts every unforked leaf, held or not). A cancelled attempt writes its end on main (`follow!`), and then `land-ends!` files a problem task "copy it by hand" for it, which contradicts "terminal". The collector marks every branch head, including each retained `:base/<branch>` ref, whatever its age, but follows parents only inside `:seon.config.db/snapshot-window-ms` (`datahike.gc/reachable-in-branch`). A merge base kept as a base ref therefore survives; a commit that is no longer any head, such as a predecessor's end commit after its branch is deleted, survives only inside the window. The `:datahike.gc/roots` fork change the hybrid depends on is absent from the pinned reference (zero occurrences).

### 1.4 What decides completion, in one sentence per kind

- **Implement**: the agent's branch shows its tagged proofs green at the head, no test broken from the fork commit, and every new red is a proof. Today this can also be true when the proofs were green before any work (section 3, edge 9).
- **Prove**: its tagged proofs green, product non-empty and new since the fork, each red by assertion failure or `:seon.error/unimplemented`.
- **Send-back**: `my.task/send-back!` with a target; never green.
- **Merge**: a `:done` terminal end asks for a merge request. The merge itself is root's act, done by `my.root/merge!` (or by the auto-merge dial, which is off).

### 2.2 What each rejected or revised idea was, and why

- **Datahike `merge!` for copies** (hybrid-agent-world §2): rejected in favour of a plain transaction with provenance, because a parented commit keeps the branch's lineage in the garbage collector's walk. Correction for planners: `datahike.gc/reachable-in-branch` follows `datahike/parents` only for commits inside the window (`in-range?`), so the pinning is bounded by `:seon.config.db/snapshot-window-ms`, not unbounded. The argument still holds for a window of one hour: a parent older than the window is not followed, but a merge inside it keeps a branch's history alive for the window.
- **Sol's and Opus's per-push designs**: both rejected end-only copying in favour of continuous push. Opus's ownership list and Sol's retention roots converged into the hybrid, with root's db<->flow as the only pusher.
- **Message delivery as database facts** (hybrid-agent-world §2): rejected; the owner's "messages are channels" decision is the one live kind.
- **Verdict tiers** (`seon.turn/reached-verdicts`): removed. The compiled gate is the single verdict (Q3).
- **Auto-merging on green** (`a9a0c23d1`): switched off (`f43646710`) until fences are removed; the owner later said root reviews each diff before it merges (fable-replan Q8).
- **Joins by parented merge** (R1 §6): open. Recommended in R1, but it reintroduces lineage pinning. No design has settled it.
- **Successor forks main after a predecessor's branch is deleted** (hybrid-agent-world H7): replaced by forking the predecessor's stored end commit (decision F, verify-astra header). The fallback to main is gone (b7cc27520).

### 4.2 Git (no reference copy in this repository; the words and rules)

- **Merge base** is the common ancestor (`git merge-base`). Seon's `seon.cluster.source/merge-base` is a retained commit, not the ancestor of the two heads. It is correct only while the base advances with each merge.
- **Three-way per path**: base, ours, theirs. Changed on one side only takes that side. Changed on both to the same value takes it. Changed on both to different values is a conflict and stays unmerged. Seon's per-identity equivalent is `seon.program/three-way` with `seon.cluster.squash/squash-merge`'s rules.
- **Fast-forward**: when base equals ours, the target moves to theirs, with no merge commit. Seon has no fast-forward; every merge computes a three-way, which is why a repeat must produce nothing (base advances).
- **Merge commit**: two parents, ours and theirs. This is `accept-merge!`'s shape.
- **Squash merge** (`git merge --squash`): one parent (ours), the merged result, no merge head. This is the facts copy's shape, by design.
- **Ref update with compare-and-swap**: `git update-ref <ref> <new> <old>` moves a ref only if it still holds the old value. The writer's `:datahike/expected-basis-t` plays the same role.
- **Unmerged** is git's word for an identity with conflict stages in the index until resolved. The hybrid uses "unmerged" for "head differs from merged", which is a different meaning (section 6).
- **Ours and theirs** swap in a rebase; Seon never rebases, so ours is the target everywhere.
- **Merge request** is a forge word (GitLab's pair: source and target branch) and is allowed by the vocabulary as the git family's. **Request changes** (for send-back) is a forge word too, not git's.

### 4.3 clojure.test and kaocha

- `clojure.test` reports through `clojure.test/report` event maps with `:type` `:pass`, `:fail` or `:error`. A test is green when it emits no `:fail` and no `:error` and at least one `:pass`. Seon's `seon.test/green-members` is stricter in its own evidence: began and ended, completed and terminated, pass count above zero. Keep the stricter reading.
- Kaocha (`reference-code/kaocha`) is named in the vocabulary as the test runner library. This dig did not verify that Seon's runner consumes kaocha's report maps; the planners should check before citing it.

### 4.4 core.async.flow (`reference-code/core.async/src/main/clojure/clojure/core/async/flow.clj`)

- `create-flow`, `start`, `stop`, `pause`, `resume`, `ping`, `pause-proc`, `resume-proc`, `ping-proc`, `inject`, `process`.
- `pause`, `resume` and `ping-proc` are the acknowledgement seam verify-astra #9 needs: a pause is acknowledged when `ping-proc` reports the proc stopped doing IO. Seon's pause writes only a flag today.
- The transitions `::flow/resume` (prime `db<->flow`) and `::flow/stop` (unlisten) are the lifecycle hooks Seon already uses.
- The work launcher (`seon.flow/submit!`, `flow/work-launcher`) is Seon's own, not part of core.async.flow.

## 7. Contradictions between the documents and the code, and decisions no ruling has made

### 7.1 Stale claims in the planning documents (corrected here)

- `verify-astra.md`'s status column is stale for #5, #7 and #9: `b7cc27520` fixed the fork fallback, the inline fallback, and the stop's interrupt.
- `verify-astra.md` #10 was true at `61bca1ed`; the pinned reference (`42309184`) applies the transaction once.
- `verify-astra.md` #12: the hand list `task-ref-attributes` is absent from `src`; `attempt-rows-tx` still imports entities.
- `hybrid-push.md` §1 says "a parented copy would pin the deleted branch's lineage to main and reclaim nothing" (in `hybrid-agent-world.md` §2). The collector follows parents only inside the window (`in-range?`), so the pin is bounded by `:seon.config.db/snapshot-window-ms`. The argument against parented copies still holds for facts (the copy's parent keeps the agent's whole lineage reachable inside the window), but "nothing" overstates the cost: parents outside the window are not walked.
- `hybrid-agent-world.md` §2 fork point H7 (main's head after the attempt write) was overtaken by F (`verify-astra.md` header). `write-attempt!` implements F.
- `merge.md` §5 names `:seon.config.merge/auto-merge` and a root-owned runner. Neither exists. The live dial is `:seon.config.root/land?`, false at HEAD.
- `seon.task/assign!`'s docstring names a `:no-proofs` refusal the body does not check.
- `my.program/request-merge!`'s docstring says a successful end "copies it to main"; that is the squash, and it is correct only for facts, not for the code's merge request, which waits for root.
- `R1` §6 proposes a parented `merge!` for joins; `docs/research/agent-platform/2026-10-12/` decision F chose an octopus. Both are documented; the code has neither (first sorted commit).
- The hybrid's claim that a crash loses nothing is right for derivable work because the prime at `::flow/resume` derives from facts. It does not cover a copy whose transaction committed while its later effects did not, which is edge 1: the marker is the only evidence and it lies.

### 7.2 Decisions no ruling has made (the planners must decide or name the owner)

1. **Join shape.** Octopus (decision F) or parented `merge!` (R1 §6). They differ on lineage pinning and on whether a join is one commit or several.
2. **Copy basis.** Astra #2 and the hybrid's `:seon.task.attempt/merged` are the same idea (last merged commit, atomic with the merge). The owner has not chosen the attribute's home (attempt or main's provenance). Decide before U1.
3. **Already-green proofs.** Refuse at assignment, or require a red-first observation at completion (the Prove rule applied to Implement), or both. No ruling. CLAUDE.md's law says a green-before-work proof proves nothing, so the law is already decided; the mechanism is not.
4. **Sibling merges that turn a fork-era green red.** No design. The merge gate catches it at the merge request, not in the agent's compartment. Decide whether the agent must re-judge after a sibling merge, and where.
5. **Held successors keeping branches** (edge 22). Derive waiting only from successors whose intent is `:running`, or keep until root says otherwise.
6. **Cancel.** Delete the branch with no problem task (verify-astra #9), or keep it for audit like an error end.
7. **Attempt, step, end, done, problem task, `:root` conflict rule.** Section 6 lists them; the owner's vocabulary rule says they must be the library's or git's words.
8. **Auto-merge.** The dial is off. R-10 says the criteria come from root's reviews. No criteria exist. Decide the first criteria before turning it on, or keep root's review as the gate.
9. **The merge request's own identity.** Today a merge task and a merge request are two entities; the push design keeps one per attempt. Decide one identity: `seon.id/id` over `[assignment commit]` (today's merge request) or over the attempt alone (push design).
10. **Fork change `:datahike.gc/roots`.** Option A in R-4. It is absent from the pinned reference. Either the fork change merges, or the window must cover every merge base a branch can need. Decide before any code relies on a predecessor's end commit older than `:seon.config.db/snapshot-window-ms` after its branch is deleted.
