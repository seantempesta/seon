## #9: exact cause

The chain of events, all at HEAD:

1. **The boot captures the boot commit.** `seon.cluster/published-program`
   (`cluster.clj:1808`) builds the base with `sci.eval/cluster-ctx` on the
   `current-src` connection. `cluster-ctx*` (`sci/eval.clj:2606-2608`) stores
   `{::loaded-database (loaded-program db)}` in the program snapshot. That value
   is the `current-src` database at boot. `stand-cluster-runtime!`
   (`cluster/boot.clj:79`) forks that base, and `fork-cluster-ctx`
   (`sci/eval.clj:2672-2675`) copies the snapshot, including `::loaded-database`.
2. **Acquisition carries the captured value forward.** `acquire!`
   (`sci/eval.clj:2542`) passes `(::loaded-database snapshot)` into `base-ctx`.
   `derive-base-ctx` (`:2385`) merges it. `acquire-program!` (`:1869`) prefers the
   snapshot's value over `(loaded-program db)`. The snapshot keeps the result
   (`:1948`). Every later acquisition compares against the same value: the boot commit.
3. **The adoption record is ignored.** `development-source-refresh!` reloads
   (`cluster.clj:2426`), arms (`:2440`), and then writes the cluster row's
   `:seon.source/commit-id` to the published commit (`:2459-2471`). Nothing
   reads that record again, because the constructor's value always takes precedence.
4. **Why it became worse with `5f2aa93f4`.** Every row changed since boot counts
   as overridden against the boot commit, and so do its reverse-closure callers
   (`:1872-1884`). `install-row!` (`:966-981`) now refuses every interpreted row
   whose indexed `:seon.fn/host-bound?` is not `false` (`host-bound-row?`
   `:891-901`). Rows the JVM already runs compiled are therefore sent to SCI,
   which then refuses them. The other refusals, such as "Unable to resolve symbol:
   managing-process-identity", are interpreted callers that reach private host
   state they cannot see.

`acquired-database?` (`:2452`) compares only the program revision basis of the
branch. A fork whose branch rows did not change keeps its acquisition across an
adoption, even though the JVM moved underneath it.

## #9: which commit to track, and from where

**The loaded program is the commit named by the adoption record,
`:seon.source/commit-id` on the adopting cluster's row, read from that cluster's
live connection at every acquisition.**

- The value is Datahike's commit id of the `current-src` branch
  (`source/current` → `registry/branch-commit-id`). Adoption transacts the record
  only after reload and arming succeed. It is a fact, not a stamp. Nothing is
  attached to a value.
- It must come from the adopting cluster's connection, not from the acquired
  branch. There is one set of loaded namespaces per JVM. A branch's own record
  is its branch-point value.
  - Suppose an isolated branch acquired after an adoption compared against its
    own old record. Rows the adoption changed would look unchanged, and the
    branch would bind the new compiled Vars. Code would move underneath an
    isolated agent, which violates the ruling in AGENTS.md: "nothing moves
    under it until it merges".
  - Comparing against the JVM's record instead makes the isolated agent
    interpret the older rows of its own branch. A host-bound row among them
    refuses by name, which is the honest answer.
- Datahike seam: `d/commit-as-db` (`reference-code/datahike/src/datahike/versioning.cljc:473-492`,
  fork `fbd1ad2d`) materializes the commit. The existing `base-ctx-key`
  (`sci/eval.clj:2394-2410`) already keys the memoized base on the loaded commit id.
- No new cache is needed. Record query: 0.066 ms. `loaded-program`: 1.7 ms.
  `function-digests` of it: 9.7 ms. All were measured on default and are warm
  through Datahike's query cache.

## #9: fix design (hunks in `tmp/m9-adoption/loaded-program.patch`)

1. **`sci/eval.clj`: split `loaded-program`.**
   - `loaded-source [snapshot database]` returns the `::loaded-connection` value
     when the context holds one, and otherwise the acquired value.
   - `loaded-commit-id [database]` is the record query, with the same
     `current-src` and ambiguity branches as today.
   - `loaded-program` materializes that commit.
2. **`acquire!`** derives `::loaded-database` from
   `(loaded-program (loaded-source snapshot database))` on every re-acquisition.
   It no longer copies the old snapshot's value. `::loaded-connection` is copied
   back onto the new snapshot, so the memoized base stays a function of its key.
3. **`acquired-database?`** also requires the acquisition's loaded commit id to
   equal `loaded-commit-id` of the source. That adds one 0.07 ms query per call
   (`sci/eval.clj:3261` evaluation entry and the `seon.test` caller).
4. **`cluster-ctx*` and `fork-cluster-ctx`** accept `::loaded-connection` in their
   arm-request `select-keys`. A fork inherits the base's value through the
   snapshot copy, so isolated agents, the MCP branch path and tests read the
   cluster's connection, never their own.
5. **`cluster/boot.clj:74-76`** adds `:seon.sci.eval/loaded-connection connection`
   to `arm-request`.
   - **`cluster.clj` needs no hunk.** The record write at `:2459-2471` is already
     the authority.
   - `published-program` must not pass its connection, because it releases that
     connection at `:1818`.
6. **Contracts.** The arm-request schemas of `cluster-ctx` and `fork-cluster-ctx`
   gain `[:seon.sci.eval/loaded-connection {:optional true} :seon.db/connection]`.

**Regression (sci/eval owner, `test/seon/sci/branch_execution_test.clj`)**, using
the canonical fixture, real SCI and armed contracts:

- Build `cluster-ctx` with `{::eval/loaded-connection connection}` and acquire.
- Change one compiled host-bound row's digest, then transact the cluster
  record = that commit.
- Assert that `acquired-database?` is false once only the record has moved.
- Assert that after `acquire!` the snapshot's loaded commit equals the record,
  `interpreted-count` is 0 and there are no acquisition refusals.
- Assert the same for a fork on an isolated branch opened at the head.
- Stability: for a branch opened before the record moved, assert that it
  interprets exactly its own differing row, and the host-bound one refuses by name.

At HEAD the first two assertions fail, as in the probe above.

Before writing the test, verify that the canonical fixture carries exactly one
`:seon.source/commit-id`: `cluster-ctx*` calls `loaded-program` at construction.

**Known limit.** With several clusters in one JVM, each ordinary cluster's own
record describes the program it retained, not the JVM. The ruling in AGENTS.md
("default alone runs compiled") points every cluster at default's connection.
Choosing the connection per cluster at boot is a follow-up for the boot owner.
It is not a blocker for M9's single-cluster case.

## #17b: verified cause

- **`da703089b`**, the armed commit: `write-owned-values-error` had **no**
  `:malli/schema`. `git show da703089b:src/seon/db.clj` gives `:3037-3040`.
- **`6bf3bde78`** (15:07), inside the published range `da703089b..af5eea72f`,
  **added** the contract with `[:map-of :keyword :map]`. Datahike's `:schema`
  also maps attribute entity ids to their idents.
- **`1819cdcd3`** (15:13, after the range) fixed it to `[:map-of [:or :keyword :int] :map]`.
  At HEAD this is `db.clj:3286` (and `:3712`).
- **The log names the refusing write.** In
  `tmp/reload-per-declaration-evidence/adopt-c-to-d.log` the refusal carries
  `:seon.boot/population :seon.source/commit-id`, with the expected schema
  printed as `[:map-of :keyword :map]`. That is the adoption **record**
  transaction (`cluster.clj:2459-2471`), which runs after reload and after
  `instrument/apply!` armed the adopted contract.

So adoption ran the adopted code under the adopted code's own contract, which is
what the issue asks for. The contract itself was wrong. Neither "arm before the
writes" nor "arm from rows" would have changed the result.

**Residual (cluster.clj owner, not new):** a record refusal after the reload leaves
the JVM at the published commit while the record still names the prior commit.
With the #9 fix, acquisitions then over-interpret until the next adoption
reconciles. The docstring of `refresh-source!` states that reconciliation, and
M11 covers adoption cost. The live check of the loaded contract against default
was not run: default was replaced (pid 9104, start 00:28:15Z) during this lane
and had no connection for more than 2 minutes. Source verification only.

## Out-of-scope finding: refusal recording costs 30–120 s

The "installed code" acquisition took **120,890 / 29,555 / 67,995 ms** in three
runs. The other acquisitions took 602 and 1,014 ms.

- A 500 ms stack sample, taken 100 times during the 68 s run, found the acquiring
  thread inside `record-acquisition-refusals!` → `seon.db/transact-call` in
  **100/100** samples.
- The refusals are already recorded in one transaction. Each `error/commit-tx`
  still adds its own `[:db.fn/call #'commit-call …]` (`error.clj:1535`), and
  `commit-call` reads `db/carried-projection` (`:1398`). The docstring of
  `carried-projection` (`db.clj:1357-1369`) says a speculative value's key
  includes every earlier operation of its transaction. So each of the 108 calls
  would miss the memo.
- This matches cause 1 in
  [warm-restart-hangs-in-agent-arm-waiting-on-an-atom-monitor](../../seon/issues/warm-restart-hangs-in-agent-arm-waiting-on-an-atom-monitor.md).
  The writer thread was not sampled, so this cause is consistent with the evidence
  but **not verified**. That issue is the durable path: extend it with these three
  timings.
- It is over 10 s, so it is a defect. The #9 fix removes this instance (0
  refusals), but a real override of a widely called function still pays it.
