## What was built (and where the spec puts it)

- `system-message [db agent-id]` → string: the `(help)` lines (`seon.bootstrap/help-value`, fixed in place: run named
  tests with `my.test/check`, `clojure.repl/apropos`, `my.program/source`, Markdown is read as code), then every
  context-relevant namespace (`seon.cluster.instruction/toolkit-namespaces`) with each public function's docstring
  summary and its documented example. Nothing hand-written in the producer.
- `task-context [db handle]` → vector of `:seon.agent.loop/unit` `{why, form, value}`: the task; `task-edges`; per
  proof test its recorded result, recorded failing assertions (only when any) and source; per must-read/subject
  function `(doc f)` and `(clojure.repl/source-fn 'f)`; the registered schema keys its declared contract names; other
  tasks naming the same functions; recorded errors raised by them (only when any). Each form is a requery the agent can
  run itself.
- `context-text [units annotated?]` → each unit as `user=> form` + value printed whole by the value printer
  (`seon.print/full` through `seon.render.value/render-ai`); a string value (source) prints as its text.
- Test: `test/seon/agent/loop_test.clj` (two behaviors, green in `bin/seon check`).

**Spec vs reality.** Spec §3 puts the context in `seon.agent.loop/context` as the agent schema's own `:seon.render/ai`,
with a live `task-view` unit (the steps view, task.clj:496-520) and an inbox; a system message is not in the spec at all
(live-run report: "protocol as a mandatory context unit or system message"). I built the smallest version that matches
the spec's namespace and "rendered live from the db, nothing stored": two unwired producers in `seon.agent.loop`; the
`task-view` unit is replaced by `task-context` (the steps view carries only id/name/intent/steps, no proofs or refs).
Not built: the agent render, budget, inbox, history, `seon.cache` wrapping (spec P4). Decision for the owner: system
message as a separate cacheable provider message (built here) vs a mandatory first unit (spec wording).

### Can an agent do the task from this context alone?

- **Find:** yes. The task names the function; its doc, contract schemas and full source are present; the proof test's
  source says what is asserted.
- **Change:** yes for the code (`in-ns` + `defn`, in help). The schema forms are stored strings and print as strings.
- **Test:** yes: `(my.test/check {:seon.test/changed ['the-proof]})` is in the system message, verified at the REPL.
- **Finish: no.** The proofs are already green, so "done = proofs green" says the task is finished before any change,
  while the intent (e.g. a 36x cost, a whole-history scan) is not what the proof measures. `my.task/complete!` does not
  exist yet (spec §4, TARGET), so the agent also cannot bail with a reason; only `my.agent/done` (end session) exists.
