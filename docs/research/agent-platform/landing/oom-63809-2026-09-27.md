# oom-63809-opus: default's `OutOfMemoryError: Java heap space` (2026-09-27 ~17:29Z)

## Still broken (read this first)

- **Any evaluation that returns an infinite lazy seq kills the JVM.** For
  example, `(range)` at the REPL. Admission bounds the value inside the arm
  (`seon.sci.admit/admit`, which checks the interrupt at every node). The
  evaluation then keeps the live value whole, and `seon.turn/unbound-value?`
  (turn.clj:94-103 at e9877da0f) walks it with `(tree-seq coll? seq value)`.
  That walk happens after disarm, with no bound, no deadline and no interrupt.
  It is called for every form, twice: `seon.problems/form-problem`
  (problems.clj:219) and `seon.turn/evaluation-facts` (turn.clj:124). An
  infinite seq never ends. A finite seq is realized in full, a second time,
  outside the arm. The corpus lane re-probed on the new JVM:
  `(map f (range 200000))` is realized to 200,000 elements by
  `unbound-value?`, although the agent was shown 32.
  Filed as task `d1efccd3ab7e` (`the-unbound-check-walks-the-live-value-without-a-bound`) in
  `resources/seon/tasks/seon.turn.edn`. Owner: the next `turn.clj` holder
  (root assigns; `turn.clj` has no holder in the ledger now). The run/eval
  session-model hold does not cover this check. The corpus lane filed the
  same class as `a-result-is-walked-whole-after-evaluation` (f91574f41). It
  dropped that entry as a duplicate of `d1efccd3ab7e` in b44d2229b, so
  `d1efccd3ab7e` is the one task for this class.
- **Root's question: does the heap confirm the corpus lane's account?** Yes,
  on every point. The dominator is a realized chain of `clojure.lang.LazySeq`
  and `clojure.lang.Cons` cells, not `ChunkedCons`. SCI's `(range)` is
  `sci.interrupt/range-seq`, which produces unchunked cells. The chain holds
  115.9 M `Long`s and retains 10.2 GB, 93.7 % of the heap. Its only GC root is
  a Java local of the turn thread. That thread is inside
  `unbound-value?` ← `form-problem` (problems.clj:219) ← `resume-turn`
  (turn.clj:5368). The evidence is below.
- **Why the gate did not stop the in-flight walk.** The gate is
  admission-only by construction.
  - `own-arm` (kernel.clj:331-338) checks the pressure state only when a new
    outer SCI arm is taken, and "cuts none admitted".
  - The crossing handler `memory-pressure-crossed!` (boot.clj:397) only
    closes arming, prints, and records a fault. It holds no reference to
    running work and interrupts nothing.
  - The walk was not armed work at all. It ran after the evaluation disarmed,
    so no arm, deadline or interrupt existed for anything to cut. SCI's
    `range-seq` polls the thread's interrupt function, and outside an arm that
    function is inert.
  - Its in-flight list was also blind to the run: see the next bullet.

  Stopping in-flight work under pressure would not fix this class. The fix is
  that no work runs unbounded after disarm.
- **The memory-pressure gate named the wrong in-flight work.** It printed
  "In flight when it began: no open run" while a hosted branch agent's run was
  open. `seon.cluster.boot/open-runs` (boot.clj:388) queries each running
  cluster's own connection. `running-instances` holds only `"default"`
  (probed on the live JVM), so an open run on a hosted branch (`corpus-2`)
  is never listed. Filed as task `d287c254b094` (`the-memory-gate-names-in-flight-work-it-cannot-see`)
  in `resources/seon/tasks/seon.sci.kernel.edn`.
- **Is the gate's contract honest?** Only in part. `own-arm` (kernel.clj:331-338)
  refuses new arms and, by its own comment, "cuts none admitted". That behaviour
  is what the gate does, and it matches the law "timeout is not termination".
  The false statements are elsewhere:
  - The `seon.sci.eval` namespace docstring (eval.clj:31) says "O4's heap
    watermark plus the caller's submission backstop cover what this
    [interrupt] cannot". They do not. The watermark governs only *new SCI
    arms*. Unarmed work goes on running into the OOM: the post-admission
    phases of a run (form-problem, evaluation-facts, settlement), JVM-mode
    prepl evaluations and web requests.
  - The printed in-flight list reported "no open run" while one was open.

  The gate is not the fix. What killed the JVM was unbounded work outside any
  arm, and the one-JVM law says such work must not exist. An honest contract
  reads: "refuses new SCI arms; neither stops nor names unarmed work." The
  docstring sentence goes, and the in-flight list covers hosted branches.
- Installed proof is pending for both tasks. This lane was read-only and
  changed no source.

## Cause

The probe-valid-clojure-opus corpus runner (`tmp/valid-clojure-corpus/runner.clj`,
`run-all!` on branch `corpus-2`, started 17:26:32Z through MCP `eval_clj` jvm)
reached item `h35-lazy-infinite`, whose whole source was `(range)`. Items h21
to h34 finished by 17:26:36Z (result mtimes). No result for h35 was written.
The MCP call timed out at 17:28:32Z (120 s). The evaluation kept running,
because a timeout is not termination. The JVM died between 17:28:39Z and
17:29:02Z (the lane's next probe got `transport-closed`). The lane then
replaced the item with the finite `h35-lazy-large` (`(range 1000000)`), and it
passes on the new JVM in 561 ms.

Chain (heap evidence below):

1. `seon.cluster.agent/evaluate-source!` (agent.clj:793) → hosted agent's
   turn on a flow proc → `seon.turn/resume-turn` (turn.clj:5361-5368) →
   `phase` → `seon.problems/form-problem` (problems.clj:219)
   → `seon.turn/unbound-value?` (turn.clj:101) → `clojure.core/some` over
   `tree-seq`, which realizes SCI's `(range)` (`sci.interrupt/range-seq`) one
   element at a time.
2. The head of the seq is retained. The armed wrapper's `apply` holds the
   argument list (`ArraySeq` → `Object[1]` → the LazySeq, a Java local of the
   turn thread). The evaluation map holds `:seon.sci.admit/value` whole, and
   `bind-result!` holds the result handle. So every realized cell stays live.
3. SCI's interruptible `range-seq` consults the interrupt function. Outside an
   arm the thread has no arm, so nothing interrupts it
   (`sci.interrupt$range_seq$gen` closes over `clojure.core$constantly`).

The thread that threw the OOM was a victim: a web request

## The owning fix (for the assignee; not done here)

The smallest composition deletes a walk rather than bounding it.

- Admission already visits every node of the value inside the arm, once,
  bounded by the storage cap. It names an SCI object leaf by
  `object-node` (admit.clj). SCI's unbound marker is such a leaf. The admitted
  print node or record can therefore answer "contains an unbound marker"
  from that one walk.
- `unbound-value?` then reads the admitted result instead of
  `(tree-seq coll? seq live-value)`. The second caller disappears too:
  `evaluation-facts` (turn.clj:124) and `form-problem` (problems.clj:219) each
  walked the same value. Cost goes from O(realized value), unbounded, ×2 per
  form to O(1) per form.
- Class regression: an ordinary run of `(range)` on a test branch returns its
  bounded value, settles, and leaves the JVM's old gen flat. The finite version
  asserts `@seen` stays at the printed prefix after the run settles.

Wider class (same law, "nothing walks a live value unbounded"): any
post-admission consumer of `:seon.sci.admit/value` that walks it. That means
`disposition` (turn.clj:5181), render selection and `final-shown`. Each should
be checked for a full traversal. They were not measured here.
