## Landed: R10 partial, render once (`5c88d5110`, `src/seon/test/runner.clj` +31/−26, net +5)

Before this change, each failing assertion rendered expected/actual three times: once in
`failure-report`, again in `capture-event!`'s `failure-message`, and again when `report-event!`
printed `failure-message`. `message-text` also ran three times. Now `capture-and-report-event!`
builds the `failure-report` once per failing event. That one report feeds the stored evidence, the
identity and the gate-log text. `failure-message` lays out the report's already-rendered fields and
now declares a contract, `[:=> [:cat :map :map :seon.test.failure/report] :string]`.
`report-error!`, `report-event!` and `capture-event!` take the report as an argument. Deleted
paths: the two re-rendering calls to `report-value` inside `failure-message` and the per-event
`failure-report` inside `capture-event!`. No definitions were deleted, so the result is net +5
lines. No test calls the changed arities; tests reach this code through
`capture-and-report-event!`, whose signature is unchanged.

REPL evidence (jvm, default; scratch namespace `tmp.r10-runner` holds the five new forms, interning
default's other runner functions; nothing of default's was redefined):
- Five edge cases compared old `failure-message` with the new layout-from-report under
  `*testing-contexts*`: nil expected, message with no operands, Throwable actual, non-string
  message, empty message. All `:same? true`.
- A real `clojure.test/test-vars` run of a probe test (a `testing` failure, a pass, a thrown
  ex-info), old vs new `capture-and-report-event!`: same gate-log output, same counters
  `{:error 1 :fail 1}`, same captured results (identities, reports, `failure-message`). Every
  stored report validates against `:seon.test.failure/report` in the live projection.
- Timing: five failures on a 300-map vector took old 43.6 / 43.5 / 43.1 ms and new
  15.3 / 15.3 / 22.6 ms, with identical output. One `failure-report` costs 6.3 ms; the old
  `failure-message` cost 8.7 ms each time it ran; the new layout costs 0.02 ms.
- Scratch copies run unarmed, so real values were validated explicitly: reports against
  `:seon.test.failure/report`, output string.

## Landed: R6 (`src/seon/cluster.clj` +9/−71, `test/seon/cluster/mcp_test.clj` +25/−83)

The patch deletes `nil-deref?` (5 lines), `first-seon-frame` (9), `exception-summary` (20) and
`mcp-projection-error` (20), plus the `exception-summary-value` branches in `mcp-project`, for
+9/−71 (net −62). A JVM exception's prepl value (`Throwable->map`, via, trace, cause, data, phase)
then goes through the ordinary admit → `render.value/prepare` path like any value. A projection
that itself throws degrades to `render.value/floor`, the bounded Throwable text built from the
whole cause chain, in both `mcp-project` and `mcp-valf`.

Probe on default: I called `#'seon.cluster/mcp-project` with the ordinary branch (`exception?`
false) on that envelope. It returned the whole cause (both via links with message, class and
`{:seon.probe/k 1}`, cause, phase, trace) in 12.5 ms, blob-backed at 9,223 bytes, retrievable by
digest. The summary took 2.3 ms because it stores nothing. The difference is the ordinary
blob put for any value over `:seon.config.eval.result/blob-threshold`.

Tests converted in the same commit. Deleted `jvm-nil-deref-is-a-flat-error-value`,
`jvm-ex-info-projects-its-message-class-and-first-party-frame` and the flat-summary scenario,
including its retired "10× smaller than the envelope" assumption. They are replaced by the
lifecycle scenario `jvm-exceptions-keep-the-whole-cause`. It asserts that a small exception stays
inline, that every via link's message, class and ex-data is present, that the root cause is the
value's `:cause`, and that an oversized cause pages by digest at `[:cause]`. On default, the same
ordinary path returned inline, `[{:seon.probe/member 1} nil]` data per link; an oversized
5,000-char cause returned windowed, retrievable, with a 72-char page and total 5,000. The five
`seon.dev.mcp` error schemas stay (no schema retirement in this cut); retiring them is the
follow-up step.
