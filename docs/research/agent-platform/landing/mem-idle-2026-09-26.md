## Design: one cache owner with a memory cap (recommendation, not implemented)

The owner rulings are that every cache is configurable, uses a library rather than a hand-rolled cache, and sits under a fixed memory cap. Three options:

1. **Config dials on the existing core.cache LRUs** (simplest).
   - Each `defonce … lru-cache-factory` threshold becomes one map dial, `:seon.config/cache-thresholds {cache-id n}`.
   - Guarantee: a bound on entry count. There is no byte cap, because entries differ in size by 1,000×: an arity base is 50 MB, a program identity is under 1 KB.
   - Cost: about 40 lines.
   - Sacrifice: no process-wide memory cap.
2. **One Caffeine cache, keyed `[cache-id key]`, with `maximumWeight` set to one byte dial and a weigher (recommended).**
   - Caffeine 2.9.3 and 3.2.4 are already in `~/.m2`. The cache needs no hand-rolled eviction: it uses W-TinyLFU and gives per-cache `recordStats` miss counts through `stats()`.
   - Weigher: a size recorded when an entry is inserted, never a deep object walk. For an arity base that is edges × 500 B. For a base ctx, the program's definition count × a measured bytes-per-definition. For a projection, its schema count × a measured bytes-per-schema. For a render entry, the pulled datom count.
   - Callers keep the `lookup-or-miss` shape. core.cache ships a wrapped protocol, so the change is a `seon.cache` namespace of about 60 lines that replaces about 15 `defonce` caches. Most of those deletions are one line, so the change is roughly net-neutral.
   - Datahike's `CachedStorage` cannot share this cache without a fork change: it creates its own core.cache LRU at `persistent_set.cljc:463`. It should take its own dial (`:store-cache-size`, already Datahike config) and become one instance per physical store in the fork. That fork change is about 20 lines and deletes the per-connection copies.
   - Cost: about 1 day with review. Guarantee: a fixed byte cap for derived values.
3. **Soft references (`softValues`)**: the GC evicts entries under pressure. Nothing is tuned, but eviction is unpredictable, all caches are cleared at once near OOM, and latency jumps. This is not recommended.
