# Shake the language: identity, ownership and time

Seon already has declaration rows, an issue writer, immutable database projections, contract compilation, merge comparison and a render path. The smallest composition is to feed those owners better declarations, keeping identity, revision and historical observation distinct.

**Verdict:** the central design is attractive: facts beside their producer, tests pointing to tasks, one effective contract, one acquired value with two faces. The previous review's principal P0 corrections are present in the requirements. The remaining fragility is concentrated at changes of authority or time: minting versus revising a task, file versus row edits, and retaining a value versus executing it later. Three P0 findings below block their affected slices; they do not require postponing every finite task read or explicit-contract annotation.

The language is least beautiful where an agent must remember whether a declaration is generated, explicit, migrated, runtime, not yet born, already shown, or written through a shell before knowing who may change it. Most of those distinctions are useful provenance or lifetime facts. They should not become separate authoring languages.

## Ranked findings

### P0-1 — task identity is currently a moving target

L2.5 says authored tasks are named qualified keywords; L7.2 requires the ID itself to read as the problem. L3b.6 instead derives it through `seon.id` from the task's defining data, including an authored task's “own data.” L1.9 requires the exact literal token everywhere. None defines the immutable identity inputs or distinguishes an edit from a new task. R:652 still migrates IDs “from its slug.”

If intent, `needs`, evidence path or subjects participate in a continuously recomputed ID, ordinary triage creates another entity. Existing annotations, proof edges, attempts and acceptance retain the old ID. If they do not participate, the writer needs the explicit creation-only rule. Even a harmless EDN map reorder can change a raw `seon.id/id` input's hash. This is an identity defect before it is a grep defect.

**Smallest correction:** specify an immutable defining tuple, mint once through `seon.id`, persist the resulting qualified keyword literally, and put mutable content under a separate revision digest. Preserve a readable creation label in the keyword; never maintain a second mutable slug authority. Exact proposed semantics appear below. Blocks authoritative minting/migration, not reading already unambiguous IDs.

### P0-2 — task EDN and the runtime writer can overwrite each other's intentions

L7.1 permits task data from EDN or a runtime writer; 7.9 reconciles by ID; 7.13 coordinates task admission with program admission. L2.8/7.7 correctly protect attempts and decisions, and 7.15 correctly forbids two current Markdown/task representations. **Neither decides two edits to the task's own `intent` or `needs`.** R:627–643 gives reconciliation no authoring base or conflict result. Reusing `issue/index-tx`'s transaction authority only serializes the last desired state; it cannot discover the author's earlier base.

**Smallest correction:** both entrances submit a desired task declaration with the revision they read to the existing task/issue writer. Compare at that writer; unchanged re-ingestion is a no-op; a competing revision returns base/current/proposed values. Preserve runtime facts by declared ownership, not an ever-growing keep-list. For a file-backed declaration, retain the last synchronized file/row basis and use the same accepted declaration for write-back; no independent “file always wins” mode. A runtime-only task needs no file until explicitly exported. No task merge engine is required: stale same-task edits may simply refuse for repair.

The task-before-program sequence in 7.13 is sound. State its failure semantics: if the task is admitted and the program gate later refuses, the task remains valid, possibly raised; there is no accepted program or settled task. Acceptance must bind the reviewed **task revision**, proof identities/digests and tested destination, not just resolve a still-existing task ID. Otherwise a changed requirement can inherit acceptance of its previous meaning.

### P0-3 — the write-back race promise exceeds the file writer's guarantee

R:509–519 promises that a colleague's intervening edit is never overwritten. Counterexample: write-back reads base B, proves candidate C, rechecks B; a shell writes S; write-back renames C over S. The published digest equals C and every stated post-check passes. S has disappeared. The restore path has the analogous check-then-restore window. An atomic rename makes replacement indivisible; it does not condition replacement on the old digest. The existing writer explicitly acknowledges this limit (`fs/jvm.clj:702–709`).

**Smallest correction:** M1 uses the existing one-file/one-owner discipline to exclude simultaneous shell edits from capture through installation/publication. Retain digest checks to detect observed drift, but state the cooperative-writer boundary honestly. This is a constraint, not a new lock service. If arbitrary external editing must remain supported, the guarantee needs a separately reviewed file-installation mechanism before implementation; another post-write comparison cannot prove no lost edit. Canonicalizing before the gate, as F:265–282 requires, remains correct.

### P1-1 — the one-edge rule needs an end to its exceptions

L7.4 gives code ownership of subjects but permits unborn subjects in EDN; 7.8 permits runtime writers to name existing subjects before code does. It does not define transfer when the definition appears, an annotation is added, or a task settles. A naive union of “EDN subjects + runtime subjects + reverse annotations” preserves stale subjects after code drops the ID, defeating 7.6. A rename can then resemble settlement or abandonment.

**Smallest correction:** code annotations are the only actionable subject edge for existing declarations. A runtime/unborn subject is a proposed attachment, with provenance, consumed or explicitly dismissed when triage attaches code. The writer refuses two current owners of the same actionable edge. Root acceptance plus removal of **all current subject annotations for that task** is settlement; removal alone never is. The acceptance value checks this final state. A rename carries every still-open task token into the new declaration before retiring the old one; it does not remint task IDs.

L7.2 uses a set for subject tasks but 7.3 gives a test one scalar task. One regression can prove two tasks. Requiring cloned tests to preserve that distinction is ugly and violates the aim not to explode the suite (3.2). Let the existing test-owned relation be many-valued, using one spelling consistently; do not also list proofs in task EDN. This is a proposed cardinality simplification, not an assertion that it is already installed.

### P1-2 — one effective contract is good; its derivation still has competing rules

L1.12 now decides: explicit `:malli/schema` wins; otherwise outputs come from the one analyzer. D:131–177 still specifies a hand-maintained tail-form interpreter and recommends `:seon.fn/returns`; D:213–220 preserves three producers by calling one helper. Those are superseded choices, not new open options. R:377–379 similarly retains the retired done-when compiler. Revise in place before assigning implementation from them.

D:185–195 says disagreement is advice, then becomes refusal when a census reaches zero, with an immediate closed-map exception. A census cannot change language semantics. A closed input map omitting a destructured key is not necessarily wrong: `(fn [{:keys [acme/x] :or {x 0}}] x)` can intentionally accept `{}`. A body reading an undeclared optional key is not proof that the contract must allow it. Keep explicit-contract precedence and diagnostic advice; reject actual malformed contracts and incompatible declared arities through their existing owners. Do not implement a second partial type system from a mismatch count.

D:273–274,387 keys derivation by source digest alone. Binding resolution also reads namespace aliases; effective compilation reads referenced schemas and named predicates; analyzer inference has its own revision/configuration. A key's schema can change while both source and the stored symbolic contract form stay identical. **Separate syntactic derivation from effective compilation.** Reuse the existing schema dependency graph and compiled projection. Changed referenced meaning invalidates preparation, arming and test evidence; unrelated writes do not. Preserve unresolved authored declarations as data while refusing executable adoption. F:319–320 demands a stored provenance fact, while D:207–209 says provenance is derived and leaves a boolean to the face owner: choose derivation from the admitted declaration/analysis once, not renderer-owned flags.

### P1-3 — retaining executable objects is not retaining an immutable observation

L1.11 and F:355–363 correctly separate evaluation-owned functions from program identity. Q:301–312 correctly makes continuations fail when sources or producer evidence are gone/stale. But L9.5's explicit lazy expander crosses from rendering into **new execution**. A live lazy result can close over a connection, mutable object or Var; retaining it does not pin what later realization will read. A page bound also does not bound the time/effects of one element.

**Smallest correction:** ordinary retrieval navigates already represented data. Realizing a lazy prefix is a new ordinary evaluation with its own execution bound, actual-exit ownership, read/effect evidence and shown text. It never re-evaluates the origin form. Do not advertise a historical snapshot of an arbitrary closure. If the originating context/program evidence changed, refuse the historical expansion as stale; a deliberately requested current evaluation is separately labelled current. An inline renderer whose namespace/dependencies disappeared is likewise unavailable/stale, not resolved to a new same-named function. Saved shown bytes remain readable until ordinary retention removes them.

Q:305 still uses query + branch + basis as historical coordinates, whereas R:259–263 explicitly requires retained commit identity and history across divergent branches. Use the origin commit/lineage already owned by Datahike, with an honest expiry; branch name plus transaction number is insufficient if that branch is repointed. No new permanent result store follows from this requirement.

### P1-4 — the migration promises durable entry points but retires their identity

L3b.6 retains the old issue path “until it is rewritten”; 7.15 promises old entry points resolve the same current task. R:606 and 665–668 retire the old slug identity without stating how those entry points continue. Rewriting one evidence document does not update forty citations or preserve their historical meaning.

**Smallest correction:** retain the old path/revision as a structured historical reference on the migrated task through the existing issue owner; derive reverse lookup from that fact. Keep the Markdown at its cited path as evidence, or leave a generated pointer when it is moved. Neither is a second editable task. Do not retire an old identity lookup until its public callers resolve through this relation. Historical `file:line` still refers to the pinned old bytes; current-task navigation follows the association. No global hand-maintained redirect file and no parsing prose to find aliases.

### P1-5 — several “derived” views still smuggle in another population or cost

F:151–167's `K(agent)` means **ever shown since opening**, not present in the selected prompt. It also stores subject identity without schema revision, so a changed schema can be suppressed as already known. Either label it “previously shown” and key observation by identity plus shown definition digest, or let current prompt selection supply the relevant evidence. Do not add a second hand-maintained context inventory. The simplest first face omits this optimization and shows schema handles; add suppression only when one recorder supplies exact evidence.

Q:360–378 says the query executes before the reuse check and also says cache hits cost evidence comparison only. Both cannot price the same path. The existing read-evidence owner should decide currency before reacquisition; otherwise say explicitly that reuse saves rendering only. Equality of a source descriptor containing arbitrary values also cannot be an unbounded cycle check (Q:288): compare admitted bounded coordinates/identities, not lazy values or huge caller data.

These do not justify rejecting Q's improvements: its revision now separates opening execution from rendering (Q:216–225), makes children handles by default, preserves history bytes, and gives continuation failures names. Those fixes should remain.

### P2 — the spec itself has accumulated a second language

The latest ruling is often clear, but older rows still teach alternatives. L1.7's status lists `subjects`/`done-when`; 5b.1's superseded text includes `attempts` despite 7.7; 3.13 says every proof is a database predicate despite 3.2's behavioral/data distinction. L1.14's “digests … equal” is ambiguous beside F:253–255's correct recomputation. L8.6 retains “never recorded as cluster faults” beside “errors … like any evaluation's”; classify agent mistakes versus core faults explicitly. R still calls 8.6/9.5 open, proposes a new 7.13 with another meaning, and treats the issue index as hand-maintained (R:862–863), which A already corrected.

Delete superseded executable advice from living rows; keep its history in Git/the dated review. Preserve row IDs for citations. Each companion should name the authoritative L row and specify only its mechanism. The face can show code, effective contract and exact handles without asking the reader to reconstruct a sequence of rulings.

## Representation and hand-maintained-list census

This census covers semantic representations and rule/dispatch lists in L and the four designs, including transitional ones. Repeated prose, example values, historical measurements and slice budgets are not additional runtime stores. **Keep** means distinct information/lifetime; **derive** means one producer with evidence; **remove/settle** means competing authority or an unspecified transition. Multiple representations are a signal to ask who owns each, not automatically a defect.

## Make `seon.id` and literal-token grep coherent

The owner rulings are compatible if **derived** means how an ID is created and **literal** means how it is subsequently represented. They are incompatible if an ID is continuously recomputed from a mutable task map, or if grep is promised to resolve every Clojure alias.

Recommended clarification of L3b.6, 2.5, 7.2 and 1.9, in place:

1. **Choose immutable defining data at creation.** An authored task uses an owning namespace and an explicitly chosen immutable creation name; a generated task uses producer identity and subject identity. These are ordered, bounded native values. Where a compound input is necessary, the identity owner receives its canonical ordered representation, not an arbitrary map/set's print order. Creation evidence retains the tuple so a same-digest/different-tuple collision can refuse rather than conflate tasks. Do not hash the ID into itself.
2. **Derive once through `seon.id`.** The task writer composes one qualified keyword from its namespace, frozen readable creation label and the derived digest. Schematic example, **not an executed hash**: `:seon.cluster.task/merge-adds-and-retracts--<digest>`. The digest uses the existing ID owner; the label is decoration within that same immutable token, not a second unique slug attribute. Identical defining tuples reconcile the same identity; a collision refuses. A later intent edit changes the declaration revision, not this token. A producer/subject identity change requires explicit reconciliation or a new task with a supersession decision; guessing equivalence is forbidden.
3. **Persist the resulting token as data.** The EDN writes `:seon.task/id :seon.cluster.task/merge-adds-and-retracts--…`; every `:seon/tasks` member and naming-test edge writes that exact token. The creation expression never occupies a task-file ID slot. Canonical metadata expands auto-resolved keyword spellings. A namespaced map for outer task keys is harmless if the ID value itself remains the full token. No hand-maintained reverse index or generated comment anchor is needed for task tokens.
4. **Keep file location separate from stable identity.** Creation namespace names the initial task file. Moving responsibility need not rename the task or move its declaration; an explicit file move carries source provenance. Do not remint IDs merely to keep an inferred directory rule true. `(task <literal-id>)` returns current data, historical creation/evidence and exact expansion calls.
5. **State the grep domain honestly.** `rg -F -- '<literal-task-id>' resources/seon/tasks src test` finds every source-backed task definition and literal annotation in those roots; use broader roots for script/external sources. Render the same token without abbreviation. Runtime-only tasks/closures have a one-call database/evaluation handle and explicit runtime provenance, **not a fictitious source hit**. If a runtime task is exported to EDN it keeps its ID. Ordinary `defn f`, namespace aliases, syntax quote and body `::k` cannot satisfy “every resolved reference is literally present.” Narrow the general 1.9 promise to literal declared handles plus indexed semantic references; retain the strict literal promise for persisted task tokens.

This keeps the readable problem name without making identity depend on the current English summary. It gives grep one exact token and the REPL the same identity. It adds no alias registry, filename parser or slug synchronizer. The cost is one digest over a small defining tuple at creation; updates compare declaration revisions and indexed edges. These are proposed semantics for root/Opus to integrate, not a new ID format installed by this audit.

The broad direction should survive the shake. The strongest parts are already small compositions: a proof is an ordinary test; a reverse task view is a join; a derived schema reference is an ordinary contract dependency; a renamed definition is additions/retractions through one program writer; a view is one acquired value rendered under explicit inputs. Preserve these instead of adding a service for each scenario.

## The five changes that most improve robustness and beauty

1. **Freeze task identity at creation; revise content separately.** Specify the immutable `seon.id` tuple, one readable literal keyword, collision refusal, and the exact source/runtime scope of grep. Fixes P0-1 and makes references durable without a slug registry.
2. **Give every current fact one writer and every edit a basis.** Route EDN and REPL task changes through the existing revision-aware task writer; consume proposed subject attachments; make proof links many-valued; retain old issue paths as historical associations. Fixes P0-2 and removes competing edge/migration authorities.
3. **Make contract meaning one dependency-aware value.** Explicit complete contract wins; otherwise Malli inputs plus the one analyzer's outputs produce the complete contract. Delete `returns`, the local tail grammar and census-based refusal; reuse schema dependency invalidation for arming/preparation/proof. Fixes P1-2 with fewer keys and rules.
4. **Separate saved observation, retrieval and new execution.** Keep exact shown bytes; continue retained represented data only with valid origin/producer evidence; realize lazy results only as new bounded evaluations. Drop speculative “already known” suppression until its evidence is exact. Fixes P1-3/P1-5 without another result store.
5. **Constrain write-back to the guarantee the existing writer can make, then prune the spec.** Use exclusive file ownership for the first slice, retain candidate proof and loud accepted-but-not-written results, and remove superseded instructions from L/R/F/D in place. Fixes P0-3 and leaves one readable language rather than a history of exceptions.
