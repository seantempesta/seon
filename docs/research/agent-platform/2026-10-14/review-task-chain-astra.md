# TASK-CHAIN independent review

REVIEWER = Astra (Codex). 2026-10-14.

**Verdict: the one-branch design is substantially simpler, but S1–S4 are not implementation-ready.** The largest gaps are the done predicate, branch discovery/recovery, and final acceptance of branch-local assignments. Fix their contracts before launching implementation; no new scheduler, product attribute, or retry mechanism is needed.

Basis: CLAUDE.md, the complete revised draft, all five named 2026-10-14 evidence files and six 2026-10-13 context maps; current source at HEAD `fdc34a9ba30083ccf01fa46e1ad58fb38e54dea1`. The draft is an existing working-tree modification. Default reports source archive `cde025f68be2c15f497891999d1f62ad6b30ee0c`, so HEAD and installed code are distinguished below. **Observed** means read directly in source or measured here; **inferred** means a consequence not exercised end to end. ## 1. The proposed done rule cannot use the current judge unchanged

**Scenario/failure (inferred):** Design adds a contracted stub before Prove writes its tests. Prove then creates an intentionally red successor proof. §2.3 selects changed/reaching tests, while §2.4 calls `seon.cluster.source/results-verdict`. That function currently refuses every non-green member except `:seon.task/product`, and every surviving changed function without a green/designed-red reaching member. Delete product without changing that contract and neither handoff works. It also refuses reds already red on target; `:seon.source/red-on-target` classifies a refusal, not permission. “Nothing green on main red here” is therefore not its current predicate.

**Proposed edit to §2.3–4 and S2:** “Execution selection and completion requirements are different sets. Run the current task's proofs, branch-defined/changed tests, and reaching tests. For advancement require a nonempty proof field with current green results and no regression of a relevant main-green test. New red tests outside this task's proofs remain visible; they do not stop an intermediate handoff. Design's contract check and Prove's red/coverage check live in their ordinary handoff deftests. Final acceptance additionally requires all branch-defined/changed and reaching tests green, complete contracts, and coverage of surviving changed functions.” Amend the existing results owner to take explicit required tests; remove its product-specific exception. Keep final contract/coverage acceptance in `seon.cluster.source/merge-verdict`, not an intermediate approximation of merging.

**Precise missing cases:** branch-added red successor test permits Prove's green handoff; Design's new contracted stub permits Design's handoff; a task's own red, missing, stale, errored or assertionless proof prevents done; an inherited relevant main-green test red on the branch prevents done. An unknown main result is **unknown**, not evidence of either prior green or prior red. State whether an unknown baseline stops advancement; recommend that root receives the unknown rather than silently certifying “no regression.” The agent's runner obtains missing evidence; root's re-judge runs no tests. Final merge's existing baseline test execution remains in `seon.cluster.source/prepare-merge!`.

## 2. Moving attempts off main also moves execution authority and every attempt reader

**Observed:** `seon.cluster.agent/plan-facts` and `seon.cluster.agent/lifecycle-facts` enumerate main's assignments. `seon.cluster.agent/write-attempt!`, `seon.cluster.agent/write-merge-base!`, `seon.cluster.agent/seed-attempt!`, `seon.cluster.agent/close!`, and `seon.cluster.agent/failed-pass!` assume that placement. More immediately, `seon.turn/attempt-running?` explicitly reads `seon.task/execution` on **main**, ignoring the branch copy. A task existing only on its chain branch cannot run through that predicate. `seon.task/assign!` also has a main-to-branch copy path.

`my.root/merge-requests` and `my.root/open-assignment` enumerate/check main. **`my.root/ended` is not an attempt query:** it filters root's inbox for end messages, whereas `seon.turn/end-task-call` explicitly emits no message. Leaving messaging unchanged does not make that tool show chain ends. `seon.context/ended` must read the corresponding branch's saved end summary before retirement.

**Proposed edit to §2.2, §2.7, S3:** “Root resolves each pointer once per pass and carries that held branch database and connection through planning, attempt creation, execution control, end reading, and advancement. An agent reads its task's execution on that same branch. The pointer is discovery, not a copied status. Root tools enumerate these same held assignments; `my.root/ended` derives ends from them, not from an assumed end message. Root's problem is the only failure fact written to main before final acceptance.” Convert the named writers/readers together; delete the chain's `seon.cluster.agent/seed-attempt!` copy and per-attempt main merge-base write. Keep root's existing global `max-running` accounting across all pointers rather than applying the full allowance independently to each chain.

**Red assertions:** task and attempt absent on main; branch task `:running`; first proof executes; an end written solely on the branch wakes root and advances exactly once; `my.root/ended` reports that end; two chains consume the shared allowance without hiding or copying either chain's attempts.

**Two-chain scope (inferred):** each fork also inherits main's unrelated tasks/assignments. Running the existing unrestricted queries on each pointed branch would count or launch those copies repeatedly. Add: “A pointer's work is only its first task's `next` closure and attempts of those tasks; inherited unrelated entities are not another chain's work.” Assert an unrelated main-running task is not launched on either chain. Scope the query at its owner, rather than filtering a wrongly built action list.

## 3. A restart currently retires the proposed chain, including a failed chain kept for root

**Observed owners:** boot calls `seon.cluster.registry/retire-unclaimed!` before branch acquisition. Its `seon.cluster.registry/cluster-claims` retains cluster branches and branches named by open **agent entities on the cluster branch**; it does not read `:dh.ref/*`. A pointer alone is not a claim. `seon.db/branch-connection` only borrows an already-open connection. `datahike.reference/resolve-reference` accepts a connection **or database value**, but returns nil when the supplied connector finds neither. `seon.cluster/recover-runs!` operates only on its supplied connection; `seon.turn/recover-call` closes open turns and interrupts unfinished evaluations, not assignments.

**Failure (inferred):** after restart, branch-local agents cannot retain their own chain through main's claim query. Even if the branch survives, the draft's connector returns nil until somebody opens it. Root cannot infer that a missing connection means an abandoned chain.

**Proposed edit to §2 and S1/S3:** “A main pointer claims its chain branch and retained base in `seon.cluster.registry/cluster-claims`, including while failed/paused. Root's boot/resume derivation reads the retained head through `seon.db/branch-database` (release that materialized value after use), or acquires its connection through the existing store/registry owner before resolving. Install the branch listener before deriving work. Recover open turns on every retained chain connection through `seon.cluster/recover-runs!`; never replay a form or restore private SCI values.” No alternate recovery service.

The spec must choose interrupted-attempt behavior. **Recommended precise rule:** an attempt interrupted during active work ends `:error`, preserves committed work and spent budget, and gives root one problem; it is not automatically relaunched. An attempt durably created but never started can be hosted under the same id. A committed end is re-judged, a committed advance starts its successor, and an accepted merge resumes publication. These distinguish recovery of facts from replay of execution. Add one table test over those durable stopping points using the existing recovery owners.

## 4. Final merge is not “the ordinary last assignment” with the proposed placement

**Observed:** `seon.merge/assignment-row` refuses an assignment missing on main; `seon.merge/assigned-task` joins main's assignment to main's task. `seon.cluster.source/tested-task-basis` records task/ancestor declarations from main and selects through the old three-value `seon.task/obligations`. The candidate program replacement does not by itself transport cluster-partition task entities into the test world. `seon.merge/merge-tx` applies the whole cluster-facts delta but gives an outcome to only its selected assignment. Earlier assignments in a multi-task branch remain undecided unless separately completed. Once copied to main, `seon.cluster.agent/lifecycle-facts` can process those old ends again, merge or retire their shared branch. The task's new `:outcome :done` is not the assignment outcome that those readers test.

The one-branch evidence's final-merge recommendation explicitly assumes the last assignment **already exists on main**, with earlier outcomes facts-synced there. That is the superseded design, not evidence for §2.6.

**Proposed edit to §2.5–6/S3:** “The final request carries the pointer-resolved source branch and terminal assignment identity into the existing merge owner; main is only the destination. `seon.merge/assignment-row`, `seon.merge/assigned-task`, and the tested task basis read the held source. Prepare judges the complete fork-to-head declaration delta and binds the terminal task to its proofs in the candidate test world. Acceptance takes the final task declaration/proof basis from that source, while comparing destination declarations through the existing writer transaction. It admits all chain tasks and their attempt facts once, closes all their decided assignments in that transaction, and records one terminal merge for publication. Intermediate done assignments never independently request merge, publication, or branch deletion.” Specify task outcomes (`:done` remains task completion) separately from assignment outcomes (`:done` intermediate, `:merged` terminal is a viable use of the proposed enum); do not let callers guess which entity owns each value.

**Required red:** three different agents/tasks on one source; no source assignment/task on target before acceptance; one final acceptance imports all three tasks plus all earlier code changes, leaves no earlier open merge request, and publishes once. Second pass is a no-op. Add concurrent disjoint-chain merges and a conflicting-declaration case: first succeeds, second reports its conflict and retains its branch. This reuses `seon.program/three-way` and `seon.cluster.source/accept-merge!`, not a lock or a new acceptance path.

## 5. Pointer creation, publication, and retirement need durable stopping points

**Observed:** `datahike.reference/reference->tx-map` emits reference fields, no Seon entity identity. Declaring attributes alone is insufficient to specify a standalone checked entity: `seon.db/write-owned-values-error` rejects identity-less unowned entities. The cross-reference evidence tested raw `datahike.api/with`, and its checked write stopped earlier at undeclared attributes. It did not prove the proposed complete checked reference entity. Choose its schema/ownership explicitly; e.g. reference maps can be components owned by root's existing agent entity, avoiding a separate pointer identity registry. Do not make `:dh.ref/value` globally unique: the library permits multiple references to the same target.

**Creation (inferred):** fork, chain transaction, main pointer are separate durable operations. Branch-first is preferable: pointer-first advertises a nonexistent task and cannot yet know its allocated eid. An unpointed branch after a crash is acceptable before any agent was launched; `seon.cluster.registry/retire-unclaimed!` can collect it at boot. A repeated create call with the same first-task identity must return the existing chain rather than overwrite its plan/proofs or create a second pointer. `seon.task/chain!` must own identity derivation, not accept wrong ids then bolt on equality checks.

**Finish (inferred):** “publish!, retract pointer, retire” loses the only discovery fact if retirement fails or the process dies between those actions. `seon.merge/publish!` can return `:seon.merge/waiting` or a publication refusal. Those are not publication success. Moreover, `seon.merge/merge-onto` records `:merge-commit`/`:merged-declarations` in its `answer` transaction **after** acceptance; the crash between those writes needs a derivable publication record.

**Proposed edit to §2.1/6–7:** “No agent starts until pointer installation is committed. A pointer stays through failure and publication waiting/refusal. Acceptance durably identifies the merge to publish in its existing transaction (or publication derives it from that transaction's provenance). After publication succeeds, root joins graphs, releases owned contexts/connections, retires the branch/base, then retracts the pointer. On restart a missing branch with recorded terminal completion permits pointer cleanup; otherwise it is unknown and shown to root. Abandon first records root's existing closed/reason decision, then uses the same retirement/cleanup path.” Make the pointer's location, owned schema, lookup/upsert identity, wake declaration, and these transitions part of S1/S3's contracts.

## 6. A set-valued next implies a graph the sequential flow does not implement

**Scenario (inferred):** `A.next = #{B C}` starts two agents on one branch; B finishes without a successor and merges/deletes it while C is working. A diamond also lets either predecessor overwrite a join's plan and start it early. Two *separate chains* are fine; this is concurrent writers within one chain. No evidence supplied measures or specifies that case.

**Smallest proposed edit to §1–2:** “The MVP is a linear chain generated from the ordered template vector; `next` is an optional single task ref. The chain constructor owns its links. Arbitrary graph authoring is outside this contract.” This avoids join counters, locks, predecessor completion rules, and a cycle check over a graph the constructor cannot generate. If branching is binding owner intent, section 2 needs an explicit join/last-writer/whole-chain completion design before implementation; it cannot be inferred from the word “each.” Derive backwards context through the existing ref index; no `prev` attribute is needed.

## 7. No automatic relaunch requires a complete terminal and explicit-restart rule

**Observed:** `seon.task/end-kind` still classifies `:stalled` and `:capped` as relaunch, `:sent-back` as merge; `seon.task/ready-rules` blocks historical non-relaunched ends. `seon.cluster.agent/assignment-actions` uses main-end absence as “undecided.” §2.7 deletes relaunch but omits stalled, stopped/cancelled, and how “set running again” supersedes a prior end. Merely writing the already-present `:running` adds no new fact. An agent whose admission closed cannot be restarted in place (`seon.turn/task-end`, `seon.turn/next-agent-work`).

**Proposed edit:** “All non-done terminal ends, including stalled/cancelled, preserve the chain until root decides. A processed failure atomically moves the task to held on its branch and retains its end/refusal; root's explicit held→running write authorizes the next numbered attempt with a new agent id on the same branch. Read readiness from that execution decision and the latest attempt, not any historical blocking end. Reopening a completed earlier task explicitly clears its completion and downstream completions before work resumes; no send-back automatically does this. Root's problem identity derives from the terminal assignment, so repeated wakes do not create another problem.” Use the existing attempt counter and writer, not a relaunch allowance under a new name. The spec should also state whether root instead abandons/recreates a chain for earlier-stage rework; that is the smaller MVP if backward rework is unnecessary.

## 10. Plan copy-forward must use the task writer's derived facts

**Observed:** `seon.task/with-references`, `seon.task/task-delta`, and `seon.task/advance-assignments-tx` derive references/revisions in the task writer; a plain checked `seon.db/transact!` is not that task writer. `my.task/refine!` still routes intent/product to `seon.task/goal-owner`, has no next-task proof operation, and writes successive targets separately. `seon.task/created-by` is how file reconciliation preserves runtime-created tasks. The new raw chain transaction omits that ownership detail.

**Failure (inferred):** changing only a successor's plan leaves its references stale; merging root's inherited snapshot of a later plan can overwrite that task's newer work if an advance is repeated. S1's flat templates also contradict the existing non-parent `:intent` requirement unless file admission changes with them.

**Proposed edit to §1/2.1/2.5:** “Use one task transaction producer for create, refine and advance; it derives identity, references, revision and runtime creation ownership from final task values. `seon.task/chain!` preserves its negative tempids through that producer. Refine writes the held task's plan/instructions; Prove sets its immediate successor's proof field through the same owner. Advance reads the finished task and successor at the writer and writes completion, exact plan replacement, newly derived references and successor execution together. Once completion exists, advance is no work; it never recopies over a successor's refinement.” Specify initial later plans (recommend absent until advance), name derivation, override precedence, and that plan copies are intentional per-task versions. Empty proof sets store as absence under Datahike cardinality-many; read that as empty, never as proven.
