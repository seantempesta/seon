Owned by [one-merge-base.md](one-merge-base.md). Replaces the grep ledger of lane `omb-r2` (`a41868d3a`, still in Git history), whose "uses the base for" column was a template and whose 92 basis-t sites were unread. Each row below is a **site** (one function, or a small group read together), with what the code does there, a verdict, and whether it combines a t or a database from different branches.

Verdicts: **convert** (must read the one merge base, or the diff, after phase 2/3), **delete** (its whole purpose is a base copy the plan deletes), **unrelated** (a t or commit id within one lineage, or another meaning: publication, eval basis, loaded program). ## Adoption record: which uses, and is it a second copy of the base?

**The meaning.** The adoption record is `:seon.source/commit-id` on the `:seon.cluster/name` entity: the **published source commit** (a commit on `:current-src`, whose lineage is publication's, not main's) whose program the cluster adopted. `seon.sci.eval/loaded-commit-id` states it: "the commit on the entity carrying `:seon.cluster/name`. Other entities may carry `:seon.source/commit-id` with another meaning." Of the 452 hit lines only these mean it:
- Writers: `registry/record-fork!` (via `fork-entity`, `ensure-cluster!`, `reset-cluster!`) at a cluster branch's creation; `cluster/development-source-refresh!` and `cluster/rehearsal-adoption!` at adoption (a plain transaction with `adoption-guard-tx`); `test/prepare-checkpoint!` on a checkpoint branch (a readiness marker, "completion is a fact, the source record written last"); `merge/adoption-record-tx` on a chain branch (the one `merge-main!` moves).
- Readers: `sci.eval/loaded-commit-id`, `loaded-source`, `loaded-program` (through the adopting cluster's live connection, never a branch's own record: "a branch's own record is its branch-point value"); `test/world-base`, `branch-changes` (read `recording`, i.e. the cluster's); `test/clean-request-handle` (`built-on`: the **candidate's own** record); `test/select`, `admit-run` (cluster db, as run evidence); `cluster/development-source-refresh!` (`prior-commit` and `task/adopt-tasks-call` use it as the base of the publication-to-main three-way); `status/cluster-row`, `render/source-generation`.
- Everything else (`source/current`, accepted/prepared `:seon.source/commit-id`, test results, `registry/branch-heads`, `acquire-context!`'s `(db/commit-id selected)`) is the published commit, a merge or branch head, or the executing value's commit.

**The answer: two different roles under one attribute.**
1. **On the cluster branch (main) it is a different fact, not a copy of the merge base.** It names a commit on another lineage (`:current-src`) and says which published program main has adopted. Adoption is a plain transaction, so the graph has no edge to derive it from, and the JVM-loaded program (compiled Vars) is its other reader. Keep it. (If adoption later wrote a merge commit with the published commit as a parent, the record would equal the merge base of main and `:current-src`; that is outside this plan.)
2. **On a chain branch it is a copy of main's record at the merge base, which the graph derives.** The branch never writes it itself; it inherits it at fork and `adoption-record-tx` re-copies main's value at each forward merge. Checked on two live chain branches (JVM read on default): for `:chain-f1f6dc8e6652` and `:chain-e439df9798c6`, the record read at the commit the base ref holds equals the record in the branch's own head (`6ad046be...` and `6acf905a...`; the second differs from main's current `6ad046be...`, so it is genuinely the base's value, not main's head). Its only branch-own reader is `test/clean-request-handle` (`built-on`). Once the merge base comes from the graph, `built-on` = the record read from the merge-base value, `adoption-record-tx` is deleted, and the datom on a chain branch is no reader's input.
Evidence is by fully qualified symbol: readers of a branch's own record: `seon.test/clean-request-handle`. Not a branch-own read: `seon.sci.eval/loaded-source` (live adopting connection), `seon.test/world-base` and `seon.test/branch-changes` (`recording`), `seon.cluster/development-source-refresh!` (cluster connection).
**Condition for Opus (P2):** point `built-on` at `merge-base` first, rerun `seon.test.clean-world-test` and `seon.merge-forward-test/a-forward-merge-moves-the-branch-onto-mains-adoption-record` (the latter asserts the deleted copy; rewrite it to assert the record at the merge base), then delete `adoption-record-tx`. One cost to measure: a `commit-as-db` of the merge base per request, versus the pull on the candidate today. `:seon.source/commit-id` also belongs to `seon.sci.eval/acquisition-attributes`, so the record's content revision enters the SCI program key; confirm the key does not depend on the chain branch's record staying current.

## Conversion order for phase 2 (callee before caller; HEAD boots after each step)

Each step ends with HEAD booting and the named tests green; nothing is deleted until its last caller moved (P4).
1. `datahike.versioning/merge-base` (P1, fork).
2. `seon.cluster.source/merge-base`: new body on the graph (two heads in, base db out). Keep the old argument list working until step 3 is done.
