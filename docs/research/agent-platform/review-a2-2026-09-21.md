## Exact replacement text

### Replace §0's “Why…” and “simpler way” paragraphs

Datahike already carries attribute revisions on committed database values. Retain only the read's dependency plan and the corresponding eligible source identity/revisions; compare against one supplied database value before refresh. This deletes history-pattern replay and result-digest replay. The remaining work is proportional to retained evidence and its named attributes. A wildcard remains conservative; the system turn evaluates selected forms once and compares their shown text. Faster selection alone does not prove a faster turn.

The final-report hook receives the writer's resolved identities, attempted assertions, effective changes and final database. Use those to select affected owning values and program referrers, then validate the final state. Identity upsert stays inside Datahike. Neither deletion nor partial-update admission requires another submission-time existence check. Work is proportional to the changed declarations and affected owners/referrers, which can be larger than the submitted transaction.

Native values can remove the codec only after the dependency's current and temporal indexes preserve their semantics. Cardinality-one and an absent AVET index are insufficient proof. Pull's default cap can be removed independently; existing query-work bounds and typed failures remain. See the blocking probes in §6.

### Replace §2(a), §6.1 and §6.2

Capture the Datahike plan and the selected source's immutable revision evidence during the read. Currency requires eligible evidence, matching source ownership/temporal identity and matching dependency revisions. Ineligible or unavailable evidence never proves current. Preserve the existing boolean consumer behavior: refresh conservatively; an error value must not be treated as true. Fix transaction-time revision advancement at Datahike's existing seam before removing the refinements.

Keep `:all` for wildcards, automatic component expansion and unconstrained attributes. Never derive a complete future dependency set from attributes present in today's EAVT result. For a request already constrained to one attribute, derive that attribute from the request, not the returned datoms. Ask B2 whether each wildcard consumer needs the whole entity; where it does, keep it. Source ownership, empty results, newly inserted attributes, schema changes, transaction-time reads, reconnects and temporal values are required cases.

Do not replace evidence with just a commit ID. `source-context-unchanged?` compares two contexts and participates in a larger cache algorithm; exporting it alone removes neither evidence capture nor source compatibility. Keep the small existing projection rather than adding a second public fork API.
