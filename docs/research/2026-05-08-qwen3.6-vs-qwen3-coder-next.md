# Qwen3.6-35B-A3B vs Qwen3-Coder-Next-80B-A3B for the agent Phase 0

## Setup

Two open-weight Qwen MoE models are realistic Phase-0 candidates on the
RTX 6000 96GB box that a sibling project runs:

- **Qwen3.6-35B-A3B-Instruct** — Apr 2026 release. Unified general post-train,
  multimodal (text+image+video), 35B total / 3B active, 256K native context,
  hybrid Gated-DeltaNet + Gated-Attention layers. The model a sibling project's vLLM is
  already serving.
- **Qwen3-Coder-Next-80B-A3B** — Feb 2026 release (arxiv 2603.00729). Coder-
  specialized post-train on top of the Qwen3-Next general MoE, 80B total / 3B
  active, hybrid attention/MoE. Trained against ~800K verifiable SWE tasks
  in 20K parallel Docker environments (the agentic-RL substrate from yesterday's
  deep-dive).

Sean's reframe: *Phase 0 generates training data; the model used for the
harness can be different from the model deployed at inference.* So the question
is **which is smartest+fastest for iteration NOW**, not which we'll ship.

## Per-axis honest read

### Knowledge / world-model
Qwen3.6 wins decisively. MMLU-Pro 85.2 vs 80.52 (+4.7), GPQA 86.0 vs 74.49
(+11.5). Coder-Next was post-trained heavily on code; the breadth penalty is
real on graduate-reasoning surface (GPQA in particular).

### Reasoning / math
Direct comparison is muddy because of AIME year mismatches, but Qwen3.6's
AIME26 (92.7) and HMMT Feb 26 (83.6) on a 2026 exam set are stronger signals
than Coder-Next's AIME25 (83.07) on a 2025 exam set. **Qwen3.6 wins**, with
the caveat that exam-year-leakage uncertainty cuts both ways.

### Tool-use (function-calling, BFCL)
Both models lack official BFCL numbers. The Qwen3-Next-Thinking precursor
scores 72.0 on BFCL-v3 — that's the **architectural proxy** for Coder-Next.
Community FP8 benchmarks put Qwen3.6 at ~78% on BFCL — unofficial but plausibly
higher than the precursor. Both are in the GLM-4.5 / top-Qwen ballpark; neither
clearly dominates the other on this axis. **Call it a tie until either Qwen
team publishes or BFCL leaderboard adds them.**

### Agentic loop (multi-turn customer-agent / information-agent)
**Qwen3.6 wins on published evidence.** TAU3-Bench 67.2, MCPMark 37.0,
MCP-Atlas 62.8 are all published. Coder-Next has zero tau-bench-family
numbers — its agentic story is told only via SWE-Bench/Terminal-Bench (code-
agent loops, not customer-agent loops). For an information-agent like the agent,
this is the most relevant axis and it strongly favors Qwen3.6.

### Coding (function-level / competitive)
**Coder-Next wins.** EvalPlus 86.56, MultiPL-E 88.23, CRUXEval 95.88, OJBench
23.01, Codeforces 2100 — Qwen3.6 doesn't publish any of these. The puzzle is
why Qwen3.6 wins LiveCodeBench v6 (80.4 vs 58.93) — likely a generation gap:
Qwen3.6 was trained on more recent LiveCodeBench-era data than Coder-Next.

### Coding (agentic — SWE-Bench / Terminal-Bench)
**Qwen3.6 wins**, which is the most surprising finding. Coder-Next is the
*coder-specialized* model and loses to the unified post-train on the headline
agentic-coding benchmarks. Likely two reasons: (1) Qwen3.6 inherits Coder-Next's
agentic-RL substrate AND adds another generation of post-training; (2) Qwen3.6's
"thinking preservation" propagates reasoning across multi-turn — a critical
agentic-loop primitive Coder-Next lacks.

### Multilingual / Arabic
Wash on published evidence. Neither publishes Arabic (ArabicMMLU/OALL/AraGen).
Both inherit the Qwen-family multilingual prior. Cultural fluency for KSA
comes from the cultural-LoRA + virtue-preamble layers, not from the base.
Phase-0 base choice is **decoupled** from the cultural-fluency question.

## Inference-cost comparison (RTX 6000 96GB)

Both fit on the RTX 6000 Blackwell single-GPU 96GB box that a sibling project runs.

| Aspect | Qwen3.6-35B-A3B | Qwen3-Coder-Next-80B-A3B |
|--------|-----------------|---------------------------|
| Total params | 35B | 80B |
| Active params/token | 3B | 3B |
| FP8 weight memory | ~35 GB | ~80 GB |
| Headroom for KV cache (96 GB box) | ~60 GB | ~16 GB |
| Native context | 256K | (not extracted; likely 256K per family default) |
| Multi-instance (one model + persona-reactor) | Yes (2x ~70 GB total) | Risky — two 80B models won't fit |
| Generation speed | Same (3B active each) | Same (3B active each) |

**Key consequence for Phase-0 architecture:** the agent's harness wants to run an
**agent + a persona-reactor** simultaneously (the persona-reactor simulates the
user, the agent observes and queries). With Qwen3.6-35B-A3B on the 96GB box,
that's ~70 GB of weights and ~25 GB of KV-cache headroom — viable. With
Qwen3-Coder-Next-80B-A3B, two instances is 160 GB, won't fit. We'd need to
either share one instance (loses the agent/persona separation) or scope down.

This is a **structural Phase-0 win for Qwen3.6** that the published-benchmarks
discussion alone wouldn't surface.

## Recommendation: **Use Qwen3.6-35B-A3B for Phase 0**

Three reasons, in order of weight:

1. **the agent's primary axis is multi-turn customer-agent / information-agent.**
   On that axis, Qwen3.6 has published numbers (TAU3-Bench 67.2, MCPMark 37.0,
   MCP-Atlas 62.8). Coder-Next has none. The Coder-Next paper's own evidence
   is for a different problem (code-agent SWE-Bench loops). Phase-0 wants
   benchmark-published prior on the *closest published proxy* to the actual
   task, and only Qwen3.6 has that.

2. **Multi-instance topology fits.** the agent's harness needs agent + persona-
   reactor running concurrently for trajectory generation. Two 35B-A3B
   instances fit on a single RTX 6000 96GB; two 80B-A3B instances don't.
   This is an iteration-speed multiplier independent of any benchmark number.

3. **a sibling project already runs Qwen3.6-35B-A3B in production.** The vLLM service is
   live; the tool-call parser config is dialed in; the deployment muscle is
   built. Phase 0 wants the lowest-friction "spin up an experiment" path. Even
   if Coder-Next were a marginal benchmark win, the operational tax of running
   a second model family during the experimentation phase would dominate.

The reframe Sean made — "we're generating training data; model choice is
decoupled from deployment" — actually strengthens this. The Phase-0 base is
chosen to **maximize iteration velocity on trajectory quality + scoring**.
The deployed the agent can be a different model later (a fine-tuned 35B-A3B for
the volume tier; a fine-tuned Coder-Next for a code-aware tier; an Opus-class
for a premium tier). Phase 0 is about building the data pipeline, not about
locking in the inference model.

### What would have to be true for Coder-Next to win instead

Be honest about where this recommendation could be wrong. Coder-Next would
win Phase 0 if any of these hold:

1. **the agent's actual Phase-0 task turns out to be code-shaped.** If the persona-
   reactor agent gets primarily evaluated on writing/reading/manipulating code
   artifacts (queries to a database, calls to a programming-style API surface),
   Coder-Next's EvalPlus 86.56 / Codeforces 2100 advantage matters. Today's
   pitch for the agent is information-agent, not code-agent — so this is unlikely
   but not impossible.

2. **The function-call envelope is the bottleneck.** Coder-Next was trained
   harder on the Hermes/`<tool_call>` envelope (per yesterday's deep-dive) and
   is more "trigger-happy" with tools. If Phase-0 trajectories show Qwen3.6
   refusing-to-call-tools or doing low-quality argument-construction, Coder-Next
   could be the better workhorse despite the worse benchmark surface for
   information-agent tasks. **Worth empirically checking** in the first week
   of Phase 0 — same prompt, same MCP tool surface, count tool-call-quality
   diffs across N trajectories.

3. **Qwen3.6's 78% community-reported BFCL doesn't replicate.** If a controlled
   measurement reveals Qwen3.6 actually scores below 70% on BFCL while Coder-
   Next inherits Qwen3-Next-Thinking's 72%, the function-calling axis flips.
   Same empirical check as #2 closes this question.

4. **80B vs 35B totally misses on raw breadth/depth in a way the benchmarks
   don't surface.** This is the "vibes test" failure mode — Qwen3.6's
   benchmarks look better but the model just feels less capable in long
   conversation. The NVIDIA developer forum hint (AzamPatti: "Sometimes
   coder-next gets stuck in a few things and 122B fixes it at once") suggests
   real-world preferences may not track the leaderboard. Worth a side-by-side
   head-to-head on N realistic the agent queries before committing.

## Confidence + caveats

**Confidence:** medium-high on the recommendation, low-medium on the BFCL
ballpark, and medium on the tau-bench ballpark. Both models are too new for
the public leaderboards to have caught up; we're inferring from precursor
sibling models more than we'd like.

**The biggest single source of uncertainty** is that neither candidate has
official BFCL or tau-bench numbers. We're triangulating off Qwen3-Next-80B-A3B
(72.0 BFCL-v3, 67.8 TAU2-Retail) as the architectural floor for Coder-Next,
and Qwen3.6-35B-A3B's *third-party* extracted TAU3-Bench 67.2 (different
benchmark version! not directly comparable) as the floor for Qwen3.6. Cleaner
empirical comparison would do the same N-trajectory side-by-side as #2/#3
above.

**The biggest single source of confidence** is that on the agentic-coding
benchmarks where both *do* publish (SWE-Bench Verified/Pro/Multilingual,
Terminal-Bench 2.0, LiveCodeBench), Qwen3.6 wins every single one despite
being less than half the size and being the "general" rather than "coder"
post-train. That's not a small or noisy edge; it's a wide consistent win.

## What this doesn't decide

- **Whether Qwen3-Coder-Next is a better deployment target for production
  the agent.** That depends on what the production the agent does, which depends on
  Phase-0 outputs. Reopen this question post-Phase-0.
- **Whether to fine-tune the Phase-0 model.** Phase-0 starts off-the-shelf;
  LoRA training on the best-trajectories is a separate decision once we have
  N≥thousands of scored trajectories.
- **Whether to use thinking mode on Qwen3.6.** The model card distinguishes
  Thinking vs Instruct sampling; the agent's harness should test both. `enable_
  thinking=True` with `preserve_thinking=True` across multi-turn is plausibly
  the strongest the agent-flavored mode given the fact-graph projection use case
  (yesterday's deep-dive flagged this as a concrete Phase-0 experiment).

## Bottom line

**Qwen3.6-35B-A3B for Phase 0.** Smartest on the agent's primary axis (multi-turn
agent / customer-agent), fastest to iterate on (the only candidate that lets
us run agent + persona-reactor concurrently on a single RTX 6000), fits the
existing sibling-project infra. Revisit only if empirical Week-1 trajectories show
Coder-Next wins on tool-call envelope quality or breadth-of-knowledge in the
information-agent loop — both are 1-day side-by-side experiments, not
multi-week investigations.
