# Forks

Every library we customize is a git submodule under `reference-code/`, pinned at a commit of our fork that carries a short list of our own commits on top of an upstream base, each marked **Generic** (an upstream candidate) or **Jolt** (specific to running on Jolt, kept on our line).

## Branch scheme

The branches each fork keeps: our working line, one fix per topic, and the generic fix cut for upstream.

- ``jolt/main`` in each fork is our working line; it may stay Jolt-specific.
- ``jolt/<topic>`` holds one fix, cut from ``jolt/main`` (or from the topic it needs) and merged into ``jolt/main`` once measured. A pin may sit on a topic branch that has not yet been merged into ``jolt/main``; its section says so.
- ``upstream/<topic>`` is a generic fix cut cleanly from upstream's own main, the only candidate for an upstream pull request, opened only when 100% sure.
- Commits in the forks carry no AI trailers.
- Submodule URLs (`.gitmodules`) are the GitHub forks, ``https://github.com/seantempesta/<lib>`` (owner, 2026-10-23); `persistent-sorted-set` and `jolt-overlay` are private, so a fresh clone needs the owner's GitHub login. A fork's branches are pushed there, never `main`, never forced. The rule comes from DECISIONS, "Libraries on Jolt". Every pinned commit is pushed to its GitHub fork on a `jolt/<topic>` branch by whoever made it, with no ask (owner, 2026-10-23), no force, never the fork's main.
- Pin bumps happen only in root's merges into main ([merging](merging.md)). `git -C <dir> log --oneline -- reference-code/<lib>` in this repository lists each bump with what it brought.

## Following upstream

How a fork relates to the library it was cut from ([decisions](decisions.md#the-forks-follow-upstream-theirs-when-almost-as-good-ours-written-to-be-offered-owner-2026-11-10)).

- **A fork is upstream's head plus what Seon needs.** Its difference from upstream is a cost paid at every merge, so it is kept small: where upstream's solution and ours do the same job and theirs is almost as good, we take theirs and drop ours; ours stays for the Jolt port, for a measured gain upstream cannot give (the number is written beside it), or for something Seon calls that upstream has no equivalent of.
- **A fork is merged often, in small steps.** A merge of upstream goes in chronological slices, each built and gated before the next; a fork that has fallen far behind and whose changes mostly overlap upstream's own redesigns is rebuilt the other way round: upstream's head, with only what Seon needs applied on top as fresh commits.
- **Fork code is written to be offered.** It follows the upstream project's own style, naming, docstrings, tests and changelog rules; one reason a commit, with its test; no unrelated edits. A pull request is opened only when the change is proven in Seon, and by the owner.
- **A pin proves whole before it lands.** A fork's own gates and a few named tests are not a prove: a pin bump runs `bin/prove` whole on its own branch, every fork unit included, and comes to the landing with that run's result ([merging](merging.md#conflicts-and-pins)). A Jolt pin also runs every Jolt gate and states each red one beside today's pin and upstream.
- **A stricter upstream compiler is a law.** What upstream refuses at compile (a malformed `ns` form, an overlapping `fn` arity, a method declared twice) is a class Seon's code may not contain; Jolt's `tools/ns_audit.clj` reads a source tree for the first without loading it.

## Own suites

A pin bump runs the forks' own tests on Jolt, so a fork commit cannot change core semantics unseen. `bin/check`'s `forks` step (`bin/forks`) runs each unit `test/forks/baseline.edn` names, a Datahike test namespace or a konserve or persistent-sorted-set test file, in one of a few Jolt processes (`test/forks/run.jolt`, on the `:dhtest` alias, with Jolt's konserve backends loaded as `seon.db` loads them and a temp directory of the process's own: the units dealt into the run's jobs, longest first by the last run's walls in `target/forks.ms`, which orders the deal and judges nothing), and is red when a unit's counts differ from the ones the baseline records. A unit its process gave no counts for runs again alone and is judged by that, and that process's log is kept with its exit status (`target/forks-died/`, its path printed: a Jolt process dying mid-suite is a defect to find, and its last lines are the evidence); a unit right alone and wrong beside others is a leak between units, red. One process a unit took 367 s for 88 units (load ~8); a few processes 153 s at four (load ~6, 2026-11-10), most of it three units (datoms-diff 86 s, background-gc 77 s, query-identity-join 59 s). Its key is `:pins` (```seon.proofs/check-steps```' `"forks" :pins`): the checkout's `:env` and every submodule's pin (the `:seon.pin` classes of `seon.fx/inputs`' `:config`), so a bump of datahike, konserve, persistent-sorted-set or jolt selects it (as does an edit to `bin/`, `test/forks/` or a config file, the `:env` inputs), and a change to Seon's `.clj` program or its message does not. Until 2026-10-29 it was keyed by `:env` alone, which the pins had left for classes of their own, so a pin bump reused the last green fork run (Jolt 80579b46 merged that way; `bin/forks` on main then ran FORKS OK). The baseline holds the units green on Jolt at the pins; a red namespace joins it once fixed, and a commit that moves a unit's counts records the new ones there. The fork audit of 2026-10-27 found the first regression this would have caught: `cc614f4e` made `query-planner-test` throw where it had joined nothing ([datahike](#datahike), `e8a2999d`).

### A fiber's state is safe by construction

An agent's eval is a fiber on the agent's one OS thread ([why](processes.md)), so Jolt must keep each fiber's state right across a pause and keep what fibers share whole. On the JVM a virtual thread's bindings travel with it and a `finally` runs once, by construction; in Jolt each was written per site, and two sites were wrong on 2026-11-11 (a binding pushed again on resume, `ec4c1e44`; a first-use race, `c0ea8fd2`). A read-only sweep then listed 13 findings over 25 sites, and finders run under Jolt's suites showed which are real (owner, 2026-11-11: "I want the classes eliminated so the guard is unnecessary"). The rules, each enforced by a gate of the fork when its pin lands:

- **A pause unwinds and a resume rewinds every wind hook but a `finally`** (``host/chez/fibers.ss``), which is how a paused fiber hands the OS thread its parameters back and releases a mutex. So state a fiber owns is never set in an entry hook: it lives in the slice the scheduler saves and restores at every pause (bindings, namespace, transaction today), made by one macro, and scoped constructs are built from four constructors that take no entry hook from their caller (fiber-scoped, exit-only cleanup, OS-thread-scoped, held mutex).
- **A table the whole process shares** is filled before a second fiber or thread exists, or is an immutable value in one box replaced by compare-and-set, or is a table type whose lock is inside its operations.
- **A fast path for one thread** is chosen by "a second fiber or thread has ever existed" (``jolt-mt?``, set where one is made), never by counting OS threads: measured before `c5e8be67`, every agent and test child reported single-threaded, and two fibers forcing one lazy sequence ran its body twice. The price is in [cost](cost.md): an unchunked lazy-seq chain 12 to 21 ticks an element once a fiber exists, a chunked one about 2% (owner, 2026-11-11: "Pay it").
- **What is kept per OS thread is not read as a fiber's own** (a ``ThreadLocal``, an eval's byte count, the error position): it moves into the slice.
- **Not eliminable, and why:** `with-redefs` changes a var for the whole process, as on the JVM; a weak table keyed by live objects cannot be an immutable value; Chez's own string-keyed tables can be interrupted mid-insert, so ours take a lock inside; and the refusal to pause while a counted lock is held stays, a loud typed error. LMDB is not a case: its envs are opened so a read transaction is not tied to its thread.

The findings, the finders' counts and the lists of constructs are working papers of the session that did the sweep; the open work is the tasks `jolt.host/a-fibers-own-state-lives-in-its-slice`, `jolt.host/a-scoped-construct-has-no-entry-hook` and `jolt.host/a-shared-table-is-frozen-swapped-or-locked-inside`.
