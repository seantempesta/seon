# The turn loop

An agent works its task in a loop inside its own process: run its proofs, end if the done rule refuses nothing, otherwise send the context to the model and evaluate its reply, then run its proofs again.

## Work, from release to judge

Root's reconciler starts an agent for a released task (a fork, or a wake of the agent parked on the task's branch) and evaluates ```seon.turn/work!``` in it, naming the task and `:seon.agent/max-turns`. The loop ends on the first of:

- the done rule refuses nothing (`:green`; all green at the start ends it with no model call);
- `my.task/fail!` asked to stop (`:failed`, the task held for root: [tasks](tasks.md#a-refused-run-is-held-for-root));
- a merge task's merge of main is too hairy (`:merge-failed`, [below](#a-merge-tasks-loop));
- the turns run out (`:cap`, [the cap](#the-cap));
- `my.turn/wait` asked to stop, or a reply made no eval call (`:waiting`);
- the model call fails (`:error`: [model](model.md#failures)).

## The end

An agent's end is a fact on its branch, and root reads it once to decide how its task stands.

The loop writes it (`seon.turn/end!`, through ```seon.agent/write-end!```): `:seon.agent/outcome` (`:green` `:red` `:waiting` `:cap` `:failed` `:merge-failed` `:error`), the reason, the error that ended it as data, the turns' `:waste`, and `:seon.agent/ended-turn`, the turn it came on. The process's death writes it the same way. The live runtime is staged onto the branch (`seon.stage/stage!`) so the next agent on it holds it. Each wake begins by clearing the end before it (```seon.agent/clear-end!```). Root's judge reads the end with ```seon.reconcile/pull-end```, asks the agent for its test results, reads the branch and its diff, and stores its decision on the task from those measured facts (`seon.reconcile/judge-tx`; a merge task is green only when merging main again brings nothing new): [reconcile](reconcile.md#a-task-holds-how-its-work-ended). An agent that wrote none (it died, was killed, or never reached its end) is a task `:dead`; an outside agent's `:done` writes its end through `seon.turn/hand-back!`.

## The cap

The cap is the agent's own: `:seon.agent/turn` (and the turns that threw) against `:seon.agent/max-turns`, never restarting across wakes.

A wake raises the budget. The write that starts a woken agent adds `:seon.config.agent/wake-turns` to `:seon.agent/max-turns` (``seon.task/start-tx``), whoever sent the message that woke it, so an agent whose turns are spent runs again when it is messaged, that many turns more (`seon.agent-test/a-capped-agent-that-is-messaged-runs-its-allowance`, `seon.reconcile-test/a-wake-raises-max-turns-by-its-allowance`). It is the main control of the agentic loop: an agent nobody messages is never woken, and one that is woken has an allowance. An agent whose last turn waits when its turns are spent ends `:cap`, never `:waiting` (`seon.agent-test/a-task-at-its-cap-is-recorded-cap-never-waiting`), and its task stands `:cap`; a person may still raise `:seon.agent/max-turns` and release the task (`my.root/run!`), and the same agent continues from its branch. A reply with no evals (`evals` empty or missing, or plain text) stops the agent early, with turns left (`seon.agent-test/a-reply-with-no-evals-stops-with-turns-left`). The page reads the cap as its turn line (`seon.render.ui/turn`).

## Observe

Each turn starts from facts measured now, never remembered: `seon.turn/observe` asks the test service (`seon.agent/prove!`, `seon.prove`: one test run per branch and program digest whoever asks, in a fork of the agent) to run the task's accumulated proofs and the tests the branch changed, each test bounded by `:seon.config.agent/test-ticks`. The results are facts on the branch (```seon.agent/record-results!```: each test's verdict at its reach digest now, its failing assertions as data, a process test left to root's gate as `:deferred`), and a test run that cannot be made is one too (`:seon.agent/test-error`, every proof then `:not-run`). Nothing else is observed or held: how the work stands (the proofs, the done rule's reasons over them, the contract gaps, what the work caused, the unmerged entries, whether it can merge) is ```seon.ctx.status/status``` of those facts, which the agent's walk draws once and the loop's done check reads from it (`seon.turn`'s `status-now`: [render](render.md#how-the-work-stands)), the same value the page and the model read.

## Act

`seon.turn/act!` records what the context is built from (its basis: the commit it reads, the task and the turn's number: everything the request shows is a fact of that commit, what the turn took among them) rather than the context's text, places the page before its call when it moved (a call Seon makes, generated from the two bases and never stored: [the render is an eval](render.md#the-render-is-an-eval)), builds the request from the agent's records ([render](render.md#the-models-context-a-cached-prefix-then-the-turn): the system prompt and the records in order, the page among them), and asks root's `:model` owner for a completion. Each of the reply's evals (an `intent` and one or more forms: [prompt](prompt.md)) goes through the one REPL path (`seon.repl/eval-string`: read, evaluate, record), and its answer is that eval's result, which the next model call reads. The turn's facts (reply, reasoning, finish reason; each call's evaluations are evals of the turn, below), its tokens and the prefix-cache counts ([model](model.md#usage-is-recorded-never-assumed)) go on the branch, on the turn's model call (`:seon.model-call/*`, its own entity pointing at its agent) beside the basis and the hash of the bytes it sent (`:seon.model-call/sent-hash`; the request itself is made again from its records, [the debug page](render.md#the-debug-page-is-the-wire-request)).

## The turn is a number

A turn is a number, not an entity (owner, 2026-11-04: "wtf is a turn but a number? An agent has turns and evals why are we organizing them on top of other entities"). `:seon.agent/turn` is the agent's: agent-wide, never restarting across wakes (the cap reads it: [above](#the-cap)). It moves when a model turn starts, in `seon.turn/act!`, in the same transaction as the turn's model call's first facts; the model call is `<agent key>/<n>`, with `:seon.model-call/agent`, `n` and `origin`, and later its reply, reasoning, finish, truncation and error (a failed call's typed error is on it). A context read an outside agent makes (`seon.turn/context-block`) moves no number: its model call is `<agent key>/read-<k>`, `k` the agent's own count of reads, counted from the branch.

Each record names the model call of the turn in force when it is written (```seon.task/call-ref```, which makes that call when no request has been made for its turn): `:seon.eval/call` on every eval of the agent (the agent's code's and an outside `seon_eval`'s included; the loop's own eval and a context read, which are no conversation record, name none). A message names no call: it is delivered by being on the branch ([users](users.md#messages)), and the turn that read it is derived (`seon.ctx/turn-members`): the first turn whose basis `:t` is at or after the transaction that delivered it. A model turn's messages (`seon.turn/deliver!`) come before its basis, so it reads them; the loop's own (`seon.turn/tell-error!`, the repeated-turn note) and one the agent's code takes in the middle of a turn (`seon.agent/messages`) come after it, so the next turn reads them. Before its first turn the number is 0, and its records name the call `<agent key>/0`. So agent -> call -> its records is one pull ([the pattern](ctx.md#the-pattern)); the call a record names has an `origin` only once a request was made for its turn, which is what `seon.turn/agent-usage` counts.

So the conversation is its turns in the order of their numbers (```seon.ctx/turns```), through one past the turn in force, since what is delivered comes before the turn that reads it begins; a turn nothing has come of is no element. Each is a component (`seon.render.ui/conversation-turn`) reading its records through what its model call holds in ctx (```seon.ctx/turn-evals```) and the messages the list gives it (```seon.ctx/placed-messages```, which `seon.ctx/turn-members` answers for one turn): its messages as they were delivered (those whose delivery falls after the basis of the turn before and at or before its own; one delivered after a turn's basis, mid-turn, reads at the next turn's start, shown before its call exists as the turn now opening), its reply holding the evals it ran as they ran, then the evals of other hands (```seon.ctx/turn-evals``` holds that order, so a reply's tool results stand right after its tool calls, as a provider requires). The page's chat and the model's history read this one order (`seon.ctx.wire-test/the-chat-and-the-request-walk-one-sequence`). It rests on when each record reached the branch, never on its entity id: a message's id is a content id (`:seon.message/id`), the same on every branch, so one brought down by a merge of main keeps main's id and still reads at the turn after it arrived (`seon.ctx.wire-test/a-message-delivered-mid-turn-reads-after-that-turns-evals-on-a-branch-that-merged-main`). An outside agent's session is one turn, so each of its evals runs that one component again: it reads its member set and no member's id (written once, ```seon.ratom/untracked```), a lookup for each earlier member, so the calls stay flat and its bytes grow by what the list of markers costs. A request for turn *n* is made on the db at its commit, which holds the records of earlier turns and the messages delivered in *n*; its evals and its reply come of it. A reply's text and reasoning are its model call's, and its evals name it, so unlinking an eval from `@ctx` never moves another to a different reply.

## An eval can be run again

A person's step button runs an eval again in its own place (```seon.repl/again```, optionally as edited code): the same record by its `:seon.eval/id`, its call and author kept, its code and response replaced, its old ones in the db's history. So the next request reads the new one where the old one stood (the provider's cache breaks from that message on, once), and its handle names the new answer, while the old handle still reads the old one. ```seon.repl/again-to``` runs the conversation's evals down to one (those naming a call, Seon's left out), in order, stopping at the first that fails, as a person evaluates a file down to a line. Their code runs for real, so an outside effect happens again; the call is made through root's `again!` with origin `:context`, so the button's own call is no record of the conversation.

## An agent goes back to an eval

A person's Back to here takes an agent's session to just after an eval (```seon.root/back!```): a new branch from the commit holding that eval's last write, made through the writer's `:clone-branch`, then this process ended and one spawned on the new branch under the same key, so the same page goes on from that point and the old branch stays as it was. Only what is on the branch comes back: an atom and a definition in `agent.*` lived in the process, so To here runs the steps again to rebuild them. A task the agent was working moves to the new branch, parked on the new process ([parked](#parked)): a person can run its steps again or edit them, and a message wakes it. It is refused, with nothing ended, when the agent isn't idle (before or when the branch is made), when it is already going back, or when no agent could be started (no fork server, too many), and an eval with no commit of its own (a sweep took it, or a later eval shares it) is refused rather than another point taken in its place. It reads the branch's commits back from its head to the eval, in root's api step, a person's rare act.

## An eval can be inserted

An agent is a record, one REPL and one queue of evals run serially, and the model is one source of evals. Another is whoever creates the agent: `seon.root/spawn!` takes `:evals`, pairs of intent and code (`(spawn! sys {:task t :evals [["Read the pattern." "(:seon.ctx/pattern @ctx)"]]})`). Root sends them at the agent's hello as one write, which its REPL runs before any request the spawn's answer makes (`seon.repl/insert!`, over `seon.repl/run-calls`, which a reply's calls run through too): each is an ordinary eval, recorded as any is (`:seon.eval/by` is who asked, "root"; the turn in force, which is 0 before the first model turn; no call id, since no model made one), and every one runs, whatever the one before it did, as a reply's calls do (docs/decisions.md#every-eval-of-a-reply-runs-owner-2026-11-08). Nothing is stored for them beyond an eval's own attributes, and no reader asks who ran one.

What differs from a call the model made is only where the model's reply is: an eval has none to name. The page draws it as its own entry of the conversation (a model's eval is a step under its reply). The request makes its call from its own id, intent and code (```seon.ctx.wire/eval-msgs```: any eval with an intent and no call id; its call id is `eval-<id>`, as every eval's is): the assistant message that made it and the tool message that answered, standing alone, so a reply's own message is never edited. An eval with no intent (an outside agent's, the page's) is one user message, as it was. The agent's own loop eval and a context read name no model call, so no reader of the conversation reaches them.

Unlinking one from `@ctx` is as unlinking any: the next request is made from the records that remain, and the records before it are the same bytes. The page is no record at all: a call generated before each model call from its basis and the one before (```seon.ctx.wire/page-diff-msgs```), so nothing of it is stored or unlinked.

## Who runs which tests

Tests run three times in a task's work, each on what it needs:
- **each turn**, in the agent: the task's proofs and the tests the branch changed, in a fork, each test under `:seon.config.agent/test-ticks` (one bound everywhere, per test: a test past it is red, `:seon.test/ticks-spent`, the same in the judge);
- **the gate**, in the turn: a clear status runs the judge's selection, then the process tests it left on the merge gate's checkout (```seon.agent/judge!```, [merging](merging.md#a-merge-runs-what-the-change-reaches)), so a red comes back as a reason with a turn left.
- **the judge**, in root: when the loop ends, root asks the agent's REPL for its test results (`:tests`, the plan's in-process tests under the same per-test bound; each green the turn left at its digest is reused, so the judge runs only what the turn did not, and forks nothing when that is none) and judges the end from them, the writer's diff of the branch and the branch's end (`seon.reconcile/judge-tx`); a process test that is none of the task's proofs never runs in a turn or the judge, and is read as deferred ([merging](merging.md#a-merge-runs-what-the-change-reaches));
- **the merge**: the writer's merge gate takes the branch only when its contract gaps are none, the same `seon.merge/uncontracted` answer, and the process tests the change reaches run before it merges, on the root's gate checkout, nobody asking (a root with none holds it) ([merging](merging.md#a-merge-runs-what-the-change-reaches)).

## A merge task's loop

Every work's agent first merges main into its branch with no model call (a kept branch made before main moved holds main's program, its tests and their digests included; one at main's head brings nothing). A merge task's agent merges main again each time all is green, until a merge brings nothing new; it stops early when the merge is too hairy (`seon.reconcile/hairy`, over the task's facts: the conflicts, the turns, and the names the task's proofs and plan's cites hold, never the plan re-parsed). Its unmerged entries are in its context, and it resolves them at the REPL ([agent](agent.md#merging)).

## What a turn merges from main

Messages to the agent and what root decided of its task are on main, and a turn delivers them onto its branch before it observes, so its context and page read them from the branch like any other fact: `seon.turn/deliver!`, the one way outside facts reach the branch. Root writes nothing to a live process for them, so a session whose process is gone (parked in an earlier boot, a lost wake) takes them when it is spawned again.
- **Messages** (```seon.agent/undelivered```, ```seon.task/undelivered```): the `:seon.message/*` entities main holds to the agent (its ref in `:seon.message/to`, one seek of its entity), whose entity its branch does not hold: a person's (`seon.root/message!`, to any agent main knows, live or not), another agent's, and root's, a stage boundary or a `:verdict` (below), which are messages from `"root"`. Each is written on the branch with the same id, in main's order, with this agent's ref only; the agent removes one with `(swap! ctx update :messages dissoc e)`, and it is not delivered again ([messages](users.md#messages)).
- **Opened evals** (```seon.agent/untaken-facts```): each eval of its own the page opened (main's `:seon.agent/opened`, written by `seon.root/opened!`), copied onto the branch as `:seon.eval/opened`. What wakes a parked agent is a send, over a Flow channel to the reconciler ([messages](users.md#messages)), not a count.

An end the done rule refuses (`:green` or `:red` by the agent's own word, but not done by root's facts) is told why rather than held: root's judge writes a `:verdict` message from root with the reasons and results it judged on and stands the task `:told`, and the reconciler wakes the session for it ([processes](processes.md#a-parked-process)). The same reasons again hold the task, except a verdict that is only `:behind`, which only a task no merge task follows gets: main moved under the branch, which is no news of the agent's (the same count twice is two different mains), so it is told again until `:seon.config.merge/max-behind` judgments were `:behind` (`seon.reconcile/judgment`). A task a merge task follows is never judged behind at all: the merge task merges main into the branch and the gate tests what it writes, so its green work is done and its merge starts (bin/check swarm held green tasks after three behind verdicts under a busy main, 2026-10-31: `seon.reconcile-test/a-green-work-task-judged-behind-is-done-and-its-merge-runs`). Green work merges main before it ends, a work task's as a merge's, until the merge brings nothing new (`seon.turn/work!`), so it ends on main as main is. A merge task's refused end holds at once, and so does an outside agent's, which read the verdict as `seon_done`'s answer.

## Effects from an agent

An agent reaches outside only through root's owner procs ([fx](root.md)): ```seon.agent/fx!``` asks an effect kind and waits for its outcome (`{:value ...}` or its declared error), recorded with the eval that asked; ```seon.agent/fx-send!``` starts it and answers its key at once, and the outcome arrives later as a message `{:from :fx :k :kind :body}` in the inbox. Inside a test fork nothing leaves the process: the test binds ```seon.agent/*fx-stub*``` to a function of kind and request that answers the outcome, and with none bound the effect is the typed `:seon.fx/in-test` error.

## The tests in a fork of the agent

The tests a turn or the judge runs execute in a fork of the agent, within the per-test tick bound ([above](#who-runs-which-tests)), so the plan is selected in the parent and run in the child. What the selection reads: ```seon.agent/test-inputs``` (the reach inputs of the tests: root's binary's when it was built from its source, else blank), ```seon.agent/branch-graph``` (the branch's reach graph, the base's updated to the branch's db and held while that db is the newest asked: a second ask is a key lookup) and ```seon.agent/judges?``` (a `deftest` of a namespace that is not scratch). The plan, the fork and the test service are in [merging](merging.md#the-test-service). Each test is written as it starts on a pipe to the parent, so a death names the test that was running. The parent reads the pipe with ```seon.agent/read-to-exit``` (to the pipe's end of file or the child's exit, whichever comes first, because a process the child forked may hold the write end) and answers with ```seon.agent/test-run-answer``` (the last line when it is the result; else the child died while running the test last started, and the answer is one error report on it; a pipe still held is an error report of its own). ```seon.agent/test-report``` keeps one `clojure.test` report: type, test var, message, the failing assertion's expected and actual by the one printer, and a cost proof's measurements and verdict.

## Parked

A session is the agent's branch across its tasks, and an agent that ends waiting or at its cap parks its process on the task (`:parked`, `:cap`) until the next message to the agent wakes it, with its allowance of turns ([the cap](#the-cap)): the same agent, no fork ([processes](processes.md#a-parked-process)); a parked agent costs its memory and nothing else, and it stays in memory by choice (docs/decisions.md#a-parked-agent-stays-in-memory-and-replay-is-deliberate). A reply with text and no calls parks it whatever its proofs say, with no further turn (docs/decisions.md#a-reply-with-no-calls-pauses-the-agent-whatever-its-proofs-say); a blank or cut reply says nothing, so the next turn reads the same state. A message is an entity on main first and a turn delivers it onto the branch (above), so a wake that was lost, or a process that died, loses no word: the task is `:lost` and the next start a spawn of the same agent.

Starting and resuming are meant to be one mechanism (owner, 2026-10-25), loading the session at a commit: a new task loads its branch's head, a dead process loads the same head, and a rewind (`d/branch!` at the commit, a pointer) loads the earlier one. A load forks, loads the program diff from main's image to the commit (about 0.35 s, most of its cost), binds ``result/a3f9c1d2`` to each recorded data value, and replays only the pure evals of the record, each marked as replayed; an eval that asked an effect is listed and never replayed unless the agent evaluates it again by hand ([processes](processes.md#a-parked-process): a replay trusts no form whose effect hides behind a helper or whose world moved on). This is planned, not built, and any replay is to be deliberate rather than automatic (task `seon.reconcile/root-work-is-tasks`; the design and its lab measurements are in `docs/turn.md`).

## An outside agent

A Claude session works a task through the same path: `seon_attach` and `seon_done` on the server. ```seon.turn/context-block``` gives it the request a model would be sent: the system prompt and the records of its conversation with the page among them as the evals Seon ran ([render](render.md#the-render-is-an-eval)), as one text, or with `wire` as the JSON body a provider is sent (`seon.ctx.wire/wire-turn`). A read by the agent's own outside model takes its messages and has Seon show the page, as before a model's turn; an observer's leaves both, and its request ends with the page whole. The outside model's read is recorded as a model call of the agent with origin `:outside`, holding its basis and the hash of what it sent; a read moves no turn. An observer's read writes nothing (owner, 2026-11-10: "A read never writes"): no commit, no model call, and no record of the eval the server ran it by (`seon.server-test/a-context-read-that-only-looks-writes-nothing`). Its `seon_eval` is one reply, a turn (```seon.turn/outside-reply!```): opened as a model's turn is (`seon.turn/open-turn!`: what it takes, the page shown if it moved, the number, its basis), its evals through ```seon.repl/run-calls```, its message on its model call (`:seon.model-call/model` "outside"), so an outside agent's conversation reads as a model's, turn by turn, and no turn grows. Its answer is what a model's next request would add: its results and any page eval Seon ran, before them and after them, so a change reaches it with the reply that made it and it never re-reads the conversation to see one. A read runs no proof and waits on none: its verdicts are the status's, and an agent whose one REPL is in an eval that hasn't ended (a test blocked on nothing) is read by root from its branch, saying so. An interrupt ending a prove takes its test child with it, so nothing is left running, and that run answers as a death, no verdict.
