# Config

Every limit, bound and default of the platform is one key in one aero file, documented beside its value, validated by its schema, and read through one resolver.

## The file

`resources/seon/config/default.edn` holds every key with its unit, its provenance (a ruling or a measurement) and what happens at its bound, in v1's shape. Its schemas are ``resources/seon/schemas/seon.config*.edn``; `:seon.config/config` is the whole config, a closed map, so an unknown key, an invalid value or a missing required key refuses boot with `:seon.config/refused`, naming each key. ```seon.config/config``` is the map this process loaded with, validated, built by ```seon.config/resolved``` (a key whose value is nil is dropped as absent, then the map is validated) and checked against ```seon.config/keys-declared```. A key may differ by the process's profile (`--profile NAME` on its command line, default `:default`, handed to aero's `#profile`: `:seon.config.store/sole-writer?` is false under `:scripted`; ```seon.config/profile``` reads it). The profile is recorded as `:seon.config.root/profile`, so main's root entity says which profile a root runs under; the key is not in `default.edn` because the file is read under the profile, so the loader supplies it as its own layer. **The first `bin/update` after the `--profile` change merges must be `nice -n 15 bin/update --profile deepseek`**: the running root's old binary builds its resume arguments without `--profile`, so the restart would come up with no model provider. Machine-dependent values are derived at load: `#seon/checkout "p"` is `p` under the checkout (`SEON_CHECKOUT`, else `JOLT_PWD`). `#seon/own-branch "b"` is `b` in the main tree and `b-<worktree>` in a git worktree (its `.git` a file): worktrees share refs, so each commits its merges on a branch of its own (`:seon.config.source/branch`). No key decides by time ([clocks](clocks.md)): the stall bounds (`:seon.config.agent/stall-ms`, `:seon.config.proofs/stall-factor`) only say when a stall is recorded, and the stop bound is a guard in its owner, not a key.

## Layers

Later layers win, key by key, and the merged map is validated once (```seon.config/load-layers``` reads them, ```seon.config/layered``` merges them):

1. the shipped file, as this binary was built (```seon.config/built-text```) and then as this process's branch states it ([below](#a-process-holds-its-branchs-config)), read under the command line's `--profile NAME` (default `:default`); the profile's own record, `:seon.config.root/profile`, is the next entry of ```seon.config/sources``` ("--profile NAME", or "no --profile");
2. the checkout's own `config/local.edn` (gitignored), a layer only where a command line names it with `--config`: `bin/root` passes it to the standing root (a test's root, started with a starter, takes none) and `bin/ports` to `seon ports`, so a check's or a test's process reads only the config it is given (a check's root in the main tree once read the standing root's source tree from it). `bin/ports` writes it with the checkout's ports from the main tree's `config/worktree-ports` (gitignored; main 7888/7777, worktree k 7900+10k/7901+10k; `bin/worktree --remove` frees the block); `bin/ports` owns the port keys and writes them on
   every run under their current names, keeping the ports and every other entry, and
   `bin/build`, `bin/test` and `bin/check` run `bin/ports --write` first;
3. the command line: `--profile NAME` (above), `--config FILE` and `--set :ns/key=edn` (```seon.config/overrides```), read from `*command-line-args*` while namespaces load (Jolt's jolt/argv binds it in a built binary), taken out of the mode's own args. No environment variable selects a profile: `bin/test`, `bin/check` and a test's root (`seon.test-store/start-root!`) pass `--profile scripted`; `bin/root start --profile deepseek` (and `bin/update --profile deepseek`, which hands its arguments to the restarted root) runs agents on DeepSeek; `my.root/resume-args` carries the profile to `bin/root next`.

```seon.config/sources``` names the layer of every key (the `:seon.config/sources` fact on main). `#env` appears only where a script sets one (leaving the file: task `seon.config/per-run-keys-ride-the-command-line`). No port is listened on unless the config says so: `:seon.config.web/port` and `:seon.config.root/server-port` ship 0.

**A value one run needs goes on that run's command line, never in the environment**: the standing root's `config/local.edn` is a later layer than the shipped file's `#env` defaults, so a port handed to a client through `SEON_SERVER_PORT` is overridden by a stale local file, and the client config keys a port nothing listens on. `--set :seon.config.root/server-port=N` is the top layer and always wins. Not this: a new `#env` read for a per-run value.

## A process holds its branch's config

Which layer a key came from is not part of what a process reads (```seon.config/in-force```): it differs by process while a digest takes no place, so a reader of it could be green in one process and red in another at one digest. Root's boot writes it on main (```seon.config/boot-sources```, `:seon.config/sources`), and readers read it there.

A running process reads config from its own branch's db, never from the file: an agent keeps the whole disk, and a file it writes acts on nothing until an import (owner, 2026-11-07). The class this ends: one agent's unmerged `spit` of a key with no schema into the file turned a second agent's live test red and stopped a new process, and no merge or digest saw it.

- **At load** a process has no db, so ```seon.config/built-text``` is the file's text, baked when `seon.config` compiles, as the schema forms are; a file on disk can't stop a process starting. It is read under this process's profile, `#env` and checkout, under its `--config` and `--set` layers (```seon.config/config```). `config/local.edn` and the command line stay layers of the checkout and the process, over whatever base.
- **At start**, once it stands on a branch, it holds what that branch's entries state (```seon.program/hold-config!```, ```seon.config/hold!```): root right after it loads main's program (```seon.root/boot!```'s), before the fork server forks, so the fork server and every agent inherit it; a resumed agent from its branch (```seon.program/load-diff!```). The entries (`:config/key`, `:config/form`, each form the value's exact text with its tags unread, [source](source.md#a-program-file)) are written out as one map and read as aero reads the file, so `#env`, `#or`, `#ref` and `#seon/checkout` resolve for this process (```seon.config/of-entries```). A db with no entries (a store before them, a test's world) changes nothing.
- **Every read** takes that map: ```seon.config/resolve``` and ```seon.config/value``` read it, one deref over what they did (498 ticks against 485, 1,760 bytes both, 3 calls both, measured 2026-11-07), and ```seon.config/resolve-in``` is unchanged. Nothing pulls per read.
- **It moves** only when a transaction of its own branch names an entry: a merge loading in place (```seon.program/load-changes!```, in root's writer, the fork server and an agent merging main) or the agent's own write (`seon.agent/transact!`). Holding again costs 4.4 M ticks and 13.7 MB, reading the entries and every schema entry; nothing is held again otherwise.
- **The source is the process's own branch**, never whatever db is around: a test's ``(my.test/world)`` holding entries changes nothing a key reads.
- **A place stays where it loaded.** A key whose schema says `:seon.config/place` is read before any db or says where this process runs, so an entry for it waits for a rebuild. Of that set the store is located by `:seon.config.root/runs-dir`, `store-path`, `main` and `:seon.config.store/sole-writer?`, and the import by `:seon.config.source/root`, `dirs` and `branch`; the rest are each checkout's or root's own by the digest's rule (```seon.fx/config-input```), and no key outside it was needed before a db.
- **A branch's schema counts.** A key a branch adds is validated against the config map as that branch's schema entries state it (```seon.config/of-entries```'s `changes`), so ``(my.schema/register! k form)``, the map's entry for it, then an edit of the file's text reads at that branch's REPL and no other's. The map's entry is `{:optional true}` while the binary is behind: what it loaded with has no such key, and a required one refuses it (each test on a config it built from that value says so). A write of entries the schema refuses is refused before it lands (```seon.program/config-refused```), naming the key.

Reading the file as the program holds it: ```seon.config/shipped-text```. What a branch's value does to test digests: ```seon.agent/branch-inputs``` overlays the held map on the boot's inputs, key by key ([merging](merging.md#verdicts-are-a-cache)).

### What waits for a rebuild

A top-level `def` reads config once, at load, and a root's start reads its `:bind/*` buffers and limits once, so a value a branch states doesn't reach them. Each such key says so on its schema entry, `:seon.config/at-load true`, which `seon.main-test/a-key-read-at-load-says-so` holds of src's `def`s. ```seon.config/waiting``` answers each key, place or at-load, whose stated value differs from what this process loaded with, `{k {:running :stated}}`; an edit that leaves any says so, and the dashboard's config panel names them. A key read at a root's start takes main's value at that start, so it stays listed until a rebuild though a restart has already taken it: it overstates, and never hides.

## The resolver

```seon.config/resolve``` is the one way code reads a setting: `(seon.config/resolve k ctx)`, with ctx `{:task m :model id}`, looks in the task's or agent's own settings (`:seon.task/config`), the model's entry (default `:seon.config.ai/model`), that model's provider's, then the config's own key (```seon.config/resolve-in```). It answers `{:value v :source s}`, where `s` is `[:task]`, `[:model id]`, `[:provider id]` or `[:config layer]`; a key set nowhere refuses with an error that names the key, the task, the model and its provider and points to `seon.config/keys-declared`. ```seon.config/value``` is its value, the read every caller makes. The task's settings include the model that answers its turns, `:seon.config.ai/provider` and `:seon.config.ai/script` (```seon.config/provider-at``` reads them each turn), so a test's scripted reply rides its task and not the root's arguments ([merging](merging.md#a-merge-runs-what-the-change-reaches): the shard's agent tests share one root). Ask it at the [server](server.md#ops): `(seon.config/resolve :seon.config.ai/max-in-flight {:model "deepseek-v4-pro"})`.

## The model manifest

`:seon.config.ai/providers` and `:seon.config.ai/models` are v1's manifest entries, for the models we use; each field is documented beside its value in the file. A provider carries its base URL, the name of its key's environment variable (never the key) and its wire key; a model its provider, version, context window, max output, prices and the provider's concurrency ceiling. Either can state a setting by its `:seon.config.*` key to override the top-level one for itself. ```seon.config/provider``` builds a model's provider and ```seon.config/with-provider``` attaches it. Which provider runs: [model](model.md).

## Facts on main

At boot root writes the config in force on main as an entity of its own, named by the content id of its map (`:seon.config/id`, ```seon.task/config-tx```: the same config is one entity on every branch), and gives root's entity one ref to it (`:seon.root/config`) and the layer each key came from; root's entity holds root's own attributes, so by its attributes it is root and not the config (`seon.config-test/the-config-in-force-is-its-own-entity`). An entity per provider and per model is written beside it. When a commit of main touches an entry, root's writer writes the config as this process now holds it (```seon.config/moved```): a new entity when its content moved, which root's ref then names, so the turn's ```seon.config/provider-at``` reads what merged. These are platform records, which a merge never carries. ```seon.config/from-db``` reads the config back on main or on any branch made from it (every declared key the entity root's `:seon.root/config` names holds, a set-valued key read back as the set it was), so an agent, the dashboard and the context read it there; the dashboard shows it through the schema's declared render, `seon.render.ui/config-panel` ([dashboard](dashboard.md)). `bin/check config` proves that an agent reads it from its branch.

## A bound fails loudly

A limit is removed, or derived from measurements with its provenance, and reaching it is a typed error or a problem that names the key: never a silent cut, drop or clamp (owner, 2026-10-30: "Please don't put any artificially low limits that will bite us in our asses and especially if they won't loudly crash"; "The limits should always fail loudly btw. That budget is useful to catch problems IF we use it right."). Each key's comment in `resources/seon/config/default.edn` gives its unit, its provenance (the commit whose message holds the numbers) and what happens at the bound. Before adding a bound, measure the population it bounds and ask what happens at the bound and who sees it: a fixed 1 GiB byte budget for an eval, set from one agent's 17 evals, stopped root's whole-program loads, a prove and a heap test before it was removed. A budget is right when work stays under it nine times in ten and an overrun is worth looking at. Nothing cuts an agent's own context or evals ([decisions](decisions.md#no-artificial-limits-or-cuts-on-an-agents-context-or-evals-owner-2026-10-29)).

## Constants

Every limit, bound or default is a config key. A number left in src is one of the kinds below, each named here with its reason, and `seon.main-test/a-bound-is-a-config-key` is red on any other. It reads src's forms from the compiler's facts and flags every top-level `def` of a number and every literal count over 2 given to `take`, `take-last`, `drop` or `drop-last`. Not covered, so a review reads for them: a number in `subs`, `repeat`, `partition`, `nth`, a `let`, a comparison or a `def` wrapped in a call. A foreign interface's constant, named in upper case as its C header names it (a socket flag such as `seon.sock/AF-UNIX`, LMDB's `seon.db/MDB_NOSYNC`), is the interface's value, not a bound, and is not listed; the case is trusted, so a bound written in upper case escapes the law, and review reads for it.

- `seon.cost/tick-allowance`, `seon.cost/steeper-by`, `seon.cost/ratchet`, `seon.cost/growth-share`, `seon.cost/increment-floor`: the cost judge's own definitions of a proof's tolerance, which task `seon.cost/cost-tolerances-are-derived` derives from measurement instead ([cost](cost.md)).
- `seon.cost/min-points`: three, the fewest sizes a cost proof measures, because a growth is judged on a curve and two points always make a line. A definition of a growth judgement, not a tolerance; a proof the cap leaves fewer is refused ([cost](cost.md)).
- `seon.program/place-gap`: the space a file's forms are placed apart, a unit of the sort key, not a bound: no size depends on it, and a gap with no room places the file anew.
- `seon.cron/day-ms`: a day's length in milliseconds, a unit of the calendar the cron proc reads a time of day against, not a bound.
- `seon.server/verdict-line`: the ten reds `seon_done`'s line names with their first failure; it counts the rest, and the form under its `:handle` reads them all
- `seon.fx/runner-end`: the six lines of the runner's output that an error names beside its log path, when the runner made no plan: its error, where, and the verdict lines after them (three cut the error); the log holds the rest, and the error says where.
