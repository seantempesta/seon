# Health

Health is the set of open problems: a value computed when something reads it (`seon.problems/health`). It is never stored, never precomputed and never polled. Root's page, an agent's context and the done rule each read it on the db they hold. It is the recorded classes (`seon.problems/report`) beside the derived ones (`:dead-citation`, `:unnamed-site`, `:stale-pin`, `:stale-section`, `:orphan-page`, `:leadless-section`, `:uncited-task`, `:problem-unlinked`), one value by class (`:seon.problems/report`).

## Two kinds of problem

A **recorded** problem is one only an effect can observe. Any code reports one by transacting it: an error recorded once per signature (`seon.error`), or a run's red proof, cost verdict, death, conflict, unmerged entry, deferred test or waste written as a fact at its end, a task held for root (`:failed`), and a test's newest red result. `seon.problems/report` reads what was recorded, at a cost that follows the problems and never the program. A recorded error closes, with nothing written, once its subject has a fact written after its last occurrence (`seon.problems/closed?`). The subject (`:seon.error/subject`) is a var, a section, or an attribute that only a live proc writes, so its cause being gone is itself the fact. For example, a watcher's death names root's `:seon.root/watch` (`my.root/watch-died-tx`), so the next boot's watcher closes it; a refused read of the task files names `:seon.root/tasks` (```my.root/load-answer```), the outcome of root's last read of them, written with the error in one transaction (```my.root/load-error-tx```) and by every good read (```my.root/tasks-read-tx```). So the first read whose outcome differs closes it, a good one of the same bytes as before the refused one included, while the same refused read again writes the same value, no datom, and it stays open. A subject's fact is the producer's latest outcome: written on success and on failure, never a counter, and an unchanged outcome writes nothing. A read shows one refused file at a time (`seon.task/load-tx` answers the first), so a second file refused later replaces the first's outcome and closes its row; it opens again once the second is fixed and the first is the one shown. An error that names no subject stays open until someone reads it.

A **derived** problem is something the program's facts make true now. It is a read over facts the loaders already write, so nothing writes the problem and nothing closes it. It is open exactly while it is true, and fixing the fact closes it. `seon.problems/health` is `report` plus the derived classes, in the same value, and `my.root/problems` answers it for root's main with the api's fold of repeats not yet written. Not this: a check that stores its findings and must remember to retract them, or a timer that re-runs a scan.

## A dead citation

A wiki section stores the names its own text cites as references (`:seon.section/names`, written by `seon.docs/load-tx` through `seon.ref/kept`). A prose word is kept only when it names something at load; a backticked name is always kept. When one of those names no longer names anything (`seon.ref/names-on-db?`, the one rule, reading main's var names as a set first), it is a `:dead-citation` row (`seon.problems/dead-citations`, a set lookup per cited name, so its cost follows the citations). The commonest case is a var deleted after the page cited it.

A link (or a cited `path#anchor`) that reaches no section is kept on its section as `:seon.section/dead-links` instead of refusing the load, so one stale link never takes the wiki down. `seon.problems/dead-citations` reads those targets too (one seek each): one still no stored section is a `:dead-citation` row with the target under `:target` ("<section> links to <target>, which is no section"), closed when the section exists.

Not covered:
- A task's plan. It cites the vars it will create (its write set), so "names nothing" there is the plan, not a dead citation; `seon.task/citation-problems` answers those at the write ([references](references.md#task-references)).
- A cited keyword or path.

[references](references.md#the-wiki-in-the-store) has how the wiki is stored.

## A law's unnamed site

A law the compiler's facts answer exactly is a derived class too: `seon.problems/laws` holds each one as data (the fact that marks a site, the page that must name it, the check drivers it leaves out), and `seon.problems/unnamed-sites` lists each site whose page does not cite its function (`:unnamed-site`). A site is a live form of Seon's own `src` (bin/laws scans src; `seon.check` and `seon.e2e`, the check drivers, are left out): an agent's app and any test are not, since a deftest's `is` expands to a catch. A form is named by the var it defines, else the multimethod or protocol it extends, else its form id. The one law held so is `catch`, whose sites come from `:form/catches` and page is [failure points](failure-points.md). Clocks, measures and resolution stay `bin/laws`' text scan until the compiler's facts can tell their sites: a host member is recorded as `jolt.host/static-member`, not by its name, and a quoted symbol counts as a ref.

## A red test

The test service ([merging](merging.md#the-test-service)) leaves a fact per test digest on main. `seon.problems/test-reds` reads the newest result of each test (the entity under `:seon.proof/latest`; class `:test-red`, area tests): a red one is an open row naming the test, the branch and tx it ran at, and the agent that asked. A red on an agent's branch is not on main, so it is not a row. A later green at a new digest is the entity's newer result, so the row is gone with nothing written; the red result stays in the history.

## A stale section

A wiki section that cites code is stale when what it describes of that code changed after its text: a cited var's contract or docstring (`seon.problems/stale-sections`, class `:stale-section`; owner, 2026-10-25, DECISIONS Dogfood rulings). A body that changed while both stayed is not a change of what the section describes. When the loader writes a section's text it records the form id of each var the text cites (`:seon.section/read`, `seon.docs/read-map`; a form id is the form's own digest, so it moves exactly when the form's text does), and while the text is unchanged a reload keeps what was recorded: it is the code as it stood when the section was last written. A cited var whose form id now differs has its `:var/contract` and `:var/doc` facts read as of the transaction that wrote the section's read (or its review) and compared with today's: a contract or docstring change is itself a transaction (`seon.program/def-tx` asserts and retracts them, history kept), so no digest of meaning is stored. The row names the section, the var, what changed (`:changed`), what it was (`:was`) and is (`:now`). The eval that makes such a change says so in its response (`:redefined`, `seon.program/meaning-changes` over its own transaction), with the sections citing the var, so the agent sees the change it made and what to update. A form id unchanged since the read cannot have changed what it says, so only the names whose form moved read history (the before and after on main are in the commit that made this the rule). It closes when the section is edited, which re-reads the code, or when someone has read it as it is and says so with `my.docs/reviewed!` (who, and the form ids it read at; the older reviews stay in the history), with the text untouched. The comparison is by value, never by tx: a branch's tx counter is its own.

A section with no record yet (every section the day this was merged, and the first load of an old store) takes its baseline from git, so the sections already stale show up (`:seon.config.root/wiki-baseline`, `seon.root/wiki-baseline`): the commit that last changed the section's lines (`git blame --porcelain` of its page, the newest committer time among the section's lines; a line not committed yet means today), and for each var it cites the id of the form defining it in its file at that commit (`git ls-tree` for whether the commit has the file, then `git show`, read without loading by `seon.source/defining-ids`, which finds the form by its head and name and gives it the id `seon.program/account` would). Git is the `:history` effect (`seon.fx/wiki-history`, the effect owner); the loader stays pure over what it answers (`seon.docs/baseline-plan`, `baseline-reads`). A var the old file does not mention at all, or a file the commit did not have (`git ls-tree` says so), is recorded as `:absent` and is stale: it is code that appeared after the section, and the section may not describe it. A var whose form changed since the commit is read both ways by one reader, the old file and today's form as written (`seon.source/defining-meanings`: docstring and `:malli/schema`, read without loading; the contract carries the arity), and recorded as `:changed`, stale, when they differ, else as today's form id; the live `:var/contract` is not compared there, since it is the resolved schema and old text cannot give it. A var the old file mentions but no form `defining-ids` knows (one by its head) defines is not guessed `:absent`: the section is unread. A section with an uncommitted line is recorded as of today, nothing unread. A review is a git commit, so a rebuilt store reads a reviewed section fresh: `my.docs/reviewed!` also makes an empty commit with the trailer `Reviewed: docs/x.md#heading` (the `:git` effect, on the merges branch; off a checkout the commit is owed), and the baseline takes, per section, the newer of the commit that last changed its lines and the last commit whose trailer names it, from one `git log HEAD --grep='^Reviewed: '` (the checkout's own history: a review on a branch that never reached it, or was abandoned, does not freshen the section) (an empty commit touches no file, so a per-file log would never find it; a tie goes to the review). A section git cannot answer for (not a git checkout, a file git cannot show, an old file that does not read) is recorded as of today and carries `:seon.section/baseline-unread`, shown as one attention row until the section is edited. Measured on Seon's own wiki on 2026-10-23, once: 4.7 s (0.3 s planning, 3.9 s of git for 46 commits and 299 old files, 0.5 s reading them), 139 of the 303 sections cite code, and 88 of those were stale (229 rows: 214 changed, 15 cited code that appeared later).

It is attention, never a reason to refuse done (root's ruling, 2026-10-23): every edit of a var stales the sections that cite it, and refusing done for that would force a doc edit with every code edit. A branch that changes a var sees, in its context under `:attention`, the sections it made stale (`seon.problems/caused-split`), the docs to read and probably fix; `seon.problems/caused` and the done rule do not carry them.

## A stale pin

A pin the wiki states is stale when it is not the gitlink root's last source import recorded (`seon.problems/stale-pins`, class `:stale-pin`). The page that states pins is `docs/forks.md`: each line of the form "`reference-code/<name>` pinned at `<sha>`" (`seon.problems/pins` holds the page and the line's shape). Root records the gitlinks of `reference-code/` when it imports its source (`:seon.root/source`, its `:pins`); the class compares the stated sha, as a prefix, with that record.

While root has recorded no import there is nothing to compare, and the class has no rows: unknown is not a mismatch. A row names the section, the path, the sha stated and the gitlink recorded; fixing the page, or bumping the pin and rewriting the line in the same commit, closes it. Cost: the page's sections (one range of addresses) and their text.

## An orphan page

A page of the wiki that no other page links to, the map (docs/README.md) included as a linker, is an `:orphan-page` (`seon.problems/orphan-pages`): a section of another page has a reference to one of its sections, or it is orphaned. The map is the root and is not judged, and a db whose wiki has no map has no orphans (unknown). Adding a link anywhere closes it, with nothing written.

## A section with no lead

A section whose first block is a list, a table or code, not a paragraph, has no lead and is a `:leadless-section` (`seon.problems/leadless-sections`): its summary is its heading alone and its embedding has no sentence saying what it is about. [The wiki's rule](README.md) is a leading sentence that stands alone for every section, and a heading that only groups subsections says what they share. Writing the sentence closes it, with nothing else written.

## A task that cites nothing

An `:implement` task that is ready (not done, every task it needs done) is an `:uncited-task` (`seon.problems/uncited-tasks`) when the plan it holds, its own and its needs' (its design step's, `seon.task/accumulate`) cites no var, attribute or section (`:no-references`), when it names no proof (`:no-proofs`), or when a proof is still the placeholder `seon.context` writes for a missing one (`:placeholder-proof`). The context pulls what the plan cites ([references](references.md#task-references)), so a plan in prose alone gives the agent nothing to read. A design step's prose plan is its input and is never judged: the design step writes the cited plan. The row closes when the design step's plan cites a name (one backtick, [references](references.md#the-delimiter-picks-the-depth)), the proofs are named and no proof is the placeholder, with nothing written to close it. Cost: the task, kind and `needs` datoms once, then a walk of each ready implement task's needs.

## A problem with no page

Every problem class declares the section of the wiki that says what it is and how it is fixed (`:seon.problems/docs` on `:seon.problems/class`, beside its area), and a row shows the link. A class with an open row whose section is no stored section, or that declares none, is a `:problem-unlinked` (`seon.problems/problem-unlinked`, area health), itself a class that declares its own section, so a missing page for the unlinked class is one more row. A db with no wiki has none (unknown). Not built: the case of a recorded error that no task answers and whose owner namespace has no task file.

## Checks are callers of Seon

`bin/check health [CLASS ...]` (`seon.check/health-check`) is the one check of these classes, and it holds a checkout to what a Seon agent is held to: what its branch caused (root's ruling, 2026-10-23). It boots Seon on the checkout's source and task files and loads the wiki (the head). It then loads the base commit's tree onto that db with root's own loaders (the base). The base commit is ```seon.fx/base-commit```: with a branch checked out, its merge base with git's main (`:seon.config.source/main`), so a branch with no commits of its own caused nothing; with main checked out and a clean tree, the previous main, so the merge session's run on a merged main judges the merge; with main checked out and uncommitted changes, HEAD. The step judges `seon.problems/caused-split` of the two, the done rule's own reading (```seon.check/branch-health```). It prints each row the branch caused (and `attention` rows, the sections it changed under the wiki, which never fail it), and how many rows the head holds open in all, and ends `HEALTH OK` or `HEALTH FAILED`. A problem the base already had is not the branch's: it is root's to show, live, in its context and on its page. `bin/prove` keys the step by the tree and the base's tree (`seon.proofs/step-digests`), so an unchanged pair reuses its result. `bin/laws catch` calls it for `:unnamed-site`; it checks nothing of its own. Not this: a second checker over the files (`bin/check docs` beside the class), or the tree's absolute open rows as a branch's verdict (red on an unchanged main, so every session learned to read past it).

## What a branch caused

`seon.problems/caused` is the set of derived problems a branch's head has that its merge base had not and that refuse its done: what the branch's own work broke (`seon.problems/caused-split`'s `:caused`; the classes `:seon.problems/attention` declares, the stale sections, go to its `:attention` instead, [above](#a-stale-section)).
- The agent's turn computes it each turn (`seon.turn`'s observe, by `caused-split`), so its context lists them with the done rule's other reasons.
- Root's judge records it at the run's end (`:seon.run/caused`, from the writer's `:branch-diff`).
- `seon.reconcile/done-explain` gives `:open-problem` as a reason while any is open, so the task is held for root naming it ([tasks](tasks.md#the-done-rule)).

Nothing gates an evaluation. An agent may break a citation in one eval and fix it three evals later (AGENTS §4: get out of an agent's way). A merge needs no rule of its own: a branch behind main is refused `:behind` and judged again after merging main.

## Every writer: root loads what changed

Root watches its checkout and its repository's refs, so whoever writes (a Claude session, a Seon agent, the owner's editor, git) reaches the same facts with no script of their own (owner, 2026-10-23: "seon code detecting and updating, not external scripts").
- `target/watch` (native/watch.c, built by `bin/build`) is an OS child over macOS FSEvents (latency 0, no timer, no poll). It prints one record per change: its kind letter, the absolute path, then NUL, since a path may hold a newline. It exits when its parent does. Its first record, ready, means the stream is registered: `FSEventStreamStart` returns before fseventsd delivers to a stream, and a change made just after it was lost (1 in 600 under load), with nothing in fseventsd's history that recent to replay. The stream starts from the event id current when it is made, and fseventsd ends the history it sends (empty) with an event flagged HistoryDone, after which live events follow: that sentinel is ready, and a change replayed before it is not reported. FSEvents may still deliver late under load (5 to 18 s measured).
- `seon.watch/start!` reads it on one edge thread, the blocking read AGENTS §5 allows. That thread is an outside caller of root's API, as a server connection is: a proc's step must never wait on the api's answers. Each batch is what the stream holds when a read returns, so no clock decides.
- `my.root/watch!` (started by ```seon.main/root-serve```, the standing root `bin/root` runs) decides what each batch makes root load (`my.root/watch-loads`):
  - a path by its loader: a page under docs/, a task file, Seon's source;
  - the checkout's own branch moving (its ref, ```seon.fx/head-ref```: a commit or merge on it): the source. The repository's refs are every worktree's, so another branch's commit loads nothing (a root-test root loaded the repository's 806 task files when other sessions' work moved them, 2026-10-25: `seon.watch-test/another-worktrees-commit-loads-nothing`);
  - a rescan or a moved root, where FSEvents coalesced or dropped events under a subtree: the loaders reading under that subtree (a build's under target/: none; the checkout itself: every kind), and of the refs, the source alone.
- `my.root/watch!` loads each kind once (`load-kinds!`); a batch no loader reads writes nothing, so root's own store writes never feed back. Batches, paths and rescans are counted in root's `:seon.root/watch` fact. The last batch that loaded is kept there too, each kind with the first record that made it (`:last-load`, ```my.root/watch-loads```), so a load says why.
- FSEvents delivers to a new watcher writes made just before it began (its journal had not yet flushed them, and their event ids come after the watcher's start), so a root booted seconds after a merge sees the merge's writes. Reloading the wiki or the source unchanged writes nothing; such an event once made a test root load the checkout's 810 task files. A test root's task dir is its own (```seon.test-store/start-root!```, `seon.root-test/a-test-roots-task-files-are-its-own`).
- What changed while root was down is boot's to load, as it always was: the wiki (`seon.root/wiki-tx`) and the source (`seon.root/import-source!`). Task files load on their change, and once at boot when the watcher is ready (`my.root/watch!`: a fresh or erased store holds none, a file changed while root was down is read, and an unchanged read writes nothing; about 0.2 s for the checkout's 60 files).
- A watcher that cannot start or dies is a `:platform` error on main (`seon.root/platform-tx`), shown on the banner; root goes on unwatched, never polling ([failure points](failure-points.md)).

`load-kinds!` answers the problems a load made true (`seon.problems/caused`, of main before and after), kept as `:last-opened` in the watch fact; a loader's typed error (a refused task file) is recorded as a `:platform` error (`my.root/load-errors`), and a throw in a batch's handler is the watcher's recorded death, whose message is also kept on the watch fact as `:error`.

## Cost

Measured on 2026-10-23 (`seon.problems-test/dead-citations-follow-the-citations`, every citation dead, the worst case): 68 us, 68 KB and 4 contracted calls per cited name at n=1000, against an estimate of 90 us, 170 KB and 6. A citation that names something costs one set lookup. On root's own store (152 sections, 1,280 vars), a set built from main's var names and read for 1,712 names took 0.37 ms, against 18 ms for one AVET seek per name; that is why the class reads a set.

`unnamed-sites` costs about 75 us and 75 KB per catch form (measured at n=10, 100 and 1000: linear, two contracted calls per site, `seon.problems-test/unnamed-sites-follow-the-catch-forms`); `stale-pins`, `health` and `caused` have their own cost proofs in the same file. `caused` compares base and head by value (not by tx: a branch's tx counter is its own) and reads the rules only for what differs: the sections whose citations or dead links differ, the sections citing a name a var or task lost, and the forms carrying a law's fact whose catches or text differ (every site when a section of a law's page changed). Its floor is a scan of those attributes' datoms, with no pull and no rule. Measured in a REPL on Seon's own program (300 sections, 880 citations, 1,735 vars, 30 catch forms), after deleting a var that is cited: 11-12 ms, against 26-29 ms for reading both classes in full over both dbs; an unchanged branch 7 ms. With `:stale-section` read only for the vars the branch changed (`seon.program/changed-vars`) and the sections that differ, an unchanged branch is 7.7 ms and a change 8.5 ms; the whole of `health` on that program is 12.7 ms (0 stale sections right after a load, 0 orphan pages, 0 unlinked classes). `seon.problems-test/caused-follows-what-changed` holds it at 10, 100 and 1000 sections and sites with a fixed change (its bounds: 5,900 ticks and 32.5 KB per section and site for the scan, 24 contracted calls however large), and `caused-agrees-with-the-full-reading` checks it against the full reading on eight changes.
