# Storage

One durable store holds every branch as Datahike index trees in konserve, one node per key, on LMDB, each node at the address of its content (`:crypto-hash?`, which `seon.db/layout` sets when a store is made). A commit costs the nodes it rewrites, so what it writes depends on how values are laid out, whether history is kept, and how nodes are encoded. The store is opened in `seon.db`: `seon.db/open!` makes and seeds a store that does not exist (```seon.db/store-cfg```, ```seon.db/made-cfg```), makes root's main branch from `:db`'s head when the store lacks it, shares the id page ([ids](#ids)), installs the attributes the store lacks and syncs when any of these wrote. Its failure points are in [failure points](failure-points.md), and its config keys (`:seon.config.store/*`) in [config](config.md).

## Identity

A store is named by the id it records, never by where it lies, so a kept store opens wherever it is copied, moved or archived. ```seon.db/store-cfg``` reads the id from the store's `:db` head (```seon.db/stored-id```, Datahike's own read path, 0.8 ms) and mints `(hasch/uuid path)` only for a store it is about to make (`seon.db/open!` creates that store from the config ```seon.db/made-cfg``` derives); Datahike's connect refuses a config whose id differs from the stored one (`:store-identity-mismatch`). A copy keeps its original's id, as a Datahike replica does, so one process opens one of them. A connection's db names the store where it lies: our Datahike's `datahike.connector/deref-conn` keeps the connection's own config, as connect does, so `(:config @conn)` after a move names the new path. Proof: `seon.db-test/a-moved-store-opens`.

## A value is read before its last release

A db value reads its index nodes lazily from its store's LMDB env, and the last release of the store's connections (`d/release`) closes that env. An open env costs its process descriptors and address space (about 5 `lsof` entries and its 64 GiB map, measured 2026-10-27), and a store removed and made again at its path must open its own files, not the old mapping (`seon.db-test/a-store-made-again-at-a-removed-path-is-a-new-store`), so a released env is not kept. (No lock bounds it: one process holds 50 envs at once, [failure points](failure-points.md#lmdb-locks).) So a value is read before its last release. A read after it answers `{:type :lmdb-env-closed :path}` naming the store (konserve's `konserve.jolt.lmdb-ffi/close-env` marks the env, and every transaction begun on it after throws); before, it was an invalid memory reference that killed the process. Proof: `seon.db-test/a-read-after-release-is-a-typed-error`. Not this: an env kept open while a value reaches it, which lets the collector decide a second lifetime beside release (root's ruling, 2026-10-27). A db value is also read before it is let go, and a process keeps an older one only as a point (`seon.db/point`), made again with `seon.db/at-commit`: [root's heap](machine.md#roots-heap).

## Who writes a branch

An agent owns its branch and root owns main: each branch has one writer, the agent through its own connection and main through root's `:writer` proc ([root](root.md#the-root-graph)), and a change reaches main only by a merge ([sharing](sharing.md#a-merge)).

## A kept db value is a reference

A db value is used, then let go: whatever must keep a point in time past its moment keeps `{:branch :commit :t}` and re-creates the db from it, and nothing hands a db value to another function or process to hold (owner, 2026-10-28: "I don't want us carrying around large values for no reason. At those points we need to change db's into whatever facts we need to re-create that point in time."; 2026-11-07: "don't pass around databases ever. We have a data format and schema for it."). A held db value pins its whole version of the index: measured 2026-10-28, the render, vectors and reconciler procs each held about 160 MB this way, the reconciler's 230 transactions stale ([machine](machine.md#what-a-process-owns-in-memory)). An error kept past its moment follows the same rule ([errors](errors.md#an-error-keeps-data)).

## A point's commit

A commit's record holds its last transaction (`:max-tx`) and its parents, and nothing more about its transactions is stored (owner, 2026-11-11: "We don't need to store data that we can derive"). What it holds is derived: the transactions after its base's `:max-tx` up to its own (```datahike.versioning/commit-tx-range```), its base the parent its db was built on: the one parent (the writer builds a commit on its branch's head); of a merge's, the parent with the greatest `:max-tx` whose last transaction the merge's db holds, read from that db once. Transaction ids are issued once across the store's branches ([ids](#ids)) and a transaction entity is written only by its own transaction, so a db holds exactly its lineage's transactions, and the ids in a commit's span that are not in its db are other branches'. Without history a db keeps no transaction entity, so there a merge's base is refused `:commit-base-ambiguous`; Seon's store keeps history (`:seon.config.store/keep-history?`).

So the point of a branch at transaction t is found by walking the branch's lineage: ```datahike.versioning/commit-at-tx``` answers `{:branch :commit :t}`, the commit whose last transaction is the greatest at or before t (exact when `(= t (:t p))`), never one that also holds later transactions; ```datahike.versioning/commit-holding-tx``` the commit whose span holds t. Each refuses, naming `:branch` and `:tx`: `:tx-after-head`, `:tx-before-first-commit`, `:commit-expired` (a commit collection removed, met on the walk or as the answer). The walk reads each commit record it meets once per process and keeps its max-tx, parents, branch and, for a merge, its base in memory, keyed by commit id (```datahike.versioning/forget-commit-points!``` drops it); memory keeps the walk, never the answer's existence: every answer is confirmed by one `exists?` of its commit, so a commit removed since, by this process's collection or another's, is `:commit-expired`. A first lookup reads the commits from the db's commit back to the answer and the answer's `exists?`; a repeat, the `exists?` alone; after k new commits, k and the `exists?`. It stops at the first commit whose last transaction is at or before t, so a point near the head reads few commits and an old one many. Seon's retention sweep removes main's commits older than its kept generations, keeping a live branch's merge base with main and the commits a branch names (`:seon.agent/base-commit` among them; [collection](#collection)), so a walk to an old point of main can meet a removed commit and answer `:commit-expired` though a kept commit lies beyond it: a caller that holds a commit id branches from it and asks no lookup.

Measured 2026-11-11 on an LMDB store with Seon's layout, one-datom commits, the point at the first of n commits: a first lookup 169k, 1.69M and 16.9M engine ticks at n = 10, 100 and 1,000, one commit-record read a commit (16.8k ticks, 64 KB); a repeat the `exists?`, 9.0k ticks (settled: 9.4k for the whole lookup); a merge on the way adds about 128k once (its db read and a seek a parent). Walking the same span by `d/commit-as-db` (42k ticks and 185 KB a commit) cost 379k, 4.17M and 42.1M. The commit graph record (parents, generation, branch) reads in 12.6k ticks and 40 KB but has no `:max-tx`, so it cannot carry the walk unless it stored a derivable value. Proof: `datahike.test.commit-at-tx-test`.

## Durability is continuous group commit

A write is answered once the store has committed it (every process can read it), and one followed by an outside effect waits for the sync that covers it; no fixed collection point delays a commit (owner, 2026-10-21: "Why have an arbitrary 10ms collection point?"). The one writer is root's `:writer` proc ([root](root.md#the-root-graph)), and the `durable` and `window` check steps prove it across a kill and a reopen ([checks](checks.md#modes)).

Root's write to main is answered once the store holds it (owner, 2026-11-10: answered means every process can read it; [decisions](decisions.md#a-write-to-main-is-answered-after-the-store-holds-it-owner-2026-11-10)): ```seon.writer/writer-proc``` commits each step's batch (each write applied with `datahike.writer/apply!`, main's content mark after them when they moved it, then one `commit-pending!`, unsynced: another process reads it at once, MDB_SAFENOSYNC) before it answers, so an agent or the fork server that reads main from the store after an answer reads the write; durability is the flusher's sync after it, and a `:flush?` write is answered after that sync. Answering at the apply, before the store commit (built and measured 2026-11-10: 0.45 ms p50), was refused: an agent that read main right after the answer could miss the write (`seon.agent-test/an-agents-first-search-reads-the-index-it-inherited` passed by timing). Measured on a worktree root at load 12-14, 40 one-datom writes (`:seon.root/collected` rewritten, `@(seon.root/transact-main! sys tx)`): p50 7.6-8.5 ms, p90 8-25 ms, against 21-24 ms before root's main connection streamed (```seon.db/open-main!```: where root is the store's sole writer, `:seon.config.store/sole-writer?`, a deref of its connection is its own value, 107 ticks, not a read of the head, 58,739). An op that throws after the batch it committed keeps the state after that commit (```seon.procs-test/a-refused-op-keeps-the-batch-committed-before-it```).

A store is opened ``MDB_SAFENOSYNC`` (```seon.db/store-cfg```): a commit is not flushed, and the flusher's ```seon.db/sync!``` makes every commit so far durable and the store's steady snapshot, whose pages LMDB keeps from reuse until the next sync is durable. A process killed, root included, loses nothing: the OS keeps its writes, and the next opener reads every commit. An OS crash or a power loss loses the commits made after the last sync, never the store: the first process to open it after the reboot rolls it back to that sync's commit ([failure points](failure-points.md#lmdb-crash-safety)). While the flusher is stalled, the pages freed since its last sync are not reused, so the file grows by them.

## The map is address space

LMDB's map (`:seon.config.store/lmdb-map-bytes`, 64 GiB) is address space only: an open or a fork costs the same at 1 or 64 GiB, and the file grows only as it is used. Anything that walks a map page by page pays for its size, under the file's one VM-object lock that every process mapping the store shares: the memory probe once did (`VM_REGION_EXTENDED_INFO` on every region, ~1.5 ms per GiB), and 100 agents took 18 s to be ready instead of 0.65 s. Jolt's `jolt.host/process-footprint-bytes` now makes one `task_info` call on macOS, the kernel's ledger of the process's own memory (and reads one `smaps_rollup` line on Linux), so its cost does not grow with what is mapped (`jolt.process-test/a-process-reads-its-own-footprint`). Not this: a smaller map; at 1 GiB the kept store hit Datahike's fatal-commit-error.

## The proof: what a commit costs

`seon.db-test/a-commit-costs-what-it-writes` says a turn committed by itself costs what the same turn costs in one big commit, plus one root-to-leaf path per index (32 KB at most). Its turns are realistic: each reply is real text (the checkout's `docs/`), and each evaluated value is real source (its `src/`). A repeated letter compresses about 3× better than real turn text, which once made LZ4 look like the fix. Sample data must look like production data, or the numbers lie. Twenty turns, LMDB, branching factor 64:

| layout | one commit | per turn | bound | per turn / bound |
|---|---|---|---|---|
| values inline, no compression | 178 KB | 1,485 KB | 818 KB | 1.82 |
| values inline, LZ4 | 102 KB | 862 KB | 742 KB | 1.16 |
| out of line from 1,024 B, no compression | 111 KB | 376 KB | 751 KB | 0.50 |
| out of line from 1,024 B, LZ4 | 78 KB | 237 KB | 718 KB | 0.33 |

Inline values were the cause. Every commit rewrites the tail leaf of `:eavt` and `:aevt`, which holds each value inline, so a turn's text was written again by every later commit until its leaf split, and the waste grew with the agent's work. With values inline and LZ4, per-turn cost against the bound is 0.83 at 10 turns, 1.16 at 20 and 1.74 at 40. Out of line it stays near flat: 0.29, 0.33 and 0.41. Every layout commits in about 1.7 ms per turn. The default layout (out of line from 1,024 B) with the default codec, zstd, writes less again ([compression](#compression)).

## What a datom costs to add

`seon.db-test/a-datom-costs-its-index-inserts` says a datom added in memory (`d/db-with`, as every test plan's import is) costs its floor: its inserts into `:eavt` and `:aevt`, one `:eavt` descent for a cardinality-one attribute's current value, the datom and its place in the tx-data, measured at about 6.8k ticks and 10.5 KB on the test store's seed. It costs 7.2k ticks and 11.1 KB. What kept it from its floor was in two dependencies ([forks](forks.md)): a protocol call read every field of the record (Datahike's DB has 21), and Datahike found the current value through a slice's seq and copied the DB record for writes that change nothing. An identity costs more than its `:avet` insert and seek should (`seon.db-test/an-identity-costs-its-seek`, an accepted overrun on its task): 8.3k ticks and 19 KB per datom for a `:db/unique` one, 12.9k and 43 KB for a content id (measured 2026-11-10 at 100 datoms; the figures before, 11.5k and 34 KB, 16.9k and 65 KB, were taken at 1,000).

Making a store costs what its schema and its seed are. ```seon.db/make!``` allocated 1.05 GB, by phase (no history): create 0, schema transact 609 MB for 459 attributes, seed 2,000 datoms 286 MB, sync 0. The schema transact was quadratic, because Datahike's `update-rschema` rebuilt the whole reverse schema after each schema datom (50 attributes 22 MB, 150 98 MB, 435 599 MB); with the reverse schema updated by the attribute added and retracted (our fork, `set-ids!` in [datahike](forks.md#datahike)) it reads 8.7, 23 and 67 MB, one attribute added to a 400-attribute schema 835 KB down to 114 KB, and `open!` 1,052 down to 366 MB. The 286 MB left is the seed's 36 transactions, linear by design (content-id hashing 42 KB an entity, 8 KB an operation), so a test that needs several stores branches one seeded store. The test store's setup, measured 2026-10-29 (engine ticks, bytes allocated): the process's seed (```seon.test-store```, in memory) is 70 M ticks and 203 MB, of which the schema is 20 M and 70 MB and the 36 seed transactions 48 M and 124 MB; the same datoms in two transactions (the tasks refer to vars by lookup ref, so two at least) are 45 M and 112 MB, 6% less, because the cost is the content ids hashed, not the transactions; a fork of a kept LMDB store into memory (`datahike.api/fork-database`) is 55 M, no cheaper than seeding. It is paid once a shard process (`:seon.config.proofs/jobs` 4: a full run's 0.28 G of 120 G), and a run of few tests pays it for each shard it starts. A branch made and deleted (```seon.db/open-main!```, ```seon.db/delete-main!```) is 0.55 M ticks and 1.7 MB at 1,350 datoms and 0.63 M and 1.8 MB at 147,569, flat (```seon.db-test/a-branch-costs-what-it-holds-not-the-store```): the audit's 1.6 G ticks in `seon.test-store/test-branch!` in `seon.vector-test` are that test's bodies, since a closure is no contracted call and its work counts as its caller's own. A durable test store would pay the schema once a run but make each write dearer (a branch with ten transactions 3.7 M ticks on LMDB, 1.6 M in memory), so the test store stays in memory. A durable store of a test's own made fresh is 22 M ticks and 82 MB (the schema in one transaction); a fork of a kept schema store (`datahike.api/fork-database`) is 5.8 M and 23 MB, but it is not the store `open!` makes: its roster records its heads with no ids (the id page then restarts at 1, entity ids its own datoms hold), and `d/branches` lists no `:db`, so a collection and `gc-storage` misread it (`seon.db-test/a-collection-runs-when-a-branch-is-gone`, `gc-runs-through-the-sync-writer` and `a-large-value-lives-once-under-its-own-key` failed on one, 2026-10-29). That is a gap in the fork of Datahike (`datahike.versioning/fork-database`), to fix there before a test store is forked, for about 16 M ticks a store of about fifty a full run. After `make!` and a full collection live data is +1 MB: the rest is garbage. `seon.db/install-missing!` compares only `:db/contentId` and `:db/index`, so a changed `:db/noHistory` on an attribute the store holds is not seen; no attribute carries one.

A one-datom write through root's writer rewrites 23-27 index nodes and costs ~685k ticks (Deep fixes, notes nodes-per-write-2026-11-11.md): 13 of the nodes are the transaction entity's own three datoms (`:db/txInstant`, `:seon.tx/runtime`, `:seon.tx/branch`), 4-6 history, 8 the floor; the commit is ~112k ticks fixed and 18.2k a node. So an attribute indexed by value or kept in history costs nodes on every write that carries it: `:seon.tx/branch` is not indexed by value (read off the transaction entity, never sought by it: 5 nodes, 61k ticks a write), and `:seon.root/collected` keeps no history (only its last value is read: 4 nodes, 110k ticks on that write). Ten transactions in one commit wrote 31 nodes, not 250: what shares a commit is worth more than any per-key cut.

## Plain data

Plain data is what the store keeps as data and EDN carries, and one predicate says what it is: ```seon.contract/plain?```, the schema `:seon.db/plain`: nil, a boolean, a number, character, string, keyword, symbol, uuid or instant, or a map, vector, set or list of them. It is narrower than the test Datahike runs on a data value (`datahike.schema/plain-data?`), on purpose: that one walks any seq, and asking of a lazy or infinite value would realize it, and it admits bytes, which EDN does not carry; a sorted collection's comparator is a function, and a record is a type. So everything plain the store keeps (`seon.db-test/plain-is-what-the-store-keeps`), and what is not plain is made so where it is written: `seon.contract/plainly` answers data and never prints (a record as a map of its fields, a sorted collection unsorted, a var as its symbol, a lazy seq as a vector up to the bound, anything else as `{:seon.value/type <class>}`; every error passes through it at its constructor, `seon.contract/error`), `seon.contract/kept` bounds what an error holds past its moment, by the same walk. An eval's record keeps a value only up to `:seon.config.store/max-value-chars` (1,048,576 characters, counted by a walk that stops at the bound, `seon.contract/within?`): past it the response holds `{:seon.value/gone {:type :over}}`, the transcript says it is gone, and the handle (``result/e<n>``) still reads the value in the live process.

## The write checks every datom

A write holds each value to its attribute's declared schema, its branch's form where the branch registered one, so a value the schema refuses is never stored. The store itself checks only a value's type, and for a data attribute only that it is plain. ```seon.db/invalid-datom``` runs at the two points every write passes (```seon.agent/transact!``` and the writer's `:tx` op) and answers the declared `:seon.db/invalid-datom`, naming the attribute and where in the value. It reads a map's attributes and `:db/add`'s, walks a nested entity, takes a ref's id or lookup as it is, and leaves alone an attribute no schema declares (an agent's own, whose registry is its branch's), a retraction and a transaction function. It costs one validation per datom: one definition's contracted calls went from 83 to 101 (the owner's yes, 2026-11-06). The check costs one validator call a datom: each attribute's validator is found once a transaction from the schema the registry in effect holds (```seon.contract/held```), and nothing is kept from one write to the next, so a branch that changes an attribute's schema is held to the new one at its next write (63 ticks and 96 B a datom, measured 2026-11-10; proof ```seon.db-test/the-datom-check-costs-a-validator-call-a-datom```).

## The write checks every entity it touches

A transaction is refused, and nothing of it stored, when it breaks an entity it touched (a datom of it names the entity): leaves it holding attributes an entity schema owns without one that schema requires ([a schema is a set of keys written together](data-modeling.md#a-schema-is-a-set-of-keys-written-together)). ```seon.db/invalid-entity``` reads the report Datahike's transact made, before it becomes the value. ```seon.db/connect``` gives every connection's writer ```seon.db/transact-checked``` as its `'transact!`, so root's batch and an agent's run-ahead apply both pass it, and a value written with no connection (a test's world, an agent's test fork) passes ```seon.db/with```. The refusal is the typed `:seon.db/invalid-entity`: the entity by its identity, the schema and the missing keys, by the one printer; an agent's eval and root's requester receive it as itself. An entity the write only refers to is not touched, so not asked.
- **What a write broke.** A schema is asked of an entity when the write added or retracted an attribute it owns. It refuses a required key the entity held before and not after, and, on an entity that held none of the schema's required keys before (the write makes it that thing), every one it lacks. An entity incomplete before (an older build wrote it) is left as it was by a write that broke nothing of it, and a whole-store scan reports it; one left holding none of the required keys has stopped being that thing (`seon.db-test/a-write-holds-each-entity-it-touches-to-the-schemas-its-keys-select`).
- **A branch's own schemas.** A branch that registered entity schemas of its own, or changed one, is held to its own: the write's `{:forms :registry}` (the per-datom check's) give the entity index again for that write, derived with the branch's forms over the registry; every other write reads the binary's, derived once.
- **Cost.** One seek per (touched entity, required key) on the value after, and on the value before for the entities it touched; a write costs its touched entities' required keys, never an entity's size or the store's. A write on a branch that changed an entity schema also derives that branch's index (the registry's size). Checking a whole store took 2.4 billion ticks on the standing store with its six branches (2026-11-08), every entity passing once config and root's boot were optional.
- **One path, every transaction.** A transaction on a database value goes through `seon.db/with` (or `seon.db/db-with`), and one on a connection through the connection's checked `'transact!`; a function never checks a write itself (owner, 2026-11-08: "in whatever tx processing code we have we check everything rather than require functions to manually check it"), and a state the path refuses is a design failure, fixed at its cause, never an exemption. A transaction is checked once, where it becomes data (owner, 2026-11-08: "I'm okay paying validation costs as long as they are intelligent (like at tx time) I'm not okay with looping and checking the same data over and over again"): a hypothetical whose result is never stored, or whose real write follows through a connection, is `seon.db/speculate` (or `seon.db/speculate-db`, its value after), unchecked, and the write is checked when it happens. `bin/laws transactions` is red on a Datahike transaction call at a site this list does not name; the sites, each with why it is on the path: `seon.db/with` and `seon.db/transact-checked` (the path); `seon.db/connect` (the one way a connection is opened: it gives the connection's writer `transact-checked` as its `'transact!`, added there and never stored in the config, which is plain data that travels to a fork); `seon.db/speculate` (a hypothetical: nothing of it stored); `seon.db/seed!`, `seon.db/install-missing!`, `seon.db/retain!`, `seon.root/import-tree!`, `seon.root/seed!`, `seon.root/boot!` (the catch-up of a resumed boot: the files of its checkout that changed since main last indexed them), `seon.root/kept-index!` (a kept index's code), `seon.agent/init!`, `seon.agent/merge-main!`, `seon.writer/other-op` (a session's files written on their tree's branch as it is made, `:branch-for-tree`: [a session proves through root](merging.md#a-session-proves-through-root)) (a transaction on a connection: its writer's checked `'transact!`; a merge written through the writer's ``'merge!`` too: Datahike builds a writer's ``'merge!`` over the ``'transact!`` its connection supplies, ``datahike.writer/writer-fn-map``, so the merge's arg-map passes `transact-checked` and a merge the check refuses is not written); `seon.agent/transact!`, `seon.writer/commit-batch` and `seon.writer/mark!` (an agent's run-ahead `apply!`, and the writer's `apply!` of its batch and of main's [content mark](#mains-content-mark), which call that same `'transact!`); `seon.writer/writer-proc` (the content mark at the writer's start, through main's connection).
- **A speculation applies what it reads.** A caller that reads a few attributes after a hypothetical speculates the transaction cut to them (```seon.db/project-tx```: each map keeps its `:db/id` and those attributes, every `:db/retractEntity` stays), never the whole: an import's config check and its source fact's counts each speculated the checkout's whole program, 2.7 G ticks and 4.7 GB a call, before (`seon.source-test/a-speculation-of-what-it-reads-reads-what-the-whole-would`).
- **An entity named by a ref ends with its target.** An entity whose schema requires a ref (a vector's identity, `:seon.vector/of`; a cite's `:seon.cite/target`; a form's `:form/ns`) has no meaning without that entity, and the check above would refuse it left without the key, so when a transaction retracts an entity whole, the path retracts the entities that require a ref to it with it (no attribute is a component, so Datahike's own cascade adds none); no writer retracts them by hand, and none is left holding the rest of itself (owner, 2026-11-08: identity refs cascade; managing session, 2026-11-10: a cite ends with its target, since an import that retracted a var a generated task cited was refused whole). A cite it ends leaves its task `:seon.task/gone`, the target named, in the same write ([task references](references.md#task-references)). Proofs: `seon.db-test/an-entity-named-by-a-ref-ends-with-its-target`, `seon.problems-test/a-cite-ends-with-its-target-and-its-task-shows-what-is-gone`.

## Entity ids

The entity whose unique attribute holds a value is found by `seon.db/eid`: one seek in that attribute's AVET index, never a Datalog query (a query planned per call cost ~95 µs and 100 KB at 100 tasks). It is the one lookup; every namespace that needs an entity id by value calls it. Reading an entity's facts needs no id first: a pull by lookup ref (`(d/pull db attrs [:seon.root/id :root])`) answers nil when no entity holds the value, so root's facts, a task, an agent or an error record are pulled directly.

## Ids

Every entity id and every transaction id is issued once across the whole store: every branch, every process. So a datom names the same entity and the same transaction wherever it travels, onto main by a merge or into a query over several branches. The ids come from one page every process writing the store shares (```seon.db/ids!```, `native/ids.c`): two 64-bit words, the last entity id and the last transaction id issued, mapped from the file `ids` beside `data.mdb` (an anonymous page for a store in memory). A process forked from root (the fork server, an agent, a clone) maps the same page, so it needs nothing at fork. Datahike takes them through its id source (`datahike.ids`, `datahike.writing/set-ids!`):
- a transaction takes its id when it begins, and a branch's t (`:max-tx`) is the id of the last transaction written on it: increasing as the branch is written, with gaps where other branches took ids. A merge carries a branch's transactions with their own, older ids, so the ids of the transactions a branch holds are not in the order they were written there, and what orders transactions is their time ([history](#history));
- each fresh entity id is one atomic fetch-add. Measured 2026-10-23: 28-34 ns an id, 200-240 ns with 10 processes contending, 30M ids with none lost or repeated; an LMDB counter key cost 9.6 us alone and ~500 us contended (docs/storage.md#ids);
- every writer takes its ids from the page, so the page is past every head's ids unless it was lost or made apart from the store. A process killed loses nothing (both files' pages stay in the OS page cache). The page is behind only when it is new or a copy (a `data.mdb` cloned without its `ids` file, as `bin/check` and the test stores take theirs; an `ids` file copied, which is another inode), when the data file beside it was replaced (another copy of the store renamed or cloned in under the kept `ids` file), or after the OS lost dirty pages (power lost, the OS crashed: LMDB runs `MDB_NOSYNC` and the page is never msync'd), which a boot follows. So the page carries a stamp, the OS boot identity and the device and inode of the `ids` file and of the store's data file (```seon.db/data-file```), written once it has been moved past the heads (`native/ids.c` lays it out and says which boot identity each OS gives). An open reads every branch's head (`datahike.writing/set-ids!`, O(branches): 2 reads, 23.7k ticks and 68 KB a branch) only when the stamp is not this boot's and these files': once per boot per store, after a compaction (```seon.db/compact-if-due!``` renames a new data file into place), and for a new, copied or remade page or data file; an anonymous page is never stamped. Not caught: a data file overwritten in place (a copy onto the existing file keeps its inode), or a volume that lost dirty pages without a boot (forced off or unplugged). A stamped open reads no head: 0.37 M ticks, 1.86 MB and 10 reads at 1, 10, 100 and 1,000 branches alike (measured 2026-11-10). An id issued but never committed is a gap, never reused;
- an explicit id in tx-data (a carried datom's) moves the page past it.

**Content ids.** An entity with an identity marked `{:seon.db/content-id true}` in its schema (Datahike's `:db/contentId`: the program's, `:form/id`, `:var/name`, `:ns/name`, `:file/path` and the rest, and the platform's, `:seon.agent/key`, `:seon.message/id`, `:seon.result/hash` and the rest) takes its id from its identity: `datahike.db.transaction/content-eid`, the hash of `[attribute value]` (hasch's uuid, Datahike's content hash: 17-19 us a call on Jolt, measured 2026-10-23) taken into `[ce0, emax]` = `[2^40, 2^60)`. Every branch that mints one identity mints one entity, so a merge carries its datoms as they are, with no remapping (owner's ruling 2026-10-23; the content-eids pricing study, 2026-10-23, not kept). The partition, every id a fixnum: counter entity ids below `tx0` (2^29), transaction ids in `[tx0, 2^40)`, content ids above. Every entity map takes it where Datahike resolves each map, top-level or nested (under a ref, a component, a reverse ref, in a cardinality-many value, any depth): ```datahike.db.transaction/entity-map->op-vec``` gives a map that names no entity yet its content id after the upsert lookup, so one identity in one transaction is one entity whatever the order and nesting of its maps (their attributes merge, as two top-level maps' do), and an identity the db already holds keeps its id, one minted at a counter id before its attribute gained `:db/contentId` too. A top-level tempid is resolved before anything else (`content-tempids`), so a ref to it made before its map takes the content id; a nested map's tempid that an earlier ref resolved to a counter id is retried at it. An identity names its entity for good: asserting another value of it on that entity, a rename or a hash collision (about 4e-7 at a million identities), is refused `:entity-id/collision`, never merged. `:form/id` itself is now hasch's uuid of the namespace and text (it was Clojure's 32-bit `hash`). Cost, measured 2026-10-23 at 110k datoms: nodes written per commit 0.97x the counter's with 1 new identity, 1.51x with 2 and 4.50x with 10 (commit 3.4 -> 3.9, 3.8 -> 6.7, 8.2 -> 20.2 ms); commits that add no identity write the same. Proofs: `seon.db-test/an-identity-names-its-entity-on-every-branch`, `seon.db-test/a-nested-map-takes-its-content-id`, `seon.db-test/content-ids-cost-the-writes-the-model-says`, and Datahike's `datahike.test.content-id-test`.

**Several roots on one store.** Ids no longer stand in the way: every process maps the same page, so two roots issue distinct ids. Two things still do, so a store has one root:
- **The branch roster.** `d/branch!` appends to it with a read and three writes under a lock of its own process only, so two processes branching at once can drop one branch from `d/branches` (task `seon.db/two-processes-branch-one-store-at-once`).
- **Collection.** A root collects only as the store's only writer ([collection](#collection)), and it cannot see another root's live agents.

A speculation (`d/with`) takes no ids. The fork server's replica of main is each stored commit of main, read from the store (```seon.writer/stored!``` sends the notice), so its t is main's. Proofs: `seon.db-test/each-id-is-issued-once-across-branches`, `seon.db-test/a-reopened-store-issues-past-every-head`, `seon.db-test/an-open-reads-no-head-but-its-own`, `seon.db-test/a-killed-writer-leaves-the-page-past-its-commits`, `seon.db-test/a-copied-or-new-page-is-moved-past-the-heads`, `seon.db-test/a-page-from-another-boot-is-moved-past-the-heads`, `seon.db-test/a-page-beside-a-replaced-data-file-is-moved-past-the-heads`, and `bin/check ids` (two agents' processes). This replaced per-agent leases of entity ids, whose blocks held about 5,400 agents per store and whose transaction ids were per branch (two branches forked at one t gave their first transactions one id).

## A root's main and its branch names

Many roots, and every check and test, share one store, so a branch's name is qualified by the root that owns it. ```seon.db/main-branch``` is the branch a root works on as its main (its config's `:branch`, `:db` when none), and ```seon.db/conn-main``` is the same for a connection. ```seon.db/on-main``` names branch b of the root whose main is `main` as the store does (`:db` names main itself; on `:db`, the production main, b is b; on any other main b is qualified by main's name), ```seon.db/off-main``` undoes it for one branch (the name an agent's or a message's facts carry), and ```seon.db/of-main``` over the store's branches, main itself left out. ```seon.db/branch?``` asks whether a branch exists by its head key, one read (`d/branches` folds the whole roster). ```seon.db/open-main!``` gives a root its main on a store whose `:db` exists, made from `:db`'s head when the store lacks it (one pointer write), and answers `[conn existed?]`. ```seon.db/head``` reads a branch's committed value from the store, since another process may have committed it; ```seon.db/store?``` asks whether a durable LMDB store exists at a path; ```seon.db/agents-dir``` is where a root's agents keep their stderr (`<store path>-agents/<main>`). A check's or test's main is deleted by the run that made it (`seon.db/delete-main!`, [collection](#collection)).

## Forked processes read memory

An LMDB env is its opener's alone, so every forked process opens the store itself ([an agent's reads and writes](#an-agents-reads-and-writes)). The fork server, once forked, reads every node of main's indexes into its heap through its own env (```seon.db/preload!```, which answers the datom count), so the agents it forks inherit them decoded. The map's use is recorded, not acted on: ```seon.db/map-use``` answers `{:used-bytes :map-bytes}` for an LMDB store (the data file's length, since LMDB grows the file as it uses pages, beside the map's address space).

## A commit's report

The writer turns Datahike's tx-report into what main's readers receive: ```seon.db/report->tx``` is the report as explicit-id tx-data (the transaction entity's own datoms left out). Readers of main apply the ops and the meta together, so a commit's own facts arrive beside its datoms ([history](#history)). ```datahike.transaction-test/a-replaced-value-is-retracted-in-the-report``` holds that a card-one assertion over a held value puts the retraction of the old value in the report beside the assertion (upstream's report holds only the assertion), so a reader of a transaction's datoms sees a ref move an entity away from its old parent. ```datahike.transaction-test/a-keyword-attributes-two-values-are-two-values``` holds that two keywords in a card-many value are two values, never a lookup ref, even when the first names a unique attribute.

## What a read scanned

Datahike records what a read scanned, so a cached view is valid until a transaction touches it ([render](render.md#components)). `d/with-reads` runs a read and answers `[value reads]`, and `d/reads-index` turns the reads into keys by what was scanned: `[:e e]` and `[:ea e a]` for entities and their attributes (a pull), `[:av a v]` for a point query on a unique value, `[:a a]` for an attribute scan, and `:any` for an open range (```datahike.reads-test/a-read-records-what-it-scanned```). The recorder is a dynamic binding, so a read made inside a Flow step, or from a go block inside it, is recorded too (```datahike.reads-test/a-read-inside-a-flow-step-is-recorded```). `d/reads-touched?` asks whether a transaction's datoms touch an index: a datom of a pulled entity, added or retracted, does; another entity's does not; and a schema datom touches every read (```datahike.reads-test/a-transaction-touches-only-what-a-read-scanned```). It costs the transaction's datoms, five keys and one set lookup each, and nothing per recorded read (```datahike.reads-test/a-transaction-costs-its-datoms-to-match```, ```datahike.reads-test/matching-is-flat-in-what-was-read```).

The same fork makes a query answer what it asked ([forks](forks.md#datahike)). Datalog evaluates no call inside a predicate's arguments, so a nested call is refused rather than read as a constant list that matches no result (```datahike.query-test/a-nested-call-in-a-predicate-is-refused```), and a predicate that throws is an error, never a false that drops every result (```datahike.query-test/a-predicate-that-throws-is-an-error```).

## An agent's reads and writes

An agent reads and writes its own branch through four functions it has in every namespace. ```my.db/db``` is the branch's current db value in this process, and ```my.db/q``` and ```my.db/pull``` are `d/q` and `d/pull` against it, so a read costs a read of the value. ```my.db/transact!``` sends tx-data to the writer for this branch and answers `{:t :datoms}` once the writer has committed; the agent then applies the same report to its own value. Inside a test, a fork of the agent, a transaction applies to the fork's db only, so a test's writes vanish. The branch is one of the store's many ([a root's main](#a-roots-main-and-its-branch-names)).

A forked process reads the store through an env of its own. LMDB forbids using an env across `fork()` (lmdb.h's caveats: a read transaction begun through an inherited env takes a reader slot under the parent's pid, which a writer reclaims once the parent dies, and the snapshot's pages can be reused under the child). So a child forgets what it inherited (```seon.db/after-fork!```: the env and connections dropped, never closed, their node caches kept), connects on its own, and makes every db value it holds of its parent's again through that connection, by its commit: an agent its main as forked (```seon.agent/init!```), a clone and a test child their parent's branch, base, main and index (```seon.agent/own-store!```; an agent commits what ran ahead before forking a test child, so its value is a commit), as the fork server already did with root's. What the parent decoded is reused through the node cache. A read through an inherited env is refused, ``MDB_ENV_FORKED`` ([failure points](failure-points.md#lmdb-locks)), so a value not made again is an error at its first cold read, never a read under the parent's reader slot.

## Merges read what changed

A merge decides what merges from the datoms that differ, never by reading whole programs. ```seon.merge/delta-three-way``` takes the datoms that differ between the merge base and each side (`datahike.api/datoms-diff`, which skips every subtree the two trees share by address), the program keys their entities bear on either side (```seon.merge/touched-keys```, or ```seon.merge/touched-by``` over datoms a caller already holds: a form's own key and its definitions', a definition's own and its form's, a schema entry's, declared data), and reads each key's content on base, ours and theirs by index seeks (```seon.merge/program-of```). It answers what `seon.merge/three-way` over three whole programs answers: every case of `seon.merge-test` checks both. The writer's merge and `:branch-diff`, an agent's `merge-main!`, a turn's contract gaps and `seon.merge/unmerged` read this way; ```seon.merge/program``` stays for tests and `mg/check`.

`datoms-diff` between two plain values costs what differs: the children of each branch that differs are compared by one hashed lookup each, the leaves that differ are merged once, and that merge is the answer, with no lookup in either whole set (a branch that buffers edits, which on Jolt none does, adds one), so its work is linear in the entries of the nodes that differ, and grows with the store's size only by the tree's height (`seon.merge-cost-test/a-diff-of-two-commits-costs-the-nodes-that-differ`). When either side is a temporal or filtered db value (as-of, since, history, filtered: it holds no index of its own) it reads each side's `datoms` over the range asked for and merges them once, so it costs the range: a diff from an as-of value is given components that bound it, or it reads every datom of both sides (`datahike.db/datoms-diff`).

What merges is then written as it is (```seon.merge/merge-tx```, ```seon.merge/carried-tx```): the datoms the branch wrote for the keys that merge, with their own entity ids and transaction ids, its retractions first (so a card-one change writes no extra retraction under the merge's transaction), and the facts of the transactions that made them (their instants, their runtime), after the Datahike declarations of the attributes those datoms use that main lacks (`attribute-declarations`). Ids are issued once across the store and identities take [content ids](#ids), so on main they name the same entities and transactions: a merge adds what the branch wrote, never a copy, and the same datom is one datom in every branch's history. Platform records (evaluations, model calls, messages) bear no program key, so they stay where they were written. The writer's octopus merge and an agent's `merge-main!` both merge this way; a conflict's unmerged entry is still written by the merge. Datahike keeps a carried datom's tx (`transact-add`, `transact-retract-datom`). Proof: `seon.merge-test/a-merge-carries-the-branchs-own-datoms`. This deleted the old apply-tx and its five setters (94 lines), which re-transacted each key's content by identity under the merge's transaction.

Measured 2026-10-23 (docs/storage.md): on a 115k-datom main, a merge's three program reads took 6.6 s of 6.7 s. `seon.merge-cost-test/a-three-way-costs-the-changes-not-the-program` holds the three-way flat at about 7 ms from 100 to 10,000 forms, with one form changed on each side. That proof keeps a store on disk, because the in-memory test store gives index nodes no addresses, so a diff there shares nothing and reads everything.

## Main's content mark

Main moves on nearly every request by records that are no program (an agent's status, busy then idle; embeddings, 64 a batch), so a reader of main's content that diffs on each move pays the diff for nothing: an agent's request paid ~3 M ticks of main's content diffs, and a model turn more (measured 2026-11-10). Main's root entity carries a content mark instead, `:seon.root/content-t`: a t past every t main held before the commit that last moved its content. The writer moves it in that same commit (```seon.writer/writer-proc```: a run-ahead commit, a `:flush?` batch, an octopus merge), whenever the commit's resolved datoms touch content (```seon.merge/moves-content?```: an attribute a program key's content reads, or the task content a branch carries), and at its own start, so what a boot wrote before the writer ran (a seed, a catch-up) shares no mark with a branch's older base. So two commits of main with one mark hold the same content, read with two entity reads (```seon.merge/same-content?```): an agent's merge of main and what main changed since its base answer from it with no diff (```seon.agent/merge-main!```, ```seon.agent/main-changes```), and so does the commit that stands for main's program (```seon.merge/content-commit```). A db no writer marked answers false and is diffed, and a merge that declares data reads its diff, since declared data moves no mark. Only main's points are asked: a branch's own writes move no mark. Proofs: `seon.procs-test/the-writer-marks-the-commit-that-moves-mains-content`, `seon.merge-test/same-content-is-read-from-mains-mark`, `seon.agent-test/a-merge-of-a-main-moved-only-by-records-reads-no-content`.

Main's readers in root judge a commit notice by its `:ops`: the test service proves main, and the fork server moves its reach graph, only at a commit that moves the program (```seon.program/moves-program?```); the render and the reconciler read records, so every commit is theirs; the vectors proc still runs a round (one diff since its last) on every commit, its own writes included (task ``seon.vector/a-commit-of-no-text-starts-no-round``).

## The union

Every datom any branch committed is held once in U, one ordinary Datahike db, and queried with plain `d/q`, `d/pull` and `d/entity` over `(d/history U)` (```seon.union```; root: `(my.root/union sys)`). Ids are issued once and identities take content ids ([ids](#ids)), and merges write datoms as they are ([merges](#merges-read-what-changed)), so the union is a set union with nothing to resolve: an equal datom is the same datom. What is true now on one branch stays that branch's head; U answers what happened across branches, and each datom's transaction names its branch (`:seon.tx/branch`, in every transaction's tx-meta, ```seon.db/tx-meta```). U holds assertions in its current indexes and retractions in its temporal ones, and its schema lifts every attribute to cardinality many with no uniqueness (```seon.union/lifted-schema```), since constraints belong to a branch.

Root's writer keeps it: built when first asked (`:union`; main's history, then each branch from its merge base), then every main commit and every agent's commit notice adds that branch's datoms since the commit U holds (```seon.union/catch-up```: the datoms that differ, by `datoms-diff`, with the branch's retractions from its history). No poll: U moves when a commit does.

The owner's example, root's message on main and the agent's reply on its branch, is one query (`seon.union-test/conversation`):

```clojure
(d/q '[:find ?body ?reply ?branch :in $
       :where [?m :seon.message/from "root"] [?m :seon.message/body ?body]
              [?r :seon.message/from "demo/f#1" ?tx] [?r :seon.message/body ?reply] [?tx :seon.tx/branch ?branch]]
     (my.root/union sys))
```

Measured 2026-10-23 (REPL, LMDB, main 46,708 datoms, each branch one turn of ~15 datoms; docs/storage.md):

| | 10 branches | 100 branches |
|---|---|---|
| build: main's history, then each branch | 991 ms | 1,274 ms (about 3 ms a branch) |
| keeping it current: one branch's commit | 0.93 ms | 1.30 ms |
| one agent's conversation | 0.75 ms | 0.63 ms |
| every conversation | 0.87 ms | 4.2 ms (100 evals) |

U lives in root's writer, in memory: about main's history plus what branches add. Persisting it under one store key, so a booted root does not rebuild it, waits until a measurement asks; the rebuild is about 1 s at 50k datoms. Proofs: `seon.union-test/a-message-and-its-reply-on-two-branches-are-one-query`, `seon.procs-test/the-writer-keeps-the-union-current`.

## History

A store keeps history when `:seon.config.store/keep-history?` is true, the default (v1's ruling 23, and Datahike's own default). With history, `d/history`, `as-of` and `since` work, a retraction stays a datom, and a transaction keeps its tx-meta. ``:db/txInstant`` is part of that tx-meta: Datahike applies tx-meta only when history is on, and drops it silently when it is off. The flag is fixed when a store is made (Datahike's `store-fixed-record-keys`). So ```seon.db/made-cfg``` adds it only when a store is created (`seon.db/open!`, and the test store), and ```seon.db/store-cfg``` never names it. A connect adopts what the store recorded, so a store made either way still opens, and keeps the layout it was made with. Proofs: `seon.db-test/the-store-keeps-history`, `seon.db-test/a-kept-store-keeps-the-history-it-was-made-with`.

Every transaction Seon makes names the runtime that made it and its branch in its tx-meta: `:seon.tx/branch` and `:seon.tx/runtime`, the latter Jolt's own key for compiled units (`jolt.host/runtime-fingerprint`: Jolt's version, its runtime fingerprint over the binary's image and Chez's boot files, its trace tag), from ```seon.db/tx-meta```, at the writer's group commit and merges, an agent's transactions and merge-main, and a store's seed. Only the transactions that install the two tx-meta attributes lack them: ```seon.db/install-missing!``` installs those attributes alone, first, in a new store and in a kept one made before them, then every other attribute the store lacks (or holds without its declared `:db/contentId`) in one transaction that carries tx-meta, and answers the attributes it added; nothing missing writes nothing. A branch keeps the schema it was created with, so an agent resuming a kept branch runs it on that branch too, before it loads the branch's program, and writes the program facts its forms were recorded without (```seon.program/gained-tx```: a form cut before `:form/keywords` gains the keys its contract names; the keys its code alone names wait for the form's next analysis). Without it a branch created before an attribute killed its agent at resume, the program's first read of that attribute refused (`seon.root-test/an-agent-resumes-a-branch-cut-before-an-attribute`, `seon.program-test/a-branch-cut-before-form-keywords-gains-them-on-resume`). A runtime Jolt cannot name is refused by `tx-meta`'s contract, never recorded as no runtime. Two inline datoms per transaction (the runtime's is about 90 B). Proofs: `seon.procs-test/the-writers-transactions-name-their-runtime`, `seon.procs-test/a-writers-merge-names-its-runtime`, `seon.agent-test/an-agents-transactions-name-their-runtime`, `seon.agent-test/after-merge-main-the-agent-judges-against-the-new-base` (its merge commit), `seon.db-test/a-kept-store-from-before-the-runtime-attribute-opens`.

Main's transaction facts reach the fork server's replica of main as well, since the replica is main's stored commit itself: the writer sends one notice per stored commit (```seon.writer/stored!```: the commit's id and its transactions' ops, in order), and the fork server, having opened the store after fork as agents do (```seon.db/after-fork!```), loads that commit (`d/commit-as-db`) and runs ```seon.program/load-changes!``` over the ops; nothing is replayed ([ids](#ids)). Proofs: `seon.procs-test/the-fork-servers-replica-is-main-at-each-commit`, `seon.procs-test/the-fork-server-step`.

An agent reads history at its REPL. ```seon.db/history``` answers what an entity's attributes have been, oldest first, as rows `{:a :v :added? :t :at}` read from `d/history` and stored nowhere else; `:attrs` narrows it and `:pull` draws a ref's value as of its row's transaction, so a replaced form shows the text it had. ```seon.db/at``` answers the db at a `:t`, a `:commit` or a `:branch`. A store that keeps none answers `:seon.db/no-history`, and an entity, t, commit or branch it does not hold answers `:seon.db/unresolved`: never an empty history or the nearest point. `my.agent/history` takes a var's symbol as well, and `my.db/at` is the agent's own branch's. A `:t` from a row reads that moment: `(my.db/at {:t t})`.

A transaction's `t` is its id, issued once across the store ([ids](#ids)): a branch's `max-tx` is the id of the last transaction written on it, increasing as the branch is written (so it tells one value of a branch from a later one), and one `t` names one transaction on every branch, so a merged datom keeps the `t` it was written at ([merges](#merges-read-what-changed)). A datom's `t` names its transaction; it does not order transactions: a merge carries a branch's transactions with their own ids and their own times, so on the branch merged into a carried transaction can hold an id and a time below those of one written there before it. What orders transactions is their time, `[:db/txInstant, tx id]` (owner, 2026-11-11, [decisions](decisions.md#ids-are-unique-across-branches-order-by-time-not-by-transaction-id-owner-2026-11-11)). Datahike stamps ``:db/txInstant`` as the later of the wall clock and one millisecond past the instant of the db's last transaction (its `:max-tx`'s; ``datahike.db.transaction/next-tx-instant``), so it strictly increases along the transactions one db line writes. Datahike lets a transaction supply its own ``:db/txInstant`` (upstream's back-dating for imports); Seon's write refuses one ([the write check](#the-write-checks-every-entity-it-touches)), so the store alone stamps time. Across branches compare by commit (`seon.db/branch-base` reads the merge base by commit). v1's merges failed on per-branch ids: 774 ids named different transactions.

Cost:
- Appended turns: the same with history on or off (20 turns: 1,598 vs 1,674 KB uncompressed). Datahike's temporal indexes hold only replaced and retracted datoms, and a turn only adds.
- Replacing one cardinality-one value: 13.5 → 20.7 KB per commit (1.5×), because the commit also writes a path in the temporal `:eavt` and `:aevt`. LZ4: 9.4 → 14.5 KB.

## Compression

konserve compresses every stored value (index nodes, values out of line, commits) with the codec `:seon.config.store/compressor` names: `:zstd` (the default), `:lz4` or `:none`. Each value's header names its codec, so a store holding several kinds reads them all. The codecs are `konserve.jolt.zstd` (libzstd's simple API, one frame per value at level 3) and `konserve.jolt.lz4` (liblz4's frame API), both over `jolt.ffi` in the [konserve fork](forks.md). Their libraries are built from pinned source, never taken from the system: `bin/build zstd` compiles `reference-code/zstd` (the official repository, a submodule at v1.5.7) and `bin/build lz4` the lz4 Chez itself vendors (`reference-code/chez/lz4`), into `target/lib`. `bin/env` exports `JOLT_ZSTD_LIB` and `JOLT_LZ4_LIB`, as it does for LMDB. Proof: `seon.db-test/stored-values-compress-through-the-codecs-the-build-made`.

Measured on data from kept stores, each value compressed by itself as the store does:

| data (median size) | LZ4 | zstd-3 | zstd-19 | zstd-3 with a trained dictionary |
|---|---|---|---|---|
| model replies (0.4 KB) | 1.56× | 2.16× | 2.23× | 4.17× |
| eval records (0.5 KB) | 1.49× | 2.05× | 2.13× | 7.29× |
| source forms (0.5 KB) | 1.45× | 2.02× | 2.08× | 2.92× |
| task plans (0.2 KB) | 1.24× | 1.74× | 1.78× | 2.94× |

On 0.9 KB records, zstd-3 compresses at ~260 MB/s and decompresses at ~580 MB/s (LZ4: 1,330 and 7,550 MB/s). A 2 KB value takes 1–3 µs either way, well under a commit's fsync. On the proof's workload with values out of line, zstd writes 194 KB per 20 per-turn commits, against 233 KB with LZ4, at the same ~1.9 ms a commit. A dictionary trained on our own values compresses small ones 2–5× better, and is faster too. It is not used: it needs a corpus that represents the running system.

## Values out of line

A datom value at least `:seon.config.store/value-out-of-line-bytes` large (1,024, the default; `:never` keeps every value inline) is stored once under its own key inside Datahike's store, and the index nodes hold a reference to it. Datahike's `:index-config :value-out-of-line-bytes` does this in the node storage of [our fork](forks.md), ``datahike.index.persistent-set/CachedStorage``:
- `store` writes a node whose keys hold such values with a `ValueRef` to each value's content key (hasch's uuid of the value, Datahike's own content address), and writes the value once: nothing is written when the store or the commit's queue already holds it. `:eavt` and `:aevt` share one copy.
- `restore` swaps the values back before the node enters the cache, so a live node never holds a reference.
- GC's mark (`mark`, `mark-unseen`) adds the keys each stored node references, so a value lives while a tree reaches it.

The size is a lower bound of the value's serialized size: a string's characters, a collection's elements. Hashing a 2 KB value and asking the store for it each cost about 15–18 µs on Jolt, and a commit rewrites the tail nodes with every large value in them. So the key of a value known to be stored (read back, or found by the store) is kept in the node cache under its datom, whose hash the datom caches. A value only queued for writing is not kept there, so a commit that fails before the write leaves no reference to a value the store lacks. Stored nodes describe themselves, so a store holding both kinds reads either, whatever the config key says now. Proof: `seon.db-test/a-large-value-lives-once-under-its-own-key`.

Thresholds measured at 20 turns with LZ4: 4,096 B moves nothing (a turn's values are 1.5–2.5 KB) and costs 862 KB per turn; 1,024 B costs 237 KB; 256 B costs 223 KB (it also moves the basis, ~400 B). 1,024 is the default: it takes nearly all the gain, and every value it moves is its own LMDB key.

## A run-ahead value shown on the connection

A writer that is its branch's only writer may answer a write when it is applied and store it afterwards. `datahike.writer/apply!` applies a transaction to the connection's run-ahead value without committing; with `{:show? true}` the applied value is also the connection's value, so the next deref reads the write. `commit-pending!` stores the newest value in one commit, however many applies came before; `abandon-pending!` drops them and the connection is the committed value again.

- **A shown value has no commit.** Its `:datahike/commit-id` is nil and `:datahike/uncommitted-parent` names the commit it was applied on (`datahike.writer/shown?`), so a kept reference ([a kept db value is a reference](#a-kept-db-value-is-a-reference)) cannot name a commit that does not hold what was read: whatever needs a commit id waits for the commit.
- **One kind of write at a time.** While a run-ahead is pending, a transact, a batch or a merge on that connection is refused (`:run-ahead-pending`): it would build on the committed value and leave the pending writes out of the branch.
- **The commit is made from the unmarked value**, so the mark is never stored.

Proof: `datahike.test.run-ahead-test` ([forks](forks.md#datahike)).

## What a connection's deref reads

A deref of a connection whose writer does not stream reads the branch's head from the store and builds a db value from it, every time: 58.7k ticks and 259 KB on a store of 7,675 datoms, against 24 ticks for the value the connection already holds (measured 2026-11-10, `datahike.connector/deref-conn`). The read is there so a process sees commits another process made to the branch. A value shown by a run-ahead is answered without it. A `:sync` writer made with `{:writer {:backend :sync :streaming? true}}` answers upstream's `-streaming?` (Datahike `a8887be5`): its connection's deref is the value the connection holds, for a process that is its branch's only writer and so has no other process's commit to see. Seon's own code does not ask for it yet.

## A commit the store refuses

A commit can throw on a value the writes hold: the key of a value out of line is hasch's uuid of it, and hasch had no encoding for `clojure.lang.Ratio`, so a large value holding a ratio (`(mapv #(/ % 3) (range 1 3000))`) threw at its commit while a small one, whose datom is no key, did not (our `jolt-overlay` now encodes it as a number, [forks](forks.md#jolt-overlay); `seon.db-test/a-large-value-holding-ratios-commits-and-reads-back`). Any such value must leave the agent alive, so the commit is the edge ([failure points](failure-points.md)): `seon.agent/commit!` catches the throw, drops the writes applied since the last commit that held (`datahike.writer/abandon-pending!`, which resets the writer's run-ahead value, so the connection's committed value is the truth and the next commit starts from the last good one), resets the agent's `:db` to the committed value (`seon.ctx` patches `@ctx` by the datoms the two values differ by, so the dropped writes leave it too) and answers `:seon.agent/commit-refused`. The agent hears it under `:unrecorded` beside its next eval's answer, and as a message from seon in a model turn: what its code wrote to the branch did not stay, definitions it evaluated are still in the process. Proof: `seon.agent-test/a-commit-the-store-refuses-leaves-the-agent-alive`.

## Plain values

A value that is plain data (a map, vector, set or list of strings, numbers, keywords, symbols, uuids and instants) is stored as data: its attribute is ``:db.type/data`` in [our Datahike](forks.md), and the store's serializer (jfasl) writes it with no text in between. The schema says so by its shape, with no mark: an attribute whose schema is a vector, sequential, tuple, map, map-of, `:any`, or an `:or` whose arms differ in type is plain data (```seon.schema.datahike/declaration``` answers the Datahike attribute map for it, or the `:seon.schema/unstorable` error that says why a schema has none): a model call's basis and split, a task's evidence and failures, an agent's error, the config's maps, merge entries. A vector keeps its order and its duplicates, which cardinality many cannot; a `[:set T]` of scalars or refs stays cardinality many, one datom a member, so a query can join on a member. `datahike.datom/compare-value` gives plain data a total order consistent with `=`, so such values sit in an index like any other. A kept store that holds an attribute as another value type is refused at open with `:seon.db/types-differ`, naming the attributes, because a value type is fixed once installed. Proofs: `seon.db-test/a-kept-store-whose-types-differ-is-refused`, and every test that writes these attributes.

Measured on 5,006 real eval records: jfasl is the same size as EDN text (4.65 vs 4.67 MB). A record reads in 1.3 µs instead of 11 µs and writes in 1.6 µs instead of 14.4 µs, and instants, uuids and keywords come back as themselves. It compresses about 10% less well than EDN text without a dictionary (zstd-3: 1.84× vs 2.05×), 4% less with one.

## Collection

Root collects the store while it is the store's only writer: at quiescence, with no agent live, and only when no other root writes the store. The reconciler asks once per quiet spell (```seon.reconcile/quiet```, which also records the spell on main as `:seon.root/quiescent` and does not await either answer), root refuses while an agent is live (`seon.root/api-proc`, `:collect`), and the writer runs ```seon.db/collect!```:
- When `:seon.config.store/sole-writer?` is false, it sweeps nothing and records nothing (`{:skipped true :shared true}`). The key is false under the `:scripted` profile, which is the profile of bin/test's shards and bin/check's steps, whose roots share one store. Production runs one root per store (task `seon.db/two-processes-branch-one-store-at-once`).
- When a branch named in main's `:seon.root/collected` record is gone, it runs `datahike.api/gc-storage`. A new main with no record yet only records the branches it sees: every check step boots a new main on one store of hundreds of branches, and a full sweep at its first quiescence held its spawns behind root's writer for seconds (`bin/check scale`: 8.2 s to ready). That sweeps every key no branch reaches: nodes, and the values out of line that the mark keeps while a tree reaches them.
- When branches were only added, it records them as seen and sweeps nothing. So a branch that exists at one quiescence and is gone at a later one gets reclaimed.
- The record (`{:swept :ms :branches :gone}`) is committed on main through the writer's batch.
- A sweep only frees pages for LMDB to reuse, and its file never shrinks (221 MB to 249 MB on a kept store), so one that swept anything leaves a mark, and the next boot, before anything opens the store, replaces it by a copy of its pages in use (```seon.db/compact-if-due!```: to 165 MB there, under 200 ms). The rename is atomic, and a copy that fails leaves the store as it was, the error on root's `:boot` view.

Seon's `:sync` writer runs the collection itself, not as a transaction (fork `594815d`). Proofs: `seon.db-test/a-collection-runs-when-a-branch-is-gone`, `seon.db-test/a-root-that-shares-its-store-never-collects`, `seon.db-test/gc-runs-through-the-sync-writer`, `seon.procs-test/a-collection-waits-until-no-agent-is-live`, `seon.reconcile-test/quiescence-is-reported-when-nothing-can-move`.

A long-running store's growth is commit snapshots, as each commit rewrites about 18 nodes, and collecting deleted branches sweeps none of them (0 keys on a kept store of 79,820). So at boot, while root is the only process and nothing live holds an old commit, ```seon.db/retain!``` sweeps what is older than main's newest `:seon.config.store/keep-commits`, when that many commits have reached main since its last sweep, by the commit graph's generation, never a clock, and the freed pages are compacted at once. Each branch's head, its merge base with main and each commit an agent's facts name stay whole. By content checksum on a clone, with a no-sweep control, every branch's head, history and as-of reads were the same after a sweep (57 percent of the keys) and after compaction, and a merge base is found as before, as the commit graph stays ([datahike](forks.md#datahike), `jolt/gc-keep`). A real root on a clone of a kept store merged agents across it, with `keep-commits` at 5: an agent with its branch off generation 324 and its work done before a sweep to about generation 371 resumed, proved and merged, an agent started after it merged too, and both merges stood after a second sweep. The sweep took the file from 422 to 258 MB in 5.4 s, and the next, 64 commits on, swept 2,898 keys and left 256 MB, about 45 keys a commit. A store that sweeps stays near one size: at 1,000 commits between sweeps that is about 45,000 keys a sweep. What goes is reading another old commit by id, which answers nil, so a point in time past the keep is still read exactly as of its `t`, while no commit is left at or before it to fork a new session from: such a point expires ([decisions](decisions.md#a-new-session-starts-at-the-commit-at-or-before-a-point-a-read-is-exact-at-any-transaction-owner-2026-11-11)). A turn's basis holds its `:t` as well as its commit, so the debug page draws a past turn past the keep as of `t`: on real turns of a kept store, byte for byte the request its commit makes. What its branch did since its merge base is a diff of two commits' trees, which a db as of a t cannot read, so that part is left out, and where that shows, the page says the draw differs from what was sent.

**With content-addressed nodes** ([sharing](sharing.md#what-a-branchs-nodes-are)) one node may be named by several branches, by a kept older commit, or by two indexes of one db, so a node is garbage only when nothing reaches it: mark and sweep (`datahike.gc/gc-storage!`, which marks from every branch head and kept commit) is correct as before, and Datahike's online collection, which deletes an address the moment one tree replaces it, stays off (it is off by default and skips a store of more than one branch). The sweep lists the store's keys once, so a commit that writes a node identical to one listed as garbage could lose it: collection stays at quiescence, with root the only writer, as above. What is garbage at all: with history kept a retracted datom is still named by every branch's history, so a collection with no branch gone swept 0 keys; garbage comes from a dropped branch, from commit snapshots past the keep (`retain!`), or from history given up (Datahike's purge). Measured on scratch stores with content keys (2026-11-09): a full mark costs 20 to 32 k ticks a live node, linear and independent of the number of branches (3,805 nodes 97 M ticks; 73,425 nodes 2.3 G ticks, 7.2 s), plus about 1.5 k ticks a stored key to list them; dropping half of 4 branches swept 40 percent of the keys, and compaction then shrank the file 43 to 57 percent. Reference counts would make the mark incremental, at about half again each commit's cost (estimated), so collection stays whole and runs on the events that make garbage.

History is kept, so other garbage comes from deleted branches: check and test mains, which the run that made them deletes (```seon.db/delete-main!```). Measured on a copy of a kept store (297 branches, 159,152 keys), a full collection took 11 s and swept 5,148 keys (3%). On a fresh root's store, a deleted branch was reclaimed at the next quiescence (19 keys, 488 ms).

Why only with no agent live: every commit is one LMDB write transaction (nodes, values, commit record and head), and LMDB's writer lock serializes commits from every process. But a commit can reuse a value out of line that the store held when its node was flushed. A collection running at that moment could sweep the value, because no branch reached it. Collecting concurrently would need a mark outside the lock, then a short delta mark and sweep inside one write transaction, plus commits that re-assert reused values in their own transaction. Collecting beside live agents is not built.

A live agent holds its branch: root refuses a second spawn on a branch a live agent holds, and caps the live agents at `:seon.config.root/max-agents` ([root](root.md#holders-and-refused-spawns)).

Why only as the only writer: Datahike's collection sees the in-flight commits of its own process only (`datahike.gc/gc-storage!`'s safe point). A commit in another process can find a value stored, and then that value is swept before its commit lands. Or its nodes can be written before the cutoff but land after the mark. Neither was reproduced at n = 100 (the store-gc bug note (the store-gc finding, 2026-10-23, not kept in its worktree, not yet on main)). One hole was a real bug, and it is fixed in [our Datahike](forks.md) (`jolt/gc-cache-epoch`). The node cache keeps a value's key under its datom, and that key is trusted only in the collection generation it was found in. `gc-storage!` counts up the store's generation (`datahike.index.interface/collection-key`) after its sweep, so every process asks the store again. Before the fix, an [e a v] reused after a collection (a dropped main's ids are minted again) named a value the sweep had deleted, and its node failed on read with `:value-not-found`. Proof: `datahike.test.gc-value-key-test`.

## Compiled code

The store holds definitions (`:form/src`), never compiled code: a process gets its program compiled by inheriting it (an agent forks the fork server's image, copy-on-write) or by loading forms it lacks: ```seon.program/load-all!``` (every live form a db has that the binary lacks), ```seon.program/load-changes!``` (the forms and removals a merge's resolved tx-data carry, which ```seon.agent/merge-main!``` loads right after its merge commit) and ```seon.program/load-diff!``` (the forms one db has over another, and the removals), and evaluations are records that nothing re-runs. A real form loads in 1.6–5 ms; Jolt's compiled units are 15× their source, hold absolute paths and are valid only under the runtime that compiled them, so they are not stored (task `seon.program/compiled-units-in-the-store` holds the idea). A branch's program at commit C is `d/commit-as-db` at C (0.7–0.9 ms) and `seon.program/load-diff!` to it, from definitions only: code and data definitions restore exactly; host cells (atoms, delays) come back empty and host objects (LMDB, sockets, procs, foreign libraries) are made fresh, as at boot.

An agent's `:base`, against which it chooses the tests that judge its branch, is main at the branch's merge base: the image it forked from, then ```seon.db/branch-base``` after each `seon.agent/merge-main!`. A turn reads what its branch changed since that base once (```seon.agent/branch-changes```: ```seon.merge/delta-changes```, keys compared by content, so a form is one key on every branch, [content ids](#ids)), and its readers project it: ```seon.merge/divergence``` (what the merge carries, `:will-merge`, `my.branch/changes`), ```seon.merge/changed-vars``` (the tests a turn runs, the stale sections), ```seon.merge/uncontracted```. Measured 2026-10-27: the one read is 1.3-1.8 MB from 100 to 10,000 forms, where a turn read the same diff four to six times before (~2.5-3.3 MB), and each later read is one call (```seon.program-cost-test/a-turns-diff-reads-what-the-branch-changed```). The writer's `:spawn` names main's commit and t on `:fork`, and a new agent whose branch or image is elsewhere (```seon.agent/misaligned```) reports `:seon.agent/fork-misaligned` with its hello. The fork server keeps a replica of main, loaded from each stored commit of main ([history](#history)), so an agent forks holding main rather than reading it whole from the store in every process. Proofs: `seon.agent-test/after-merge-main-the-agent-judges-against-the-new-base`, `seon.procs-test/a-fork-names-the-commit-its-agent-starts-at`, `seon.procs-test/a-fork-at-another-commit-is-recorded-misaligned`.

Related: [source](source.md) (merges read a branch's history by commit), [failure points](failure-points.md).

## A renamed attribute

A stored keyword is renamed by erasing the store, never by a migration ([decisions](decisions.md)), so a store made before a rename is refused when it opens: ```seon.db/retired-names``` holds each old name and its new one, and ```seon.db/install-missing!``` throws `:seon.db/name-retired` naming them and changes nothing in the store. Opened instead, it would gain the new attribute with nothing under it, and its next write-back would rewrite each resource from nothing. Proof: `seon.db-test/a-kept-store-on-a-retired-name-is-refused`.
