# Storage

One durable store holds every branch as Datahike index trees in konserve, one content-addressed node per key, on LMDB. A commit costs the nodes it rewrites, so what it writes depends on how values are laid out, whether history is kept, and how nodes are encoded. The store is opened in `seon.db` (`seon.db/open!`, ```seon.db/store-cfg```). Its failure points are in [failure points](failure-points.md), and its config keys (`:seon.config.store/*`) in [config](config.md).

## Identity

A store is named by the id it records, never by where it lies, so a kept run opens wherever it is copied, moved or archived. ```seon.db/store-cfg``` reads the id from the store's `:db` head (```seon.db/stored-id```, Datahike's own read path, 0.8 ms) and mints `(hasch/uuid path)` only for a store it is about to make; Datahike's connect refuses a config whose id differs from the stored one (`:store-identity-mismatch`). A copy keeps its original's id, as a Datahike replica does, so one process opens one of them. With the `:sync` writer, `(:config @conn)` still names the path a store was made at (`datahike.connector/deref-conn` reads the stored config; task `seon.db/deref-keeps-the-connections-config`): use the `:cfg` that ```seon.db/open!``` answers. Proof: `seon.db-test/a-moved-store-opens`.

## The proof: what a commit costs

`seon.db-test/a-commit-costs-what-it-writes` says a turn committed by itself costs what the same turn costs in one big commit, plus one root-to-leaf path per index (32 KB at most). Its turns are realistic: each reply is real prose (the checkout's `docs/`), and each evaluated value is real source (its `src/`). A repeated letter compresses about 3× better than real turn text, which once made LZ4 look like the fix. Sample data must look like production data, or the numbers lie. Twenty turns, LMDB, branching factor 64:

| layout | one commit | per turn | bound | verdict |
|---|---|---|---|---|
| layout | one commit | per turn | bound | per turn / bound |
|---|---|---|---|---|
| values inline, no compression | 178 KB | 1,485 KB | 818 KB | 1.82 |
| values inline, LZ4 | 102 KB | 862 KB | 742 KB | 1.16 |
| out of line from 1,024 B, no compression | 111 KB | 376 KB | 751 KB | 0.50 |
| out of line from 1,024 B, LZ4 (the defaults) | 78 KB | 237 KB | 718 KB | 0.33 |

Inline values were the cause. Every commit rewrites the tail leaf of `:eavt` and `:aevt`, which holds each value inline, so a turn's text was written again by every later commit until its leaf split, and the waste grew with the run. With values inline and LZ4, per-turn cost against the bound is 0.83 at 10 turns, 1.16 at 20 and 1.74 at 40. Out of line it stays near flat: 0.29, 0.33 and 0.41. Every layout commits in about 1.7 ms per turn.

## Entity ids

The entity whose unique attribute holds a value is found by `seon.db/eid`: one seek in that attribute's AVET index, never a Datalog query (a query planned per call cost ~95 µs and 100 KB at 100 tasks). It is the one lookup; every namespace that needs an entity id by value calls it. Reading an entity's facts needs no id first: a pull by lookup ref (`(d/pull db attrs [:seon.root/id :root])`) answers nil when no entity holds the value, so root's facts, a task, an attempt or an error record are pulled directly (session DUP-HELPERS, task ``seon.db/one-entity-id-lookup``).

## Ids

Every entity id and every transaction id is issued once across the whole store: every branch, every process. So a datom names the same entity and the same transaction wherever it travels, onto main by a merge or into a query over several branches. The ids come from one page every process writing the store shares (```seon.db/ids!```, `native/ids.c`): two 64-bit words, the last entity id and the last transaction id issued, mapped from the file `ids` beside `data.mdb` (an anonymous page for a store in memory). A process forked from root (the fork server, an agent, a clone) maps the same page, so it needs nothing at fork. Datahike takes them through its id source (`datahike.ids`, `datahike.writing/set-ids!`):
- a transaction takes its id when it begins, and a branch's t (`:max-tx`) is its last transaction's id: increasing on each branch, with gaps where other branches took ids;
- each fresh entity id is one atomic fetch-add. Measured 2026-10-23: 28-34 ns an id, 200-240 ns with 10 processes contending, 30M ids with none lost or repeated; an LMDB counter key cost 9.6 us alone and ~500 us contended ([notes/global-ids/MEASURED.md](../notes/global-ids/MEASURED.md) §6);
- the page is moved past every branch head's ids when a store opens (O(branches) head reads, once), so an id issued but never committed is a gap, never reused, and a page lost in a crash is rebuilt from the heads;
- an explicit id in tx-data (a carried datom's) moves the page past it.

**Content ids.** An entity with a program identity (`:form/id`, `:var/name`, `:ns/name`, `:method/key`, `:impl/key`, `:schema/key`, `:schema.file/path`: `{:seon.db/content-id true}` in seon.facts.edn, Datahike's `:db/contentId`) takes its id from its identity: `datahike.db.transaction/content-eid`, the hash of `[attribute value]` (hasch's uuid, Datahike's content hash: 17-19 us a call on Jolt, measured 2026-10-23) taken into `[ce0, emax]` = `[2^40, 2^60)`. Every branch that mints one identity mints one entity, so a merge carries its datoms as they are, with no remapping (owner's ruling 2026-10-23; notes/content-eids-2026-10-23.md). The partition, every id a fixnum: counter entity ids below `tx0` (2^29), transaction ids in `[tx0, 2^40)`, content ids above. Datahike mints them before anything resolves (`content-tempids`), so a ref to a tempid made before its entity map takes the content id too, and Seon's minting code is unchanged. An identity names its entity for good: asserting another value of it on that entity, a rename or a hash collision (about 4e-7 at a million identities), is refused `:entity-id/collision`, never merged. `:form/id` itself is now hasch's uuid of the namespace and text (it was Clojure's 32-bit `hash`). Cost, measured 2026-10-23 at 110k datoms: nodes written per commit 0.97x the counter's with 1 new identity, 1.51x with 2 and 4.50x with 10 (commit 3.4 -> 3.9, 3.8 -> 6.7, 8.2 -> 20.2 ms); commits that add no identity write the same. Proofs: `seon.db-test/an-identity-names-its-entity-on-every-branch`, `seon.db-test/content-ids-cost-the-writes-the-model-says`.

A speculation (`d/with`) takes no ids. The fork server's replica of main applies each main commit as main's own transaction t (```seon.db/replay```), so its t is main's. Proofs: `seon.db-test/each-id-is-issued-once-across-branches`, `seon.db-test/a-reopened-store-issues-past-every-head`, and `bin/check ids` (two agents' processes). This replaced per-agent leases of entity ids, whose blocks held about 5,400 agents per store and whose transaction ids were per branch (two branches forked at one t gave their first transactions one id).

## Merges read what changed

A merge decides what merges from the datoms that differ, never by reading whole programs. ```seon.merge/delta-three-way``` takes the datoms that differ between the merge base and each side (`datahike.api/datoms-diff`, which skips every subtree the two trees share by address), the program keys their entities bear on either side (```seon.merge/touched-keys```: a form's own key and its definitions', a definition's own and its form's, a schema entry's, declared data), and reads each key's content on base, ours and theirs by index seeks (```seon.merge/program-of```). It answers what `seon.merge/three-way` over three whole programs answers: every case of `seon.merge-test` checks both. The writer's merge and `:branch-diff`, an agent's `merge-main!`, a turn's contract gaps and `seon.merge/unmerged` read this way; ```seon.merge/program``` stays for tests and `mg/check`.

What merges is then carried as it is (```seon.merge/merge-tx```, ```seon.merge/carried-tx```): the datoms the branch wrote for the keys that merge, with their own entity ids and transaction ids, its retractions first (so a card-one change writes no extra retraction under the merge's transaction), and the facts of the transactions that made them (their instants, their runtime). Ids are issued once across the store and identities take [content ids](#ids), so on main they name the same entities and transactions: a merge adds what the branch wrote, never a copy, and the same datom is one datom in every branch's history. Platform records (turns, evaluations, attempts) bear no program key, so they stay where they were written. The writer's octopus merge and an agent's `merge-main!` both merge this way; a conflict's unmerged entry is still written by the merge. Datahike keeps a carried datom's tx (`transact-add`, `transact-retract-datom`). Proof: `seon.merge-test/a-merge-carries-the-branchs-own-datoms`. This deleted `seon.merge/apply-tx` and its five setters (94 lines), which re-transacted each key's content by identity under the merge's transaction.

Measured 2026-10-23 (notes/global-ids/MEASURED.md §5): on a 115k-datom main, a merge's three program reads took 6.6 s of 6.7 s. `seon.merge-cost-test/a-three-way-costs-the-changes-not-the-program` holds the three-way flat at about 7 ms from 100 to 10,000 forms, with one form changed on each side. That proof keeps a store on disk, because the in-memory test store gives index nodes no addresses, so a diff there shares nothing and reads everything.

## History

A store keeps history when `:seon.config.store/keep-history?` is true, the default (v1's ruling 23, and Datahike's own default). With history, `d/history`, `as-of` and `since` work, a retraction stays a datom, and a transaction keeps its tx-meta. `:db/txInstant` is part of that tx-meta: Datahike applies tx-meta only when history is on, and drops it silently when it is off. The flag is fixed when a store is made (Datahike's `store-fixed-record-keys`). So ```seon.db/made-cfg``` adds it only when a store is created (`seon.db/open!`, and the test store), and ```seon.db/store-cfg``` never names it. A connect adopts what the store recorded, so a store made either way still opens: the standing root's store was made without history, and it keeps that layout. Proofs: `seon.db-test/the-store-keeps-history`, `seon.db-test/a-kept-store-keeps-the-history-it-was-made-with`.

Every transaction Seon makes names the runtime that made it in its tx-meta: `:seon.tx/runtime`, Jolt's own key for compiled units (`jolt.host/runtime-fingerprint`: Jolt's version, its runtime fingerprint over the binary's image and Chez's boot files, its trace tag), from ```seon.db/tx-meta```, at the writer's group commit and merges, an agent's transactions and merge-main, and a store's seed. Only the transaction that installs `:seon.tx/runtime` itself lacks it: ```seon.db/install-missing!``` installs that attribute alone, first, in a new store and in a kept one made before it, and every later transaction carries it. A runtime Jolt cannot name is refused by `tx-meta`'s contract, never recorded as no runtime. One inline datom per transaction (about 90 B). Proofs: `seon.procs-test/the-writers-transactions-name-their-runtime`, `seon.procs-test/a-writers-merge-names-its-runtime`, `seon.agent-test/an-agents-transactions-name-their-runtime`, `seon.agent-test/after-merge-main-the-agent-judges-against-the-new-base` (its merge commit), `seon.db-test/a-kept-store-from-before-the-runtime-attribute-opens`.

Main's transaction facts reach the fork server's replica of main as well. The writer sends each commit's datoms (```seon.db/report->tx```) together with its transaction entity's facts (```seon.db/report->tx-meta```: its instant and any tx-meta), and the fork server applies both as main's own transaction t (```seon.db/replay```, [ids](#ids)). Proof: `seon.procs-test/the-fork-server-step`.

Cost, measured 2026-10-22:
- Appended turns: the same with history on or off (20 turns: 1,598 vs 1,674 KB uncompressed). Datahike's temporal indexes hold only replaced and retracted datoms, and a turn only adds.
- Replacing one cardinality-one value: 13.5 → 20.7 KB per commit (1.5×), because the commit also writes a path in the temporal `:eavt` and `:aevt`. LZ4: 9.4 → 14.5 KB.

## Compression

konserve compresses every stored value (index nodes, values out of line, commits) with the codec `:seon.config.store/compressor` names: `:zstd` (the default), `:lz4` or `:none`. Each value's header names its codec, so a store holding several kinds reads them all. The codecs are `konserve.jolt.zstd` (libzstd's simple API, one frame per value at level 3) and `konserve.jolt.lz4` (liblz4's frame API), both over `jolt.ffi` in the [konserve fork](forks.md). Their libraries are built from pinned source, never taken from the system: `bin/build zstd` compiles `reference-code/zstd` (the official repository, a submodule at v1.5.7) and `bin/build lz4` the lz4 Chez itself vendors (`reference-code/chez/lz4`), into `target/lib`. `bin/env` exports `JOLT_ZSTD_LIB` and `JOLT_LZ4_LIB`, as it does for LMDB. Proof: `seon.db-test/stored-values-compress-through-the-codecs-the-build-made`.

Measured 2026-10-22 on data from the standing root's kept runs, each value compressed by itself as the store does:

| data (median size) | LZ4 | zstd-3 | zstd-19 | zstd-3 with a trained dictionary |
|---|---|---|---|---|
| model replies (0.4 KB) | 1.56× | 2.16× | 2.23× | 4.17× |
| eval records (0.5 KB) | 1.49× | 2.05× | 2.13× | 7.29× |
| source forms (0.5 KB) | 1.45× | 2.02× | 2.08× | 2.92× |
| task plans (0.2 KB) | 1.24× | 1.74× | 1.78× | 2.94× |

On 0.9 KB records, zstd-3 compresses at ~260 MB/s and decompresses at ~580 MB/s (LZ4: 1,330 and 7,550 MB/s). A 2 KB value takes 1–3 µs either way, well under a commit's fsync. On the proof's workload with values out of line, zstd writes 194 KB per 20 per-turn commits, against 233 KB with LZ4, at the same ~1.9 ms a commit. A dictionary trained on our own values compresses small ones 2–5× better, and is faster too. It waits until we have a corpus that represents the running system (owner, 2026-10-22); it would live in the store under its content key, named by each frame.

## Values out of line

A datom value at least `:seon.config.store/value-out-of-line-bytes` large (1,024, the default; `:never` keeps every value inline) is stored once under its own key inside Datahike's store, and the index nodes hold a reference to it. Datahike's `:index-config :value-out-of-line-bytes` does this in the node storage of [our fork](forks.md), `datahike.index.persistent-set/CachedStorage`:
- `store` writes a node whose keys hold such values with a `ValueRef` to each value's content key (hasch's uuid of the value, Datahike's own content address), and writes the value once: nothing is written when the store or the commit's queue already holds it. `:eavt` and `:aevt` share one copy.
- `restore` swaps the values back before the node enters the cache, so a live node never holds a reference.
- GC's mark (`mark`, `mark-unseen`) adds the keys each stored node references, so a value lives while a tree reaches it.

The size is a lower bound of the value's serialized size: a string's characters, a collection's elements. Hashing a 2 KB value and asking the store for it each cost about 15–18 µs on Jolt, and a commit rewrites the tail nodes with every large value in them. So the key of a value known to be stored (read back, or found by the store) is kept in the node cache under its datom, whose hash the datom caches. A value only queued for writing is not kept there, so a commit that fails before the write leaves no reference to a value the store lacks. Stored nodes describe themselves, so a store holding both kinds reads either, whatever the config key says now. Proof: `seon.db-test/a-large-value-lives-once-under-its-own-key`.

Thresholds measured at 20 turns with LZ4: 4,096 B moves nothing (a turn's values are 1.5–2.5 KB) and costs 862 KB per turn; 1,024 B costs 237 KB; 256 B costs 223 KB (it also moves the basis, ~400 B). 1,024 is the default: it takes nearly all the gain, and every value it moves is its own LMDB key.

## Plain values

A value that is plain data (a map, vector, set or list of strings, numbers, keywords, symbols, uuids and instants) is stored as data: its attribute is `:db.type/data` in [our Datahike](forks.md), and the store's serializer (jfasl) writes it with no text in between. Seon marks such an attribute `{:seon.db/data true}` on its schema (```seon.schema.datahike/declaration```): a turn's basis, calls and split, a task's evidence, an attempt's failures and errors, the config's maps, merge entries. `datahike.datom/compare-value` gives plain data a total order consistent with `=`, so such values sit in an index like any other. A kept store that holds an attribute as another value type is refused at open with `:seon.db/types-differ`, naming the attributes, because a value type is fixed once installed. Proofs: `seon.db-test/a-kept-store-whose-types-differ-is-refused`, and every test that writes these attributes.

Measured on 5,006 real eval records: jfasl is the same size as EDN text (4.65 vs 4.67 MB). A record reads in 1.3 µs instead of 11 µs and writes in 1.6 µs instead of 14.4 µs, and instants, uuids and keywords come back as themselves. It compresses about 10% less well than EDN text without a dictionary (zstd-3: 1.84× vs 2.05×), 4% less with one.

## Collection

Root collects the store while it is the store's only writer: at quiescence, with no agent live (owner, 2026-10-22, simplest first). The reconciler asks once per quiet spell (```seon.reconcile/quiet```), root refuses while an agent is live (`seon.root/api-proc`, `:collect`), and the writer runs ```seon.db/collect!```:
- When a branch named in main's `:seon.root/collected` record is gone, it runs `datahike.api/gc-storage`. A new main with no record yet only records the branches it sees: every check step boots a new main on one store of hundreds of branches, and a full sweep at its first quiescence held its spawns behind root's writer for seconds (scale 8.2 s to ready, 2026-10-22). That sweeps every key no branch reaches: nodes, and the values out of line that the mark keeps while a tree reaches them.
- When branches were only added, it records them as seen and sweeps nothing. So a branch that exists at one quiescence and is gone at a later one gets reclaimed.
- The record (`{:swept :ms :branches :gone}`) is committed on main through the writer's batch.

Seon's `:sync` writer runs the collection itself, not as a transaction (fork `594815d`). Proofs: `seon.db-test/a-collection-runs-when-a-branch-is-gone`, `seon.db-test/gc-runs-through-the-sync-writer`, `seon.procs-test/a-collection-waits-until-no-agent-is-live`, `seon.reconcile-test/quiescence-is-reported-when-nothing-can-move`.

With history kept and runs kept, garbage comes from deleted branches: check and test mains, which `seon drop` deletes. Measured 2026-10-22: on a copy of the standing store (297 branches, 159,152 keys), a full collection took 11 s and swept 5,148 keys (3%). On a fresh root's store, a deleted branch was reclaimed at the next quiescence (19 keys, 488 ms).

Why only with no agent live: every commit is one LMDB write transaction (nodes, values, commit record and head), and LMDB's writer lock serializes commits from every process. But a commit can reuse a value out of line that the store held when its node was flushed. A collection running at that moment could sweep the value, because no branch reached it. Collecting concurrently would need a mark outside the lock, then a short delta mark and sweep inside one write transaction, plus commits that re-assert reused values in their own transaction. That is the design to build when collection has to run beside live agents.

## Compiled code

The store holds definitions (`:form/src`), never compiled code: a process gets its program compiled by inheriting it (an agent forks the fork server's image, copy-on-write) or by loading forms it lacks (```seon.program/load-all!```, `load-changes!`, `load-diff!`), and evaluations are records that nothing re-runs. Measured 2026-10-22 (`notes/store-native-2026-10-22.md`): a real form loads in 1.6–5 ms, ~3.6 ms of it compile and 1–2 ms contract arming; a Chez unit loads from bytes in 0.01 ms and is deterministic, but Jolt's units are 15× their source, hold absolute paths and are valid only under the runtime that compiled them, so the owner ruled (2026-10-22): compiled units are not stored now, because forks already inherit compiled code, and the idea stays open (deferred: task `seon.program/compiled-units-in-the-store`). Returning a branch to any commit needs no re-run statements, and that already holds: its program at commit C is `d/commit-as-db` at C (0.7–0.9 ms) and `seon.program/load-diff!` to it, from definitions only. Code and data definitions restore exactly; host cells (atoms, delays) come back empty and host objects (LMDB, sockets, procs, foreign libraries) are made fresh, as at boot; an agent's REPL state outside its definitions is carried only by `clone!` (task `seon.program/a-repl-at-a-commit` is the function, not yet built). An agent's `:base`, against which it chooses the tests that judge its branch, is main at the branch's merge base: the image it forked from, then ```seon.db/branch-base``` after each `seon.agent/merge-main!`. ```seon.program/changed-vars``` compares forms by `:form/id`, which names one entity on every branch ([content ids](#ids)). The writer's `:spawn` names main's commit and t on `:fork`, and a new agent whose branch or image is elsewhere (```seon.agent/misaligned```) reports `:seon.agent/fork-misaligned` with its hello. Proofs: `seon.agent-test/after-merge-main-the-agent-judges-against-the-new-base`, `seon.procs-test/a-fork-names-the-commit-its-agent-starts-at`, `seon.procs-test/a-fork-at-another-commit-is-recorded-misaligned`. The fork server's replica stays: replaying a main commit costs ~1 ms, while reading main whole from the store costs 0.3–0.4 s and its heap in every process (task `seon.agent/an-agents-base-is-its-merge-base`).
