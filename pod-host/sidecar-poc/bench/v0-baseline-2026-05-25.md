# V0 datahike-cljs baseline — Node bench numbers (2026-05-25)

D1 of the sidecar-vs-V0 measurement pair. Numbers from
`pod-host/libdatahike-cljs/`'s existing `bench.cljs` harness running on
Node v24.2.0 / Darwin arm64 / M1 Pro 32GB.

## Setup

- **Node**: v24.2.0
- **OS**: Darwin 24.6.0 / arm64 (M1 Pro)
- **Build**: `pod-host/libdatahike-cljs/out/bench.js` via shadow-cljs `:bench`
- **datahike-cljs**: per `pod-host/libdatahike-cljs/deps.edn`
- **Schema**: `:vault` (5 attrs — `:note/id`, `:note/path`, `:note/text`,
  `:note/created-at`, `:note/tag`)
- **Iterations per measurement**: 5
- **Bulk-load batch**: 1000 entities/tx
- **Tx-batches measured**: 100, 1000

## Run command (verbatim, reproducible)

```bash
cd pod-host/libdatahike-cljs
shadow-cljs compile bench
BENCH_SIZES=1000 \
BENCH_BACKENDS=memory,fs,sqlite-file,tiered-mem-fs \
BENCH_ITERATIONS=5 \
BENCH_TX_BATCHES=100,1000 \
BENCH_BATCH=1000 \
BENCH_OUT=out/bench-v0-baseline-1k.edn \
node out/bench.js
```

Raw EDN: `pod-host/libdatahike-cljs/out/bench-v0-baseline-1k.edn` (47899 bytes).
Raw stdout log: `/tmp/bench-v0-1k.log` (preserved for the run that generated
this report).

## What was attempted but did not work

- **Size 10000 across all backends — Node OOM.** With `--max-old-space-size=8192`
  Node still ran out of heap during `:a-join-query` on the 10000-entity DB
  (the join produces a ~10000×10000 cross product even with the vault
  schema's narrow attr set). This is a real V0 limitation worth flagging:
  full table-cross-join queries on datahike-cljs cannot run on 10k entities
  in the 8GB Node heap. Documented as a caveat below.
- **`:max-query`, `:median-query`** — fail with `Cannot compare [object Object]
  to [object Object]` on the vault schema int variant. This appears to be a
  pre-existing harness bug, not a V0 perf result. Excluded from the tables.
- **`:idb` backend** — not in the default set; skipped by configuration.
- **`:lmdb` backend** — not attempted (not in the bench harness's default
  backend list).

## Backends measured

| Backend | Implementation | Persistence |
|---|---|---|
| `memory` | in-process maps | none (GC'd) |
| `fs` | konserve.node-filestore | one `.ksv` per key on disk |
| `sqlite-file` | konserve-sqlite-cljs over node-sqlite3-wasm | SQLite WAL on disk |
| `tiered-mem-fs` | konserve.memory front + node-filestore back | hot-cache + disk |

All four backends used `:schema-flexibility :write`, `:keep-history? false`,
default `:datahike.index/persistent-set`.

## Bulk-load — N entities at batch 1000

| Backend | Total ms (1k) | Throughput (entities/sec) |
|---|---:|---:|
| memory | 295.3 | 3386 |
| fs | 1317.9 | 759 |
| sqlite-file | 419.2 | 2385 |
| tiered-mem-fs | 322.9 | 3097 |

Single observation (one full load); std=0. Bulk-load is a one-shot
measurement, not a per-iteration distribution.

## Connection time (re-open existing store)

Median over 5 connect calls, ms.

| Backend | median | min | max | std |
|---|---:|---:|---:|---:|
| memory | 4.26 | 0.43 | 12.26 | 4.00 |
| fs | 0.30 | 0.22 | 0.67 | 0.17 |
| sqlite-file | 0.24 | 0.21 | 0.74 | 0.20 |
| tiered-mem-fs | 0.27 | 0.25 | 0.62 | 0.14 |

(`memory` is slower because its connect always re-creates the in-memory
store — there's no persistence to re-attach to. Persistent backends
re-attach to existing on-disk state cheaply.)

## Transaction time — single 100-entity batch vs single 1000-entity batch

Median over 5 iterations, ms. Each entry is one `(d/transact! conn batch)`.

| Backend | tx-100 (ms) | tx-1000 (ms) | per-entity 100 | per-entity 1000 |
|---|---:|---:|---:|---:|
| memory | 71.5 | 615.6 | 0.72 ms | 0.62 ms |
| fs | 188.1 | 754.7 | 1.88 ms | 0.75 ms |
| sqlite-file | 121.1 | 470.4 | 1.21 ms | 0.47 ms |
| tiered-mem-fs | 51.9 | 290.3 | 0.52 ms | 0.29 ms |

Per-entity cost shrinks with batch size for all backends. Tiered-mem-fs is
the throughput winner; in-memory `memory` is slowest here counterintuitively
because index updates dominate when there's no disk amortization to hide
them.

## "Vault" queries — realistic note-store shapes

5 iterations per query; values are median ms.

| Backend | scan-all | scan-by-tag | indexed-by-id | pull-by-path | range-by-time |
|---|---:|---:|---:|---:|---:|
| memory | 8.64 | 20.30 | 0.47 | 0.17 | 7.18 |
| fs | 8.87 | 58.07 | 0.45 | 0.16 | 7.06 |
| sqlite-file | 8.00 | 31.22 | 0.46 | 0.12 | 6.91 |
| tiered-mem-fs | 8.67 | 31.95 | 0.37 | 0.12 | 6.52 |

`indexed-by-id` and `pull-by-path` are sub-millisecond across all four
backends — datahike's btset indexes paying off. `scan-by-tag` is the
worst-case shape (multi-cardinality attr scan); `fs` is materially slower
there than the others, suggesting konserve.file's per-key read cost
dominates when many keys must be touched.

## Joins (size=1000)

| Backend | e-join (med ms) | a-join (med ms) | v-join (med ms) |
|---|---:|---:|---:|
| memory | 19.2 | 4103.8 | 26.6 |
| fs | 58.1 | 8043.2 | 9.0 |
| sqlite-file | 31.3 | 4175.5 | 8.4 |
| tiered-mem-fs | 31.1 | 4006.7 | 8.6 |

`:a-join-query` (join over two attrs of the same kind) is the cross-product
worst case — 4s on 1k entities, would not finish on 10k in 8GB Node heap.
e-join (entity-pivot) is 30ms-ish. v-join (value-pivot, joining two attrs
on equal value) is 8-30ms.

## Predicates (size=1000)

`:equals-query` on a string attr: 500-1500ms across all backends. This is
expected — equality predicates without a fixed value force a full scan.

## Limit + aggregates (size=1000)

| Function | memory | fs | sqlite-file | tiered-mem-fs |
|---|---:|---:|---:|---:|
| limit-query | 7.66 | 7.37 | 7.61 | 7.55 |
| sum-query | 68.91 | 26.61 | 25.67 | 25.21 |
| avg-query | 61.07 | 25.63 | 26.51 | 25.30 |
| variance-query | 143.48 | 27.77 | 27.48 | 27.42 |
| stddev-query | 76.93 | 28.40 | 27.98 | 28.37 |

Aggregates are scan-based — they have to materialize the full attr value
sequence before computing. `memory` is consistently slower because in this
harness `memory` is the only backend whose data isn't index-friendly
amortized (no opportunity for the konserve frontend cache to keep the
index hot — the in-memory backend has no frontend cache).

## Headline observations

1. **Per-entity transaction cost is 0.3-2 ms across backends.** That's
   the real lower bound for V0 — any architecture must beat this or
   accept it. (D2 sidecar tx ranges 33-200ms wall — see comparison doc.)
2. **Single-shape indexed reads (`indexed-by-id`, `pull-by-path`) are
   sub-millisecond.** This is V0's strength: in-process datahike with
   no IPC means each query is a single function call.
3. **Multi-value attr scans (`scan-by-tag`) and full-table joins
   (`a-join-query`) scale poorly.** This is true of datahike on JVM
   too, but matters more in Node because Node's heap pressure under
   join cross-products is harsher.
4. **`tiered-mem-fs` is consistently the fastest persistent backend**
   on writes. Mirrors the upstream finding that tiered stores beat
   plain konserve-file because the frontend cache absorbs read hits.

## Caveats

- **Single host (M1 Pro)** — numbers are aarch64-specific, may differ on x86.
- **No 10k-entity numbers** — Node OOM (see "What was attempted").
- **5 iterations** is small. Reported std/min/max conveys distribution; the
  median is reasonably stable but expect ±20% on individual measurements.
- **Vault schema only** — synthetic mode (`BENCH_SCHEMA=synthetic`) not
  run in this pass; the asymmetries annotation in the EDN documents
  which query shapes change between schemas.
- **No cache** — V0 has no Rust-host snapshot cache; every query is a
  direct datahike call. This is the apples-to-oranges with the sidecar
  bench, where cache hits serve from Rust memory without invoking
  datahike at all.
